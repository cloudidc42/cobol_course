## ขั้นตอนที่ 961: คำถามพื้นฐาน/ไวยากรณ์ (Fundamentals & Syntax)

หมวดนี้คือคำถามที่ผู้สัมภาษณ์ใช้คัดกรองว่าผู้สมัครมีพื้นฐาน COBOL จริงหรือไม่ มักถามในรอบแรกของการ
สัมภาษณ์ทางเทคนิค

### คำถามที่ 961.1: จงอธิบายความแตกต่างระหว่าง `PIC 9(5)`, `PIC S9(5)`, และ `PIC 9(5)V99`

**เฉลย**: `PIC 9(5)` เก็บตัวเลขไม่มีเครื่องหมาย (unsigned) 5 หลัก ตั้งแต่ 00000-99999 `PIC S9(5)`
เพิ่ม `S` ทำให้เก็บเครื่องหมายบวก/ลบได้ (signed) แต่เครื่องหมายไม่ได้กินพื้นที่เก็บข้อมูลเพิ่มเสมอไป
(ขึ้นกับ `USAGE`, ค่าเริ่มต้น `DISPLAY` มักฝังเครื่องหมายไว้ในหลักสุดท้าย) `PIC 9(5)V99` เพิ่ม `V`
(Implied Decimal Point) หมายถึงมีทศนิยม 2 ตำแหน่งที่**ไม่ถูกเก็บเป็นอักขระจริงในหน่วยความจำ** (ต่างจาก
Edited PICTURE ที่ใช้ `.` จริง) โปรแกรมต้องรู้เองว่าตำแหน่งทศนิยมอยู่ตรงไหนผ่าน `V` เท่านั้น (ทบทวน
Part 006)

### คำถามที่ 961.2: `COMPUTE` กับ `ADD`/`SUBTRACT` ต่างกันอย่างไร ควรเลือกใช้เมื่อไหร่

**เฉลย**: `ADD`/`SUBTRACT`/`MULTIPLY`/`DIVIDE` เป็นคำสั่งเลขคณิตพื้นฐานที่ทำการดำเนินการเดียวต่อคำสั่ง
เหมาะกับนิพจน์ง่าย ๆ และอ่านง่ายแบบภาษาอังกฤษ (`ADD A TO B GIVING C`) ส่วน `COMPUTE` รองรับนิพจน์
คณิตศาสตร์ที่ซับซ้อนหลายขั้นตอนในบรรทัดเดียว (`COMPUTE C = (A + B) * D / E`) ในทางปฏิบัติ ทีมพัฒนา
ส่วนใหญ่เลือกใช้ `COMPUTE` เมื่อนิพจน์มีมากกว่า 1 การดำเนินการ เพราะอ่านง่ายกว่าการเขียน `ADD`/`SUBTRACT`
ต่อกันหลายบรรทัด แต่บาง coding standard ขององค์กร (โดยเฉพาะระบบเก่ามาก) นิยมบังคับใช้ `ADD`/`SUBTRACT`
เพราะอ่านง่ายกว่าสำหรับผู้ที่ไม่คุ้นเคยกับนิพจน์คณิตศาสตร์ ทบทวน Part 009

### คำถามที่ 961.3: 88-level Condition Name มีประโยชน์อย่างไร เมื่อเทียบกับการเขียน `IF` เทียบค่าตรง ๆ

**เฉลย**: 88-level (Condition Name) ผูกชื่อที่มีความหมายทางธุรกิจเข้ากับค่าที่เป็นไปได้ของฟิลด์ เช่น

```cobol
       01  WS-POL-STATUS       PIC X(1).
           88  POLICY-ACTIVE           VALUE "A".
           88  POLICY-CANCELLED        VALUE "X".
```

ทำให้เขียน `IF POLICY-ACTIVE` แทน `IF WS-POL-STATUS = "A"` ได้ ประโยชน์หลักคือ **อ่านง่ายขึ้นมาก และ
ถ้าค่าที่แทนความหมายเปลี่ยน (เช่นเปลี่ยนจาก "A" เป็น "1") แก้ที่จุดประกาศ 88-level จุดเดียว ไม่ต้องไล่
แก้ทุก `IF` ในโปรแกรม** ลดความเสี่ยงจากการพิมพ์ literal ผิดด้วย ทบทวน Part 010

### คำถามที่ 961.4: `WORKING-STORAGE SECTION` กับ `LOCAL-STORAGE SECTION` ต่างกันอย่างไร

**เฉลย**: ตัวแปรใน `WORKING-STORAGE` จะคงค่าไว้ตลอดอายุของโปรแกรม (คงอยู่ข้ามการเรียกใช้ถ้าโปรแกรม
ถูกเรียกซ้ำโดยไม่จบการทำงาน) ในขณะที่ `LOCAL-STORAGE` จะถูกสร้างใหม่และตั้งค่าเริ่มต้นใหม่ทุกครั้งที่
โปรแกรมถูกเรียก (คล้ายตัวแปร local ในภาษาสมัยใหม่ที่ scope จำกัดอยู่แค่การเรียกครั้งเดียว) `LOCAL-STORAGE`
มีประโยชน์มากสำหรับโปรแกรมที่ถูกเรียกซ้ำแบบ recursive หรือถูกเรียกจากหลาย thread พร้อมกัน เพื่อป้องกัน
ไม่ให้ค่าจากการเรียกครั้งก่อนหลงเหลือมารบกวนการเรียกครั้งใหม่

### คำถามที่ 961.5: `USAGE COMP` ต่างจาก `USAGE DISPLAY` (ค่าเริ่มต้น) อย่างไร ทำไมถึงสำคัญกับ Performance

**เฉลย**: ทดสอบจริงด้วยโปรแกรมนี้:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO5.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-DISPLAY-NUM      PIC 9(9)      VALUE 123456789.
       01  WS-COMP-NUM         PIC 9(9) COMP VALUE 123456789.

       PROCEDURE DIVISION.
           DISPLAY "DISPLAY FIELD SIZE (BYTES): "
               FUNCTION LENGTH(WS-DISPLAY-NUM)
           DISPLAY "COMP FIELD SIZE (BYTES)   : "
               FUNCTION LENGTH(WS-COMP-NUM)
           DISPLAY "VALUES MATCH  : " WS-DISPLAY-NUM " / " WS-COMP-NUM
           STOP RUN.
```

**ผลลัพธ์จริง**:

```
DISPLAY FIELD SIZE (BYTES): 9
COMP FIELD SIZE (BYTES)   : 4
VALUES MATCH  : 123456789 / 123456789
```

`USAGE DISPLAY` (ค่าเริ่มต้นถ้าไม่ระบุ) เก็บตัวเลขเป็นอักขระ 1 หลักต่อ 1 ไบต์ (9 หลัก = 9 ไบต์)
`USAGE COMP` (Binary/Computational) เก็บเป็นเลขฐานสองที่คอมไพเลอร์บีบอัดให้ใช้พื้นที่น้อยกว่ามาก
(9 หลักในตัวอย่างนี้ใช้เพียง 4 ไบต์) และ**ซีพียูประมวลผลเลขฐานสองได้เร็วกว่าการแปลงจากอักขระทุกครั้ง
ที่คำนวณมาก** ในระบบ Batch ที่ต้องประมวลผลนับล้าน record ต่อคืน การเลือก `COMP` สำหรับฟิลด์ที่ใช้
คำนวณหนัก (ตัวนับ, ตัวแปรสะสม) แทน `DISPLAY` ส่งผลต่อ performance อย่างมีนัยสำคัญ (ทบทวน Part 068
เรื่อง Performance Tuning)

### คำถามที่ 961.6: จงอธิบายว่าทำไมโปรแกรม COBOL ถึงต้องมี Period (`.`) ปิดท้ายประโยค และเกิดอะไรขึ้นถ้าลืม

**เฉลย**: Period ใน COBOL (โดยเฉพาะใน COBOL-74 รุ่นเก่าที่ไม่มี Scope Terminator อย่าง `END-IF`)
ทำหน้าที่ปิดขอบเขตของประโยค (sentence) ถ้าลืมใส่ period ในจุดที่ควรจะมี ผลกระทบจะแตกต่างกันไปตามบริบท
เช่น ถ้าลืม period ท้าย `IF` block ที่ใช้ `END-IF` ปิดอยู่แล้ว มักไม่มีปัญหาเพราะ `END-IF` ทำหน้าที่ปิด
ขอบเขตแทน แต่ในโค้ดรุ่นเก่าที่ไม่มี Scope Terminator การลืม period อาจทำให้คำสั่งถัดไปถูก "ดูดเข้าไป"
เป็นส่วนหนึ่งของเงื่อนไขก่อนหน้าโดยไม่ได้ตั้งใจ ทำให้ตรรกะผิดพลาดแบบที่คอมไพเลอร์ไม่ error แต่ผลลัพธ์
ผิดเงียบ ๆ (ทบทวน Part 003 และ Part 049 เรื่องความแตกต่างของ Dialect)

## ขั้นตอนที่ 962: คำถามโครงสร้างข้อมูลและการจัดการไฟล์ (Data Structures & File Handling)

### คำถามที่ 962.1: `SEARCH` กับ `SEARCH ALL` ต่างกันอย่างไร เมื่อไหร่ควรใช้แบบไหน

**เฉลย**: `SEARCH` ทำ **Linear Search** (ค้นหาทีละตัวจากต้นจนพบหรือหมดตาราง) ใช้ได้กับตารางทุกชนิดไม่
ว่าจะเรียงลำดับหรือไม่ `SEARCH ALL` ทำ **Binary Search** (ค้นหาแบบแบ่งครึ่ง) ซึ่งเร็วกว่ามากสำหรับ
ตารางขนาดใหญ่ แต่**บังคับว่าตารางต้องเรียงลำดับตาม key ที่ระบุใน `ASCENDING KEY`/`DESCENDING KEY`
อยู่แล้วเท่านั้น** ทดสอบจริง:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO6.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-CODE-TABLE.
           05  WS-CODE-ENTRY OCCURS 5 TIMES
                   ASCENDING KEY IS WS-CODE
                   INDEXED BY WS-IDX.
               10  WS-CODE      PIC X(4).
               10  WS-DESC      PIC X(12).
       01  WS-SEARCH-CODE      PIC X(4) VALUE "P003".
       01  WS-FOUND            PIC X(1) VALUE "N".

       PROCEDURE DIVISION.
           MOVE "P001" TO WS-CODE(1)
           MOVE "WIDGET"     TO WS-DESC(1)
           MOVE "P002" TO WS-CODE(2)
           MOVE "GADGET"     TO WS-DESC(2)
           MOVE "P003" TO WS-CODE(3)
           MOVE "BOLT"       TO WS-DESC(3)
           MOVE "P004" TO WS-CODE(4)
           MOVE "CASING"     TO WS-DESC(4)
           MOVE "P005" TO WS-CODE(5)
           MOVE "SCREW"      TO WS-DESC(5)

           SEARCH ALL WS-CODE-ENTRY
               WHEN WS-CODE(WS-IDX) = WS-SEARCH-CODE
                   MOVE "Y" TO WS-FOUND
                   DISPLAY "FOUND " WS-SEARCH-CODE " -> "
                       WS-DESC(WS-IDX)
           END-SEARCH

           IF WS-FOUND = "N"
               DISPLAY "NOT FOUND: " WS-SEARCH-CODE
           END-IF
           STOP RUN.
```

**ผลลัพธ์จริง**: `FOUND P003 -> BOLT`

ถ้าตารางมีข้อมูลไม่เรียงลำดับแล้วใช้ `SEARCH ALL` ผลลัพธ์จะไม่น่าเชื่อถือ (อาจหาไม่เจอทั้งที่มีอยู่จริง)
เพราะ Binary Search อาศัยสมมติฐานเรื่องการเรียงลำดับเป็นพื้นฐานของอัลกอริทึม ทบทวน Part 017

### คำถามที่ 962.2: Indexed File กับ Relative File ต่างกันอย่างไร แต่ละแบบเหมาะกับงานแบบไหน

**เฉลย**: Indexed File ใช้ **key ที่เป็นข้อมูลจริง** (เช่น รหัสลูกค้า, เลขที่กรมธรรม์) ในการค้นหา
ภายในมีโครงสร้างดัชนี (index) ช่วยให้ค้นหาเร็วแม้ key ไม่ต่อเนื่องกัน (มีช่องว่างจากการลบ record)
Relative File ใช้ **เลขลำดับ relative record number (RRN)** ในการเข้าถึงโดยตรง เร็วมากถ้ารู้ตำแหน่ง
ที่ต้องการ แต่**เหมาะกับกรณีที่ key เป็นเลขลำดับต่อเนื่องไม่มีช่องว่างเท่านั้น** เช่น หมายเลขที่นั่ง
เครื่องบินในเที่ยวบินหนึ่ง (1 ถึง 180 ไม่มีข้าม) ถ้า key มีช่องว่างบ่อย (เช่น รหัสลูกค้าที่บางรายถูก
ลบทิ้งไปแล้ว) Indexed File เหมาะสมกว่ามาก ทบทวน Part 028-029

### คำถามที่ 962.3: File Status Code `"23"` กับ `"22"` ต่างกันอย่างไร ควรจัดการอย่างไร

**เฉลย**: `"23"` หมายถึง Record Not Found (พยายามอ่าน/ลบ record ที่ไม่มีอยู่จริงด้วย key ที่ระบุ)
`"22"` หมายถึง Duplicate Key (พยายามเขียน record ที่มี key ซ้ำกับที่มีอยู่แล้ว) ทั้งสองกรณีควรจัดการ
ด้วย `INVALID KEY` clause หรือตรวจสอบ File Status field โดยตรงหลังทุกคำสั่งไฟล์ **ไม่ควรปล่อยให้
โปรแกรมล่ม** — ในระบบธุรกิจจริง `"23"` มักหมายถึงข้อมูลอ้างอิงผิดพลาด (เช่น เลขที่ใบสั่งซื้อที่พิมพ์ผิด)
ซึ่งควร log แล้วข้ามไปประมวลผลรายการถัดไป ไม่ใช่หยุดทั้ง batch job ทบทวน Part 030

### คำถามที่ 962.4: Composite Key ในไฟล์ Indexed คืออะไร ใช้เมื่อไหร่

**เฉลย**: Composite Key คือการรวมหลายฟิลด์เข้าด้วยกันเป็น key เดียว เช่น รหัสคลัง+รหัสสินค้า
(ทบทวน Part 095 ขั้นตอนที่ 941) ใช้เมื่อการระบุ record หนึ่งตัวต้องอาศัยมากกว่าหนึ่งฟิลด์ประกอบกัน
เช่น สต๊อกสินค้าที่ต้องแยกตามทั้งคลังและรหัสสินค้าพร้อมกัน ลำดับของฟิลด์ในการประกอบ key มีผลต่อลำดับ
การเรียงข้อมูลเมื่ออ่านแบบ sequential ด้วย (ฟิลด์ที่มาก่อนจะเป็น "กลุ่มหลัก" ของการเรียงลำดับ)

### คำถามที่ 962.5: `OCCURS DEPENDING ON` คืออะไร แก้ปัญหาอะไร

**เฉลย**: `OCCURS DEPENDING ON` (ODO) ทำให้จำนวนสมาชิกของตารางเป็น**ตัวแปร** ไม่ใช่ค่าคงที่ตายตัว
เช่น `05 WS-ITEM OCCURS 1 TO 100 TIMES DEPENDING ON WS-ITEM-COUNT` แก้ปัญหากรณีที่ record มีจำนวน
รายการย่อยไม่แน่นอน (เช่น ใบสั่งซื้อหนึ่งใบอาจมี 1 ถึง 100 รายการสินค้า) โดยไม่ต้องจองพื้นที่สูงสุด
เสมอ (ประหยัดพื้นที่เมื่อรายการจริงน้อยกว่าค่าสูงสุดมาก) ข้อควรระวังคือ `WS-ITEM-COUNT` ต้องถูกกำหนด
ค่าที่ถูกต้อง**ก่อน**เข้าถึงตารางเสมอ ไม่เช่นนั้นอาจเข้าถึงพื้นที่นอกขอบเขตที่จัดสรรจริง

## ขั้นตอนที่ 963: คำถามโครงสร้างโปรแกรมและการควบคุมการทำงาน (Control Flow & Program Structure)

### คำถามที่ 963.1: `PERFORM paragraph-name THRU paragraph-name-2` ทำงานอย่างไร ต่างจาก `PERFORM paragraph-name` เฉย ๆ อย่างไร

**เฉลย**: `PERFORM A THRU C` จะรันย่อหน้า A แล้วรันต่อเนื่องไปเรื่อย ๆ ตามลำดับที่เขียนไว้ในโปรแกรม
จนถึงและรวมย่อหน้า C (ไม่ใช่แค่ A กับ C สองย่อหน้าเท่านั้น แต่รวมทุกย่อหน้าที่**อยู่ระหว่างกลาง**ตาม
ลำดับการเขียนโค้ดด้วย) ในขณะที่ `PERFORM A` เฉย ๆ จะรันแค่ย่อหน้า A เพียงย่อหน้าเดียว เทคนิคนี้มีความ
เสี่ยงถ้ามีการเพิ่มย่อหน้าใหม่แทรกกลางระหว่าง A กับ C ในภายหลังโดยไม่ตั้งใจ เพราะย่อหน้าใหม่นั้นจะถูก
รันไปด้วยโดยอัตโนมัติแม้จะไม่ได้ตั้งใจให้เป็นส่วนหนึ่งของ THRU block — coding standard สมัยใหม่จำนวนมาก
จึงแนะนำให้หลีกเลี่ยง `THRU` แล้วใช้ `PERFORM` เรียกทีละย่อหน้าแยกกันชัดเจนแทน ทบทวน Part 014

### คำถามที่ 963.2: `CALL...BY REFERENCE` กับ `BY CONTENT` กับ `BY VALUE` ต่างกันอย่างไร

**เฉลย**: `BY REFERENCE` (ค่าเริ่มต้น) ส่ง**ที่อยู่หน่วยความจำ** ของตัวแปรไปให้ subprogram ทำให้
subprogram แก้ไขค่าแล้วสะท้อนกลับมาที่โปรแกรมเรียกได้ (คล้าย pass-by-reference ในภาษาอื่น) `BY CONTENT`
ส่ง**สำเนาค่า ณ ขณะนั้น** ไปให้ subprogram ใช้ แต่การแก้ไขค่าภายใน subprogram**ไม่สะท้อนกลับ**มาที่
ตัวแปรต้นทาง `BY VALUE` (มาตรฐาน COBOL รุ่นใหม่กว่า คล้าย `BY CONTENT` แต่มีข้อจำกัดเพิ่มเติมและมักใช้
เมื่อเรียกโปรแกรมที่ไม่ใช่ COBOL เช่น C ผ่าน `CALL` ทบทวน Part 072) การเลือกใช้ผิดประเภทเป็นสาเหตุบั๊ก
ที่พบบ่อยมาก เช่น ตั้งใจจะให้ subprogram แก้ไขค่ากลับมาแต่ดันใช้ `BY CONTENT` ทำให้ค่าที่โปรแกรมหลัก
เห็นไม่เปลี่ยนแปลงเลย ทบทวน Part 032

### คำถามที่ 963.3: `EVALUATE TRUE` มีประโยชน์อย่างไรเมื่อเทียบกับ `IF...ELSE IF` ที่ซ้อนกันหลายชั้น

**เฉลย**: `EVALUATE TRUE` ทำให้ตรวจสอบเงื่อนไขที่**ไม่เกี่ยวข้องกันโดยตรง**หลายเงื่อนไขได้อย่างเป็น
ระเบียบ อ่านง่ายกว่า `IF...ELSE IF` ที่ซ้อนกันลึกหลายชั้นมาก (nested IF ที่ลึกเกิน 3-4 ชั้นมักอ่านยาก
และแก้ไขเสี่ยงต่อการพลาด) รูปแบบ `WHEN condition-1 ... WHEN condition-2 ...` ของ `EVALUATE TRUE` ทำให้
เงื่อนไขแต่ละอันอยู่ในระดับเดียวกันทางสายตา (indentation เท่ากัน) ต่างจาก nested IF ที่ระดับ indentation
ลึกขึ้นเรื่อย ๆ ตามจำนวนเงื่อนไข ตัวอย่างการใช้จริงคือตรรกะ cascade การพิจารณาเคลมใน Part 094 ขั้นตอน
ที่ 935-936 ที่ตรวจสอบ 5 เงื่อนไขตามลำดับด้วย `EVALUATE TRUE` แทนที่จะซ้อน `IF` 5 ชั้น

### คำถามที่ 963.4: `DECLARATIVES` กับ `USE` Statement คืออะไร แก้ปัญหาอะไร

**เฉลย**: `DECLARATIVES` เป็นส่วนพิเศษท้าย `PROCEDURE DIVISION` ที่ให้กำหนด**ตรรกะจัดการ error ของ
ไฟล์แบบรวมศูนย์**ผ่าน `USE ... ON ERROR`/`USE AFTER STANDARD ERROR PROCEDURE` แทนที่จะต้องตรวจสอบ
File Status หลังทุกคำสั่ง `READ`/`WRITE` ด้วยตนเองซ้ำ ๆ ทุกจุดในโปรแกรม ประโยชน์คือ **รวมจุดจัดการ
error ไว้ที่เดียว** ทำให้บำรุงรักษาง่ายขึ้นเมื่อต้องเปลี่ยนวิธีจัดการ error (เช่น เปลี่ยนจาก log อย่าง
เดียวเป็น log พร้อมส่ง alert) ไม่ต้องไล่แก้ทุกจุดในโปรแกรม ทบทวน Part 048

### คำถามที่ 963.5: Nested Program คืออะไร ต่างจาก Subprogram ที่เรียกผ่าน `CALL` แบบธรรมดาอย่างไร

**เฉลย**: Nested Program คือโปรแกรมที่ถูกประกาศ**ภายใน**โปรแกรมหลักโดยตรง (ใช้ `END PROGRAM` คั่น)
ทำให้ scope ของตัวแปรใน `WORKING-STORAGE` ของโปรแกรมแม่สามารถถูกมองเห็นได้จากโปรแกรมลูกที่ซ้อนอยู่ข้างใน
(ถ้าประกาศถูกต้องตามกฎ) ต่างจาก Subprogram แยกไฟล์ที่ถูก `CALL` แบบธรรมดา ซึ่งมี scope ของตัวแปรแยก
จากกันอย่างสมบูรณ์ ต้องส่งผ่านค่าทาง parameter เท่านั้น Nested Program เหมาะกับกรณีที่ logic ย่อยนั้น
**ใช้เฉพาะภายในโปรแกรมแม่เท่านั้น ไม่มีการใช้ซ้ำที่อื่น** ในขณะที่ Subprogram แยกไฟล์เหมาะกับ logic
ที่ต้องใช้ซ้ำจากหลายโปรแกรม ทบทวน Part 034

## ขั้นตอนที่ 964: คำถามเชิง Debugging (พร้อมบั๊กจริงที่คอมไพล์และรันแล้ว)

หมวดนี้แตกต่างจากหมวดอื่น: ทุกคำถามแสดง**บั๊กจริงที่เกิดขึ้นจากการคอมไพล์และรันจริง** ไม่ใช่การอธิบาย
เชิงทฤษฎีเฉย ๆ เพราะคำถามแนว Debugging ในการสัมภาษณ์จริงมักให้ดูโค้ดที่มีปัญหาแล้วถามว่า "จะเกิดอะไรขึ้น"

### คำถามที่ 964.1: โค้ดนี้จะแสดงผลอะไร และทำไม

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO1.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-BIG-AMOUNT       PIC 9(7)V99 VALUE 123456.78.
       01  WS-SMALL-AMOUNT     PIC 9(3)V99.

       PROCEDURE DIVISION.
           MOVE WS-BIG-AMOUNT TO WS-SMALL-AMOUNT
           DISPLAY "BIG AMOUNT   : " WS-BIG-AMOUNT
           DISPLAY "SMALL AMOUNT : " WS-SMALL-AMOUNT
           STOP RUN.
```

**ผลลัพธ์จริง**:

```
BIG AMOUNT   : 0123456.78
SMALL AMOUNT : 456.78
```

**เฉลย**: `WS-SMALL-AMOUNT` มี `PIC 9(3)V99` (รองรับแค่ 3 หลักก่อนจุดทศนิยม) แต่ `WS-BIG-AMOUNT` มี
ค่า 123456.78 (6 หลักก่อนทศนิยม) เมื่อ `MOVE` COBOL จะ**ตัดหลักที่มีนัยสำคัญสูงสุด (high-order digits)
ทิ้งอย่างเงียบ ๆ โดยไม่ error หรือเตือนอะไรเลยตอน runtime** ผลลัพธ์ที่ได้คือ 456.78 (เก็บเฉพาะ 3 หลัก
ท้ายสุดก่อนทศนิยม) ซึ่งเป็นค่าที่**ผิดอย่างสิ้นเชิง**เมื่อเทียบกับค่าจริง นี่คือบั๊กที่อันตรายมากในระบบ
การเงินเพราะไม่มี error ให้เห็นเลย ข้อคิดสำคัญ: **ต้องตรวจสอบว่าฟิลด์ปลายทางมีขนาดใหญ่พอเสมอก่อน MOVE
ข้อมูลตัวเลขที่มีขนาดต่างกัน** หรือใช้ `ON SIZE ERROR` ร่วมกับ `COMPUTE` เพื่อดักจับกรณีนี้แทนการ `MOVE`
ตรง ๆ เมื่อไม่แน่ใจขนาดของข้อมูล

### คำถามที่ 964.2: โค้ดนี้มีปัญหาอะไร และทำไมการคอมไพล์แบบปกติถึงไม่แจ้งเตือน

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO2.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-TABLE.
           05  WS-ITEM OCCURS 5 TIMES PIC 9(3).
       01  WS-GUARD            PIC X(3) VALUE "SAFE".
       01  WS-IDX              PIC 9(2).

       PROCEDURE DIVISION.
           PERFORM VARYING WS-IDX FROM 1 BY 1 UNTIL WS-IDX > 6
               MOVE 111 TO WS-ITEM(WS-IDX)
           END-PERFORM
           DISPLAY "GUARD AFTER LOOP: " WS-GUARD
           STOP RUN.
```

**ผลลัพธ์จริงเมื่อคอมไพล์แบบปกติ** (`cobc -x -o demo2 demo2.cob`):

```
GUARD AFTER LOOP: SAF
```

**ผลลัพธ์จริงเมื่อคอมไพล์ด้วย `-debug`** (`cobc -x -debug -o demo2c demo2.cob`):

```
libcob: demo2.cob:12: error: subscript of 'WS-ITEM' out of bounds: 6
	maximum subscript for 'WS-ITEM': 5
```

**เฉลย**: `WS-ITEM` มีแค่ 5 ช่อง (index 1-5) แต่ลูปเขียนไปถึง index 6 (`UNTIL WS-IDX > 6` หมายความว่า
loop ทำงานตอน WS-IDX = 1,2,3,4,5,6) เมื่อ index 6 ถูกใช้ COBOL จะเขียนข้อมูลลงในหน่วยความจำที่**อยู่
ถัดจากตารางไปทันที** ซึ่งบังเอิญเป็นตำแหน่งของ `WS-GUARD` ทำให้ค่า "SAFE" ถูกเขียนทับกลายเป็น "SAF"
โดยที่**คอมไพเลอร์แบบปกติไม่ตรวจสอบขอบเขต subscript เลยตอน runtime** (เพื่อความเร็วสูงสุด) นี่คือ
เหตุผลที่ subscript ออกนอกขอบเขตเป็นหนึ่งในบั๊กที่**อันตรายที่สุด**ใน COBOL เพราะไม่มี error ชัดเจน
มีแต่ข้อมูลข้างเคียงที่เสียหายอย่างเงียบ ๆ การคอมไพล์ด้วย flag `-debug` (เปิด runtime error checking
ทั้งหมด) จะช่วยตรวจจับปัญหานี้ได้ระหว่างการพัฒนาและทดสอบ ซึ่งเป็นแนวทางปฏิบัติที่ดีที่ควรใช้เสมอในช่วง
Testing ก่อนขึ้น Production (แม้ Production build มักปิด flag นี้เพื่อความเร็ว)

### คำถามที่ 964.3: โค้ดนี้ให้ผลลัพธ์ที่ผิดพลาดทางธุรกิจอย่างไร ทั้งที่คอมไพล์และรันผ่านไม่มี error

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO3.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-COVERAGE         PIC 9(7)V99 VALUE 100000.00.
       01  WS-CLAIMS-PAID      PIC 9(7)V99 VALUE 150000.00.
       01  WS-REMAINING-BAD    PIC 9(7)V99.
       01  WS-REMAINING-GOOD   PIC S9(7)V99.

       PROCEDURE DIVISION.
           COMPUTE WS-REMAINING-BAD = WS-COVERAGE - WS-CLAIMS-PAID
           COMPUTE WS-REMAINING-GOOD = WS-COVERAGE - WS-CLAIMS-PAID
           DISPLAY "UNSIGNED RESULT (WRONG): " WS-REMAINING-BAD
           DISPLAY "SIGNED RESULT (RIGHT)  : " WS-REMAINING-GOOD
           IF WS-REMAINING-BAD <= 0
               DISPLAY "UNSIGNED CHECK: EXHAUSTED - NOT REACHED"
           ELSE
               DISPLAY "UNSIGNED CHECK: STILL HAS COVERAGE - WRONG"
           END-IF
           IF WS-REMAINING-GOOD <= 0
               DISPLAY "SIGNED CHECK: COVERAGE EXHAUSTED - CORRECT"
           ELSE
               DISPLAY "SIGNED CHECK: STILL HAS COVERAGE"
           END-IF
           STOP RUN.
```

**ผลลัพธ์จริง**:

```
UNSIGNED RESULT (WRONG): 0050000.00
SIGNED RESULT (RIGHT)  : -0050000.00
UNSIGNED CHECK: STILL HAS COVERAGE - WRONG
SIGNED CHECK: COVERAGE EXHAUSTED - CORRECT
```

**เฉลย**: วงเงินคุ้มครอง 100,000 แต่จ่ายสินไหมไปแล้ว 150,000 (สมมติสถานการณ์ที่ข้อมูลผิดพลาดสะสมมา)
ผลต่างที่แท้จริงคือ **-50,000** (ติดลบ) แต่ `WS-REMAINING-BAD` ประกาศเป็น `PIC 9(7)V99` (ไม่มี `S`
นำหน้า คือ unsigned) ทำให้ COBOL เก็บ**ค่าสัมบูรณ์**ของผลลัพธ์แทน กลายเป็น 50,000.00 (ค่าบวก) ซึ่งทำให้
เงื่อนไข `IF WS-REMAINING-BAD <= 0` ไม่เป็นจริง โปรแกรมจึงเข้าใจผิดว่า "ยังมีวงเงินคุ้มครองเหลืออยู่"
ทั้งที่ความจริงวงเงินคุ้มครองหมดไปนานแล้ว นี่คือบั๊กเชิงตรรกะทางธุรกิจที่ร้ายแรงมาก เพราะระบบจะยังคง
**อนุมัติจ่ายสินไหมเพิ่มต่อไปได้อีก** ทั้งที่ไม่ควรจะเป็นเช่นนั้น ข้อคิดสำคัญ: **ฟิลด์ใดก็ตามที่มีโอกาส
ได้ผลลัพธ์ติดลบจากการคำนวณ (แม้ในทางธุรกิจไม่ควรติดลบก็ตาม) ต้องประกาศเป็น Signed (`S9...`) เสมอ
เพื่อให้ตรวจจับความผิดปกติได้ถูกต้อง** อ้างอิงเทคนิคนี้จาก Part 094 ขั้นตอนที่ 935 ที่ใช้ `PIC S9(9)V99`
สำหรับ `WS-REMAINING-COVERAGE` โดยเฉพาะเพราะเหตุผลนี้

### คำถามที่ 964.4: ทำไมสองบรรทัดนี้ให้ผลลัพธ์ต่างกัน ทั้งที่คำนวณนิพจน์เดียวกัน

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO4.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-TOTAL            PIC 9(5)V99 VALUE 100.00.
       01  WS-PARTS            PIC 9(3)    VALUE 7.
       01  WS-SHARE-TRUNC      PIC 9(5)V99.
       01  WS-SHARE-ROUNDED    PIC 9(5)V99.

       PROCEDURE DIVISION.
           COMPUTE WS-SHARE-TRUNC = WS-TOTAL / WS-PARTS
           COMPUTE WS-SHARE-ROUNDED ROUNDED = WS-TOTAL / WS-PARTS
           DISPLAY "SHARE (TRUNCATED, NO ROUNDED) : " WS-SHARE-TRUNC
           DISPLAY "SHARE (WITH ROUNDED)          : " WS-SHARE-ROUNDED
           STOP RUN.
```

**ผลลัพธ์จริง**:

```
SHARE (TRUNCATED, NO ROUNDED) : 00014.28
SHARE (WITH ROUNDED)          : 00014.29
```

**เฉลย**: 100.00 หาร 7 ได้ 14.2857142... ซึ่งมีทศนิยมมากกว่าที่ `PIC 9(5)V99` (2 ตำแหน่งทศนิยม) จะ
เก็บได้ ถ้าไม่ระบุ `ROUNDED` COBOL จะ**ตัดทิ้ง (truncate)** ทศนิยมส่วนเกินไปตรง ๆ ได้ 14.28 แต่ถ้าระบุ
`ROUNDED` COBOL จะปัดเศษตามหลักคณิตศาสตร์ (ปัดขึ้นเพราะทศนิยมตำแหน่งที่ 3 คือ 5 ซึ่ง >= 5) ได้ 14.29
ซึ่งใกล้เคียงค่าจริงมากกว่า ในระบบการเงินที่ต้องแบ่งเงินคืนลูกค้าหรือคำนวณดอกเบี้ยจำนวนมาก **การลืม
`ROUNDED` สะสมความคลาดเคลื่อนเล็กน้อยในแต่ละรายการ ซึ่งเมื่อรวมนับล้านรายการอาจกลายเป็นยอดเงินที่ต่าง
กันอย่างมีนัยสำคัญ** (ปัญหานี้เรียกว่า "penny rounding problem" ที่เป็นที่รู้จักกันดีในวงการระบบการเงิน)
ควรตรวจสอบกับฝ่ายธุรกิจ/บัญชีเสมอว่าการคำนวณแต่ละจุดควรปัดเศษแบบใด (ปัดขึ้น/ปัดลง/ปัดตามหลักคณิตศาสตร์)
แล้วใช้ `ROUNDED` หรือ `ROUNDED MODE IS` (มาตรฐานใหม่กว่าที่ระบุรูปแบบการปัดเศษเฉพาะเจาะจงได้) ให้ตรง
ตามข้อกำหนดทางธุรกิจเสมอ

## ขั้นตอนที่ 965: คำถามด้านประสิทธิภาพและการปรับแต่ง (Performance & Optimization)

### คำถามที่ 965.1: ทำไม `SEARCH ALL` (Binary Search) ถึงเร็วกว่า `SEARCH` (Linear Search) มาก และเร็วกว่าเท่าไหร่โดยประมาณ

**เฉลย**: Linear Search ต้องตรวจสอบโดยเฉลี่ย N/2 รายการสำหรับตารางขนาด N (เลวร้ายสุดคือ N รายการ)
Binary Search ตรวจสอบเพียง log2(N) รายการ เพราะแบ่งครึ่งตารางทิ้งทีละรอบ สำหรับตารางขนาด 1,000,000
รายการ Linear Search อาจต้องตรวจสอบเฉลี่ย 500,000 รายการ ในขณะที่ Binary Search ตรวจสอบเพียงประมาณ
20 รายการเท่านั้น (log2(1,000,000) ≈ 20) ความแตกต่างนี้มีผลกระทบมหาศาลกับ batch job ที่ต้องค้นหาตาราง
ซ้ำ ๆ นับล้านครั้งต่อการรันหนึ่งครั้ง แต่ต้องแลกด้วยข้อกำหนดว่าตารางต้องเรียงลำดับไว้ก่อนเสมอ (ทบทวน
คำถามที่ 962.1)

### คำถามที่ 965.2: ทำไมการอ่านไฟล์ Indexed แบบสุ่ม (Random Access) ถึงช้ากว่าการอ่านแบบลำดับ (Sequential Access) แม้จะเป็นไฟล์เดียวกัน

**เฉลย**: การอ่านแบบ Sequential อ่าน record ต่อเนื่องกันตามลำดับที่จัดเก็บจริงในดิสก์ ซึ่งเป็นรูปแบบ
การเข้าถึงข้อมูลที่ดิสก์ (และ Operating System cache) ทำงานได้มีประสิทธิภาพสูงสุด (sequential I/O)
ส่วนการอ่านแบบสุ่มด้วย key แต่ละครั้งอาจต้องกระโดดไปอ่านตำแหน่งที่ต่างกันมากในดิสก์ (random I/O) ซึ่ง
ช้ากว่ามากโดยเฉพาะกับ Hard Disk Drive แบบจานหมุน (แม้ SSD จะลดผลกระทบนี้ลงมาก แต่ยังคงมี overhead
จากการค้นหาผ่านโครงสร้างดัชนีอยู่ดี) นี่คือเหตุผลที่โปรแกรม batch ที่ต้องประมวลผล record จำนวนมาก
(เช่น `STMTGEN` ใน Part 070 หรือ `POLRENEW` ใน Part 094) นิยมเปิดไฟล์ด้วย `ACCESS MODE IS SEQUENTIAL`
และประมวลผลตามลำดับที่จัดเก็บจริง แทนที่จะวนอ่านทีละ key แบบสุ่ม แม้จะทำได้ทั้งสองแบบก็ตาม

### คำถามที่ 965.3: การเลือก `USAGE COMP`/`COMP-3` แทน `USAGE DISPLAY` ช่วยเรื่อง Performance อย่างไร (นอกจากประหยัดพื้นที่)

**เฉลย**: นอกจากประหยัดพื้นที่ (ดูคำถามที่ 961.5) การคำนวณเลขฐานสอง (`COMP`) หรือ Packed Decimal
(`COMP-3`) โดยตรงยังเร็วกว่าการคำนวณด้วยข้อมูลแบบ `DISPLAY` (ที่เก็บเป็นอักขระ) เพราะซีพียูไม่ต้อง
แปลงข้อมูลจากรูปแบบอักขระเป็นเลขฐานสองก่อนคำนวณทุกครั้ง (implicit conversion overhead) ในระบบ Batch
ขนาดใหญ่ที่มีการคำนวณหนัก ๆ (เช่น `BATCHINT` คำนวณดอกเบี้ยทุกบัญชีใน Part 070) การเลือกชนิดข้อมูลที่
เหมาะสมสำหรับฟิลด์ที่ใช้คำนวณบ่อยที่สุดสามารถลดเวลาประมวลผลรวมได้อย่างมีนัยสำคัญเมื่อคูณด้วยจำนวน
record ที่มหาศาล

### คำถามที่ 965.4: ทำไมการเปิด-ปิดไฟล์ซ้ำ ๆ ในลูปถึงเป็นปัญหาด้าน Performance ยกตัวอย่างจากหลักสูตรนี้

**เฉลย**: การ `OPEN`/`CLOSE` ไฟล์เป็นการดำเนินการระดับระบบปฏิบัติการ (system call) ที่มี overhead
สูงกว่าการดำเนินการในหน่วยความจำมาก ถ้าเปิด-ปิดไฟล์ซ้ำในลูปที่รันหลายพัน/หมื่นครั้ง overhead นี้จะสะสม
กลายเป็นปัญหา performance ที่ชัดเจน ตัวอย่างจากหลักสูตรนี้คือ `PORDER` ใน Part 095 ขั้นตอนที่ 943 ที่
**จงใจอ่านไฟล์ตัวนับ (`POCTL.DAT`) เพียงครั้งเดียวตอนเริ่มโปรแกรม เก็บไว้ในหน่วยความจำ แล้วบันทึกกลับ
เพียงครั้งเดียวตอนจบ** แทนที่จะเปิด-ปิดไฟล์ตัวนับทุกครั้งที่สร้างใบสั่งซื้อหนึ่งใบ ซึ่งจะช้ากว่ามากถ้า

### คำถามที่ 966.1: JCL คืออะไร ทำไมโปรแกรม COBOL บน Mainframe ถึงรันตรง ๆ ไม่ได้ ต้องผ่าน JCL ก่อน

### คำถามที่ 966.2: VSAM KSDS ต่างจาก Indexed File ที่ทดสอบด้วย GnuCOBOL ในหลักสูตรนี้อย่างไร

**เฉลย**: ทั้งคู่ใช้แนวคิดพื้นฐานเดียวกัน (จัดเก็บและค้นหา record ผ่าน key) แต่ VSAM KSDS มีรายละเอียด
เฉพาะของ Mainframe ที่ GnuCOBOL ISAM handler (Berkeley DB) ไม่มี เช่น Alternate Index (ดัชนีรองที่
ให้ค้นหาด้วยฟิลด์อื่นนอกจาก primary key ได้), การแยก Data Component กับ Index Component อย่างชัดเจน,
แนวคิด CI (Control Interval) และ CA (Control Area) ที่ส่งผลต่อการจัดสรรพื้นที่และ performance,
และการจัดการ Cluster ที่ผูก Data/Index เข้าด้วยกัน สิ่งที่หลักสูตรนี้ทำคือใช้ Indexed File ของ
GnuCOBOL เป็น**ตัวแทนแนวคิด**เพื่อให้ทดสอบได้จริง แต่ผู้ที่จะทำงานกับ VSAM จริงต้องศึกษารายละเอียด
เพิ่มเติมเหล่านี้ ทบทวน Part 055-056

### คำถามที่ 966.3: Pseudo-conversational Programming ใน CICS คืออะไร ทำไมถึงสำคัญ

**เฉลย**: ในระบบ CICS ที่รองรับผู้ใช้จำนวนมากพร้อมกัน การให้แต่ละ transaction "ค้างรอ" การกดปุ่มถัดไป
ของผู้ใช้ (แบบ conversational เต็มรูปแบบ) จะกิน memory และทรัพยากรของระบบไว้นานเกินจำเป็น เพราะผู้ใช้
อาจใช้เวลาคิดนานก่อนกดปุ่มถัดไป Pseudo-conversational Programming แก้ปัญหานี้โดยให้ transaction
**จบการทำงานและคืนทรัพยากรทั้งหมดทันที**หลังส่งหน้าจอกลับไปให้ผู้ใช้ แล้วเมื่อผู้ใช้กดปุ่มถัดไป ระบบจะ
เริ่ม transaction ใหม่ที่ดึงข้อมูลสถานะที่บันทึกไว้ (ผ่าน COMMAREA) กลับมาทำงานต่อราวกับเป็นการสนทนา
ต่อเนื่อง ทำให้ระบบรองรับผู้ใช้จำนวนมากพร้อมกันได้อย่างมีประสิทธิภาพสูงสุดโดยไม่เปลืองทรัพยากรเกินจำเป็น
ทบทวน Part 064

### คำถามที่ 966.4: Cursor ใน DB2 ใช้ทำอะไร ทำไม COBOL ถึงต้องใช้ Cursor ในขณะที่ SQL ทั่วไปไม่จำเป็นต้องมี

**เฉลย**: คำสั่ง SQL แบบ `SELECT` ปกติคืนผลลัพธ์เป็น**ชุดข้อมูลหลายแถวพร้อมกัน (result set)** แต่ COBOL
เป็นภาษาที่ประมวลผลทีละ record (record-at-a-time) ไม่มีแนวคิดเรื่อง "ชุดข้อมูล" แบบธรรมชาติเหมือน SQL
Cursor จึงเป็นกลไกเชื่อมสองโลกนี้เข้าด้วยกัน: มันทำหน้าที่เหมือน "ตัวชี้" ที่ให้ COBOL `FETCH` ผลลัพธ์
จาก SQL query ออกมาทีละแถว ประมวลผลแถวนั้นเสร็จแล้วค่อย `FETCH` แถวถัดไป วนไปจนหมด ทำให้ COBOL
ประมวลผลผลลัพธ์จาก SQL ได้ในรูปแบบที่สอดคล้องกับธรรมชาติของภาษา (ทีละ record) ทบทวน Part 059

## ขั้นตอนที่ 967: คำถามด้าน COBOL สมัยใหม่และการเชื่อมต่อระบบ (Modern COBOL & Integration)

### คำถามที่ 967.1: จะเชื่อมต่อโปรแกรม COBOL กับระบบภายนอกที่สื่อสารด้วย JSON ได้อย่างไร ถ้าคอมไพเลอร์ที่ใช้ไม่รองรับ `JSON GENERATE`/`JSON PARSE`

**เฉลย**: มาตรฐาน COBOL-2014 กำหนด `JSON GENERATE`/`JSON PARSE` ไว้ แต่ compiler บางตัว/บาง build
(รวมถึง GnuCOBOL build ที่ใช้ทดสอบส่วนใหญ่ในหลักสูตรนี้ ตามที่ Part 045 พิสูจน์ไว้) ไม่ได้เปิดใช้งาน
JSON library ในกรณีนี้สามารถสร้าง/แยกวิเคราะห์ JSON ด้วยมือผ่าน `STRING`/`UNSTRING`/`FUNCTION TRIM`
ได้ ทดสอบจริง:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DEMO7.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-CUST-ID          PIC X(6)  VALUE "C00042".
       01  WS-CUST-NAME        PIC X(20) VALUE "JANE DOE".
       01  WS-CUST-BALANCE     PIC 9(7)V99 VALUE 1500.50.
       01  WS-BALANCE-EDITED   PIC ZZZZZZ9.99.
       01  WS-JSON-OUT         PIC X(200).

       PROCEDURE DIVISION.
           MOVE WS-CUST-BALANCE TO WS-BALANCE-EDITED
           STRING '{"custId":"' DELIMITED BY SIZE
                  FUNCTION TRIM(WS-CUST-ID) DELIMITED BY SIZE
                  '","name":"' DELIMITED BY SIZE
                  FUNCTION TRIM(WS-CUST-NAME) DELIMITED BY SIZE
                  '","balance":' DELIMITED BY SIZE
                  FUNCTION TRIM(WS-BALANCE-EDITED) DELIMITED BY SIZE
                  '}' DELIMITED BY SIZE
               INTO WS-JSON-OUT
           DISPLAY "JSON: " FUNCTION TRIM(WS-JSON-OUT)
           STOP RUN.
```

**ผลลัพธ์จริง**: `JSON: {"custId":"C00042","name":"JANE DOE","balance":1500.50}`

จุดสำคัญคือต้อง `MOVE` ฟิลด์ตัวเลขไปยัง Edited PICTURE (`PIC ZZZZZZ9.99`) ก่อน แล้วค่อย `TRIM` เพื่อให้
ได้ตัวเลขที่มีจุดทศนิยมจริงและไม่มีเลขศูนย์นำหน้าที่ไม่จำเป็น (ตาม convention ของ JSON) การ `TRIM`
ฟิลด์ตัวเลขแบบ unedited (`PIC 9...V99`) ตรง ๆ จะไม่ได้ผลลัพธ์ที่ถูกต้อง เพราะเลขศูนย์นำหน้าไม่ใช่
ช่องว่างที่ `TRIM` จะตัดออกให้ ทบทวนแนวทางนี้อย่างละเอียดใน Part 045

### คำถามที่ 967.2: ทำไมการห่อหุ้ม (wrap) โปรแกรม COBOL ด้วย REST API ถึงเป็นที่นิยมมากกว่าการเขียนใหม่ทั้งหมด (Rewrite)

### คำถามที่ 967.3: การทำ Unit Test สำหรับโปรแกรม COBOL มีความท้าทายอะไรที่ต่างจากภาษาสมัยใหม่

มากกว่าคำตอบสำเร็จรูป

### คำถามที่ 968.1: จงออกแบบกระบวนการกระทบยอดข้อมูลแบบ Batch (Batch Reconciliation Process) ระหว่างระบบบัญชีสองระบบที่ควรมียอดรวมตรงกัน

**แนวทางคำตอบที่ดี**: เริ่มจากถามคำถามเพื่อความชัดเจนก่อนเสมอ (เช่น "ข้อมูลจากสองระบบมาในรูปแบบไฟล์
หรือฐานข้อมูล", "ต้องกระทบยอดระดับ record หรือแค่ยอดรวม"), จากนั้นเสนอโครงสร้าง:

```
   ระบบ A (ต้นทาง)         ระบบ B (ปลายทาง)
        |                        |
        v                        v
   Extract ไฟล์ A          Extract ไฟล์ B
        |                        |
        +----------+-------------+
                   v
              SORT ทั้งสองไฟล์ด้วย key เดียวกัน
                   |
                   v
         Master-Detail Matching
         (อ่านทั้งสองไฟล์พร้อมกัน เทียบ key)
                   |
        +----------+-----------+
        v          v           v
   ตรงกัน      มีใน A         มีใน B
   (matched)   ไม่มีใน B      ไม่มีใน A
               (A-only)       (B-only)
                   |
                   v
         รายงานผลต่าง + ยอดควบคุม (Control Total)
```

องค์ประกอบสำคัญที่ควรกล่าวถึง: **(1) การ SORT ทั้งสองไฟล์ด้วย key เดียวกันก่อนเสมอ** (ทบทวน Part 027
เรื่อง SORT/MERGE), **(2) เทคนิค Master-Detail Matching** เพื่อจับคู่ record ที่ตรงกันและแยกที่ไม่ตรง
กันออกมา (ทบทวน Part 026 และ Part 070 เรื่อง `RECONCILE`), **(3) Control Total** (ยอดรวมและจำนวน
record ของแต่ละไฟล์ก่อนเริ่มกระทบยอด) เพื่อตรวจสอบตั้งแต่ต้นว่าข้อมูลนำเข้าถูกต้องครบถ้วน ไม่ใช่กระทบ
ยอด record ต่อ record ไปเรื่อย ๆ โดยไม่มีจุดตรวจสอบภาพรวม, และ **(4) การจัดการ tolerance** (ผลต่าง
เล็กน้อยที่ยอมรับได้จากการปัดเศษ อาจไม่ควรถือเป็นข้อผิดพลาดที่ต้องรายงาน) คำตอบที่ดีควรอ้างอิงถึง
โปรแกรม `RECONCILE` ใน Part 070 ขั้นตอนที่ 699 ที่เป็นตัวอย่างการทำ Control Total Reconciliation จริง

### คำถามที่ 968.2: จงออกแบบระบบที่ต้องประมวลผลไฟล์ธุรกรรมขนาด 50 ล้าน record ภายในหน้าต่างเวลา (batch window) 4 ชั่วโมงทุกคืน จะออกแบบอย่างไรให้ทันเวลา

**แนวทางคำตอบที่ดี**: ประเด็นสำคัญที่ควรพูดถึง: (1) **เลือกชนิดข้อมูลที่มีประสิทธิภาพ** (`COMP`/
`COMP-3` แทน `DISPLAY` สำหรับฟิลด์คำนวณหนัก ทบทวนคำถามที่ 965.3), (2) **ลด Random I/O ให้มากที่สุด**
โดยจัดเรียง (SORT) ไฟล์ธุรกรรมให้อยู่ในลำดับเดียวกับ Master File ก่อนประมวลผล แล้วอ่านทั้งสองไฟล์แบบ
Sequential พร้อมกัน (Master-Detail Matching) แทนการอ่าน Master File แบบสุ่มทีละ record (ทบทวนคำถาม
ที่ 965.2), (3) **พิจารณาแบ่งงานเป็นส่วนย่อยที่ทำขนานกันได้ (parallelization)** ถ้าข้อมูลสามารถแบ่ง
ตามช่วง key ได้อย่างอิสระ (เช่น แบ่งตามช่วงเลขบัญชี รันหลาย job พร้อมกัน), (4) **วัดผลก่อนปรับแต่ง
เสมอ** อย่าเดาว่าจุดไหนช้า ให้วัดเวลาจริงของแต่ละขั้นตอนก่อนตัดสินใจว่าจะปรับแต่งส่วนไหน (ทบทวนหลักการ
นี้จาก Part 068 เรื่อง Performance Tuning) คำตอบที่ดีควรแสดงว่าผู้ตอบเข้าใจว่า "การปรับแต่ง performance
ที่ดีที่สุดคือการลดจำนวนครั้งของการดำเนินการที่แพงที่สุด (มักเป็น I/O) ไม่ใช่แค่เขียนโค้ดให้กระชับขึ้น"

### คำถามที่ 968.3: จงออกแบบวิธีเพิ่มฟิลด์ใหม่เข้าไปใน Record ของไฟล์ Master ขนาดใหญ่ที่มีโปรแกรมอื่นอีก 15 โปรแกรมใช้ Copybook เดียวกันอยู่ โดยไม่ทำให้ระบบเดิมพัง

**แนวทางคำตอบที่ดี**: ประเด็นสำคัญคือ **ต้องเพิ่มฟิลด์ใหม่ต่อท้าย (append) เสมอ ไม่ใช่แทรกกลาง**
เพราะโปรแกรมเดิมทั้ง 15 โปรแกรมอ้างอิงตำแหน่ง (offset) ของฟิลด์เดิมตาม Copybook เวอร์ชันเก่า ถ้าแทรก
ฟิลด์ใหม่กลางโครงสร้าง จะทำให้ตำแหน่งของฟิลด์ที่อยู่ถัดจากจุดแทรกเลื่อนไปทั้งหมด และโปรแกรมเดิมที่ยัง
ไม่ได้คอมไพล์ใหม่ด้วย Copybook เวอร์ชันใหม่จะอ่านข้อมูลผิดตำแหน่งทันที (โดยไม่มี error ให้เห็นเลย
เหมือนปัญหาที่ Part 031 ขั้นตอนที่ 304 สาธิตไว้) ขั้นตอนที่ปลอดภัยคือ: (1) เพิ่มฟิลด์ใหม่ต่อท้ายสุดของ
Copybook, (2) กำหนดค่าเริ่มต้น (`VALUE`) ที่เหมาะสมสำหรับ record เก่าที่ยังไม่มีค่าในฟิลด์นี้ (หรือ
เขียนโปรแกรม conversion แยกต่างหากเพื่อเติมค่าเริ่มต้นให้ทุก record ที่มีอยู่แล้ว), (3) คอมไพล์ทั้ง
15 โปรแกรมใหม่ด้วย Copybook เวอร์ชันใหม่พร้อมกัน (ไม่ใช่ทยอยทำทีละโปรแกรม เพราะจะมีช่วงที่บางโปรแกรม
ใช้ Copybook เก่าบางโปรแกรมใช้ใหม่พร้อมกัน เสี่ยงต่อการอ่าน record ผิดโครงสร้าง), และ (4) ทดสอบให้
ครบทั้ง 15 โปรแกรมก่อน deploy จริง คำตอบที่ดีควรแสดงความเข้าใจว่า**การเปลี่ยนแปลงโครงสร้างข้อมูลที่
ใช้ร่วมกันหลายโปรแกรมเป็นหนึ่งในการเปลี่ยนแปลงที่มีความเสี่ยงสูงที่สุดในระบบ COBOL Legacy**

## ขั้นตอนที่ 969: คำถามเชิงพฤติกรรมและสถานการณ์เฉพาะของงาน Legacy System

### คำถามที่ 969.1: คุณได้รับมอบหมายให้แก้บั๊กในโปรแกรม COBOL ที่ไม่มีเอกสารประกอบเลย และคนที่เขียนดั้งเดิมเกษียณไปแล้ว 10 ปี คุณจะเริ่มต้นอย่างไร

**แนวทางคำตอบที่ดี**: แสดงกระบวนการที่เป็นระบบ ไม่ใช่ "อ่านโค้ดทั้งหมดตั้งแต่บรรทัดแรก" ซึ่งไม่สมจริง
สำหรับโปรแกรมขนาดใหญ่ แนวทางที่ดีกว่า: (1) หาก่อนว่าบั๊กเกิดขึ้น**เมื่อไหร่และในสถานการณ์ใด** (reproduce
ปัญหาให้ได้ก่อนเสมอ), (2) ใช้ `PROCEDURE DIVISION` เป็นแผนที่ (มักมีชื่อย่อหน้าที่สื่อความหมาย แม้จะ
ไม่มีเอกสาร) ไล่ตามลำดับการทำงานจากจุดเริ่มโปรแกรมจนถึงจุดที่คาดว่าเกี่ยวข้องกับบั๊ก, (3) เพิ่ม
`DISPLAY` ชั่วคราว (หรือใช้เครื่องมือ debug ถ้ามี) เพื่อตรวจสอบค่าตัวแปรในจุดที่สงสัย, (4) เปรียบเทียบ
ค่าที่คาดหวังกับค่าจริงทีละจุดจนพบตำแหน่งที่ค่าเริ่มผิด, (5) **ก่อนแก้ไขใด ๆ ให้เขียน test case ที่
reproduce บั๊กได้ก่อนเสมอ** เพื่อยืนยันว่าการแก้ไขได้ผลจริงและไม่ทำให้เคสอื่นพัง คำตอบที่ดีควรแสดงความ
อดทนและวิธีคิดที่เป็นระบบ เพราะนี่คือสถานการณ์ที่**เกิดขึ้นจริงบ่อยมาก**ในงาน COBOL Legacy

### คำถามที่ 969.2: คุณพบว่าโค้ดที่เพื่อนร่วมทีมเขียนมีปัญหาการออกแบบที่ร้ายแรง (เช่น ไม่ตรวจสอบ File Status เลย) แต่ระบบใช้งานมาหลายปีแล้วไม่มีปัญหา คุณจะจัดการสถานการณ์นี้อย่างไร

**แนวทางคำตอบที่ดี**: คำตอบที่ดีควรแสดงความสมดุลระหว่างความรอบคอบทางเทคนิคกับการสื่อสารที่สร้างสรรค์
ไม่ใช่แค่ "รีบไปแก้เอง" หรือ "เงียบไว้เพราะไม่ใช่เรื่องของฉัน" แนวทางที่ดี: (1) เข้าใจก่อนว่าทำไมโค้ด
เดิมถึง "ดูเหมือนไม่มีปัญหา" มานาน (อาจเป็นเพราะสถานการณ์ที่จะทำให้เกิดปัญหายังไม่เคยเกิดขึ้นจริง เช่น
ไฟล์ที่อ้างอิงไม่เคยหายไปเลยในรอบหลายปีที่ผ่านมา ไม่ได้แปลว่าจะไม่เคยหายในอนาคต), (2) ประเมินความเสี่ยง
และผลกระทบทางธุรกิจถ้าปัญหานี้เกิดขึ้นจริง (เช่น ถ้าเป็นระบบที่กระทบเงินลูกค้า ความเสี่ยงสูงกว่าระบบ
รายงานภายใน), (3) นำเสนอปัญหาอย่างสร้างสรรค์ต่อทีม พร้อมข้อเสนอแก้ไขที่ชัดเจน แทนการตำหนิ, (4) ถ้า
การแก้ไขมีความเสี่ยงสูง (กระทบระบบที่ใช้งานมานาน) ควรเสนอแผนทดสอบที่รัดกุมก่อน deploy พร้อมแผนสำรอง
(rollback plan) เสมอ

### คำถามที่ 969.3: ทำไมคุณถึงอยากเรียน/ทำงานสาย COBOL ในยุคที่เทคโนโลยีสมัยใหม่มีให้เลือกมากมาย

**แนวทางคำตอบที่ดี**: นี่คือคำถามเชิงแรงจูงใจที่ผู้สัมภาษณ์ใช้ประเมินว่าผู้สมัครเข้าใจความจริงของ
อุตสาหกรรมนี้หรือไม่ คำตอบที่ดีควรสะท้อนความเข้าใจที่ลึกซึ้งกว่า "เพราะมีคนขาดแคลน เงินเดือนดี" เพียง
อย่างเดียว (แม้จะเป็นความจริงส่วนหนึ่งตามที่ Part 001 อธิบายไว้) ควรผสมกับความเข้าใจในคุณค่าที่แท้จริง
ของงานนี้ เช่น "ระบบที่ผมดูแลกระทบชีวิตคนนับล้าน ความรับผิดชอบและความท้าทายทางเทคนิคของการรักษาระบบ
ที่มั่นคงและแม่นยำสูงสุดในขณะที่ต้องปรับตัวให้ทันโลกสมัยใหม่ เป็นสิ่งที่ผมสนใจมากกว่าการเขียนแอปใหม่
ที่อาจถูกแทนที่ด้วยเทรนด์ใหม่ในอีกไม่กี่ปี" — คำตอบที่ดีควรมีความเฉพาะตัวและแสดงว่าผู้สมัครได้ไตร่ตรอง
มาจริง ไม่ใช่คำตอบท่องจำทั่วไป

## ขั้นตอนที่ 970: สถานการณ์จำลองการสัมภาษณ์แบบเต็มรูปแบบ (Mock Interview Capstone)

### สถานการณ์จำลอง: การสัมภาษณ์ตำแหน่ง COBOL Developer ระดับ Mid-level

ต่อไปนี้คือชุดคำถามที่ออกแบบให้ต่อเนื่องกันเหมือนการสัมภาษณ์จริงหนึ่งรอบ ประมาณ 45-60 นาที ครอบคลุม
ทั้งเทคนิคและการออกแบบ ลองจับเวลาตัวเองตอบแต่ละข้อโดยไม่เปิดเอกสารดู

**คำถามที่ 1 (Warm-up)**: แนะนำตัวและเล่าถึงโปรเจกต์ COBOL ที่คุณภูมิใจที่สุด

*สิ่งที่ผู้สัมภาษณ์มองหา*: ความสามารถในการอธิบายงานทางเทคนิคให้เข้าใจง่าย และความลึกซึ้งของความเข้าใจ
ในโปรเจกต์ที่เลือกพูดถึง — ควรเลือกพูดถึง Case Study ที่ซับซ้อนที่สุดที่ทำในหลักสูตรนี้ (เช่น Part 094
หรือ Part 095) พร้อมอธิบายเหตุผลการออกแบบ ไม่ใช่แค่ท่องรายการเทคนิคที่ใช้

**คำถามที่ 2 (เทคนิคพื้นฐาน)**: อธิบายว่าทำไม `PIC 9(7)V99` ถึงเหมาะกับการเก็บจำนวนเงินมากกว่า
Floating-Point

จะเลือก Organization แบบไหนของไฟล์ และทำไม

แล้วถามว่า "โค้ดนี้จะพิมพ์อะไรออกมา และทำไม"

**คำถามที่ 8 (พฤติกรรม/ปิดท้าย)**: มีคำถามอะไรอยากถามเราไหม

*คำแนะนำ*: อย่าตอบว่า "ไม่มีครับ/ค่ะ" เตรียมคำถามที่แสดงความสนใจจริงจัง เช่น "ทีมนี้ใช้ COBOL dialect
ไหน (GnuCOBOL/IBM Enterprise/Micro Focus)", "ระบบปัจจุบันมีแผน Modernization อย่างไรในอีก 2-3 ปีข้างหน้า",
หรือ "ทีมมีกระบวนการ Code Review และ Testing สำหรับการเปลี่ยนแปลงระบบ Legacy อย่างไร" — คำถามเหล่านี้
แสดงว่าคุณคิดถึงบริบทการทำงานจริง ไม่ใช่แค่ต้องการได้งาน

### เคล็ดลับสุดท้ายสำหรับวันสัมภาษณ์จริง

1. **เตรียมเครื่องมือให้พร้อมถ้าเป็นการสัมภาษณ์แบบเขียนโค้ดสด**: ถ้าเป็นไปได้ ขอทดสอบว่าสภาพแวดล้อม
   การเขียนโค้ดที่ใช้ในการสัมภาษณ์ (มักเป็น shared editor ออนไลน์) รองรับ COBOL syntax highlighting
   หรือไม่ ถ้าไม่รองรับก็ไม่ต้องกังวล เพราะผู้สัมภาษณ์ทราบข้อจำกัดนี้ดีอยู่แล้ว
2. **พูดกระบวนการคิดออกมาดัง ๆ เสมอ**: โดยเฉพาะคำถาม Debugging และ System Design ผู้สัมภาษณ์สนใจ
   วิธีคิดมากกว่าคำตอบสุดท้ายเพียงอย่างเดียว การเงียบคิดในใจนานแล้วตอบคำตอบสุดท้ายทีเดียวทำให้ผู้
   สัมภาษณ์ประเมินกระบวนการคิดของคุณไม่ได้เลย
3. **ยอมรับอย่างตรงไปตรงมาถ้าไม่รู้คำตอบ**: ในสายงาน Legacy System ไม่มีใครรู้ทุกอย่าง การตอบว่า
   "ผมไม่เคยเจอสถานการณ์นี้มาก่อน แต่ผมคิดว่าน่าจะลองตรวจสอบ... " แสดงถึงความซื่อสัตย์และกระบวนการคิด
   ที่ดี ดีกว่าการเดาสุ่มแบบไม่มีเหตุผลรองรับมาก
4. **เชื่อมโยงคำตอบกลับไปยังโปรเจกต์จริงที่คุณทำเสมอเมื่อทำได้**: แทนที่จะตอบเชิงทฤษฎีล้วน ๆ ให้อ้างอิง
   ถึงประสบการณ์จริงจากโปรเจกต์ในหลักสูตรนี้ ("ผมเจอปัญหาคล้ายกันตอนทำ Case Study ระบบประกันภัย ตอนนั้น
   ผมแก้ด้วยวิธี...") ซึ่งแสดงให้เห็นว่าคุณมีประสบการณ์ลงมือทำจริง ไม่ใช่แค่ท่องทฤษฎี

## สรุปท้ายบท

ใน Part นี้ เราได้รวบรวมคลังคำถามสัมภาษณ์งาน COBOL Developer ที่ครอบคลุมทุกระดับความยาก:

- **พื้นฐาน/ไวยากรณ์** (ขั้นตอนที่ 961): PICTURE Clause, 88-level, COMP vs DISPLAY
- **โครงสร้างข้อมูลและไฟล์** (ขั้นตอนที่ 962): SEARCH/SEARCH ALL, Indexed/Relative File, Composite Key
- **โครงสร้างโปรแกรม** (ขั้นตอนที่ 963): PERFORM THRU, CALL parameter passing, EVALUATE, DECLARATIVES
- **Debugging** (ขั้นตอนที่ 964): 4 บั๊กจริงที่คอมไพล์และรันแล้ว (truncation, subscript overflow,
  signed/unsigned, rounding)
- **Performance** (ขั้นตอนที่ 965): Binary vs Linear Search, Sequential vs Random I/O, COMP/COMP-3
- **Mainframe** (ขั้นตอนที่ 966): JCL, VSAM, CICS Pseudo-conversational, DB2 Cursor
- **COBOL สมัยใหม่** (ขั้นตอนที่ 967): JSON แบบ manual, REST API Wrapper, Unit Testing, Docker
- **ออกแบบระบบ** (ขั้นตอนที่ 968): Batch Reconciliation, Performance ระดับ 50 ล้าน record, การเปลี่ยน
  Record Layout อย่างปลอดภัย
- **พฤติกรรม/สถานการณ์ Legacy** (ขั้นตอนที่ 969): การแก้บั๊กในโค้ดไม่มีเอกสาร, การจัดการความขัดแย้งเชิง
  เทคนิคในทีม, แรงจูงใจในการทำงานสาย COBOL
- **Mock Interview เต็มรูปแบบ** (ขั้นตอนที่ 970): สถานการณ์จำลอง 8 คำถามต่อเนื่องพร้อมเคล็ดลับปิดท้าย

คุณได้เดินทางผ่านหลักสูตร COBOL แบบครบวงจร 97 Part แล้ว ตั้งแต่ประวัติศาสตร์และเหตุผลที่ COBOL ยังคง
