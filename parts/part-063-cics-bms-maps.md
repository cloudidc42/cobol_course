# Part 063: CICS BMS Maps และการออกแบบหน้าจอ (ขั้นตอนที่ 621–630)

## คำนำของ Part นี้

Part 061 แนะนำแนวคิดพื้นฐานของ CICS ในฐานะ Transaction Processing Monitor และ Part 062 พาเราไปรู้จัก
คำสั่งพื้นฐานที่โปรแกรม COBOL ใช้คุยกับหน้าจอเทอร์มินัล 3270 ผ่าน `EXEC CICS SEND` และ
`EXEC CICS RECEIVE` แต่ถ้าสังเกตดี ๆ ตัวอย่างใน Part 062 ยังคง "ฮาร์ดโค้ด" ตำแหน่งและข้อความบนหน้าจอ
ปะปนอยู่ในตรรกะโปรแกรมโดยตรง ซึ่งเป็นปัญหาใหญ่มากเมื่อระบบเติบโตขึ้น: ถ้าฝ่ายออกแบบหน้าจอ (UI/UX)
ต้องการขยับตำแหน่งฟิลด์แค่ 1 คอลัมน์ โปรแกรมเมอร์ต้องไปตามหาและแก้โค้ด COBOL ที่ฝังตำแหน่งไว้ทุกจุด

**BMS (Basic Mapping Support)** คือคำตอบของ IBM ต่อปัญหานี้ตั้งแต่ยุค CICS แรกเริ่ม: มันคือชุด
Assembler Macro พิเศษ (`DFHMSD`, `DFHMDI`, `DFHMDF`) ที่ให้เราออกแบบ **หน้าตาของหน้าจอ** แยกออกจาก
**ตรรกะของโปรแกรม** อย่างสิ้นเชิง คล้ายกับที่เว็บสมัยใหม่แยก HTML/CSS ออกจาก JavaScript logic
Part นี้จะพาคุณเรียนรู้ตั้งแต่แนวคิด ไปจนถึงโครงสร้าง Macro ทั้ง 3 ตัว, ไบต์คุณลักษณะ (Attribute Byte)
ที่ควบคุมพฤติกรรมแต่ละฟิลด์, และโครงสร้างของ Symbolic Map Copybook ที่ระบบสร้างให้อัตโนมัติ ซึ่งเป็น
สะพานเชื่อมระหว่างหน้าจอกับโปรแกรม COBOL ของเรา

> **⚠️ กรอบคำเตือนสำคัญ: ข้อจำกัดของสภาพแวดล้อมสำหรับ Part นี้**
>
> เช่นเดียวกับ Part 058–060 (Embedded SQL/DB2) เนื้อหาทั้งหมดใน Part 063–069 (CICS ขั้นสูง, IMS,
> Batch Patterns บางส่วน, DFSORT, Performance, Security) เกี่ยวข้องกับเทคโนโลยี Middleware ของ IBM
> Mainframe ที่ต้องอาศัยซอฟต์แวร์เฉพาะทาง (CICS Transaction Server, BMS Macro Assembler, IMS) ซึ่ง
> **ไม่มีอยู่ในสภาพแวดล้อม Linux + GnuCOBOL ที่ใช้เรียนหลักสูตรนี้** BMS Macro (`DFHMSD`/`DFHMDI`/
> `DFHMDF`) ไม่ใช่แม้แต่ภาษา COBOL — มันคือ Assembler Macro ที่ต้องผ่าน **BMS Macro Assembler**
> (ส่วนหนึ่งของ CICS Transaction Server บน z/OS) เพื่อ "ประกอบ" (assemble) ออกมาเป็น Physical Map
> (load module) และ Symbolic Map (COBOL copybook) — ไม่มีเครื่องมือใดใน GnuCOBOL ที่ประมวลผล
> Macro เหล่านี้ได้เลย
>
> **ดังนั้น**: ตัวอย่าง BMS Macro และโค้ด COBOL ที่มี `EXEC CICS` ทุกตัวอย่างใน Part นี้เป็น
> **ไวยากรณ์อ้างอิง (Reference Syntax)** ที่เขียนตามมาตรฐาน IBM CICS จริงอย่างถูกต้องแม่นยำ เหมาะสำหรับ
> การอ่านทำความเข้าใจโครงสร้างและนำไปใช้งานจริงเมื่อมีสภาพแวดล้อม Mainframe/CICS จริง แต่**ไม่สามารถ
> ประกอบ (assemble) คอมไพล์ หรือรันบนสภาพแวดล้อมนี้ได้** จะมีป้ายกำกับ
> `⚠️ REFERENCE SYNTAX — ไม่สามารถ assemble/compile/รันได้ในสภาพแวดล้อมนี้` กำกับไว้เสมอ
> เพื่อไม่ให้สับสนกับโค้ด GnuCOBOL ล้วนที่คอมไพล์และรันได้จริงในหลาย ๆ Part ก่อนหน้า (เช่น Part 040
> เรื่อง SCREEN SECTION ที่เราจะใช้เป็นจุดเทียบเคียงตลอด Part นี้)

## ขั้นตอนที่ 621: ทำไมต้องมี BMS — แยกหน้าจอออกจากตรรกะโปรแกรม

### ปัญหาของการฮาร์ดโค้ดหน้าจอ

ลองจินตนาการโปรแกรม CICS ที่ต้องแสดงฟอร์มค้นหาลูกค้า ถ้าเขียนด้วยคำสั่ง `EXEC CICS SEND TEXT` ที่ระบุ
ตำแหน่งบรรทัด/คอลัมน์ตรง ๆ ในทุกจุดของ `PROCEDURE DIVISION` (แบบที่ Part 062 แสดงไว้แบบง่าย ๆ)
จะเกิดปัญหาต่อไปนี้เมื่อระบบโตขึ้น:

1. **ตรรกะธุรกิจปนกับการจัดวางหน้าจอ** — นักพัฒนาที่ต้องแก้ปัญหาการคำนวณดอกเบี้ย ต้องไล่อ่านโค้ดที่
   เต็มไปด้วยตำแหน่งคอลัมน์ ทำให้อ่านยากและแก้ไขเสี่ยงต่อการพังหน้าจอโดยไม่ตั้งใจ
2. **แก้ไขหน้าจอ 1 จุด กระทบโค้ดหลายที่** — ถ้าต้องเพิ่มฟิลด์ใหม่ 1 ฟิลด์ ตำแหน่งของฟิลด์ที่อยู่ถัดไป
   ทั้งหมดอาจต้องขยับ และโปรแกรมเมอร์ต้องตามแก้ทุกจุดที่อ้างอิงตำแหน่งเดิม
3. **ทีมออกแบบหน้าจอ (UI) ไม่สามารถทำงานแยกจากทีมเขียนตรรกะได้** — เพราะทั้งสองส่วนผูกติดกันในไฟล์
   เดียวกัน

### แนวทางแก้ของ IBM: BMS (Basic Mapping Support)

**BMS** คือชุดเครื่องมือของ CICS ที่ให้เรา **นิยามหน้าจอ (Map)** แยกเป็นไฟล์ต่างหาก โดยใช้ภาษา
Assembler Macro เฉพาะทาง 3 ตัวหลัก:

| Macro | หน้าที่ |
|---|---|
| `DFHMSD` | นิยาม **Mapset** — กลุ่มของหน้าจอ (Map) ที่เก็บรวมกันเป็นไฟล์เดียว |
| `DFHMDI` | นิยาม **Map** หนึ่งหน้าจอ ภายใน Mapset นั้น (ขนาดจอ, ตำแหน่งเริ่มต้น) |
| `DFHMDF` | นิยาม **Field** หนึ่งฟิลด์ ภายใน Map นั้น (ตำแหน่ง, ความยาว, คุณสมบัติ) |

เมื่อนำ Macro เหล่านี้ไปผ่าน **BMS Macro Assembler** (เรียกใช้งานเป็นขั้นตอนหนึ่งใน JCL — ทบทวนแนวคิด
Job Step จาก Part 052) จะได้ผลลัพธ์ออกมา **สองอย่าง** พร้อมกัน:

1. **Physical Map** — load module ไบนารีที่ CICS runtime โหลดขึ้นมาใช้จริงตอน `SEND MAP` เพื่อจัดรูปแบบ
   ข้อมูลส่งไปที่จอ 3270 (ผู้ใช้ไม่เห็นโค้ดนี้ตรง ๆ)
2. **Symbolic Map** — copybook ภาษา COBOL ที่ให้โปรแกรมเมอร์ `COPY` เข้าไปใน `WORKING-STORAGE
   SECTION` เพื่ออ้างอิงแต่ละฟิลด์ด้วยชื่อที่มีความหมาย (จะสอนละเอียดในขั้นตอนที่ 626)

### เทียบเคียงกับ SCREEN SECTION ที่เรียนไปแล้วใน Part 040

นักเรียนที่ผ่าน Part 040 มาแล้วจะคุ้นเคยกับแนวคิด "กำหนดตำแหน่งฟิลด์บนจอด้วย LINE/COLUMN" อยู่แล้ว
เพราะ `SCREEN SECTION` ของ COBOL เองก็ทำสิ่งที่คล้ายกันมาก:

| แง่มุม | SCREEN SECTION (Part 040) | BMS (Part นี้) |
|---|---|---|
| ใช้งานกับ | โปรแกรม batch/interactive ทั่วไปบนเทอร์มินัลข้อความ | โปรแกรม CICS ออนไลน์บนจอ 3270 |
| ภาษาที่เขียน | COBOL ล้วน ๆ ใน DATA DIVISION | Assembler Macro แยกไฟล์ต่างหาก |
| การคอมไพล์ | คอมไพล์รวมไปกับโปรแกรมโดย `cobc` ตรง ๆ | ต้อง assemble แยกก่อน ได้ผลลัพธ์ 2 ชิ้น (physical+symbolic) |
| การอ้างอิงฟิลด์ | ใช้ชื่อตัวแปร COBOL ตรง ๆ | ใช้ชื่อฟิลด์ใน Symbolic Map ที่ระบบ generate ให้ |
| แยกหน้าจอออกจาก logic? | ไม่แยก (อยู่ไฟล์เดียวกับโปรแกรม) | แยกสมบูรณ์ (คนละไฟล์ คนละขั้นตอน build) |
| การรันบน GnuCOBOL | **รันได้จริง** (ทดสอบแล้วใน Part 040) | **ไม่รันได้** (ต้องมี CICS + BMS Assembler จริง) |

กล่าวอีกนัยหนึ่ง: ถ้า `SCREEN SECTION` คือ "วิธีที่ COBOL แบบ standalone จัดการหน้าจอด้วยตัวเอง"
BMS ก็คือ "วิธีที่โลก CICS จัดการหน้าจอแบบแยกส่วนและทำงานร่วมกับ Transaction Manager" — แนวคิดเรื่อง
ตำแหน่ง (LINE/COLUMN), การป้องกันไม่ให้ผู้ใช้แก้ไขบางฟิลด์ (protected), และ Highlight เป็นแนวคิดร่วม
ที่ทั้งสองระบบมีเหมือนกัน แต่ BMS ไปไกลกว่ามากในเรื่องการแยกส่วนและการบีบอัดข้อมูลส่งผ่านเครือข่าย
(3270 Data Stream) ซึ่งจำเป็นมากในยุคที่แบนด์วิดท์เครือข่ายราคาแพง

### ข้อควรระวัง

- อย่าสับสนระหว่าง "Mapset" กับ "Map" — Mapset คือไฟล์/โมดูลที่รวมหลาย Map ไว้ด้วยกัน (เช่น mapset
  `CUSTMSET` อาจมี map `CUSTINQ1` สำหรับหน้าค้นหา และ `CUSTINQ2` สำหรับหน้าแสดงผลละเอียด) ส่วน Map
  คือหน้าจอเดียวที่ผู้ใช้เห็น ณ ขณะหนึ่ง
- BMS ไม่ใช่ COBOL และไม่ใช่ JCL — มันคือภาษา Assembler Macro ที่มีไวยากรณ์ของตัวเอง (คอลัมน์การเขียน
  ก็ต่างจาก COBOL Fixed-Format) นักเรียนที่คุ้นเคยกับ COBOL อาจสับสนได้ถ้าไม่ระวังจุดนี้

### แบบฝึกหัดที่ 621.1

**โจทย์**: จงอธิบายว่าทำไมการแยก BMS (นิยามหน้าจอ) ออกจากโปรแกรม COBOL (นิยามตรรกะ) จึงมีประโยชน์
มากกว่าการฮาร์ดโค้ดตำแหน่งหน้าจอในโปรแกรมโดยตรง โดยยกตัวอย่างสถานการณ์จริงประกอบ

**เฉลยแนวทาง**: การแยกส่วนทำให้ทีมออกแบบหน้าจอ (business analyst/UI designer) สามารถแก้ไขตำแหน่ง
ฟิลด์ ความกว้าง หรือข้อความบนหน้าจอได้โดยไม่ต้องแตะโค้ด COBOL เลย เช่น ถ้าฝ่ายธุรกิจต้องการเปลี่ยน
ป้ายข้อความ "CUSTOMER NAME" เป็น "CUST FULL NAME" เพียงแก้ค่า `INITIAL=` ใน `DFHMDF` ของฟิลด์นั้น
แล้ว assemble ใหม่ ก็เสร็จ โดยไม่กระทบตรรกะการคำนวณหรือการเชื่อมต่อฐานข้อมูลในโปรแกรม COBOL แม้แต่
บรรทัดเดียว ต่างจากการฮาร์ดโค้ดที่ทุกการเปลี่ยนแปลงหน้าจอเสี่ยงทำให้โปรแกรมเมอร์ต้องแก้โค้ด logic
ปนไปด้วยโดยไม่จำเป็น

## ขั้นตอนที่ 622: DFHMSD Macro — นิยาม Mapset

### โครงสร้างพื้นฐานของ DFHMSD

`DFHMSD` คือ Macro ตัวแรกสุดในไฟล์ BMS แต่ละไฟล์ ทำหน้าที่ประกาศจุดเริ่มต้นของ Mapset และกำหนด
คุณสมบัติที่ใช้ร่วมกันของทุก Map ภายในนั้น

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ assemble/compile/รันได้ในสภาพแวดล้อมนี้**

```
CUSTMSET DFHMSD TYPE=&SYSPARM,                                       X
               MODE=INOUT,                                           X
               LANG=COBOL,                                           X
               STORAGE=AUTO,                                         X
               TIOAPFX=YES,                                          X
               CTRL=(FREEKB,FRSET)
```

### อธิบายทีละพารามิเตอร์

- **ชื่อ label ซ้ายมือ (`CUSTMSET`)**: ชื่อของ Mapset นี้ (สูงสุด 7-8 ตัวอักษรตามข้อจำกัดยุคเก่าของ
  z/OS dataset member name) จะใช้อ้างอิงตอนเขียน `EXEC CICS SEND MAP ... MAPSET('CUSTMSET')`
- **`TYPE=&SYSPARM`**: จุดที่ชาญฉลาดที่สุดของ BMS — ไฟล์ต้นฉบับเดียวกันถูก assemble **สองรอบ**
  ด้วยค่า `SYSPARM` ต่างกัน: รอบแรกกำหนด `SYSPARM=MAP` เพื่อสร้าง **Physical Map** (load module)
  รอบที่สองกำหนด `SYSPARM=DSECT` เพื่อสร้าง **Symbolic Map** (COBOL copybook) — ไฟล์ BMS เดียว
  จึงเป็น "ต้นทาง" ของทั้งสองผลลัพธ์เสมอ ไม่มีวันไม่ตรงกัน (out of sync) ระหว่าง physical กับ
  symbolic เพราะมาจากไฟล์เดียวกัน
- **`MODE=INOUT`**: Mapset นี้ใช้ได้ทั้งส่งข้อมูลออกจอ (`OUT`) และรับข้อมูลจากจอ (`IN`)
- **`LANG=COBOL`**: บอก BMS Assembler ว่า Symbolic Map ที่จะ generate ต้องเป็นไวยากรณ์ COBOL
  (ถ้าทีมใช้ PL/I หรือ Assembler เป็นภาษาโปรแกรม ก็เปลี่ยนค่านี้ได้)
- **`STORAGE=AUTO`**: บอกว่า Symbolic Map area จะถูกจองพื้นที่หน่วยความจำแบบอัตโนมัติ (ไม่ใช่ static)
- **`TIOAPFX=YES`**: เพิ่ม filler 12 ไบต์ที่ต้นของ Symbolic Map (ใช้สำหรับ Terminal I/O Area prefix
  ภายในของ CICS) — เหตุผลที่ Symbolic Map ที่จะเห็นในขั้นตอนที่ 626 มี `FILLER PIC X(12)` เป็น
  ฟิลด์แรกเสมอ
- **`CTRL=(FREEKB,FRSET)`**: ควบคุมพฤติกรรมคีย์บอร์ดเทอร์มินัล `FREEKB` ปลดล็อกคีย์บอร์ดให้ผู้ใช้พิมพ์
  ได้ทันทีที่หน้าจอแสดงผล ส่วน `FRSET` (Force Reset MDT) รีเซ็ตสถานะ "ฟิลด์ถูกแก้ไข" (Modified Data
  Tag จะอธิบายในขั้นตอนที่ 625) ของทุกฟิลด์เมื่อส่งจอใหม่

### ข้อควรระวัง

- ชื่อ Mapset (`CUSTMSET` ในตัวอย่าง) ต้อง**ตรงกับชื่อไฟล์/member ที่เก็บบน Partitioned Dataset (PDS)
  บน z/OS เป๊ะ** เพราะ CICS จะค้นหา load module โดยใช้ชื่อนี้เป็น key
- การลืม assemble ด้วย `SYSPARM` ทั้งสองค่า (ทำแค่ `MAP` แต่ลืม `DSECT` หรือกลับกัน) จะทำให้ได้แค่
  ผลลัพธ์อย่างเดียว โปรแกรมเมอร์ COBOL จะไม่มี copybook ให้ `COPY` หรือ CICS จะหา physical map
  ไม่เจอตอนรัน

### แบบฝึกหัดที่ 622.1

**โจทย์**: จงอธิบายว่าทำไมการ assemble ไฟล์ BMS ต้นฉบับเดียวกันด้วยค่า `SYSPARM` สองค่า (`MAP` และ
`DSECT`) จึงดีกว่าการเขียนไฟล์ต้นฉบับแยกกันสองไฟล์สำหรับ Physical Map และ Symbolic Map

**เฉลย**: เพราะถ้าเขียนแยกไฟล์กัน มีความเสี่ยงสูงที่นักพัฒนาจะแก้ไขไฟล์หนึ่งแล้วลืมแก้อีกไฟล์ให้ตรงกัน
(เช่น เพิ่มฟิลด์ใหม่ใน Physical Map แต่ลืมเพิ่มใน Symbolic Map) ทำให้ Physical Map กับ Symbolic Map
"ไม่ตรงกัน" (out of sync) ซึ่งจะทำให้โปรแกรมอ่าน/เขียนข้อมูลผิดตำแหน่งโดยไม่มี compile error ใด ๆ
เตือนเลย การใช้ไฟล์ต้นฉบับเดียวกันที่ควบคุมด้วย `TYPE=&SYSPARM` รับประกันว่าทั้งสองผลลัพธ์จะสอดคล้องกัน
เสมอ เพราะมาจาก source code ชุดเดียวกัน 100%

## ขั้นตอนที่ 623: DFHMDI Macro — นิยาม Map (หน้าจอ) หนึ่งหน้า

### หนึ่ง Mapset มีได้หลาย Map

Mapset หนึ่งตัวสามารถบรรจุหลาย Map (หลายหน้าจอ) ไว้ด้วยกันได้ เพื่อความสะดวกในการจัดกลุ่มหน้าจอ
ที่เกี่ยวข้องกัน (เช่น mapset ของระบบลูกค้าอาจมี map สำหรับหน้าค้นหา, หน้ารายละเอียด, และหน้าแก้ไข
รวมอยู่ในไฟล์เดียว) `DFHMDI` คือ Macro ที่ใช้ประกาศแต่ละ Map เหล่านี้

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ assemble/compile/รันได้ในสภาพแวดล้อมนี้**

```
CUSTMSET DFHMSD TYPE=&SYSPARM,MODE=INOUT,LANG=COBOL,                 X
               STORAGE=AUTO,TIOAPFX=YES,CTRL=(FREEKB,FRSET)
*
CUSTINQ1 DFHMDI SIZE=(24,80),                                        X
               LINE=1,                                               X
               COLUMN=1,                                             X
               MAPATTS=(COLOR,HILIGHT)
*
      (... DFHMDF fields go here - see step 624 ...)
*
CUSTMSET DFHMSD TYPE=FINAL
      END
```

### อธิบายทีละพารามิเตอร์

- **`CUSTINQ1`**: ชื่อของ Map นี้ (นี่คือชื่อที่ใช้ใน `EXEC CICS SEND MAP('CUSTINQ1')` — ต่างจากชื่อ
  Mapset ที่ใช้ใน `MAPSET('CUSTMSET')`)
- **`SIZE=(24,80)`**: ขนาดของหน้าจอเป็น (แถว, คอลัมน์) — `24,80` คือขนาดมาตรฐานของจอ 3270 รุ่น Model 2
  (จอที่พบได้บ่อยที่สุดในยุค Mainframe) รุ่นอื่นมีขนาดใหญ่กว่า เช่น Model 3 (32,80), Model 4 (43,80),
  Model 5 (27,132)
- **`LINE=1, COLUMN=1`**: ตำแหน่งเริ่มต้นของ Map นี้บนจอ (มุมซ้ายบน) ปกติจะเป็น 1,1 เสมอสำหรับ Map
  ที่ใช้เต็มจอ
- **`MAPATTS=(COLOR,HILIGHT)`**: ประกาศว่า Map นี้รองรับคุณสมบัติสี (`COLOR`) และการเน้นข้อความ
  (`HILIGHT`) ซึ่งต้องอาศัยเทอร์มินัลรุ่นที่รองรับ Extended Attributes (3270 รุ่นเก่าที่สุดรองรับแค่
  monochrome + attribute byte พื้นฐานเท่านั้น)
- **`DFHMSD TYPE=FINAL`**: Macro สุดท้ายที่ต้องมีเสมอเพื่อบอก Assembler ว่า Mapset จบแล้ว (ปิดท้ายด้วย
  `END` ตามธรรมเนียม Assembler ทั่วไป)

### ข้อควรระวัง

- ชื่อ Map (`CUSTINQ1`) **ต้องไม่ซ้ำกับชื่อ field ใด ๆ** ภายใน mapset เดียวกัน เพราะทั้งหมดจะกลายเป็น
  label ใน Assembler namespace เดียวกัน
- ถ้า mapset มีหลาย Map จะต้องมี `DFHMDI` แยกสำหรับแต่ละ Map และ field (`DFHMDF`) ของแต่ละ Map ต้อง
  อยู่ต่อจาก `DFHMDI` ของ Map นั้นเสมอ ก่อนจะขึ้น `DFHMDI` ของ Map ถัดไป (ลำดับในไฟล์มีความหมาย
  เหมือนโครงสร้างต้นไม้)

### แบบฝึกหัดที่ 623.1

**โจทย์**: ถ้าต้องการให้ mapset หนึ่งตัวมี 2 หน้าจอ คือหน้าค้นหา (`CUSTSRCH`) และหน้าแสดงผล
(`CUSTDISP`) จะต้องมี `DFHMDI` กี่ตัว และเรียงลำดับอย่างไรในไฟล์?

**เฉลย**: ต้องมี `DFHMDI` 2 ตัว โดยแต่ละตัวต้องตามด้วยชุด `DFHMDF` ของฟิลด์ในหน้าจอนั้นทันที ลำดับ
ในไฟล์คือ: `DFHMSD` (เปิด mapset) → `DFHMDI` ของ `CUSTSRCH` → `DFHMDF` ทั้งหมดของหน้า CUSTSRCH →
`DFHMDI` ของ `CUSTDISP` → `DFHMDF` ทั้งหมดของหน้า CUSTDISP → `DFHMSD TYPE=FINAL` → `END`

## ขั้นตอนที่ 624: DFHMDF Macro — นิยาม Field แต่ละฟิลด์บนหน้าจอ

### หัวใจของการออกแบบหน้าจอ

`DFHMDF` คือ Macro ที่ใช้บ่อยที่สุดในไฟล์ BMS เพราะต้องเขียนซ้ำสำหรับทุกฟิลด์บนหน้าจอ (ทั้งข้อความ
ป้าย/label ที่ตายตัว และฟิลด์ที่รับ/แสดงข้อมูลจริง)

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ assemble/compile/รันได้ในสภาพแวดล้อมนี้**

```
         DFHMDF POS=(2,1),                                           X
               LENGTH=15,                                            X
               ATTRB=(PROT,BRT),                                     X
               INITIAL='CUSTOMER ID:'
CUSTID   DFHMDF POS=(2,17),                                          X
               LENGTH=5,                                             X
               ATTRB=(UNPROT,NUM,IC),                                X
               PICIN='9(5)'
         DFHMDF POS=(4,1),                                           X
               LENGTH=15,                                            X
               ATTRB=(PROT,BRT),                                     X
               INITIAL='CUSTOMER NAME:'
CNAME    DFHMDF POS=(4,17),                                          X
               LENGTH=20,                                            X
               ATTRB=(PROT)
         DFHMDF POS=(6,1),                                           X
               LENGTH=15,                                            X
               ATTRB=(PROT,BRT),                                     X
               INITIAL='BALANCE:'
CBAL     DFHMDF POS=(6,17),                                          X
               LENGTH=12,                                            X
               ATTRB=(PROT),                                         X
               PICOUT='ZZZ,ZZ9.99'
MSG      DFHMDF POS=(22,1),                                          X
               LENGTH=79,                                            X
               ATTRB=(PROT,BRT,ASKIP)
```

### อธิบายทีละพารามิเตอร์

- **ชื่อ label ซ้ายมือ (`CUSTID`, `CNAME`, `CBAL`, `MSG`)**: ถ้าใส่ชื่อ จะมีฟิลด์นี้ปรากฏใน Symbolic
  Map ให้โปรแกรม COBOL อ้างอิงได้ (ขั้นตอนที่ 626) — สังเกตว่าฟิลด์ **ข้อความป้ายตายตัว** (label เช่น
  "CUSTOMER ID:") **ไม่มีชื่อ label** เพราะโปรแกรมไม่จำเป็นต้องแก้ไขข้อความเหล่านี้ระหว่างรัน
- **`POS=(line,col)`**: ตำแหน่งของฟิลด์นี้บนจอ นับจากมุมซ้ายบนของ Map (ไม่ใช่ของจอทั้งหมด ถ้า Map
  ไม่ได้เริ่มที่ 1,1)
- **`LENGTH=n`**: ความยาวของฟิลด์เป็นตัวอักษร (**ไม่รวม** ไบต์ attribute ที่อยู่ข้างหน้าฟิลด์ ซึ่ง
  CICS จัดการให้อัตโนมัติ — จะอธิบายละเอียดในขั้นตอนที่ 625)
- **`ATTRB=`**: คุณสมบัติของฟิลด์ ค่าที่ใช้บ่อยที่สุด:
  - `PROT` / `UNPROT`: ป้องกันไม่ให้ผู้ใช้พิมพ์ทับ (สำหรับ label หรือข้อมูลที่แสดงผลอย่างเดียว) กับ
    อนุญาตให้ผู้ใช้พิมพ์ได้ (สำหรับฟิลด์ input)
  - `NUM`: บังคับให้เทอร์มินัลรับได้เฉพาะตัวเลข (ถ้าผู้ใช้พิมพ์ตัวอักษร คีย์บอร์ดจะล็อก)
  - `BRT` / `NORM` / `DRK`: ความสว่าง — `BRT` (Bright เน้นสว่าง), `NORM` (ปกติ), `DRK` (Dark ซ่อนไม่
    แสดงผลเลย เช่น ใช้กับช่องรหัสผ่าน)
  - `IC` (Insert Cursor): บอกให้เคอร์เซอร์กระโดดไปที่ฟิลด์นี้ทันทีที่ส่งหน้าจอ (สะดวกมากสำหรับฟิลด์
    แรกที่ผู้ใช้ต้องกรอก)
  - `ASKIP` (Auto Skip): เคอร์เซอร์ข้ามฟิลด์นี้ไปอัตโนมัติโดยไม่ให้หยุดพัก (มักใช้ร่วมกับ `PROT`)
- **`INITIAL='...'`**: ข้อความเริ่มต้นที่ปรากฏบนฟิลด์นี้ทันทีที่ส่งจอ (ใช้กับ label ที่ตายตัว หรือ
  ค่าเริ่มต้นของฟิลด์ input)
- **`PICIN=`/`PICOUT=`**: กำหนดรูปแบบ PICTURE สำหรับแปลงข้อมูลตอนรับเข้า (`PICIN`) และตอนแสดงผล
  (`PICOUT`) เทียบเท่ากับ `PICTURE` Clause ที่นักเรียนคุ้นเคยจาก Part 006 นั่นเอง เพียงแต่ทำงาน
  ที่ระดับ BMS ก่อนที่ข้อมูลจะเข้าไปถึงโปรแกรม COBOL

### ข้อควรระวัง

- **ผลรวมของทุกฟิลด์ (รวม label) ต้องไม่เกินขนาดจอที่ประกาศไว้ใน `DFHMDI SIZE=`** ถ้าฟิลด์ใดวางเกิน
  แถวหรือคอลัมน์สุดท้ายของจอ การ assemble จะ error ทันที
- ฟิลด์ `UNPROT` (รับข้อมูลจากผู้ใช้) **ต้องไม่วางติดกับฟิลด์ `UNPROT` อื่นโดยไม่มี label หรือ
  `PROT` field คั่น** เพราะจอ 3270 ใช้ attribute byte เป็นตัวกำหนดขอบเขตฟิลด์ ถ้าไม่มีขอบเขตชัดเจน
  ผู้ใช้จะพิมพ์ข้อมูลของฟิลด์หนึ่งล้นเข้าไปในอีกฟิลด์โดยไม่รู้ตัว
- ฟิลด์ที่ไม่มีชื่อ label (เช่น field ข้อความ label ธรรมดา) จะไม่ปรากฏใน Symbolic Map เลย — ถ้าลืม
  ใส่ชื่อให้ฟิลด์ที่โปรแกรมจำเป็นต้องอ่าน/เขียนค่า จะไม่มีทางอ้างอิงถึงมันได้จากโปรแกรม COBOL

### แบบฝึกหัดที่ 624.1

**โจทย์**: จงอธิบายว่าทำไมฟิลด์รหัสผ่าน (password field) บนหน้าจอ CICS มักใช้ `ATTRB=(UNPROT,DRK)`
แทนที่จะเป็น `ATTRB=(UNPROT,BRT)`

**เฉลย**: `DRK` (Dark) ทำให้ตัวอักษรที่ผู้ใช้พิมพ์ **ไม่แสดงผลบนจอเลย** แม้ผู้ใช้จะพิมพ์ได้ปกติ
(เพราะยังเป็น `UNPROT`) ข้อมูลจะยังถูกส่งกลับไปที่โปรแกรมตามปกติ แต่คนที่มองข้ามไหล่ผู้ใช้จะไม่เห็น
รหัสผ่านบนจอ ต่างจาก `BRT` ที่จะทำให้ตัวอักษรพิมพ์แสดงเด่นชัดบนจอ ซึ่งไม่เหมาะกับข้อมูลอ่อนไหว

## ขั้นตอนที่ 625: Attribute Byte — กลไกเบื้องหลังทุกฟิลด์บนจอ 3270

### ไบต์ที่มองไม่เห็นแต่สำคัญที่สุด

ทุกฟิลด์บนจอ 3270 มี **ไบต์คุณลักษณะ (Attribute Byte)** แฝงอยู่ 1 ไบต์ ที่ตำแหน่ง**ก่อนหน้าฟิลด์นั้น
ทันที** (ไม่ใช่ส่วนหนึ่งของข้อมูลที่ผู้ใช้เห็นหรือพิมพ์) ไบต์นี้คือสิ่งที่บอกฮาร์ดแวร์เทอร์มินัลว่า
"ฟิลด์ที่ตามมาต่อจากนี้ มีคุณสมบัติอะไรบ้าง" — `ATTRB=` ใน `DFHMDF` ที่เราเขียนในขั้นตอนก่อนหน้า
ก็คือค่าที่จะถูกเข้ารหัสลงในไบต์นี้นั่นเอง

### บิตสำคัญภายใน Attribute Byte

| คุณสมบัติ | ความหมาย |
|---|---|
| Protected / Unprotected | ผู้ใช้พิมพ์ทับได้หรือไม่ |
| Numeric | จำกัดให้พิมพ์ได้เฉพาะตัวเลข (ใช้ร่วมกับ Unprotected) |
| Display / Non-display (Dark) | แสดงผลตัวอักษรที่พิมพ์หรือซ่อนไว้ |
| Intensity (Normal/Bright) | ความสว่างของข้อความ |
| **Modified Data Tag (MDT)** | ธงบอกว่า "ฟิลด์นี้ถูกแก้ไขตั้งแต่ครั้งล่าสุดที่ส่งจอ" |

### MDT คือกลไกที่ทำให้ CICS มีประสิทธิภาพสูง

**Modified Data Tag (MDT)** คือแนวคิดที่ฉลาดที่สุดของสถาปัตยกรรม 3270: เมื่อผู้ใช้พิมพ์ข้อมูลลงไป
ในฟิลด์ใดก็ตาม ฮาร์ดแวร์เทอร์มินัลจะ**เปิดธง MDT ของฟิลด์นั้นเป็น 1 โดยอัตโนมัติ** เมื่อผู้ใช้กด Enter
หรือ PF Key เทอร์มินัลจะส่งกลับไปที่ CICS **เฉพาะฟิลด์ที่มี MDT=1 เท่านั้น** (ไม่ส่งข้อมูลทั้งจอกลับไป)

ทำไมสิ่งนี้ถึงสำคัญมากในยุคที่ Mainframe ถือกำเนิด? เพราะแบนด์วิดท์เครือข่ายในยุคนั้นมีจำกัดมหาศาล
การส่งเฉพาะฟิลด์ที่เปลี่ยนแปลงจริง (แทนที่จะส่งข้อมูลทั้งจอ 24×80 = 1,920 ไบต์ทุกครั้ง) ช่วยลดปริมาณ
ข้อมูลที่ต้องส่งผ่านเครือข่ายได้มหาศาล และแนวคิดนี้ยังเป็นต้นแบบของแนวคิด "ส่งเฉพาะส่วนที่เปลี่ยน"
(delta update) ที่พบได้ในเทคโนโลยีเว็บสมัยใหม่หลายตัวด้วยซ้ำ

### ตัวอย่าง: CTRL=FRSET ที่เจอในขั้นตอนที่ 622

ทบทวนจากขั้นตอนที่ 622 — `CTRL=(FREEKB,FRSET)` ใน `DFHMSD` มี `FRSET` (Force Reset) ซึ่งหมายถึง
**รีเซ็ต MDT ของทุกฟิลด์กลับเป็น 0 ทุกครั้งที่ส่งจอใหม่** เหตุผลคือถ้าไม่รีเซ็ต ฟิลด์ที่ผู้ใช้เคยแก้ไข
ในรอบก่อนหน้าจะยังคงมี MDT=1 ค้างอยู่ ทำให้รอบถัดไปโปรแกรมได้รับข้อมูลฟิลด์นั้นกลับมาซ้ำอีกทั้งที่
ผู้ใช้ไม่ได้แตะต้องมันเลยในรอบปัจจุบัน

### ข้อควรระวัง

- โปรแกรมเมอร์มือใหม่มักเข้าใจผิดว่า `RECEIVE MAP` จะได้รับ**ทุกฟิลด์**กลับมาเสมอ แต่ความจริงคือ
  ฟิลด์ที่ผู้ใช้ไม่ได้แตะต้องเลย (MDT=0) จะมีค่า **length เป็นค่าลบ** (-1) ใน Symbolic Map's `-L`
  field (จะอธิบายในขั้นตอนที่ 626) ซึ่งโปรแกรมต้องตรวจสอบก่อนใช้งานฟิลด์นั้นเสมอ
- การกำหนด `ATTRB=(IC)` ให้กับหลายฟิลด์ในหน้าจอเดียวกันไม่มีผลเสีย (compile ผ่านปกติ) แต่ผลลัพธ์จริง
  คือ **ฟิลด์สุดท้ายที่มี `IC` เท่านั้นที่เคอร์เซอร์จะไปหยุดจริง** ควรมี `IC` แค่ฟิลด์เดียวต่อหน้าจอ

### แบบฝึกหัดที่ 625.1

**โจทย์**: จงอธิบายว่าทำไมกลไก Modified Data Tag (MDT) จึงช่วยลดภาระเครือข่ายได้มาก เมื่อเทียบกับ
การส่งข้อมูลทั้งหน้าจอกลับไปทุกครั้งที่ผู้ใช้กด Enter

**เฉลย**: เพราะ MDT ทำให้เทอร์มินัลส่งกลับเฉพาะฟิลด์ที่ผู้ใช้แก้ไขจริงเท่านั้น แทนที่จะส่งข้อมูลทั้งจอ
(ซึ่งรวมถึง label และฟิลด์ protected ที่ไม่มีทางเปลี่ยนแปลงอยู่แล้ว) ตัวอย่างเช่น หน้าจอที่มี 20 ฟิลด์
แต่ผู้ใช้แก้ไขแค่ 2 ฟิลด์ การส่งกลับด้วย MDT จะส่งข้อมูลแค่ 2 ฟิลด์นั้น (บวกตำแหน่งของแต่ละฟิลด์)
แทนที่จะส่งข้อมูลทั้ง 20 ฟิลด์ ซึ่งในยุคที่ Mainframe เชื่อมต่อกับเทอร์มินัลผ่านสายสื่อสารความเร็วต่ำ
การประหยัดแบนด์วิดท์แบบนี้มีผลต่อประสิทธิภาพระบบโดยรวมอย่างมีนัยสำคัญ

## ขั้นตอนที่ 626: Symbolic Map Copybook — สะพานเชื่อมสู่โปรแกรม COBOL

### ผลลัพธ์จากการ Assemble ด้วย SYSPARM=DSECT

เมื่อ BMS Macro ในขั้นตอนที่ 622–624 ถูก assemble ด้วย `SYSPARM=DSECT` (ทบทวนจากขั้นตอนที่ 622)
ผลลัพธ์ที่ได้คือ **Symbolic Map Copybook** ซึ่งเป็นไวยากรณ์ COBOL ล้วน ๆ ที่พร้อมให้ `COPY` เข้าไปใน
`WORKING-STORAGE SECTION` ของโปรแกรม ต่อไปนี้คือ Symbolic Map ที่ระบบสร้างให้จาก field ทั้งสามตัว
(`CUSTID`, `CNAME`, `CBAL`) ในขั้นตอนที่ 624:

> ⚠️ **REFERENCE SYNTAX — เป็นโค้ด COBOL จริง แต่เป็นผลลัพธ์ที่ต้องมาจาก BMS Assembler เท่านั้น
> ไม่มี BMS Assembler ในสภาพแวดล้อมนี้จึงไม่สามารถ generate ไฟล์นี้ขึ้นมาเองได้**

```cobol
       01  CUSTINQ1I.
           02  FILLER               PIC X(12).
           02  CUSTIDL              PIC S9(4) COMP.
           02  CUSTIDF              PIC X.
           02  FILLER REDEFINES CUSTIDF.
               03  CUSTIDA          PIC X.
           02  CUSTIDI              PIC 9(5).
           02  CNAMEL               PIC S9(4) COMP.
           02  CNAMEF               PIC X.
           02  FILLER REDEFINES CNAMEF.
               03  CNAMEA           PIC X.
           02  CNAMEI               PIC X(20).
           02  CBALL                PIC S9(4) COMP.
           02  CBALF                PIC X.
           02  FILLER REDEFINES CBALF.
               03  CBALA            PIC X.
           02  CBALI                PIC X(12).
           02  MSGL                 PIC S9(4) COMP.
           02  MSGF                 PIC X.
           02  FILLER REDEFINES MSGF.
               03  MSGA             PIC X.
           02  MSGI                 PIC X(79).

       01  CUSTINQ1O REDEFINES CUSTINQ1I.
           02  FILLER               PIC X(12).
           02  FILLER               PIC X(3).
           02  CUSTIDO              PIC 9(5).
           02  FILLER               PIC X(3).
           02  CNAMEO               PIC X(20).
           02  FILLER               PIC X(3).
           02  CBALO                PIC X(12).
           02  FILLER               PIC X(3).
           02  MSGO                 PIC X(79).
```

### อธิบายความหมายของ Suffix แต่ละตัว

สำหรับทุกฟิลด์ที่ตั้งชื่อไว้ใน `DFHMDF` (เช่น `CUSTID`) ระบบจะ generate ฟิลด์ย่อยออกมา 4 ตัวเสมอ
โดยแต่ละตัวมี suffix บอกหน้าที่:

| Suffix | ตัวอย่าง | ความหมาย |
|---|---|---|
| **`-L`** | `CUSTIDL` | ความยาว (Length) ของข้อมูลที่ผู้ใช้พิมพ์จริงหลัง `RECEIVE MAP` (ถ้าผู้ใช้ไม่แตะฟิลด์นี้เลย ค่าจะเป็น **-1**) |
| **`-F`** | `CUSTIDF` | ไบต์ Flag/Attribute ดิบ ใช้ภายในกลไกของ CICS |
| **`-A`** | `CUSTIDA` | มุมมอง `REDEFINES` ของ `-F` ที่โปรแกรมเมอร์ใช้ตั้งค่า Attribute Byte ใหม่ก่อน `SEND MAP` (เช่น เปลี่ยนสีฟิลด์เป็นแดงเมื่อพบข้อผิดพลาด) |
| **`-I`** | `CUSTIDI` | ค่าข้อมูล**ขาเข้า** (Input) — ค่าที่ผู้ใช้พิมพ์เข้ามา อ่านได้หลัง `RECEIVE MAP` |
| **`-O`** | `CUSTIDO` | ค่าข้อมูล**ขาออก** (Output) — ค่าที่โปรแกรมต้องการแสดงผล ตั้งค่าก่อน `SEND MAP` |

สังเกตว่า **`01 CUSTINQ1I`** (โครงสร้างหลักที่ลงท้ายด้วย `I`) และ **`01 CUSTINQ1O`** (ที่ `REDEFINES`
ทับพื้นที่หน่วยความจำเดียวกัน) ใช้พื้นที่หน่วยความจำ**ร่วมกัน** — เหตุผลที่ต้องออกแบบแบบนี้เพราะ
โครงสร้างข้อมูลขาเข้า (มี `-L`, `-F`/`-A` นำหน้าทุกฟิลด์) กับขาออก (มีแค่ filler กั้นตำแหน่ง 3 ไบต์
แทน) มีความกว้างของแต่ละฟิลด์ไม่เท่ากัน การใช้ `REDEFINES` ทำให้ COBOL มองเห็นหน่วยความจำก้อนเดียวกัน
ได้สองมุมมองตามแต่ว่ากำลังจะรับ (`-I`) หรือส่ง (`-O`) ข้อมูล — นี่คือเหตุผลที่ชื่อไฟล์นี้ในโจทย์งานถูก
เรียกว่า "โครงสร้าง -I suffix": ชื่อ group ระดับ `01` หลักของ Symbolic Map ลงท้ายด้วย `I` เสมอ
(`CUSTINQ1I`) แม้จะมี group `01 ...O` ที่ `REDEFINES` ทับอยู่ก็ตาม

### ข้อควรระวัง

- **ค่า `-L` เป็นค่าลบ (-1) หมายถึงฟิลด์นั้นไม่ถูกแตะต้องเลย ไม่ใช่หมายถึง error** — ทบทวนจากขั้นตอนที่
  625 เรื่อง MDT: ถ้าผู้ใช้ไม่พิมพ์อะไรลงในฟิลด์นั้น (MDT=0) ค่าที่ `RECEIVE MAP` คืนกลับมาจะยังเป็น
  ค่าเดิมที่ฝังอยู่ในหน่วยความจำ (ขยะจากรอบก่อนหน้า) ดังนั้นโปรแกรมเมอร์**ต้องตรวจสอบ `-L` ก่อนใช้ค่า
  `-I` ของฟิลด์นั้นเสมอ** (`IF CUSTIDL > 0 ... `)
- ห้ามแก้ไข Symbolic Map Copybook ด้วยมือโดยตรง — เพราะมันเป็นไฟล์ที่ generate มาจาก BMS ต้นฉบับ
  การแก้ไขตรงจะถูกเขียนทับทันทีที่มีการ assemble ใหม่ ควรแก้ที่ไฟล์ BMS ต้นฉบับเท่านั้น

### แบบฝึกหัดที่ 626.1

**โจทย์**: หลัง `EXEC CICS RECEIVE MAP` โปรแกรมพบว่า `CUSTIDL` มีค่าเป็น -1 จงอธิบายว่าเหตุการณ์นี้
มีความหมายว่าอย่างไร และโปรแกรมควรจัดการอย่างไร

**เฉลย**: ค่า -1 หมายความว่าผู้ใช้**ไม่ได้พิมพ์หรือแก้ไข**ฟิลด์ `CUSTID` เลยในรอบที่ผ่านมา (Modified
Data Tag ของฟิลด์นี้เป็น 0) ค่าที่อยู่ใน `CUSTIDI` ในขณะนี้จึงไม่ใช่ข้อมูลที่เชื่อถือได้ (อาจเป็นค่าขยะ
จากหน่วยความจำก่อนหน้า) โปรแกรมควร**ข้ามการประมวลผลฟิลด์นี้** หรือถ้าฟิลด์นี้เป็นฟิลด์บังคับกรอก
(mandatory) ควรแสดงข้อความแจ้งเตือนผู้ใช้ให้กรอกข้อมูลก่อนกด Enter อีกครั้ง แทนที่จะนำค่าที่ไม่แน่นอน
ไปประมวลผลต่อ

## ขั้นตอนที่ 627: Physical Map เทียบกับ Symbolic Map — สองผลลัพธ์จากไฟล์เดียว

### ทบทวนภาพรวม

ขั้นตอนที่ผ่านมาได้อธิบายกลไกทีละส่วนแล้ว ขั้นตอนนี้จะสรุปภาพรวมทั้งหมดของกระบวนการแปลง BMS
ให้เห็นเป็นภาพเดียว:

```
[BMS Source: DFHMSD + DFHMDI + DFHMDF ในไฟล์เดียว]
              |
              |-- assemble ด้วย SYSPARM=MAP -----> Physical Map (load module ไบนารี)
              |                                     ใช้โดย CICS runtime ตอน SEND MAP/RECEIVE MAP
              |
              '-- assemble ด้วย SYSPARM=DSECT ---> Symbolic Map (COBOL copybook)
                                                    ใช้โดยโปรแกรมเมอร์ COBOL ตอน COPY เข้า
                                                    WORKING-STORAGE SECTION
```

### ความแตกต่างที่สำคัญ

| แง่มุม | Physical Map | Symbolic Map |
|---|---|---|
| รูปแบบผลลัพธ์ | Load module (ไบนารี) | Copybook (ข้อความ COBOL) |
| ใครใช้งาน | CICS runtime (ไม่มีมนุษย์อ่านโดยตรง) | โปรแกรมเมอร์ COBOL |
| เก็บที่ไหน | CICS Load Library (PDS ชนิด load module) | Copybook Library (PDS ชนิด source) |
| เนื้อหา | ตำแหน่ง/ความยาว/attribute ของทุกฟิลด์ แบบไบนารี พร้อมใช้ทันที | โครงสร้างข้อมูล COBOL (`01`/`02` level พร้อม PICTURE) |
| ถูกอ้างอิงด้วย | `MAPSET('...')` + `MAP('...')` ใน `EXEC CICS` | `COPY mapname.` ใน `WORKING-STORAGE SECTION` |
| แก้ไขโดยตรงได้ไหม | ไม่ได้ (ต้อง assemble ใหม่จาก BMS source) | ไม่ควร (จะถูกเขียนทับเมื่อ assemble ใหม่) |

### เหตุใดต้องแยกสองผลลัพธ์ แทนที่จะรวมเป็นไฟล์เดียว

CICS runtime ต้องการความเร็วสูงสุดตอนวาดหน้าจอ (เพราะมีธุรกรรมเป็นพันเป็นหมื่นรายการต่อวินาทีในระบบ
จริง) การใช้ load module ไบนารีที่โหลดเข้าหน่วยความจำแล้วใช้งานตรง ๆ (ไม่ต้องแปลความหมายซ้ำทุกครั้ง)
จึงเร็วกว่าการ parse ไฟล์ข้อความมาก ในขณะที่โปรแกรมเมอร์ COBOL ต้องการ **ชื่อฟิลด์ที่มีความหมาย**
เพื่อเขียนโค้ดที่อ่านง่าย (`MOVE CUST-NAME TO CNAMEO` อ่านง่ายกว่า `MOVE CUST-NAME TO
WS-FIELD-AT-OFFSET-47` มาก) BMS จึงแยกสองความต้องการนี้ออกจากกันอย่างชาญฉลาด โดยให้ทั้งคู่มาจาก
"ความจริงชุดเดียว" (single source of truth) คือไฟล์ BMS ต้นฉบับ

### ข้อควรระวัง

- ถ้า Physical Map ถูก assemble ใหม่ (เช่น แก้ตำแหน่งฟิลด์) **แต่ Symbolic Map เก่ายังไม่ได้ compile
  ใหม่เข้าโปรแกรม** โปรแกรมจะยังใช้โครงสร้างข้อมูลเดิมทำงานร่วมกับหน้าจอใหม่ ซึ่งอาจทำให้ข้อมูลเขียน
  ผิดตำแหน่งได้ (แม้ทั้งสองมาจากไฟล์ BMS เดียวกัน แต่คนละรอบเวลาของการ deploy) — ในกระบวนการทำงานจริง
  จึงต้อง assemble ทั้งสองส่วนพร้อมกันเสมอเป็นส่วนหนึ่งของ build pipeline เดียวกัน
- Physical Map ผูกกับรุ่นเทอร์มินัล (`SIZE=` ที่ระบุใน `DFHMDI`) ถ้าเทอร์มินัลจริงมีขนาดเล็กกว่าที่
  ระบุ (เช่น ใช้ emulator ที่ตั้งค่าเป็น Model 2 แต่ mapset design เป็น Model 3) หน้าจอจะแสดงผลไม่ครบ

### แบบฝึกหัดที่ 627.1

**โจทย์**: จงอธิบายว่าทำไม CICS runtime จึงเลือกใช้ Physical Map แบบ load module ไบนารี แทนที่จะอ่าน
ไฟล์ BMS ต้นฉบับ (ข้อความ) ตรง ๆ ทุกครั้งที่ต้องส่งหน้าจอ

**เฉลย**: เพราะระบบ CICS ต้องประมวลผลธุรกรรมจำนวนมหาศาลต่อวินาที การ parse ไฟล์ข้อความ (แปลความหมาย
ของ Macro ใหม่ทุกครั้ง) จะช้ากว่าการโหลด load module ไบนารีที่ถูก "แปลง" (compile) เป็นโครงสร้างข้อมูล
พร้อมใช้งานไว้ล่วงหน้าแล้วอย่างมาก Physical Map ที่เป็นไบนารีจึงถูกออกแบบมาเพื่อประสิทธิภาพสูงสุดในการ
ใช้งานจริง ในขณะที่ไฟล์ BMS ต้นฉบับ (ข้อความ) มีหน้าที่แค่เป็น "พิมพ์เขียว" สำหรับตอน build/assemble
เท่านั้น ไม่ได้ถูกใช้งานซ้ำระหว่างการรันจริง

## ขั้นตอนที่ 628: ตัวอย่างสมบูรณ์ — ออกแบบหน้าจอสอบถามข้อมูลลูกค้า

### โจทย์การออกแบบ

มาประกอบทุกความรู้จากขั้นตอนที่ 621–627 เข้าด้วยกัน เพื่อออกแบบหน้าจอ CICS สำหรับ "สอบถามข้อมูล
ลูกค้าด้วยรหัสลูกค้า" ที่มีองค์ประกอบครบถ้วน: ฟิลด์ input, ฟิลด์ output, ป้ายข้อความ, บรรทัดข้อความ
แจ้งเตือน, และคำแนะนำการใช้ PF Key

> ⚠️ **REFERENCE SYNTAX — ไวยากรณ์อ้างอิงสมบูรณ์แบบ ไม่สามารถ assemble ได้ในสภาพแวดล้อมนี้**

```
CUSTMSET DFHMSD TYPE=&SYSPARM,                                       X
               MODE=INOUT,                                           X
               LANG=COBOL,                                           X
               STORAGE=AUTO,                                         X
               TIOAPFX=YES,                                          X
               CTRL=(FREEKB,FRSET)
*
CUSTINQ1 DFHMDI SIZE=(24,80),LINE=1,COLUMN=1
*
         DFHMDF POS=(1,30),LENGTH=20,ATTRB=(PROT,BRT),               X
               INITIAL='CUSTOMER INQUIRY'
*
         DFHMDF POS=(3,1),LENGTH=15,ATTRB=(PROT,BRT),                X
               INITIAL='CUSTOMER ID:'
CUSTID   DFHMDF POS=(3,17),LENGTH=5,ATTRB=(UNPROT,NUM,IC),           X
               PICIN='9(5)'
*
         DFHMDF POS=(5,1),LENGTH=15,ATTRB=(PROT),                    X
               INITIAL='CUSTOMER NAME:'
CNAME    DFHMDF POS=(5,17),LENGTH=20,ATTRB=(PROT,ASKIP)
*
         DFHMDF POS=(6,1),LENGTH=15,ATTRB=(PROT),                    X
               INITIAL='BALANCE:'
CBAL     DFHMDF POS=(6,17),LENGTH=12,ATTRB=(PROT,ASKIP),             X
               PICOUT='ZZZ,ZZ9.99'
*
         DFHMDF POS=(7,1),LENGTH=15,ATTRB=(PROT),                    X
               INITIAL='STATUS:'
CSTAT    DFHMDF POS=(7,17),LENGTH=10,ATTRB=(PROT,ASKIP)
*
MSG      DFHMDF POS=(22,1),LENGTH=79,ATTRB=(PROT,BRT,ASKIP)
*
         DFHMDF POS=(24,1),LENGTH=79,ATTRB=(PROT,NORM,ASKIP),        X
               INITIAL='PF3=EXIT  ENTER=INQUIRE'
*
CUSTMSET DFHMSD TYPE=FINAL
      END
```

### สรุปการออกแบบ

- **บรรทัด 1**: หัวเรื่องหน้าจอ (protected, bright, ไม่มีชื่อ label เพราะไม่ต้องอ่าน/เขียนจากโปรแกรม)
- **บรรทัด 3**: ฟิลด์ input เดียวของหน้าจอนี้ (`CUSTID`) มี `IC` เพื่อให้เคอร์เซอร์กระโดดมาที่นี่ทันที
  และมี `NUM` เพื่อบังคับว่าต้องเป็นตัวเลขเท่านั้น
- **บรรทัด 5–7**: ฟิลด์ output ล้วน ๆ (`CNAME`, `CBAL`, `CSTAT`) ทั้งหมดเป็น `PROT` + `ASKIP` เพื่อ
  ป้องกันไม่ให้ผู้ใช้พิมพ์ทับข้อมูลที่โปรแกรมแสดงผล
- **บรรทัด 22**: `MSG` — ฟิลด์ที่ใช้แสดงข้อความแจ้งเตือน/ข้อผิดพลาดจากโปรแกรม (เว้นว่างตอนแรก
  โปรแกรมจะ `MOVE` ข้อความเข้าไปก่อน `SEND MAP` เมื่อพบปัญหา เช่น "CUSTOMER NOT FOUND")
- **บรรทัด 24**: คำแนะนำการใช้ PF Key ที่ตายตัว (ไม่มี label เพราะไม่เปลี่ยนแปลง)

### ข้อควรระวัง

- สังเกตว่าฟิลด์ output ทุกตัวใช้ `ASKIP` คู่กับ `PROT` เสมอ — ถ้าลืม `ASKIP` เคอร์เซอร์จะยังคง
  "ค้าง" รอที่ฟิลด์ protected นั้น (แม้พิมพ์ไม่ได้ ก็ยังกดลูกศรเข้าไปหยุดได้ ทำให้ผู้ใช้สับสนว่าทำไม
  พิมพ์ไม่ได้) `ASKIP` ทำให้เคอร์เซอร์ข้ามฟิลด์นี้ไปยังฟิลด์ที่พิมพ์ได้ถัดไปโดยอัตโนมัติ
- บรรทัดข้อความแจ้งเตือน (`MSG`) ควรมีความกว้างเพียงพอสำหรับข้อความที่ยาวที่สุดที่โปรแกรมจะแสดง
  (79 คอลัมน์ในตัวอย่างนี้ เกือบเต็มความกว้างจอ) เพื่อไม่ให้ข้อความถูกตัดทิ้ง

### แบบฝึกหัดที่ 628.1

**โจทย์**: จงเพิ่มฟิลด์ใหม่ `CPHONE` (เบอร์โทรศัพท์ลูกค้า, ยาว 10 ตัวอักษร, protected/output-only)
ไว้ที่บรรทัด 8 คอลัมน์ 17 พร้อม label "PHONE:" ที่บรรทัด 8 คอลัมน์ 1

**เฉลย**:

```
         DFHMDF POS=(8,1),LENGTH=15,ATTRB=(PROT),                    X
               INITIAL='PHONE:'
CPHONE   DFHMDF POS=(8,17),LENGTH=10,ATTRB=(PROT,ASKIP)
```

ต้องแทรกทั้งสอง `DFHMDF` นี้ก่อนฟิลด์ `MSG` (บรรทัด 22) เพื่อรักษาลำดับจากบนลงล่างของหน้าจอ และเพิ่ม
`CPHONEO`/`CPHONEI` เข้าไปในโปรแกรม COBOL หลัง assemble Symbolic Map ใหม่แล้ว

## ขั้นตอนที่ 629: เชื่อม Symbolic Map เข้ากับโปรแกรม COBOL

### วงจรชีวิตของหน้าจอในโปรแกรม CICS

มาดูว่าโปรแกรม COBOL ใช้ Symbolic Map จากขั้นตอนที่ 626 และ 628 อย่างไรจริง ๆ ในทางปฏิบัติ

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้ (ต้องมี CICS Translator + CICS runtime)**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. CUSTINQ.
       AUTHOR. COBOL-COURSE.

       ENVIRONMENT DIVISION.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
      *> The Symbolic Map copybook generated by the BMS Assembler
      *> in step 626, brought in via COPY exactly like any other
      *> copybook learned in Part 033.
           COPY CUSTMSET.

       01  WS-CUST-NAME             PIC X(20).
       01  WS-CUST-BALANCE          PIC 9(9)V99.
       01  WS-DISPLAY-BALANCE       PIC ZZZ,ZZ9.99.
       01  WS-FOUND-FLAG            PIC X VALUE "N".
           88  CUSTOMER-FOUND       VALUE "Y".

       PROCEDURE DIVISION.
       MAIN-PARA.
      *> First time this transaction runs, EIBCALEN is 0 (no
      *> COMMAREA yet) - send the blank inquiry screen and wait.
           IF EIBCALEN = 0
               PERFORM SEND-INITIAL-SCREEN
           ELSE
               PERFORM RECEIVE-AND-PROCESS
           END-IF.
           EXEC CICS RETURN
               TRANSID('CINQ')
           END-EXEC.

       SEND-INITIAL-SCREEN.
           MOVE SPACES TO CUSTINQ1O.
           EXEC CICS SEND MAP('CUSTINQ1')
               MAPSET('CUSTMSET')
               ERASE
           END-EXEC.

       RECEIVE-AND-PROCESS.
           EXEC CICS RECEIVE MAP('CUSTINQ1')
               MAPSET('CUSTMSET')
               INTO(CUSTINQ1I)
           END-EXEC.

      *> Guard clause from step 626 - check the -L field before
      *> trusting the -I value at all.
           IF CUSTIDL > 0
               PERFORM LOOKUP-CUSTOMER
               PERFORM BUILD-RESPONSE-SCREEN
           ELSE
               MOVE SPACES TO MSGO
               STRING 'PLEASE ENTER A CUSTOMER ID' DELIMITED BY SIZE
                   INTO MSGO
               EXEC CICS SEND MAP('CUSTINQ1')
                   MAPSET('CUSTMSET')
                   DATAONLY
               END-EXEC
           END-IF.

       LOOKUP-CUSTOMER.
      *> In a real system this would be a VSAM READ (Part 055) or
      *> a DB2 EXEC SQL SELECT (Part 058) keyed by CUSTIDI.
      *> Simulated here for illustration only.
           IF CUSTIDI = 10001
               MOVE "SOMCHAI JAIDEE" TO WS-CUST-NAME
               MOVE 5000.00 TO WS-CUST-BALANCE
               SET CUSTOMER-FOUND TO TRUE
           ELSE
               MOVE "N" TO WS-FOUND-FLAG
           END-IF.

       BUILD-RESPONSE-SCREEN.
           MOVE SPACES TO CUSTINQ1O.
           IF CUSTOMER-FOUND
               MOVE WS-CUST-NAME TO CNAMEO
               MOVE WS-CUST-BALANCE TO WS-DISPLAY-BALANCE
               MOVE WS-DISPLAY-BALANCE TO CBALO
               MOVE 'ACTIVE' TO CSTATO
               MOVE SPACES TO MSGO
           ELSE
               MOVE SPACES TO CNAMEO
               MOVE SPACES TO CBALO
               MOVE SPACES TO CSTATO
               STRING 'CUSTOMER NOT FOUND' DELIMITED BY SIZE
                   INTO MSGO
      *> Turn the message field bright red to draw attention -
      *> this is the point of having a writable -A field.
               MOVE DFHBMBRY TO MSGA
           END-IF.
           EXEC CICS SEND MAP('CUSTINQ1')
               MAPSET('CUSTMSET')
               DATAONLY
           END-EXEC.
```

### อธิบายจุดสำคัญ

- **`COPY CUSTMSET.`**: ดึง Symbolic Map เข้ามาใน `WORKING-STORAGE SECTION` — เหมือนกับที่เรียนใน
  Part 033 ทุกประการ เพียงแต่เนื้อหาของ copybook นี้มาจาก BMS Assembler แทนที่จะเขียนเอง
- **`EXEC CICS RECEIVE MAP(...) INTO(CUSTINQ1I)`**: รับข้อมูลจากจอเข้าสู่โครงสร้าง `-I` (Input) ตามที่
  อธิบายในขั้นตอนที่ 626
- **`IF CUSTIDL > 0`**: การ์ดตรวจสอบ MDT ก่อนใช้งานค่า ตามที่เตือนไว้ในขั้นตอนที่ 626
- **`EXEC CICS SEND MAP(...) DATAONLY`**: ใช้ `DATAONLY` แทน `ERASE` เมื่อต้องการส่งเฉพาะข้อมูลที่
  เปลี่ยนแปลง (ฟิลด์ output ใหม่) โดยไม่ต้องล้างและวาดหน้าจอทั้งหมดใหม่ (ประหยัดการส่งข้อมูลเครือข่าย
  ตามหลักการเดียวกับ MDT ในขั้นตอนที่ 625)
- **`MOVE DFHBMBRY TO MSGA`**: `DFHBMBRY` คือค่าคงที่ (ที่มาจาก copybook มาตรฐาน `DFHBMSCA` ของ CICS)
  แทนค่า attribute byte สำหรับ "protected, bright red" — นี่คือตัวอย่างการเปลี่ยน attribute ของ
  ฟิลด์ **ระหว่างที่โปรแกรมทำงาน** ผ่านฟิลด์ `-A` ที่กล่าวถึงในขั้นตอนที่ 626

### ข้อควรระวัง

- โค้ดที่มี `EXEC CICS` **ต้องผ่าน CICS Translator ก่อนเสมอ** (แปลง `EXEC CICS ... END-EXEC` เป็น
  `CALL 'DFHEI1' ...` ที่ COBOL Compiler ธรรมดาเข้าใจ) คล้ายกับที่ Part 058 อธิบายเรื่อง DB2
  Precompiler สำหรับ `EXEC SQL` — GnuCOBOL ไม่มี CICS Translator เช่นกัน
- ต้อง `MOVE SPACES TO CUSTINQ1O` (หรือฟิลด์ output ที่เกี่ยวข้อง) **ก่อน** ตั้งค่าฟิลด์ใหม่ทุกครั้ง
  มิฉะนั้นข้อมูลเก่าจากรอบก่อนหน้าอาจค้างอยู่ในฟิลด์ที่ไม่ได้ตั้งค่าใหม่ (หลักการเดียวกับ
  `MOVE SPACES TO RPT-RECORD` ก่อน `STRING` ที่ Part 027/028 เตือนไว้ซ้ำหลายครั้ง)

### แบบฝึกหัดที่ 629.1

**โจทย์**: จงอธิบายว่าทำไมโปรแกรมจึงใช้ `DATAONLY` แทน `ERASE` ตอนส่งหน้าจอผลลัพธ์กลับไป
(`BUILD-RESPONSE-SCREEN`) ทั้งที่ตอนส่งหน้าจอเริ่มต้น (`SEND-INITIAL-SCREEN`) ใช้ `ERASE`

**เฉลย**: `ERASE` จะล้างหน้าจอทั้งหมดแล้ววาดใหม่ทั้งหมด เหมาะสำหรับการแสดงหน้าจอครั้งแรก (ยังไม่มี
อะไรอยู่บนจอเลย) ส่วน `DATAONLY` จะส่งเฉพาะข้อมูลของฟิลด์ output ที่เปลี่ยนแปลง โดยไม่แตะต้อง label
หรือโครงสร้างหน้าจอที่วาดไว้แล้วตั้งแต่รอบแรก (เช่น หัวเรื่อง "CUSTOMER INQUIRY" หรือคำแนะนำ PF Key
ที่บรรทัด 24 ไม่จำเป็นต้องส่งซ้ำ) การใช้ `DATAONLY` จึงประหยัดข้อมูลที่ต้องส่งผ่านเครือข่ายมากกว่า
`ERASE` และทำให้จอไม่กระพริบ (flicker) เพราะไม่ต้องล้างจอทั้งหมดทุกรอบ

## ขั้นตอนที่ 630: เปรียบเทียบ SCREEN SECTION กับ BMS และสรุปหลักการออกแบบหน้าจอ

### ตารางเปรียบเทียบฉบับสมบูรณ์

ตอนนี้เราเรียนรู้ BMS ครบทุกองค์ประกอบแล้ว มาสรุปเปรียบเทียบกับ `SCREEN SECTION` (Part 040) อย่าง
ละเอียดอีกครั้ง เพื่อให้เห็นภาพรวมทั้งสองแนวทางในการสร้าง UI แบบ text-mode:

| แง่มุม | SCREEN SECTION (Part 040) | BMS + CICS (Part นี้) |
|---|---|---|
| ระดับการแยกส่วน (Separation) | หน้าจอกับ logic อยู่ไฟล์เดียวกัน | แยกไฟล์ BMS ออกจากโปรแกรม COBOL อย่างสมบูรณ์ |
| หน่วยที่ใช้กำหนดตำแหน่ง | `LINE`/`COLUMN` clause ใน COBOL | `POS=(line,col)` ใน `DFHMDF` |
| การป้องกันฟิลด์ | `PROTECTED` clause | `ATTRB=(PROT)` |
| การเน้นข้อความ | `HIGHLIGHT`/`REVERSE-VIDEO` | `ATTRB=(BRT)`/สี ผ่าน `MAPATTS` |
| กลไกส่งเฉพาะที่เปลี่ยน | ไม่มี (ส่ง/รับทั้งหมดที่ compile ไว้) | มี ผ่าน MDT (ขั้นตอนที่ 625) |
| ต้องมี Transaction Manager ไหม | ไม่ต้อง (รันได้แบบ standalone) | ต้องมี CICS ควบคุมวงจรชีวิต |
| เหมาะกับ | โปรแกรมเดี่ยว, เครื่องมือ admin, การเรียนรู้แนวคิด UI พื้นฐาน | ระบบ Transaction Processing ขนาดใหญ่ที่มีผู้ใช้พร้อมกันหลักพัน-หมื่นคน |
| ทดสอบบน GnuCOBOL ได้ไหม | ได้ (ทดสอบจริงแล้วใน Part 040) | ไม่ได้ (ต้องมี CICS จริง) |

### หลักการออกแบบหน้าจอที่ควรยึดถือ (ใช้ได้ทั้งสองแนวทาง)

1. **จัดกลุ่มฟิลด์ที่เกี่ยวข้องกันให้อยู่ใกล้กัน** — ฟิลด์ชื่อ ที่อยู่ เบอร์โทร ควรอยู่ติดกันเป็นกลุ่ม
   ไม่กระจัดกระจาย
2. **ใช้ label ที่ชัดเจนและสม่ำเสมอ** — ใช้รูปแบบ label เดียวกันทั้งระบบ (เช่น ใช้ตัวพิมพ์ใหญ่ทั้งหมด
   ลงท้ายด้วย `:` เสมอ)
3. **สงวนพื้นที่บรรทัดสุดท้าย ๆ ไว้สำหรับข้อความระบบ** — บรรทัดข้อความแจ้งเตือน (`MSG`) และคำแนะนำ
   PF Key ควรอยู่ตำแหน่งเดียวกันทุกหน้าจอในระบบเดียวกัน เพื่อให้ผู้ใช้คุ้นเคย
4. **ใส่ `IC` ให้กับฟิลด์แรกที่ผู้ใช้ต้องกรอกเสมอ** — ลดภาระผู้ใช้ในการเลื่อนเคอร์เซอร์เอง
5. **ฟิลด์ output ทุกตัวควรเป็น `PROT` + `ASKIP` เสมอ** — ป้องกันผู้ใช้พิมพ์ทับและไม่ทำให้เคอร์เซอร์
   ค้าง (ทบทวนจากขั้นตอนที่ 628)
6. **ตรวจสอบ `-L` ก่อนใช้ `-I` เสมอ** — ป้องกันการนำข้อมูลขยะจากฟิลด์ที่ไม่ถูกแตะต้องไปประมวลผล
   (ทบทวนจากขั้นตอนที่ 626 และ 629)

### สรุปเส้นทางความรู้ของ Part นี้

Part นี้พาเราเดินทางจาก "ทำไมต้องแยกหน้าจอออกจากโปรแกรม" ไปจนถึงรายละเอียดทางเทคนิคที่ลึกที่สุดของ
3270 Data Stream (Attribute Byte, MDT) และปิดท้ายด้วยการเขียนโปรแกรม COBOL จริงที่ใช้ Symbolic Map
ครบวงจร ความรู้ทั้งหมดนี้เป็นรากฐานสำคัญสำหรับ Part 064 ที่จะสอนแนวคิดที่ซับซ้อนยิ่งขึ้น: **การเขียน
โปรแกรม Pseudo-conversational** ซึ่งเป็นวิธีที่ CICS จัดการหลายหน้าจอต่อเนื่องกันโดยไม่ผูกทรัพยากร
ของระบบไว้กับผู้ใช้แต่ละคนตลอดเวลา

### แบบฝึกหัดที่ 630.1

**โจทย์**: จงออกแบบ (วาดคร่าว ๆ เป็นตาราง หรือบรรยาย) หน้าจอ CICS สำหรับ "แก้ไขที่อยู่ลูกค้า" ที่มี
ฟิลด์ต่อไปนี้: รหัสลูกค้า (input, numeric), ที่อยู่บรรทัด 1 (input, ตัวอักษร 30 ตัว), ที่อยู่บรรทัด 2
(input, ตัวอักษร 30 ตัว), รหัสไปรษณีย์ (input, numeric 5 หลัก) พร้อมระบุ `ATTRB=` ที่เหมาะสมสำหรับ
แต่ละฟิลด์ และตำแหน่งฟิลด์ที่ไม่ชนกัน

**เฉลยแนวทาง**:

```
         DFHMDF POS=(2,1),LENGTH=12,ATTRB=(PROT,BRT),                X
               INITIAL='CUSTOMER ID:'
CUSTID   DFHMDF POS=(2,14),LENGTH=5,ATTRB=(UNPROT,NUM,IC),           X
               PICIN='9(5)'
         DFHMDF POS=(4,1),LENGTH=12,ATTRB=(PROT),                    X
               INITIAL='ADDRESS 1:'
ADDR1    DFHMDF POS=(4,14),LENGTH=30,ATTRB=(UNPROT)
         DFHMDF POS=(5,1),LENGTH=12,ATTRB=(PROT),                    X
               INITIAL='ADDRESS 2:'
ADDR2    DFHMDF POS=(5,14),LENGTH=30,ATTRB=(UNPROT)
         DFHMDF POS=(6,1),LENGTH=12,ATTRB=(PROT),                    X
               INITIAL='POSTAL CODE:'
PCODE    DFHMDF POS=(6,14),LENGTH=5,ATTRB=(UNPROT,NUM),              X
               PICIN='9(5)'
```

จุดสำคัญที่ต้องตรวจสอบ: (1) ทุกฟิลด์ input มี label protected คั่นอยู่ก่อนหน้าเสมอ ไม่มีฟิลด์ input
สองตัวติดกันโดยไม่มีอะไรคั่น (ทบทวนข้อควรระวังในขั้นตอนที่ 624) (2) ตำแหน่งคอลัมน์เริ่มต้นของแต่ละฟิลด์
(`14`) ไม่ทับซ้อนกับความยาวของ label ก่อนหน้า (label ยาวสุด 12 ตัว + เว้น 1 ช่อง = เริ่มที่คอลัมน์ 14
พอดี) (3) มีเพียงฟิลด์แรก (`CUSTID`) ที่ใส่ `IC` เพื่อให้เคอร์เซอร์เริ่มต้นที่นี่

## สรุปท้ายบท

Part นี้พาคุณเจาะลึกเทคโนโลยี **BMS (Basic Mapping Support)** ซึ่งเป็นรากฐานของการออกแบบหน้าจอ
ในโลก CICS ตั้งแต่แนวคิดพื้นฐานไปจนถึงรายละเอียดทางเทคนิคที่ลึกที่สุด:

- ทำไมต้องแยกการออกแบบหน้าจอออกจากตรรกะโปรแกรม และเทียบเคียงกับ `SCREEN SECTION` จาก Part 040
- โครงสร้าง Macro ทั้งสาม: `DFHMSD` (Mapset), `DFHMDI` (Map), `DFHMDF` (Field)
- Attribute Byte และกลไก **Modified Data Tag (MDT)** ที่ทำให้ CICS ประหยัดแบนด์วิดท์เครือข่าย
- โครงสร้าง Symbolic Map Copybook พร้อม suffix `-L`, `-F`, `-A`, `-I`, `-O` และเหตุผลที่ต้องมี
  `REDEFINES` ระหว่างโครงสร้าง Input (`...I`) กับ Output (`...O`)
- ความแตกต่างระหว่าง Physical Map (load module) กับ Symbolic Map (COBOL copybook)
- ตัวอย่างโปรแกรม COBOL สมบูรณ์ที่เชื่อมต่อกับ Symbolic Map จริง
- หลักการออกแบบหน้าจอที่ดีซึ่งใช้ได้ทั้งกับ BMS และ SCREEN SECTION
