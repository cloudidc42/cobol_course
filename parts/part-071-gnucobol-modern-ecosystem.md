## ขั้นตอนที่ 701: GnuCOBOL ไม่ใช่ Native Compiler — มันคือ Transpiler-แล้วเรียก-gcc

### ความเข้าใจผิดที่พบบ่อย

หลายคนที่เริ่มเรียน COBOL ด้วย GnuCOBOL (รวมถึงคุณเองในช่วงแรก ๆ ของหลักสูตรนี้ที่ Part 002) มักเข้าใจว่า
`cobc` ทำงานเหมือนคอมไพเลอร์ทั่วไป: **อ่านซอร์สโค้ด COBOL แล้วแปลงเป็นภาษาเครื่อง (machine code) โดยตรง**
เหมือนที่ `gcc` แปลง C เป็นภาษาเครื่อง หรือ `javac` แปลง Java เป็น bytecode

ความจริงแล้ว **GnuCOBOL ทำงานเป็นสองขั้นตอนซ้อนกัน**:

1. **แปลง (Translate)**: `cobc` อ่านซอร์สโค้ด COBOL แล้ว**สร้างซอร์สโค้ดภาษา C ขึ้นมาใหม่**ที่ทำงาน
   เทียบเท่ากับโปรแกรม COBOL ต้นฉบับทุกประการ
2. **คอมไพล์ (Compile)**: `cobc` เรียก `gcc` (หรือคอมไพเลอร์ C ตัวอื่นที่ตั้งค่าไว้) มาคอมไพล์ไฟล์ C ที่
   สร้างขึ้นนั้นให้เป็นภาษาเครื่องจริง ๆ อีกทีหนึ่ง แล้วเชื่อมโยง (link) เข้ากับ **libcob** (runtime
   library ของ GnuCOBOL ที่ให้บริการฟังก์ชันพื้นฐาน เช่น `cob_display`, `cob_stop_run`)

พูดง่าย ๆ คือ **GnuCOBOL "ยืมจมูก" ของ gcc หายใจ** — มันไม่ได้ผลิตภาษาเครื่องด้วยตัวเอง แต่ใช้ gcc ที่
เป็นคอมไพเลอร์ C ที่โตเต็มที่และผ่านการพัฒนามาหลายสิบปีเป็นเครื่องมือทำงานหนักแทน นี่คือเหตุผลที่ Part 002
บอกให้คุณติดตั้ง **ทั้ง GnuCOBOL และ gcc** คู่กันเสมอ (แม้ผู้เรียนส่วนใหญ่จะไม่เคยเรียก `gcc` ตรง ๆ เลยจน
ถึงตอนนี้)

### แผนภาพกระบวนการทั้งหมด

```
  step701.cob                    step701.c                    step701 (executable)
  (COBOL source)                 (generated C source)         (machine code)

  IDENTIFICATION DIVISION.       #include <libcob.h>
  PROGRAM-ID. STEP701.    ---->  int main(...) {         ---->  01001111 01000011 ...
  PROCEDURE DIVISION.              cob_init(...);                (real x86-64 instructions)
  DISPLAY "Hello.".                cob_display(...);
  STOP RUN.                        cob_stop_run(...);
                                  }

         [cobc: TRANSLATE]              [gcc: COMPILE + LINK against libcob.so]
```

### อธิบายทีละส่วน

- บรรทัด `preprocessing` และ `parsing`: `cobc` อ่านและตรวจสอบไวยากรณ์ COBOL ก่อน (ยังไม่เกี่ยวกับ C เลย)
  ชื่อไฟล์ชั่วคราว (`/tmp/cob13586_0.cob`) จะแตกต่างกันไปในแต่ละครั้งที่รัน เพราะเป็นตัวเลขสุ่ม/PID
- บรรทัด `translating`: **นี่คือขั้นตอนหัวใจของ Part นี้** — `cobc` แปลงไฟล์ COBOL ที่ผ่านการตรวจสอบแล้ว
  ให้เป็นไฟล์ C (`.c`) จะเจาะลึกไฟล์นี้แบบเต็ม ๆ ในขั้นตอนที่ 702
- บรรทัด `executing: gcc -c ...`: `cobc` เรียก **`gcc` ครั้งที่หนึ่ง** เพื่อคอมไพล์ไฟล์ C ที่เพิ่งสร้างให้
  เป็น object file (`.o`) — สังเกตว่าคำสั่งนี้เป็นคำสั่ง `gcc` ธรรมดา ไม่มีอะไรเกี่ยวกับ COBOL เลย
- บรรทัด `executing: gcc ... -lcob`: `cobc` เรียก **`gcc` ครั้งที่สอง** เพื่อ link object file เข้ากับ
  **`libcob`** (flag `-lcob`) ให้กลายเป็นไฟล์ execute สมบูรณ์ — `libcob` คือคลังฟังก์ชัน runtime ที่ให้
  บริการทุกอย่างที่ COBOL ต้องการตอนรันจริง เช่น การแสดงผล (`cob_display`), การจัดการไฟล์, เลขคณิตทศนิยม
  ที่แม่นยำ (Part 001 ขั้นตอนที่ 5), และการจัดการ `CALL`/`PERFORM`
- **สรุปสั้น ๆ**: `cobc -x` = (ตรวจสอบไวยากรณ์ COBOL) + (แปลงเป็น C) + (เรียก `gcc -c`) + (เรียก
  `gcc` link กับ `-lcob`) ทั้งหมดในคำสั่งเดียว ซ่อนความซับซ้อนทั้งหมดไว้เบื้องหลังเพื่อให้ใช้งานง่ายเหมือน
  คอมไพเลอร์ทั่วไป

### ทำไมต้องออกแบบมาแบบนี้

1. **ประหยัดแรงพัฒนา**: การเขียน code generator ที่ผลิตภาษาเครื่องโดยตรงสำหรับทุกสถาปัตยกรรม CPU (x86,
   ARM, ฯลฯ) เป็นงานมหาศาล การผลิต C แทนแล้วให้ `gcc` (ซึ่งรองรับหลายสถาปัตยกรรมอยู่แล้ว) ทำงานส่วนที่
   ยากที่สุดต่อ ทำให้ GnuCOBOL **พกพาข้ามแพลตฟอร์มได้ทันที** ไปตามที่ `gcc` รองรับ (นี่คือเหตุผลสำคัญ
   ข้อหนึ่งที่ Part 001 ขั้นตอนที่ 7 บอกว่า GnuCOBOL "รันได้ทุกแพลตฟอร์ม")
2. **ได้ Optimizer ของ gcc มาฟรี**: `gcc` มี Optimization ระดับสูงที่พัฒนามาหลายสิบปี GnuCOBOL ได้ใช้
   ประโยชน์จากสิ่งนี้ทันทีโดยไม่ต้องพัฒนา Optimizer ของตัวเอง
3. **นี่ไม่ใช่เรื่องแปลกในโลกคอมไพเลอร์**: ภาษาอื่น ๆ จำนวนมากก็ใช้แนวทาง "Transpile-to-C" เช่นกัน (เช่น
   บางเวอร์ชันของ Eiffel, Nim ในโหมดหนึ่ง) และแม้แต่ COBOL เชิงพาณิชย์บางระบบบนแพลตฟอร์มที่ไม่ใช่
   Mainframe ก็ใช้แนวทางคล้ายกันนี้เช่นกัน (รายละเอียดเปรียบเทียบเชิงลึกอยู่ในขั้นตอนที่ 708)

### ข้อควรระวัง

- เพราะพึ่งพา `gcc`, เครื่องที่จะ**คอมไพล์** โปรแกรม COBOL ด้วย GnuCOBOL **ต้องติดตั้ง gcc (หรือ C
  compiler ที่ compatible) ไว้เสมอ** แม้ผู้เขียนโปรแกรมจะไม่เคยเห็นภาษา C เลยก็ตาม — นี่ต่างจากคอมไพเลอร์
  เชิงพาณิชย์บางตัวที่ฝัง code generator ของตัวเองไว้ครบในซอฟต์แวร์เดียว ไม่ต้องพึ่งคอมไพเลอร์ภาษาอื่น
- เครื่องที่จะ**รัน**โปรแกรมที่คอมไพล์แล้ว (ไม่จำเป็นต้องคอมไพล์เอง) ยังคงต้องมี **`libcob` runtime
  library** ติดตั้งอยู่ (ไม่ต้องมี `gcc` หรือ `cobc` ก็ได้ถ้าไม่ต้องคอมไพล์เพิ่ม) รายละเอียดเรื่อง
  dynamic linking นี้จะอธิบายเต็มรูปแบบในขั้นตอนที่ 704
- คำสั่ง `cobc -x -v` มีประโยชน์มากตอน**แก้ปัญหาการคอมไพล์ที่ซับซ้อน** (เช่น หา library ไม่เจอตอน link)
  เพราะทำให้เห็นคำสั่ง `gcc` จริงที่ถูกเรียก สามารถคัดลอกมารันเองเพื่อ debug ทีละขั้นตอนได้

### แบบฝึกหัดที่ 701.1

**โจทย์**: จงอธิบายว่าทำไมข้อความ error จากการคอมไพล์ COBOL ผิดไวยากรณ์ (เช่น ลืมใส่ `.` ท้ายประโยค) กับ
ข้อความ error จากปัญหาตอน link (เช่น หา library ไม่เจอ) จึงมีรูปแบบและช่วงเวลาที่ปรากฏต่างกัน

**เฉลยแนวทาง**: error ทางไวยากรณ์ COBOL เกิดขึ้นในขั้นตอน "parsing" ซึ่งเป็นงานของ `cobc` เองล้วน ๆ
ก่อนที่จะมีการสร้างไฟล์ C ด้วยซ้ำ ข้อความจึงอ้างอิงบรรทัดและไวยากรณ์ COBOL โดยตรง (เช่น
`step701.cob:7: error: ...`) ส่วน error ตอน link (เช่น undefined reference, library not found) เกิด
ขึ้นในขั้นตอน `executing: gcc ... -lcob` ซึ่งเป็นงานของ `gcc`/linker ล้วน ๆ ข้อความจึงมักมาในรูปแบบของ
`gcc`/`ld` เอง (เช่น `undefined reference to ...`) ไม่ใช่รูปแบบข้อความของ `cobc` เพราะ ณ จุดนั้น `cobc`
ได้ส่งไม้ต่อให้ `gcc` ทำงานแทนตัวเองไปแล้วอย่างสมบูรณ์

## ขั้นตอนที่ 702: เปิดฝากระโปรง — ใช้ cobc -C อ่านโค้ด C ที่ถูกสร้างขึ้นจริง

### แฟล็ก -C คือหน้าต่างสู่กลไกภายใน

ขั้นตอนที่แล้วเราเห็นแค่ "ชื่อ" ของไฟล์ C ที่ถูกสร้างขึ้นชั่วคราว (แล้วถูกลบทิ้งทันทีหลังคอมไพล์เสร็จ)
ขั้นตอนนี้เราจะสั่งให้ `cobc` **หยุดแค่ขั้นตอนแปลงเป็น C แล้วเก็บไฟล์นั้นไว้ให้เราอ่าน** ด้วยแฟล็ก `-C`
(แปลว่า "translation only")

```bash
cobc -C step701.cob -o step701.c
wc -l step701.c
```

โปรแกรม COBOL 8 บรรทัดถูกขยายเป็นโค้ด C เกือบ 200 บรรทัด! มาดูส่วนที่สำคัญที่สุดกัน

### ส่วนหัวไฟล์และ Include

```c

#include <stdio.h>
#include <string.h>
#define  COB_KEYWORD_INLINE __inline
```

`libcob.h` คือ header ที่ประกาศฟังก์ชันและโครงสร้างข้อมูลทั้งหมดของ runtime library — ทุกไฟล์ C ที่
GnuCOBOL สร้างจะ include ไฟล์นี้เสมอ

### ฟังก์ชันที่แทน PROCEDURE DIVISION

```c
static int
STEP701_ (const int entry)
{
  /* ... setup code omitted ... */

  /* PROCEDURE DIVISION */

  /* Line: 5         : Entry     STEP701                 : step701.cob */
  l_2:;

  /* Line: 6         : Paragraph MAIN-PARA               : step701.cob */
  /* Line: 7         : DISPLAY            : step701.cob */
  cob_display (0, 1, 1, &c_1);
  /* Line: 8         : STOP RUN           : step701.cob */
  cob_stop_run (b_2);

  /* ... cleanup code omitted ... */
}
```

สังเกตสิ่งที่น่าทึ่งที่สุด: **`cobc` แทรกคอมเมนต์บอกเลขบรรทัดของไฟล์ `.cob` ต้นฉบับไว้กำกับทุกคำสั่ง**
(`/* Line: 7 ... */`) นี่คือกลไกที่ทำให้ error message ตอน runtime crash (เช่นที่ Part 031 ขั้นตอนที่
304 เคยแสดงให้เห็น) สามารถอ้างอิงกลับไปยังเลขบรรทัดในไฟล์ COBOL ต้นฉบับได้ แม้ตัวโปรแกรมที่รันจริงจะเป็น
C ไปแล้วก็ตาม

จุดสำคัญอีกจุด: `DISPLAY "Hello from GnuCOBOL."` กลายเป็นการเรียกฟังก์ชัน **`cob_display(...)`** และ
`STOP RUN` กลายเป็น **`cob_stop_run(...)`** — ทุกคำสั่ง COBOL ที่เราเรียนมาตลอด 70 Part ล้วนถูกแปลงเป็น
การเรียกฟังก์ชันจาก `libcob` แบบนี้ทั้งหมด (`ADD` เป็น `cob_add`, `MOVE` เป็น `cob_move`,
`PERFORM` เป็น C `goto`/loop และอื่น ๆ)

### จุดที่ต่างกันเมื่อใช้ -x ร่วมด้วย: ฟังก์ชัน main() ตัวจริง

ลองสั่งแปลงแบบเดียวกันอีกครั้ง แต่เพิ่ม `-x` (บอกว่านี่คือโปรแกรมที่รันเดี่ยวได้ ไม่ใช่ subprogram):

```bash
cobc -x -C step701.cob -o step701_x.c
grep -c "main (int argc" step701.c
grep -c "main (int argc" step701_x.c
```

```
0
1
```

ไฟล์ที่แปลง**โดยไม่มี** `-x` ไม่มีฟังก์ชัน C `main()` เลย! ส่วนไฟล์ที่แปลง**พร้อม** `-x` มีฟังก์ชันนี้เพิ่ม
เข้ามา:

```c
/* Main function */
int
main (int argc, char **argv)
{
  cob_init (argc, argv);
  cob_stop_run (STEP701 ());
}
```

โค้ดสั้น ๆ แค่ 3 บรรทัดนี้อธิบายทุกอย่างที่ `-x` ทำ: **เริ่มต้น runtime ของ GnuCOBOL ด้วย `cob_init`
แล้วเรียกฟังก์ชันของโปรแกรม COBOL หลัก (`STEP701()`) เหมือนเป็นฟังก์ชัน C ธรรมดาตัวหนึ่ง** จากนั้นส่งค่า
ที่ได้กลับไปให้ `cob_stop_run` เพื่อจบกระบวนการ — นี่คือคำตอบว่าทำไม `-x` (build executable) กับการไม่ใส่
`-x` (build เป็น callable module สำหรับ `CALL` จากโปรแกรมอื่น ตามที่เรียนมาใน Part 031) จึงให้ผลลัพธ์
เป็นไฟล์ที่มีพฤติกรรมต่างกันโดยสิ้นเชิง — **ความต่างอยู่ที่การมีหรือไม่มีฟังก์ชัน `main()` ตัวนี้เพียง
อย่างเดียว**

### ข้อควรระวัง

- ไฟล์ `.c` ที่สร้างจาก `-C` เป็นเพียง**ไฟล์ชั่วคราวเพื่อการศึกษา**เท่านั้น **ห้ามแก้ไขแล้วนำกลับไป
  คอมไพล์ใช้งานจริงเด็ดขาด** เพราะไฟล์นี้ไม่ได้ถูกออกแบบมาให้มนุษย์แก้ไข (ไม่มี error-checking กลับไปยัง
  COBOL ต้นฉบับอีกต่อไป) และจะทำให้เสียประโยชน์ของการดูแลซอร์สโค้ดที่ระดับ COBOL ไปเลย
- คุณจะเห็นไฟล์ผู้ช่วยเพิ่มเติมเช่น `step701.c.h` และ `step701.c.l.h` ถูกสร้างคู่กับ `.c` เสมอ (เก็บ
  ตัวแปร WORKING-STORAGE และโครงสร้าง module) — ไฟล์เหล่านี้ถูก `#include` เข้าไปในไฟล์ `.c` หลัก ไม่ใช่
  ไฟล์ขยะที่ลบทิ้งได้ตามใจถ้ายังต้องการคอมไพล์ไฟล์ `.c` นั้นต่อด้วยตัวเอง
- ชื่อฟังก์ชัน C ภายใน (เช่น `STEP701_`, ชื่อ label `l_2`) เป็นรายละเอียดการ implement ภายในของ GnuCOBOL
  ที่**อาจเปลี่ยนแปลงได้ในแต่ละเวอร์ชัน** ห้ามเขียนโค้ดใด ๆ ที่พึ่งพาชื่อเหล่านี้ตรง ๆ

### แบบฝึกหัดที่ 702.1

**โจทย์**: จงอธิบายว่าทำไมไฟล์ C ที่แปลงจากโปรแกรม COBOL ที่ไม่มี `-x` (ตั้งใจให้เป็น subprogram ที่ถูก
`CALL` เท่านั้น) จึงไม่มีฟังก์ชัน `main()` และผลจะเป็นอย่างไรถ้าพยายามคอมไพล์ไฟล์ `.c` แบบนั้นให้เป็น
executable โดยตรงด้วย `gcc` เอง (ไม่ผ่าน `cobc -x`)

**เฉลยแนวทาง**: ไฟล์ที่ไม่มี `main()` ถูกออกแบบมาให้เป็น "ส่วนประกอบ" ที่รอถูกเรียกจากโปรแกรมอื่น (ผ่าน
`CALL` เหมือนที่เรียนมาใน Part 031) ไม่ใช่จุดเริ่มต้นของกระบวนการเอง — ในระบบปฏิบัติการ การจะรันโปรแกรม
ได้ต้องมีจุดเริ่มต้นชื่อ `main()` เสมอ (นี่คือกฎของ C/OS ไม่ใช่กฎเฉพาะของ COBOL) ถ้าพยายาม `gcc -c
file.c -o file.o` แล้ว `gcc file.o -o file` โดยตรงโดยไม่มี `main()` อยู่ในไฟล์ใดเลยที่ link เข้าด้วยกัน
`gcc`/linker จะแจ้ง error ทำนอง `undefined reference to 'main'` ทันที เพราะ linker หาจุดเริ่มต้นของ
กระบวนการไม่เจอ

## ขั้นตอนที่ 703: ห้าขั้นตอนย่อยของการคอมไพล์ — แยกทำเองทีละสเต็ป

### cobc ซ่อนขั้นตอนย่อยไว้ 5 ระดับ

`cobc -x file.cob -o file` ที่เราพิมพ์กันจนคุ้นมือ แท้จริงแล้วครอบคลุมขั้นตอนย่อยถึง 5 ระดับ และ `cobc`
มีแฟล็กให้เราสั่งหยุดที่แต่ละระดับได้ ซึ่งมีประโยชน์มากเวลาต้อง debug ปัญหาการคอมไพล์ที่ซับซ้อน

| แฟล็ก | ความหมาย | ผลลัพธ์ที่ได้ |
|---|---|---|
| `-E` | Preprocess only (ระดับ COBOL) | ไฟล์ `.i` ที่ COPY ถูกขยายแล้ว คอลัมน์ถูก normalize แล้ว |
| `-C` | Translate only | ไฟล์ `.c` (ตามที่เห็นในขั้นตอนที่ 702) |
| `-S` | Compile only (ไม่ assemble) | ไฟล์ `.s` (assembly ของ CPU สถาปัตยกรรมนั้น) |
| `-c` | Compile and assemble, ไม่ link | ไฟล์ `.o` (object file) |
| *(ไม่ใส่แฟล็ก / ใส่ `-x`)* | ทำครบทุกขั้นตอน + link | ไฟล์ execute สมบูรณ์ |

### ทดสอบทั้ง 5 ระดับกับโปรแกรมเดียวกัน

```bash
head -8 step701.i
```

### อธิบายทีละส่วน

- **`-E` (preprocess)**: ยังคงเป็นข้อความ COBOL อ่านออกได้ปกติ (ไม่ใช่ C เลย) ขั้นตอนนี้ทำงานคล้าย C
  Preprocessor (`#include`, `#define`) แต่ในระดับ COBOL — คือการขยาย `COPY` Statement (Part 033) ให้
  กลายเป็นเนื้อหาเต็ม และปรับ column format ให้เป็นมาตรฐานเดียวกัน ก่อนที่ parser จะวิเคราะห์ไวยากรณ์ต่อ
- **`-S` (compile to assembly)**: ผลลัพธ์เป็นภาษา Assembly ของสถาปัตยกรรม CPU ปัจจุบัน (x86-64 ในที่นี้)
  — นี่คือขั้นตอนที่ `gcc` (ไม่ใช่ `cobc`) แปลง C เป็น Assembly ให้ `cobc` แค่ส่งต่อคำสั่ง `-S` ให้ `gcc`
  ทำงานแทน
- **`-c` (compile and assemble)**: ได้ **object file** (`.o`) ที่เป็นภาษาเครื่องแล้ว แต่ **ยังไม่ได้
  link** เข้ากับ `libcob` และยังไม่มีจุดเริ่มต้น `main()` จริงที่พร้อมรัน — `file` command ยืนยันว่าเป็น
  ไฟล์ ELF (รูปแบบไฟล์บน Linux) ประเภท "relocatable" คือยังรอการ link อยู่

### ประกอบร่างด้วยมือ: จาก .c ถึง Executable โดยไม่ใช้ cobc -x เลย

มาพิสูจน์ความเข้าใจให้แน่นด้วยการ **ทำทุกขั้นตอนเองด้วยมือ** โดยไม่ใช้ `cobc -x` เลยสักครั้ง — ใช้แค่
`cobc -C` แปลงเป็น C แล้วที่เหลือให้ `gcc` ทำงานตรง ๆ:

```bash
cobc -x -C step701.cob -o step701_gen.c
gcc -c step701_gen.c -o step701_gen.o
gcc step701_gen.o -o step701_gen_exe -lcob
./step701_gen_exe
```

```
Hello from GnuCOBOL.
```

โปรแกรมรันได้ผลลัพธ์เหมือนเดิมทุกประการ **โดยที่คำสั่ง `cobc` ถูกเรียกแค่ครั้งเดียว** (แปลงเป็น C) และ
`gcc` ทำงานที่เหลือทั้งหมดเอง (`-C` ต้องใส่ `-x` ควบคู่ด้วยเพื่อให้ไฟล์ C ที่ได้มีฟังก์ชัน `main()` ตามที่
อธิบายไว้ในขั้นตอนที่ 702 มิเช่นนั้น `gcc` จะ link ไม่ผ่านเพราะหา `main` ไม่เจอ)

### ข้อควรระวัง

- การ link ด้วยมือ**ต้องระบุ `-lcob` เสมอ** และมักต้องใส่ `-L` ตามด้วย path ที่ `libcob.so` อยู่ ถ้าไม่ได้
  ติดตั้งไว้ใน path มาตรฐานของระบบ (`cobc -x -v` ตามขั้นตอนที่ 701 จะโชว์ path ที่ถูกต้องให้เสมอ ถ้าไม่
  แน่ใจให้เปิดดูจากตรงนั้นก่อน)
- ไฟล์ `.i`, `.s`, `.o` ที่สร้างจากแต่ละแฟล็กเป็นไฟล์ชั่วคราวเพื่อการศึกษา/debug เท่านั้น ไม่ควรนำเข้า
  version control หรือแจกจ่ายเป็นส่วนหนึ่งของซอร์สโค้ดโปรเจกต์จริง
- ลำดับการ compile-then-link ต้องทำตามลำดับเสมอ (`.c` → `.o` → executable) จะข้ามขั้นตอนใดขั้นตอนหนึ่ง
  ไม่ได้ เช่น จะ link ไฟล์ `.c` ตรง ๆ (ข้าม `-c`) ก็ยังพอทำได้ (`gcc` จัดการให้อัตโนมัติ) แต่จะ compile
  ไฟล์ `.i`/`.s` ให้กลายเป็น `.o` ได้ต้องใช้ flag ที่ตรงกับประเภทไฟล์นั้นเสมอ

### แบบฝึกหัดที่ 703.1

**โจทย์**: จงอธิบายว่าทำไมขั้นตอน `-E` (preprocess) ของ GnuCOBOL จึงยังคงแสดงผลเป็นภาษา COBOL (ไม่ใช่
ภาษา C) ทั้งที่ C Preprocessor (`cpp`) ของภาษา C ทำงานคล้ายกันแต่ผลลัพธ์เป็นภาษา C

**เฉลยแนวทาง**: `-E` ของ `cobc` ทำงานอยู่ใน**ระดับ COBOL** เท่านั้น หน้าที่ของมันคือขยาย `COPY`
Statement (Part 033) และจัดรูปแบบคอลัมน์ให้เป็นมาตรฐาน ซึ่งทั้งหมดนี้เกิดขึ้น**ก่อน**ที่ parser ของ
`cobc` จะวิเคราะห์ไวยากรณ์ COBOL และ**ก่อน**ขั้นตอน translate เป็น C (`-C`) เสียอีก ลำดับที่ถูกต้องคือ
COBOL ต้นฉบับ → (E: ขยาย COPY, จัด column) → COBOL ที่ normalize แล้ว → (parse ตรวจไวยากรณ์) → (C:
แปลงเป็น C) → ไฟล์ C → (gcc compile) → object file → (gcc link) → executable ขั้นตอน `-E` จึงยังอยู่ใน
โลกของ COBOL ล้วน ๆ ไม่เกี่ยวกับ C เลยแม้แต่น้อย ต่างจาก C Preprocessor ที่ทำงานอยู่ในระบบนิเวศของภาษา
C โดยตรงตั้งแต่ต้น

## ขั้นตอนที่ 704: Static Linking กับ Dynamic Linking — libcob แบบฝังใน vs แบบใช้ร่วม

### สองวิธีที่โปรแกรมจะ "มี" libcob อยู่ด้วย

จากขั้นตอนที่ 701–703 เรารู้แล้วว่าทุกโปรแกรม COBOL ที่คอมไพล์ด้วย GnuCOBOL ต้องพึ่งพา `libcob` เสมอ
คำถามคือ **libcob จะถูกรวมเข้ากับไฟล์ execute ของเราอย่างไร?** มีสองแนวทางหลัก:

- **Dynamic Linking (ค่าเริ่มต้นของ GnuCOBOL)**: ไฟล์ execute เก็บแค่ "การอ้างอิง" ไปยัง `libcob.so`
  (ไฟล์ Shared Object) ระบบปฏิบัติการจะโหลด `libcob.so` เข้ามาในหน่วยความจำ**ตอนรันจริง** ทำให้ไฟล์
  execute มีขนาดเล็ก แต่ต้องมี `libcob.so` ติดตั้งอยู่ในเครื่องที่จะรันเสมอ
- **Static Linking**: โค้ดของ `libcob` (จากไฟล์ `libcob.a`) ถูก**คัดลอกเข้าไปฝังอยู่ในไฟล์ execute
  โดยตรง** ทำให้ไฟล์มีขนาดใหญ่ขึ้นมาก แต่**พกพาไปรันบนเครื่องอื่นได้โดยไม่ต้องติดตั้ง libcob เพิ่ม**
  (ยกเว้น library ระบบพื้นฐานอื่น ๆ ที่ libcob เองก็ต้องพึ่งพาต่ออีกที)

### พิสูจน์ Dynamic Linking แบบปกติ

```bash
cobc -x step701.cob -o step701_dyn
ldd step701_dyn | grep -i cob
```

```
	libcob.so.5 => /lib/x86_64-linux-gnu/libcob.so.5 (0x00007fe47b128000)
```

`ldd` (list dynamic dependencies) ยืนยันว่าไฟล์ execute ที่ได้จาก `cobc -x` แบบปกติ**อ้างอิง**ไปยัง
`libcob.so.5` เท่านั้น ไม่ได้เก็บโค้ดของมันไว้ในตัวเอง

### พิสูจน์ Static Linking ด้วยมือ

GnuCOBOL รุ่นและ build ที่ใช้ในเอกสารนี้ไม่มีแฟล็ก `-static` ระดับสูงที่ทำ static-link แบบสมบูรณ์ให้
อัตโนมัติ (ลองแล้วพบว่าไฟล์ที่ได้ยังคง dynamic-link กับ `libcob.so` เหมือนเดิม) แต่เราทำ static link ได้
เองด้วยการเรียก `gcc` ตรง ๆ พร้อมสั่งให้ link กับ **`libcob.a`** (static archive) แทน `libcob.so`:

```bash
cobc -C -x step701.cob -o step701_static_src.c
gcc -c step701_static_src.c -o step701_static_src.o
gcc step701_static_src.o -o step701_truly_static \
    -Wl,-Bstatic -lcob -Wl,-Bdynamic -lgmp -lncursesw -ltinfo -lc
```

```bash
ldd step701_truly_static
```

```
	linux-vdso.so.1 (0x00007f150b930000)
	libgmp.so.10 => /lib/x86_64-linux-gnu/libgmp.so.10 (0x00007f150b838000)
	libncursesw.so.6 => /lib/x86_64-linux-gnu/libncursesw.so.6 (0x00007f150b7fc000)
	libtinfo.so.6 => /lib/x86_64-linux-gnu/libtinfo.so.6 (0x00007f150b7c8000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f150b400000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f150b932000)
```

```bash
./step701_truly_static
```

```
Hello from GnuCOBOL.
```

สังเกตให้ดี: **`libcob.so` หายไปจากรายการ `ldd` โดยสิ้นเชิง!** โปรแกรมยังคงพึ่งพา library ระบบอื่น ๆ ที่
`libcob` เองใช้ภายใน (`libgmp` สำหรับเลขคณิตทศนิยมแม่นยำสูงตามที่ Part 001 กล่าวถึง, `libncursesw`/
`libtinfo` สำหรับ Screen Section ตาม Part 040) แต่โค้ดของ `libcob` เองถูกฝังเข้าไปในไฟล์ execute
เรียบร้อยแล้ว

### เปรียบเทียบขนาดไฟล์

```bash
ls -la step701_dyn step701_truly_static
```

```
-rwxr-xr-x 1 root root  16736 step701_dyn
-rwxr-xr-x 1 root root 449256 step701_truly_static
```

ไฟล์แบบ static ใหญ่กว่าไฟล์แบบ dynamic ถึง **ประมาณ 27 เท่า** สำหรับโปรแกรม "Hello World" ง่าย ๆ
เพียงโปรแกรมเดียว! นี่คือต้นทุนที่ต้องแลกกับความสะดวกในการพกพา

### ทำไมเรื่องนี้ถึงสำคัญในโลกการทำงานจริง

| ประเด็น | Dynamic Linking | Static Linking |
|---|---|---|
| ขนาดไฟล์ execute | เล็ก | ใหญ่กว่ามาก |
| ต้องติดตั้ง libcob บนเครื่องปลายทางไหม | ต้อง | ไม่ต้อง (ฝังมาในตัว) |
| อัปเดต libcob แก้บั๊ก/ความปลอดภัย | ทำครั้งเดียว ทุกโปรแกรมได้ผลทันที | ต้อง compile ใหม่ทุกโปรแกรม |
| เหมาะกับ | เซิร์ฟเวอร์ที่ควบคุม environment เองได้ (เช่น Docker image ที่เตรียม libcob ไว้แล้ว - Part 076) | แจกจ่ายไฟล์เดี่ยวไปยังเครื่องที่ไม่รู้จักสภาพแวดล้อมล่วงหน้า |

ในทางปฏิบัติ ทีม COBOL ส่วนใหญ่ที่ deploy บนเซิร์ฟเวอร์ที่ตัวเองควบคุม (เช่น Container ตาม Part 076)
มักเลือก **Dynamic Linking** เพราะจัดการอัปเดต security patch ของ runtime library ได้ง่ายกว่ามาก

### ข้อควรระวัง

- แฟล็ก `-static` ของ `cobc` ในบาง build **อาจไม่ทำงานตามที่คาดหวัง** (ตามที่พิสูจน์ไว้ข้างต้น) เพราะ
  ขึ้นอยู่กับว่า build ของ GnuCOBOL นั้นมี `libcob.a` (static archive) พร้อมใช้งานและตั้งค่า config ไว้
  รองรับหรือไม่ — ควรตรวจสอบด้วย `ldd` เสมอหลัง build เพื่อยืนยันว่าได้ผลลัพธ์ตามที่ต้องการจริง
- การ static link ต้องระบุ library ที่ `libcob` เองพึ่งพา (`libgmp`, `libncursesw`, `libtinfo`) ให้ตรง
  ตามที่ build นั้นต้องการ ถ้าลืมจะเกิด `undefined reference` ตอน link — ใช้ `ldd` กับ dynamic version
  เดิมของโปรแกรมเพื่อดูว่ามี library อะไรบ้างที่ต้องนำมาใส่
- ไฟล์ static ใหญ่ขึ้นไม่ได้แปลว่าโปรแกรมทำงานเร็วขึ้นแต่อย่างใด ขนาดที่ใหญ่ขึ้นมาจากโค้ดของ `libcob`
  ที่ถูกคัดลอกเข้ามาเท่านั้น ไม่เกี่ยวกับประสิทธิภาพการทำงานเลย

### แบบฝึกหัดที่ 704.1

**โจทย์**: จงอธิบายว่าทำไมองค์กรที่มีโปรแกรม COBOL หลายร้อยโปรแกรมรันอยู่บนเซิร์ฟเวอร์เดียวกัน มักจะ
เลือก Dynamic Linking แทน Static Linking แม้ Static Linking จะพกพาง่ายกว่าก็ตาม

**เฉลยแนวทาง**: ถ้ามีโปรแกรม COBOL หลายร้อยตัวและใช้ Static Linking ทุกตัว เมื่อพบช่องโหว่ความปลอดภัย
หรือบั๊กใน `libcob` เอง ทีมงานต้อง **compile ใหม่และ deploy ใหม่ทุกโปรแกรมทั้งหมด** เพื่อให้ได้
`libcob` เวอร์ชันที่แก้ไขแล้ว ซึ่งใช้เวลาและมีความเสี่ยงสูงมาก ในทางกลับกัน ถ้าใช้ Dynamic Linking
ทุกโปรแกรม การอัปเดตไฟล์ `libcob.so` เพียงไฟล์เดียวบนเซิร์ฟเวอร์ก็ทำให้**ทุกโปรแกรมที่ dynamic-link ไว้
ได้ประโยชน์จากการแก้ไขทันที**โดยไม่ต้อง compile โปรแกรมใดใหม่เลย นี่คือเหตุผลที่ Dynamic Linking เป็น
ตัวเลือกที่นิยมกว่ามากในสภาพแวดล้อมที่ควบคุมได้เอง เช่น เซิร์ฟเวอร์ภายในองค์กรหรือ Docker image (Part
076) ที่เตรียม `libcob.so` เวอร์ชันเดียวให้ทุกโปรแกรมใช้ร่วมกัน

## ขั้นตอนที่ 705: ตัวแปรสภาพแวดล้อมที่ปรับพฤติกรรม Runtime โดยไม่ต้องคอมไพล์ใหม่

### แนวคิด: Environment Variable คือ "การตั้งค่า" ที่ไม่ต้องแก้โค้ด

GnuCOBOL runtime (`libcob`) อ่านค่าจากตัวแปรสภาพแวดล้อม (Environment Variable) ของระบบปฏิบัติการหลาย
ตัวเพื่อปรับพฤติกรรมการทำงาน **โดยไม่ต้องแก้ไขซอร์สโค้ดหรือคอมไพล์ใหม่เลย** — เป็นแนวทางเดียวกับที่
ซอฟต์แวร์สมัยใหม่หลายตัวใช้ (เช่น `DATABASE_URL` ในเว็บแอปพลิเคชัน) ขั้นตอนนี้จะสาธิตสองตัวแปรที่มี
ประโยชน์มากที่สุด

### ตัวแปรที่ 1: COBCPY — เปลี่ยน path ค้นหา Copybook

Part 033 สอนว่า `COPY "filename.cpy"` ค้นหาไฟล์ในโฟลเดอร์ปัจจุบันโดยอัตโนมัติ แต่ในโปรเจกต์จริงที่มี
Copybook รวมกันไว้ที่โฟลเดอร์กลาง (shared copybook directory) เราต้องการให้ `cobc` มองหาไฟล์ที่นั่นแทน
โดยไม่ต้องคัดลอกไฟล์มาไว้ทุกที่ — ตัวแปร **`COBCPY`** ทำหน้าที่นี้:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP705CPY.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
           COPY "greetmsg.cpy".

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY WS-GREETING.
           STOP RUN.
```

ไฟล์ Copybook เก็บไว้ในโฟลเดอร์แยกต่างหาก (`copybooks/greetmsg.cpy`), **ไม่ได้อยู่ในโฟลเดอร์เดียวกับ**
`step705cpy.cob`:

```cobol
       01  WS-GREETING    PIC X(30) VALUE "Hello from a copybook.".
```

**ทดสอบโดยไม่ตั้งค่า COBCPY (คาดว่าจะ fail):**

```bash
cobc -x step705cpy.cob -o step705cpy
```

```
step705cpy.cob:7: error: greetmsg.cpy: No such file or directory
step705cpy.cob: in paragraph 'MAIN-PARA':
step705cpy.cob:11: error: 'WS-GREETING' is not defined
```

**ทดสอบโดยตั้งค่า COBCPY ให้ชี้ไปยังโฟลเดอร์ copybooks:**

```bash
COBCPY=/tmp/cobol-check-m/copybooks cobc -x step705cpy.cob -o step705cpy
./step705cpy
```

```
Hello from a copybook.
```

การตั้งค่า `COBCPY` แบบนี้ (นำมาต่อหน้าคำสั่งในบรรทัดเดียว) ทำให้ตัวแปรมีผล**เฉพาะคำสั่งนั้นคำสั่งเดียว**
เหมาะสำหรับทดสอบ ส่วนในโปรเจกต์จริงมักตั้งค่าถาวรไว้ใน build script หรือไฟล์ config ของทีม

### ตัวแปรที่ 2: COB_LIBRARY_PATH — โหลด Dynamic Module ตอนรันจริง

Part 031 ขั้นตอนที่ 301 สอนว่าโปรแกรมย่อย (subprogram) ต้องถูก `cobc` link รวมเข้ากับโปรแกรมหลักตั้งแต่
ตอนคอมไพล์ (`cobc -x main.cob sub.cob -o program`) — แต่ GnuCOBOL ยังรองรับอีกแนวทางหนึ่ง: **สร้าง
โปรแกรมย่อยเป็น Shared Module แยกต่างหาก (`.so`) แล้วให้โปรแกรมหลักค้นหาและโหลดมันตอน "รันจริง"** โดยไม่
ต้อง link รวมกันตั้งแต่ตอนคอมไพล์เลย — ตัวแปรที่ควบคุมว่าจะค้นหาโมดูลเหล่านี้จากที่ไหนคือ
**`COB_LIBRARY_PATH`**

**Subprogram ที่จะ build เป็น dynamic module ด้วยแฟล็ก `-m`:**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP705DYN.
       AUTHOR. COBOL-COURSE.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "  This module was loaded dynamically at run time.".
           GOBACK.
```

```bash
cd dynmods
cobc -m step705dyn.cob -o step705dyn.so
```

**โปรแกรมหลัก (ไม่ link กับ STEP705DYN เลยตอนคอมไพล์!):**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP705MAIN.
       AUTHOR. COBOL-COURSE.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: about to CALL a dynamically loaded module.".
           CALL "STEP705DYN".
           DISPLAY "Main: back after the dynamic CALL.".
           STOP RUN.
```

```bash
cobc -x step705main.cob -o step705main
```

**ทดสอบโดยไม่ตั้งค่า COB_LIBRARY_PATH (คาดว่าจะ fail ตอนรัน):**

```bash
./step705main
```

```
Main: about to CALL a dynamically loaded module.
libcob: error: module 'STEP705DYN' not found
```

**ทดสอบโดยตั้งค่า COB_LIBRARY_PATH ให้ชี้ไปยังโฟลเดอร์ dynmods:**

```bash
COB_LIBRARY_PATH=/tmp/cobol-check-m/dynmods ./step705main
```

```
Main: about to CALL a dynamically loaded module.
libcob: error: module 'STEP705DYN' not found
```

**ยังคง error!** นี่คือกับดักสำคัญที่ต้องอธิบายในหัวข้อถัดไป

### อธิบายจุดสำคัญ — และกับดักที่พบขณะทดสอบจริง

`cobc -info` ยืนยันว่า **`COB_MODULE_EXT` ของ build นี้คือ `so`** และไฟล์ `.so` ก็ถูกสร้างถูกต้องแล้ว
(`step705dyn.so` มีอยู่จริงในโฟลเดอร์ `dynmods`) แต่การโหลดยังคง fail จนกระทั่งพบสาเหตุจากการทดสอบจริง:

> **runtime dynamic loader ของ build นี้ค้นหาไฟล์โดยจับคู่ชื่อแบบ case-sensitive ตรงกับ PROGRAM-ID**
> (ตัวพิมพ์ใหญ่-เล็กต้องตรงกันเป๊ะ) ไม่ใช่ชื่อไฟล์ต้นฉบับ `.cob` (ซึ่งมักตั้งเป็นตัวพิมพ์เล็กตามธรรมเนียม
> การตั้งชื่อไฟล์) — เมื่อเปลี่ยนชื่อไฟล์จาก `step705dyn.so` เป็น **`STEP705DYN.so`** (ตัวพิมพ์ใหญ่ตรงกับ
> `PROGRAM-ID. STEP705DYN.` เป๊ะ) การโหลดก็สำเร็จทันที:

```bash
cp dynmods/step705dyn.so dynmods/STEP705DYN.so
COB_LIBRARY_PATH=/tmp/cobol-check-m/dynmods ./step705main
```

```
Main: about to CALL a dynamically loaded module.
  This module was loaded dynamically at run time.
Main: back after the dynamic CALL.
```

- `-m` บอก `cobc` ให้ build เป็น dynamically loadable module (`.so`) แทนที่จะ build เป็นโปรแกรมที่ link
  รวมเข้ากับโปรแกรมหลักตั้งแต่ตอนคอมไพล์
- `COB_LIBRARY_PATH` บอก runtime ของ `libcob` ว่าให้เพิ่มโฟลเดอร์ใดในรายการค้นหาโมดูลตอนเจอ `CALL` ที่
  ไม่ได้ link รวมมาด้วย
- **ชื่อไฟล์ `.so` ต้องตรงกับ `PROGRAM-ID` แบบตัวพิมพ์ใหญ่-เล็กเป๊ะ** ในสภาพแวดล้อมที่ทดสอบนี้ — เป็น
  รายละเอียดที่เอกสารทั่วไปมักไม่กล่าวถึงชัดเจน แต่พิสูจน์ได้จากการทดสอบจริงตามขั้นตอนข้างต้น

### ข้อควรระวัง

- เทคนิคการโหลด module แบบนี้เกี่ยวข้องกับแนวคิด **Dynamic CALL** ที่ Part 043 จะสอนอย่างละเอียดเต็ม
  รูปแบบ (รวมถึง `CANCEL` เพื่อยกเลิกโมดูลที่โหลดค้างไว้ในหน่วยความจำ) — ขั้นตอนนี้เป็นเพียงการแนะนำ
  ตัวแปรสภาพแวดล้อมที่เกี่ยวข้องเท่านั้น
- ถ้าตั้งชื่อไฟล์ผิด (ตัวพิมพ์ไม่ตรง หรือสะกดผิด) จะได้ error `module 'X' not found` เหมือนกับตอนไม่ได้
  ตั้งค่า `COB_LIBRARY_PATH` เลย ทำให้ดูเหมือนปัญหาเดิม — ควรตรวจสอบชื่อไฟล์อย่างละเอียดก่อนสงสัยว่า
  `COB_LIBRARY_PATH` ตั้งค่าผิด
- `COBCPY` และ `COB_LIBRARY_PATH` รองรับหลายโฟลเดอร์พร้อมกันโดยคั่นด้วย `:` (เหมือน `PATH` ของ Linux)
  ทำให้กำหนดหลายแหล่งค้นหาพร้อมกันได้

### แบบฝึกหัดที่ 705.1

**โจทย์**: จงอธิบายว่าทำไมเทคนิคการตั้งค่า `COBCPY`/`COB_LIBRARY_PATH` จึงเรียกว่าเป็นการปรับพฤติกรรม
"โดยไม่ต้องคอมไพล์ใหม่" ทั้งที่ตัวอย่าง `COBCPY` ข้างต้นก็ยังต้องเรียก `cobc` คอมไพล์อยู่ดี

**เฉลยแนวทาง**: กรณี `COBCPY` มีผลตอน**คอมไพล์** จริง (เพราะ `COPY` ถูกขยายตอน preprocess) แต่จุดสำคัญคือ
**ซอร์สโค้ด `.cob` เองไม่ต้องแก้ไขเลย** แม้จะย้ายตำแหน่งของ Copybook ไปที่ใดก็ตาม เพียงเปลี่ยนค่า
`COBCPY` ให้ชี้ตำแหน่งใหม่ก็ compile ผ่านได้ทันที ส่วนกรณี `COB_LIBRARY_PATH` มีผลตอน**รันจริง**เท่านั้น
(ไม่เกี่ยวกับการคอมไพล์เลยแม้แต่น้อย) — โปรแกรมหลัก `STEP705MAIN` ถูกคอมไพล์เพียงครั้งเดียว แต่สามารถหา
โมดูล `STEP705DYN` เจอหรือไม่เจอก็ได้ขึ้นอยู่กับค่า `COB_LIBRARY_PATH` ตอนรัน โดยไม่ต้องคอมไพล์โปรแกรม
หลักใหม่เลย นี่คือความหมายที่แท้จริงของ "ปรับพฤติกรรม runtime โดยไม่ต้องคอมไพล์ใหม่"

## ขั้นตอนที่ 706: Dialect ผ่าน -std= — เขียนโค้ดเดียวกัน พฤติกรรมอาจต่างกัน

### ทบทวนจาก Part 049

Part 049 แนะนำแนวคิดเรื่อง Compiler Directives และความแตกต่างระหว่าง COBOL Dialects ไว้แล้วในระดับ
ทฤษฎี ขั้นตอนนี้จะพิสูจน์ให้เห็น**ผลกระทบที่จับต้องได้จริง**ของการเลือก Dialect ผ่านแฟล็ก **`-std=`**
ของ `cobc`

```bash
cobc --help | grep -A4 "\-std"
```

```
  -std=<dialect>        warnings/features for a specific dialect
                        <dialect> can be one of:
                        default, cobol2014, cobol2002, cobol85, xopen,
                        ibm-strict, ibm, mvs-strict, mvs,
```

GnuCOBOL มี Dialect Configuration ให้เลือกใช้มากกว่า 15 แบบ (ดูรายชื่อไฟล์ `.conf` ทั้งหมดได้ที่โฟลเดอร์
config ของ GnuCOBOL เช่น `acu`, `bs2000`, `cobol85`, `ibm`, `mf`, `mvs`, `realia`, `rm`, `xopen` และ
เวอร์ชัน `-strict` ของแต่ละแบบ) — สะท้อนความจริงที่ว่า COBOL แต่ละค่ายมีรายละเอียดพฤติกรรมที่ไม่เหมือน
กันเป๊ะมาตั้งแต่อดีต

### พิสูจน์ว่า Dialect ต่างกันจริง: PIC ... COMP กับการ Truncate

โค้ดตัวอย่างนี้ประกาศตัวแปรไบนารี (`COMP`) ขนาด 4 หลัก แล้วพยายาม `MOVE` ค่าที่มี 5 หลักเข้าไป:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP706TRUNC.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-COUNTER          PIC 9(4) COMP.

       PROCEDURE DIVISION.
       MAIN-PARA.
           MOVE 12345 TO WS-COUNTER.
           DISPLAY "WS-COUNTER (PIC 9(4) COMP) after MOVE 12345 = "
               WS-COUNTER.
           STOP RUN.
```

**คอมไพล์และรันภายใต้ Dialect ต่าง ๆ:**

```bash
cobc -x -std=default step706trunc.cob -o step706t_default
./step706t_default

cobc -x -std=ibm step706trunc.cob -o step706t_ibm
./step706t_ibm

cobc -x -std=mf step706trunc.cob -o step706t_mf
./step706t_mf
```

**ผลลัพธ์จริง (สามบรรทัด สามค่าจากโปรแกรมเดียวกันเป๊ะ):**

```
WS-COUNTER (PIC 9(4) COMP) after MOVE 12345 = 2345
WS-COUNTER (PIC 9(4) COMP) after MOVE 12345 = 12345
WS-COUNTER (PIC 9(4) COMP) after MOVE 12345 = 2345
```

### วิเคราะห์: ทำไมค่าถึงต่างกัน

`PIC 9(4) COMP` ระบุว่าฟิลด์นี้ควรเก็บได้แค่ **4 หลัก** (0–9999) แต่ในหน่วยความจำจริง `COMP` เป็นเลข
ฐานสอง (binary) ที่ปกติจอง 2 ไบต์ ซึ่ง**สามารถเก็บค่าได้ถึง 65535** (มากกว่า 4 หลักที่ PICTURE ระบุไว้)
คำถามคือ: เมื่อ `MOVE` ค่า 12345 (5 หลัก) เข้าไป ควรจะ **ตัดให้เหลือ 4 หลักตาม PICTURE** (`2345`) หรือ
**เก็บค่าเต็มตามความจุจริงของหน่วยความจำฐานสอง** (`12345`)?

- **`-std=default` และ `-std=mf`**: เลือกตัดให้เหลือ 4 หลักตาม PICTURE เป๊ะ (`2345`) — พฤติกรรมนี้
  ตรงไปตรงมาและปลอดภัยกว่าในแง่ที่ข้อมูลไม่มีทาง "เกิน" ขอบเขตที่ประกาศไว้
- **`-std=ibm`**: **ไม่ตัด** เก็บค่าเต็ม (`12345`) ตามความจุจริงของพื้นที่หน่วยความจำฐานสอง — นี่คือ
  พฤติกรรมที่ตรงกับ IBM Enterprise COBOL บน Mainframe จริง (รายละเอียดเปรียบเทียบเชิงลึกอยู่ในขั้นตอนที่
  708)

นี่ไม่ใช่แค่ความแตกต่างทางทฤษฎี — **โปรแกรมเดียวกันเป๊ะ ให้ผลลัพธ์ต่างกันจริงเพียงเพราะเปลี่ยนแฟล็ก
`-std=`** ถ้าทีมงานย้าย (migrate) โปรแกรมจาก Mainframe จริง (ที่มักใช้พฤติกรรมแบบ `-std=ibm`) มารันบน
GnuCOBOL โดยลืมตั้งค่า dialect ให้ตรงกัน ตรรกะทางธุรกิจที่พึ่งพาพฤติกรรมการ "ไม่ตัดทศนิยม/หลัก" นี้อาจ
พังโดยไม่มีใครสังเกตเห็นจนกว่าจะเกิดปัญหาข้อมูลผิดพลาดในระบบจริง

### ข้อควรระวัง

- ตัวเลือก `-std=` ควรถูกกำหนดไว้**ตายตัวในระดับโปรเจกต์** (เช่น ใน Makefile หรือ build script) ไม่ควร
  ปล่อยให้แต่ละคนในทีมคอมไพล์ด้วยค่า default ที่ต่างกันเอง เพราะจะทำให้พฤติกรรมของโปรแกรมไม่แน่นอนขึ้นอยู่
  กับว่าใครเป็นคนคอมไพล์
- เมื่อทำโปรเจกต์ Modernization (ย้ายจาก Mainframe มา GnuCOBOL ตามที่จะเรียนเต็มรูปแบบในเฟส 5 นี้) **ต้อง
  ตรวจสอบ dialect ที่ใช้งานจริงบน Mainframe ต้นทางก่อนเสมอ** และเลือก `-std=` ที่ตรงกันที่สุดบน GnuCOBOL
  แล้วยัง**ต้องทดสอบซ้ำ (regression test)** เพราะการตั้งค่า dialect ช่วยได้แค่ลดความต่าง ไม่ได้รับประกัน
  ว่าพฤติกรรมจะเหมือนกัน 100% ทุกกรณี
- อย่าสับสนระหว่าง `-std=` (ปรับพฤติกรรม/ไวยากรณ์ที่ยอมรับ) กับ `-fbinary-truncate` (แฟล็กเฉพาะเจาะจงที่
  ควบคุมพฤติกรรมการตัดค่าของ `COMP` โดยตรง โดยไม่ต้องเปลี่ยน dialect ทั้งชุด) — ในงานที่ต้องการควบคุม
  เฉพาะจุดแบบละเอียด อาจเลือกใช้แฟล็กเฉพาะแทนการเปลี่ยน `-std=` ทั้งหมด

### แบบฝึกหัดที่ 706.1

**โจทย์**: จงอธิบายว่าทำไมผลลัพธ์ของโปรแกรมข้างต้นภายใต้ `-std=mf` (Micro Focus dialect) จึงเหมือนกับ
`-std=default` (ตัด COMP ให้เหลือตาม PICTURE) แทนที่จะเหมือนกับ `-std=ibm`

**เฉลยแนวทาง**: แม้ Micro Focus/OpenText และ IBM จะเป็นคอมไพเลอร์เชิงพาณิชย์ที่แข่งขันกันในตลาด Mainframe/
Enterprise COBOL เหมือนกัน (ตามที่ Part 001 ขั้นตอนที่ 7 กล่าวถึง) แต่ **แต่ละค่ายมีประวัติศาสตร์และ
พฤติกรรม default ที่พัฒนาแยกกันมาตามบริบทของตัวเอง** ไม่ได้แปลว่า "ไม่ใช่ IBM" แล้วพฤติกรรมจะเหมือนกัน
โดยอัตโนมัติ กรณีนี้พฤติกรรมการตัด `COMP` ตาม PICTURE ของ Micro Focus dialect บังเอิญตรงกับพฤติกรรม
default ของ GnuCOBOL เอง (ซึ่งถือว่าเป็นพฤติกรรมที่ปลอดภัยกว่าและเป็นที่นิยมในสภาพแวดล้อม Open Systems
โดยทั่วไป) ในขณะที่ IBM Mainframe เลือกพฤติกรรมที่ใช้ความจุเต็มของหน่วยความจำฐานสองแทน บทเรียนสำคัญคือ
**ห้ามสรุปเอาเองว่า Dialect ใด Dialect หนึ่งจะมีพฤติกรรมเหมือนกับอีก Dialect หนึ่งโดยไม่ทดสอบจริง**
ไม่ว่าจะดูใกล้เคียงกันแค่ไหนก็ตาม

## ขั้นตอนที่ 707: ระบบนิเวศคอมไพเลอร์ COBOL แบบโอเพนซอร์ส — GnuCOBOL, COBOL-IT, TinyCOBOL

### GnuCOBOL ไม่ได้อยู่คนเดียวในโลกโอเพนซอร์ส

ตลอด 70 Part ที่ผ่านมา เราใช้ GnuCOBOL เป็นเครื่องมือหลักเพียงตัวเดียว แต่ในความเป็นจริง มีความพยายาม
สร้างคอมไพเลอร์ COBOL แบบโอเพนซอร์สอีกหลายโครงการตลอดหลายทศวรรษที่ผ่านมา ขั้นตอนนี้จะพาไปรู้จักภาพรวม
ของระบบนิเวศนี้ในระดับที่เพียงพอสำหรับการสนทนาในวงการอย่างมีความรู้ (ไม่ได้ลงลึกเชิงเทคนิคเท่า GnuCOBOL
เพราะโครงการเหล่านี้ไม่ได้ติดตั้งในสภาพแวดล้อมของหลักสูตรนี้ และมีความสำคัญในทางปฏิบัติน้อยกว่ามาก)

### ประวัติโดยสรุปของ GnuCOBOL

GnuCOBOL มีจุดเริ่มต้นภายใต้ชื่อ **OpenCOBOL** ซึ่งพัฒนาโดย Keisuke Nishida เป็นหลักในช่วงต้นทศวรรษ 2000
ต่อมาโครงการได้เข้าร่วมเป็นส่วนหนึ่งของ GNU Project และเปลี่ยนชื่อเป็น **GnuCOBOL** ในช่วงต้นทศวรรษ 2010
โดยมีทีมผู้ดูแลหลัก (ที่ปรากฏชื่อในผลลัพธ์ `cobc -info` ของเราเอง) ได้แก่ Roger While, Ron Norman, Simon
Sobisch และ Edward Hart สืบทอดงานพัฒนาต่อมาจนถึงปัจจุบัน (2026) ทำให้ GnuCOBOL กลายเป็น **คอมไพเลอร์
COBOL แบบโอเพนซอร์สที่ได้รับความนิยมและมีการพัฒนาต่อเนื่องมากที่สุด** ในตลาดปัจจุบัน

### COBOL-IT

**COBOL-IT** คือคอมไพเลอร์ที่แยกสาย (fork) ออกมาจากฐานโค้ดเดียวกันกับ OpenCOBOL/GnuCOBOL ในช่วงปลาย
ทศวรรษ 2000 โดยมีเป้าหมายเพื่อนำเสนอทางเลือกที่มี**การสนับสนุนเชิงพาณิชย์ (Commercial Support)** ควบคู่
ไปกับความเป็นโอเพนซอร์ส พร้อมเครื่องมือเสริมสำหรับสภาพแวดล้อม Enterprise เช่น การรองรับ Windows ที่ดี
ขึ้นและเครื่องมือ GUI เพิ่มเติม อย่างไรก็ตาม **ปัจจุบัน (2026) มีข้อมูลว่าการพัฒนาอย่างต่อเนื่องของ
COBOL-IT มีความไม่แน่นอนและซบเซาลงมากเมื่อเทียบกับ GnuCOBOL** ทำให้ในทางปฏิบัติ GnuCOBOL กลายเป็นตัวเลือก
หลักของชุมชนโอเพนซอร์สไปโดยปริยาย

### TinyCOBOL

**TinyCOBOL** เป็นอีกหนึ่งโครงการคอมไพเลอร์ COBOL โอเพนซอร์สที่มีประวัติศาสตร์ยาวนาน มีแนวคิดมุ่งเน้นความ
เรียบง่ายและขนาดเล็ก (ตามชื่อโครงการ) เหมาะกับการใช้งานในสภาพแวดล้อมที่จำกัดทรัพยากร แต่**มีระดับการ
พัฒนาและความนิยมในปัจจุบันต่ำกว่า GnuCOBOL อย่างมาก** ทำให้ในทางปฏิบัติแทบไม่ปรากฏการใช้งานในโปรเจกต์
Enterprise จริงเมื่อเทียบกับ GnuCOBOL

### ตารางเปรียบเทียบโดยสรุป

| คอมไพเลอร์ | จุดเริ่มต้น/ความเกี่ยวข้อง | สถานะปัจจุบัน (2026) | เหมาะกับ |
|---|---|---|---|
| **GnuCOBOL** | สืบทอดจาก OpenCOBOL, เข้าร่วม GNU Project | พัฒนาต่อเนื่องแข็งขัน, เป็นมาตรฐานโอเพนซอร์ส de facto | การเรียนรู้, โปรเจกต์โอเพนซอร์ส, Modernization |
| COBOL-IT | แยกสายจากฐานโค้ดเดียวกับ OpenCOBOL | การพัฒนาซบเซาลงมากเมื่อเทียบกับอดีต | องค์กรที่เคยลงทุนกับ license/support เดิมอยู่แล้ว |
| TinyCOBOL | โครงการอิสระ เน้นความเรียบง่าย/ขนาดเล็ก | มีการพัฒนาน้อยมากในปัจจุบัน | งานเฉพาะทางที่ทรัพยากรจำกัดมาก (พบไม่บ่อยในทางปฏิบัติ) |

### ทำไมหลักสูตรนี้ยืนยันเลือก GnuCOBOL

เหตุผลเดิมจาก Part 001 ขั้นตอนที่ 7 ยังคงเป็นจริงและยิ่งชัดเจนขึ้นเมื่อมองภาพรวมระบบนิเวศทั้งหมด:
GnuCOBOL คือคอมไพเลอร์โอเพนซอร์สเพียงตัวเดียวในกลุ่มนี้ที่ **ยังคงมีการพัฒนาต่อเนื่องอย่างจริงจัง**
รองรับมาตรฐาน COBOL สมัยใหม่ได้กว้างขวางที่สุด และมีชุมชนผู้ใช้งาน/เอกสารอ้างอิงมากที่สุดในกลุ่มตัวเลือก
โอเพนซอร์สทั้งหมด

### ข้อควรระวัง

- ข้อมูลเรื่องสถานะการพัฒนาของโครงการโอเพนซอร์สเปลี่ยนแปลงได้ตลอดเวลา (โครงการอาจกลับมาคึกคักหรือหยุด
  พัฒนาไปเลยก็ได้) หากต้องตัดสินใจเลือกคอมไพเลอร์สำหรับโปรเจกต์จริง **ควรตรวจสอบสถานะล่าสุดของแต่ละ
  โครงการเองก่อนเสมอ** ไม่ควรอ้างอิงจากข้อมูล ณ เวลาที่เขียนหลักสูตรนี้เพียงอย่างเดียว
- อย่าสับสนระหว่าง "โอเพนซอร์ส" กับ "ฟรีไม่มีค่าใช้จ่ายเสมอไป" — บางโครงการในกลุ่มนี้เคยเสนอทั้งรุ่นฟรี
  และรุ่นเชิงพาณิชย์ที่มีการสนับสนุนแบบมีค่าใช้จ่ายควบคู่กัน (dual-licensing model) ซึ่งต่างจาก GnuCOBOL
  ที่เป็น GPL License แบบเต็มรูปแบบตลอดมา

### แบบฝึกหัดที่ 707.1

**โจทย์**: จงอธิบายว่าทำไมการที่ "โครงการยังพัฒนาต่อเนื่อง" จึงเป็นปัจจัยสำคัญกว่า "ฟีเจอร์ที่มีให้ตอนนี้"
เมื่อองค์กรต้องเลือกคอมไพเลอร์ COBOL โอเพนซอร์สสำหรับใช้งานระยะยาว

**เฉลยแนวทาง**: ระบบ COBOL ในองค์กรมักมีอายุการใช้งานยาวนานหลายสิบปี (ตามที่ Part 001 อธิบายไว้ตั้งแต่
ต้นหลักสูตร) การเลือกคอมไพเลอร์ที่มีฟีเจอร์ครบถ้วนในวันนี้แต่หยุดพัฒนาในอนาคตจะทำให้องค์กรติดขัดเมื่อ
มาตรฐาน COBOL ใหม่ออกมา (เช่น ฟีเจอร์ที่เกี่ยวกับ JSON/Cloud integration ในอนาคต) หรือเมื่อพบช่องโหว่
ความปลอดภัยที่ต้องได้รับการแก้ไข ในขณะที่โครงการที่ยังพัฒนาต่อเนื่องจะได้รับการอัปเดตความปลอดภัย ฟีเจอร์
ใหม่ และการแก้บั๊กอย่างสม่ำเสมอ ทำให้ความเสี่ยงระยะยาวต่ำกว่ามาก แม้ฟีเจอร์ปัจจุบัน ณ วันที่ตัดสินใจอาจดู
ใกล้เคียงกันก็ตาม

### ตัวอย่างเชิงแนวคิด: ความแตกต่างของ "จุดเริ่มต้นการคอมไพล์"

เพื่อให้เห็นภาพชัดเจนว่าประสบการณ์การคอมไพล์ต่างกันแค่ไหน ลองเทียบคำสั่งเดียวกัน:

**GnuCOBOL (ทดสอบจริงได้ ตามที่ทำมาตลอดหลักสูตรนี้):**

```bash
cobc -x mypgm.cob -o mypgm
./mypgm
```

**แนวคิดการคอมไพล์บน Mainframe จริงด้วย IBM Enterprise COBOL (เชิงอ้างอิงเท่านั้น ไม่สามารถรันบน
GnuCOBOL ได้ - ทบทวนรูปแบบ JCL เต็มจาก Part 052):**

```
//COMPRUN  JOB (ACCT),'COMPILE AND RUN',CLASS=A,MSGCLASS=X
//COMPSTEP EXEC IGYWCL
//COBOL.SYSIN DD DSN=MY.SOURCE.COBOL(MYPGM),DISP=SHR
//LKED.SYSLMOD DD DSN=MY.LOAD.LIB(MYPGM),DISP=SHR
//GOSTEP   EXEC PGM=MYPGM
//SYSOUT   DD SYSOUT=*
```

ความต่างที่เห็นได้ทันที: GnuCOBOL ใช้คำสั่งเดียวจบเหมือนภาษาโปรแกรมสมัยใหม่ทั่วไป ส่วน Mainframe จริง

Execute Step แยกกันอย่างชัดเจน สะท้อนธรรมชาติของสภาพแวดล้อม Mainframe ที่ทุกขั้นตอนถูกควบคุมและบันทึกไว้
อย่างเป็นทางการ (ตามที่ Part 052-053 อธิบายไว้อย่างละเอียดแล้ว)

## ขั้นตอนที่ 709: เครื่องมือ Debug และ Trace — -ftraceall, COB_SET_TRACE, และ gdb

### ทำไมการ Debug โปรแกรมที่ "แปลงเป็น C ก่อน" ถึงมีข้อดีซ่อนอยู่

เพราะ GnuCOBOL แปลง COBOL เป็น C ก่อนคอมไพล์จริง (ตามขั้นตอนที่ 701-702) เราจึงได้ประโยชน์พิเศษ: **เครื่อง
มือ Debug ของโลก C ทั้งหมด (เช่น `gdb`) สามารถนำมาใช้กับโปรแกรม COBOL ที่คอมไพล์ด้วย GnuCOBOL ได้จริง**
นอกจากนี้ GnuCOBOL ยังมีกลไก Trace ระดับ COBOL ของตัวเองที่ใช้งานง่ายกว่ามากสำหรับการ debug ทั่วไป

### วิธีที่ 1: Trace ระดับ COBOL ด้วย -ftraceall และ COB_SET_TRACE

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP709TRACE.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-COUNT     PIC 9(2) VALUE 0.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Starting.".
           PERFORM ADD-PARA 3 TIMES.
           DISPLAY "Finished. Count=" WS-COUNT.
           STOP RUN.

       ADD-PARA.
           ADD 1 TO WS-COUNT.
```

คอมไพล์พร้อมแฟล็ก **`-ftraceall`** (เพิ่มโค้ด hook สำหรับติดตามการทำงานเข้าไปในไฟล์ execute):

```bash
cobc -x -ftraceall step709trace.cob -o step709trace
```

รันโดยตั้งค่าตัวแปรสภาพแวดล้อม **`COB_SET_TRACE=Y`** เพื่อเปิดใช้งาน hook ที่เพิ่งคอมไพล์เข้าไป:

```bash
COB_SET_TRACE=Y ./step709trace
```

**ผลลัพธ์จริง:**

```
Source: 'step709trace.cob'
Program-Id: STEP709TRACE
Program-Id: STEP709TRACE         Entry: STEP709TRACE                    Line:      9
Program-Id: STEP709TRACE     Paragraph: MAIN-PARA                       Line:     10
Program-Id: STEP709TRACE                DISPLAY                         Line:     11
Starting.
Program-Id: STEP709TRACE                PERFORM                         Line:     12
Program-Id: STEP709TRACE     Paragraph: ADD-PARA                        Line:     16
Program-Id: STEP709TRACE                ADD                             Line:     17
Program-Id: STEP709TRACE     Paragraph: ADD-PARA                        Line:     16
Program-Id: STEP709TRACE                ADD                             Line:     17
Program-Id: STEP709TRACE     Paragraph: ADD-PARA                        Line:     16
Program-Id: STEP709TRACE                ADD                             Line:     17
Program-Id: STEP709TRACE                DISPLAY                         Line:     13
Finished. Count=03
Program-Id: STEP709TRACE                STOP RUN                        Line:     14
```

สังเกตว่า trace แสดง**ทุกคำสั่งที่ทำงานจริงตามลำดับ** พร้อมเลขบรรทัดในไฟล์ `.cob` ต้นฉบับ (เชื่อมโยงกับ
คอมเมนต์เลขบรรทัดในไฟล์ C ที่เห็นในขั้นตอนที่ 702) รวมถึงเห็นชัดเจนว่า `PERFORM ADD-PARA 3 TIMES` วนกลับ
ไปที่ `ADD-PARA` (บรรทัด 16) ครบ 3 รอบพอดีตามที่ตั้งใจ — มีประโยชน์มากเวลาต้องการเข้าใจ **flow การทำงาน
จริง**ของโปรแกรมที่ซับซ้อนโดยไม่ต้องเดาใจ

### วิธีที่ 2: ใช้ gdb กับโปรแกรม COBOL โดยตรง

เพราะไฟล์ execute ที่ได้จริง ๆ คือโปรแกรม C ที่คอมไพล์แล้ว เราจึงเปิดด้วย **`gdb`** และตั้งจุดพัก
(breakpoint) ที่ฟังก์ชัน C ที่แทนโปรแกรม COBOL ของเราได้โดยตรง (ต้องคอมไพล์ด้วย `-g` เพื่อให้มีข้อมูล
debug symbol):

```bash
cobc -x -g step709trace.cob -o step709trace_g
gdb -q -batch -ex "break STEP709TRACE_" -ex run -ex "bt" -ex "continue" ./step709trace_g
```

**ผลลัพธ์จริง:**

```
Breakpoint 1 at 0x1315: file step709trace.c, line 51.
Breakpoint 1, STEP709TRACE_ (entry=0) at step709trace.c:51
#0  STEP709TRACE_ (entry=0) at step709trace.c:51
#1  0x00005555555552f0 in STEP709TRACE () at step709trace.c:46
#2  0x00005555555552d7 in main (argc=1, argv=0x7fffffffcb58) at step709trace.c:34
Starting.
Finished. Count=03
```

Backtrace (`bt`) ยืนยันสิ่งที่เราเรียนรู้มาตั้งแต่ขั้นตอนที่ 702 อย่างเป็นรูปธรรม: **`main()` เรียก
`STEP709TRACE()` ซึ่งเรียก `STEP709TRACE_()`** — เห็นห่วงโซ่การเรียกฟังก์ชัน C จริงที่ COBOL ของเราถูก
แปลงมาเป็น ยืนยันด้วยเครื่องมือ debug ของโลก C โดยตรง

### อธิบายจุดสำคัญ

- `-ftraceall`/`COB_SET_TRACE=Y` เหมาะกับการ debug **ระดับตรรกะทางธุรกิจของ COBOL** (อยากรู้ว่าโปรแกรม
  เดินทางผ่าน paragraph ไหนบ้าง ตามลำดับอะไร) โดยไม่ต้องรู้จัก C เลยแม้แต่น้อย
- `gdb` เหมาะกับการ debug **ระดับลึกที่เกี่ยวกับหน่วยความจำ/ค่าตัวแปรจริงในขณะรัน** (เช่น กรณี Part 031
  ขั้นตอนที่ 304 ที่โปรแกรมเกิด SIGSEGV) — เพราะ gdb ทำงานที่ระดับ C/Assembly โดยตรง จึงต้องตั้ง
  breakpoint ที่ **ชื่อฟังก์ชัน C** (เช่น `STEP709TRACE_`) ไม่ใช่ชื่อ paragraph ของ COBOL โดยตรง (เพราะ
  paragraph ภายใน `PROCEDURE DIVISION` เดียวมักถูกแปลงเป็น C label/goto ภายในฟังก์ชันเดียวกัน ไม่ใช่
  ฟังก์ชันแยกต่างหาก)

### ข้อควรระวัง

- `-ftraceall` เพิ่ม overhead ให้กับโปรแกรมทุกครั้งที่ทำงาน (แม้จะไม่ได้ตั้งค่า `COB_SET_TRACE=Y` ตอนรัน
  ก็ตาม เพราะ hook ถูกคอมไพล์ฝังไว้ในไฟล์ execute แล้ว) **ไม่ควรใช้แฟล็กนี้กับไฟล์ execute ที่จะ deploy
  ขึ้นระบบจริง (Production)** ควรใช้เฉพาะระหว่างพัฒนา/แก้ปัญหาเท่านั้น แล้ว build ใหม่โดยไม่ใส่แฟล็กนี้
  ก่อน deploy จริง
- การตั้ง breakpoint บนชื่อ paragraph ตรง ๆ ด้วย `gdb` (เช่น `break ADD-PARA`) **จะไม่พบสัญลักษณ์นั้น
  เลย** (`Function "ADD-PARA" not defined.`) เพราะเหตุผลที่อธิบายไว้ข้างต้น ต้องตั้งที่ชื่อฟังก์ชันของ
  ทั้งโปรแกรม (`PROGRAM-ID` ตามด้วย `_`) แทน แล้วไล่ดูค่าตัวแปรผ่านชื่อภายในของ `libcob` (เช่น
  `b_2`, `f0` ตามที่เห็นในขั้นตอนที่ 702) ซึ่งอ่านยากกว่าชื่อตัวแปร COBOL ต้นฉบับมาก
- ทั้งสองวิธีต้องคอมไพล์ด้วยแฟล็กพิเศษเสมอ (`-ftraceall` หรือ `-g`) — โปรแกรมที่คอมไพล์แบบปกติ (ไม่มี
  แฟล็กเหล่านี้) จะไม่มีข้อมูลเพียงพอให้ทั้ง trace และ gdb ทำงานได้อย่างมีประโยชน์

### แบบฝึกหัดที่ 709.1

**โจทย์**: จงอธิบายว่าทำไม backtrace จาก `gdb` ในตัวอย่างข้างต้นจึงแสดง **3 เฟรม** (`STEP709TRACE_`,
`STEP709TRACE`, `main`) ทั้งที่โปรแกรม COBOL ต้นฉบับดูเหมือนจะมีแค่ "จุดเริ่มต้นเดียว"

**เฉลยแนวทาง**: ตามที่ขั้นตอนที่ 702 อธิบายไว้ โครงสร้างไฟล์ C ที่ `cobc -x` สร้างขึ้นมี 3 ชั้นเสมอ:
(1) ฟังก์ชัน `main()` ที่เรียก `cob_init` แล้วเรียกฟังก์ชันของโปรแกรม, (2) ฟังก์ชันที่ตั้งชื่อตรงกับ
`PROGRAM-ID` (เช่น `STEP709TRACE()`) ที่ทำหน้าที่เป็นจุดเข้า (entry point) แบบง่าย เรียกฟังก์ชันจริงต่อ
อีกที, และ (3) ฟังก์ชันที่มีขีดล่างต่อท้าย (`STEP709TRACE_()`) ที่บรรจุ**เนื้อหาจริงทั้งหมด**ของ
`PROCEDURE DIVISION` (รวมถึงโค้ด initialization และการจัดการ CANCEL callback ที่เห็นในขั้นตอนที่ 702)
โครงสร้าง 3 ชั้นนี้เป็นรายละเอียดการ implement ภายในของ GnuCOBOL ที่ผู้เขียนโปรแกรม COBOL ไม่จำเป็นต้อง
สนใจเลยในการเขียนโค้ดปกติ แต่จะปรากฏให้เห็นทันทีที่ debug ด้วยเครื่องมือระดับ C อย่าง `gdb`

### แนวทางการมีส่วนร่วมกับโครงการโอเพนซอร์สแบบ GnuCOBOL

แม้จะยังไม่มีประสบการณ์เขียน C ขั้นสูง ก็มีหลายวิธีที่ผู้เรียน COBOL อย่างเราจะมีส่วนร่วมกับโครงการแบบนี้
ได้ในระยะยาว:

1. **รายงานบั๊กพร้อมตัวอย่างโค้ดที่ reproduce ได้ชัดเจน** — มีคุณค่ามากแม้ไม่ได้เขียนโค้ดแก้เอง
2. **ปรับปรุงเอกสาร (Documentation)** — โครงการโอเพนซอร์สจำนวนมากขาดแคลนคนเขียนเอกสารมากกว่าขาดคนเขียนโค้ด
3. **เขียนชุดทดสอบ (Test Case)** — เพิ่มความมั่นใจให้กับทุกการเปลี่ยนแปลงในอนาคตของโครงการ
4. **ช่วยตอบคำถามผู้เริ่มต้นคนอื่นในชุมชน** — เป็นวิธีที่ผู้เรียนหลักสูตรนี้ทำได้ทันทีหลังเรียนจบ

### ปิดท้าย Part นี้ด้วยการประกอบร่างทุกอย่างที่เรียนมา: Makefile

ตลอด Part นี้เราเรียนรู้ขั้นตอนย่อยของการคอมไพล์อย่างละเอียด (701-703), การ link (704), ตัวแปร
environment (705), และ dialect (706) — ในโปรเจกต์จริงที่มีหลายไฟล์ COBOL ประกอบกัน (เหมือนระบบธนาคาร
จำลองใน Part 070 ที่มีถึง 8+ โปรแกรม) การพิมพ์คำสั่ง `cobc` ยาว ๆ ซ้ำ ๆ ด้วยมือทุกครั้งไม่สะดวกและเสี่ยง
ต่อความผิดพลาด เครื่องมือมาตรฐานที่ใช้แก้ปัญหานี้ในโลกซอฟต์แวร์ (ไม่ใช่แค่ COBOL) คือ **`make`** ร่วมกับ
ไฟล์ **`Makefile`**

**โครงสร้างโปรเจกต์ตัวอย่าง (สองโปรแกรมที่ CALL กัน เหมือนที่เรียนมาตั้งแต่ Part 031):**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP710MAIN.
       AUTHOR. COBOL-COURSE.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Built by Makefile.".
           CALL "STEP710SUB".
           STOP RUN.
```

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP710SUB.
       AUTHOR. COBOL-COURSE.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "  Subprogram linked in by the same Makefile rule.".
           GOBACK.
```

**Makefile ที่ทำให้การ build ทั้งโปรเจกต์เหลือคำสั่งเดียว:**

```
COBC    = cobc
TARGET  = step710app
SOURCES = main.cob sub.cob

.PHONY: all run clean

all: $(TARGET)

$(TARGET): $(SOURCES)
	$(COBC) -x $(SOURCES) -o $(TARGET)

run: all
	./$(TARGET)

clean:
	rm -f $(TARGET) *.o
```

**ทดสอบจริง:**

```bash
make run
```

```
cobc -x main.cob sub.cob -o step710app
./step710app
Built by Makefile.
  Subprogram linked in by the same Makefile rule.
```

```bash
make clean
```

```
rm -f step710app *.o
```

`make run` เรียก rule `all` ก่อน (เพราะ `run` พึ่งพา `all`) ซึ่งจะคอมไพล์เฉพาะเมื่อไฟล์ `$(TARGET)` ยัง
ไม่มีอยู่หรือไฟล์ต้นฉบับใหม่กว่าไฟล์ execute ที่มีอยู่แล้ว (พฤติกรรม incremental build มาตรฐานของ `make`)
จากนั้นจึงรันโปรแกรม ส่วน `make clean` ลบไฟล์ที่ build ออกทั้งหมดเพื่อเริ่มต้นใหม่

### ข้อควรระวัง

- Makefile ข้างต้นเป็นตัวอย่างพื้นฐานที่สุด โปรเจกต์จริงขนาดใหญ่ (เช่น ระบบธนาคารจำลองจาก Part 070 ที่มี
  Copybook และหลายโปรแกรมที่ `CALL` กัน) มักต้องมี rule ที่ซับซ้อนกว่านี้ เช่น แยกคอมไพล์แต่ละไฟล์เป็น
  `.o` ก่อนแล้วค่อย link (ใช้ประโยชน์จาก incremental build ได้ดีกว่า ไม่ต้องคอมไพล์ไฟล์ที่ไม่ได้แก้ไข
  ใหม่ทุกครั้ง) และจัดการ dependency ระหว่างไฟล์ `.cpy` กับไฟล์ `.cob` ที่ COPY เข้ามาด้วย
- **`Makefile` ต้องใช้ตัวอักษร Tab (ไม่ใช่ Space) ในการเยื้องบรรทัดคำสั่งของแต่ละ rule เสมอ** (เช่น
  บรรทัด `$(COBC) -x $(SOURCES) -o $(TARGET)`) เป็นกฎเก่าแก่ของ `make` ที่ยังคงเข้มงวดมาจนถึงปัจจุบัน
  ถ้าใช้ Space แทน Tab จะได้ error `missing separator` ทันที
- เนื้อหาเรื่องการนำ Git และ CI/CD Pipeline มาจัดการโปรเจกต์ COBOL หลายไฟล์อย่างเป็นระบบเต็มรูปแบบจะสอน
  ละเอียดใน Part 078 และ Part 080 ของหลักสูตรนี้ — Makefile ในขั้นตอนนี้เป็นเพียงจุดเริ่มต้นของแนวคิด
  Build Automation เท่านั้น

**โจทย์**: จงอธิบายว่าทำไมการรายงานบั๊กไปยังโครงการโอเพนซอร์สอย่าง GnuCOBOL โดยแนบผลลัพธ์จาก `cobc
-info` เต็มรูปแบบ จึงมีประโยชน์มากกว่าการรายงานแค่ "โปรแกรมคอมไพล์ไม่ผ่าน" เฉย ๆ

**เฉลยแนวทาง**: ตามที่ขั้นตอนที่ 706 พิสูจน์ไว้ พฤติกรรมของ GnuCOBOL อาจแตกต่างกันได้ตาม dialect
(`-std=`) ที่ใช้ และตามที่ `cobc -info` แสดงให้เห็น แต่ละ build อาจเปิด/ปิดฟีเจอร์บางอย่างต่างกัน (เช่น
Indexed File Handler, JSON library) ขึ้นอยู่กับตัวเลือกตอน build GnuCOBOL เอง หากรายงานแค่ "คอมไพล์ไม่
ผ่าน" โดยไม่แนบข้อมูลเวอร์ชัน คอมไพเลอร์ C ที่ใช้ และฟีเจอร์ที่เปิด/ปิดอยู่ ทีมพัฒนาอาจไม่สามารถ
reproduce ปัญหาได้เลยเพราะสภาพแวดล้อมของตนอาจต่างจากผู้รายงานโดยสิ้นเชิง การแนบ `cobc -info` เต็ม
รูปแบบช่วยให้ทีมพัฒนาเห็นภาพสภาพแวดล้อมทั้งหมดในคำสั่งเดียว ลดรอบการถามตอบไปมาเพื่อขอข้อมูลเพิ่มเติม และ
เพิ่มโอกาสที่ปัญหาจะได้รับการแก้ไขอย่างรวดเร็วและถูกต้องตรงจุด

## สรุปท้ายบท

Part 071 พาเราเปิดฝากระโปรงของเครื่องมือที่ใช้มาตลอด 70 Part เพื่อทำความเข้าใจ GnuCOBOL ในระดับที่ลึกกว่า
เดิมมาก สิ่งที่เราได้เรียนรู้:

- **GnuCOBOL คือ Transpiler ที่แปลง COBOL เป็น C ก่อน แล้วเรียก gcc คอมไพล์อีกทีหนึ่ง** ไม่ใช่คอมไพเลอร์
  ที่ผลิตภาษาเครื่องโดยตรง (ขั้นตอนที่ 701)
- ใช้ `cobc -C` **มองเห็นโค้ด C จริงที่ถูกสร้างขึ้น** และเข้าใจว่า `-x` เพิ่มฟังก์ชัน `main()` เข้ามาให้
  โดยเฉพาะ (ขั้นตอนที่ 702)
- การคอมไพล์แบ่งเป็น **5 ขั้นตอนย่อย** (`-E`, `-C`, `-S`, `-c`, และ link) ที่แยกทำเองได้ทีละสเต็ปด้วยมือ
  (ขั้นตอนที่ 703)
- ความแตกต่างระหว่าง **Static Linking กับ Dynamic Linking** และเหตุผลที่ GnuCOBOL/องค์กรส่วนใหญ่เลือก
  Dynamic Linking เป็นค่าเริ่มต้น (ขั้นตอนที่ 704)
- ตัวแปรสภาพแวดล้อม **`COBCPY`** (ปรับ path ค้นหา copybook) และ **`COB_LIBRARY_PATH`** (โหลด dynamic
  module ตอนรันจริง) พร้อมกับดักเรื่องชื่อไฟล์ที่ต้อง case-sensitive ตรงกับ `PROGRAM-ID` (ขั้นตอนที่ 705)
- **`-std=`** ควบคุม Dialect ที่ส่งผลต่อพฤติกรรมจริงของโปรแกรม พิสูจน์ด้วยตัวอย่าง `COMP` truncation ที่
  ให้ผลต่างกันระหว่าง default/mf กับ ibm (ขั้นตอนที่ 706)
- ภาพรวมระบบนิเวศคอมไพเลอร์ COBOL โอเพนซอร์สอื่น ๆ (COBOL-IT, TinyCOBOL) และเหตุผลที่ GnuCOBOL เป็น
  ตัวเลือกหลักในปัจจุบัน (ขั้นตอนที่ 707)
- เปรียบเทียบเชิงเทคนิคเชิงลึกกับ **IBM Enterprise COBOL** และ **Micro Focus/OpenText** ต่อยอดจากตาราง
  ใน Part 001 (ขั้นตอนที่ 708)
- เครื่องมือ **Debug/Trace**: `-ftraceall`/`COB_SET_TRACE` สำหรับ trace ระดับ COBOL และ `gdb` สำหรับ
  debug ระดับ C โดยตรง พร้อมพิสูจน์โครงสร้าง 3 ชั้นของฟังก์ชัน C ที่ถูกสร้างขึ้น (ขั้นตอนที่ 709)
- ชุมชนผู้พัฒนา GnuCOBOL, วิธีรายงานบั๊กอย่างมีประสิทธิภาพด้วย `cobc -info`, และการใช้ **Makefile**
  ประกอบร่างโปรเจกต์หลายไฟล์เป็นคำสั่งเดียว (ขั้นตอนที่ 710)
