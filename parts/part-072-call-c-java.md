# Part 072: การเชื่อมต่อ COBOL กับภาษาอื่น (C, Java) ผ่าน CALL (ขั้นตอนที่ 711–720)

## คำนำของ Part นี้

Part 071 พาเราเปิดฝากระโปรงของ GnuCOBOL จนเห็นชัดเจนว่า **ทุกโปรแกรม COBOL ที่เราเขียนมาตลอดหลักสูตรนี้
แท้จริงแล้วถูกแปลงเป็นภาษา C ก่อนคอมไพล์เป็นภาษาเครื่องจริง** ความเข้าใจนี้เปิดประตูสู่คำถามที่สำคัญมาก
สำหรับ COBOL สมัยใหม่: **ในเมื่อ COBOL "คุยกับ" C อยู่แล้วเป็นปกติเบื้องหลัง แล้วเราจะให้โปรแกรม COBOL
ของเราเรียกใช้ฟังก์ชัน C ที่เขียนขึ้นเองโดยตรงได้หรือไม่?**

คำตอบคือ **ได้แน่นอน** และ Part นี้จะพาคุณลงมือทำจริงทุกขั้นตอน: ตั้งแต่การ `CALL` ฟังก์ชัน C ธรรมดา ๆ
ตัวหนึ่งจากโปรแกรม COBOL, ทำความเข้าใจ Calling Convention ที่ทำให้สองภาษานี้คุยกันรู้เรื่อง, ไปจนถึง
กับดักอันตรายที่มักเกิดขึ้นจริงเมื่อสองภาษาที่มีกฎการจัดการหน่วยความจำต่างกันมาทำงานร่วมกัน (พิสูจน์ด้วย
บั๊กจริงที่ทดสอบเจอในสภาพแวดล้อมของหลักสูตรนี้เอง ไม่ใช่แค่คำเตือนลอย ๆ)

จากนั้น Part นี้จะขยายขอบเขตไปไกลกว่า C: เราจะพิสูจน์ว่า COBOL สามารถทำงานร่วมกับ **Java** ได้จริงถึง
สองรูปแบบ — ทั้งแบบเรียก Java เป็น subprocess ผ่านไฟล์แลกเปลี่ยนข้อมูล และแบบที่ก้าวหน้ากว่านั้นคือให้
**Java เรียกกลับเข้ามาหา COBOL ผ่านกลไก JNI (Java Native Interface) จริง** ซึ่งเป็นเทคนิคที่ใช้กันจริงใน
โปรเจกต์ Modernization ระดับองค์กรที่ต้องการห่อหุ้ม (wrap) ตรรกะทางธุรกิจเดิมที่เขียนด้วย COBOL ให้ระบบ
สมัยใหม่ที่เขียนด้วย Java เรียกใช้งานได้โดยไม่ต้องเขียนตรรกะนั้นใหม่ทั้งหมด — เนื้อหาเรื่องการห่อหุ้ม
COBOL ด้วย REST API แบบเต็มรูปแบบจะสอนต่อใน **Part 073**

> **หมายเหตุความซื่อสัตย์เรื่องการทดสอบ**: สภาพแวดล้อมที่ใช้เขียน Part นี้มี GnuCOBOL, gcc, **และ JDK

> ขั้นตอนที่ 720 ที่ปกติถือเป็นเนื้อหาขั้นสูง** ได้ถูกคอมไพล์และรันทดสอบจริงจนได้ผลลัพธ์ที่แสดงไว้ทุก

> **ย้ำกฎเหล็กของหลักสูตร**: โค้ด COBOL/C/Java/Bash ทุกตัวอย่างในเอกสารนี้เป็นภาษาอังกฤษล้วน (comment,

## ขั้นตอนที่ 711: ทำไมต้องเชื่อมต่อ COBOL กับภาษาอื่น และแนวคิด Calling Convention

### เหตุผลเชิงธุรกิจที่ทำให้การเชื่อมต่อข้ามภาษาสำคัญ

ระบบ COBOL ในองค์กรจริง (ตามที่ Part 001 อธิบายสถิติไว้ตั้งแต่ต้นหลักสูตร) มักมีอายุหลายสิบปีและมีตรรกะ
ทางธุรกิจที่ผ่านการทดสอบมาอย่างยาวนานฝังอยู่ในตัวโปรแกรม การเขียนตรรกะเหล่านี้ใหม่ทั้งหมดด้วยภาษาอื่นมี
ความเสี่ยงสูงมาก (ตามที่ Part 001 ขั้นตอนที่ 3 อธิบายไว้) แนวทางที่นิยมกว่าคือ **"ห่อหุ้ม" (wrap) หรือ
"เชื่อมต่อ" (integrate)** โค้ด COBOL เดิมเข้ากับระบบสมัยใหม่ แทนที่จะเขียนใหม่ทั้งหมด — นี่คือหัวใจของ
สิ่งที่เรียกว่า **Legacy Modernization** ที่จะเป็นธีมหลักของเฟส 5 ทั้งเฟสนี้

การเชื่อมต่อ COBOL กับภาษาอื่นมีเหตุผลหลักสามข้อ:

1. **นำ Library ที่มีอยู่แล้วมาใช้**: บางงาน (เช่น การเข้ารหัสข้อมูลสมัยใหม่ การประมวลผลภาพ) มี Library
   สำเร็จรูปในภาษา C/Java อยู่แล้ว การเขียน COBOL ใหม่ทั้งหมดเพื่อทำงานเดียวกันเป็นการเสียเวลาโดยใช่เหตุ
2. **เชื่อมกับระบบสมัยใหม่**: ระบบ Web/Mobile สมัยใหม่มักเขียนด้วย Java/Python/Node.js — การเชื่อมต่อ
   โดยตรงทำให้ระบบใหม่เรียกใช้ตรรกะ COBOL เดิมได้โดยไม่ต้องย้ายข้อมูลหรือเขียนใหม่
3. **Performance-critical Routine**: บางครั้งมีการคำนวณเฉพาะทางที่ C ทำได้เร็วกว่า (เช่น การประมวลผล
   บิตระดับต่ำ) การเรียก C จาก COBOL เฉพาะจุดนั้นช่วยเพิ่มประสิทธิภาพโดยไม่ต้องเขียนทั้งระบบใหม่

### แนวคิดพื้นฐาน: Calling Convention คืออะไร

เมื่อโปรแกรมสองส่วนที่เขียนด้วยคนละภาษาต้อง "คุยกัน" ทั้งสองฝั่งต้องตกลงกันล่วงหน้าว่า:

- พารามิเตอร์จะถูกส่งผ่านไปอย่างไร (ผ่าน Stack? ผ่าน Register ของ CPU? ผ่าน pointer?)
- ใครเป็นผู้รับผิดชอบจัดสรร/คืนหน่วยความจำ
- ค่าที่ return กลับมาจะอยู่ที่ไหน

กฎชุดนี้เรียกว่า **Calling Convention** และในโลกของระบบปฏิบัติการอย่าง Linux/Windows บน CPU ตระกูล x86
มีมาตรฐานที่เรียกว่า **C Calling Convention (หรือ C ABI - Application Binary Interface)** ที่แทบทุกภาษา
โปรแกรมที่คอมไพล์เป็นภาษาเครื่องยึดตามเป็นมาตรฐานกลาง — Part 071 ขั้นตอนที่ 701-702 พิสูจน์ให้เห็นแล้วว่า
**GnuCOBOL เองก็แปลง COBOL เป็น C ก่อนคอมไพล์** ซึ่งหมายความว่า **โปรแกรม COBOL ที่คอมไพล์แล้วก็ยึดตาม C
ABI นี้อยู่แล้วโดยธรรมชาติ** — นี่คือเหตุผลที่การเรียก C จาก COBOL ทำได้ตรงไปตรงมากว่าที่หลายคนคาดคิด

### กฎสำคัญที่สุดข้อเดียวที่ต้องจำใน Part นี้

> **`CALL` ของ COBOL ส่งพารามิเตอร์แบบ `BY REFERENCE` เป็นค่าเริ่มต้นเสมอ (ทบทวนจาก Part 032) ซึ่งตรงกับ
> การส่ง "pointer" ในภาษา C พอดี** — นี่คือเหตุผลที่ COBOL เรียกฟังก์ชัน C ได้อย่างเป็นธรรมชาติ โดยที่
> ฟังก์ชัน C แค่ต้องรับพารามิเตอร์เป็น pointer ตามชนิดข้อมูลที่ตรงกันเท่านั้น

### ตัวอย่างแรก: CALL ฟังก์ชัน C ที่เรียบง่ายที่สุด

**ฟังก์ชัน C (`chello.c`):**

```c
#include <stdio.h>

/* The simplest possible C function a COBOL program can CALL: no
   parameters, no return value used by the caller. GnuCOBOL still
   expects it to behave like a normal C function - see the very next
   step for why its return type matters even here. */
void chello(void)
{
    printf("  (C) Hello from a plain C function.\n");
}
```

**โปรแกรม COBOL (`step711main.cob`):**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP711MAIN.
       AUTHOR. COBOL-COURSE.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: written entirely in COBOL.".
           CALL "chello".
           DISPLAY "Main: back in COBOL after the C function.".
           STOP RUN.
```

**คอมไพล์: ส่งทั้งไฟล์ .cob และไฟล์ .c เข้า cobc พร้อมกัน**

```bash
cobc -x step711main.cob chello.c -o step711
./step711
```

**ผลลัพธ์จริง:**

```
Main: written entirely in COBOL.
  (C) Hello from a plain C function.
Main: back in COBOL after the C function.
```

### อธิบายจุดสำคัญ

- `CALL "chello"` มีหน้าตาเหมือนกับ `CALL "STEP301SUB"` ที่เรียนมาตั้งแต่ Part 031 **ทุกประการ** — COBOL
  ไม่สนใจเลยว่าโปรแกรม/ฟังก์ชันที่ถูกเรียกเขียนด้วยภาษาอะไร ขอแค่ชื่อตรงกับสิ่งที่ถูก link เข้ามาด้วยก็พอ
  นี่คือพลังของการที่ทั้งสองภาษายึด C ABI เดียวกัน
- คำสั่งคอมไพล์ `cobc -x step711main.cob chello.c -o step711` แทบไม่ต่างจาก `cobc -x main.cob
  sub.cob -o program` ที่เรียนมาตั้งแต่ Part 031 เลย เพียงแค่ไฟล์ที่สองเป็น `.c` แทนที่จะเป็น `.cob` —
  `cobc` ฉลาดพอที่จะรู้ว่าไฟล์ `.c` ต้องส่งให้ `gcc` คอมไพล์ตรง ๆ (ไม่ต้องผ่านขั้นตอนแปลจาก COBOL)
- ชื่อฟังก์ชัน C (`chello`) ต้องสะกด**ตรงกับที่ระบุใน `CALL "..."` เป๊ะ รวมถึงตัวพิมพ์เล็ก-ใหญ่** เพราะ
  ภาษา C เป็น case-sensitive ตามธรรมชาติ (ต่างจากชื่อ `PROGRAM-ID` ของ COBOL ที่มักเขียนเป็นตัวพิมพ์ใหญ่
  ตามธรรมเนียม)

### ข้อควรระวัง — สิ่งที่สังเกตเห็นแต่ยังไม่อธิบายตอนนี้

ถ้าคุณลองตรวจสอบ exit code ของโปรแกรมข้างบนด้วย `echo $?` หลังรัน คุณอาจพบว่า **ค่าที่ได้ไม่ใช่ 0** ทั้งที่
โปรแกรมแสดงผลถูกต้องทุกบรรทัดและไม่มี error ใด ๆ ปรากฏให้เห็นเลย! นี่ไม่ใช่ความผิดพลาดในการเขียนเอกสารนี้
แต่เป็น**กับดักจริงที่ตั้งใจปล่อยทิ้งไว้ให้สังเกตเห็น** — ขั้นตอนถัดไปจะอธิบายสาเหตุที่แท้จริงและวิธีแก้
ไขอย่างละเอียด

### แบบฝึกหัดที่ 711.1

**โจทย์**: จงอธิบายว่าทำไมการที่ทั้ง COBOL (ผ่านการแปลงเป็น C ของ GnuCOBOL) และภาษา C ธรรมดายึดตาม "C
Calling Convention" เดียวกัน จึงเป็นเงื่อนไขจำเป็นที่ทำให้ `CALL "chello"` ทำงานได้โดยไม่ต้องเขียนโค้ด
แปลงข้อมูลระหว่างสองภาษาเพิ่มเติมเลย

**เฉลยแนวทาง**: ถ้าทั้งสองฝั่งไม่ได้ยึดกฎการส่งพารามิเตอร์/การจัดการ Stack แบบเดียวกัน โปรแกรม COBOL ที่
เรียก `CALL` จะวางพารามิเตอร์ไว้ในตำแหน่งหนึ่ง (ตาม COBOL ABI) แต่ฟังก์ชัน C ที่ถูกเรียกอาจไปมองหา
พารามิเตอร์ในตำแหน่งอื่น (ตาม C ABI ที่ต่างกัน) ทำให้อ่านค่าผิดพลาดหรือโปรแกรมล่มทันที เพราะ GnuCOBOL
แปลง COBOL เป็น C ก่อนคอมไพล์เสมอ (Part 071 ขั้นตอนที่ 701-702) โค้ดที่ได้จากโปรแกรม COBOL จึงเป็น
ฟังก์ชัน C ธรรมดาที่ยึด C ABI เดียวกันกับฟังก์ชัน C ทั่วไปโดยอัตโนมัติอยู่แล้ว การเรียกข้ามกันจึงทำได้
โดยตรงโดยไม่ต้องมีชั้นแปลงข้อมูล (Marshaling Layer) เพิ่มเติมเหมือนการเชื่อมต่อภาษาที่ใช้ runtime คนละ
แบบกัน (เช่น Java ที่ใช้ JVM ซึ่งจะอธิบายในขั้นตอนที่ 718-720)

## ขั้นตอนที่ 712: CALL ฟังก์ชัน C พร้อมพารามิเตอร์ — และกับดัก Exit Code ปริศนา

### ฟังก์ชัน C ที่รับ-คืนค่าผ่านพารามิเตอร์ (ไม่ใช่ return แบบภาษา C ทั่วไป)

ทบทวนจาก Part 031 ขั้นตอนที่ 303: **`CALL` ของ COBOL ไม่มีแนวคิดเรื่อง "ค่าที่ return" แบบฟังก์ชันปกติ**
การ "ส่งค่ากลับ" ต้องทำผ่านพารามิเตอร์ที่ส่งเข้าไปแล้วให้ผู้ถูกเรียกเขียนทับค่าลงไป — หลักการเดียวกันนี้
ใช้ได้กับการเรียกฟังก์ชัน C เช่นกัน

**ฟังก์ชัน C (`cmath.c`):**

```c
#include <stdio.h>

/* Simple C function to be called from COBOL via CALL. It takes two
   ints passed BY REFERENCE (pointers) and returns their sum through
   a third pointer parameter - COBOL's CALL has no notion of a
   "return value" the way a C function does, so results travel back
   through parameters, exactly like a COBOL subprogram.
   IMPORTANT: the function returns "int" (not "void") and explicitly
   returns 0. GnuCOBOL's CALL mechanism treats whatever value ends up
   in the CPU's return register as the called module's return code,
   which a later plain "STOP RUN" (with no explicit code) can pick up
   as the whole PROGRAM's exit status. A "void" C function leaves
   that register full of garbage - see this step's pitfall box for
   what that garbage looks like when it happens for real. */
int addtwo(int *a, int *b, int *result)
{
    *result = *a + *b;
    return 0;
}
```

**โปรแกรม COBOL (`step712main.cob`):**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP712MAIN.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-A          PIC S9(9) COMP-5 VALUE 10.
       01  WS-B          PIC S9(9) COMP-5 VALUE 32.
       01  WS-RESULT     PIC S9(9) COMP-5 VALUE 0.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: calling C function addtwo(" WS-A ", "
               WS-B ")".
           CALL "addtwo" USING WS-A WS-B WS-RESULT.
           DISPLAY "Main: result from C = " WS-RESULT.
           STOP RUN.
```

```bash
cobc -x step712main.cob cmath.c -o step712
./step712
echo "exit=$?"
```

**ผลลัพธ์จริง:**

```
Main: calling C function addtwo(+0000000010, +0000000032)
Main: result from C = +0000000042
exit=0
```

### อธิบายจุดสำคัญ

- `CALL "addtwo" USING WS-A WS-B WS-RESULT` ไม่มีคำว่า `BY REFERENCE` ปรากฏให้เห็น เพราะ **`BY
  REFERENCE` คือค่าเริ่มต้นของ COBOL อยู่แล้ว** (ทบทวนจาก Part 032) — พารามิเตอร์ทั้งสามตัวจึงถูกส่งเป็น
  pointer ไปยังหน่วยความจำจริงของ `WS-A`, `WS-B`, `WS-RESULT` ตรงกับที่ฟังก์ชัน C ประกาศรับเป็น
  `int *a, int *b, int *result` พอดี
- `PIC S9(9) COMP-5` คือชนิดข้อมูลไบนารีของ GnuCOBOL ที่ตรงกับ `int` ของภาษา C บนแพลตฟอร์มนี้ (อธิบาย
  รายละเอียดขนาดหน่วยความจำแบบเจาะลึกในขั้นตอนที่ 713) การเลือกใช้ `S9(9) COMP-5` แทน `PIC 9(9)`
  (DISPLAY ธรรมดา) เป็นสิ่งจำเป็นมากเมื่อจะส่งข้อมูลให้ C เพราะ DISPLAY numeric เก็บข้อมูลเป็นตัวอักษร
  ตัวเลขทีละไบต์ (zoned decimal) ซึ่ง**ไม่ตรงกับรูปแบบ `int` ของ C เลย**
- ฟังก์ชัน `addtwo` **ประกาศ return type เป็น `int` และมี `return 0;` อย่างชัดเจน** — นี่คือกุญแจสำคัญ
  ที่แก้ปัญหา Exit Code ปริศนาจากขั้นตอนที่แล้ว

### เจาะลึกกับดัก: ทำไม Exit Code ถึงผิดพลาดถ้า C ฟังก์ชัน return เป็น void

มาพิสูจน์ให้เห็นชัดเจนด้วยการย้อนกลับไปใช้ `void` เหมือนขั้นตอนที่ 711 แต่คราวนี้กับฟังก์ชันที่มี
พารามิเตอร์:

```c
#include <stdio.h>

/* BUG (deliberately introduced to prove the pitfall): this looks
   almost identical to addtwo() above, but returns "void" instead of
   "int". */
void addtwo_broken(int *a, int *b, int *result)
{
    *result = *a + *b;
}
```

คอมไพล์และรันด้วยโปรแกรม COBOL เดียวกัน (แค่เปลี่ยนชื่อฟังก์ชันที่ `CALL`):

```
Main: calling C function addtwo(+0000000010, +0000000032)
Main: result from C = +0000000042
exit=192
```

**สังเกตให้ดี**: ผลลัพธ์ที่ `DISPLAY` ออกมา **ถูกต้องทุกประการ** (`+0000000042`) แต่ **exit code ของ
กระบวนการทั้งโปรแกรมกลับกลายเป็น 192 แทนที่จะเป็น 0!** ไม่มี error message ใด ๆ ปรากฏให้เห็นเลยระหว่าง
รัน — นี่คือเหตุผลที่กับดักนี้อันตรายมาก เพราะโปรแกรมดู "ทำงานถูกต้องสมบูรณ์" ทุกอย่าง แต่ระบบภายนอกที่
คอยตรวจสอบ exit code ของโปรแกรม (เช่น สคริปต์ควบคุม Batch Job ตามที่ Part 066 สอนเรื่อง Job Scheduling
หรือ JCL Condition Code ตามที่ Part 053 สอน) จะเห็นว่าโปรแกรม "ล้มเหลว" ทั้งที่จริง ๆ แล้วทำงานถูกต้อง

### วิเคราะห์สาเหตุที่แท้จริง

กลไก `CALL` ของ GnuCOBOL คาดหวังว่าโปรแกรม/ฟังก์ชันที่ถูกเรียก (ไม่ว่าจะเป็น COBOL subprogram หรือ
ฟังก์ชัน C) จะ **"คืนค่า" กลับมาผ่าน Register ของ CPU ที่ใช้ส่งค่า return ตามธรรมเนียมของ C ABI เสมอ**
(เพราะ `CALL` ของ COBOL เองก็ทำงานแบบนี้ — โปรแกรมย่อย COBOL ที่ `GOBACK` ก็ส่งค่ากลับผ่าน Register
เดียวกันนี้) เมื่อฟังก์ชัน C ประกาศเป็น `void` คอมไพเลอร์ C จะ**ไม่เขียนคำสั่งใด ๆ ลงใน Register นั้นเลย**
ปล่อยให้มีค่าที่หลงเหลือ (garbage) จากคำสั่งก่อนหน้าอยู่ ค่าขยะนี้ถูกกลไกภายในของ GnuCOBOL อ่านไปตีความ
เป็น "ค่าที่โปรแกรมย่อยส่งกลับ" และเมื่อโปรแกรมหลักเรียก `STOP RUN` โดยไม่ระบุค่าอย่างชัดเจน **ค่าที่
เหลืออยู่นี้ก็กลายเป็น Exit Code ของกระบวนการทั้งหมดไปโดยปริยาย** (รายละเอียดกลไก `RETURN-CODE` ที่อยู่
เบื้องหลังเรื่องนี้จะอธิบายเต็มรูปแบบในขั้นตอนที่ 716)

### ข้อควรระวัง

- **ฟังก์ชัน C ทุกตัวที่จะถูก `CALL` จากโปรแกรม COBOL ควรประกาศ return type เป็น `int` และมี `return`
  ค่าที่ชัดเจนเสมอ (แนะนำให้ return 0 เมื่อสำเร็จ) แม้ตรรกะของฟังก์ชันจะไม่ได้ใช้ค่า return นั้นเลยก็ตาม**
  — นี่คือกฎที่สำคัญที่สุดข้อหนึ่งของ Part นี้และควรกลายเป็นธรรมเนียมปฏิบัติทันทีเมื่อเขียน C สำหรับ
  COBOL
- อย่าไว้ใจแค่ผลลัพธ์ `DISPLAY` ที่ถูกต้องว่าโปรแกรมทำงานสมบูรณ์แล้ว **ต้องตรวจสอบ exit code ด้วยเสมอ**
  โดยเฉพาะในโปรแกรมที่เรียกใช้ฟังก์ชันภายนอก เพราะปัญหาแบบนี้ไม่มี error message เตือนเลยแม้แต่นิดเดียว
- ปัญหานี้เป็นตัวอย่างที่ดีของ**คลาสบั๊กที่เกิดจาก "สมมติฐานเงียบ" (Implicit Contract)** ระหว่างสอง
  ภาษา — ไม่มีเอกสารใดบังคับให้ฟังก์ชัน C ต้อง return int ตอนคอมไพล์ (คอมไพล์ผ่านสมบูรณ์แบบไม่มี
  warning) แต่พฤติกรรม runtime กลับผิดเพี้ยนอย่างเงียบ ๆ

### แบบฝึกหัดที่ 712.1

**โจทย์**: จงอธิบายว่าทำไมการทดสอบโปรแกรมด้วยการดู `DISPLAY` output เพียงอย่างเดียว (โดยไม่ตรวจสอบ exit
code) จึงไม่เพียงพอสำหรับการยืนยันว่าโปรแกรมที่เชื่อมต่อกับภาษาอื่นทำงานถูกต้องสมบูรณ์

**เฉลยแนวทาง**: ตามที่พิสูจน์ในขั้นตอนนี้ โปรแกรมที่มีบั๊ก (ฟังก์ชัน C เป็น `void`) ให้ผลลัพธ์ `DISPLAY`
ที่ถูกต้องทุกประการเหมือนโปรแกรมที่ไม่มีบั๊กเลย ความแตกต่างปรากฏเฉพาะที่ **exit code ของกระบวนการ**
เท่านั้น (0 กับ 192) ซึ่งไม่ปรากฏให้เห็นในหน้าจอปกติเลยนอกจากจะตรวจสอบด้วยคำสั่งเช่น `echo $?` โดยตรง
ระบบอัตโนมัติจำนวนมากในโลกการทำงานจริง (เช่น Job Scheduler ตาม Part 066, CI/CD Pipeline ตาม Part 078,
หรือ Shell Script ที่เรียกโปรแกรมต่อกันเป็น Batch Chain) **ตัดสินความสำเร็จ/ล้มเหลวของโปรแกรมจาก exit
code เป็นหลัก ไม่ใช่จากข้อความที่แสดงผล** ดังนั้นการทดสอบโปรแกรมที่เชื่อมต่อข้ามภาษาจึงต้องตรวจสอบทั้ง
ผลลัพธ์ที่แสดงและ exit code ควบคู่กันเสมอ มิเช่นนั้นบั๊กแบบนี้อาจหลุดรอดไปจนถึงระบบ Production และทำให้
ขั้นตอนถัดไปในสาย Batch Job เข้าใจผิดว่างานก่อนหน้าล้มเหลว

## ขั้นตอนที่ 713: ขนาดข้อมูล COMP-5 ต้องตรงกับชนิดข้อมูล C เป๊ะ — พิสูจน์บั๊กจากขนาดไม่ตรงกัน

### COMP-5 ไม่ใช่แค่ "ตัวเลขไบนารี" — ขนาดจริงขึ้นอยู่กับจำนวนหลัก

Part 032 สอนเรื่องการส่งพารามิเตอร์ไว้ แต่ยังไม่ได้เจาะลึกเรื่องขนาดหน่วยความจำที่แท้จริงของ `COMP-5`
ซึ่งสำคัญมากเมื่อต้องจับคู่กับชนิดข้อมูลของภาษา C ให้ตรงกันเป๊ะ เราตรวจสอบเรื่องนี้ได้โดยใช้ `cobc -C`
(เทคนิคจาก Part 071 ขั้นตอนที่ 702) ดูไฟล์ผู้ช่วย `.c.l.h` ที่เก็บตัวแปร WORKING-STORAGE จริง:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SIZETEST.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  A PIC S9(4) COMP-5.
       01  B PIC S9(9) COMP-5.
       01  C PIC S9(18) COMP-5.
       PROCEDURE DIVISION.
       MAIN-PARA. STOP RUN.
```

```bash
cobc -C sizetest.cob -o sizetest.c
cat sizetest.c.l.h
```

**ผลลัพธ์จริง (ส่วนที่สำคัญ):**

```
/* WORKING-STORAGE Data */
static int	b_2;	/* RETURN-CODE */
static cob_u8_t	b_8[2] __attribute__((aligned));	/* A */
static cob_u8_t	b_9[4] __attribute__((aligned));	/* B */
static cob_u8_t	b_10[8] __attribute__((aligned));	/* C */
```

### ตารางขนาดหน่วยความจำจริงของ COMP-5 (ยืนยันด้วยการทดสอบจริง)

| PICTURE Clause | จำนวนหลัก | ขนาดในหน่วยความจำ | ชนิดข้อมูล C ที่ตรงกัน (บนแพลตฟอร์ม 64-bit นี้) |
|---|---|---|---|
| `PIC S9(4) COMP-5` | 1-4 หลัก | 2 ไบต์ | `short` |
| `PIC S9(9) COMP-5` | 5-9 หลัก | 4 ไบต์ | `int` |
| `PIC S9(18) COMP-5` | 10-18 หลัก | 8 ไบต์ | `long long` |

นี่คือกฎที่ **ต้องจำให้แม่นก่อนเขียน C ฟังก์ชันใด ๆ ที่จะรับพารามิเตอร์จาก COBOL** — เลือกขนาดผิดแม้แค่
นิดเดียวก็นำไปสู่บั๊กที่ตรวจจับไม่ได้ตอนคอมไพล์ (เหมือนที่ Part 031 ขั้นตอนที่ 304 พิสูจน์ไว้กับการ
`CALL` ระหว่าง COBOL ด้วยกันเองเรื่องจำนวนพารามิเตอร์ไม่ตรงกัน — หลักการเดียวกันนี้ยิ่งอันตรายกว่าเมื่อ
ข้ามภาษา)

### พิสูจน์บั๊กจริงจากขนาดไม่ตรงกัน

**ฟังก์ชัน C ที่มีบั๊ก (เข้าใจผิดว่าพารามิเตอร์เป็น `short` แต่ COBOL ส่งมาเป็น 4-byte `int`):**

```c
#include <stdio.h>
/* BUG: this treats the incoming pointer as "short *" (2 bytes) even
   though the COBOL caller's PIC S9(9) COMP-5 field is 4 bytes wide. */
int badsize(short *a, short *b, short *result)
{
    *result = *a + *b;
    return 0;
}
```

**โปรแกรม COBOL:**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP713BAD.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-A          PIC S9(9) COMP-5 VALUE 20000.
       01  WS-B          PIC S9(9) COMP-5 VALUE 20000.
      *> Deliberately start with a nonzero, nonsense value so any
      *> byte that the mismatched C function fails to touch stays
      *> visible in the final DISPLAY, instead of hiding the bug.
       01  WS-RESULT     PIC S9(9) COMP-5 VALUE 777777.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: calling badsize(" WS-A ", " WS-B
               ") - correct answer is 40000".
           CALL "badsize" USING WS-A WS-B WS-RESULT.
           DISPLAY "Main: WS-RESULT (4-byte COMP-5) = " WS-RESULT.
           STOP RUN.
```

```bash
cobc -x step713bad.cob sizemismatch.c -o step713bad
./step713bad
```

**ผลลัพธ์จริง:**

```
Main: calling badsize(+0000020000, +0000020000) - correct answer is 40000
Main: WS-RESULT (4-byte COMP-5) = +0000760896
```

**ผลลัพธ์ผิดพลาดอย่างชัดเจน!** คำตอบที่ถูกต้องคือ 40000 แต่ได้ 760896 แทน

### วิเคราะห์สาเหตุ

`WS-A` และ `WS-B` เป็น `PIC S9(9) COMP-5` (4 ไบต์ตามตารางข้างต้น) แต่ฟังก์ชัน `badsize` เข้าใจผิดว่าเป็น
`short *` (มองเห็นแค่ 2 ไบต์แรกของแต่ละตัว) เมื่ออ่านค่า 20000 ผ่านมุมมอง `short` (ซึ่งพอดียังอ่านค่า
ถูกต้องเพราะ 20000 ยังอยู่ในขอบเขตของ `short` ที่เก็บได้ถึง 32767) การคำนวณภายในฟังก์ชันจึงยังคำนวณผล
ลัพธ์คลาดเคลื่อน แต่ปัญหาที่ร้ายแรงกว่าคือ **ตอนเขียนผลลัพธ์กลับ ฟังก์ชันเขียนแค่ 2 ไบต์แรกของ
`WS-RESULT`** (ซึ่งเป็น `int` 4 ไบต์จริง) ทำให้ **2 ไบต์บนของ `WS-RESULT` ยังคงเป็นค่าขยะเดิมจาก
`VALUE 777777` ที่ตั้งไว้ตอนแรก** ผลลัพธ์สุดท้ายจึงเป็นการผสมกันระหว่างค่าที่คำนวณผิดพลาดกับค่าขยะที่หลง
เหลืออยู่ ไม่ใช่แค่ "ปัดเศษผิด" แต่เป็น**ข้อมูลที่เสียหายโดยสมบูรณ์**

### ข้อควรระวัง

- **ขนาดของพารามิเตอร์ C ต้องตรงกับขนาดจริงของ COMP-5 ฝั่ง COBOL เป๊ะเสมอ** ไม่มีการเตือนใด ๆ ตอน
  คอมไพล์เลยแม้แต่น้อย (เหมือนกับปัญหาจำนวนพารามิเตอร์ไม่ตรงกันใน Part 031 ขั้นตอนที่ 304 — คอมไพล์แต่
  ละไฟล์แยกกันจึงไม่มีการตรวจสอบข้าม compilation unit)
- ตัวเลขขนาดเล็กที่บังเอิญพอดีกับขอบเขตของชนิดข้อมูลที่ผิด (เช่นตัวอย่างนี้ที่ 20000 ยังอยู่ในขอบเขตของ
  `short`) **อาจไม่ทำให้เห็นบั๊กชัดเจนในการทดสอบเบื้องต้น** จนกว่าจะมีตัวเลขที่ใหญ่พอในระบบจริงจึงจะเห็น
  ปัญหา — ควรทดสอบด้วยค่าที่หลากหลาย โดยเฉพาะค่าขอบเขต (boundary value) เสมอ
- แนวทางที่ปลอดภัยที่สุดคือ **กำหนด PICTURE ให้เห็นชัดเจนในคอมเมนต์ของฟังก์ชัน C เสมอว่าคาดหวังขนาดกี่
  ไบต์** (ดังตัวอย่าง comment ในโค้ด `addtwo`/`badsize` ข้างต้น) เพื่อให้ผู้ดูแลโค้ดในอนาคตตรวจสอบได้ง่าย

### แบบฝึกหัดที่ 713.1

**โจทย์**: จงอธิบายว่าทำไมการทดสอบด้วยค่า `WS-A = 20000, WS-B = 20000` (ผลรวม 40000) จึงเผยบั๊กได้ชัดเจน
กว่าการทดสอบด้วยค่าเล็ก ๆ เช่น `WS-A = 10, WS-B = 32` เหมือนในขั้นตอนที่ 712

**เฉลยแนวทาง**: ค่า 10 และ 32 มีผลรวม 42 ซึ่งเป็นตัวเลขที่เล็กมาก แม้ฟังก์ชัน C จะอ่าน/เขียนแค่ 2 ไบต์
แรกของฟิลด์ 4 ไบต์ (ตามมุมมอง `short` ที่ผิด) 2 ไบต์บนที่เหลือก็ยังคงเป็น 0 พอดี (เพราะเริ่มต้นด้วย
`VALUE 0` และตัวเลขมีค่าน้อยมาก) ทำให้ผลลัพธ์ที่อ่านแบบ 4 ไบต์เต็มกลับดู "ถูกต้อง" โดยบังเอิญ ซ่อนบั๊ก
ไว้ไม่ให้เห็น ในทางตรงข้าม ค่า 20000 และ 20000 (ผลรวม 40000) เกินขอบเขตที่ `short` 2 ไบต์จะเก็บได้อย่าง
ถูกต้องในบางกรณี และการตั้งค่าเริ่มต้นของ `WS-RESULT` เป็น `777777` (ไม่ใช่ 0) ทำให้ 2 ไบต์บนที่ไม่ถูก
แตะต้องยังคงมีค่าขยะที่ไม่ใช่ศูนย์หลงเหลืออยู่ เมื่ออ่านค่าทั้ง 4 ไบต์รวมกัน ผลลัพธ์จึงผิดเพี้ยนอย่างชัดเจน
บทเรียนสำคัญคือ **การทดสอบด้วยค่าเล็ก ๆ หรือค่าเริ่มต้นเป็นศูนย์เสมอ อาจซ่อนบั๊กประเภทนี้ไว้ได้** ควร
ทดสอบด้วยค่าที่หลากหลายและตั้งค่าเริ่มต้นเป็นค่าที่ไม่ใช่ศูนย์เพื่อเผยบั๊กแบบนี้ให้เห็นชัดเจนตั้งแต่ขั้น
ตอนพัฒนา

## ขั้นตอนที่ 714: ส่งข้อความ (PIC X) ระหว่าง COBOL กับ C — ไม่มี Null Terminator

### ความแตกต่างพื้นฐานระหว่างสตริงของ COBOL กับ C

ภาษา C แทนสตริง (string) ด้วย array ของ `char` ที่ **จบด้วยไบต์ `\0` (null terminator)** เสมอ — ฟังก์ชัน
มาตรฐานอย่าง `strlen()` ทำงานโดยไล่หาไบต์ `\0` นี้เพื่อรู้ว่าสตริงจบตรงไหน

แต่ COBOL **ไม่มีแนวคิดเรื่อง null terminator เลย** ฟิลด์ `PIC X(n)` คือ**พื้นที่ความยาวคงที่ n ไบต์**
เติมด้วยช่องว่าง (space) ทางด้านขวาเสมอถ้าข้อมูลสั้นกว่าความยาวที่ประกาศไว้ (ทบทวนกฎ MOVE จาก Part 008)
— **นี่คือจุดที่ทำให้การส่งข้อความข้ามภาษาต้องระมัดระวังเป็นพิเศษ**

### ฟังก์ชัน C ที่ทำงานกับ PIC X โดยตรง

```c
#include <string.h>
#include <ctype.h>

/* Converts a fixed-length, SPACE-padded COBOL PIC X field to upper
   case in place. COBOL character data passed BY REFERENCE (the
   default) arrives as a plain pointer to a byte buffer - there is NO
   null terminator, unlike a normal C string, and the buffer is
   exactly as many bytes as the COBOL PICTURE clause declares. "len"
   is passed so this C function knows how many bytes it may safely
   touch, since it cannot find the end with strlen(). */
int touppercase(char *text, int *len)
{
    int i;
    for (i = 0; i < *len; i++) {
        text[i] = toupper((unsigned char) text[i]);
    }
    return 0;
}
```

### โปรแกรม COBOL

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP714MAIN.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-TEXT       PIC X(20) VALUE "somchai jaidee".
      *> PIC S9(9) COMP-5 is GnuCOBOL's 4-byte native binary integer
      *> width - matching C's "int" (also 4 bytes on this platform)
      *> exactly. Using a size that does not match the C parameter's
      *> real size is a classic and dangerous interop bug (see the
      *> pitfall box).
       01  WS-LEN        PIC S9(9) COMP-5 VALUE 20.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: before = [" WS-TEXT "]".
           CALL "touppercase" USING WS-TEXT WS-LEN.
           DISPLAY "Main: after  = [" WS-TEXT "]".
           STOP RUN.
```

```bash
cobc -x step714main.cob cstring.c -o step714
./step714
```

**ผลลัพธ์จริง:**

```
Main: before = [somchai jaidee      ]
Main: after  = [SOMCHAI JAIDEE      ]
```

### อธิบายจุดสำคัญ

- `WS-TEXT PIC X(20)` เก็บ `"somchai jaidee"` (14 ตัวอักษร) พร้อมช่องว่างเติมท้ายอีก 6 ตัว รวมเป็น 20
  ไบต์พอดี — ฟังก์ชัน C มองเห็นพื้นที่นี้เป็น `char[20]` ธรรมดา **ไม่มี `\0` ปรากฏที่ตำแหน่งใดเลย**
- ฟังก์ชัน `touppercase` **ไม่ใช้ `strlen()` เลย** (เพราะจะหา `\0` ไม่เจอ อาจไล่อ่านเลยขอบเขตของฟิลด์ไป
  จนกว่าจะเจอไบต์ที่บังเอิญเป็น 0 ในหน่วยความจำข้างเคียง ซึ่งเป็นอันตรายมาก) แต่ใช้พารามิเตอร์ `len`
  (ส่งมาจาก `WS-LEN`) เพื่อรู้ขอบเขตที่ปลอดภัยแทน — **นี่คือรูปแบบมาตรฐานที่ต้องใช้เสมอเมื่อ C ทำงานกับ
  ข้อมูลข้อความจาก COBOL**
- ผลลัพธ์แสดงให้เห็นว่าช่องว่างท้าย (`      `) ยังคงอยู่ครบถ้วนหลังแปลงเป็นตัวพิมพ์ใหญ่ เพราะ
  `toupper()` กับตัวอักษรช่องว่างไม่มีผลใด ๆ (ไม่ใช่ตัวอักษร a-z) — พฤติกรรมนี้ถูกต้องตามที่ควรจะเป็น

### ข้อควรระวัง

- **ห้ามใช้ฟังก์ชันมาตรฐานของ C ที่พึ่งพา null terminator (เช่น `strlen`, `strcpy`, `printf("%s", ...)`)
  กับข้อมูลที่มาจากฟิลด์ COBOL `PIC X` โดยตรงเด็ดขาด** เพราะไม่มี `\0` รับประกันอยู่ในข้อมูลนั้นเลย ฟังก์ชัน
  เหล่านี้อาจไล่อ่านเลยขอบเขตของฟิลด์ไปจนกว่าจะเจอไบต์ 0 ที่ใดที่หนึ่งในหน่วยความจำ ซึ่งอาจนำไปสู่ปัญหา
  ความปลอดภัยร้ายแรง (Buffer Over-read) ในโค้ด production จริง
- ถ้าจำเป็นต้องใช้ฟังก์ชันมาตรฐานของ C ที่ต้องการ null-terminated string จริง ๆ ต้อง**คัดลอกข้อมูลไปยัง
  buffer ใหม่ที่มีขนาดใหญ่กว่าความยาวเดิม 1 ไบต์ แล้วเติม `\0` เองอย่างชัดเจน** ก่อนเรียกใช้ฟังก์ชันนั้น
- ต้องส่งความยาวของข้อความ (`len`) ไปพร้อมกับตัวข้อความเองเสมอเมื่อ C ต้องประมวลผลข้อความจาก COBOL —
  อย่าคาดเดาความยาวจากภายในฟังก์ชัน C เอง

### แบบฝึกหัดที่ 714.1

**โจทย์**: จงอธิบายว่าทำไมการที่ COBOL "ไม่มีแนวคิดเรื่อง null terminator" จึงถือเป็นทั้งข้อดีและข้อควร
ระวังในเวลาเดียวกันเมื่อเปรียบเทียบกับสตริงของ C

**เฉลยแนวทาง**: ข้อดีคือ**ความยาวของ field ที่ `PIC X(n)` ประกาศไว้ชัดเจนตายตัวเสมอ** ไม่ต้องเผื่อพื้นที่
เพิ่ม 1 ไบต์สำหรับ `\0` เหมือน C string และไม่มีความเสี่ยงเรื่อง "ลืมปิดท้ายด้วย null" ที่เป็นบั๊กคลาสสิก
ในโลก C (เช่น Buffer Overflow ที่โด่งดัง) — ทุกฟิลด์มีขนาดคงที่ที่รู้ล่วงหน้าแน่นอน ตรวจสอบง่าย ข้อควร
ระวังคือ**เมื่อต้องส่งข้อมูลนี้ไปให้ภาษาอื่นที่คาดหวัง null-terminated string (เช่น C มาตรฐาน)** ต้อง
แปลงรูปแบบก่อนเสมอ (เติม `\0` เอง หรือส่งความยาวไปด้วยอย่างชัดเจนแบบที่ตัวอย่างนี้ทำ) มิเช่นนั้นฟังก์ชัน
มาตรฐานของ C ฝั่งนั้นจะไม่รู้ว่าข้อความจบตรงไหน ซึ่งอาจนำไปสู่การอ่านข้อมูลเลยขอบเขตที่ตั้งใจไว้

## ขั้นตอนที่ 715: BY VALUE และ RETURNING เมื่อเรียก C — ส่งสำเนา ไม่ใช่ที่อยู่

### ทบทวน BY VALUE จาก Part 032

Part 032 สอนไว้ว่า `BY VALUE` ส่ง**สำเนาของค่า**ไปให้ผู้ถูกเรียก ไม่ใช่ที่อยู่ของหน่วยความจำจริง —
ผู้ถูกเรียกแก้ไขค่าที่ได้รับเท่าไรก็ไม่มีผลย้อนกลับมาที่ผู้เรียกเลย ต่างจาก `BY REFERENCE` (ค่าเริ่มต้น)
ที่ใช้มาตลอดในขั้นตอนก่อนหน้าของ Part นี้ ทั้งสองแบบนี้ใช้ได้กับการเรียก C เช่นกัน และ `BY VALUE` ยัง
สอดคล้องพอดีกับวิธีที่ฟังก์ชัน C ทั่วไปมักรับพารามิเตอร์ตัวเลขธรรมดา (ไม่ใช่ pointer)

### ฟังก์ชัน C ที่รับค่าแบบธรรมดา (ไม่ใช่ pointer) และคืนค่ากลับแบบฟังก์ชัน C ปกติ

```c
#include <stdio.h>

/* This C function receives "n" BY VALUE - a plain int, not a
   pointer. Doubling it here can NEVER be seen by the caller, because
   only a copy of the number was handed over, not a reference to the
   caller's storage. */
int doubleit(int n)
{
    n = n * 2;
    printf("  (C) doubleit: received %d, doubled to %d internally.\n",
        n / 2, n);
    return n;
}
```

### โปรแกรม COBOL — ใช้ BY VALUE ร่วมกับ RETURNING

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP715MAIN.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-N          PIC S9(9) COMP-5 VALUE 21.
       01  WS-DOUBLED    PIC S9(9) COMP-5 VALUE 0.

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: WS-N before CALL = " WS-N.
      *> BY VALUE passes a COPY of WS-N's current value to the C
      *> function - the C side receives a plain "int", not a pointer,
      *> matching ordinary C function call conventions exactly.
           CALL "doubleit" USING BY VALUE WS-N
               RETURNING WS-DOUBLED.
           DISPLAY "Main: WS-N after CALL  = " WS-N
               " (unchanged - BY VALUE never modifies the caller)".
           DISPLAY "Main: WS-DOUBLED from RETURNING = " WS-DOUBLED.
           STOP RUN.
```

```bash
cobc -x step715main.cob cvalue.c -o step715
./step715
```

**ผลลัพธ์จริง:**

```
Main: WS-N before CALL = +0000000021
  (C) doubleit: received 21, doubled to 42 internally.
Main: WS-N after CALL  = +0000000021 (unchanged - BY VALUE never modifies the caller)
Main: WS-DOUBLED from RETURNING = +0000000042
```

### อธิบายจุดสำคัญ

- `USING BY VALUE WS-N` ส่ง**สำเนา**ของค่า 21 ไปให้ `doubleit` — ฟังก์ชัน C รับพารามิเตอร์เป็น `int n`
  ธรรมดา (ไม่ใช่ `int *n`) ตรงกับที่ C จะเขียนฟังก์ชันปกติที่ไม่ต้องแก้ไขค่าของผู้เรียกเลยทุกประการ
- ผลลัพธ์ `WS-N after CALL = +0000000021` (ยังคงเป็น 21 ไม่ใช่ 42) **ยืนยันชัดเจนว่า BY VALUE ไม่มีทาง
  แก้ไขค่าต้นทางของผู้เรียกได้เลย** แม้ภายในฟังก์ชัน C จะคำนวณและ `printf` ค่า 42 ออกมาก็ตาม เพราะสิ่งที่
  ฟังก์ชันแก้ไขคือ**สำเนา**ในพารามิเตอร์ `n` ของตัวเองเท่านั้น
- **`RETURNING WS-DOUBLED`** คือ syntax เสริมของ `CALL` (มาตรฐาน COBOL-2002 เป็นต้นมา) ที่ทำให้รับ
  ค่าที่ฟังก์ชัน C `return` กลับมาแบบปกติ (ไม่ต้องผ่านพารามิเตอร์แบบที่ทำในขั้นตอนที่ 712-713) — ใช้ได้
  ดีเมื่อฟังก์ชัน C ที่จะเรียกเขียนในสไตล์ C มาตรฐานทั่วไปที่ไม่ได้ออกแบบมาเพื่อ COBOL โดยเฉพาะ
- สังเกตว่า `WS-DOUBLED PIC S9(9) COMP-5` ต้องมีขนาดตรงกับ `int` ที่ `doubleit` return กลับมาด้วย ตาม
  กฎเดียวกับที่เรียนในขั้นตอนที่ 713

### ข้อควรระวัง

- ถ้าลองสั่ง `echo $?` หลังรันโปรแกรมนี้ จะพบว่า **exit code เป็น 42 ไม่ใช่ 0!** นี่ไม่ใช่บั๊กจากฟังก์ชัน
  C แบบขั้นตอนที่ 712 แต่เป็นผลข้างเคียงของ `RETURNING` เอง — รายละเอียดกลไกนี้และวิธีควบคุมให้ได้ exit
  code ที่ต้องการจะอธิบายเต็มรูปแบบในขั้นตอนที่ 716 ถัดไปทันที
- `BY VALUE` เหมาะกับพารามิเตอร์ตัวเลขธรรมดาเท่านั้น **ไม่ควรใช้กับข้อมูลขนาดใหญ่ เช่น Group Item หรือ
  PIC X ความยาวมาก** เพราะการคัดลอกข้อมูลทุกครั้งที่เรียกจะสิ้นเปลืองทรัพยากรโดยไม่จำเป็น (ทบทวนหลักการ
  เดียวกันจาก Part 032)
- `RETURNING` รับค่าได้เพียง**ค่าเดียว**เท่านั้น ถ้าต้องการค่ากลับหลายค่า ยังคงต้องใช้เทคนิคพารามิเตอร์
  `BY REFERENCE` แบบขั้นตอนที่ 712-713 เหมือนเดิม

### แบบฝึกหัดที่ 715.1

**โจทย์**: จงอธิบายว่าทำไมการใช้ `BY VALUE` กับพารามิเตอร์ `WS-N` ในตัวอย่างนี้จึง "ปลอดภัยกว่า" การใช้
`BY REFERENCE` (ค่าเริ่มต้น) ในสถานการณ์ที่ผู้เรียกไม่ต้องการให้ค่าต้นทางถูกแก้ไขโดยไม่ได้ตั้งใจ

**เฉลยแนวทาง**: เมื่อใช้ `BY REFERENCE` ฟังก์ชันที่ถูกเรียกจะได้รับที่อยู่ของหน่วยความจำจริงของผู้เรียก
ไปตรง ๆ หากฟังก์ชันนั้นมีบั๊กหรือเขียนโค้ดผิดพลาด (ไม่ว่าจะตั้งใจหรือไม่) แก้ไขค่าที่ตำแหน่งนั้นโดยไม่
ควร ผู้เรียกจะเห็นค่าของตัวเองเปลี่ยนแปลงไปโดยไม่คาดคิด (Side Effect) ซึ่งอาจทำให้ตามหาสาเหตุของบั๊กได้
ยากมากในระบบใหญ่ ในทางตรงข้าม `BY VALUE` รับประกันทางเทคนิคว่า**ไม่มีทางที่ฟังก์ชันปลายทางจะแก้ไขค่าต้น
ทางของผู้เรียกได้เลย** ไม่ว่าฟังก์ชันนั้นจะเขียนถูกหรือผิดก็ตาม เพราะสิ่งที่ส่งไปคือสำเนาที่แยกออกจากกัน
โดยสมบูรณ์ ทำให้เหมาะมากสำหรับพารามิเตอร์ที่เป็นแค่ "ข้อมูลนำเข้า" (Input-only) ที่ไม่ต้องการให้มีการ
แก้ไขค่ากลับมาเลย

## ขั้นตอนที่ 716: RETURN-CODE Special Register — ที่มาที่แท้จริงของ Exit Code ปริศนา

### RETURN-CODE คืออะไร

Part 011 เคยกล่าวถึงแนวคิด Special Register ผ่าน ๆ มาบ้าง (เช่นใน EVALUATE) แต่ยังไม่ได้เจาะลึกตัวที่
สำคัญที่สุดตัวหนึ่งสำหรับ Part นี้: **`RETURN-CODE`** — เป็น Special Register ที่ GnuCOBOL จองไว้ให้
อัตโนมัติในทุกโปรแกรม (ไม่ต้องประกาศเองใน `WORKING-STORAGE SECTION`) ใช้เก็บ **"รหัสสถานะการทำงาน"**
ของโปรแกรม และมีกฎสำคัญสองข้อ:

1. **`CALL ... RETURNING ...`** (แบบที่ใช้ในขั้นตอนที่ 715) จะ**อัปเดตค่าของ `RETURN-CODE` โดยอัตโนมัติ**
   ให้เท่ากับค่าที่ฟังก์ชันปลายทาง return กลับมา
2. **`STOP RUN` โดยไม่ระบุค่าใด ๆ อย่างชัดเจน จะใช้ค่าปัจจุบันของ `RETURN-CODE` เป็น Exit Code ของ
   กระบวนการทั้งหมด**

กฎสองข้อนี้รวมกันคือคำอธิบายที่แท้จริงของปรากฏการณ์ที่เห็นในขั้นตอนที่ 712 และ 715: การเรียก `CALL` (ไม่
ว่าจะเป็นฟังก์ชัน C แบบ `void` ที่ทิ้งค่าขยะไว้ในขั้นตอนที่ 712 หรือ `RETURNING` ที่รับค่า 42 มาในขั้นตอน
ที่ 715) **แก้ไขค่า `RETURN-CODE` โดยไม่รู้ตัว** และเมื่อ `STOP RUN` ตามมาโดยไม่ระบุค่า ค่านั้นก็รั่วไหล
ออกไปเป็น exit code ของทั้งโปรแกรมทันที

### พิสูจน์ด้วยการควบคุม RETURN-CODE อย่างชัดเจน

นำโปรแกรมจากขั้นตอนที่ 715 (ที่มี exit code = 42) มาแก้ไขโดยเพิ่มการควบคุม `RETURN-CODE` อย่างชัดเจน
ก่อน `STOP RUN`:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP716MAIN.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-N          PIC S9(9) COMP-5 VALUE 21.
       01  WS-DOUBLED    PIC S9(9) COMP-5 VALUE 0.

       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "doubleit" USING BY VALUE WS-N
               RETURNING WS-DOUBLED.
           DISPLAY "Main: WS-DOUBLED = " WS-DOUBLED.
      *> RETURNING (and, in some runtimes, any CALL's return value)
      *> updates the special register RETURN-CODE. A plain STOP RUN
      *> with no explicit value uses WHATEVER is currently in
      *> RETURN-CODE as the process's OS exit status - so without
      *> this line, the shell would see exit code 42, not 0, purely
      *> as a side effect of the CALL above.
           MOVE 0 TO RETURN-CODE.
           STOP RUN.
```

```bash
cobc -x step716main.cob cvalue.c -o step716
./step716
echo "exit=$?"
```

**ผลลัพธ์จริง:**

```
  (C) doubleit: received 21, doubled to 42 internally.
Main: WS-DOUBLED = +0000000042
exit=0
```

เพียงเพิ่มบรรทัด **`MOVE 0 TO RETURN-CODE.`** ก่อน `STOP RUN` ค่า exit code ก็กลายเป็น 0 ตามที่ต้องการ
ทันที ทั้งที่ผลลัพธ์ `WS-DOUBLED` ยังคงถูกต้อง (42) เหมือนเดิมทุกประการ — พิสูจน์ชัดเจนว่า `RETURN-CODE`
กับผลลัพธ์ทางธุรกิจของโปรแกรม (`WS-DOUBLED`) เป็นคนละเรื่องกันโดยสิ้นเชิง

### อธิบายจุดสำคัญ

- `RETURN-CODE` เขียนและอ่านได้เหมือนตัวแปรธรรมดา (`MOVE 0 TO RETURN-CODE`, `DISPLAY RETURN-CODE`) แม้
  จะไม่ต้องประกาศเองก็ตาม — เป็นกลไกเดียวกับที่ Mainframe ใช้ส่งต่อ **Condition Code** ระหว่าง Step ต่าง
  ๆ ใน JCL (ทบทวนจาก Part 053) ทำให้แนวคิดนี้ไม่ใช่เรื่องใหม่ในโลก COBOL แต่เป็นรากฐานเดียวกันที่ขยายมา
  ใช้กับการเชื่อมต่อภาษาอื่นด้วย
- กฎทองคือ: **ทุกโปรแกรม COBOL ที่เป็นจุดเริ่มต้น (Top-level, มี `-x` ตอนคอมไพล์) ที่เรียก `CALL` ที่มี
  การใช้ `RETURNING` หรือเรียกฟังก์ชันภายนอก ควรตั้งค่า `RETURN-CODE` อย่างชัดเจนก่อน `STOP RUN` เสมอ**
  ไม่ควรปล่อยให้ค่าที่หลงเหลือจาก `CALL` ก่อนหน้ารั่วไหลออกไปเป็น exit code โดยไม่ได้ตั้งใจ
- ถ้าต้องการให้โปรแกรมส่ง exit code ที่มีความหมาย (เช่น รายงานสถานะความสำเร็จ/ล้มเหลวให้ shell script
  ที่เรียกโปรแกรมนี้ทราบ) ก็สามารถตั้งค่า `RETURN-CODE` เป็นค่าที่ต้องการได้โดยตรงเช่นกัน (เช่น
  `MOVE 4 TO RETURN-CODE` เพื่อสื่อว่า "สำเร็จแต่มีคำเตือน" ตามธรรมเนียม Condition Code ของ Mainframe)

### ข้อควรระวัง

- อย่าลืมว่าปัญหาในขั้นตอนที่ 712 (ฟังก์ชัน C เป็น `void`) กับปัญหาในขั้นตอนนี้ (`RETURNING` ที่ตั้งใจใช้
  งานจริง) **มีสาเหตุร่วมกันคือกลไก `RETURN-CODE` เดียวกัน** แต่วิธีแก้ต่างกัน: กรณีแรกควรแก้ที่ต้นเหตุ
  (ทำให้ฟังก์ชัน C คืนค่าที่ถูกต้องเสมอ) ส่วนกรณีนี้ (`RETURNING` ที่ตั้งใจใช้) ควรแก้ด้วยการ **ควบคุม
  `RETURN-CODE` อย่างชัดเจนก่อน `STOP RUN`** แทนที่จะหลีกเลี่ยงการใช้ `RETURNING` ไปเลย
- ระวังอย่าตั้งชื่อตัวแปรของตัวเองซ้ำกับ `RETURN-CODE` (เป็นคำสงวนของ COBOL) และควรตรวจสอบใน Code
  Review ของทีมว่าทุกโปรแกรม Top-level มีการจัดการ `RETURN-CODE` อย่างตั้งใจก่อน `STOP RUN` เสมอ ไม่ใช่
  ปล่อยให้เป็นไปตามยถากรรมจากผลข้างเคียงของ `CALL` ก่อนหน้า

### แบบฝึกหัดที่ 716.1

**โจทย์**: จงอธิบายว่าทำไมกลไก `RETURN-CODE` ที่ดูเหมือนจะสร้างปัญหา (exit code ปริศนา) ในขั้นตอนที่
712 และ 715 จึงยังคงเป็นการออกแบบที่มีเหตุผลในบริบทของ Mainframe/Batch Processing

**เฉลยแนวทาง**: ในโลก Mainframe/Batch Processing (ทบทวนจาก Part 053 และ Part 066) การส่งต่อ "สถานะ"
ระหว่าง Step ต่าง ๆ ใน Job เดียวกันเป็นเรื่องปกติและจำเป็นมาก (เช่น Step ที่สองควรทำงานต่อก็ต่อเมื่อ
Step แรกสำเร็จ) `RETURN-CODE`/Condition Code คือกลไกมาตรฐานที่ทำสิ่งนี้ได้โดยไม่ต้องออกแบบระบบสื่อสาร
ระหว่างโปรแกรมที่ซับซ้อน การที่ `CALL`/`RETURNING` เชื่อมโยงกับ `RETURN-CODE` โดยอัตโนมัติจึงเป็นความ
ตั้งใจที่สอดคล้องกับปรัชญานี้: ทำให้ค่าที่โปรแกรมย่อยหรือฟังก์ชันภายนอก "รายงานผล" กลับมา สามารถไหลต่อ
ไปเป็น exit code ของกระบวนการทั้งหมดได้โดยอัตโนมัติ เพื่อให้ระบบ Batch ภายนอก (JCL, Shell Script)
ตรวจสอบได้ง่าย ปัญหาที่แท้จริงไม่ได้อยู่ที่การออกแบบกลไกนี้ แต่อยู่ที่ **โปรแกรมเมอร์ต้องตระหนักรู้และ
ควบคุมมันอย่างตั้งใจเสมอ** แทนที่จะปล่อยให้เป็นผลข้างเคียงที่ไม่ได้ตั้งใจ ซึ่งเป็นบทเรียนสำคัญของขั้นตอน
นี้ทั้งหมด

## ขั้นตอนที่ 717: การ Link แยกส่วน — คอมไพล์ C เป็น Object File ล่วงหน้า

### ทำไมต้อง Compile C แยกต่างหาก

ตัวอย่างทั้งหมดที่ผ่านมาใน Part นี้ส่งไฟล์ `.c` เข้า `cobc` โดยตรง (`cobc -x main.cob cfile.c -o
program`) ซึ่งสะดวกสำหรับตัวอย่างเล็ก ๆ แต่ในโปรเจกต์จริงที่มีไฟล์ C จำนวนมากหรือใช้ Library ภายนอก
ที่ซับซ้อน (เช่น ต้องระบุ compiler flag พิเศษเฉพาะของไฟล์ C นั้น) มักนิยม**คอมไพล์ไฟล์ C ให้เป็น Object
File (`.o`) ล่วงหน้าด้วย `gcc -c` ก่อน แล้วค่อยส่ง Object File นั้นให้ `cobc` นำไป link รวมกับโปรแกรม
COBOL อีกที** — เทคนิคเดียวกับที่เรียนไปแล้วใน Part 071 ขั้นตอนที่ 703 (แยกทำทีละสเต็ป)

### ทดสอบ: Compile C แยกก่อน แล้วค่อยส่งเข้า cobc

นำฟังก์ชัน `addtwo` จากขั้นตอนที่ 712 มาคอมไพล์เป็น Object File ล่วงหน้าด้วย `gcc` ตรง ๆ:

```bash
gcc -c cmath.c -o cmath_pre.o
```

จากนั้นส่ง Object File (`.o`) แทนที่จะเป็นไฟล์ `.c` ต้นฉบับเข้า `cobc`:

```bash
cobc -x step712main.cob cmath_pre.o -o step717
./step717
```

**ผลลัพธ์จริง (เหมือนกับขั้นตอนที่ 712 ทุกประการ):**

```
Main: calling C function addtwo(+0000000010, +0000000032)
Main: result from C = +0000000042
```

### อธิบายจุดสำคัญ

- `cobc` ฉลาดพอที่จะรู้จักไฟล์ `.o` (Object File) และส่งต่อให้ `gcc` ใช้ตอน **link** เท่านั้น (ไม่ต้อง
  คอมไพล์ใหม่อีกครั้ง เพราะเป็นภาษาเครื่องอยู่แล้ว) แตกต่างจากไฟล์ `.c` ที่ `cobc` จะสั่ง `gcc` ให้คอมไพล์
  ก่อนแล้วค่อย link ตามที่เห็นในขั้นตอนก่อนหน้า
- เทคนิคนี้มีประโยชน์มากเมื่อไฟล์ C มีความซับซ้อน ต้องการ compiler flag เฉพาะของตัวเอง (เช่น `-O3` เพื่อ
  Optimization ระดับสูงสำหรับฟังก์ชันคำนวณหนัก ๆ) ที่แตกต่างจาก flag มาตรฐานที่ `cobc` ใช้กับไฟล์ COBOL
  — แยก compile ทำให้ควบคุม flag ของแต่ละส่วนได้อย่างอิสระจากกัน
- ในโปรเจกต์ขนาดใหญ่ที่มีไฟล์ C หลายไฟล์ การแยก compile ล่วงหน้าแบบนี้ยังช่วยให้ **Build System อย่าง
  Makefile (Part 071 ขั้นตอนที่ 710) ทำ Incremental Build ได้ดีขึ้น** — ไฟล์ C ที่ไม่ได้แก้ไขไม่ต้อง
  compile ซ้ำทุกครั้งที่ build ทั้งโปรเจกต์ใหม่

### ข้อควรระวัง

- Object File ที่คอมไพล์แยกต่างหากต้อง**คอมไพล์ด้วยสถาปัตยกรรม CPU และ ABI เดียวกันกับที่ `cobc`/`gcc`
  ใช้** (เช่น ทั้งคู่เป็น x86-64 Linux) มิเช่นนั้นจะ link ไม่ผ่านหรือทำงานผิดพลาดตอนรันจริง — ปัญหานี้
  พบบ่อยเมื่อพยายามนำ Object File ที่คอมไพล์บนเครื่อง/ระบบปฏิบัติการหนึ่งไปใช้กับอีกเครื่องหนึ่งที่
  สถาปัตยกรรมต่างกัน
- ต้องคอมไพล์ Object File ใหม่ทุกครั้งที่แก้ไขไฟล์ `.c` ต้นฉบับ (Makefile ที่ดีจะจัดการเรื่องนี้ให้
  อัตโนมัติผ่าน dependency tracking) มิเช่นนั้นจะ link กับโค้ดเวอร์ชันเก่าที่ยังไม่ได้แก้ไขโดยไม่รู้ตัว

### แบบฝึกหัดที่ 717.1

**โจทย์**: จงอธิบายว่าทำไมการส่งไฟล์ `.o` (object file) เข้า `cobc` จึงเร็วกว่าการส่งไฟล์ `.c` ต้นฉบับ
เมื่อไฟล์ C นั้นไม่ได้ถูกแก้ไขเลยตั้งแต่ครั้งก่อน

**เฉลยแนวทาง**: เมื่อส่งไฟล์ `.c` เข้า `cobc` ทุกครั้ง `cobc` จะสั่งให้ `gcc` **คอมไพล์ไฟล์นั้นใหม่ทุก
ครั้งไม่ว่าจะมีการแก้ไขหรือไม่ก็ตาม** (ตามที่ Part 071 ขั้นตอนที่ 701 อธิบายไว้ว่า `cobc -x` ทำทุกขั้น
ตอนรวมกันเสมอ) แต่ถ้าคอมไพล์เป็น Object File (`.o`) ไว้ล่วงหน้าแล้ว และไฟล์ `.c` ต้นฉบับไม่ได้ถูกแก้ไข
เลย **ไม่มีความจำเป็นต้องคอมไพล์ C ใหม่อีกเลย** เพราะ Object File ที่มีอยู่แล้วก็คือผลลัพธ์เดียวกันเป๊ะ
กับที่จะได้จากการคอมไพล์ใหม่ การส่ง `.o` เข้า `cobc` โดยตรงจึงข้ามขั้นตอน "แปลง C เป็นภาษาเครื่อง" ไปได้
เลย เหลือแค่ขั้นตอน link เท่านั้น ซึ่งเร็วกว่ามากโดยเฉพาะเมื่อไฟล์ C มีขนาดใหญ่หรือมีจำนวนมากในโปรเจกต์

## ขั้นตอนที่ 718: เตรียมความพร้อมสำหรับ Java — ตรวจสอบ JDK และภาพรวม 3 แนวทาง

### ตรวจสอบว่ามี JDK ในเครื่องหรือไม่ก่อนเริ่ม

การเชื่อมต่อ COBOL กับ Java ต้องการ **Java Development Kit (JDK)** ซึ่งประกอบด้วย `javac` (ตัวคอมไพล์
Java เป็น bytecode) และ `java` (ตัวรัน bytecode นั้นบน JVM) ก่อนลงมือเขียนโค้ดใด ๆ ควรตรวจสอบก่อนเสมอ:

```bash
java -version
javac -version
```

**ผลลัพธ์จริงในสภาพแวดล้อมที่ใช้เขียน Part นี้:**

```
openjdk version "21.0.10" 2026-01-20
OpenJDK Runtime Environment (build 21.0.10+7-Ubuntu-124.04)
OpenJDK 64-Bit Server VM (build 21.0.10+7-Ubuntu-124.04, mixed mode, sharing)
javac 21.0.10
```

> **หมายเหตุ**: หากเครื่องของคุณไม่มี JDK ติดตั้งไว้ คำสั่งข้างต้นจะแจ้ง `command not found` แทน — ในกรณี
> นั้นต้องติดตั้ง JDK ก่อน (เช่น OpenJDK ผ่านตัวจัดการแพ็กเกจของระบบปฏิบัติการ) จึงจะทำตามขั้นตอนที่ 719
> และ 720 ได้จริง ขั้นตอนที่ 711-717 ที่ผ่านมาทั้งหมด (การเชื่อมต่อกับ C) **ไม่ต้องพึ่งพา JDK เลย** ยังคง
> ใช้งานได้ปกติแม้ไม่มี Java ในเครื่องก็ตาม

### สามแนวทางหลักในการเชื่อมต่อ COBOL กับ Java

| แนวทาง | หลักการ | ความซับซ้อน | ความเร็วในการสื่อสาร |
|---|---|---|---|
| **1. Subprocess + File Exchange** | COBOL เขียนไฟล์ข้อมูล แล้วสั่งรัน Java เป็นกระบวนการแยก (ผ่าน `CALL "SYSTEM"`), Java อ่าน-เขียนไฟล์กลับ | ต่ำที่สุด ไม่ต้องรู้จัก JNI เลย | ช้าที่สุด (เปิด process ใหม่ทุกครั้ง, I/O ผ่านไฟล์) |
| **2. Subprocess + Pipe/stdin-stdout** | คล้ายข้อ 1 แต่ส่งข้อมูลผ่าน standard input/output แทนไฟล์ | ปานกลาง | เร็วกว่าข้อ 1 เล็กน้อย (ไม่ต้องเขียน/อ่านดิสก์) |
| **3. JNI (Java Native Interface)** | Java เรียกฟังก์ชัน C โดยตรงในหน่วยความจำเดียวกัน (ไม่มี process แยก), C นั้นเรียกต่อเข้าไปยังโมดูล COBOL | สูงที่สุด ต้องเข้าใจทั้ง JNI และ C-to-COBOL calling | เร็วที่สุด (ไม่มี process overhead) |

สูงสุด) และ**แนวทางที่ 3** (ขั้นตอนที่ 720 — ซับซ้อนกว่ามากแต่มีประสิทธิภาพสูงและเป็นแนวทางที่ใช้จริงใน

### ทดสอบกลไกพื้นฐานก่อน: CALL "SYSTEM"

ก่อนเขียนโปรแกรมเต็มรูปแบบ มาทดสอบกลไกพื้นฐานที่สุดที่ทำให้ COBOL สั่งรันกระบวนการอื่นของระบบปฏิบัติการ
ได้ก่อน — **`CALL "SYSTEM"`** เป็น System Routine พิเศษที่ GnuCOBOL เตรียมไว้ให้ ทำหน้าที่เหมือนฟังก์ชัน
`system()` ของภาษา C (ส่งคำสั่งไปให้ shell ของระบบปฏิบัติการรัน แล้วรอจนกว่าจะเสร็จ):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP718SYS.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-COMMAND    PIC X(40) VALUE "echo hello-from-the-shell".

       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "Main: about to CALL SYSTEM.".
           CALL "SYSTEM" USING WS-COMMAND.
           DISPLAY "Main: back from SYSTEM.".
           STOP RUN.
```

```bash
cobc -x step718sys.cob -o step718sys
./step718sys
```

**ผลลัพธ์จริง:**

```
Main: about to CALL SYSTEM.
hello-from-the-shell
Main: back from SYSTEM.
```

### อธิบายจุดสำคัญ

- `CALL "SYSTEM"` เป็นชื่อพิเศษที่สงวนไว้ในตัว `libcob` เอง (ตรวจสอบรายชื่อ System Routine ทั้งหมดที่
  GnuCOBOL รองรับได้ด้วย `cobc -list-system`) **ไม่ใช่การเรียกโปรแกรม COBOL หรือฟังก์ชัน C ที่เราเขียน
  เอง** แต่เป็นฟังก์ชันสำเร็จรูปที่ `libcob` เตรียมไว้ให้ใช้งานได้ทันที
- คำสั่งที่ส่งเข้าไปใน `CALL "SYSTEM"` จะถูก**ส่งต่อไปให้ shell ของระบบปฏิบัติการรันตรง ๆ** และ **COBOL
  จะรอ (block) จนกว่ากระบวนการนั้นจะรันเสร็จสมบูรณ์ก่อนจึงทำงานบรรทัดถัดไปต่อ** — พฤติกรรม "รอจนเสร็จ"
  นี้คล้ายกับการ `CALL` โปรแกรมย่อย COBOL ปกติมาก (ควบคุมกลับมาที่ผู้เรียกก็ต่อเมื่อกระบวนการที่ถูกเรียก
  จบแล้วเท่านั้น)
- เพราะ `CALL "SYSTEM"` เรียก shell ตรง ๆ จึงสามารถสั่งรันโปรแกรมอะไรก็ได้ที่ shell รู้จัก **รวมถึงคำสั่ง
  `java`** — นี่คือกุญแจสำคัญที่ขั้นตอนที่ 719 จะนำไปใช้จริง

### ข้อควรระวัง

- `CALL "SYSTEM"` ให้อำนาจควบคุมระบบปฏิบัติการเต็มรูปแบบเท่ากับ Shell Script ธรรมดา ซึ่งหมายความว่า
  **ต้องระวังเรื่องความปลอดภัยอย่างมาก** หากคำสั่งที่ส่งเข้าไปมาจากข้อมูลผู้ใช้โดยตรงโดยไม่ผ่านการ
  ตรวจสอบ (ทบทวนหลักการ "Validate then Trust" จาก Part 069 ขั้นตอนที่ 690) อาจเปิดช่องให้เกิดการโจมตี
  แบบ Command Injection ได้
- คำสั่งที่รันผ่าน `CALL "SYSTEM"` ทำงานอยู่ใน**โฟลเดอร์ทำงานปัจจุบัน (Current Working Directory)
  เดียวกับที่โปรแกรม COBOL กำลังรันอยู่** — สำคัญมากเมื่อคำสั่งนั้นต้องอ้างอิงไฟล์แบบ relative path (เช่น
  การรัน Java class ที่ compile ไว้ในโฟลเดอร์เดียวกัน)
- Exit code ของคำสั่งที่รันผ่าน `CALL "SYSTEM"` **ไม่ได้ถูกตรวจสอบหรือรายงานกลับมาให้ COBOL ทราบโดย
  อัตโนมัติ**ในตัวอย่างพื้นฐานนี้ — ถ้าต้องการทราบว่าคำสั่งสำเร็จหรือล้มเหลว ต้องออกแบบให้โปรแกรมภายนอก
  เขียนผลลัพธ์/สถานะกลับมาในรูปแบบที่ COBOL อ่านต่อได้ (เช่น ไฟล์ผลลัพธ์ ตามที่ขั้นตอนที่ 719 จะสาธิต)

### แบบฝึกหัดที่ 718.1

**โจทย์**: จงอธิบายว่าทำไม `CALL "SYSTEM"` จึงถูกจัดเป็น "System Routine" ที่แยกต่างหากจาก `CALL` ปกติ
ที่เรียนมาตั้งแต่ Part 031 ทั้งที่ไวยากรณ์ดูคล้ายกันมาก

**เฉลยแนวทาง**: `CALL` ปกติ (Part 031) เรียกหาโปรแกรม/ฟังก์ชันที่ **ถูก link เข้ามาในไฟล์ execute
เดียวกัน** (หรือโหลดเป็น dynamic module ตามที่ Part 071 ขั้นตอนที่ 705 อธิบาย) ซึ่งทำงานอยู่ใน**
กระบวนการ (process) เดียวกัน**กับโปรแกรมที่เรียก ในทางตรงข้าม `CALL "SYSTEM"` ไม่ได้เรียกหาโปรแกรมที่
link มาด้วยเลย แต่เป็นฟังก์ชันพิเศษที่ `libcob` implement ไว้ให้ทำหน้าที่**สร้างกระบวนการใหม่ทั้งหมด
(new process)** ผ่าน shell ของระบบปฏิบัติการ ซึ่งเป็นกลไกที่แตกต่างไปจากการ `CALL` ธรรมดาโดยสิ้นเชิงใน
ระดับระบบปฏิบัติการ (ต้องใช้ System Call อย่าง `fork`/`exec` ของ Linux เบื้องหลัง ไม่ใช่แค่การกระโดดไปยัง
ที่อยู่ของฟังก์ชันในหน่วยความจำเดียวกัน) GnuCOBOL จึงจัดมันไว้เป็นรายชื่อพิเศษ (System Routine) ที่แยก
ต่างหากจากกลไก `CALL` ปกติ แม้ไวยากรณ์ที่ใช้เรียกจะคล้ายกันก็ตาม

## ขั้นตอนที่ 719: ตัวอย่างจริง — COBOL เรียก Java เป็น Subprocess แลกเปลี่ยนข้อมูลผ่านไฟล์

### ภาพรวมของระบบที่จะสร้าง

เราจะสร้างระบบเล็ก ๆ ที่ COBOL ทำหน้าที่ **"ส่งคำขอ"** คำนวณดอกเบี้ยแบบง่าย ไปให้โปรแกรม Java ที่ทำหน้าที่
**"ประมวลผล"** แล้วส่งผลลัพธ์กลับมาให้ COBOL แสดงผล — สถาปัตยกรรมนี้คือรูปแบบพื้นฐานที่สุดของการ
"Integration" ระหว่างสองระบบที่เขียนด้วยคนละภาษาโดยสิ้นเชิง ไม่ต้องรู้จัก JNI หรือกลไกภายในของ JVM เลย
แม้แต่น้อย

```
   step719main.cob              INPUT.TXT             InterestCalc.java
   (COBOL, writes request) --> (500.00 / 2.50) -->    (Java, reads + computes)
                                                              |
   step719main.cob              OUTPUT.TXT                   |
   (COBOL, reads result)  <--   (12.50)          <-----------+
```

### โปรแกรม Java: InterestCalc.java

```java
import java.io.*;
import java.math.BigDecimal;
import java.math.RoundingMode;

/*
 * InterestCalc.java - a tiny standalone Java program used as a
 * subprocess "service" called from COBOL. It reads two lines from
 * INPUT.TXT (principal and annual rate percent), computes simple
 * interest for one year, and writes the result to OUTPUT.TXT. This
 * is the file-exchange integration pattern: COBOL and Java never
 * link together or share memory at all - they only agree on a file
 * format, the same way two completely separate programs on a batch
 * schedule would hand off data to each other.
 */
public class InterestCalc {
    public static void main(String[] args) throws Exception {
        BufferedReader in = new BufferedReader(new FileReader("INPUT.TXT"));
        BigDecimal principal = new BigDecimal(in.readLine().trim());
        BigDecimal ratePercent = new BigDecimal(in.readLine().trim());
        in.close();

        BigDecimal rate = ratePercent.divide(new BigDecimal("100"));
        BigDecimal interest = principal.multiply(rate)
                .setScale(2, RoundingMode.HALF_UP);

        PrintWriter out = new PrintWriter(new FileWriter("OUTPUT.TXT"));
        out.println(interest.toPlainString());
        out.close();

        System.out.println("InterestCalc (Java): computed interest = "
                + interest.toPlainString());
    }
}
```

**คอมไพล์ Java ให้เสร็จก่อนล่วงหน้า** (COBOL จะแค่รัน `java` ไม่ได้รัน `javac`):

```bash
javac InterestCalc.java
```

### โปรแกรม COBOL: step719main.cob

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP719MAIN.
       AUTHOR. COBOL-COURSE.

      ******************************************************************
      * STEP719MAIN demonstrates COBOL "calling" a separate Java
      * program - not through CALL/LINKAGE SECTION like the C examples
      * in this Part, but as an independent OS PROCESS launched with
      * CALL "SYSTEM". COBOL and Java exchange data purely through two
      * plain text files, the same pattern used to hand batch work
      * between unrelated systems in real integration projects.
      ******************************************************************

       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT INPUT-FILE ASSIGN TO "INPUT.TXT"
               ORGANIZATION IS LINE SEQUENTIAL.
           SELECT OUTPUT-FILE ASSIGN TO "OUTPUT.TXT"
               ORGANIZATION IS LINE SEQUENTIAL.

       DATA DIVISION.
       FILE SECTION.
       FD  INPUT-FILE.
       01  INPUT-LINE            PIC X(20).
       FD  OUTPUT-FILE.
       01  OUTPUT-LINE           PIC X(20).

       WORKING-STORAGE SECTION.
       01  WS-PRINCIPAL          PIC 9(7)V99 VALUE 500.00.
       01  WS-RATE               PIC 9(3)V99 VALUE 2.50.
      *> Numeric-edited fields give us an ACTUAL decimal point
      *> character in the text, since Java's BigDecimal parser (and
      *> most other languages) expects "500.00", not the raw packed
      *> digit string "000050000" that a plain numeric field holds
      *> internally (V has no storage position of its own).
       01  WS-PRINCIPAL-EDITED    PIC Z(6)9.99.
       01  WS-RATE-EDITED         PIC Z(2)9.99.
       01  WS-INTEREST-TEXT      PIC X(20)   VALUE SPACES.
       01  WS-COMMAND            PIC X(60)   VALUE
               "java InterestCalc".

       PROCEDURE DIVISION.
       MAIN-PARA.
      *> Step 1: write the request as plain text - this is the only
      *> "interface contract" between the two languages.
           OPEN OUTPUT INPUT-FILE.
           MOVE WS-PRINCIPAL TO WS-PRINCIPAL-EDITED.
           MOVE SPACES TO INPUT-LINE.
           STRING FUNCTION TRIM(WS-PRINCIPAL-EDITED) DELIMITED BY SIZE
               INTO INPUT-LINE.
           WRITE INPUT-LINE.
           MOVE WS-RATE TO WS-RATE-EDITED.
           MOVE SPACES TO INPUT-LINE.
           STRING FUNCTION TRIM(WS-RATE-EDITED) DELIMITED BY SIZE
               INTO INPUT-LINE.
           WRITE INPUT-LINE.
           CLOSE INPUT-FILE.

           DISPLAY "COBOL: wrote INPUT.TXT, launching Java as a "
               "subprocess...".

      *> Step 2: CALL "SYSTEM" hands the command line to the
      *> operating system's shell and BLOCKS until that process
      *> finishes - much like CALL to a COBOL subprogram, control
      *> returns here only once the whole Java run has completed.
           CALL "SYSTEM" USING WS-COMMAND.

           DISPLAY "COBOL: Java subprocess finished, reading "
               "OUTPUT.TXT...".

      *> Step 3: read the answer back the same simple way it was sent.
           OPEN INPUT OUTPUT-FILE.
           READ OUTPUT-FILE INTO WS-INTEREST-TEXT
               AT END
                   MOVE "ERROR - NO OUTPUT" TO WS-INTEREST-TEXT
           END-READ.
           CLOSE OUTPUT-FILE.

           DISPLAY "COBOL: interest computed by Java = "
               FUNCTION TRIM(WS-INTEREST-TEXT).
           STOP RUN.
```

```bash
cobc -x step719main.cob -o step719
./step719
```

**ผลลัพธ์จริง (ยืนยันด้วยการรันจริงทั้งระบบ):**

```
COBOL: wrote INPUT.TXT, launching Java as a subprocess...
InterestCalc (Java): computed interest = 12.50
COBOL: Java subprocess finished, reading OUTPUT.TXT...
COBOL: interest computed by Java = 12.50
```


> Proxy หรือ Sandbox บางประเภท) อาจเห็นข้อความ diagnostic เพิ่มเติมจาก `java` ปรากฏขึ้นก่อนผลลัพธ์จริง

> หนึ่งของผลลัพธ์โปรแกรม และจะไม่ปรากฏบนเครื่องทั่วไปที่ไม่มีการตั้งค่าลักษณะนี้

### อธิบายจุดสำคัญ

- ผลลัพธ์ `12.50` มาจากการคำนวณดอกเบี้ยแบบง่าย: `500.00 x (2.50/100) = 12.50` — Java ทำการคำนวณด้วย
  `BigDecimal` ซึ่งเป็นชนิดข้อมูลทศนิยมแม่นยำสูงของ Java (คล้ายกับที่ PICTURE Clause ของ COBOL ทำได้
  โดยธรรมชาติตามที่ Part 001 ขั้นตอนที่ 5 อธิบายไว้ - Java ต้องใช้ Library เพิ่มเติมเพื่อให้ได้ความแม่นยำ
  ระดับเดียวกัน)
- **`PIC Z(6)9.99` (Numeric-edited)** คือกุญแจสำคัญที่ทำให้ข้อความที่ส่งออกไปมี **จุดทศนิยมจริง** (`.`)
  ปรากฏอยู่ในข้อความ ต่างจาก `PIC 9(7)V99` ที่ `V` เป็นเพียงตำแหน่งสมมติที่ไม่มีการจัดเก็บจริง (ทบทวนจาก
  Part 006) — หากไม่แปลงผ่าน Numeric-edited ก่อน ข้อความที่ Java ได้รับจะเป็น `00005000000` ที่ไม่มีจุด
  ทศนิยมเลย ทำให้ `BigDecimal` ของ Java แปลความหมายผิดพลาดทันที
- **ไฟล์ `INPUT.TXT`/`OUTPUT.TXT` คือ "สัญญา" (Contract) เดียวที่เชื่อมสองภาษานี้เข้าด้วยกัน** — COBOL
  และ Java ไม่ได้แชร์หน่วยความจำ ไม่ได้เรียกฟังก์ชันของกันและกันโดยตรงเลยแม้แต่น้อย รู้จักกันแค่ผ่าน
  รูปแบบไฟล์ข้อความที่ตกลงกันไว้ล่วงหน้าเท่านั้น — นี่คือทั้งจุดแข็ง (เรียบง่าย debug ง่าย ภาษาอะไรก็อ่าน
  ไฟล์ข้อความได้) และจุดอ่อน (ช้า เพราะต้องเขียน-อ่านดิสก์ และต้องรอกระบวนการ Java เปิด-ปิดใหม่ทุกครั้ง)
  ของแนวทางนี้

### ข้อควรระวัง

- ตัวแปร `WS-COMMAND` เก็บคำสั่ง `"java InterestCalc"` แบบตรงไปตรงมา — ในระบบจริงควรระบุ path แบบเต็ม
  ของ `java` และไฟล์ `.class` เพื่อไม่ให้ผลลัพธ์ขึ้นอยู่กับโฟลเดอร์ทำงานปัจจุบันหรือ `PATH` ของระบบที่
  อาจเปลี่ยนแปลงได้
- แนวทางนี้ **ไม่เหมาะกับงานที่ต้องการความเร็วสูงหรือเรียกบ่อยมาก** (เช่น เรียกนับพันครั้งต่อวินาที)
  เพราะการเปิดกระบวนการ Java ใหม่ทุกครั้ง (รวมถึงการเริ่มต้น JVM ซึ่งมีค่าใช้จ่ายด้าน Performance สูง)
  เหมาะกับงาน Batch ที่เรียกเป็นครั้งคราวมากกว่า — ขั้นตอนที่ 720 จะแนะนำแนวทางที่เร็วกว่านี้มาก
- ต้อง `javac InterestCalc.java` ให้เรียบร้อย**ก่อน**รันโปรแกรม COBOL เสมอ (COBOL ในตัวอย่างนี้แค่รัน
  `java` ไม่ได้สั่ง compile ให้) หากลืมขั้นตอนนี้ `CALL "SYSTEM"` จะรันคำสั่งที่หาไฟล์ `.class` ไม่เจอ
  และ `OUTPUT.TXT` จะไม่ถูกสร้างขึ้นเลย ทำให้ COBOL อ่านไฟล์ผลลัพธ์ไม่เจอ

ข้อความ จึงทำให้โปรแกรม Java ตีความข้อมูลผิดพลาด ทั้งที่ตัวเลขที่เก็บใน COBOL นั้นถูกต้องสมบูรณ์

**เฉลยแนวทาง**: `PIC 9(7)V99` เก็บค่า 500.00 เป็นสตริงตัวเลข 9 หลักต่อกันโดยไม่มีจุดทศนิยมจริงในหน่วย
ความจำ (`V` เป็นเพียงตำแหน่งที่ compiler รู้ไว้เองว่าทศนิยมอยู่ตรงไหนเวลาคำนวณ แต่ไม่มีไบต์เก็บสัญลักษณ์
`.` จริง) ดังนั้นเมื่อ `MOVE`/`STRING` ค่านี้ออกไปเป็นข้อความตรง ๆ จะได้สตริง `"000050000"` ไม่ใช่
`"500.00"` โปรแกรม Java ที่ใช้ `new BigDecimal(...)` แปลงสตริงเป็นตัวเลขจะตีความ `"000050000"` เป็น
เลขจำนวนเต็ม 50000 (ไม่มีทศนิยมเลย) ซึ่งผิดไปจากค่าจริงที่ตั้งใจสื่อความหมาย (500.00) อย่างสิ้นเชิง
การแปลงผ่าน Numeric-edited field (`PIC Z(6)9.99`) ก่อนส่งออกไปเป็นข้อความ จึงเป็นขั้นตอนที่จำเป็นเสมอ
เมื่อต้องส่งตัวเลขทศนิยมของ COBOL ออกไปให้ระบบภายนอกที่คาดหวังรูปแบบข้อความมาตรฐานที่มีจุดทศนิยมจริง
ปรากฏอยู่

## ขั้นตอนที่ 720: แนวทางจริงในโปรดักชัน — JNI Glue Library เรียกเข้า COBOL โดยตรง

### เมื่อ File Exchange ไม่เร็วพอ: โลกของ JNI

ขั้นตอนที่ 719 พิสูจน์ว่า COBOL กับ Java ทำงานร่วมกันได้จริง แต่ด้วยต้นทุนของการเปิดกระบวนการ Java ใหม่
ทุกครั้ง ในระบบ Enterprise จริงที่ต้องการเรียกใช้ตรรกะ COBOL จาก Java บ่อยครั้งและรวดเร็ว (เช่น API
Endpoint ที่รับ Request หลายพันครั้งต่อวินาที) แนวทางที่ใช้จริงในอุตสาหกรรมคือ **JNI (Java Native
Interface)** — กลไกมาตรฐานของ Java ที่อนุญาตให้โค้ด Java เรียก "Native Method" ที่implement ด้วยภาษา C
ได้โดยตรง **ในหน่วยความจำเดียวกัน ไม่มีการเปิดกระบวนการใหม่เลย**

แนวทางที่ใช้ในโปรดักชันจริงคือ: **เขียน C "Glue Library"** ที่ implement ฟังก์ชัน native ตามสัญญาณของ
JNI แล้วภายในฟังก์ชันนั้น**เรียกต่อเข้าไปยังโมดูล COBOL** โดยใช้กลไกเดียวกันเป๊ะกับที่เราพิสูจน์ไปแล้วใน
ขั้นตอนที่ 711-717 (COBOL คอมไพล์แล้วกลายเป็นฟังก์ชัน C ธรรมดาที่เรียกได้ตรง ๆ) — พูดง่าย ๆ คือ **Java
เรียก C และ C เรียก COBOL** โดยที่ C Glue Library เป็นสะพานเชื่อมตรงกลาง

```
   Java (CobolBridge.java)
        |  System.loadLibrary + native method call
        v
   C Glue Library (CobolBridgeImpl.c, implements JNI signature)
        |  calls the COBOL module's C function directly (steps 711-717 technique)
        v
   COBOL module (COBMOD.cob, compiled by cobc, no -x, just a plain C-callable function)
```

> **ยืนยันความซื่อสัตย์**: ตัวอย่างในขั้นตอนนี้เป็นเทคนิคระดับสูงที่ปกติถือเป็นเนื้อหาขั้นสูงมากในหลาย
> หลักสูตร แต่เนื่องจากสภาพแวดล้อมที่ใช้เขียนเอกสารนี้มี JDK พร้อม `jni.h` header ติดตั้งครบถ้วน จึง
> **ทดสอบคอมไพล์และรันจริงจนสำเร็จทุกขั้นตอน** ไม่ใช่เนื้อหาเชิงทฤษฎีที่ไม่ได้ทดสอบ

### ขั้นที่ 1: โมดูล COBOL ที่จะถูกเรียกจาก C

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. COBMOD.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       LINKAGE SECTION.
       01  LK-A          PIC S9(9) COMP-5.
       01  LK-B          PIC S9(9) COMP-5.
       01  LK-RESULT     PIC S9(9) COMP-5.

       PROCEDURE DIVISION USING LK-A LK-B LK-RESULT.
       MAIN-PARA.
           COMPUTE LK-RESULT = LK-A + LK-B.
           GOBACK.
```

สังเกตว่าโปรแกรมนี้**ไม่มีอะไรพิเศษเลยเมื่อเทียบกับ Subprogram ปกติที่เรียนมาตั้งแต่ Part 031** — ไม่รู้
ตัวด้วยซ้ำว่าสุดท้ายแล้วจะถูกเรียกจาก Java ผ่าน JNI คอมไพล์เป็น Object File ธรรมดา (ไม่ใส่ `-x` เพราะ
ไม่ใช่โปรแกรมที่รันเดี่ยว ทบทวนจาก Part 071 ขั้นตอนที่ 702):

```bash
cobc -c cobmod.cob -o cobmod.o
```

### ขั้นที่ 2: พิสูจน์ก่อนว่า C ธรรมดาเรียกโมดูลนี้ได้จริง (ไม่มี Java เลย)

ก่อนจะเพิ่มความซับซ้อนของ JNI เข้ามา ให้พิสูจน์ก่อนว่าโค้ด C ธรรมดา ๆ เรียกฟังก์ชันที่มาจากโมดูล COBOL
ได้โดยตรงจริง (สลับทิศทางจากขั้นตอนที่ 711-717 ที่ COBOL เป็นฝ่ายเรียก C):

```c
#include <stdio.h>
#include <libcob.h>
extern int COBMOD(void *, void *, void *);
int main(int argc, char **argv) {
    cob_init(argc, argv);
    int a = 7, b = 35, result = -1;
    int rc = COBMOD(&a, &b, &result);
    printf("rc=%d result=%d\n", rc, result);
    return 0;
}
```

```bash
gcc rawmaintest.c cobmod.o -o rawmaintest -lcob
./rawmaintest
```

**ผลลัพธ์จริง:**

```
rc=42 result=42
```

จุดสำคัญที่สุดของขั้นตอนนี้: **`cob_init(argc, argv)` ต้องถูกเรียกก่อนเสมอ** ก่อนเรียกฟังก์ชันของ
โปรแกรม COBOL ใด ๆ (นี่คือสิ่งที่ `main()` ที่ GnuCOBOL สร้างให้อัตโนมัติตอนใช้ `-x` ทำอยู่แล้วโดยที่เรา
ไม่เคยต้องคิดถึงมันเลยตลอดหลักสูตรนี้ - ทบทวนจาก Part 071 ขั้นตอนที่ 702) หากลืมเรียก `cob_init` ก่อน
จะได้ error `libcob: error: cob_init() has not been called` ทันที

### ขั้นที่ 3: เขียน Java Class ที่ประกาศ Native Method

```java
public class CobolBridge {
    static {
        System.loadLibrary("cobolbridge");
    }

    /* This native method is implemented in C (CobolBridgeImpl.c) -
       the JNI "glue" that a real production system would ship. The C
       side does not do the addition itself; it forwards straight
       into the COBOL module COBMOD, compiled by GnuCOBOL, using the
       exact plain-C-function-call technique proven in step 711-716
       of this Part. */
    public static native int addViaCobol(int a, int b);

    public static void main(String[] args) {
        int result = addViaCobol(7, 35);
        System.out.println("Java: COBOL (via JNI) computed 7 + 35 = "
                + result);
    }
}
```

คอมไพล์และสั่งให้ `javac` สร้าง JNI Header ไฟล์ให้อัตโนมัติ (แฟล็ก `-h`):

```bash
javac CobolBridge.java
javac -h . CobolBridge.java
```

**Header ที่ javac สร้างให้อัตโนมัติ (`CobolBridge.h`):**

```c
/* DO NOT EDIT THIS FILE - it is machine generated */
#include <jni.h>
JNIEXPORT jint JNICALL Java_CobolBridge_addViaCobol
  (JNIEnv *, jclass, jint, jint);
```

### ขั้นที่ 4: เขียน C Glue Library ที่เรียกเข้า COBOL

```c
#include "CobolBridge.h"
#include <libcob.h>

/* This is the "glue" a production system would write: it implements
   the exact native method signature JNI generated from CobolBridge.h,
   and internally does nothing COBOL-specific except call the COBOL
   module COBMOD - compiled separately by GnuCOBOL - exactly the way
   any plain C caller would (step 720's rawmaintest.c proves this same
   call mechanism directly, without Java involved at all). cob_init()
   is only safe to call once per process, guarded here with a flag. */

extern int COBMOD(void *, void *, void *);

static int cobol_runtime_ready = 0;

JNIEXPORT jint JNICALL Java_CobolBridge_addViaCobol
  (JNIEnv *env, jclass cls, jint a, jint b)
{
    int ai = (int) a;
    int bi = (int) b;
    int result = 0;

    if (!cobol_runtime_ready) {
        cob_init(0, NULL);
        cobol_runtime_ready = 1;
    }

    COBMOD(&ai, &bi, &result);
    return (jint) result;
}
```

**คอมไพล์เป็น Shared Library ที่ Java จะโหลดผ่าน `System.loadLibrary`:**

```bash
gcc -shared -fPIC \
    -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" \
    CobolBridgeImpl.c cobmod.o \
    -o libcobolbridge.so -lcob
```

### ขั้นที่ 5: รันจริง — Java เรียก COBOL ผ่าน JNI

```bash
java -Djava.library.path=. CobolBridge
```

**ผลลัพธ์จริง:**

```
Java: COBOL (via JNI) computed 7 + 35 = 42
```

**คำตอบ 42 มาจากโมดูล COBOL จริง ๆ** (`COMPUTE LK-RESULT = LK-A + LK-B` ที่คำนวณ 7 + 35) ไม่ใช่การ
คำนวณในฝั่ง Java เลยแม้แต่น้อย — Java เรียก `addViaCobol(7, 35)` ซึ่งเป็น native method, JVM หา
`libcobolbridge.so` ตามชื่อที่ `System.loadLibrary("cobolbridge")` ระบุ (เติม `lib`/`.so` ให้อัตโนมัติ
ตามธรรมเนียมของ Linux), เรียกฟังก์ชัน C ที่ implement ตาม signature ของ JNI ซึ่งภายในเรียกต่อไปยังฟังก์ชัน
`COBMOD` ที่มาจากการคอมไพล์ COBOL โดยตรง แล้วส่งผลลัพธ์ไหลกลับทางเดิมทั้งหมด

### อธิบายจุดสำคัญ

- **นี่คือทิศทางตรงข้ามกับขั้นตอนที่ 711-717 ทั้งหมด**: ที่ผ่านมา COBOL เป็นฝ่าย `CALL` ไปหา C ส่วนใน
  ขั้นตอนนี้ **Java เป็นฝ่ายเรียก C (ผ่าน JNI) แล้ว C เป็นฝ่ายเรียกต่อไปยัง COBOL** — แต่กลไกที่ทำให้ C
  เรียก COBOL ได้นั้น**เป็นเทคนิคเดียวกันเป๊ะ**กับที่พิสูจน์ไว้ในขั้นที่ 2 ของขั้นตอนนี้ (ประกาศ `extern`
  แล้วเรียกฟังก์ชันตรง ๆ พร้อม `cob_init` ก่อนเสมอ)
- **`cob_init` ปลอดภัยที่จะเรียกเพียงครั้งเดียวต่อกระบวนการ** โค้ด Glue ในตัวอย่างนี้ใช้ตัวแปร
  `cobol_runtime_ready` เป็น flag ป้องกันการเรียกซ้ำ — สำคัญมากในระบบจริงที่ native method นี้อาจถูก
  เรียกจาก Java หลายครั้ง (การเรียก `cob_init` ซ้ำโดยไม่ระวังอาจทำให้เกิดปัญหาได้)
- JNI Header (`CobolBridge.h`) ถูก `javac -h` **สร้างขึ้นอัตโนมัติ** ตรงตาม signature ที่ Java ประกาศไว้
  ทุกประการ (`Java_CobolBridge_addViaCobol` ตั้งชื่อตามกฎ `Java_<ClassName>_<methodName>` ของ JNI) —
  ผู้เขียน C Glue เพียงแค่ implement ฟังก์ชันตาม signature ที่ได้มา ไม่ต้องเขียนเองจากศูนย์

### สิ่งที่ระบบ Production จริงจะเพิ่มเติมจากตัวอย่างนี้

ตัวอย่างข้างต้นแสดงกลไกหลักที่แท้จริงและทดสอบได้จริง แต่ระบบ Production ระดับองค์กรจะมีรายละเอียดเพิ่ม
เติมมากกว่านี้ (เนื้อหาเชิงแนวคิด ไม่ได้ทดสอบในเอกสารนี้):

- **การจัดการ Thread Safety**: `cob_init`/การเรียกโมดูล COBOL จากหลาย Java Thread พร้อมกันต้องมีกลไก
  ป้องกัน Race Condition ที่ละเอียดกว่า flag ตัวเดียวแบบในตัวอย่างนี้มาก
- **การแปลง Exception**: หากโมดูล COBOL เกิดปัญหา (เช่น File Status ผิดพลาดตามที่ Part 030 สอน) C Glue
  ควรแปลงเป็น Java Exception ที่เหมาะสมแทนที่จะปล่อยให้โปรแกรมล่มเงียบ ๆ
- **การจัดการชนิดข้อมูลที่ซับซ้อนกว่า int**: การส่ง Group Item หรือข้อความ PIC X ระหว่าง Java-C-COBOL
  ต้องใช้ JNI API เพิ่มเติม (เช่น `GetStringUTFChars`, `NewByteArray`) ร่วมกับเทคนิคจากขั้นตอนที่ 713-714
  ของ Part นี้
- **Build Automation**: โปรเจกต์จริงจะใช้ Maven/Gradle (ฝั่ง Java) ร่วมกับ Makefile (ฝั่ง COBOL/C ตามที่
  Part 071 ขั้นตอนที่ 710 สอน) แทนการพิมพ์คำสั่ง `gcc`/`javac` ด้วยมือทีละคำสั่งแบบตัวอย่างนี้

### ข้อควรระวัง

- **สภาพแวดล้อมส่วนใหญ่ไม่มี `jni.h` และ JDK พร้อมใช้งานแบบในเอกสารนี้** ก่อนทำตามตัวอย่างนี้ต้องติดตั้ง
  JDK ที่มี Header สำหรับพัฒนา (มักมาพร้อมกับ JDK เต็มรูปแบบ ไม่ใช่แค่ JRE) และต้องตั้งค่า `$JAVA_HOME`
  ให้ถูกต้องก่อนคอมไพล์ C Glue Library เสมอ
- ชื่อฟังก์ชัน C ต้องตรงกับที่ `javac -h` สร้างให้**เป๊ะทุกตัวอักษร** (รวมถึงชื่อ Package ถ้ามี ซึ่งจะถูก
  แทรกเข้าไปในชื่อฟังก์ชันด้วย เช่น `Java_com_example_CobolBridge_addViaCobol`) — สะกดผิดแม้นิดเดียวจะ
  ทำให้ JVM หาฟังก์ชันไม่เจอตอนรันจริง (`UnsatisfiedLinkError`) แม้จะคอมไพล์ C Glue ผ่านได้ปกติก็ตาม
  เพราะ JVM ค้นหาชื่อฟังก์ชันตอนรันจริงเท่านั้น ไม่ใช่ตอนคอมไพล์
- `System.loadLibrary("cobolbridge")` คาดหวังไฟล์ชื่อ **`libcobolbridge.so`** (เติม `lib` นำหน้าและ
  `.so` ต่อท้ายให้อัตโนมัติตามธรรมเนียมของ Linux) และไฟล์นั้นต้องอยู่ใน path ที่ระบุผ่าน
  `-Djava.library.path=...` ตอนรัน `java` เสมอ มิเช่นนั้นจะได้ error หาไลบรารีไม่เจอทันที

### แบบฝึกหัดที่ 720.1

**โจทย์**: จงอธิบายว่าทำไมเทคนิคที่ใช้ในขั้นตอนที่ 720 นี้ (Java เรียก C Glue แล้ว C Glue เรียก COBOL)
จึงเร็วกว่าเทคนิค Subprocess + File Exchange จากขั้นตอนที่ 719 อย่างมีนัยสำคัญ

**เฉลยแนวทาง**: ในขั้นตอนที่ 719 ทุกครั้งที่ COBOL ต้องการผลลัพธ์จาก Java ต้อง **เปิดกระบวนการ (process)
ใหม่ทั้งหมด** ซึ่งรวมถึงการเริ่มต้น JVM ใหม่ทุกครั้ง (มีค่าใช้จ่ายด้าน Performance สูงมาก เพราะ JVM ต้อง
โหลดคลาสมาตรฐานและเตรียมสภาพแวดล้อมใหม่หมดทุกครั้ง) บวกกับการเขียน-อ่านไฟล์บนดิสก์สองรอบ (เขียน
INPUT.TXT, อ่าน OUTPUT.TXT) ซึ่งช้ากว่าการเข้าถึงหน่วยความจำมาก ในทางตรงข้าม เทคนิค JNI ในขั้นตอนที่ 720
ทำงานอยู่ **ภายในกระบวนการ (process) เดียวกันตลอดเวลา**: JVM ที่รันอยู่แล้วเพียงแค่เรียกฟังก์ชันในหน่วย
ความจำเดียวกัน (ผ่าน Shared Library ที่โหลดไว้ครั้งเดียวตอนเริ่มโปรแกรมด้วย `System.loadLibrary`) การส่ง
ค่า `int` ระหว่าง Java-C-COBOL ก็ทำผ่าน Register/Stack ของ CPU โดยตรง (ตามหลักการ Calling Convention ที่
เรียนมาตั้งแต่ขั้นตอนที่ 711) ไม่ต้องผ่านดิสก์หรือเปิดกระบวนการใหม่เลยแม้แต่ครั้งเดียว ทำให้เร็วกว่ากันได้
หลายระดับ (มักเร็วกว่าหลายพันเท่าสำหรับการเรียกที่ถี่มาก) นี่คือเหตุผลที่ระบบ Production ที่ต้องการความ
เร็วสูง (เช่น API ที่รับ Request จำนวนมาก) เลือกใช้แนวทาง JNI แม้จะซับซ้อนกว่าในการพัฒนาและดูแลรักษามาก
กว่าแนวทาง Subprocess + File Exchange ก็ตาม

## สรุปท้ายบท

Part 072 พาเราก้าวข้ามขอบเขตของภาษา COBOL เพียงลำพังเป็นครั้งแรกในหลักสูตรนี้ โดยพิสูจน์ทุกเทคนิคด้วย
การคอมไพล์และรันจริงทั้งหมด สิ่งที่เราได้เรียนรู้:

- เหตุผลเชิงธุรกิจของการเชื่อมต่อ COBOL กับภาษาอื่น และหลักการ **Calling Convention/C ABI** ที่ทำให้
  COBOL (ซึ่งแปลงเป็น C อยู่แล้วตาม Part 071) เรียกฟังก์ชัน C ได้อย่างเป็นธรรมชาติ (ขั้นตอนที่ 711)
- การ `CALL` ฟังก์ชัน C พร้อมพารามิเตอร์ `BY REFERENCE` และ**กับดักสำคัญที่สุดของ Part นี้**: ฟังก์ชัน C
  ต้อง return `int` เสมอ ไม่เช่นนั้น exit code ของทั้งโปรแกรมจะผิดเพี้ยนอย่างเงียบ ๆ (ขั้นตอนที่ 712,
  พิสูจน์ด้วยบั๊กจริง exit=192)
- ขนาดหน่วยความจำที่แท้จริงของ `COMP-5` (`short`/`int`/`long long`) ต้องตรงกับชนิดข้อมูล C เป๊ะ พิสูจน์
  ด้วยบั๊กข้อมูลเสียหายจริงเมื่อขนาดไม่ตรงกัน (ขั้นตอนที่ 713)
- การส่งข้อความ `PIC X` ให้ C โดยไม่มี null terminator ต้องส่งความยาวไปด้วยเสมอ (ขั้นตอนที่ 714)
- `BY VALUE` และ `RETURNING` เมื่อเรียก C — ส่งสำเนาแทนที่อยู่ และรับค่ากลับแบบฟังก์ชัน C มาตรฐาน
  (ขั้นตอนที่ 715)
- กลไก **`RETURN-CODE`** Special Register ที่อยู่เบื้องหลังปัญหา exit code ปริศนาทั้งหมด และวิธีควบคุม
  ด้วย `MOVE 0 TO RETURN-CODE` ก่อน `STOP RUN` (ขั้นตอนที่ 716)
- การคอมไพล์ไฟล์ C แยกเป็น Object File ล่วงหน้าแล้วค่อย link เข้ากับ COBOL (ขั้นตอนที่ 717)
- การตรวจสอบ JDK และภาพรวม 3 แนวทางเชื่อมต่อ Java พร้อมทดสอบ `CALL "SYSTEM"` พื้นฐาน (ขั้นตอนที่ 718)
- ตัวอย่างเต็มรูปแบบที่ทดสอบจริง: **COBOL เรียก Java เป็น Subprocess** แลกเปลี่ยนข้อมูลผ่านไฟล์ คำนวณ
  ดอกเบี้ยจริงและได้ผลลัพธ์ถูกต้อง (ขั้นตอนที่ 719)
- แนวทางที่ใช้จริงในโปรดักชัน: **JNI Glue Library** ที่ทดสอบจนสำเร็จจริงในสภาพแวดล้อมนี้ — Java เรียก C
  ผ่าน JNI แล้ว C เรียกต่อเข้าไปยังโมดูล COBOL โดยตรง ได้ผลลัพธ์ที่คำนวณจริงจาก COBOL กลับมาที่ Java
  (ขั้นตอนที่ 720)

เทคนิคการเชื่อมต่อ COBOL กับ C ที่เรียนอย่างละเอียดใน Part นี้ (โดยเฉพาะกลไก Calling Convention และ
การจัดการหน่วยความจำที่ต้องระมัดระวัง) จะเป็นพื้นฐานสำคัญมากสำหรับ **Part 073** ที่เราจะนำ COBOL มา
ห่อหุ้มเป็น **REST API Wrapper Service** อย่างเต็มรูปแบบ — ทำให้ระบบ COBOL เดิมที่มีอยู่สามารถให้บริการ
กับโลกภายนอกผ่านมาตรฐาน HTTP/JSON ที่ระบบสมัยใหม่ทุกตัวเข้าใจได้ทันที ซึ่งเป็นก้าวสำคัญที่สุดก้าวหนึ่งของ
การทำ Legacy Modernization ในโลกความเป็นจริง
