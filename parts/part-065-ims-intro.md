# Part 065: IMS DB/DC เบื้องต้น (ขั้นตอนที่ 641–650)

## คำนำของ Part นี้

ตลอด Part 057–064 เราเรียนรู้โลกของ **DB2** (ฐานข้อมูลเชิงสัมพันธ์) และ **CICS** (Transaction
Processing Monitor) ซึ่งเป็นคู่เทคโนโลยีที่นิยมที่สุดในการสร้างระบบออนไลน์บน Mainframe ยุคปัจจุบัน
แต่ก่อนที่ DB2 และแม้กระทั่งแนวคิดฐานข้อมูลเชิงสัมพันธ์จะถือกำเนิดขึ้นด้วยซ้ำ IBM มีเทคโนโลยีอีกชุดหนึ่ง
ที่เก่าแก่กว่ามาก และ**ยังคงทำงานอยู่จริง**ในสถาบันการเงินและองค์กรรัฐบาลขนาดใหญ่หลายแห่งทั่วโลกจนถึง
ปี 2026: **IMS (Information Management System)**

IMS ถือกำเนิดขึ้นในปี 1966 จากโครงการ Apollo ของ NASA (ระบบติดตามชิ้นส่วนอะไหล่จรวดขนาดมหาศาล) และ
กลายเป็นระบบจัดการฐานข้อมูลเชิงพาณิชย์ตัวแรก ๆ ของโลก แม้จะดูเป็นเทคโนโลยีเก่าแก่ที่สุดใน Part
Mainframe ของหลักสูตรนี้ แต่ IMS ยังคงเป็นระบบที่ประมวลผลธุรกรรมทางการเงินระดับหลักพันล้านรายการต่อวัน
ในธนาคารขนาดใหญ่หลายแห่ง เนื่องจากความเร็วและความเสถียรที่พิสูจน์มาแล้วกว่าครึ่งศตวรรษ

Part นี้จะพาคุณเข้าใจแนวคิดพื้นฐานของ IMS ตั้งแต่โครงสร้างฐานข้อมูลแบบลำดับชั้น (Hierarchical) ที่
แตกต่างจาก DB2 โดยสิ้นเชิง ไปจนถึงวิธีที่โปรแกรม COBOL สื่อสารกับ IMS ผ่านชุดคำสั่ง **DL/I (Data
Language/I)** ที่เรียกผ่านซับรูทีนพิเศษชื่อ `CBLTDLI`

> **⚠️ ข้อจำกัดของสภาพแวดล้อม**: เช่นเดียวกับ Part 058–064 เนื้อหาทั้งหมดใน Part นี้ต้องอาศัย IMS
> ซึ่ง**ไม่มีอยู่ในสภาพแวดล้อม GnuCOBOL ที่ใช้เรียนหลักสูตรนี้เลย** IMS เป็นซอฟต์แวร์ Middleware ของ
> IBM ที่แยกต่างหากจาก DB2/CICS โดยสิ้นเชิง (แม้จะทำงานบน z/OS เหมือนกัน) ตัวอย่างโค้ด COBOL ที่มี
> `CALL 'CBLTDLI'` ทุกตัวอย่างใน Part นี้เป็น **ไวยากรณ์อ้างอิง (Reference Syntax)** ที่ถูกต้องตาม
> มาตรฐาน IBM IMS จริง แต่**ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้** จะมีป้ายกำกับ
> `⚠️ REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้` กำกับไว้เสมอ

## ขั้นตอนที่ 641: IMS คืออะไร — ประวัติและภาพรวม

### จุดกำเนิดจากโครงการอวกาศ

IMS มีที่มาย้อนไปถึงปี 1966 เมื่อ North American Aviation (ผู้รับเหมาของ NASA สำหรับโครงการ Apollo)
ร่วมกับ IBM และ Caterpillar พัฒนาระบบที่เรียกว่า ICS/DL-I (Information Control System/Data
Language-I) เพื่อจัดการรายการชิ้นส่วนอะไหล่นับล้านชิ้นของจรวด Saturn V ปัญหาคือชิ้นส่วนอะไหล่มี
ความสัมพันธ์แบบ **"ส่วนประกอบย่อย" (Bill of Materials)** ตามธรรมชาติ — จรวดประกอบด้วยขั้นตอน
(stage) หลายขั้น แต่ละขั้นประกอบด้วยระบบย่อยหลายระบบ แต่ละระบบประกอบด้วยชิ้นส่วนหลายพันชิ้น ความ
สัมพันธ์แบบ "ต้นไม้" (Tree) นี้เองที่ทำให้ IBM ออกแบบ IMS ให้เป็นฐานข้อมูลแบบ **Hierarchical**
(ลำดับชั้น) ตั้งแต่วันแรก ต่างจาก DB2 ที่เกิดขึ้นทีหลังและใช้โมเดลเชิงสัมพันธ์ (Relational) แทน

### IMS ในปี 2026: ยังมีชีวิตอยู่จริงหรือ?

คำตอบคือ **ใช่อย่างแน่นอน** แม้จะดูเป็นเทคโนโลยีเก่าแก่ที่สุดในหลักสูตรนี้ แต่ IMS ยังคงเป็นระบบหลัก
ของธนาคารขนาดใหญ่หลายแห่งทั่วโลก โดยเฉพาะระบบที่ต้องการความเร็วในการเข้าถึงข้อมูลสูงสุด (IMS DB
มักเร็วกว่า DB2 อย่างมีนัยสำคัญสำหรับ pattern การเข้าถึงข้อมูลบางประเภท เพราะโครงสร้างลำดับชั้นที่
เรียบง่ายกว่าโมเดลเชิงสัมพันธ์) เหตุผลหลักที่องค์กรเหล่านี้ยังไม่ย้ายออกจาก IMS สอดคล้องกับเหตุผลที่
Part 001 อธิบายไว้เรื่องความเสี่ยงของการ Rewrite ระบบ Legacy ขนาดใหญ่

### IMS แบ่งออกเป็นสองส่วนหลัก

จุดสำคัญที่ต้องเข้าใจตั้งแต่ต้นคือ "IMS" ไม่ใช่ผลิตภัณฑ์เดียว แต่เป็น**ชุดผลิตภัณฑ์สองส่วนที่ทำงาน
ร่วมกันได้** (แต่ละส่วนสามารถใช้แยกกันได้ด้วย):

| ส่วนประกอบ | ชื่อเต็ม | หน้าที่ | เทียบเคียงได้กับ |
|---|---|---|---|
| **IMS DB** | IMS Database Manager | จัดเก็บและเข้าถึงข้อมูลแบบ Hierarchical | DB2 (แต่คนละโมเดลข้อมูล) |
| **IMS DC** (หรือ IMS TM) | IMS Data Communications / Transaction Manager | รับธุรกรรมจากเทอร์มินัล จัดคิวงาน จัดการ Transaction | CICS |

องค์กรบางแห่งใช้ **IMS DB คู่กับ CICS** (ฐานข้อมูล IMS + Transaction Manager ของ CICS) ในขณะที่บาง
แห่งใช้ **IMS DB คู่กับ IMS DC** (ทั้งคู่เป็นผลิตภัณฑ์ IMS) — ความยืดหยุ่นนี้เป็นเหตุผลหนึ่งที่ IMS
ยังคงอยู่รอดมาได้ยาวนาน เพราะองค์กรสามารถผสมผสานเทคโนโลยีตามความต้องการได้

### ข้อควรระวัง

- อย่าสับสนระหว่าง "IMS" (ผลิตภัณฑ์ Mainframe ของ IBM ที่เรียนใน Part นี้) กับคำว่า "IMS" ที่อาจ
  ปรากฏในบริบทอื่น (เช่น "Identity Management System" ในโลกความปลอดภัยไซเบอร์) — เป็นคนละเรื่องกัน
  โดยสิ้นเชิง
- IMS ไม่ใช่ระบบที่ "ถูกแทนที่แล้ว" ด้วย DB2 — ทั้งสองยังคงอยู่ร่วมกันในหลายองค์กร แต่ละตัวเหมาะกับ
  รูปแบบข้อมูลและ pattern การเข้าถึงที่ต่างกัน (จะอธิบายรายละเอียดในขั้นตอนที่ 642)

### แบบฝึกหัดที่ 641.1

**โจทย์**: จงอธิบายว่าเหตุใดปัญหา "การจัดการชิ้นส่วนอะไหล่จรวด" ของโครงการ Apollo จึงนำไปสู่การ
ออกแบบ IMS ให้เป็นฐานข้อมูลแบบ Hierarchical (ลำดับชั้น) แทนที่จะเป็นแบบอื่น

**เฉลยแนวทาง**: เพราะโครงสร้างของจรวดมีความสัมพันธ์แบบ "ส่วนประกอบย่อย" ตามธรรมชาติอยู่แล้ว
(จรวด → ขั้นตอน (stage) → ระบบย่อย → ชิ้นส่วน) ซึ่งเป็นความสัมพันธ์แบบต้นไม้ (parent-child) ที่ชัดเจน
มาก การออกแบบฐานข้อมูลให้มีโครงสร้างแบบลำดับชั้นตรง ๆ ตามธรรมชาติของข้อมูลจริง ทำให้การเข้าถึงข้อมูล
เป็นไปตามลำดับความสัมพันธ์ที่มีอยู่แล้วได้อย่างมีประสิทธิภาพสูงสุด แทนที่จะต้องออกแบบตารางแยกและ JOIN
กันแบบโมเดลเชิงสัมพันธ์ที่ยังไม่ถือกำเนิดขึ้นในขณะนั้นด้วยซ้ำ (ทฤษฎีฐานข้อมูลเชิงสัมพันธ์ของ E.F. Codd
เผยแพร่ในปี 1970 หลังจาก IMS เริ่มใช้งานจริงไปแล้วหลายปี)

## ขั้นตอนที่ 642: IMS DB เทียบกับฐานข้อมูลเชิงสัมพันธ์ — Segment และ Hierarchical Structure

### หน่วยข้อมูลพื้นฐานของ IMS DB: Segment

ใน DB2 (Part 057) หน่วยข้อมูลพื้นฐานคือ **แถว (Row)** ในตาราง (Table) แต่ใน IMS DB หน่วยข้อมูล
พื้นฐานเรียกว่า **Segment** — และ Segment เหล่านี้ถูกจัดเรียงเป็น **โครงสร้างต้นไม้ (Tree
Structure)** ที่มี Segment แม่ (Parent) หนึ่งตัว เชื่อมโยงไปยัง Segment ลูก (Child) ได้หลายตัว
และ Segment ลูกแต่ละตัวก็สามารถมี Segment ลูกของตัวเองต่อไปได้อีก (หลายระดับ)

### ตัวอย่าง: โครงสร้างฐานข้อมูลลูกค้าธนาคารแบบ IMS

```
                    CUSTOMER (root segment)
                    /                    \
            ACCOUNT (child)          ADDRESS (child)
            /         \
    TRANSACTION    BENEFICIARY
      (grandchild)   (grandchild)
```

ในโครงสร้างนี้:
- **CUSTOMER** คือ **Root Segment** (ต้นตอ) — ทุกการเข้าถึงข้อมูลต้องเริ่มจากที่นี่เสมอ
- **ACCOUNT** และ **ADDRESS** คือ Segment ลูกของ `CUSTOMER` (ลูกค้าหนึ่งคนมีได้หลายบัญชีและหลาย
  ที่อยู่)
- **TRANSACTION** และ **BENEFICIARY** คือ Segment หลานของ `CUSTOMER` (ลูกของ `ACCOUNT` อีกที)
  บัญชีหนึ่งบัญชีมีได้หลายธุรกรรมและหลายผู้รับผลประโยชน์

### เปรียบเทียบกับโมเดลเชิงสัมพันธ์ (DB2) ที่นักเรียนคุ้นเคยจาก Part 057

| แง่มุม | DB2 (Relational) | IMS DB (Hierarchical) |
|---|---|---|
| หน่วยข้อมูลพื้นฐาน | Row ในตาราง (Table) | Segment ในโครงสร้างต้นไม้ (Database Record) |
| ความสัมพันธ์ | ผ่าน Foreign Key + `JOIN` ตอน query | ฝังอยู่ในโครงสร้างต้นไม้ตั้งแต่การออกแบบ ไม่ต้อง JOIN |
| ภาษา Query | SQL (`SELECT ... WHERE ... JOIN ...`) | DL/I calls (`GU`, `GN`, `GHU`, `ISRT` ฯลฯ) |
| ความยืดหยุ่นในการ Query | สูงมาก — query รูปแบบไหนก็ได้ตามต้องการ | จำกัด — ต้องเข้าถึงตามเส้นทางลำดับชั้นที่ออกแบบไว้ |
| ความเร็วสำหรับ pattern ที่ออกแบบไว้ล่วงหน้า | เร็ว แต่มี overhead ของ query optimizer | เร็วมาก (มักเร็วกว่า DB2 สำหรับ pattern ที่ตรงกับโครงสร้าง) |
| ความยากในการเปลี่ยนโครงสร้างภายหลัง | ปรับเปลี่ยน schema ได้ง่ายกว่า | ยากกว่ามาก เพราะโครงสร้างต้นไม้ฝังลึกในการออกแบบตั้งแต่ต้น |

### ทำไมองค์กรถึงยังเลือกใช้ IMS DB แทน DB2 ในบางกรณี

จุดแข็งที่แท้จริงของ IMS DB คือ **ความเร็วในการเข้าถึงข้อมูลตามเส้นทางลำดับชั้นที่ออกแบบไว้ล่วงหน้า**
เมื่อ pattern การเข้าถึงข้อมูลของระบบชัดเจนตายตัว (เช่น "จากลูกค้าคนหนึ่ง ไปดูบัญชีทั้งหมด แล้วไปดู
ธุรกรรมของแต่ละบัญชี" เป็น pattern ที่ตายตัวและเกิดขึ้นซ้ำ ๆ นับล้านครั้งต่อวัน) IMS DB จะเร็วกว่า
DB2 อย่างมีนัยสำคัญ เพราะไม่มี overhead ของ SQL Query Optimizer ที่ต้องคิดคำนวณแผนการ query ทุกครั้ง
— ระบบธนาคารที่ต้องประมวลผลธุรกรรม ATM หรือบัตรเครดิตหลักพันล้านรายการต่อวันจึงมักยังคงพึ่งพา IMS DB
สำหรับ core banking บางส่วนอยู่จนถึงปัจจุบัน

### ข้อควรระวัง

- **การออกแบบโครงสร้างลำดับชั้นผิดพลาดตั้งแต่ต้นแก้ไขยากมากในภายหลัง** — ต่างจาก DB2 ที่เพิ่มตาราง
  ใหม่หรือเปลี่ยน schema ทำได้ค่อนข้างยืดหยุ่น การเปลี่ยนโครงสร้างต้นไม้ของ IMS DB (เช่น ต้องการเพิ่ม
  ความสัมพันธ์แบบ many-to-many ที่ไม่ใช่ parent-child ตรง ๆ) มักต้องอาศัยเทคนิคขั้นสูง เช่น
  **Logical Relationship** หรือ **Secondary Index** ซึ่งซับซ้อนกว่ามาก
- ข้อมูลใน IMS DB **ไม่สามารถ query แบบ ad-hoc ได้ง่าย** เหมือน SQL — ต้องเข้าถึงผ่านเส้นทางลำดับชั้น
  ที่กำหนดไว้ล่วงหน้าเท่านั้น (ผ่าน DL/I calls ที่จะเรียนในขั้นตอนที่ 645 เป็นต้นไป)

### แบบฝึกหัดที่ 642.1

**โจทย์**: จงออกแบบโครงสร้างลำดับชั้น (Hierarchical Structure) สำหรับระบบห้องสมุด ที่มี "หนังสือ"
เป็น root segment และแต่ละหนังสือมี "สำเนา (copy)" หลายเล่ม แต่ละสำเนามี "ประวัติการยืม" หลายรายการ

**เฉลย**:

```
                BOOK (root segment)
                       |
                    COPY (child)
                       |
              BORROW-HISTORY (grandchild)
```

`BOOK` เป็น root เพราะเป็นจุดเริ่มต้นของการค้นหาเสมอ (เช่น ค้นหาด้วย ISBN) `COPY` เป็นลูกของ `BOOK`
เพราะหนังสือชื่อเดียวกันมีได้หลายสำเนาจริง (แต่ละเล่มมีบาร์โค้ดของตัวเอง) และ `BORROW-HISTORY` เป็น
ลูกของ `COPY` เพราะประวัติการยืมแต่ละครั้งผูกกับสำเนาเล่มใดเล่มหนึ่งโดยเฉพาะ ไม่ใช่ผูกกับหนังสือ
โดยรวม (สำเนาเล่มที่ 1 อาจถูกยืมไป 5 ครั้ง ในขณะที่สำเนาเล่มที่ 2 อาจถูกยืมไปแค่ 1 ครั้ง)

## ขั้นตอนที่ 643: IMS DB เทียบกับ IMS DC — ฐานข้อมูลกับตัวจัดการธุรกรรม

### ทบทวนความแตกต่างจากขั้นตอนที่ 641

ขั้นตอนที่ 641 แนะนำไว้แล้วว่า IMS แบ่งเป็นสองส่วน มาดูรายละเอียดเพิ่มเติมของแต่ละส่วน

### IMS DB (Database Manager)

หน้าที่หลักคือจัดเก็บและให้บริการเข้าถึงข้อมูลแบบ Hierarchical ตามที่อธิบายในขั้นตอนที่ 642
IMS DB สามารถถูกเรียกใช้ได้จาก**โปรแกรมประเภทใดก็ได้** ไม่ว่าจะเป็นโปรแกรม batch ธรรมดา (คล้ายกับ
โปรแกรม COBOL อ่าน/เขียนไฟล์ Sequential/Indexed ที่เรียนมาตลอด Part 023-029) หรือโปรแกรมออนไลน์ที่
รันภายใต้ CICS หรือ IMS DC

### IMS DC / IMS TM (Data Communications / Transaction Manager)

หน้าที่หลักคือรับธุรกรรมจากเทอร์มินัล จัดคิวงาน และจัดการวงจรชีวิตของธุรกรรมออนไลน์ — ทำหน้าที่คล้าย
กับ CICS มาก (ทบทวนจาก Part 061) แต่มีสถาปัตยกรรมภายในที่ต่างกัน โดยเฉพาะเรื่องการจัดคิว: IMS DC
มีแนวคิด **Message Processing Region (MPR)** ที่ประมวลผลธุรกรรมจากคิวข้อความ (Message Queue) ซึ่ง
เป็นสถาปัตยกรรมที่ใกล้เคียงกับแนวคิด **Message Queue** ที่ระบบสมัยใหม่ (เช่น RabbitMQ, Kafka) ใช้
อยู่ทุกวันนี้อย่างน่าประหลาดใจ

### ตารางเปรียบเทียบ IMS DC กับ CICS

| แง่มุม | CICS (Part 061-064) | IMS DC |
|---|---|---|
| สถาปัตยกรรมการประมวลผล | Task-based (สร้าง Task ต่อธุรกรรม) | Message Queue-based (ธุรกรรมเข้าคิวรอ MPR ประมวลผล) |
| แนวคิด Pseudo-conversational | มี (ผ่าน COMMAREA — Part 064) | มีแนวคิดคล้ายกัน ผ่านกลไกที่เรียกว่า **Scratchpad Area (SPA)** |
| การสื่อสารกับหน้าจอ | BMS Maps (Part 063) | MFS (Message Format Service) — เทียบเท่า BMS ของฝั่ง IMS |
| ฐานข้อมูลที่ใช้ร่วมกันบ่อย | DB2 | IMS DB (แต่ก็ใช้ DB2 ร่วมได้เช่นกัน) |

### สถาปัตยกรรมที่ผสมผสาน: CICS-DBCTL

ในทางปฏิบัติจริง หลายองค์กรเลือกใช้ **CICS เป็น Transaction Manager (แทน IMS DC)** ควบคู่กับ
**IMS DB เป็นฐานข้อมูล** (แทน DB2) ผ่านส่วนประกอบที่เรียกว่า **DBCTL (Database Control)** ซึ่งเป็น
ส่วนของ IMS ที่ทำหน้าที่เชื่อมต่อ CICS เข้ากับ IMS DB โดยตรง องค์กรที่มีระบบ IMS DB เก่าแก่มาตั้งแต่
ทศวรรษ 1970 แต่ต้องการใช้ CICS สำหรับหน้าจอออนไลน์รุ่นใหม่ มักเลือกสถาปัตยกรรมนี้ เพื่อรักษาการลงทุน
เดิมในฐานข้อมูล IMS DB ไว้ ในขณะที่ได้ประโยชน์จากเครื่องมือพัฒนา CICS ที่ทันสมัยกว่า

### ข้อควรระวัง

- อย่าเข้าใจผิดว่า "ใช้ IMS DB ต้องใช้ IMS DC เสมอ" หรือ "ใช้ IMS DC ต้องใช้ IMS DB เสมอ" — ทั้งสอง
  เป็นผลิตภัณฑ์อิสระที่ผสมผสานกันได้หลายรูปแบบ (IMS DB + CICS, IMS DB + IMS DC, หรือแม้แต่ DB2 +
  IMS DC ก็เป็นไปได้ในทางเทคนิคแม้จะพบไม่บ่อย)
- Part นี้จะเน้นสอน **IMS DB** เป็นหลัก (ผ่าน DL/I calls) เพราะเป็นส่วนที่โปรแกรมเมอร์ COBOL ต้องเขียน
  โค้ดโต้ตอบโดยตรงบ่อยที่สุด ส่วน IMS DC (MFS, Scratchpad Area) จะกล่าวถึงเชิงแนวคิดเท่านั้น เพราะ
  รายละเอียดเชิงลึกอยู่นอกขอบเขตของหลักสูตรนี้

### แบบฝึกหัดที่ 643.1

**โจทย์**: จงอธิบายว่าทำไมองค์กรที่มีฐานข้อมูล IMS DB เก่าแก่มาตั้งแต่ทศวรรษ 1970 จึงอาจเลือกใช้ CICS
(แทน IMS DC) เป็น Transaction Manager สำหรับพัฒนาระบบออนไลน์ใหม่

**เฉลยแนวทาง**: เพราะการย้ายข้อมูลออกจาก IMS DB ไปเป็นรูปแบบอื่นมีความเสี่ยงสูงมาก (เหมือนที่ Part
001 และขั้นตอนที่ 642 อธิบายไว้) แต่การพัฒนาโปรแกรมออนไลน์ใหม่ด้วย CICS อาจสะดวกกว่า เพราะ CICS
เป็นเทคโนโลยีที่มีเครื่องมือพัฒนา บุคลากรที่มีทักษะ และเอกสารสนับสนุนที่แพร่หลายกว่า IMS DC ในตลาดงาน
ปัจจุบัน การใช้ DBCTL เชื่อม CICS เข้ากับ IMS DB โดยตรง ทำให้องค์กรได้ประโยชน์ทั้งสองทาง: รักษาการ
ลงทุนในฐานข้อมูล IMS DB เดิมที่มีข้อมูลสะสมมานานหลายสิบปี ในขณะที่ใช้เครื่องมือพัฒนาฝั่ง CICS ที่คุ้น
เคยและหาบุคลากรได้ง่ายกว่าสำหรับงานพัฒนาใหม่

## ขั้นตอนที่ 644: PCB และ PSB — กลไกควบคุมการเข้าถึงข้อมูล

### ทำไมต้องมี PCB/PSB

ก่อนที่โปรแกรม COBOL จะเข้าถึงข้อมูลใน IMS DB ได้ ระบบต้องรู้ก่อนว่า **โปรแกรมนี้ได้รับอนุญาตให้เข้า
ถึงฐานข้อมูลไหน มุมมองอะไรของฐานข้อมูลนั้น (บาง Segment อาจถูกซ่อนไว้ไม่ให้บางโปรแกรมเห็น) และ
โปรแกรมนี้ "อยู่ตำแหน่งไหน" ในโครงสร้างต้นไม้ ณ ขณะนั้น** — ข้อมูลทั้งหมดนี้ถูกเก็บไว้ในโครงสร้างที่
เรียกว่า **PCB (Program Communication Block)**

### PCB (Program Communication Block)

**PCB** คือพื้นที่หน่วยความจำที่ IMS จัดสรรให้กับโปรแกรมหนึ่งตัว เพื่อทำหน้าที่เป็น **"หน้าต่าง"**
มองเข้าไปยังฐานข้อมูล IMS DB หนึ่งฐาน PCB เก็บข้อมูลสำคัญ เช่น:

- ชื่อฐานข้อมูล (DBD name) ที่โปรแกรมนี้เข้าถึงได้
- **ตำแหน่งปัจจุบัน (Current Position)** ในโครงสร้างต้นไม้ — จำได้ว่า "ล่าสุดโปรแกรมอ่าน Segment
  ไหนไปแล้ว" เพื่อให้คำสั่ง "อ่านตัวถัดไป" (จะเรียนในขั้นตอนที่ 647) ทำงานได้ถูกต้อง
- **สถานะของการเรียกใช้ครั้งล่าสุด (Status Code)** — บอกว่าคำสั่งล่าสุดสำเร็จหรือไม่ (คล้าย
  `SQLCODE` ใน DB2 ที่เรียนใน Part 058 หรือ File Status Code ที่เรียนใน Part 030)

### PSB (Program Specification Block)

**PSB** คือกลุ่มของ PCB หนึ่งตัวหรือมากกว่า ที่ถูกกำหนดไว้ล่วงหน้าสำหรับโปรแกรมหนึ่งตัวโดยเฉพาะ
ถ้าโปรแกรมต้องเข้าถึงฐานข้อมูลมากกว่าหนึ่งฐาน (เช่น ฐานข้อมูลลูกค้า และฐานข้อมูลสินค้า) PSB ของ
โปรแกรมนั้นจะมี PCB สองตัว — หนึ่งตัวต่อฐานข้อมูลหนึ่งฐาน

### ความสัมพันธ์ระหว่าง DBD, PSB, และ PCB

```
DBD (Database Description)
  = นิยามโครงสร้างต้นไม้ทั้งหมดของฐานข้อมูลหนึ่งฐาน (กำหนดโดยผู้ดูแลฐานข้อมูล/DBA)
  = คล้ายกับ CREATE TABLE ทั้งหมดที่ประกอบเป็น schema ของฐานข้อมูลใน DB2

PSB (Program Specification Block)
  = นิยามว่าโปรแกรมหนึ่งตัว "มองเห็น" และ "เข้าถึงได้" ส่วนไหนของ DBD บ้าง
  = คล้ายกับ VIEW หรือสิทธิ์ (GRANT) ในโลก DB2 - จำกัดขอบเขตการมองเห็นให้แคบลง

PCB (Program Communication Block)
  = ที่เก็บสถานะการเชื่อมต่อจริงระหว่างการรันโปรแกรม (runtime) หนึ่ง PSB มีได้หลาย PCB
    (หนึ่งตัวต่อฐานข้อมูลหนึ่งฐานที่ PSB นั้นอนุญาตให้เข้าถึง)
```

### ข้อควรระวัง

- **PCB ไม่ใช่สิ่งที่โปรแกรมเมอร์สร้างขึ้นเอง** — มันถูกสร้างโดย IMS ตอนเริ่มรันโปรแกรม (ตาม PSB ที่
  ผูกไว้กับโปรแกรมนั้นในการตั้งค่าระบบ) โปรแกรมเมอร์แค่ต้องประกาศโครงสร้างข้อมูลที่ตรงกับ PCB ใน
  `LINKAGE SECTION` เพื่อรับค่าที่ IMS ส่งมาให้
- ผู้ที่ต้องกำหนด DBD และ PSB คือทีม **Database Administrator (DBA)** ไม่ใช่โปรแกรมเมอร์แอปพลิเคชัน
  — โปรแกรมเมอร์ COBOL มีหน้าที่แค่ใช้ PCB ที่ DBA เตรียมไว้ให้ผ่าน DL/I calls เท่านั้น

### แบบฝึกหัดที่ 644.1

**โจทย์**: จงอธิบายว่าทำไมโปรแกรมหนึ่งตัวที่ต้องเข้าถึงทั้งฐานข้อมูลลูกค้าและฐานข้อมูลบัญชี จึงต้องการ
PCB สองตัว แทนที่จะใช้ PCB ตัวเดียว

**เฉลย**: เพราะ PCB แต่ละตัวเป็น "หน้าต่าง" มองเข้าไปยังฐานข้อมูลหนึ่งฐานเท่านั้น (ผูกกับ DBD หนึ่งตัว)
และเก็บสถานะตำแหน่งปัจจุบัน (current position) แยกกันสำหรับแต่ละฐานข้อมูล ถ้าใช้ PCB ตัวเดียวสำหรับ
สองฐานข้อมูล IMS จะไม่สามารถแยกแยะได้ว่า "ตำแหน่งปัจจุบัน" ที่เก็บไว้นั้นหมายถึงตำแหน่งในฐานข้อมูล
ลูกค้าหรือฐานข้อมูลบัญชี การมี PCB แยกกันตามฐานข้อมูลทำให้โปรแกรมสามารถสลับไปมาระหว่างสองฐานข้อมูล
โดยแต่ละฐานยังคงจำตำแหน่งของตัวเองไว้ได้อย่างถูกต้อง

## ขั้นตอนที่ 645: DL/I Calls และ CBLTDLI — สะพานเชื่อมจาก COBOL สู่ IMS

### DL/I คือภาษาคำสั่งของ IMS

**DL/I (Data Language/I)** คือชุดคำสั่งมาตรฐานที่โปรแกรมใช้สื่อสารกับ IMS DB เทียบเท่ากับที่ SQL เป็น
ภาษาคำสั่งของ DB2 (Part 057) แต่ต่างจาก SQL ตรงที่ DL/I **ไม่ใช่ภาษาที่เขียนแยกเป็นประโยคแบบ SQL**
แต่เป็นชุดของ**การเรียกซับรูทีน (Subroutine Call)** ที่เรียกผ่านคำสั่ง COBOL มาตรฐานที่เรียนมาตั้งแต่
Part 031: `CALL`

### CBLTDLI — จุดเชื่อมต่อเดียวสู่ IMS ทั้งหมด

ทุกการเรียก DL/I จากโปรแกรม COBOL ทำผ่านการ `CALL` ไปยังซับรูทีนพิเศษชื่อ **`CBLTDLI`**
(ย่อมาจาก **CO**BOL **T**o **D**ata **L**anguage **I**) — ไม่ว่าจะต้องการ "อ่านข้อมูล", "เพิ่มข้อมูล
ใหม่", หรือ "แก้ไขข้อมูล" ทุกอย่างเรียกผ่าน `CBLTDLI` ตัวเดียวกันเสมอ โดยพารามิเตอร์ตัวแรกจะเป็น
**Function Code** (รหัสคำสั่งที่ต้องการ) เพื่อบอกว่าต้องการให้ IMS ทำอะไร

### รูปแบบมาตรฐานของการเรียก CBLTDLI

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       CALL 'CBLTDLI' USING DLI-FUNCTION
                             CUSTOMER-PCB
                             CUSTOMER-SEGMENT
                             CUSTOMER-SSA.
```

พารามิเตอร์แต่ละตัวมีความหมายดังนี้:

| พารามิเตอร์ | ความหมาย |
|---|---|
| `DLI-FUNCTION` | รหัสคำสั่ง 4 ตัวอักษร (เช่น `GU`, `GN`, `GHU`, `ISRT` — จะเรียนละเอียดในขั้นตอนที่ 646-649) |
| `CUSTOMER-PCB` | PCB ที่ผูกกับฐานข้อมูลที่ต้องการเข้าถึง (จากขั้นตอนที่ 644) ประกาศไว้ใน `LINKAGE SECTION` |
| `CUSTOMER-SEGMENT` | พื้นที่ใน `WORKING-STORAGE` ที่จะรับข้อมูล (กรณีอ่าน) หรือส่งข้อมูล (กรณีเพิ่ม/แก้ไข) |
| `CUSTOMER-SSA` | **Segment Search Argument** — เงื่อนไขการค้นหา (เช่น "หา CUSTOMER ที่ CUST-ID = 10001") |

### โครงสร้าง PCB มาตรฐานที่ต้องประกาศใน LINKAGE SECTION

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       LINKAGE SECTION.
       01  CUSTOMER-PCB.
           05  PCB-DBD-NAME         PIC X(8).
           05  PCB-SEGMENT-LEVEL    PIC XX.
           05  PCB-STATUS-CODE      PIC XX.
           05  PCB-PROC-OPTIONS     PIC X(4).
           05  PCB-RESERVED-DLI     PIC S9(5) COMP.
           05  PCB-SEG-NAME-FB      PIC X(8).
           05  PCB-LENGTH-FB-KEY    PIC S9(5) COMP.
           05  PCB-NUMB-SENS-SEGS   PIC S9(5) COMP.
           05  PCB-KEY-FB-AREA      PIC X(50).
```

**`PCB-STATUS-CODE`** คือฟิลด์ที่สำคัญที่สุด — ต้องตรวจสอบหลังทุกการเรียก `CBLTDLI` เสมอ (เทียบเท่า
`SQLCODE` ใน Part 058 หรือ File Status ใน Part 030) ค่าที่พบบ่อยที่สุด:

| ค่า `PCB-STATUS-CODE` | ความหมาย |
|---|---|
| Spaces (ว่างเปล่า) | สำเร็จ ไม่มีข้อผิดพลาด |
| `GE` | ไม่พบข้อมูลที่ค้นหา (Segment/Key Not Found) |
| `GB` | ถึงจุดสิ้นสุดฐานข้อมูลแล้ว (End of Database) ระหว่างอ่านแบบไล่ลำดับ |
| `II` | พยายามเพิ่มข้อมูลที่มี Key ซ้ำกับที่มีอยู่แล้ว (Duplicate Key) |
| `AI` | ไม่มีสิทธิ์เข้าถึง (Authorization Invalid) |

### ข้อควรระวัง

- **`CBLTDLI` เป็นซับรูทีนที่มาพร้อมกับ IMS runtime library เท่านั้น** — GnuCOBOL หรือ COBOL compiler
  ทั่วไปจะ `CALL` หาซับรูทีนชื่อนี้ไม่เจอเลย (compile ผ่าน เพราะ `CALL` เป็นไวยากรณ์ COBOL มาตรฐาน
  ที่เรียนใน Part 031 แต่จะ**รัน**ไม่ได้เพราะไม่มี object code ของ `CBLTDLI` ให้ link)
- ต้องตรวจสอบ `PCB-STATUS-CODE` **หลังทุกครั้ง**ที่เรียก `CBLTDLI` โดยไม่มีข้อยกเว้น เพราะ DL/I ไม่มี
  กลไก exception handling อัตโนมัติแบบภาษาสมัยใหม่ — การไม่ตรวจสอบอาจทำให้โปรแกรมใช้ข้อมูลที่ไม่ถูก
  ต้องต่อโดยไม่รู้ตัว (คล้ายกับคำเตือนเรื่อง `SQLCODE` ใน Part 058 และ File Status ใน Part 030)

### แบบฝึกหัดที่ 645.1

**โจทย์**: จงอธิบายว่าทำไม DL/I จึงออกแบบให้ทุกคำสั่ง (อ่าน, เพิ่ม, แก้ไข, ลบ) เรียกผ่านซับรูทีนเดียว
(`CBLTDLI`) โดยใช้ Function Code เป็นตัวบอกความแตกต่าง แทนที่จะมีซับรูทีนแยกกันสำหรับแต่ละคำสั่ง

**เฉลยแนวทาง**: การออกแบบให้มีจุดเชื่อมต่อ (interface) เดียวทำให้ระบบ Runtime ของ IMS ง่ายต่อการ
ดูแลรักษาและขยายความสามารถในอนาคต (เพิ่ม Function Code ใหม่โดยไม่ต้องสร้างซับรูทีนใหม่) นอกจากนี้ยัง
สอดคล้องกับข้อจำกัดทางเทคนิคของยุคที่ IMS ถูกออกแบบ (ทศวรรษ 1960-1970) ที่การเชื่อมโยง (link) โปรแกรม
กับซับรูทีนภายนอกจำนวนมากมีต้นทุนสูงกว่าปัจจุบันมาก การรวมทุกฟังก์ชันไว้ในจุดเข้าเดียวยังทำให้ผู้ดูแล
ระบบตรวจสอบและควบคุมการเข้าถึงฐานข้อมูลทั้งหมดได้จากจุดเดียว ซึ่งมีประโยชน์ด้านความปลอดภัยและการ
ตรวจสอบ (audit) ด้วย

## ขั้นตอนที่ 646: GU (Get Unique) — การอ่านข้อมูลแบบระบุตำแหน่งชัดเจน

### แนวคิดของ GU

**GU (Get Unique)** คือคำสั่งพื้นฐานที่สุดสำหรับการอ่านข้อมูลจาก IMS DB มีความหมายว่า **"ค้นหา
Segment ที่ตรงกับเงื่อนไขที่ระบุ โดยเริ่มค้นจากจุดเริ่มต้นของฐานข้อมูลเสมอ"** (ต่างจาก `GN` ที่จะ
เรียนในขั้นตอนถัดไป ซึ่งอ่านต่อจากตำแหน่งปัจจุบัน) `GU` มักใช้เป็นคำสั่งแรกสุดในการเข้าถึงข้อมูลของ
ทรานแซกชันหนึ่ง ๆ เสมอ

### Segment Search Argument (SSA)

ก่อนจะดูตัวอย่างโค้ด ต้องเข้าใจ **SSA (Segment Search Argument)** ก่อน — นี่คือวิธีที่ DL/I ใช้ระบุ
"ต้องการ Segment ไหน ด้วยเงื่อนไขอะไร" มีรูปแบบดังนี้:

```
segment-name (field-name  operator  value)
```

ตัวอย่างเช่น `CUSTOMER (CUST-ID = 10001)` หมายถึง "หา Segment ชื่อ CUSTOMER ที่ field CUST-ID มีค่า
เท่ากับ 10001"

### ตัวอย่าง GU

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       WORKING-STORAGE SECTION.
       01  DLI-GU                   PIC X(4) VALUE 'GU  '.
       01  CUSTOMER-SSA.
           05  FILLER               PIC X(8) VALUE 'CUSTOMER'.
           05  FILLER               PIC X    VALUE '('.
           05  FILLER               PIC X(7) VALUE 'CUSTID '.
           05  FILLER               PIC X(2) VALUE '= '.
           05  SSA-CUST-ID          PIC 9(5).
           05  FILLER               PIC X    VALUE ')'.

       01  CUSTOMER-SEGMENT.
           05  CS-CUST-ID           PIC 9(5).
           05  CS-CUST-NAME         PIC X(20).
           05  CS-CUST-BALANCE      PIC 9(9)V99.

       LINKAGE SECTION.
       01  CUSTOMER-PCB.
      *> (structure from step 644)
           05  PCB-STATUS-CODE      PIC XX.

       PROCEDURE DIVISION.
       LOOKUP-CUSTOMER-10001.
           MOVE 10001 TO SSA-CUST-ID.
           CALL 'CBLTDLI' USING DLI-GU
                                 CUSTOMER-PCB
                                 CUSTOMER-SEGMENT
                                 CUSTOMER-SSA.
           IF PCB-STATUS-CODE = SPACES
               DISPLAY 'FOUND: ' CS-CUST-NAME
           ELSE
               DISPLAY 'NOT FOUND, STATUS=' PCB-STATUS-CODE
           END-IF.
```

### อธิบายจุดสำคัญ

- `DLI-GU PIC X(4) VALUE 'GU  '` — Function Code ต้องมีความยาว 4 ตัวอักษรเสมอ (เติมช่องว่างให้ครบ
  ถ้าชื่อคำสั่งสั้นกว่า 4 ตัว)
- `CUSTOMER-SSA` คือ SSA ที่สร้างด้วย literal string ต่อกันเป็น group item — วิธีนี้ทำให้ SSA
  "ประกอบ" ขึ้นมาได้แบบไดนามิก (เปลี่ยนค่า `SSA-CUST-ID` ได้ตามต้องการก่อนเรียก `CBLTDLI` แต่ละครั้ง)
- หลัง `CALL` สำเร็จ ข้อมูลของ Segment ที่พบจะถูกนำมาใส่ใน `CUSTOMER-SEGMENT` (พื้นที่ที่เราจัดสรรไว้
  ใน `WORKING-STORAGE`) ให้โปรแกรมอ่านต่อได้ทันที

### ข้อควรระวัง

- **`GU` เริ่มค้นหาจากจุดเริ่มต้นของฐานข้อมูลเสมอ ทุกครั้งที่เรียก** — ถ้าต้องการอ่าน Segment
  หลายตัวต่อเนื่องกันตามลำดับ (เช่น อ่านบัญชีทั้งหมดของลูกค้าคนหนึ่ง) การเรียก `GU` ซ้ำหลายครั้งจะ
  ไม่มีประสิทธิภาพ ควรใช้ `GN` (ขั้นตอนที่ 647) แทนสำหรับการอ่านต่อเนื่อง
- ความยาวและรูปแบบของ SSA ต้องตรงตามข้อกำหนดของ DL/I เป๊ะ (วงเล็บ, ช่องว่าง, เครื่องหมายเปรียบเทียบ)
  ความผิดพลาดเล็กน้อยในการประกอบ SSA (เช่น ลืมช่องว่างก่อน `=`) อาจทำให้ IMS ตีความเงื่อนไขผิดไปเลย

### แบบฝึกหัดที่ 646.1

**โจทย์**: จงอธิบายว่าทำไม `GU` จึงเหมาะกับ "การเริ่มต้นเข้าถึงข้อมูลของธุรกรรมใหม่" มากกว่าการอ่าน
ข้อมูลต่อเนื่องหลายรายการ

**เฉลย**: เพราะ `GU` ค้นหาจากจุดเริ่มต้นของฐานข้อมูลทุกครั้ง ทำให้มั่นใจได้ว่าไม่ว่าตำแหน่งปัจจุบันใน
PCB จะเป็นอย่างไรมาก่อน (อาจค้างมาจากธุรกรรมก่อนหน้า) การเรียก `GU` จะได้ผลลัพธ์ที่ถูกต้องเสมอตาม
เงื่อนไขที่ระบุใน SSA ซึ่งเหมาะกับจุดเริ่มต้นของธุรกรรมใหม่ที่ต้องการ "เริ่มต้นใหม่อย่างแน่นอน"
ไม่พึ่งพาสถานะเดิมใด ๆ ต่างจาก `GN` ที่อาศัยตำแหน่งปัจจุบันเป็นจุดอ้างอิง ซึ่งเหมาะกับการอ่านข้อมูล
ต่อเนื่องมากกว่า

## ขั้นตอนที่ 647: GN (Get Next) — การอ่านข้อมูลตามลำดับต่อเนื่อง

### แนวคิดของ GN

**GN (Get Next)** อ่าน Segment **ถัดไปจากตำแหน่งปัจจุบัน** ในลำดับของโครงสร้างต้นไม้ (ทบทวนแนวคิด
"ตำแหน่งปัจจุบัน" ที่เก็บใน PCB จากขั้นตอนที่ 644) นี่คือคำสั่งที่ใช้บ่อยที่สุดสำหรับการวนอ่านข้อมูล
หลายรายการ เทียบเคียงได้กับ `READ ... NEXT RECORD` ของไฟล์ Indexed ที่เรียนใน Part 028

### ตัวอย่าง: อ่านบัญชีทั้งหมดของลูกค้าคนหนึ่งด้วย GU + GN ผสมกัน

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       WORKING-STORAGE SECTION.
       01  DLI-GU                   PIC X(4) VALUE 'GU  '.
       01  DLI-GN                   PIC X(4) VALUE 'GN  '.
       01  CUSTOMER-SSA.
           05  FILLER               PIC X(8) VALUE 'CUSTOMER'.
           05  FILLER               PIC X(3) VALUE '(ID'.
           05  FILLER               PIC X(2) VALUE '= '.
           05  SSA-CUST-ID          PIC 9(5).
           05  FILLER               PIC X    VALUE ')'.
       01  ACCOUNT-SSA              PIC X(8) VALUE 'ACCOUNT '.
       01  WS-STATUS-FLAG           PIC X VALUE 'N'.
           88  NO-MORE-ACCOUNTS     VALUE 'Y'.
       01  ACCOUNT-SEGMENT.
           05  AC-ACCT-NUMBER       PIC X(10).
           05  AC-BALANCE           PIC 9(9)V99.

       PROCEDURE DIVISION.
       LIST-ALL-ACCOUNTS-FOR-CUSTOMER.
      *> Step 1: GU positions us at the CUSTOMER root segment for
      *> ID 10001 - this becomes our "current position" in the PCB.
           MOVE 10001 TO SSA-CUST-ID.
           CALL 'CBLTDLI' USING DLI-GU
                                 CUSTOMER-PCB
                                 CUSTOMER-SEGMENT
                                 CUSTOMER-SSA.

           IF PCB-STATUS-CODE NOT = SPACES
               DISPLAY 'CUSTOMER NOT FOUND'
           ELSE
      *> Step 2: repeatedly GN the ACCOUNT segment - each call
      *> advances the "current position" to the NEXT account
      *> under the SAME customer, until IMS returns GE (no more).
               PERFORM UNTIL NO-MORE-ACCOUNTS
                   CALL 'CBLTDLI' USING DLI-GN
                                         CUSTOMER-PCB
                                         ACCOUNT-SEGMENT
                                         ACCOUNT-SSA
                   IF PCB-STATUS-CODE = SPACES
                       DISPLAY '  ACCOUNT: ' AC-ACCT-NUMBER
                           ' BALANCE: ' AC-BALANCE
                   ELSE
                       SET NO-MORE-ACCOUNTS TO TRUE
                   END-IF
               END-PERFORM
           END-IF.
```

### อธิบายจุดสำคัญ

- **`GU` ครั้งแรกกำหนด "จุดตั้งต้น"** ในโครงสร้างต้นไม้ (ลูกค้าคนที่ต้องการ) จากนั้น **`GN` แต่ละครั้ง
  จะเลื่อนตำแหน่งไปข้างหน้าทีละ Segment** ตามลำดับของโครงสร้างต้นไม้ (จากขั้นตอนที่ 642)
- **`GN` จะหยุดอัตโนมัติเมื่อออกนอกขอบเขตของลูกค้าคนปัจจุบัน** — ถ้าลูกค้า 10001 มี 3 บัญชี การเรียก
  `GN` ครั้งที่ 4 จะได้ status code ที่ไม่ใช่ spaces (มักเป็น `GE` หมายถึงไม่พบข้อมูลเพิ่มเติมที่ตรง
  เงื่อนไข) เพราะ IMS รู้ว่าตำแหน่งได้เลื่อนไปยัง Segment ของลูกค้าคนอื่นแล้ว (นอกขอบเขตที่ SSA เดิม
  จาก `GU` กำหนดไว้)
- แนวคิดนี้คล้ายกับ Master-Detail Matching ใน Part 026 ที่ใช้ Key เพื่อกำหนดขอบเขตของกลุ่มข้อมูล
  ที่เกี่ยวข้องกัน

### ข้อควรระวัง

- **`GN` โดยไม่มี Qualified SSA (แค่ชื่อ Segment เฉย ๆ ไม่มีเงื่อนไขในวงเล็บ) จะอ่านต่อไปเรื่อย ๆ
  แม้ข้ามไปยังลูกค้าคนอื่นแล้วก็ตาม** ถ้าต้องการจำกัดขอบเขตให้อยู่แค่ลูกค้าคนปัจจุบัน ต้องใช้
  **Qualified SSA ที่มีเงื่อนไขระบุชัดเจน** ร่วมกับ `GN` (เทคนิคขั้นสูงกว่าที่แสดงในตัวอย่างนี้
  เรียกว่า **GN within parent**) มิฉะนั้นโปรแกรมอาจอ่านข้อมูลของลูกค้าคนอื่นมาปนโดยไม่ตั้งใจ
- ควรตรวจสอบ `PCB-STATUS-CODE` ทุกครั้งหลัง `GN` เพื่อรู้ว่าถึงจุดสิ้นสุดของข้อมูลที่ต้องการหรือยัง
  (เหมือนกับการตรวจสอบ `AT END` หลัง `READ` ในไฟล์ Sequential ที่เรียนใน Part 025)

### แบบฝึกหัดที่ 647.1

**โจทย์**: จงอธิบายความแตกต่างระหว่าง `GU` กับ `GN` โดยเปรียบเทียบกับแนวคิด `READ` แบบ Indexed
(Part 028) ที่นักเรียนคุ้นเคยอยู่แล้ว

**เฉลย**: `GU` เทียบเคียงได้กับ `READ` แบบ `ACCESS MODE IS RANDOM` (Part 028 ขั้นตอนที่ 273) ที่
กระโดดไปหา record ที่ต้องการโดยตรงผ่านค่า Key โดยไม่สนใจตำแหน่งเดิม ส่วน `GN` เทียบเคียงได้กับ
`READ ... NEXT RECORD` (Part 028 ขั้นตอนที่ 271) ที่อ่าน record ถัดไปจากตำแหน่งปัจจุบัน โดยอาศัย
ตำแหน่งที่เก็บไว้จากการอ่านครั้งก่อนหน้าเป็นจุดอ้างอิง ความแตกต่างสำคัญคือ IMS DB มีมิติเพิ่มเติมเรื่อง
"ลำดับชั้น" (hierarchical) ทำให้ `GN` ไม่ได้แค่เลื่อนไปยัง record ถัดไปในไฟล์เดียว แต่เลื่อนไปตาม
ลำดับของโครงสร้างต้นไม้ทั้งหมด ซึ่งอาจข้ามจาก Segment ลูกของ parent หนึ่งไปยัง Segment ลูกของ parent
ถัดไปได้ถ้าไม่มีการจำกัดขอบเขตด้วย Qualified SSA

## ขั้นตอนที่ 648: GHU (Get Hold Unique) — การอ่านข้อมูลเพื่อเตรียมแก้ไข

### ทำไมต้องมี "Get Hold" แยกจาก "Get" ธรรมดา

**GHU (Get Hold Unique)** มีพฤติกรรมเหมือน `GU` ทุกประการในแง่ของการค้นหาและอ่านข้อมูล แต่มีความ
แตกต่างสำคัญหนึ่งจุด: **`GHU` จะ "ล็อก" (hold) Segment ที่อ่านมาไว้ เพื่อเตรียมพร้อมสำหรับการแก้ไข
(REPL) หรือลบ (DLET) ในขั้นตอนถัดไป** ถ้าใช้ `GU` ธรรมดาแล้วพยายามแก้ไขข้อมูลทันที IMS จะปฏิเสธ
เพราะไม่ได้ "จอง" สิทธิ์ในการแก้ไขไว้ล่วงหน้า

### เปรียบเทียบกับแนวคิดที่เรียนมาแล้ว

หลักการนี้เหมือนกับกฎของ `REWRITE` ที่ต้อง `READ` มาก่อนเสมอ (Part 025 ขั้นตอนที่ 245 และ Part 028
ขั้นตอนที่ 276) เพียงแต่ IMS แยกความแตกต่างชัดเจนกว่าด้วยการมี Function Code คนละตัว (`GU` สำหรับ
"อ่านเฉย ๆ" กับ `GHU` สำหรับ "อ่านเพื่อเตรียมแก้ไข") แทนที่จะใช้ `READ` ตัวเดียวกันเหมือน COBOL
File I/O ทั่วไป

### ตัวอย่าง: อ่านและแก้ไขยอดเงินด้วย GHU + REPL

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       WORKING-STORAGE SECTION.
       01  DLI-GHU                  PIC X(4) VALUE 'GHU '.
       01  DLI-REPL                 PIC X(4) VALUE 'REPL'.
       01  CUSTOMER-SSA.
           05  FILLER               PIC X(8) VALUE 'CUSTOMER'.
           05  FILLER               PIC X(3) VALUE '(ID'.
           05  FILLER               PIC X(2) VALUE '= '.
           05  SSA-CUST-ID          PIC 9(5).
           05  FILLER               PIC X    VALUE ')'.

       PROCEDURE DIVISION.
       DEPOSIT-INTO-ACCOUNT.
           MOVE 10001 TO SSA-CUST-ID.
      *> GHU locks this segment - no other task can modify the
      *> SAME segment until this program issues REPL, DLET, or
      *> ends its unit of work (equivalent in spirit to a database
      *> row lock in DB2, Part 059).
           CALL 'CBLTDLI' USING DLI-GHU
                                 CUSTOMER-PCB
                                 CUSTOMER-SEGMENT
                                 CUSTOMER-SSA.
           IF PCB-STATUS-CODE = SPACES
               ADD 500.00 TO CS-CUST-BALANCE
      *> REPL writes the MODIFIED CUSTOMER-SEGMENT back to the
      *> exact position GHU just held - the same "must READ before
      *> REWRITE" discipline from Part 025/028, DL/I style.
               CALL 'CBLTDLI' USING DLI-REPL
                                     CUSTOMER-PCB
                                     CUSTOMER-SEGMENT
               IF PCB-STATUS-CODE = SPACES
                   DISPLAY 'BALANCE UPDATED SUCCESSFULLY'
               ELSE
                   DISPLAY 'REPL FAILED, STATUS=' PCB-STATUS-CODE
               END-IF
           ELSE
               DISPLAY 'CUSTOMER NOT FOUND FOR UPDATE'
           END-IF.
```

### ข้อควรระวัง

- **`REPL` ต้องตามหลัง `GHU` (หรือ `GHN` — Get Hold Next) เสมอ ไม่สามารถใช้หลัง `GU`/`GN` ธรรมดาได้**
  — ถ้าพยายามเรียก `REPL` หลัง `GU` ธรรมดา IMS จะคืน status code แสดงข้อผิดพลาดทันที เพราะไม่มีการ
  "จอง" สิทธิ์ไว้ล่วงหน้า
- Segment ที่ถูก `GHU` ล็อกไว้ **จะถูกปลดล็อกอัตโนมัติ** เมื่อโปรแกรมจบหน่วยงาน (Unit of Work — ทบทวน
  แนวคิด Commit จาก Part 066 ที่จะเรียนเรื่อง Commit Interval) หรือเมื่อมีการเรียก `GHU`/`GU` ครั้ง
  ใหม่แทนที่ตำแหน่งเดิม — ไม่ควรถือ lock ค้างไว้นานเกินจำเป็น เพราะจะกีดกันไม่ให้ธุรกรรมอื่นเข้าถึง
  Segment เดียวกันได้ (หลักการเดียวกับที่ Part 064 ขั้นตอนที่ 631 เตือนเรื่องการถือทรัพยากรค้างไว้)

### แบบฝึกหัดที่ 648.1

**โจทย์**: จงอธิบายว่าทำไม IMS จึงแยก Function Code `GU` กับ `GHU` ออกจากกันอย่างชัดเจน แทนที่จะให้
`GU` ล็อก Segment ไว้เสมอทุกครั้งโดยอัตโนมัติ

**เฉลยแนวทาง**: เพราะการล็อก Segment มีต้นทุนด้านประสิทธิภาพและอาจกีดกันธุรกรรมอื่นที่ต้องการอ่าน
ข้อมูลเดียวกันพร้อมกัน (แม้จะแค่อ่านอย่างเดียวไม่ได้ต้องการแก้ไข) หากการอ่านทุกครั้งล็อกข้อมูลไว้เสมอ
โดยไม่จำเป็น ระบบที่มีธุรกรรมจำนวนมากอ่านข้อมูลเดียวกันพร้อมกัน (เช่น รายงานยอดคงเหลือที่ลูกค้าหลายคน
เรียกดูพร้อมกัน) จะเกิดการรอคิวโดยไม่จำเป็น การแยก Function Code ทำให้โปรแกรมเมอร์เลือกใช้ `GU`
สำหรับกรณีอ่านอย่างเดียว (ไม่ล็อก ประสิทธิภาพสูงสุด) และใช้ `GHU` เฉพาะกรณีที่ตั้งใจจะแก้ไขข้อมูลจริง
เท่านั้น (ยอมรับต้นทุนของการล็อกเมื่อจำเป็นเท่านั้น)

## ขั้นตอนที่ 649: ISRT (Insert) — การเพิ่มข้อมูลใหม่เข้าโครงสร้างต้นไม้

### แนวคิดของ ISRT

**ISRT (Insert)** คือคำสั่งสำหรับเพิ่ม Segment ใหม่เข้าไปในฐานข้อมูล เทียบเคียงได้กับ `WRITE` ของ
ไฟล์ COBOL (Part 025) หรือ `INSERT INTO` ของ SQL (Part 057) จุดที่ต้องระวังเป็นพิเศษคือ **การเพิ่ม
Segment ลูก (child) ต้องระบุตำแหน่งของ Segment แม่ (parent) ให้ถูกต้องก่อนเสมอ** เพราะ IMS DB ไม่มี
Foreign Key ให้ตรวจสอบความสัมพันธ์แบบ DB2 — ความสัมพันธ์ parent-child ถูกกำหนดผ่านตำแหน่งการ ISRT
โดยตรง

### ตัวอย่าง: เพิ่มบัญชีใหม่ให้ลูกค้าที่มีอยู่แล้ว

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       WORKING-STORAGE SECTION.
       01  DLI-GU                   PIC X(4) VALUE 'GU  '.
       01  DLI-ISRT                 PIC X(4) VALUE 'ISRT'.
       01  CUSTOMER-SSA.
           05  FILLER               PIC X(8) VALUE 'CUSTOMER'.
           05  FILLER               PIC X(3) VALUE '(ID'.
           05  FILLER               PIC X(2) VALUE '= '.
           05  SSA-CUST-ID          PIC 9(5).
           05  FILLER               PIC X    VALUE ')'.
       01  ACCOUNT-SSA-UNQUALIFIED  PIC X(8) VALUE 'ACCOUNT '.
       01  NEW-ACCOUNT-SEGMENT.
           05  NA-ACCT-NUMBER       PIC X(10) VALUE 'AC00099999'.
           05  NA-BALANCE           PIC 9(9)V99 VALUE 0.

       PROCEDURE DIVISION.
       ADD-NEW-ACCOUNT-FOR-CUSTOMER.
      *> Step 1: position on the PARENT (CUSTOMER) first - IMS
      *> derives the new ACCOUNT segment's parentage from wherever
      *> the PCB's current position sits at the moment of ISRT.
           MOVE 10001 TO SSA-CUST-ID.
           CALL 'CBLTDLI' USING DLI-GU
                                 CUSTOMER-PCB
                                 CUSTOMER-SEGMENT
                                 CUSTOMER-SSA.

           IF PCB-STATUS-CODE = SPACES
      *> Step 2: ISRT the new ACCOUNT segment - it becomes a CHILD
      *> of whichever CUSTOMER the PCB is currently positioned on.
               CALL 'CBLTDLI' USING DLI-ISRT
                                     CUSTOMER-PCB
                                     NEW-ACCOUNT-SEGMENT
                                     ACCOUNT-SSA-UNQUALIFIED
               IF PCB-STATUS-CODE = SPACES
                   DISPLAY 'NEW ACCOUNT ADDED SUCCESSFULLY'
               ELSE
                   DISPLAY 'ISRT FAILED, STATUS=' PCB-STATUS-CODE
               END-IF
           ELSE
               DISPLAY 'CUSTOMER NOT FOUND - CANNOT ADD ACCOUNT'
           END-IF.
```

### อธิบายจุดสำคัญ

- **ลำดับคือทุกสิ่ง**: ต้อง `GU` ไปยัง Segment แม่ (`CUSTOMER`) ให้สำเร็จก่อนเสมอ แล้วจึง `ISRT`
  Segment ลูก (`ACCOUNT`) ต่อท้าย — IMS จะใช้ **ตำแหน่งปัจจุบันใน PCB ขณะนั้น** เป็นตัวกำหนดว่า
  Segment ใหม่จะกลายเป็นลูกของ Segment แม่ตัวไหน
- ถ้าต้องการเพิ่ม **Root Segment** ใหม่ทั้งหมด (เช่น ลูกค้าใหม่ทั้งคน ไม่ใช่แค่บัญชีใหม่) ไม่จำเป็น
  ต้อง `GU` ไปยัง parent ก่อน เพราะ Root Segment ไม่มี parent — `ISRT` ตรงได้เลย

### ข้อควรระวัง

- **การ ISRT Segment ลูกโดยไม่ได้ระบุตำแหน่ง parent ที่ถูกต้องล่วงหน้า จะทำให้ข้อมูลผูกผิดคน** —
  ต่างจาก DB2 ที่ Foreign Key จะบังคับความถูกต้องของความสัมพันธ์ให้ (ทบทวนแนวคิด Referential
  Integrity จาก Part 057) IMS DB **ไม่มีการตรวจสอบอัตโนมัติแบบนี้เลย** ความถูกต้องขึ้นอยู่กับวินัย
  ของโปรแกรมเมอร์ในการ `GU`/`GHU` ไปยังตำแหน่ง parent ที่ถูกต้องก่อน `ISRT` ทุกครั้ง — นี่คือความ
  เสี่ยงสำคัญของโมเดล Hierarchical เมื่อเทียบกับ Relational
- Segment ที่ Key ซ้ำกับที่มีอยู่แล้วจะได้ status code `II` (Duplicate Key) — ต้องตรวจสอบก่อนหรือ
  จัดการ error นี้เสมอ

### แบบฝึกหัดที่ 649.1

**โจทย์**: จงอธิบายว่าทำไมการ `ISRT` Segment ลูกใน IMS DB จึงมีความเสี่ยงต่อข้อผิดพลาดด้านความ
สัมพันธ์ของข้อมูลมากกว่าการ `INSERT` แถวใหม่ที่มี Foreign Key ใน DB2

**เฉลยแนวทาง**: เพราะ DB2 มีกลไก Foreign Key Constraint ที่ฐานข้อมูลตรวจสอบให้อัตโนมัติว่าค่าที่
อ้างอิงถึง parent table นั้นมีอยู่จริง หากไม่มี ฐานข้อมูลจะปฏิเสธการ `INSERT` ทันทีโดยอัตโนมัติ
แต่ IMS DB ไม่มีกลไกตรวจสอบความสัมพันธ์แบบนี้ในตัว ความสัมพันธ์ parent-child ถูกกำหนดโดย "ตำแหน่ง
ปัจจุบันของ PCB ขณะเรียก ISRT" เท่านั้น หากโปรแกรมเมอร์เขียนโค้ดผิดพลาด (เช่น ลืม `GU` ไปยัง parent
ที่ถูกต้องก่อน หรือ `GU` ไปยัง parent ผิดคนโดยไม่ตั้งใจ) Segment ใหม่จะถูกผูกเข้ากับ parent ที่ผิดโดย
ไม่มีการแจ้งเตือนใด ๆ จากระบบเลย ความถูกต้องของความสัมพันธ์จึงขึ้นอยู่กับความระมัดระวังของโปรแกรมเมอร์
ทั้งหมด ไม่ใช่กลไกอัตโนมัติของฐานข้อมูลเหมือน DB2

## ขั้นตอนที่ 650: ตัวอย่างบูรณาการ — Traverse โครงสร้างต้นไม้เต็มรูปแบบ และสรุปเปรียบเทียบ IMS/CICS/DB2

### ตัวอย่างสมบูรณ์: อ่านลูกค้าพร้อมทุกบัญชีและทุกธุรกรรมของแต่ละบัญชี

มาปิดท้าย Part นี้ด้วยการรวมทุกคำสั่งที่เรียนมา (`GU`, `GN`, `GHU`, `ISRT`) เข้าด้วยกันในสถานการณ์จริง
ที่ต้อง traverse โครงสร้างต้นไม้ 3 ระดับ (`CUSTOMER` → `ACCOUNT` → `TRANSACTION` ทบทวนจากขั้นตอนที่
642)

> ⚠️ **REFERENCE SYNTAX — ไม่สามารถ compile/รันได้ในสภาพแวดล้อมนี้**

```cobol
       WORKING-STORAGE SECTION.
       01  DLI-GU                   PIC X(4) VALUE 'GU  '.
       01  DLI-GN                   PIC X(4) VALUE 'GN  '.
       01  CUSTOMER-SSA.
           05  FILLER               PIC X(8) VALUE 'CUSTOMER'.
           05  FILLER               PIC X(3) VALUE '(ID'.
           05  FILLER               PIC X(2) VALUE '= '.
           05  SSA-CUST-ID          PIC 9(5).
           05  FILLER               PIC X    VALUE ')'.
       01  ACCOUNT-SSA              PIC X(8) VALUE 'ACCOUNT '.
       01  TRANS-SSA                PIC X(11) VALUE 'TRANSACTION'.
       01  WS-ACCT-EOF              PIC X VALUE 'N'.
           88  NO-MORE-ACCOUNTS     VALUE 'Y'.
       01  WS-TRANS-EOF             PIC X VALUE 'N'.
           88  NO-MORE-TRANS        VALUE 'Y'.

       PROCEDURE DIVISION.
       WALK-CUSTOMER-TREE.
           MOVE 10001 TO SSA-CUST-ID.
           CALL 'CBLTDLI' USING DLI-GU
                                 CUSTOMER-PCB
                                 CUSTOMER-SEGMENT
                                 CUSTOMER-SSA.
           IF PCB-STATUS-CODE NOT = SPACES
               DISPLAY 'CUSTOMER NOT FOUND'
           ELSE
               DISPLAY 'CUSTOMER: ' CS-CUST-NAME
      *> Outer loop: walk every ACCOUNT under this customer.
               PERFORM UNTIL NO-MORE-ACCOUNTS
                   CALL 'CBLTDLI' USING DLI-GN
                                         CUSTOMER-PCB
                                         ACCOUNT-SEGMENT
                                         ACCOUNT-SSA
                   IF PCB-STATUS-CODE NOT = SPACES
                       SET NO-MORE-ACCOUNTS TO TRUE
                   ELSE
                       DISPLAY '  ACCOUNT: ' AC-ACCT-NUMBER
                       MOVE 'N' TO WS-TRANS-EOF
      *> Inner loop: walk every TRANSACTION under THIS account.
      *> Note this GN call has a DIFFERENT segment name in its SSA
      *> (TRANSACTION, not ACCOUNT) - IMS descends one more level
      *> down the tree from wherever GN just positioned us.
                       PERFORM UNTIL NO-MORE-TRANS
                           CALL 'CBLTDLI' USING DLI-GN
                                                 CUSTOMER-PCB
                                                 TRANS-SEGMENT
                                                 TRANS-SSA
                           IF PCB-STATUS-CODE NOT = SPACES
                               SET NO-MORE-TRANS TO TRUE
                           ELSE
                               DISPLAY '    TRANS: ' TR-AMOUNT
                           END-IF
                       END-PERFORM
                   END-IF
               END-PERFORM
           END-IF.
```

### ตารางสรุปเปรียบเทียบ IMS, CICS, และ DB2

หลังจากเรียนมาตลอด Part 057-065 มาสรุปภาพรวมทั้งสามเทคโนโลยี Mainframe หลักที่มักทำงานร่วมกันในระบบ
จริง:

| แง่มุม | DB2 (Part 057-060) | CICS (Part 061-064) | IMS (Part นี้) |
|---|---|---|---|
| บทบาทหลัก | ฐานข้อมูลเชิงสัมพันธ์ | Transaction Processing Monitor | ฐานข้อมูลลำดับชั้น (DB) + Transaction Manager (DC) |
| ภาษาคำสั่ง | SQL (`EXEC SQL`) | `EXEC CICS` commands | DL/I calls ผ่าน `CBLTDLI` |
| โมเดลข้อมูล | ตาราง + ความสัมพันธ์ผ่าน Foreign Key | ไม่มีโมเดลข้อมูลของตัวเอง (ใช้ DB2/VSAM/IMS DB) | โครงสร้างต้นไม้ (Segment/Parent-Child) |
| จุดแข็งหลัก | ความยืดหยุ่นในการ query, มาตรฐานอุตสาหกรรม | การจัดการธุรกรรมออนไลน์ปริมาณสูง | ความเร็วสูงสุดสำหรับ pattern การเข้าถึงที่ออกแบบไว้ล่วงหน้า |
| ปีที่ถือกำเนิด | ต้นทศวรรษ 1980 (จากทฤษฎีปี 1970) | 1968 | 1966 |
| ใช้ร่วมกันได้ไหม | ได้ (CICS+DB2 เป็นคู่ยอดนิยม) | ได้ (CICS+DB2 หรือ CICS+IMS DB ผ่าน DBCTL) | ได้ (IMS DB+CICS หรือ IMS DB+IMS DC) |

### บทสรุปเชิงแนวคิดของ Part นี้

IMS สอนบทเรียนสำคัญที่ยังคงใช้ได้ในการออกแบบระบบสมัยใหม่: **เมื่อ pattern การเข้าถึงข้อมูลของคุณ
ชัดเจนและตายตัว การออกแบบโครงสร้างข้อมูลให้สอดคล้องกับ pattern นั้นโดยตรง (แทนที่จะใช้โมเดลทั่วไปที่
ยืดหยุ่นแต่ช้ากว่า) สามารถให้ประสิทธิภาพที่เหนือกว่าอย่างมีนัยสำคัญ** แนวคิดนี้ยังคงปรากฏในเทคโนโลยี
ฐานข้อมูลสมัยใหม่หลายตัว เช่น ฐานข้อมูลเอกสาร (Document Database เช่น MongoDB) ที่ใช้โครงสร้างแบบ
ซ้อนกัน (nested/embedded documents) ซึ่งมีแนวคิดใกล้เคียงกับ Hierarchical Database ของ IMS อย่าง
น่าประหลาดใจ แม้จะห่างกันเกือบ 50 ปี

### ข้อควรระวัง

- อย่าลืมว่าตัวอย่างในขั้นตอนนี้เป็นการ Traverse "ทั้งต้นไม้" ของลูกค้าคนเดียว — ถ้า `GN` ไม่มีการ
  จำกัดขอบเขตอย่างเหมาะสม (เทคนิค Qualified SSA ที่กล่าวถึงในขั้นตอนที่ 647) การวนลูปอาจไหลข้าม
  ไปยังลูกค้าคนถัดไปโดยไม่ตั้งใจ ควรตรวจสอบ status code อย่างเข้มงวดในทุกจุดเสมอ

### แบบฝึกหัดที่ 650.1

**โจทย์**: จงสรุปเป็นย่อหน้าสั้น ๆ ว่าทำไมองค์กรจำนวนมากในโลกยังคงใช้ IMS ควบคู่ไปกับ DB2 และ CICS
แทนที่จะย้ายทุกอย่างไปเป็น DB2 ทั้งหมด

**เฉลยแนวทาง**: เพราะแต่ละเทคโนโลยีมีจุดแข็งที่แตกต่างกันสำหรับ workload คนละประเภท IMS DB ให้ความ
เร็วสูงสุดสำหรับ pattern การเข้าถึงข้อมูลที่ตายตัวและเกิดขึ้นซ้ำ ๆ ปริมาณมหาศาล (เช่น ธุรกรรม ATM/
บัตรเครดิต) ในขณะที่ DB2 ให้ความยืดหยุ่นสูงสุดสำหรับการ query ข้อมูลในรูปแบบที่หลากหลายและเปลี่ยนแปลง
ได้ตามความต้องการทางธุรกิจที่เติบโตขึ้น การย้ายระบบ IMS DB ที่มีข้อมูลสะสมมานานหลายสิบปีไปเป็น DB2
ทั้งหมดมีความเสี่ยงสูงมาก (เหมือนที่ Part 001 อธิบายไว้) และอาจไม่ได้ประโยชน์ด้านประสิทธิภาพสำหรับ
workload ที่ IMS DB ออกแบบมาให้เหมาะสมอยู่แล้ว องค์กรที่ชาญฉลาดจึงเลือกใช้แต่ละเทคโนโลยีตามจุดแข็ง
ของมัน แทนที่จะบังคับให้ทุกอย่างอยู่บนเทคโนโลยีเดียว

## สรุปท้ายบท

Part นี้พาคุณสำรวจเทคโนโลยี Mainframe ที่เก่าแก่ที่สุดในหลักสูตร แต่ยังคงมีความสำคัญอย่างยิ่งในโลก
ปัจจุบัน:

- ประวัติศาสตร์ของ IMS จากโครงการอวกาศ Apollo สู่ระบบธนาคารระดับโลกในปัจจุบัน
- โครงสร้างฐานข้อมูลแบบ **Hierarchical** (Segment, Parent-Child) และความแตกต่างจากโมเดลเชิงสัมพันธ์
  ของ DB2
- ความแตกต่างระหว่าง **IMS DB** (ฐานข้อมูล) และ **IMS DC** (ตัวจัดการธุรกรรม)
- แนวคิด **PCB** และ **PSB** ที่ควบคุมการเข้าถึงข้อมูลของแต่ละโปรแกรม
- DL/I calls พื้นฐานทั้งสี่: **GU** (อ่านแบบระบุตำแหน่ง), **GN** (อ่านต่อเนื่อง), **GHU** (อ่านเพื่อ
  เตรียมแก้ไข), **ISRT** (เพิ่มข้อมูลใหม่) ผ่านซับรูทีน **CBLTDLI**
