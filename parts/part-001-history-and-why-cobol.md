# Part 001: ประวัติศาสตร์และโลกของ COBOL, ทำไมต้องเรียน COBOL ในปี 2026, ภาพรวมอุตสาหกรรม (ขั้นตอนที่ 1–10)

## คำนำของ Part นี้

ยินดีต้อนรับสู่หลักสูตร **"สอนเขียนและพัฒนาโปรแกรมและเว็บแอปพลิเคชันด้วย COBOL"** หลักสูตรนี้จะพาคุณเดินทางตั้งแต่
ขั้นตอนที่ 1 ไปจนถึงขั้นตอนที่ 1000 ผ่านเนื้อหา 100 Part ครอบคลุมตั้งแต่การเขียนโปรแกรมพื้นฐานที่สุด
ไปจนถึงการออกแบบระบบระดับองค์กร (Enterprise-grade), Mainframe, ฐานข้อมูล, การเชื่อมต่อกับเทคโนโลยีเว็บสมัยใหม่
และการทำโปรเจกต์จริงระดับโลก

ก่อนที่เราจะเริ่มเขียนโค้ดบรรทัดแรก Part นี้จะพาคุณทำความรู้จักกับ COBOL ในภาพกว้างก่อน:
มันคืออะไร มาจากไหน ทำไมยังมีคนใช้อยู่ในปี 2026 และทำไมการเรียนรู้มันถึงยังคุ้มค่ามหาศาล
ความเข้าใจภาพรวมนี้จะเป็นแรงจูงใจและบริบทสำคัญที่ทำให้คุณเข้าใจว่าทำไมหลักสูตรถึงถูกออกแบบมาในลักษณะนี้

## ขั้นตอนที่ 1: COBOL คืออะไร และประวัติศาสตร์การถือกำเนิด

### COBOL คืออะไร

**COBOL** ย่อมาจาก **CO**mmon **B**usiness-**O**riented **L**anguage เป็นภาษาโปรแกรมเชิงกระบวนการ (Procedural Programming Language)
ที่ถูกออกแบบมาโดยเฉพาะสำหรับ **งานประมวลผลข้อมูลทางธุรกิจ** (Business Data Processing) เช่น ระบบบัญชี ระบบธนาคาร
ระบบประกันภัย ระบบเงินเดือน และระบบสินค้าคงคลัง

จุดเด่นที่ทำให้ COBOL แตกต่างจากภาษาโปรแกรมอื่นตั้งแต่วันแรกคือ **การเน้นให้โค้ดอ่านง่ายเหมือนภาษาอังกฤษ**
(English-like syntax) เพื่อให้ผู้บริหารธุรกิจที่ไม่ใช่โปรแกรมเมอร์สามารถอ่านและเข้าใจตรรกะของโปรแกรมได้

ตัวอย่างเช่น โค้ด COBOL ในการบวกเลขสองจำนวนจะมีหน้าตาประมาณนี้ (รายละเอียดวากยสัมพันธ์จะสอนใน Part ถัดไป):

```cobol
       ADD FIRST-NUMBER TO SECOND-NUMBER GIVING TOTAL-AMOUNT.
```

เปรียบเทียบกับภาษาอื่นที่อาจเขียนสั้นกว่าแต่เข้าใจยากกว่าสำหรับผู้ที่ไม่มีพื้นฐานเขียนโปรแกรม เช่น `total = a + b;`

### จุดกำเนิด: ปี 1959

COBOL ถือกำเนิดขึ้นในปี **1959 (พ.ศ. 2502)** จากการประชุมของกลุ่ม **CODASYL** (Conference on Data Systems Languages)
ซึ่งเป็นการรวมตัวของตัวแทนจากหน่วยงานรัฐบาลสหรัฐฯ (กระทรวงกลาโหม) บริษัทเอกชน และมหาวิทยาลัย
โดยมีเป้าหมายเพื่อสร้างภาษาโปรแกรมมาตรฐานกลางที่ใช้ได้กับคอมพิวเตอร์หลายยี่ห้อ (Machine-independent)

บุคคลสำคัญที่มีอิทธิพลอย่างมากต่อการออกแบบ COBOL คือ **Grace Hopper** (เกรซ ฮอปเปอร์) นักวิทยาศาสตร์คอมพิวเตอร์
และเจ้าหน้าที่กองทัพเรือสหรัฐฯ ผู้บุกเบิกแนวคิดคอมไพเลอร์ (Compiler) และภาษาโปรแกรมที่ใกล้เคียงภาษามนุษย์
แนวคิดของเธอที่ว่า "โปรแกรมควรเขียนด้วยคำศัพท์ภาษาอังกฤษแทนสัญลักษณ์ทางคณิตศาสตร์" ได้กลายเป็นรากฐานสำคัญของ COBOL

### เส้นเวลาสำคัญของ COBOL

| ปี | เหตุการณ์สำคัญ |
|---|---|
| 1959 | ก่อตั้งกลุ่ม CODASYL และเริ่มออกแบบ COBOL |
| 1960 | เผยแพร่ COBOL-60 เวอร์ชันแรก |
| 1968 | มาตรฐาน ANSI COBOL ฉบับแรก (COBOL-68) |
| 1974 | ปรับปรุงเป็น COBOL-74 เพิ่มความสามารถด้านไฟล์ |
| 1985 | COBOL-85 เพิ่ม Structured Programming (PERFORM, END-IF ฯลฯ) |
| 1997 | COBOL กลายเป็นข่าวใหญ่ระดับโลกจากปัญหา **Y2K (Year 2000)** |
| 2002 | COBOL-2002 เพิ่ม Object-Oriented Programming |
| 2014 | COBOL-2014 เพิ่มการรองรับ XML, การจัดการหน่วยความจำแบบไดนามิก |
| 2020 | เกิดการขาดแคลนโปรแกรมเมอร์ COBOL อย่างรุนแรงช่วง COVID-19 (ระบบประกันการว่างงานของรัฐในสหรัฐฯ ล่ม) |
| 2026 | COBOL ยังคงเป็นแกนหลักของระบบการเงินโลก และมีการ Modernization ผ่าน Cloud/API อย่างต่อเนื่อง |

### แบบฝึกหัดที่ 1.1

**โจทย์**: จงอธิบายด้วยคำพูดของคุณเองว่าทำไม Grace Hopper จึงเชื่อว่าภาษาโปรแกรมควรมีลักษณะคล้ายภาษาอังกฤษ
และแนวคิดนี้ส่งผลต่อการออกแบบ COBOL อย่างไร

**เฉลยแนวทาง**: Grace Hopper มองว่าอุปสรรคสำคัญของการเขียนโปรแกรมคือคนทั่วไป (โดยเฉพาะผู้บริหารธุรกิจ)
ไม่สามารถอ่านโค้ดที่เป็นสัญลักษณ์คณิตศาสตร์ล้วนได้ การใช้คำศัพท์ภาษาอังกฤษทำให้ลดช่องว่างระหว่างทีมธุรกิจ
และทีมพัฒนา ส่งผลให้ COBOL ใช้คำสั่งเช่น `ADD`, `MOVE`, `PERFORM`, `IF...END-IF` แทนสัญลักษณ์ `+`, `=`, `{}` เป็นต้น

## ขั้นตอนที่ 2: ปัญหา Y2K และบทเรียนที่โลกได้เรียนรู้

### Y2K คืออะไร

ในยุคแรกของการเขียนโปรแกรม พื้นที่จัดเก็บข้อมูล (storage) มีราคาแพงมาก โปรแกรมเมอร์จึงนิยมเก็บปี ค.ศ.
ด้วยตัวเลข 2 หลักแทนที่จะเป็น 4 หลัก เช่น ปี 1975 เก็บเป็น `75` เพื่อประหยัดพื้นที่

ปัญหาเกิดขึ้นเมื่อใกล้ถึงปี 2000: ระบบจะตีความ `00` ว่าเป็นปี 1900 แทนที่จะเป็นปี 2000
ซึ่งอาจทำให้การคำนวณดอกเบี้ย อายุ หรือวันหมดอายุผิดพลาดอย่างมหาศาลในระบบธนาคาร ประกันภัย และรัฐบาล

### ทำไมเรื่องนี้ถึงเกี่ยวกับ COBOL โดยตรง

เนื่องจาก COBOL เป็นภาษาหลักที่ใช้เขียนระบบธุรกิจตั้งแต่ยุค 1960-1990 ระบบส่วนใหญ่ที่มีปัญหา Y2K
จึงเขียนด้วย COBOL ทำให้เกิดการระดมโปรแกรมเมอร์ COBOL ครั้งใหญ่ที่สุดในประวัติศาสตร์เพื่อแก้ไขโค้ดหลายพันล้านบรรทัด
ทั่วโลกในช่วงปี 1997–1999 คาดการณ์ว่ามีการใช้งบประมาณทั่วโลกกว่า **300,000-600,000 ล้านดอลลาร์สหรัฐ**
เพื่อแก้ไขปัญหานี้

### บทเรียนสำคัญ

1. **ระบบ COBOL Legacy อยู่ได้นานกว่าที่คาดไว้มาก** — หลายระบบที่เขียนในยุค 1970 ยังทำงานอยู่จนถึงปัจจุบัน (2026)
2. **การขาดแคลนบุคลากร COBOL เป็นความเสี่ยงระดับชาติ** — เมื่อโปรแกรมเมอร์รุ่นเก่าเกษียณ องค์กรจำนวนมากหาคนแทนไม่ได้
3. **นี่คือเหตุผลที่หลักสูตรนี้ยังมีความสำคัญ** — ทักษะ COBOL เป็นทักษะหายากที่มีมูลค่าตลาดสูงขึ้นเรื่อย ๆ

### แบบฝึกหัดที่ 2.1

**โจทย์**: หากปี ค.ศ. ถูกเก็บด้วยรูปแบบ PIC 99 (ตัวเลข 2 หลัก) จงเขียนตารางเปรียบเทียบว่าปี 1965, 1999, 2000, 2025
จะถูกเก็บเป็นค่าอะไร และปัญหาจะเกิดขึ้นตรงไหน

**เฉลย**:

| ปีจริง | ค่าที่เก็บ (PIC 99) | ปัญหาที่อาจเกิด |
|---|---|---|
| 1965 | 65 | ไม่มีปัญหาในยุคนั้น |
| 1999 | 99 | ไม่มีปัญหา |
| 2000 | 00 | ระบบตีความเป็น 1900 → คำนวณอายุ/ดอกเบี้ยผิดพลาด |
| 2025 | 25 | ระบบอาจตีความเป็น 1925 แทน 2025 → ข้อมูลผิดพลาดร้ายแรง |

## ขั้นตอนที่ 3: COBOL ในโลกปัจจุบัน (2026) — สถิติที่น่าตกใจ

หลายคนเข้าใจผิดว่า COBOL เป็นภาษา "ตาย" แล้ว แต่ความจริงคือ COBOL ยังคงเป็น **กระดูกสันหลังของระบบการเงินโลก**
ต่อไปนี้คือสถิติและข้อเท็จจริงที่แสดงให้เห็นถึงความสำคัญของ COBOL ในปัจจุบัน:

- มีการประมาณการว่ามีโค้ด COBOL ที่ใช้งานอยู่จริง (active) มากกว่า **800,000 ล้านบรรทัด** ทั่วโลก
- ประมาณ **43% ของระบบธนาคาร** ทั่วโลกยังคงใช้ COBOL เป็นแกนหลักในระบบ Core Banking
- ธุรกรรม ATM ทั่วโลกกว่า **95%** ยังคงประมวลผลผ่านระบบที่มีโค้ด COBOL อยู่เบื้องหลัง
- ธุรกรรมบัตรเครดิต/เดบิตกว่า **80%** ทั่วโลกเกี่ยวข้องกับระบบ COBOL ในบางจุดของกระบวนการ
- หน่วยงานรัฐบาลสหรัฐฯ จำนวนมาก (ประกันสังคม, กรมสรรพากร) ยังใช้ระบบ COBOL ที่มีอายุมากกว่า 40 ปี
- บริษัทประกันภัยและสถาบันการเงินรายใหญ่ทั่วโลกยังคงลงทุนพัฒนาและดูแลระบบ COBOL อย่างต่อเนื่อง

### ทำไมองค์กรถึงไม่เปลี่ยนไปใช้ภาษาอื่น

หลายคนสงสัยว่าทำไมองค์กรใหญ่ ๆ ไม่ Rewrite ระบบทั้งหมดเป็นภาษาสมัยใหม่ เหตุผลหลักคือ:

1. **ความเสี่ยงสูงเกินไป**: ระบบ COBOL เหล่านี้ผ่านการทดสอบและใช้งานจริงมานานหลายสิบปี การเขียนใหม่มีความเสี่ยง
   ที่จะเกิดบั๊กที่ไม่เคยเจอมาก่อนในระบบที่เกี่ยวกับเงินของลูกค้าหลายล้านคน
2. **ต้นทุนมหาศาล**: การ Rewrite ระบบขนาดหลายล้านบรรทัดอาจใช้เวลาหลายปีและงบประมาณหลายพันล้านบาท
3. **ประสิทธิภาพที่พิสูจน์แล้ว**: COBOL บน Mainframe สามารถประมวลผลธุรกรรมได้หลายพันล้านรายการต่อวัน
   ด้วยความเสถียรสูงมาก (Uptime 99.999%)
4. **แนวทางที่นิยมคือ Modernization ไม่ใช่ Replacement**: องค์กรส่วนใหญ่เลือกที่จะ "ห่อหุ้ม" (wrap) ระบบ COBOL เดิม
   ด้วย API สมัยใหม่ แทนที่จะเขียนใหม่ทั้งหมด (เนื้อหานี้จะสอนละเอียดใน เฟส 5 ของหลักสูตร)

### แบบฝึกหัดที่ 3.1

**โจทย์**: จงยกตัวอย่างอุตสาหกรรม 3 ประเภทที่คุณคิดว่ายังคงพึ่งพา COBOL อย่างหนัก พร้อมเหตุผล

**เฉลยแนวทาง**: (1) ธนาคาร — เพราะระบบ Core Banking ต้องการความแม่นยำและเสถียรภาพสูงสุด
(2) ประกันภัย — เพราะมีข้อมูลกรมธรรม์ระยะยาวหลายสิบปีที่เก็บในรูปแบบ COBOL มาตั้งแต่ต้น
(3) หน่วยงานรัฐบาล — เพราะงบประมาณจำกัดและความเสี่ยงทางการเมืองในการเปลี่ยนระบบที่กระทบประชาชนจำนวนมาก

### กรณีศึกษาจริง: ระบบที่ขับเคลื่อนด้วย COBOL

เพื่อให้เห็นภาพชัดเจนขึ้น ต่อไปนี้คือตัวอย่างระบบจริงที่มีรายงานว่าใช้ COBOL เป็นแกนหลัก
(ยกมาเพื่อประกอบความเข้าใจเชิงอุตสาหกรรม ไม่ใช่การอ้างอิงตัวเลขทางการเงินที่แม่นยำ):

- **ระบบประมวลผลเช็คและธุรกรรมระหว่างธนาคาร (Interbank Clearing Systems)** ในหลายประเทศยังคงมีโค้ด COBOL
  เป็นส่วนประกอบสำคัญของกระบวนการ Settlement รายวัน
- **ระบบประกันสังคมและบำนาญ** ของหลายประเทศ ซึ่งเก็บประวัติการจ่ายเงินสมทบของประชาชนย้อนหลังหลายสิบปี
  การย้ายข้อมูลออกจาก COBOL มีความเสี่ยงสูงมากจึงเลือกดูแลระบบเดิมต่อไป
- **ระบบสายการบินสำหรับการจองตั๋วและจัดการเที่ยวบิน** บางระบบมีองค์ประกอบ COBOL/Mainframe ทำงานร่วมกับ
  ระบบสมัยใหม่แบบผสมผสาน (Hybrid Architecture)
- **ระบบค้าปลีกขนาดใหญ่สำหรับจัดการสต๊อกสินค้าและห่วงโซ่อุปทาน** ที่ต้องประมวลผลแบบ Batch ปริมาณมหาศาลทุกคืน

ประเด็นสำคัญที่ควรจดจำคือ ระบบเหล่านี้ไม่ได้ "หยุดพัฒนา" แต่ยังคงมีการเพิ่มฟีเจอร์ใหม่ แก้ไขบั๊ก
และเชื่อมต่อกับเทคโนโลยีใหม่อย่างต่อเนื่อง เพียงแต่แกนหลัก (core) ยังคงเป็น COBOL เนื่องจากความเสถียร
ที่พิสูจน์มาแล้วหลายสิบปี

### แบบฝึกหัดที่ 3.2

**โจทย์**: ลองค้นคว้าเพิ่มเติม (จากประสบการณ์หรือข่าวที่เคยอ่าน) ว่ามีหน่วยงานหรือธุรกิจใดในประเทศของคุณ
ที่น่าจะยังใช้ระบบ Mainframe/COBOL อยู่ พร้อมให้เหตุผลประกอบ

**เฉลยแนวทาง**: คำตอบขึ้นกับบริบทของผู้เรียนแต่ละคน แต่โดยทั่วไปกลุ่มที่มักพบคือ ธนาคารพาณิชย์ขนาดใหญ่
ที่ก่อตั้งมานาน, หน่วยงานประกันสังคม/สรรพากรของภาครัฐ, และบริษัทประกันชีวิตที่มีกรมธรรม์ระยะยาว
เนื่องจากทั้งหมดนี้มีข้อมูลปริมาณมหาศาลที่สะสมมานาน และให้ความสำคัญกับความเสถียรของระบบเหนือสิ่งอื่นใด

## ขั้นตอนที่ 4: ภาพรวมตลาดงานและค่าตอบแทนของนักพัฒนา COBOL

### สถานการณ์อุปสงค์-อุปทาน (Demand-Supply Gap)

ในขณะที่ระบบ COBOL ยังคงทำงานอย่างต่อเนื่อง แต่จำนวนโปรแกรมเมอร์ที่มีทักษะ COBOL กลับลดลงอย่างต่อเนื่อง
เนื่องจาก:

- มหาวิทยาลัยส่วนใหญ่เลิกสอน COBOL ในหลักสูตรตั้งแต่ยุค 1990-2000 หันไปสอนภาษาสมัยใหม่แทน
- โปรแกรมเมอร์รุ่นที่เขียน COBOL มาตั้งแต่ยุค 1970-1980 กำลังทยอยเกษียณอายุ (Silver Tsunami)
- ภาพลักษณ์ของ COBOL ถูกมองว่า "เก่า" ทำให้คนรุ่นใหม่ไม่สนใจเรียนรู้

ผลลัพธ์คือเกิดช่องว่างขนาดใหญ่ระหว่างความต้องการ (สูงมาก) กับอุปทาน (น้อยลงเรื่อย ๆ) ซึ่งเป็น **โอกาสทอง**
สำหรับผู้ที่เรียนรู้ COBOL ในยุคนี้

### ลักษณะงานและตำแหน่งที่เกี่ยวข้องกับ COBOL

| ตำแหน่งงาน | หน้าที่หลัก |
|---|---|
| COBOL Application Developer | พัฒนาและดูแลโปรแกรม COBOL สำหรับระบบธุรกิจ |
| Mainframe Systems Programmer | ดูแลระบบปฏิบัติการ z/OS, JCL, การจัดการทรัพยากร Mainframe |
| Legacy System Modernization Engineer | เชื่อมต่อระบบ COBOL เดิมเข้ากับ API/Cloud สมัยใหม่ |
| COBOL/DB2 Database Developer | พัฒนาโปรแกรมที่เชื่อมต่อฐานข้อมูล DB2 ผ่าน Embedded SQL |
| CICS Application Programmer | พัฒนาโปรแกรมประมวลผลธุรกรรมแบบ Online ผ่าน CICS |
| Business Systems Analyst (COBOL background) | วิเคราะห์และออกแบบระบบธุรกิจโดยเข้าใจโค้ด Legacy |

### แนวโน้มค่าตอบแทน (ภาพรวมทั่วไป ไม่ผูกกับตัวเลขที่เปลี่ยนแปลงเร็ว)

โดยทั่วไป นักพัฒนา COBOL ที่มีประสบการณ์และความเชี่ยวชาญด้าน Mainframe/CICS/DB2 มักได้รับค่าตอบแทน
**สูงกว่าค่าเฉลี่ยของนักพัฒนาซอฟต์แวร์ทั่วไปในระดับประสบการณ์เดียวกัน** เนื่องจากความหายากของทักษะ
และความสำคัญเชิงธุรกิจของระบบที่ดูแล (ระบบที่หากล่มจะกระทบเงินหรือธุรกรรมมูลค่ามหาศาล)

### แบบฝึกหัดที่ 4.1

**โจทย์**: จงอธิบายแนวคิด "Silver Tsunami" ในบริบทของอุตสาหกรรม COBOL และเสนอแนวทาง 2 ข้อ
ที่องค์กรควรทำเพื่อรับมือกับปัญหานี้

**เฉลยแนวทาง**: Silver Tsunami หมายถึงคลื่นการเกษียณอายุครั้งใหญ่ของพนักงานรุ่นเบบี้บูมเมอร์ที่เป็นกำลังหลัก
ในการดูแลระบบ COBOL แนวทางรับมือ เช่น (1) จัดทำโปรแกรม Knowledge Transfer และ Mentorship ระหว่างรุ่น
(2) ลงทุนฝึกอบรมโปรแกรมเมอร์รุ่นใหม่ผ่านหลักสูตรเฉพาะทาง (เช่นหลักสูตรนี้)

## ขั้นตอนที่ 5: เปรียบเทียบ COBOL กับภาษาโปรแกรมยอดนิยมอื่น ๆ

การเข้าใจจุดแข็งจุดอ่อนของ COBOL เทียบกับภาษาอื่นจะช่วยให้เราวางตำแหน่งการเรียนรู้ได้ถูกต้อง

| คุณสมบัติ | COBOL | Java | Python |
|---|---|---|---|
| ปีที่ถือกำเนิด | 1959 | 1995 | 1991 |
| จุดเน้นหลัก | Business Data Processing | Enterprise Applications ทั่วไป | General-purpose, Data Science |
| ความสามารถด้าน Decimal Arithmetic | ยอดเยี่ยม (แม่นยำระดับสตางค์) | ต้องใช้ BigDecimal เพิ่มเติม | ต้องใช้ Decimal module เพิ่มเติม |
| Syntax | คล้ายภาษาอังกฤษ อ่านง่ายแต่ยาว | กระชับกว่า ต้องเรียนรู้ OOP | กระชับที่สุด |
| ความสามารถประมวลผลไฟล์/แบทช์ขนาดใหญ่ | ยอดเยี่ยม ออกแบบมาเพื่อสิ่งนี้โดยตรง | ต้องใช้ Framework เพิ่มเติม | ต้องใช้ Library เพิ่มเติม |
| นิยมใช้บน Mainframe | ใช่ (มาตรฐานอุตสาหกรรม) | บางส่วน | ไม่นิยม |
| ความสามารถ Web/API สมัยใหม่ | ต้องพึ่งพา Wrapper/Integration | รองรับโดยตรง (Spring Boot ฯลฯ) | รองรับโดยตรง (Flask/Django ฯลฯ) |

### ทำไม COBOL ถึงเก่งเรื่อง Decimal Arithmetic เป็นพิเศษ

จุดเด่นที่สำคัญที่สุดของ COBOL ที่ภาษาอื่นเลียนแบบได้ยากคือ **PICTURE Clause** ที่ให้เราระบุจำนวนหลักและตำแหน่งทศนิยม
ได้อย่างชัดเจนแม่นยำ 100% (Fixed-Point Decimal) ซึ่งสำคัญมากสำหรับงานการเงินที่ต้องการความแม่นยำระดับสตางค์
โดยไม่มีปัญหาการปัดเศษแบบ Floating-Point ที่พบในภาษาอื่น เช่น

```cobol
       01  AMOUNT-DUE          PIC 9(9)V99.
       01  INTEREST-RATE       PIC 9(2)V9(4).
```

โค้ดข้างต้นระบุว่า `AMOUNT-DUE` เก็บตัวเลข 9 หลักก่อนจุดทศนิยม และ 2 หลักหลังจุดทศนิยมอย่างชัดเจน
เราจะเรียนรู้เรื่อง PICTURE Clause แบบละเอียดใน Part 006

### แบบฝึกหัดที่ 5.1

**โจทย์**: เพราะเหตุใดการคำนวณดอกเบี้ยธนาคารจึงเหมาะกับ COBOL มากกว่าภาษาที่ใช้ Floating-Point เป็นค่าเริ่มต้น
เช่น JavaScript?

**เฉลยแนวทาง**: Floating-Point (เช่น `double` ใน JavaScript) มีข้อจำกัดเรื่องการเก็บค่าทศนิยมแบบไบนารี
ทำให้เกิดความคลาดเคลื่อนเล็กน้อย (rounding error) เช่น `0.1 + 0.2` อาจไม่เท่ากับ `0.3` พอดีในบางภาษา
ซึ่งไม่สามารถยอมรับได้ในงานการเงินที่ต้องแม่นยำทุกสตางค์ ในขณะที่ COBOL ใช้ Fixed-Point Decimal
ผ่าน PICTURE Clause ทำให้การคำนวณตัวเลขทศนิยมแม่นยำ 100% ตามจำนวนหลักที่กำหนดไว้

## ขั้นตอนที่ 6: มาตรฐาน COBOL ต่าง ๆ (COBOL-85, COBOL-2002, COBOL-2014)

COBOL ไม่ได้หยุดนิ่งตั้งแต่ปี 1959 แต่มีการปรับปรุงมาตรฐานอย่างต่อเนื่องผ่านองค์กร ANSI และ ISO
หลักสูตรนี้จะอ้างอิงมาตรฐานล่าสุด (COBOL-2014) เป็นหลัก แต่จะระบุเสมอเมื่อฟีเจอร์ใดมาจากมาตรฐานเก่าหรือใหม่

### COBOL-85 (มาตรฐานพื้นฐานที่องค์กรส่วนใหญ่ยังใช้)

เพิ่มแนวคิด **Structured Programming** ที่สำคัญมาก ได้แก่:
- `END-IF`, `END-PERFORM`, `END-EVALUATE` ฯลฯ (Scope Terminators) ทำให้โค้ดชัดเจนขึ้น ไม่ต้องพึ่ง period (`.`) เพียงอย่างเดียว
- คำสั่ง `EVALUATE` (เทียบเท่า switch-case)
- การปรับปรุง `PERFORM` ให้ยืดหยุ่นขึ้น

### COBOL-2002

เพิ่มความสามารถ **Object-Oriented Programming (OOP)** เช่น CLASS, METHOD, INHERITS
แต่ในทางปฏิบัติ องค์กรส่วนใหญ่ยังคงใช้ COBOL แบบ Procedural เป็นหลัก OOP ใน COBOL จึงเป็นความรู้เสริม
ที่ไม่ได้ใช้แพร่หลายเท่าฟีเจอร์อื่น

### COBOL-2014

เพิ่มความสามารถที่ตอบโจทย์โลกสมัยใหม่ เช่น:
- `JSON GENERATE` และ `JSON PARSE` — แปลงข้อมูล COBOL เป็น JSON และกลับกัน (สำคัญมากสำหรับการเชื่อมต่อ API)
- การจัดการหน่วยความจำแบบไดนามิก (Dynamic-length data items)
- การปรับปรุงฟังก์ชัน Intrinsic Functions ให้ครอบคลุมมากขึ้น

หลักสูตรนี้จะสอนทั้งฟีเจอร์คลาสสิก (ที่ต้องรู้เพื่อทำงานกับระบบ Legacy) และฟีเจอร์สมัยใหม่
(ที่จำเป็นสำหรับการทำ Modernization) ควบคู่กันไป

### แบบฝึกหัดที่ 6.1

**โจทย์**: หากคุณต้องเขียนโปรแกรม COBOL ที่ต้องส่งข้อมูลไปยัง REST API ภายนอก คุณคาดว่าจะต้องใช้ฟีเจอร์
จากมาตรฐานปีใดเป็นหลัก และเพราะเหตุใด

**เฉลย**: COBOL-2014 เนื่องจากมีคำสั่ง `JSON GENERATE` ที่ช่วยแปลงข้อมูลจาก Data Structure ของ COBOL
ให้เป็นรูปแบบ JSON ที่ REST API ส่วนใหญ่ใช้สื่อสารกันโดยตรง (จะสอนละเอียดใน Part 045)

## ขั้นตอนที่ 8: แนวคิดการเขียนโปรแกรมเชิงกระบวนการ (Procedural Programming) ที่ COBOL ยึดถือ

COBOL เป็นภาษาโปรแกรมแบบ **Procedural** (เชิงกระบวนการ) ซึ่งหมายความว่าโปรแกรมถูกมองเป็นลำดับของ
**คำสั่ง (Statements)** ที่ทำงานตามลำดับจากบนลงล่าง ต่างจากภาษาสมัยใหม่หลายภาษาที่เน้น Object-Oriented
หรือ Functional Programming เป็นหลัก

### แนวคิดหลัก 4 ประการของ Procedural Programming ใน COBOL

1. **ลำดับการทำงาน (Sequence)**: คำสั่งทำงานตามลำดับที่เขียนไว้ในโปรแกรม
2. **การเลือกทำ (Selection)**: ใช้ `IF...ELSE` หรือ `EVALUATE` เพื่อตัดสินใจ
3. **การทำซ้ำ (Iteration)**: ใช้ `PERFORM` เพื่อวนลูป
4. **การแบ่งโมดูล (Modularization)**: ใช้ `PARAGRAPH`, `SECTION`, และ `CALL` subprogram เพื่อแบ่งโปรแกรมใหญ่
   ให้เป็นส่วนย่อยที่จัดการง่าย

### โครงสร้าง 4 Divisions ที่เป็นหัวใจของทุกโปรแกรม COBOL

ทุกโปรแกรม COBOL จะถูกแบ่งออกเป็น 4 ส่วนหลักเสมอ (จะสอนละเอียดใน Part 003):

```cobol
       IDENTIFICATION DIVISION.     *> Program name and author
       ENVIRONMENT DIVISION.        *> Runtime environment, file connections
       DATA DIVISION.               *> All variables and data structures
       PROCEDURE DIVISION.          *> The program's actual logic (statements)
```

(หมายเหตุ: โค้ด COBOL ในหลักสูตรนี้ใช้คอมเมนต์เป็นภาษาอังกฤษเสมอ เหตุผลด้านเทคนิคจะอธิบายละเอียดใน Part 002)

การแบ่งส่วนที่ชัดเจนนี้ทำให้โปรแกรม COBOL แม้จะมีขนาดหลายพันหรือหลายหมื่นบรรทัด ก็ยังสามารถอ่านและบำรุงรักษาได้
เพราะเรารู้เสมอว่า "ถ้าจะหาตัวแปร ให้ไปดูที่ DATA DIVISION" และ "ถ้าจะหาตรรกะการทำงาน ให้ไปดูที่ PROCEDURE DIVISION"

### แบบฝึกหัดที่ 8.1

**โจทย์**: จงจับคู่แนวคิด Procedural Programming ทั้ง 4 ข้อ (Sequence, Selection, Iteration, Modularization)
กับคำสั่ง COBOL ที่เกี่ยวข้อง

**เฉลย**:
- Sequence → การเรียงลำดับคำสั่งตามปกติใน PROCEDURE DIVISION
- Selection → `IF...ELSE...END-IF`, `EVALUATE`
- Iteration → `PERFORM...UNTIL`, `PERFORM VARYING`
- Modularization → `PARAGRAPH`, `SECTION`, `PERFORM paragraph-name`, `CALL subprogram`

## ขั้นตอนที่ 9: ภาพรวมเส้นทางการเรียนรู้ของหลักสูตรนี้ (Learning Roadmap)

หลักสูตรนี้ถูกออกแบบเป็น **6 เฟส** ครอบคลุม **100 Part** และ **1000 ขั้นตอน (Steps)** ดังนี้
(รายละเอียดเต็มดูได้ที่ `docs/COURSE-OUTLINE.md`)

1. **เฟส 1 — พื้นฐาน (Parts 001–015, Steps 1–150)**: โครงสร้างโปรแกรม, ชนิดข้อมูล, เงื่อนไข, ลูป, I/O พื้นฐาน
   จบเฟสด้วยโปรเจกต์เครื่องคิดเลขและระบบเกรดนักเรียน
2. **เฟส 2 — ระดับกลาง (Parts 016–035, Steps 151–350)**: ตาราง, การจัดการไฟล์, Subprogram, การจัดการข้อความ
   จบเฟสด้วยโปรเจกต์ระบบจัดการสินค้าคงคลัง
3. **เฟส 3 — ขั้นสูง (Parts 036–050, Steps 351–500)**: Intrinsic Functions, Report Writer, JSON/XML, Error Handling
   จบเฟสด้วยโปรเจกต์ระบบบัญชีลูกหนี้
4. **เฟส 4 — Mainframe/Enterprise (Parts 051–070, Steps 501–700)**: JCL, VSAM, DB2, CICS, IMS
   จบเฟสด้วยโปรเจกต์ระบบธนาคารจำลอง
5. **เฟส 5 — COBOL สมัยใหม่ (Parts 071–085, Steps 701–850)**: REST API, Docker, Cloud, CI/CD, Testing
   จบเฟสด้วยโปรเจกต์ปรับปรุงระบบ Legacy
6. **เฟส 6 — ระดับมืออาชีพ/โลก (Parts 086–100, Steps 851–1000)**: สถาปัตยกรรมองค์กร, Case Study ธนาคาร/ประกันภัย/ERP,
   การเตรียมตัวสอบและสัมภาษณ์งาน, Capstone Project สุดท้าย

### หลักการสำคัญที่ใช้ตลอดหลักสูตร

- **เรียนแล้วต้องทำได้จริง**: ทุก Step มีโค้ดตัวอย่างที่รันได้จริงพร้อมผลลัพธ์
- **ค่อยเป็นค่อยไปแต่ไม่ช้าเกินไป**: แต่ละ Part มี 10 ขั้นตอนที่ต่อยอดกัน
- **มีโปรเจกต์รวบยอดทุกเฟส**: เพื่อฝึกประยุกต์ความรู้ให้เป็นระบบที่ใช้งานได้จริง ไม่ใช่แค่ตัวอย่างเดี่ยว ๆ
- **เชื่อมโยงสู่โลกการทำงานจริง**: ตั้งแต่เฟส 4 เป็นต้นไป เนื้อหาจะจำลองสถานการณ์งานจริงในองค์กร

### แบบฝึกหัดที่ 9.1

**โจทย์**: จากเป้าหมายการเรียนรู้ของคุณเอง (เช่น อยากทำงานสาย Mainframe, อยากเข้าใจระบบธนาคาร,
อยากทำ Modernization) จงระบุว่าคุณควรให้ความสำคัญกับเฟสใดเป็นพิเศษ

**เฉลยแนวทาง**: ไม่มีคำตอบตายตัว ขึ้นกับเป้าหมายผู้เรียน เช่น หากสนใจสาย Mainframe Systems Programmer
ควรเน้นเฟส 4 เป็นพิเศษ หากสนใจสาย Modernization/Integration ควรเน้นเฟส 5 แต่ทุกเฟสควรเรียนต่อเนื่องกัน
เพราะแต่ละเฟสต่อยอดความรู้จากเฟสก่อนหน้า

## ขั้นตอนที่ 10: เตรียมความพร้อมก่อนเริ่มเรียน (Mindset และวิธีฝึกฝนที่มีประสิทธิภาพ)

### 5 หลักการฝึกฝนที่จะทำให้คุณเรียนหลักสูตรนี้ได้ผลที่สุด

1. **ลงมือพิมพ์โค้ดเองทุกตัวอย่าง อย่า Copy-Paste** — การพิมพ์เองช่วยให้กล้ามเนื้อความจำ (muscle memory)
   จดจำ Syntax ได้ดีกว่าการอ่านผ่าน ๆ มาก
2. **รันโค้ดทุกตัวอย่างจริงบนเครื่องของคุณ** — อย่าเชื่อแค่ผลลัพธ์ในเอกสาร ให้ทดลองแก้ไขค่าต่าง ๆ ดูว่าผลลัพธ์เปลี่ยนไปอย่างไร
3. **ทำแบบฝึกหัดก่อนดูเฉลยเสมอ** — แม้จะทำผิดก็มีค่ามากกว่าการอ่านเฉลยโดยไม่ได้คิดเอง
4. **อย่ากลัวข้อความ Error** — การเขียนโปรแกรม COBOL (เหมือนภาษาอื่น) จะเจอ Compile Error บ่อยมากในช่วงแรก
   ให้มองเป็นส่วนหนึ่งของกระบวนการเรียนรู้ ไม่ใช่สัญญาณว่าคุณทำไม่ได้
5. **ทำโปรเจกต์รวบยอดทุกเฟสให้จบ** — โปรเจกต์เหล่านี้คือบทพิสูจน์ว่าคุณเข้าใจเนื้อหาจริง ไม่ใช่แค่จำ Syntax ได้

### สิ่งที่ควรเตรียมก่อนเข้า Part 002

- เครื่องคอมพิวเตอร์ที่มีสิทธิ์ติดตั้งซอฟต์แวร์ (Admin/sudo access)
- พื้นที่ว่างในฮาร์ดดิสก์อย่างน้อย 2 GB สำหรับเครื่องมือพัฒนา
- การเชื่อมต่ออินเทอร์เน็ตสำหรับดาวน์โหลด GnuCOBOL และ VS Code
- สมุดจดหรือไฟล์บันทึกสำหรับจดคำถามและข้อสังเกตระหว่างเรียน

### แบบฝึกหัดที่ 10.1 (แบบฝึกหัดเตรียมความพร้อม)

**โจทย์**: ก่อนไป Part 002 ให้คุณตั้งเป้าหมายการเรียนรู้ของตัวเองเป็นข้อความสั้น ๆ 1 ประโยค เช่น
"ฉันต้องการเรียนรู้ COBOL เพื่อ..." และเขียนกำหนดเวลาคร่าว ๆ ว่าคุณจะเรียนสัปดาห์ละกี่ Part

Developer ภายใน 6 เดือน และจะเรียนสัปดาห์ละ 3-4 Part" การตั้งเป้าหมายที่ชัดเจนจะช่วยให้คุณ
มีแรงจูงใจต่อเนื่องตลอดหลักสูตรที่มีเนื้อหาจำนวนมากนี้

## อภิธานศัพท์ที่ใช้บ่อยตลอดหลักสูตร (Glossary)

เนื่องจากหลักสูตรนี้จะใช้ศัพท์เทคนิคเฉพาะทางจำนวนมาก ต่อไปนี้คือคำศัพท์พื้นฐานที่ควรทำความคุ้นเคยไว้ตั้งแต่ต้น
(จะอธิบายเพิ่มเติมอย่างละเอียดเมื่อถึง Part ที่เกี่ยวข้อง):

| คำศัพท์ | ความหมายโดยสรุป |
|---|---|
| **Mainframe** | คอมพิวเตอร์ขนาดใหญ่ที่องค์กรใช้ประมวลผลธุรกรรมปริมาณมหาศาล เน้นความเสถียรและความปลอดภัยสูงสุด |
| **z/OS** | ระบบปฏิบัติการหลักที่ใช้บน IBM Mainframe |
| **JCL (Job Control Language)** | ภาษาที่ใช้สั่งให้ Mainframe รันโปรแกรม COBOL แบบ Batch (สอนใน Part 052-053) |
| **VSAM** | รูปแบบการจัดเก็บไฟล์ประสิทธิภาพสูงบน Mainframe (สอนใน Part 055-056) |
| **CICS** | ระบบประมวลผลธุรกรรมออนไลน์แบบ Real-time บน Mainframe (สอนใน Part 061-064) |
| **DB2** | ระบบฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ยอดนิยมของ IBM ที่ใช้ร่วมกับ COBOL (สอนใน Part 057-060) |
| **Batch Processing** | การประมวลผลข้อมูลจำนวนมากพร้อมกันเป็นชุด (เช่น ประมวลผลตอนกลางคืน) ตรงข้ามกับ Online/Real-time |
| **Copybook** | ไฟล์ที่เก็บโครงสร้างข้อมูลหรือโค้ดที่ใช้ร่วมกันหลายโปรแกรม ผ่านคำสั่ง `COPY` (สอนใน Part 033) |
| **Legacy System** | ระบบเก่าที่ยังใช้งานอยู่ในองค์กร มักหมายถึงระบบ COBOL/Mainframe ในบริบทนี้ |
| **Modernization** | กระบวนการปรับปรุงระบบเก่าให้ทำงานร่วมกับเทคโนโลยีสมัยใหม่ได้ โดยไม่จำเป็นต้องเขียนใหม่ทั้งหมด |
| **GnuCOBOL** | คอมไพเลอร์ COBOL แบบ Open Source ที่ใช้เป็นเครื่องมือหลักในหลักสูตรนี้ |
| **PICTURE Clause (PIC)** | ส่วนของโค้ดที่กำหนดรูปแบบและชนิดข้อมูลของตัวแปรใน COBOL (สอนใน Part 006) |
| **Working-Storage Section** | ส่วนของ DATA DIVISION ที่ใช้ประกาศตัวแปรที่ใช้ระหว่างโปรแกรมทำงาน (สอนใน Part 005) |

## สรุปท้ายบท

ใน Part นี้ เราได้ทำความรู้จักกับ COBOL ในภาพรวม ได้แก่:

- ประวัติศาสตร์การถือกำเนิดของ COBOL ในปี 1959 และบทบาทของ Grace Hopper
- ปัญหา Y2K และบทเรียนสำคัญที่แสดงถึงความสำคัญระยะยาวของ COBOL
- สถิติที่แสดงว่า COBOL ยังคงเป็นแกนหลักของระบบการเงินโลกในปี 2026
- ภาพรวมตลาดงานและโอกาสของนักพัฒนา COBOL ในยุคที่ขาดแคลนบุคลากร
- การเปรียบเทียบ COBOL กับภาษาโปรแกรมอื่น โดยเฉพาะจุดแข็งด้าน Decimal Arithmetic
- มาตรฐาน COBOL ต่าง ๆ ตั้งแต่ COBOL-85 ถึง COBOL-2014
- ระบบนิเวศเครื่องมือ COBOL และเหตุผลที่หลักสูตรนี้เลือกใช้ GnuCOBOL
- แนวคิด Procedural Programming ที่เป็นหัวใจของ COBOL
- ภาพรวมเส้นทางการเรียนรู้ทั้ง 6 เฟสของหลักสูตร
- Mindset และวิธีฝึกฝนที่จะทำให้การเรียนรู้ได้ผลที่สุด

ตอนนี้คุณมีบริบทและแรงจูงใจที่ชัดเจนแล้วว่าทำไม COBOL ยังคงสำคัญ และหลักสูตรนี้จะพาคุณไปถึงจุดไหน
ใน **Part 002** เราจะเริ่มลงมือจริง: ติดตั้ง GnuCOBOL, ตั้งค่า VS Code, และเขียน-คอมไพล์-รันโปรแกรม COBOL
