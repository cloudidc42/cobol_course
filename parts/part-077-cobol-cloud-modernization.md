# Part 077: COBOL บน Cloud: แนวคิด Mainframe Modernization (ขั้นตอนที่ 761–770)

## คำนำของ Part นี้

Part 073-076 พาเราลงมือสร้างระบบจริงทีละชิ้น: Wrapper Service, Web Integration, Database Shim,
และ Container — ทั้งหมดคือ**เทคนิคระดับโปรแกรม (program-level techniques)** ที่ใช้เชื่อมโปรแกรม
COBOL เดี่ยว ๆ เข้ากับโลกสมัยใหม่ Part นี้จะยกระดับมุมมองขึ้นไปอีกขั้น จากคำถามระดับโปรแกรม
("จะเชื่อมโปรแกรมนี้กับเว็บ/ฐานข้อมูลอย่างไร") ไปสู่คำถามระดับองค์กร (enterprise-level):
**"จะย้ายระบบ Mainframe ทั้งองค์กรที่มีโค้ด COBOL หลายล้านบรรทัด สะสมมาหลายสิบปี ไปสู่ Cloud
ได้อย่างไร โดยไม่ทำให้ธุรกิจหยุดชะงัก"**

นี่คือคำถามที่ธนาคาร บริษัทประกันภัย และหน่วยงานรัฐทั่วโลกกำลังเผชิญอยู่จริงในปี 2026 (ตามที่กล่าวถึง
ภาพรวมไว้ตั้งแต่ Part 001) Part นี้เป็น **Part เชิงแนวคิดและกลยุทธ์ (Conceptual/Strategic Part)**
เป็นหลัก แตกต่างจาก Part 073-076 ที่เน้นโค้ดที่รันได้จริง เพราะการโยกย้ายระบบ Mainframe ระดับองค์กร
เกี่ยวข้องกับบริการ Cloud เชิงพาณิชย์ (AWS Mainframe Modernization, Micro Focus Enterprise
Server) ที่ต้องมีบัญชีและค่าใช้จ่ายจริงในการทดสอบ ซึ่งอยู่นอกขอบเขตของสภาพแวดล้อมหลักสูตรนี้ — เรา
จะซื่อตรงกับข้อจำกัดนี้ตลอด Part และเน้นให้ตัวอย่างโค้ด/configuration ที่แสดงไว้เป็นภาพประกอบความ
เข้าใจเชิงสถาปัตยกรรม พร้อมระบุชัดเจนว่าส่วนใดคือไวยากรณ์มาตรฐานที่ยังไม่ได้ทดสอบรันจริง

เนื้อหานี้จะปูพื้นฐานสำคัญให้กับ **Part 084 (Migration Strategies: COBOL to Java/C#)** ที่จะ

## ขั้นตอนที่ 761: ทำไมองค์กรถึงอยากย้าย Mainframe ไป Cloud — แรงจูงใจทางธุรกิจ

### ต้นทุนของการรัน Mainframe แบบดั้งเดิม

ทบทวนจาก Part 051: Mainframe คือคอมพิวเตอร์ขนาดใหญ่ที่มีความเสถียรสูงมาก แต่มาพร้อมต้นทุนที่สูง
เช่นกัน:

- **ค่า MIPS/MSU License**: ซอฟต์แวร์บน Mainframe (รวมถึงบางส่วนของระบบปฏิบัติการ z/OS เอง) มัก
  คิดค่าใช้จ่ายตามปริมาณการประมวลผล (MIPS - Million Instructions Per Second หรือ MSU) ทำให้ยิ่ง
  ใช้งานมากยิ่งเสียค่าใช้จ่ายสูงขึ้นแบบไม่เป็นเชิงเส้น (non-linear) ในบางกรณี
- **ค่าบำรุงรักษาฮาร์ดแวร์**: เครื่อง Mainframe จริงมีราคาสูงมากและต้องการทีมผู้เชี่ยวชาญเฉพาะทาง
  ดูแล
- **ต้นทุนบุคลากรที่หายากขึ้นเรื่อย ๆ**: ตามที่กล่าวถึงใน Part 001 ขั้นตอนที่ 4 เรื่อง "Silver
  Tsunami" — ผู้เชี่ยวชาญ Mainframe รุ่นเก่าทยอยเกษียณ ทำให้ต้นทุนการจ้างงานและ training สูงขึ้น

### ความยืดหยุ่นที่ Cloud มอบให้

ตรงข้ามกับ Mainframe แบบดั้งเดิมที่ต้องซื้อฮาร์ดแวร์ล่วงหน้าตามความจุสูงสุดที่คาดว่าจะต้องใช้
Cloud Computing มอบความสามารถ **Elastic Scaling** (ขยาย/หดทรัพยากรตามความต้องการจริงแบบอัตโนมัติ)
และรูปแบบการจ่ายเงินแบบ **Pay-as-you-go** (จ่ายตามที่ใช้จริง) ทำให้องค์กรไม่ต้องลงทุนก้อนใหญ่
ล่วงหน้าเพื่อรองรับ peak load ที่อาจเกิดขึ้นเพียงไม่กี่วันต่อปี (เช่น ช่วงสิ้นเดือนที่ระบบบัญชี
ต้องประมวลผลหนักเป็นพิเศษ)

### แรงจูงใจที่ไม่ใช่แค่เรื่องต้นทุน

- **ความเร็วในการพัฒนาฟีเจอร์ใหม่**: ระบบบน Cloud มักเชื่อมต่อกับเครื่องมือ DevOps สมัยใหม่ (CI/CD
  ที่จะสอนใน Part 078) ได้ง่ายกว่า ทำให้ออกฟีเจอร์ใหม่ได้เร็วขึ้น
- **การสรรหาบุคลากรง่ายขึ้น**: วิศวกรรุ่นใหม่คุ้นเคยกับ Cloud มากกว่า Mainframe แบบดั้งเดิม การ
  ย้ายระบบบางส่วนไป Cloud ช่วยลดการพึ่งพาผู้เชี่ยวชาญ Mainframe ที่หายากลงเรื่อย ๆ
- **ข้อกำหนดด้านกฎระเบียบที่เปลี่ยนไป**: บางประเทศ/อุตสาหกรรมเริ่มมีนโยบายสนับสนุนหรือกำหนดให้
  ใช้โครงสร้างพื้นฐานที่ทันสมัยขึ้นสำหรับบริการสาธารณะบางประเภท

### ข้อควรระวัง — Cloud ไม่ใช่คำตอบสำหรับทุกสถานการณ์

- **สำคัญมาก**: การย้ายไป Cloud ไม่ได้แปลว่าดีกว่าเสมอไป ระบบที่มีปริมาณธุรกรรมสูงมากและเสถียรภาพ
  คือสิ่งสำคัญที่สุด (เช่น ระบบ Core Banking แบบ Real-time) อาจยังคงได้ประโยชน์จากสถาปัตยกรรม
  Mainframe ดั้งเดิมมากกว่า การตัดสินใจต้องพิจารณาจากบริบทจริงขององค์กร ไม่ใช่ตามกระแสความนิยม
  (หลักการเดียวกับที่เตือนไว้ใน Part 074 ขั้นตอนที่ 739 เรื่อง Indexed File กับฐานข้อมูลสมัยใหม่)
- การย้ายระบบที่มีความเสี่ยงสูง (เช่น ระบบที่กระทบเงินของลูกค้าโดยตรง) ต้องวางแผนอย่างรอบคอบมาก
  และมักใช้เวลาหลายปี ไม่ใช่โครงการที่ทำเสร็จได้ในไม่กี่เดือน

### แบบฝึกหัดที่ 761.1

**โจทย์**: จงยกตัวอย่างระบบ 1 ประเภทที่คุณคิดว่า **ไม่ควร** รีบย้ายไป Cloud ทั้งหมดในทันที พร้อม
เหตุผลประกอบ

**เฉลยแนวทาง**: ระบบ Clearing/Settlement ระหว่างธนาคารกลาง (Interbank Clearing System ที่กล่าวถึง
ใน Part 001 ขั้นตอนที่ 3) เพราะระบบนี้ต้องการความเสถียรและความแม่นยำระดับสูงสุด ทำงานตลอด 24 ชั่วโมง
โดยแทบไม่มีช่องว่างให้ downtime และมีกฎระเบียบทางการเงินที่เข้มงวดมากกำกับดูแลอยู่ การย้ายระบบเช่นนี้
ไป Cloud ทั้งหมดในทันทีมีความเสี่ยงสูงมากทั้งด้านเทคนิคและกฎระเบียบ องค์กรส่วนใหญ่จึงเลือกใช้แนวทาง
ค่อยเป็นค่อยไป (ตามที่จะเรียนในขั้นตอนที่ 764 เรื่อง Strangler Fig Pattern) แทนการย้ายทั้งระบบทันที

## ขั้นตอนที่ 762: AWS Mainframe Modernization — ภาพรวมบริการ

### AWS Mainframe Modernization คืออะไร

**AWS Mainframe Modernization** คือชุดบริการของ Amazon Web Services ที่ออกแบบมาเฉพาะเพื่อช่วย
องค์กรย้ายระบบ Mainframe (รวมถึงโปรแกรม COBOL) ไปทำงานบน AWS Cloud โดยมีแนวทางหลัก 2 แบบให้เลือก:

1. **Replatform (Automated Refactoring)**: แปลงโค้ด COBOL ให้คอมไพล์และรันบน AWS ได้โดยตรง
   ผ่าน runtime environment ที่ AWS จัดเตรียมไว้ (เช่น Blu Age หรือ Micro Focus ที่ AWS ผูกเข้ากับ
   บริการของตน) โดย**เปลี่ยนแปลงโค้ด COBOL เดิมน้อยที่สุดเท่าที่จะทำได้**
2. **Refactor (Automated Code Conversion)**: แปลงโค้ด COBOL เป็นภาษาสมัยใหม่โดยอัตโนมัติ (เช่น
   Java) ผ่านเครื่องมือแปลงโค้ดอัตโนมัติ (automated transformation tooling) — แนวทางนี้เปลี่ยน
   แปลงมากกว่าและมักต้องการการตรวจสอบ (validation) อย่างละเอียดหลังแปลง เนื้อหานี้จะเจาะลึกกลยุทธ์
   การแปลงโค้ดเต็มรูปแบบใน **Part 084**

### สถาปัตยกรรมแนวคิด (ภาพประกอบ — ไม่ใช่ configuration ที่ทดสอบรันจริง)

```
[ Mainframe เดิม: z/OS, COBOL, JCL, VSAM, CICS, DB2 ]
                    |
                    | AWS Mainframe Modernization service
                    | (Replatform: runtime environment
                    |  ที่รองรับ COBOL/JCL โดยตรงบน AWS)
                    v
[ AWS Cloud: COBOL runtime บน EC2/ECS, ข้อมูลย้ายไป Aurora/RDS,
  Batch job จัดการผ่าน AWS Batch แทน JCL Scheduler เดิม ]
```

### เมื่อไหร่ควรเลือก Replatform เทียบกับ Refactor

| ปัจจัย | Replatform (คง COBOL ไว้) | Refactor (แปลงเป็นภาษาใหม่) |
|---|---|---|
| ความเร็วในการย้ายระบบ | เร็วกว่า (เปลี่ยนโค้ดน้อย) | ช้ากว่า (ต้องแปลงและทดสอบโค้ดใหม่ทั้งหมด) |
| ความเสี่ยงระหว่างย้าย | ต่ำกว่า (logic เดิมยังคงอยู่) | สูงกว่า (โค้ดที่แปลงอัตโนมัติอาจมีพฤติกรรมคลาดเคลื่อนเล็กน้อย) |
| ความสามารถดึงดูดนักพัฒนารุ่นใหม่ | น้อยกว่า (ยังคงต้องมีทักษะ COBOL) | มากกว่า (ทีมพัฒนาใช้ภาษาสมัยใหม่ได้เต็มที่) |
| ต้นทุนระยะสั้น | ต่ำกว่า | สูงกว่า |
| ความยืดหยุ่นระยะยาว | น้อยกว่า (ยังผูกกับ COBOL ecosystem) | มากกว่า (เข้าถึง ecosystem ภาษาสมัยใหม่เต็มรูปแบบ) |

### ข้อควรระวัง

- **สำคัญมาก**: หลักสูตรนี้ไม่มีบัญชี AWS หรือสภาพแวดล้อมที่จะทดสอบบริการ AWS Mainframe
  Modernization จริงได้ เนื้อหาในขั้นตอนนี้เป็น**ภาพรวมเชิงแนวคิดของบริการที่มีอยู่จริงในตลาด**
  (ข้อมูลอ้างอิงจากเอกสารสาธารณะของ AWS) ไม่ใช่การสาธิตการใช้งานจริง หากต้องนำไปใช้งานจริงควรศึกษา
  เอกสารทางการล่าสุดของ AWS ประกอบเสมอ เนื่องจากรายละเอียดบริการ Cloud มีการเปลี่ยนแปลงบ่อยกว่า
  มาตรฐานภาษา COBOL มาก
- อย่าตัดสินใจเลือก Replatform หรือ Refactor จากตารางเปรียบเทียบข้างต้นเพียงอย่างเดียว — ต้อง
  ประเมินร่วมกับปัจจัยเฉพาะขององค์กร เช่น ขนาดของ codebase, ความซับซ้อนของ business logic, และ
  งบประมาณที่มี

### แบบฝึกหัดที่ 762.1

**โจทย์**: จงอธิบายว่าทำไมแนวทาง Replatform จึงมีความเสี่ยงต่ำกว่า Refactor ในแง่ของ "ความถูกต้อง
ของ business logic เดิม"

**เฉลย**: Replatform เปลี่ยนแค่**สภาพแวดล้อมที่โปรแกรมทำงาน** (จาก Mainframe เป็น Cloud) โดยยังคง
ใช้โค้ด COBOL ต้นฉบับเดิม (หรือเปลี่ยนแปลงเพียงเล็กน้อยเท่าที่จำเป็นสำหรับ runtime ใหม่) ทำให้
business logic ที่ผ่านการทดสอบและใช้งานจริงมานานหลายปียังคงเดิมทุกประการ ความเสี่ยงที่จะเกิดบั๊ก
ใหม่จึงต่ำ ในขณะที่ Refactor คือการ**เขียนโค้ดใหม่ทั้งหมดในภาษาอื่น** (แม้จะทำผ่านเครื่องมืออัตโนมัติ
ก็ตาม) กระบวนการแปลงภาษาอาจตีความ edge case บางอย่างของ COBOL (เช่น พฤติกรรมการปัดเศษของ
`COMPUTE` ที่พิสูจน์ไว้ใน Part 073 ขั้นตอนที่ 723 หรือกฎ MOVE ที่ซับซ้อนจาก Part 008) ผิดเพี้ยนไป
จากต้นฉบับโดยไม่รู้ตัว จึงต้องผ่านการทดสอบเปรียบเทียบผลลัพธ์ (regression testing) อย่างละเอียดมาก
กว่าเพื่อยืนยันว่า logic ใหม่ให้ผลลัพธ์เหมือนเดิมทุกกรณี

## ขั้นตอนที่ 763: Micro Focus Enterprise Server บน Cloud

### Micro Focus Enterprise Server คืออะไร

ทบทวนจาก Part 001 ขั้นตอนที่ 7: **Micro Focus** (ปัจจุบันเป็นส่วนหนึ่งของ OpenText) คือหนึ่งใน
ผู้ผลิตคอมไพเลอร์ COBOL เชิงพาณิชย์รายใหญ่ นอกจากคอมไพเลอร์แล้ว Micro Focus ยังมีผลิตภัณฑ์
**Enterprise Server** ที่จำลองสภาพแวดล้อมการรัน COBOL/CICS/batch แบบ Mainframe ให้ทำงานบน
เซิร์ฟเวอร์ Windows/Linux ทั่วไปได้ — และสามารถ deploy บน Cloud (AWS, Azure, Google Cloud) ได้
เช่นกัน

### ความแตกต่างจากแนวทาง AWS Mainframe Modernization

| ประเด็น | Micro Focus Enterprise Server | AWS Mainframe Modernization |
|---|---|---|
| ผู้ให้บริการ | OpenText/Micro Focus (เป็นกลาง ไม่ผูกกับ Cloud provider ใดโดยเฉพาะ) | Amazon Web Services (ผูกกับ AWS ecosystem) |
| ความยืดหยุ่นด้าน Cloud provider | Deploy ได้หลาย Cloud (AWS, Azure, GCP) หรือแม้แต่ on-premise | เน้น AWS เป็นหลัก |
| การรองรับ CICS/IMS | รองรับ CICS emulation ในตัวผลิตภัณฑ์เอง | ใช้บริการ AWS ร่วมกับ partner tooling |
| รูปแบบธุรกิจ | License แบบซอฟต์แวร์ดั้งเดิม (มักมีค่า license ต่อ core/MIPS) | รูปแบบ pay-as-you-go ของ AWS |

```
[ โค้ด COBOL เดิม (อาจต้องปรับแก้เล็กน้อยสำหรับ dialect compatibility) ]
                    |
                    v
[ Micro Focus Enterprise Server รันบน VM/Container บน Cloud ใดก็ได้ ]
        - จำลอง CICS Transaction Processing
        - จำลอง JCL Batch Scheduling
        - เชื่อมต่อฐานข้อมูลสมัยใหม่ผ่าน adapter ที่ผลิตภัณฑ์เตรียมไว้ให้
```

### จุดแข็งของแนวทางนี้สำหรับองค์กรที่มีระบบ CICS ซับซ้อน

องค์กรที่มีระบบ CICS ที่ซับซ้อนมาก (ทบทวนจาก Part 061-064: BMS Maps, Pseudo-conversational
Programming) มักพบว่าการย้ายไปสู่ runtime ที่ยังคง "เข้าใจ" แนวคิด CICS อยู่แล้ว (อย่าง Micro
Focus Enterprise Server) ทำได้ราบรื่นกว่าการพยายามเขียนใหม่ทั้งหมดด้วยสถาปัตยกรรมเว็บสมัยใหม่
ตั้งแต่ต้น เพราะโปรแกรมเมอร์ COBOL/CICS เดิมยังสามารถทำงานกับระบบได้โดยใช้ความรู้เดิมเป็นส่วนใหญ่

### ข้อควรระวัง

- เช่นเดียวกับ AWS Mainframe Modernization ในขั้นตอนก่อนหน้า **หลักสูตรนี้ไม่มี license หรือ
  สภาพแวดล้อมที่จะทดสอบ Micro Focus Enterprise Server จริงได้** เนื้อหาส่วนนี้เป็นภาพรวมเชิง
  แนวคิดจากข้อมูลสาธารณะของผลิตภัณฑ์ ไม่ใช่การสาธิตจริง
- การเลือกผลิตภัณฑ์เชิงพาณิชย์ใด ๆ (AWS Mainframe Modernization, Micro Focus Enterprise Server,
  หรือผลิตภัณฑ์อื่น) ควรผ่านกระบวนการประเมิน (vendor evaluation) อย่างละเอียดโดยทีมสถาปัตยกรรม
  ขององค์กร ไม่ใช่การตัดสินใจจากเนื้อหาการศึกษาเพียงอย่างเดียว

### แบบฝึกหัดที่ 763.1

**โจทย์**: จงอธิบายว่าทำไมองค์กรที่มีระบบ CICS ที่ซับซ้อนมาก (BMS Maps จำนวนมาก, Pseudo-
conversational program หลายร้อยตัว) จึงอาจพิจารณา Micro Focus Enterprise Server มากกว่าการ
Refactor เป็น Java ทั้งหมดในทันที

**เฉลยแนวทาง**: ระบบ CICS ที่ซับซ้อนมักมี business logic ที่พันเกี่ยวกับแนวคิดเฉพาะของ CICS อย่าง
ลึกซึ้ง (เช่น Pseudo-conversational programming ที่เรียนใน Part 064 ซึ่งมีรูปแบบการจัดการ state
ที่ต่างจากโปรแกรมเว็บสมัยใหม่โดยสิ้นเชิง) การ Refactor เป็น Java ทั้งหมดในทันทีต้องตีความและแปลง
แนวคิดเหล่านี้ใหม่ทั้งหมด ซึ่งมีความเสี่ยงสูงมากที่จะตีความผิดพลาดในหลายจุดพร้อมกัน ในขณะที่ Micro
Focus Enterprise Server ยังคงรองรับแนวคิด CICS ดั้งเดิมไว้ (แค่เปลี่ยนที่ที่มันทำงาน จาก Mainframe
จริงเป็น Cloud) ทำให้ทีมเดิมที่เข้าใจ CICS อยู่แล้วยังคงดูแลระบบต่อได้ ลดความเสี่ยงของการย้ายระบบ
ลงอย่างมาก แม้จะยังไม่ได้ประโยชน์เต็มที่จากการใช้ภาษาสมัยใหม่ก็ตาม — เป็นทางเลือกที่เหมาะกับองค์กร
ที่ต้องการลดความเสี่ยงมากกว่าความเร็วในการปรับปรุงระบบ

## ขั้นตอนที่ 764: Strangler Fig Pattern — กลยุทธ์การโยกย้ายระบบแบบค่อยเป็นค่อยไป

### ที่มาของชื่อ Strangler Fig

**Strangler Fig Pattern** ตั้งชื่อตามต้นไทรพันธุ์หนึ่ง (Strangler Fig) ที่เติบโตโดยการพันรอบต้นไม้
เจ้าบ้าน (host tree) อย่างช้า ๆ จนในที่สุดต้นไม้เจ้าบ้านตายและเหลือแต่ต้นไทรที่ยืนต้นแทนที่ — แนวคิด
ทางสถาปัตยกรรมซอฟต์แวร์นี้ถูกเสนอโดย Martin Fowler เพื่ออธิบายกลยุทธ์การแทนที่ระบบเก่าด้วยระบบใหม่
**ทีละส่วนอย่างค่อยเป็นค่อยไป** แทนที่จะ "Rewrite ทั้งหมดในคราวเดียว" (Big Bang Rewrite) ที่มีความ
เสี่ยงสูงมาก

### ทำไม Big Bang Rewrite ถึงอันตรายสำหรับระบบ COBOL ขนาดใหญ่

ทบทวนเหตุผลจาก Part 001 ขั้นตอนที่ 3: ระบบ COBOL องค์กรขนาดใหญ่มักมีโค้ดหลายล้านบรรทัดที่สะสม
business rule มานานหลายสิบปี (รวมถึง edge case ที่ไม่มีใครจดจำเหตุผลได้แล้วว่าทำไมต้องมี) การพยายาม
เขียนใหม่ทั้งหมดในคราวเดียวแล้วเปิดใช้งานระบบใหม่แทนที่ระบบเก่าทันที มีความเสี่ยงสูงมากที่จะพลาด
business rule สำคัญบางอย่างไป และเมื่อพบปัญหาหลัง deploy จริงแล้ว การย้อนกลับ (rollback) ไปใช้
ระบบเก่าอาจทำได้ยากหรือเป็นไปไม่ได้เลยหากมีการเปลี่ยนแปลงข้อมูลไปมากแล้ว

### แนวคิดการทำงานของ Strangler Fig Pattern

```
ขั้นที่ 1: ระบบเก่า (COBOL) รับ request ทั้งหมด 100%
[ Client ] ---> [ Router/Facade ] ---> [ ระบบ COBOL เดิมทั้งหมด ]

ขั้นที่ 2: เริ่มย้ายฟีเจอร์ทีละส่วน - Router ตัดสินใจส่ง request
ไปที่ระบบใหม่หรือเก่าตามฟีเจอร์
[ Client ] ---> [ Router/Facade ] ---+--> [ ฟีเจอร์ A: ระบบใหม่ ]
                                     +--> [ ฟีเจอร์ B, C, D: ระบบ COBOL เดิม ]

ขั้นที่ 3: ย้ายฟีเจอร์เพิ่มขึ้นเรื่อย ๆ ตามความพร้อม
[ Client ] ---> [ Router/Facade ] ---+--> [ ฟีเจอร์ A, B: ระบบใหม่ ]
                                     +--> [ ฟีเจอร์ C, D: ระบบ COBOL เดิม ]

ขั้นสุดท้าย: ทุกฟีเจอร์ย้ายเสร็จสมบูรณ์ - ปิดระบบเก่าได้อย่างปลอดภัย
[ Client ] ---> [ Router/Facade ] ---> [ ระบบใหม่ทั้งหมด ]
```

### เชื่อมโยงกับ Wrapper Service Pattern ที่เรียนไปแล้วใน Part 073

สังเกตว่า **Router/Facade** ในแผนภาพข้างต้นทำหน้าที่คล้ายกับ **Wrapper Service** ที่เราสร้างจริง
ใน Part 073! ในทางปฏิบัติ องค์กรจำนวนมากเริ่มต้นการทำ Strangler Fig Migration ด้วยการสร้าง
Wrapper Service/API Gateway ชั้นหนึ่งก่อน (เหมือนที่เราทำใน Part 073-074) แล้วค่อย ๆ ย้าย
endpoint ทีละตัวจากการเรียก COBOL program เดิม ไปเป็นการเรียกบริการใหม่ (ที่อาจเขียนด้วย Java,
Python หรือภาษาอื่น) โดยที่ฝั่ง Client (เว็บ/มือถือ) **ไม่รู้สึกถึงความเปลี่ยนแปลงใด ๆ เลย** เพราะ
ยังคงเรียก API endpoint เดิมผ่าน Router/Facade ตัวเดียวกัน

นี่คือเหตุผลสำคัญที่ Part 073 ถูกจัดไว้เป็น Part แรกของเฟส 5: **Wrapper Service Pattern ไม่ใช่แค่
เทคนิคสำหรับเปิด API เท่านั้น แต่ยังเป็นรากฐานสำคัญของกลยุทธ์ Strangler Fig Pattern ระดับองค์กร
ด้วย**

### ข้อควรระวัง

- Strangler Fig Pattern ใช้เวลานาน (มักเป็นปีถึงหลายปีสำหรับระบบขนาดใหญ่) และต้องดูแลรักษาทั้งระบบ
  เก่าและระบบใหม่ไปพร้อมกันในช่วงเปลี่ยนผ่าน ซึ่งมีต้นทุนเพิ่มเติมที่ต้องวางแผนงบประมาณรองรับ
- การเลือกลำดับฟีเจอร์ที่จะย้ายก่อน-หลังสำคัญมาก โดยทั่วไปควรเริ่มจากฟีเจอร์ที่**มีความเสี่ยงต่ำและ
  แยกส่วนได้ชัดเจน (low-risk, loosely-coupled)** ก่อน แล้วค่อยขยับไปยังฟีเจอร์ที่ซับซ้อนและมีความ
  เสี่ยงสูงกว่าเมื่อทีมมีประสบการณ์และความมั่นใจมากขึ้น

### แบบฝึกหัดที่ 764.1

**โจทย์**: จงอธิบายว่าทำไม Router/Facade ใน Strangler Fig Pattern จึงจำเป็นต้อง "โปร่งใส"
(transparent) ต่อฝั่ง Client อย่างสมบูรณ์ และจะเกิดอะไรขึ้นหากไม่เป็นเช่นนั้น

**เฉลย**: ความโปร่งใสหมายถึงฝั่ง Client (เว็บ, มือถือ, หรือระบบอื่นที่เรียกใช้ API) ไม่จำเป็นต้อง
รู้หรือสนใจเลยว่า request ของตนถูกส่งไปประมวลผลที่ระบบเก่า (COBOL) หรือระบบใหม่ เพราะยังคงเรียก
endpoint เดิม, ได้รับ response รูปแบบเดิม หากไม่เป็นเช่นนี้ (เช่น Client ต้องเปลี่ยนวิธีเรียก API
ทุกครั้งที่มีฟีเจอร์ถูกย้ายไประบบใหม่) จะทำให้**ทุกครั้งที่ย้ายฟีเจอร์ต้องประสานงานแก้ไขฝั่ง Client
ไปพร้อมกันด้วย** ซึ่งขัดกับเป้าหมายหลักของ Strangler Fig Pattern ที่ต้องการให้การย้ายระบบทำได้แบบ
ค่อยเป็นค่อยไปโดยไม่กระทบผู้ใช้ปลายทาง หากต้องแก้ไข Client ทุกครั้งที่ย้าย ก็จะสูญเสียข้อได้เปรียบ
สำคัญที่สุดของ pattern นี้ไป กลายเป็นความซับซ้อนที่ไม่คุ้มค่า

## ขั้นตอนที่ 765: กลยุทธ์ 6R ของการโยกย้ายระบบสู่ Cloud (The 6 R's of Migration)

### ภาพรวมกรอบแนวคิด 6R

วงการ Cloud Migration ใช้กรอบแนวคิดที่เรียกว่า **6R** (ขยายจากแนวคิดดั้งเดิม 5R ที่ Gartner และ
AWS เผยแพร่ไว้) เพื่อจัดหมวดหมู่กลยุทธ์การย้ายระบบต่าง ๆ ให้ชัดเจน:

| กลยุทธ์ | ความหมาย | ตัวอย่างในบริบท COBOL |
|---|---|---|
| **Rehost** ("lift-and-shift") | ย้ายระบบไปรันบน Cloud โดยแทบไม่แก้ไขอะไรเลย | ย้าย Mainframe emulator ทั้งชุดไปรันบน Cloud VM |
| **Replatform** | ย้ายพร้อมปรับเปลี่ยนบางส่วนเพื่อใช้ประโยชน์จาก Cloud (แต่ไม่เปลี่ยนสถาปัตยกรรมหลัก) | ใช้ AWS Mainframe Modernization ที่เรียนในขั้นตอนที่ 762 |
| **Repurchase** | เปลี่ยนไปใช้ซอฟต์แวร์สำเร็จรูป (SaaS) แทนระบบที่พัฒนาเอง | เปลี่ยนระบบบัญชีเงินเดือนที่เขียนเองด้วย COBOL ไปใช้ SaaS HR platform |
| **Refactor/Re-architect** | เขียนโค้ดใหม่ในสถาปัตยกรรมและภาษาสมัยใหม่ | แปลง COBOL เป็น Java/C# ตามที่จะเรียนเต็มรูปแบบใน Part 084 |
| **Retire** | เลิกใช้ระบบที่ไม่จำเป็นอีกต่อไป | พบว่าโมดูล COBOL บางส่วนไม่มีใครใช้งานแล้ว ตัดทิ้งแทนการย้าย |
| **Retain** | คงระบบเดิมไว้บน Mainframe ต่อไปโดยไม่ย้าย | ระบบที่มีความเสี่ยงสูงเกินไปหรือยังไม่คุ้มค่าที่จะย้ายในขณะนี้ |

### ทำไมต้องประเมินทุกระบบด้วยกรอบ 6R ก่อนเริ่มโครงการ

องค์กรขนาดใหญ่มักมีระบบ COBOL หลายร้อยถึงหลายพันโปรแกรมทำงานร่วมกัน **ไม่ใช่ทุกโปรแกรมที่ควรใช้
กลยุทธ์เดียวกัน** ขั้นตอนแรกของโครงการ Modernization ที่ดีคือการทำ **Portfolio Assessment** —
สำรวจและประเมินระบบทั้งหมดว่าแต่ละส่วนควรใช้กลยุทธ์ใดในกรอบ 6R โดยพิจารณาจากปัจจัยต่าง ๆ เช่น:

- ความถี่ในการถูกใช้งาน / ความสำคัญทางธุรกิจ
- ความซับซ้อนของ business logic และการเชื่อมโยงกับระบบอื่น (coupling)
- คุณภาพและความสมบูรณ์ของเอกสารที่มีอยู่
- ความเสี่ยงหากเกิดปัญหาระหว่างการย้าย

### ตัวอย่างการจัดกลุ่มสมมติสำหรับพอร์ตระบบขนาดใหญ่ (ภาพประกอบเพื่อความเข้าใจ)

```
ระบบตรวจสอบยอดเงินแบบ read-only ความเสี่ยงต่ำ       -> Refactor (เขียนใหม่เป็น microservice)
ระบบรายงานภายในที่ไม่ค่อยมีคนใช้                     -> Retire (เลิกใช้ ย้ายข้อมูลเก็บ archive)
ระบบเงินเดือนที่ใช้ตรรกะมาตรฐานทั่วไป                -> Repurchase (เปลี่ยนไปใช้ SaaS)
ระบบ Core Banking ที่ซับซ้อนมาก ความเสี่ยงสูงสุด      -> Replatform (ย้ายด้วย Micro Focus/AWS ก่อน)
ระบบ Clearing ระหว่างธนาคารที่วิกฤตต่อธุรกิจสูงสุด    -> Retain (คงไว้บน Mainframe ต่อไปก่อน)
```

### ข้อควรระวัง

- การจัดกลุ่มข้างต้นเป็น**ตัวอย่างสมมติเพื่อประกอบความเข้าใจเท่านั้น** ระบบจริงในแต่ละองค์กรต้องผ่าน
  การประเมินอย่างละเอียดโดยทีมที่เข้าใจทั้งเทคนิคและบริบททางธุรกิจจริง ไม่มีสูตรสำเร็จตายตัวที่ใช้ได้
  กับทุกองค์กร
- อย่าลืมกลยุทธ์ **Retain** และ **Retire** — หลายครั้งการตัดสินใจที่ดีที่สุดคือ "ไม่ทำอะไรเลย" หรือ
  "เลิกใช้ไปเลย" ไม่ใช่การย้ายหรือแปลงโค้ดเสมอไป การประเมินอย่างตรงไปตรงมาว่าระบบไหนไม่คุ้มค่าที่จะ
  ลงทุนย้ายช่วยประหยัดงบประมาณได้มาก

### แบบฝึกหัดที่ 765.1

**โจทย์**: จงอธิบายว่าทำไมการทำ "Portfolio Assessment" ก่อนเริ่มโครงการ Modernization จึงสำคัญ
กว่าการรีบเลือกกลยุทธ์เดียว (เช่น "Refactor ทุกอย่างเป็น Java") มาใช้กับทุกระบบทันที

**เฉลยแนวทาง**: ระบบ COBOL ขนาดใหญ่ในองค์กรมักมีความหลากหลายมาก ทั้งด้านความสำคัญทางธุรกิจ ความ
ซับซ้อน และความเสี่ยง การใช้กลยุทธ์เดียวกับทุกระบบโดยไม่ประเมินก่อนอาจนำไปสู่การลงทุนมหาศาลใน
การ Refactor ระบบที่ไม่มีใครใช้แล้ว (ซึ่งควร Retire แทน) หรือ Refactor ระบบที่มีความเสี่ยงสูงเกินไป
จนควรใช้แนวทาง Replatform ที่ปลอดภัยกว่าก่อน การทำ Portfolio Assessment ช่วยให้องค์กรจัดสรร
งบประมาณและความเสี่ยงได้อย่างเหมาะสมกับแต่ละระบบ แทนที่จะใช้แนวทางเดียวแบบเหมารวม (one-size-fits-
all) ที่มักนำไปสู่การใช้ทรัพยากรอย่างไม่มีประสิทธิภาพและความเสี่ยงที่ไม่จำเป็น

## ขั้นตอนที่ 766: รูปแบบสถาปัตยกรรม Hybrid Cloud สำหรับช่วงเปลี่ยนผ่าน

### ทำไมต้องมี Hybrid Architecture

ในช่วงเปลี่ยนผ่านของ Strangler Fig Pattern (ขั้นตอนที่ 764) องค์กรจำเป็นต้องมีระบบที่ทำงานคาบ
เกี่ยวกันระหว่าง Mainframe เดิมกับ Cloud ใหม่ไปพร้อมกันเป็นระยะเวลาหนึ่ง (อาจเป็นปีหรือหลายปี)
สถาปัตยกรรมแบบนี้เรียกว่า **Hybrid Cloud Architecture**

### องค์ประกอบหลักของ Hybrid Architecture ในบริบท COBOL Modernization

```
[ On-Premise: Mainframe เดิม ]              [ Cloud: ระบบใหม่ ]
  - COBOL/CICS/DB2                            - Microservices (Java/Python/Node.js)
  - ข้อมูลหลัก (system of record)              - API Gateway / Wrapper Service
        |                                            |
        +---------- Secure Network Link -------------+
              (VPN, AWS Direct Connect,
               Azure ExpressRoute เป็นต้น)
                          |
                          v
              [ Data Synchronization Layer ]
        (ทำให้ข้อมูลทั้งสองฝั่งสอดคล้องกัน
         ระหว่างช่วงเปลี่ยนผ่าน)
```

### ความท้าทายสำคัญ: Data Synchronization

หนึ่งในความท้าทายที่ยากที่สุดของ Hybrid Architecture คือการทำให้ข้อมูลใน Mainframe เดิม (มักเป็น
VSAM หรือ DB2 ที่เรียนใน Part 055-060) กับข้อมูลในระบบ Cloud ใหม่ (มักเป็น PostgreSQL/MySQL หรือ
NoSQL) **สอดคล้องกันตลอดเวลา** ระหว่างช่วงเปลี่ยนผ่าน มีแนวทางหลักที่ใช้กันในโลกจริง:

- **Change Data Capture (CDC)**: เครื่องมือที่คอยตรวจจับการเปลี่ยนแปลงข้อมูลใน Mainframe แบบ
  real-time แล้วส่ง (replicate) การเปลี่ยนแปลงนั้นไปยังฐานข้อมูล Cloud โดยอัตโนมัติ
- **Batch Synchronization**: ซิงค์ข้อมูลเป็นรอบ (เช่น ทุกคืน) แทนที่จะเป็น real-time เหมาะกับระบบ
  ที่ไม่ต้องการความสดใหม่ของข้อมูลระดับวินาที (ทบทวนแนวคิด Batch Processing จาก Part 066)
- **Dual-Write Pattern**: ให้แอปพลิเคชันเขียนข้อมูลไปทั้งสองฝั่งพร้อมกันทุกครั้งที่มีการเปลี่ยนแปลง
  (ซับซ้อนกว่าและมีความเสี่ยงที่ทั้งสองฝั่งจะไม่ตรงกันหากการเขียนฝั่งใดฝั่งหนึ่งล้มเหลวกลางคัน)

### ข้อควรระวัง

- Hybrid Architecture เพิ่มความซับซ้อนของระบบโดยรวมอย่างมาก (ต้องดูแลทั้งสองระบบพร้อมกัน, ต้อง
  จัดการเรื่อง network latency ระหว่าง on-premise กับ cloud, ต้องมีแผนรับมือกรณี network link
  ขาดหาย) องค์กรควรวางแผนให้ช่วงเวลานี้สั้นที่สุดเท่าที่จะทำได้อย่างปลอดภัย ไม่ใช่ปล่อยให้ hybrid
  state คงอยู่ถาวรโดยไม่มีเป้าหมายสิ้นสุดที่ชัดเจน
- Data Synchronization ที่ผิดพลาดอาจนำไปสู่ปัญหาความไม่สอดคล้องของข้อมูล (data inconsistency)
  ที่ร้ายแรงมากในระบบการเงิน เช่น ยอดเงินคงเหลือที่แสดงในแอปมือถือ (อ่านจาก Cloud) ไม่ตรงกับยอดจริง
  ใน Mainframe (system of record ตัวจริง) — ต้องออกแบบและทดสอบกลไก synchronization อย่างละเอียด
  มากเป็นพิเศษ

### แบบฝึกหัดที่ 766.1

**โจทย์**: จงอธิบายว่าทำไม "Batch Synchronization" จึงอาจไม่เหมาะกับระบบตรวจสอบยอดเงินคงเหลือแบบ
real-time ผ่านแอปมือถือ ในขณะที่อาจเหมาะกับระบบรายงานสรุปยอดขายประจำสัปดาห์

**เฉลยแนวทาง**: ระบบตรวจสอบยอดเงินคงเหลือแบบ real-time ต้องการให้ผู้ใช้เห็นยอดเงินที่ถูกต้อง ณ
ขณะนั้นทันทีหลังทำธุรกรรม (เช่น โอนเงินแล้วยอดต้องอัปเดตทันที) หาก Batch Synchronization ทำงานแค่
วันละครั้ง ผู้ใช้อาจเห็นยอดเงินที่ล้าสมัยไปเกือบทั้งวัน สร้างความสับสนและความไม่พอใจอย่างมาก
(อาจถึงขั้นคิดว่าธุรกรรมไม่สำเร็จ) ในขณะที่ระบบรายงานสรุปยอดขายประจำสัปดาห์ไม่ต้องการความสดใหม่ของ
ข้อมูลระดับวินาที ข้อมูล ณ สิ้นวันก่อนหน้าก็เพียงพอสำหรับการสรุปผลรายสัปดาห์แล้ว การทำ Batch
Synchronization แบบทุกคืนจึงเพียงพอและประหยัดทรัพยากรกว่า Real-time Synchronization มาก

## ขั้นตอนที่ 767: กรณีศึกษาสมมติ — วางแผน Modernization สำหรับระบบสินเชื่อ

### สถานการณ์สมมติ (เพื่อการศึกษา — ไม่ใช่กรณีศึกษาจากองค์กรจริง)

ธนาคารสมมติแห่งหนึ่งมีระบบอนุมัติสินเชื่อที่เขียนด้วย COBOL รันบน Mainframe มา 25 ปี ประกอบด้วย:

- โปรแกรมคำนวณคะแนนเครดิต (Credit Scoring) — ตรรกะซับซ้อนมาก มีการปรับแก้เกณฑ์หลายร้อยครั้งตลอด
  25 ปี ไม่มีเอกสารครบถ้วน
- โปรแกรมสร้างเอกสารสัญญาสินเชื่อ — ตรรกะเรียบง่าย ส่วนใหญ่เป็นการจัดรูปแบบข้อความ
- ระบบรายงานสรุปยอดสินเชื่อประจำเดือนส่งหน่วยงานกำกับดูแล — รันเป็น batch job ทุกสิ้นเดือน
- หน้าจอ CICS สำหรับพนักงานสาขากรอกใบสมัครสินเชื่อ — ใช้งานหนักทุกวันทำการ

### แผนการประยุกต์กรอบ 6R (ภาพประกอบวิธีคิด)

| ระบบย่อย | กลยุทธ์ที่เลือก | เหตุผล |
|---|---|---|
| Credit Scoring | **Retain** (ระยะแรก) → **Replatform** (ระยะกลาง) | ความเสี่ยงสูงมาก ไม่มีเอกสารครบ ต้อง reverse engineer อย่างละเอียดก่อน (เทคนิคนี้จะสอนใน Part 083) ก่อนจะกล้าย้ายหรือแปลง |
| สร้างเอกสารสัญญา | **Refactor** ทันที | ตรรกะเรียบง่าย ความเสี่ยงต่ำ เหมาะเป็นจุดเริ่มต้นสร้างความมั่นใจให้ทีม |
| รายงานประจำเดือน | **Replatform** | ต้องการความแม่นยำสูงเพื่อหน่วยงานกำกับดูแล แต่ไม่จำเป็นต้อง real-time จึงย้ายไปรันบน Cloud ผ่าน AWS Batch ได้โดยไม่ต้องแปลงโค้ด |
| หน้าจอ CICS พนักงานสาขา | **Replatform** ผ่าน Micro Focus Enterprise Server | ทีมพนักงานคุ้นเคยกับหน้าจอเดิม เปลี่ยน UI ทั้งหมดมีความเสี่ยงด้าน user adoption สูง จึงคง UI เดิมไว้แต่ย้าย runtime ไป Cloud |

### ลำดับการดำเนินงานที่แนะนำ (Strangler Fig ในทางปฏิบัติ)

```
เดือนที่ 1-3:   Refactor "สร้างเอกสารสัญญา" เป็น microservice ผ่าน Wrapper Service
                (ใช้ pattern เดียวกับ Part 073) - สร้างความมั่นใจให้ทีมด้วยความเสี่ยงต่ำ
เดือนที่ 4-8:   Replatform "รายงานประจำเดือน" ไป AWS Batch
เดือนที่ 9-18:  Replatform "หน้าจอ CICS" ผ่าน Micro Focus Enterprise Server บน Cloud
เดือนที่ 12-30: Reverse Engineer และค่อย ๆ Replatform/Refactor "Credit Scoring"
                (ใช้เวลานานที่สุดเพราะความเสี่ยงสูงสุดและเอกสารไม่ครบ)
```

### ข้อควรระวัง

- นี่คือ**สถานการณ์สมมติเพื่อการศึกษาเท่านั้น** ไม่ใช่กรณีศึกษาจากองค์กรจริง ระยะเวลาและลำดับที่
  แสดงไว้เป็นตัวอย่างประกอบแนวคิดเท่านั้น ไม่ใช่มาตรฐานตายตัวที่ใช้ได้กับทุกโครงการ
- สังเกตว่าระบบที่มีความเสี่ยงสูงสุด (Credit Scoring) ถูกจัดไว้ให้ใช้เวลานานที่สุดและเริ่มหลังสุด
  เจตนา — นี่คือหลักการสำคัญของการบริหารความเสี่ยงในโครงการ Modernization: **เริ่มจากง่ายไปยาก
  สร้างความมั่นใจและประสบการณ์ทีมก่อนเผชิญความท้าทายที่ใหญ่ที่สุด**

### แบบฝึกหัดที่ 767.1

**โจทย์**: จงอธิบายว่าทำไมการเริ่มโครงการ Modernization ด้วยระบบ "สร้างเอกสารสัญญา" (ความเสี่ยงต่ำ)
ก่อน แทนที่จะเริ่มด้วย "Credit Scoring" (ระบบที่สำคัญที่สุดทางธุรกิจ) จึงเป็นกลยุทธ์ที่ดีกว่า

**เฉลยแนวทาง**: แม้ Credit Scoring จะเป็นระบบที่สำคัญทางธุรกิจมากที่สุด แต่ก็มีความเสี่ยงสูงสุด
เช่นกัน (ตรรกะซับซ้อน เอกสารไม่ครบ) การเริ่มโครงการด้วยระบบที่มีความเสี่ยงสูงสุดทันทีอาจทำให้ทีมยัง
ไม่มีประสบการณ์กับกระบวนการ Modernization พอที่จะรับมือกับความซับซ้อนนั้น เพิ่มโอกาสความล้มเหลวของ
โครงการทั้งหมดตั้งแต่ต้น การเริ่มด้วยระบบความเสี่ยงต่ำ (สร้างเอกสารสัญญา) ก่อนช่วยให้ทีม: (1) เรียนรู้
และปรับตัวกับเครื่องมือและกระบวนการใหม่ในสภาพแวดล้อมที่ปลอดภัยกว่า (2) สร้างผลงานที่จับต้องได้
(quick win) เพื่อสร้างความเชื่อมั่นให้ผู้บริหารและผู้มีส่วนได้ส่วนเสียสนับสนุนโครงการต่อไป (3) ค้นพบ
และแก้ไขปัญหากระบวนการ (เช่น เครื่องมือ CI/CD ที่ยังตั้งค่าไม่ดี) ในบริบทที่ผลกระทบต่ำก่อนที่จะนำไป
ใช้กับระบบที่สำคัญกว่า เมื่อทีมมีประสบการณ์และความมั่นใจมากขึ้นแล้ว จึงค่อยเผชิญกับความท้าทายของ
Credit Scoring ที่ยากและเสี่ยงกว่ามาก

## ขั้นตอนที่ 768: บทบาทของทีมงานในโครงการ Modernization

### ทีมงานที่จำเป็นและบทบาทของแต่ละคน

โครงการ Cloud Modernization ระดับองค์กรไม่ใช่งานที่ทีมพัฒนาเพียงกลุ่มเดียวทำสำเร็จได้ มักต้อง
อาศัยความร่วมมือจากหลายบทบาท:

- **COBOL/Mainframe Subject Matter Expert (SME)**: ผู้ที่เข้าใจ business logic เดิมอย่างลึกซึ้ง
  มักเป็นพนักงานที่ทำงานกับระบบนี้มานาน (อาจใกล้เกษียณตามที่กล่าวถึงใน Part 001 — "Silver
  Tsunami") ความรู้ของคนกลุ่มนี้**มีค่าอย่างยิ่ง**และมักเป็นคอขวดของโครงการ เพราะเอกสารมักไม่
  ครบถ้วน
- **Cloud Architect**: ออกแบบสถาปัตยกรรมเป้าหมายบน Cloud ตัดสินใจเลือกบริการและรูปแบบ Hybrid
  Architecture ที่เหมาะสม
- **Modern Application Developer**: เขียนโค้ดส่วนใหม่ (Wrapper Service, Microservices) ตาม
  แนวทางที่เรียนใน Part 073-076
- **Data Migration Specialist**: ดูแลการย้ายและ synchronize ข้อมูลระหว่างระบบเก่าและใหม่ (ตามที่
  กล่าวถึงในขั้นตอนที่ 766)
- **QA/Test Engineer เฉพาะทาง Regression Testing**: ตรวจสอบว่าระบบใหม่ให้ผลลัพธ์เหมือนระบบเก่า
  ทุกกรณี (เนื้อหาเรื่อง Unit Testing สำหรับ COBOL จะสอนเต็มรูปแบบใน **Part 079**)

### ความท้าทายพิเศษ: การถ่ายทอดความรู้ (Knowledge Transfer)

ปัญหาที่พบบ่อยที่สุดในโครงการ Modernization จริงคือ **SME ที่เข้าใจระบบเดิมมีจำนวนน้อยลงเรื่อย ๆ**
และบางครั้งเกษียณหรือลาออกไปก่อนที่โครงการจะเสร็จสมบูรณ์ องค์กรที่วางแผนดีจะจัดกระบวนการถ่ายทอด
ความรู้อย่างเป็นระบบ เช่น:

- จับคู่ (pair) SME รุ่นเก่ากับนักพัฒนารุ่นใหม่ตลอดโครงการ ไม่ใช่แค่ตอนเริ่มต้น
- บันทึกการตัดสินใจและเหตุผลเบื้องหลัง business rule ที่ค้นพบระหว่างทำ Reverse Engineering
  (เทคนิคนี้จะสอนเต็มรูปแบบใน **Part 083**) ไว้เป็นเอกสารที่เข้าถึงได้สำหรับทีมในอนาคต
- สร้าง automated test ที่จับพฤติกรรมของระบบเดิมไว้ให้ได้มากที่สุด **ก่อน**ที่ SME จะออกจากทีม
  (เพราะ test ที่ดีคือ "เอกสาร" ที่ทนทานที่สุดชนิดหนึ่ง — เนื้อหานี้เชื่อมโยงกับ Part 079)

### ข้อควรระวัง

- อย่าประเมินค่าความรู้ของ SME ต่ำเกินไปเพียงเพราะพวกเขาไม่คุ้นเคยกับเทคโนโลยีสมัยใหม่ — ความรู้
  เรื่อง business logic ที่พวกเขามีมักหาทดแทนไม่ได้เลยหากสูญเสียไปโดยไม่มีการบันทึกไว้ก่อน
- โครงการที่มองข้ามการถ่ายทอดความรู้ (Knowledge Transfer) และมุ่งเน้นแค่ "เทคโนโลยี" อย่างเดียว
  มีความเสี่ยงสูงมากที่จะค้นพบภายหลังว่าระบบใหม่ขาด business rule สำคัญบางอย่างไปโดยไม่รู้ตัว

### แบบฝึกหัดที่ 768.1

**โจทย์**: จงอธิบายว่าทำไม "automated test ที่จับพฤติกรรมของระบบเดิมไว้" จึงถือเป็นรูปแบบหนึ่งของ
การถ่ายทอดความรู้ (Knowledge Transfer) ไม่ใช่แค่เครื่องมือประกันคุณภาพ (QA tool) ธรรมดา

**เฉลยแนวทาง**: Automated test ที่ดี (เช่น test ที่ป้อน input หลากหลายกรณีเข้าโปรแกรม COBOL เดิม
แล้วบันทึกผลลัพธ์ที่ถูกต้องไว้เป็น "ค่าอ้างอิง") ทำหน้าที่เป็น**เอกสารที่มีชีวิต (living
documentation)** ของพฤติกรรมจริงของระบบ ต่างจากเอกสารข้อความทั่วไปที่อาจล้าสมัยหรือเขียนไม่ครบถ้วน
test เหล่านี้บังคับให้แสดงพฤติกรรมจริงของระบบผ่าน input/output คู่จริงที่พิสูจน์ได้ เมื่อ SME
ออกจากทีมไปแล้ว นักพัฒนารุ่นใหม่ยังคงสามารถดู test suite เพื่อเข้าใจว่าระบบเดิม "ควรจะ" ทำงาน
อย่างไรในแต่ละกรณี แม้จะไม่มี SME อธิบายให้ฟังโดยตรงอีกต่อไป ทำให้ automated test ทำหน้าที่ถ่ายทอด
ความรู้ที่คงทนกว่าเอกสารข้อความหรือความทรงจำของคนเพียงอย่างเดียว

## ขั้นตอนที่ 769: ตัวชี้วัดความสำเร็จ (KPI) ของโครงการ Modernization

### ทำไมต้องกำหนด KPI ที่ชัดเจนตั้งแต่ต้น

โครงการ Modernization ที่ใช้เวลานานหลายปีมีความเสี่ยงที่จะ "หลงทาง" ได้ง่าย หากไม่มีตัวชี้วัดที่
ชัดเจนตั้งแต่ต้นว่า "ความสำเร็จ" หน้าตาเป็นอย่างไร การกำหนด KPI ที่ดีช่วยให้ทีมและผู้บริหารเห็น
ความคืบหน้าที่จับต้องได้ตลอดโครงการ

### ตัวอย่างหมวดหมู่ KPI ที่ใช้ในโครงการ Modernization จริง

| หมวดหมู่ | ตัวอย่างตัวชี้วัด |
|---|---|
| **ความคืบหน้าทางเทคนิค** | จำนวนฟีเจอร์/endpoint ที่ย้ายสำเร็จ (เทียบสัดส่วนกับทั้งหมด), เปอร์เซ็นต์ของ codebase ที่ยังคงเป็น COBOL |
| **คุณภาพ/ความถูกต้อง** | จำนวนบั๊กที่พบใน production หลังย้าย (เทียบกับ baseline ของระบบเดิม), ผลการทดสอบ regression testing |
| **ประสิทธิภาพ** | response time ของ API ใหม่เทียบกับระบบเดิม, throughput (จำนวนธุรกรรมต่อวินาทีที่รองรับได้) |
| **ต้นทุน** | ค่าใช้จ่าย Cloud รายเดือนเทียบกับค่า MIPS/MSU license ของ Mainframe เดิมที่ประหยัดได้ |
| **ความเสี่ยง/เสถียรภาพ** | Uptime ของระบบใหม่, จำนวนครั้งที่ต้อง rollback กลับไประบบเดิม |
| **บุคลากร** | จำนวนนักพัฒนาที่ผ่านการ training เทคโนโลยีใหม่, ระดับความพึงพอใจของทีม |

### ข้อควรระวังเรื่องการตีความ KPI

- **อย่าใช้ "ความเร็วในการย้ายระบบ" เป็น KPI หลักเพียงอย่างเดียว** เพราะจะสร้างแรงกดดันให้ทีมเร่ง
  ย้ายระบบโดยลดขั้นตอนการทดสอบลง ซึ่งขัดกับหลักการบริหารความเสี่ยงที่เรียนไปแล้วในขั้นตอนที่ 764
  และ 767
- KPI ด้านต้นทุนต้องคำนวณอย่างครอบคลุม ไม่ใช่แค่เปรียบเทียบค่า license อย่างเดียว แต่ต้องรวมต้นทุน
  แฝงอื่น ๆ ด้วย เช่น ต้นทุนการ training ทีม, ต้นทุนการดูแล Hybrid Architecture ระหว่างช่วงเปลี่ยน
  ผ่าน (ขั้นตอนที่ 766), และความเสี่ยงทางธุรกิจหากเกิดปัญหาระหว่างย้ายระบบ

### ข้อควรระวัง

- KPI ที่ตั้งไว้ตอนเริ่มโครงการควรถูกทบทวนเป็นระยะ (เช่น ทุกไตรมาส) เพราะบริบททางธุรกิจและเทคโนโลยี
  อาจเปลี่ยนแปลงไประหว่างโครงการที่ใช้เวลาหลายปี
- ระวังการ "เล่นกับตัวเลข" (gaming the metrics) เช่น การนับ "จำนวนฟีเจอร์ที่ย้ายสำเร็จ" โดยเลือก
  ย้ายเฉพาะฟีเจอร์ง่าย ๆ จำนวนมากก่อน เพื่อให้ตัวเลขดูดี ทั้งที่ฟีเจอร์ที่สำคัญและซับซ้อนกว่ายังไม่ได้
  ถูกแตะต้องเลย

### แบบฝึกหัดที่ 769.1

**โจทย์**: จงอธิบายว่าทำไม "จำนวนบั๊กที่พบใน production หลังย้าย" จึงเป็น KPI ที่สำคัญไม่แพ้ "ความ
เร็วในการย้ายระบบ" สำหรับโครงการ Modernization ของระบบการเงิน

**เฉลยแนวทาง**: ระบบการเงินที่เรียนรู้มาตลอดหลักสูตรนี้ (ธนาคาร, บัญชี, สินเชื่อ) ต้องการความถูกต้อง
แม่นยำสูงสุด (ทบทวนเหตุผลเรื่อง Decimal Arithmetic จาก Part 001 ขั้นตอนที่ 5) หากโครงการ
Modernization เน้นแค่ "ย้ายให้เร็วที่สุด" โดยไม่ให้ความสำคัญกับคุณภาพ อาจนำไปสู่บั๊กที่กระทบเงินของ
ลูกค้าโดยตรง เช่น การคำนวณดอกเบี้ยผิดพลาด หรือยอดเงินคงเหลือไม่ตรงกัน ซึ่งสร้างความเสียหายทั้งด้าน
การเงินและชื่อเสียงขององค์กรที่ร้ายแรงกว่าการที่โครงการล่าช้าไปบ้างมาก การติดตาม KPI "จำนวนบั๊กที่
พบใน production" อย่างใกล้ชิดช่วยให้ทีมตรวจพบปัญหาคุณภาพได้เร็ว และสามารถชะลอความเร็วของการย้าย
ระบบลงเพื่อแก้ไขปัญหาก่อน แทนที่จะเร่งย้ายต่อไปทั้งที่ยังมีปัญหาคุณภาพสะสมอยู่

## ขั้นตอนที่ 770: สรุปภาพรวมเฟส 5 ตอนต้น และเชื่อมโยงสู่เนื้อหาที่เหลือ

### แบบฝึกหัดที่ 770.1 (แบบฝึกหัดรวม Part นี้)

**โจทย์**: จงเขียนสรุปสั้น ๆ (3-5 ประโยค) อธิบายให้ผู้บริหารที่ไม่มีพื้นฐานเทคนิคฟังว่าทำไมองค์กร
ควรเลือกใช้กลยุทธ์ Strangler Fig Pattern แทนการ "ปิดระบบเก่าแล้วเปิดระบบใหม่ทันที" (Big Bang)
สำหรับการย้ายระบบ COBOL ที่สำคัญต่อธุรกิจ

**เฉลยแนวทาง**: "ระบบ COBOL ของเราสะสมกฎเกณฑ์ทางธุรกิจมานานหลายสิบปี การเปลี่ยนระบบทั้งหมดในคราว
เดียวเปรียบเสมือนการเปลี่ยนเครื่องยนต์เครื่องบินขณะกำลังบินอยู่ — หากพลาดเพียงจุดเดียว ผลกระทบจะ
เกิดกับลูกค้าทุกคนพร้อมกันทันที แทนที่จะทำเช่นนั้น เราจะย้ายระบบทีละส่วนอย่างค่อยเป็นค่อยไป เริ่ม
จากส่วนที่มีความเสี่ยงต่ำที่สุดก่อน เพื่อเรียนรู้และปรับปรุงกระบวนการก่อนที่จะแตะต้องส่วนที่สำคัญ
ที่สุด วิธีนี้ใช้เวลานานกว่า แต่ลดความเสี่ยงที่จะเกิดปัญหาร้ายแรงกับลูกค้าและธุรกิจได้อย่างมาก และ
ยังทำให้เราสามารถหยุดหรือปรับแผนได้ทุกเมื่อหากพบปัญหาระหว่างทาง โดยไม่ต้องเสี่ยงกับระบบทั้งหมด
พร้อมกัน"

- แรงจูงใจทางธุรกิจเบื้องหลังการย้าย Mainframe ไป Cloud (ต้นทุน, ความยืดหยุ่น, การสรรหาบุคลากร)
  พร้อมข้อควรระวังว่า Cloud ไม่ใช่คำตอบสำหรับทุกสถานการณ์
- ภาพรวม **AWS Mainframe Modernization** (Replatform vs Refactor) และ **Micro Focus
  Enterprise Server** พร้อมระบุอย่างซื่อตรงว่าเป็นเนื้อหาเชิงแนวคิดที่ยังไม่ได้ทดสอบจริงใน
  สภาพแวดล้อมหลักสูตรนี้
- **Strangler Fig Pattern**: กลยุทธ์การย้ายระบบทีละส่วนอย่างค่อยเป็นค่อยไป และความเชื่อมโยงกับ
  Wrapper Service Pattern ที่สร้างจริงใน Part 073
- กรอบแนวคิด **6R** (Rehost, Replatform, Repurchase, Refactor, Retire, Retain) สำหรับประเมิน
  กลยุทธ์ที่เหมาะสมของแต่ละระบบย่อยในพอร์ตขององค์กร
- **Hybrid Cloud Architecture** และความท้าทายเรื่อง Data Synchronization ระหว่างช่วงเปลี่ยนผ่าน
- กรณีศึกษาสมมติของระบบสินเชื่อธนาคารที่แสดงวิธีประยุกต์แนวคิดทั้งหมดเข้าด้วยกัน
- บทบาทของทีมงานและความสำคัญของการถ่ายทอดความรู้ (Knowledge Transfer) จาก SME รุ่นเก่า
- ตัวชี้วัดความสำเร็จ (KPI) ที่ควรใช้ติดตามโครงการ Modernization อย่างสมดุล ไม่เน้นความเร็วเพียง
  อย่างเดียว
