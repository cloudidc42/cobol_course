## ขั้นตอนที่ 501: Mainframe คืออะไร — นิยามและลักษณะเฉพาะที่ทำให้แตกต่างจากเซิร์ฟเวอร์ทั่วไป

### นิยามของ Mainframe

**Mainframe** คือคอมพิวเตอร์ขนาดใหญ่ระดับองค์กร (Enterprise-class computer) ที่ออกแบบมาโดยเฉพาะสำหรับ
**การประมวลผลธุรกรรมปริมาณมหาศาล (High-Volume Transaction Processing)** ด้วยความน่าเชื่อถือ ความ
ปลอดภัย และความสามารถในการปรับขนาด (scalability) ที่สูงที่สุดในบรรดาคอมพิวเตอร์ประเภทต่าง ๆ ที่มีอยู่
ผู้ผลิต Mainframe รายใหญ่ที่สุดและมีส่วนแบ่งตลาดสูงสุดในปัจจุบันคือ **IBM** ด้วยตระกูลผลิตภัณฑ์
**IBM Z** (ชื่อรุ่นปัจจุบันคือ IBM z16/z17 ที่ใช้สถาปัตยกรรม z/Architecture)

### เปรียบเทียบ Mainframe กับเซิร์ฟเวอร์ทั่วไป (Commodity Server)

| คุณสมบัติ | Mainframe | เซิร์ฟเวอร์ทั่วไป (x86) |
|---|---|---|
| เป้าหมายการออกแบบ | ความน่าเชื่อถือ + ปริมาณธุรกรรมสูงสุด | ความคุ้มค่า + ความยืดหยุ่น |
| Uptime ที่คาดหวัง | 99.999% ขึ้นไป ("five nines" ≈ หยุดไม่เกิน 5 นาที/ปี) | ขึ้นกับการออกแบบ Cluster/HA |
| การจัดการ I/O | มี Channel Processor แยกต่างหากจาก CPU หลัก | ใช้ CPU/Bus เดียวกันกับงานประมวลผล |
| ความสามารถประมวลผลพร้อมกัน | ออกแบบมาเพื่อรันหลายพัน job/transaction พร้อมกัน | ขึ้นกับจำนวนเครื่องใน Cluster |
| การอัปเกรดโดยไม่หยุดระบบ | รองรับ (Hot-swap CPU, Memory, I/O) เป็นมาตรฐาน | ขึ้นกับสถาปัตยกรรมเฉพาะ |
| Backward Compatibility | โค้ดจากยุค 1960s ยังรันได้บน Mainframe รุ่นล่าสุด | หายากมากในระดับนี้ |

### ทำไม Mainframe จึงเหมาะกับงานธุรกิจการเงินเป็นพิเศษ

จุดแข็งที่สำคัญที่สุดของ Mainframe ที่ทำให้อุตสาหกรรมการเงิน/ธนาคาร/ประกันภัยยังคงพึ่งพาอยู่จนถึง
ปัจจุบัน (ตามที่ Part 001 อธิบายสถิติไว้) คือ:

1. **RAS (Reliability, Availability, Serviceability)** — ความน่าเชื่อถือระดับสูงสุดที่ฮาร์ดแวร์ทั่วไป
   เทียบไม่ได้ ฮาร์ดแวร์ Mainframe มีกลไกตรวจจับและแก้ไขข้อผิดพลาดในระดับวงจรไฟฟ้า (self-healing
   hardware) ที่ซับซ้อนกว่าเซิร์ฟเวอร์ทั่วไปมาก
2. **ความสามารถประมวลผล I/O มหาศาลพร้อมกัน** — Mainframe มี **Channel Processor** แยกต่างหากทำหน้าที่
   จัดการการอ่าน/เขียนข้อมูลโดยเฉพาะ ไม่แย่งทรัพยากรกับ CPU หลักที่ทำการคำนวณ ทำให้ประมวลผลธุรกรรม
   หลายพันล้านรายการต่อวันได้โดยไม่มีคอขวด (bottleneck)
3. **ความปลอดภัยระดับฮาร์ดแวร์** — มีระบบเข้ารหัสในตัวชิป (Crypto Express) และระบบควบคุมสิทธิ์เข้าถึง
   ที่ผนวกลึกเข้ากับระบบปฏิบัติการ (เช่น RACF ที่จะกล่าวถึงในขั้นตอนถัดไป)
4. **Backward Compatibility ที่ยาวนานที่สุดในอุตสาหกรรม** — โปรแกรม COBOL ที่คอมไพล์ไว้ตั้งแต่ยุค
   1970-1980 (ที่ Part 001 กล่าวถึง) ยังคงรันได้บน Mainframe รุ่นล่าสุดโดยแทบไม่ต้องแก้ไข นี่คือเหตุผล
   สำคัญที่องค์กรไม่ Rewrite ระบบใหม่ทั้งหมด (ทบทวนจาก Part 001 ขั้นตอนที่ 3)

### ข้อควรระวัง

- อย่าเข้าใจผิดว่า "Mainframe" หมายถึง "คอมพิวเตอร์รุ่นเก่าที่ล้าสมัย" — Mainframe รุ่นปัจจุบัน (เช่น
  ตระกูล IBM Z ล่าสุด) ใช้เทคโนโลยีชิปที่ทันสมัยมาก รวมถึงการเร่งความเร็วด้วย AI Accelerator ในตัว
  ความเข้าใจผิดนี้พบได้บ่อยมากในหมู่ผู้ที่ไม่เคยทำงานกับ Mainframe จริง
- Mainframe ไม่ใช่ "ซูเปอร์คอมพิวเตอร์ (Supercomputer)" — ซูเปอร์คอมพิวเตอร์เน้นความเร็วในการคำนวณ
  ทางวิทยาศาสตร์ (เช่น จำลองสภาพอากาศ) ส่วน Mainframe เน้น**ปริมาณธุรกรรม I/O ที่สูงมาก**พร้อมความ
  น่าเชื่อถือ เป็นคนละจุดประสงค์การออกแบบกันโดยสิ้นเชิง

### แบบฝึกหัดที่ 501.1

**โจทย์**: จงอธิบายว่าทำไม "Channel Processor" ที่แยกจาก CPU หลักจึงเป็นข้อได้เปรียบสำคัญของ
Mainframe สำหรับงานประมวลผลธุรกรรมทางธนาคาร

**เฉลยแนวทาง**: งานธนาคาร เช่น การถอนเงิน ATM หรือการโอนเงิน มีลักษณะเป็น **I/O-intensive** (ต้อง
อ่าน/เขียนข้อมูลบัญชีจากดิสก์บ่อยมาก) มากกว่า **CPU-intensive** (การคำนวณที่ซับซ้อน) หากใช้สถาปัตยกรรม
ที่ CPU ต้องรอทำ I/O เอง (เหมือนเซิร์ฟเวอร์ทั่วไปในระดับพื้นฐาน) CPU จะเสียเวลาส่วนใหญ่ไปกับการรอข้อมูล
แทนที่จะประมวลผล การมี Channel Processor แยกต่างหากทำให้ CPU หลักสามารถประมวลผลธุรกรรมอื่นต่อไปได้
ทันทีโดยไม่ต้องรอ I/O เสร็จสิ้นก่อน ส่งผลให้ปริมาณธุรกรรมที่ประมวลผลได้ต่อวินาที (Throughput) สูงกว่า
สถาปัตยกรรมทั่วไปมากในงานลักษณะนี้

## ขั้นตอนที่ 502: ประวัติศาสตร์ Mainframe และ z/OS — จาก System/360 ถึง z/Architecture

### จุดกำเนิด: IBM System/360 (1964)

เส้นทางของ Mainframe เริ่มต้นอย่างเป็นทางการในปี **1964** เมื่อ IBM เปิดตัว **System/360** ซึ่งถือเป็น
การปฏิวัติวงการคอมพิวเตอร์ครั้งสำคัญ เพราะเป็นครั้งแรกที่ IBM สร้างสถาปัตยกรรม**เดียว**ที่ใช้ได้กับ
คอมพิวเตอร์หลายขนาด/ราคา (ตั้งแต่เครื่องเล็กสำหรับธุรกิจขนาดกลางถึงเครื่องใหญ่สำหรับองค์กรขนาดมหึมา)
โดยโปรแกรมที่เขียนสำหรับรุ่นหนึ่งสามารถย้ายไปรันบนอีกรุ่นได้โดยไม่ต้องเขียนใหม่ — แนวคิด **Backward/
Forward Compatibility** นี้เองที่เป็นรากฐานสำคัญที่ทำให้โค้ด COBOL อายุหลายสิบปียังรันได้จนถึงปัจจุบัน

### เส้นเวลาสำคัญของ Mainframe และระบบปฏิบัติการตระกูล MVS

| ปี | เหตุการณ์สำคัญ |
|---|---|
| 1964 | IBM เปิดตัว System/360 จุดเริ่มต้นของสถาปัตยกรรม Mainframe สมัยใหม่ |
| 1974 | เปิดตัว **MVS (Multiple Virtual Storage)** ระบบปฏิบัติการที่เป็นบรรพบุรุษโดยตรงของ z/OS |
| 1988 | เปิดตัว System/390 |
| 2000 | เปิดตัว **z/Architecture** (สถาปัตยกรรม 64-bit) พร้อมเครื่องตระกูล IBM zSeries |
| 2001 | เปิดตัว **z/OS** อย่างเป็นทางการ (สืบทอดจาก OS/390 ซึ่งสืบทอดจาก MVS) |
| 2015 | เปิดตัว IBM z13 |
| 2019-2022 | เปิดตัว IBM z15, z16 พร้อมความสามารถ AI Accelerator ในตัว |
| 2023-2026 | z/OS เวอร์ชัน 3.x (z/OS 3.1, 3.2) เพิ่มการรองรับ AI, Quantum-safe Encryption, Python บน Mainframe |

### ความสัมพันธ์ระหว่าง MVS, OS/390, และ z/OS

ผู้เรียนที่อ่านเอกสารหรือบทความเก่าเกี่ยวกับ Mainframe มักพบคำว่า "MVS" ปะปนกับ "z/OS" อยู่บ่อยครั้ง
จนสับสน — ความจริงคือทั้งสามชื่อนี้คือ **วิวัฒนาการของระบบปฏิบัติการตัวเดียวกัน**:

```
MVS (1974) ──> MVS/XA ──> MVS/ESA ──> OS/390 (1995) ──> z/OS (2001 - ปัจจุบัน)
```

นี่คือเหตุผลที่คำว่า "MVS" ยังคงถูกใช้แบบไม่เป็นทางการเพื่อเรียก z/OS จนถึงทุกวันนี้ในหมู่โปรแกรมเมอร์
รุ่นเก่า (เหมือนที่คนยังเรียก "รถเมล์" แม้จะเป็นรถโดยสารรุ่นใหม่ก็ตาม) และเป็นเหตุผลที่ค่าสถานะไฟล์
(File Status) บางค่าที่พบใน GnuCOBOL (Part 030) และ Dialect flag `-std=mvs` (Part 049) ยังคงใช้ชื่อ
"MVS" อ้างอิงถึงพฤติกรรมของ z/OS ในปัจจุบัน

### ข้อควรระวัง

- อย่าเข้าใจผิดว่า z/OS คือ "ระบบปฏิบัติการใหม่ที่เขียนขึ้นใหม่ทั้งหมด" — z/OS มีรหัสต้นฉบับ (source
  code) จำนวนมากที่สืบทอดมาจาก MVS โดยตรง ผ่านการปรับปรุงและขยายความสามารถอย่างต่อเนื่องมากกว่า 50 ปี
  ไม่ใช่การเขียนใหม่ (rewrite) แต่อย่างใด
- ตัวเลขเวอร์ชัน z/OS ที่แน่นอน (เช่น 3.1, 3.2) เปลี่ยนแปลงตามเวลา ผู้เรียนควรตรวจสอบเวอร์ชันล่าสุด
  จากแหล่งข้อมูลของ IBM โดยตรงเมื่อต้องการข้อมูลที่ทันสมัยที่สุด เนื้อหาในเอกสารนี้เน้นแนวคิดและ
  ประวัติศาสตร์ที่มีความเสถียรสูง ไม่เน้นตัวเลขเวอร์ชันที่เปลี่ยนแปลงบ่อย

### แบบฝึกหัดที่ 502.1

**โจทย์**: จงอธิบายว่าทำไมแนวคิด "สถาปัตยกรรมเดียวใช้ได้กับคอมพิวเตอร์หลายขนาด" ของ System/360 ในปี
1964 จึงเป็นรากฐานสำคัญที่ทำให้โค้ด COBOL อายุหลายสิบปียังคงรันได้บน Mainframe รุ่นปัจจุบัน

**เฉลยแนวทาง**: หลักการออกแบบของ System/360 คือการรับประกัน **ความเข้ากันได้ของชุดคำสั่ง (Instruction
Set Compatibility)** ข้ามรุ่นเครื่อง IBM ยึดหลักการนี้ต่อเนื่องมาตลอดวิวัฒนาการของสถาปัตยกรรม (System/
370 → System/390 → z/Architecture) ทำให้โปรแกรมที่คอมไพล์เป็นภาษาเครื่อง (machine code) จากยุค 1970
ยังคง**รันได้ถูกต้องตรงตามความหมายเดิม** บนโปรเซสเซอร์ Mainframe รุ่นล่าสุด แม้ฮาร์ดแวร์ภายในจะ
เปลี่ยนแปลงไปโดยสิ้นเชิงก็ตาม นี่คือเหตุผลที่องค์กรสามารถรันโปรแกรม COBOL เดิมได้นานหลายสิบปีโดยไม่
ต้อง Recompile หรือ Rewrite ตราบใดที่ยังใช้ Mainframe เป็นแพลตฟอร์ม

## ขั้นตอนที่ 503: LPAR และสถาปัตยกรรมการแบ่งทรัพยากร Mainframe

### LPAR คืออะไร

**LPAR (Logical Partition)** คือการแบ่ง Mainframe เครื่องเดียวทางกายภาพออกเป็น **หลายเครื่องเสมือน
อิสระต่อกัน** ในระดับฮาร์ดแวร์ (ไม่ใช่ Virtual Machine แบบซอฟต์แวร์อย่าง VMware ที่คุ้นเคยในโลก x86)
แต่ละ LPAR สามารถรันระบบปฏิบัติการของตัวเอง (เช่น z/OS หนึ่งชุด, Linux on Z อีกชุด) แยกจากกันโดย
สมบูรณ์ พร้อมส่วนแบ่งทรัพยากร CPU/Memory/I/O ที่กำหนดไว้ชัดเจน

```
                    +----------------------------------+
                    |     IBM Z Mainframe (1 เครื่อง)     |
                    +----------------------------------+
                    |  LPAR 1   |  LPAR 2   |  LPAR 3  |
                    |  (z/OS    |  (z/OS    | (Linux   |
                    |  Production)| Test)   | on Z)    |
                    +-----------+-----------+----------+
                    |    CPU/Memory/I/O จัดสรรแยกกันชัดเจน  |
                    +----------------------------------+
```

### ทำไม LPAR จึงสำคัญมากในการดำเนินธุรกิจจริง

1. **แยกสภาพแวดล้อม Production ออกจาก Test/Development อย่างสมบูรณ์** — องค์กรมักมี LPAR แยกสำหรับ
   ระบบที่ใช้งานจริง (Production), ระบบทดสอบ (Test/QA), และระบบพัฒนา (Development) บนเครื่อง
   Mainframe กายภาพเดียวกัน โดยที่ปัญหาในระบบทดสอบจะไม่มีทางกระทบระบบ Production ได้เลย เพราะแยกกัน
   ในระดับฮาร์ดแวร์
2. **รันระบบปฏิบัติการหลายตัวพร้อมกันบนเครื่องเดียว** — LPAR หนึ่งอาจรัน z/OS สำหรับงาน COBOL/CICS
   แบบดั้งเดิม ในขณะที่อีก LPAR รัน Linux on Z สำหรับงานสมัยใหม่ (เช่น Container, Kubernetes) ทำให้
   องค์กรผสมผสานเทคโนโลยีเก่าและใหม่บนฮาร์ดแวร์ชุดเดียวกันได้
3. **ควบคุมการจัดสรรทรัพยากรได้ละเอียด** — สามารถกำหนดได้ว่า LPAR ไหนควรได้รับความสำคัญสูงกว่าเมื่อ
   ทรัพยากรขาดแคลน (เช่น LPAR Production ควรมี priority สูงกว่า LPAR Test เสมอ)

### เปรียบเทียบ LPAR กับ Virtual Machine ที่คุ้นเคยในโลก x86

| คุณสมบัติ | LPAR (Mainframe) | Virtual Machine (x86, เช่น VMware) |
|---|---|---|
| ระดับการแบ่ง | ฮาร์ดแวร์ (PR/SM Hypervisor ในตัวเครื่อง) | ซอฟต์แวร์ (Hypervisor รันบน OS หรือ bare metal) |
| ความปลอดภัยการแยกส่วน | สูงมาก (Hardware-enforced isolation) | สูง แต่ขึ้นกับคุณภาพของ Hypervisor |
| จำนวนสูงสุดต่อเครื่อง | จำกัดตามรุ่นเครื่อง (มักหลักสิบ) | อาจมีได้หลายร้อยขึ้นกับทรัพยากร |

### ข้อควรระวัง

- อย่าสับสน LPAR กับแนวคิด "Container" (Docker, Kubernetes ที่จะเรียนใน Part 076) — Container แชร์
  Kernel ของ OS เดียวกัน ในขณะที่ LPAR แต่ละตัวรันระบบปฏิบัติการของตัวเองอย่างสมบูรณ์แยกจากกัน เป็นคน
  ละระดับของการแบ่งทรัพยากรกันโดยสิ้นเชิง
- ผู้เรียนที่เพิ่งเริ่มทำงานกับ Mainframe มักไม่มีสิทธิ์เข้าถึงหรือมองเห็นการจัดการ LPAR โดยตรง (เป็น
  หน้าที่ของ Systems Programmer ที่ดูแลฮาร์ดแวร์) แต่ควรเข้าใจแนวคิดนี้ไว้เพื่อเข้าใจภาพรวมว่าทำไม
  องค์กรจึงสามารถรันหลายสภาพแวดล้อมบนเครื่อง Mainframe จำนวนน้อยได้

### แบบฝึกหัดที่ 503.1

**โจทย์**: จงอธิบายว่าทำไมธนาคารแห่งหนึ่งจึงเลือกใช้ LPAR แยกกันสำหรับระบบ Production และระบบ Test
แทนที่จะใช้ Mainframe คนละเครื่องไปเลย

**เฉลยแนวทาง**: การใช้ LPAR แยกบนเครื่องเดียวกันมีข้อได้เปรียบด้านต้นทุนอย่างมาก เพราะ Mainframe เป็น
ฮาร์ดแวร์ที่มีราคาสูงมาก การซื้อเครื่องแยกต่างหากสำหรับ Production และ Test จะเพิ่มต้นทุนมหาศาลโดยไม่
จำเป็น ในขณะที่ LPAR ให้การแยกส่วนที่ปลอดภัยเทียบเท่าการใช้เครื่องแยก (เพราะเป็นการแยกระดับฮาร์ดแวร์)
แต่สามารถแบ่งปันทรัพยากรฮาร์ดแวร์เดียวกันได้อย่างยืดหยุ่น เช่น ในช่วงเวลาที่ระบบ Test ไม่มีใครใช้งาน
ทรัพยากรส่วนนั้นอาจถูกจัดสรรเพิ่มให้ Production ชั่วคราวได้ (ขึ้นกับการตั้งค่า) ทำให้ใช้ทรัพยากรฮาร์ดแวร์
ที่มีราคาแพงได้อย่างคุ้มค่าที่สุด

## ขั้นตอนที่ 504: z/OS Operating System — ส่วนประกอบหลักที่ต้องรู้จัก

### z/OS ประกอบด้วยอะไรบ้าง

z/OS ไม่ใช่ระบบปฏิบัติการตัวเดียวโดด ๆ แต่เป็น**ชุดของส่วนประกอบ (Component)** จำนวนมากที่ทำงาน
ประสานกัน ต่อไปนี้คือส่วนประกอบหลักที่โปรแกรมเมอร์ COBOL ต้องรู้จักเป็นอย่างน้อย:

| ส่วนประกอบ | หน้าที่หลัก | จะเรียนละเอียดใน |
|---|---|---|
| **JES (Job Entry Subsystem)** | รับ จัดคิว และควบคุมการรัน Batch Job ทั้งหมด | Part 052-053 |
| **TSO (Time Sharing Option)** | ให้ผู้ใช้เข้าถึงระบบแบบ Interactive ผ่าน Terminal | Part 054 |
| **ISPF (Interactive System Productivity Facility)** | เครื่องมือแบบเมนู/หน้าจอที่รันบน TSO ใช้แก้ไขโค้ด จัดการไฟล์ | Part 054 |
| **VSAM (Virtual Storage Access Method)** | ระบบจัดเก็บไฟล์ประสิทธิภาพสูงบน Mainframe | Part 055-056 |
| **DB2** | ระบบฐานข้อมูลเชิงสัมพันธ์ของ IBM | Part 057-060 |
| **CICS (Customer Information Control System)** | ระบบประมวลผลธุรกรรมออนไลน์แบบ Real-time | Part 061-064 |
| **RACF (Resource Access Control Facility)** | ระบบควบคุมสิทธิ์การเข้าถึงทรัพยากรทั้งหมดของ z/OS | Part 069 |

### ความสัมพันธ์ของส่วนประกอบเหล่านี้ในภาพรวม

```
                         ผู้ใช้/โปรแกรมเมอร์
                        /                  \
              เข้าถึงแบบโต้ตอบ           ส่ง Job แบบ Batch
                    |                          |
                   TSO                        JES
                    |                          |
                  ISPF                    รัน JCL (Part 052)
              (แก้ไขโค้ด, จัดการไฟล์)              |
                                          รันโปรแกรม COBOL
                                                |
                        +----------------------+----------------------+
                        |                       |                     |
                   อ่าน/เขียนไฟล์            เชื่อมต่อฐานข้อมูล        ประมวลผล Online
                     VSAM                       DB2                    (ผ่าน CICS)
                        |                       |                     |
                        +-----------------------+---------------------+
                                                |
                                    RACF ควบคุมสิทธิ์การเข้าถึงทุกจุด
```

### batch vs online — สองรูปแบบการประมวลผลหลักบน z/OS

z/OS รองรับการประมวลผล 2 รูปแบบหลักที่มีลักษณะแตกต่างกันโดยพื้นฐาน (จะอธิบายลึกในขั้นตอนที่ 505):

- **Batch Processing** — โปรแกรมรันผ่าน JCL โดย JES เป็นผู้ควบคุมคิวและการจัดสรรทรัพยากร ไม่มีผู้ใช้
  โต้ตอบระหว่างการรัน (เหมือนโปรแกรมทั้งหมดที่สร้างในโปรเจกต์เฟส 3 Part 050 ที่ไม่ใช้ `ACCEPT` เลย)
- **Online/Transaction Processing** — โปรแกรมรันผ่าน CICS ตอบสนองผู้ใช้แบบ Real-time (เช่น ระบบ
  ATM, ระบบเคาน์เตอร์ธนาคาร) ที่ต้องตอบกลับภายในเสี้ยววินาที

### ข้อควรระวัง

- คำว่า "ISPF" มักถูกเข้าใจผิดว่าเป็น "ระบบปฏิบัติการ" หรือ "ภาษาโปรแกรม" — จริง ๆ แล้ว ISPF เป็นเพียง
  **เครื่องมือส่วนต่อประสานผู้ใช้แบบเมนู (Menu-driven UI Tool)** ที่รันอยู่บน TSO อีกทีหนึ่ง ไม่ใช่
  ส่วนประกอบระดับ operating system เหมือน JES หรือ VSAM
- RACF ไม่ใช่ส่วนประกอบเดียวที่ทำหน้าที่ควบคุมความปลอดภัยบน z/OS — มีผลิตภัณฑ์คู่แข่งจากค่ายอื่น
  (เช่น ACF2, Top Secret จาก Broadcom) ที่ทำหน้าที่คล้ายกันในบางองค์กร RACF เป็นเพียงตัวที่ IBM
  พัฒนาเองและพบได้บ่อยที่สุด

### แบบฝึกหัดที่ 504.1

**โจทย์**: จงอธิบายว่าทำไมโปรแกรม COBOL ตัวเดียวกัน (เช่นโปรแกรมคำนวณดอกเบี้ย) อาจถูกเรียกใช้งานได้
ทั้งผ่าน JES (แบบ Batch) และผ่าน CICS (แบบ Online) โดยไม่ต้องเขียนโปรแกรมสองเวอร์ชันแยกกัน

**เฉลยแนวทาง**: ตราบใดที่โปรแกรม COBOL เขียนตรรกะทางธุรกิจ (business logic) ไว้อย่างเป็นอิสระจาก
วิธีการเรียกใช้งาน (เช่น รับพารามิเตอร์ผ่าน `LINKAGE SECTION` ตามที่เรียนมาใน Part 031-032 แทนที่จะ
ผูกติดกับการอ่านไฟล์หรือรับ input จากช่องทางใดช่องทางหนึ่งโดยเฉพาะ) โปรแกรมนั้นสามารถถูกเรียกได้จาก
ทั้งสภาพแวดล้อม Batch (ผ่าน JCL ที่ส่งพารามิเตอร์จากไฟล์) และสภาพแวดล้อม Online (ผ่าน CICS ที่ส่ง
พารามิเตอร์จากหน้าจอผู้ใช้แบบ Real-time) เพราะ z/OS จัดเตรียมกลไก "environment" ที่แตกต่างกันให้
โปรแกรมทำงานอยู่ แต่ตัวโปรแกรม COBOL เองไม่จำเป็นต้องรู้ว่าถูกเรียกมาจากทางไหน นี่คือหลักการออกแบบที่
ดีที่หลักสูตรนี้ปลูกฝังมาตลอด (เช่น การแยก `AGINGCLC` ออกมาเป็น subprogram อิสระใน Part 050) ที่มี
ประโยชน์ยิ่งขึ้นไปอีกในโลก Mainframe จริง

## ขั้นตอนที่ 505: Batch Processing เชิงลึก — หัวใจของงาน COBOL บน Mainframe

### ทำไม Batch Processing จึงยังคงสำคัญมากในปี 2026

แม้โลกจะพูดถึง "Real-time" และ "Streaming" กันมากขึ้นเรื่อย ๆ แต่งานจำนวนมหาศาลในองค์กรการเงิน/ธนาคาร
ยังคงพึ่งพา **Batch Processing** เป็นแกนหลัก เพราะงานหลายประเภทมีลักษณะที่**เหมาะกับการประมวลผลเป็น
ชุดใหญ่ในช่วงเวลาที่กำหนด** มากกว่าการประมวลผลทันทีทีละรายการ:

- **การปิดบัญชีสิ้นวัน (End-of-Day Processing)** — ธนาคารต้องคำนวณดอกเบี้ย ปรับปรุงยอดบัญชีทุกบัญชี
  หลังจากตลาดปิดทำการ มักรันเป็น Batch Job ขนาดใหญ่ตอนกลางคืน
- **การประมวลผลรายเดือน** — เช่น การคำนวณดอกเบี้ยบัตรเครดิต, การสร้างใบแจ้งหนี้ (เชื่อมโยงกับระบบบัญชี
  ลูกหนี้ที่สร้างใน Part 050 โดยตรง — ระบบนั้นถูกออกแบบมาให้ทำงานแบบ Batch เพื่อเตรียมความเข้าใจสำหรับ
  จุดนี้พอดี)
- **การรายงานเชิงสถิติขนาดใหญ่** — การรวบรวมข้อมูลธุรกรรมนับล้านรายการเพื่อสร้างรายงานสรุป

### ลักษณะเฉพาะของ Batch Job บน z/OS

1. **ไม่มีการโต้ตอบระหว่างการรัน** — Batch Job ทั้งหมดถูกกำหนดค่าล่วงหน้าผ่าน JCL (Part 052) และรัน
   จนจบโดยไม่มีผู้ใช้พิมพ์ค่าเข้าไประหว่างทาง (สอดคล้องกับที่ Part 050 อธิบายไว้ว่าทำไมระบบบัญชีลูกหนี้
   ไม่ใช้ `ACCEPT` เลย)
2. **ควบคุมด้วย JES (Job Entry Subsystem)** — ผู้ใช้ "ส่ง" (submit) Job เข้าคิว แล้ว JES จะจัดสรร
   ทรัพยากรและรัน Job ตามลำดับความสำคัญ (Priority) ที่กำหนดไว้ ไม่ใช่รันทันทีเสมอไป
3. **Condition Code** — เมื่อแต่ละขั้นตอน (Step) ของ Job รันจบ จะได้ **Return Code** (0-4095, ตาม
   ธรรมเนียมมักใช้ 0=สำเร็จ, 4=มี warning เล็กน้อย, 8=error, 12/16=ปัญหาร้ายแรง) ที่ Step ถัดไป
   สามารถตรวจสอบก่อนตัดสินใจว่าจะรันต่อหรือไม่ (รายละเอียดเต็มรูปแบบจะสอนใน Part 053 เรื่อง Condition
   Codes)
4. **Scheduling** — Batch Job มักถูกตั้งเวลาให้รันอัตโนมัติผ่านระบบ Job Scheduler (เช่น IBM Workload
   Scheduler) ตามตารางเวลาที่กำหนดไว้ล่วงหน้า ไม่ต้องมีคนกด submit ด้วยมือทุกครั้ง (แนวคิดนี้จะขยาย
   ความเพิ่มเติมใน Part 066 เรื่อง Batch Processing Patterns)

### ตารางเปรียบเทียบ Batch Processing บน Mainframe กับสิ่งที่เรียนมาแล้วในหลักสูตรนี้

| แนวคิดบน Mainframe | สิ่งที่ใกล้เคียงที่เรียนมาแล้ว |
|---|---|
| JCL ส่ง Batch Job | คำสั่ง `cobc -x -o program program.cob && ./program` ที่ใช้ตลอดหลักสูตร |
| Return Code ของแต่ละ Step | Exit code ของโปรแกรม (`STOP RUN` กับค่า return code เฉพาะ ที่ยังไม่ได้เจาะลึกในหลักสูตรนี้) |
| ไฟล์ Input/Output ที่ระบุใน JCL ผ่าน DD Statement | `SELECT ... ASSIGN TO "filename.dat"` ใน `FILE-CONTROL` |
| Job Scheduler ตั้งเวลารันอัตโนมัติ | (ไม่มีในหลักสูตรนี้จนถึงจุดนี้ — จะกล่าวถึงใน Part 066) |

### ข้อควรระวัง

- อย่าเข้าใจผิดว่า "Batch" หมายถึง "ช้า" หรือ "ล้าสมัย" — Batch Job บน Mainframe สามารถประมวลผลข้อมูล
  นับพันล้าน record ภายในเวลาไม่กี่ชั่วโมง ด้วยความเร็วที่สถาปัตยกรรม Channel I/O (ขั้นตอนที่ 501)
  รองรับ ซึ่งเร็วกว่าการประมวลผลแบบเดียวกันบนระบบทั่วไปมาก
- โปรแกรม COBOL ที่โปรเจกต์เฟส 3 (Part 050) สร้างขึ้นเป็นเพียง**แนวคิด Batch Processing แบบง่าย**
  (รันบน Linux ไม่ใช่ z/OS จริง ไม่มี JCL/JES ควบคุม) เพื่อเตรียมความคุ้นเคยเชิงแนวคิดเท่านั้น เมื่อ
  ถึง Part 052 คุณจะได้เห็นว่าการรันโปรแกรมเดียวกันบน z/OS จริงต้องมี JCL ห่อหุ้มอย่างไร

### แบบฝึกหัดที่ 505.1

**โจทย์**: จงอธิบายว่าทำไมโปรแกรม `ARPAYMNT` จาก Part 050 (ที่อ่านไฟล์ธุรกรรมการชำระเงินแล้วอัปเดต
ไฟล์ใบแจ้งหนี้/ลูกค้า โดยไม่มี `ACCEPT` เลย) จึงเป็นตัวอย่างที่ดีของแนวคิด Batch Processing แม้จะรัน
บน GnuCOBOL/Linux ไม่ใช่ z/OS จริงก็ตาม

**เฉลยแนวทาง**: `ARPAYMNT` มีคุณสมบัติตรงตามลักษณะเฉพาะของ Batch Job ที่อธิบายในขั้นตอนนี้ครบถ้วน:
(1) ไม่มีการโต้ตอบกับผู้ใช้ระหว่างการรัน ข้อมูลนำเข้าทั้งหมดมาจากไฟล์ `PAYMENTS.DAT` ที่เตรียมไว้
ล่วงหน้า (2) ประมวลผลข้อมูลเป็นชุด (ทุกรายการในไฟล์ธุรกรรม) จนจบในการรันครั้งเดียว (3) แสดงผลสรุป
ท้ายการทำงาน (`PAYMENTS APPLIED`, `PAYMENTS REJECTED`) แทนการโต้ตอบทีละขั้นตอน แม้สภาพแวดล้อมทาง
เทคนิค (ไม่มี JCL/JES ควบคุมจริง) จะต่างจาก Mainframe จริง แต่**รูปแบบการออกแบบโปรแกรม (programming
pattern)** เป็นแนวคิดเดียวกันทุกประการ ซึ่งเป็นเหตุผลที่โปรเจกต์นั้นถูกออกแบบมาแบบนี้ตั้งแต่ต้น เพื่อ
เตรียมความเข้าใจสำหรับเฟส 4 นี้โดยเฉพาะ

## ขั้นตอนที่ 506: TSO และ ISPF — วิธีที่โปรแกรมเมอร์เข้าถึง Mainframe แบบโต้ตอบ

### TSO (Time Sharing Option) คืออะไร

**TSO** คือส่วนประกอบของ z/OS ที่ให้ผู้ใช้หลายคนเข้าถึงเครื่อง Mainframe เครื่องเดียวกัน**พร้อมกัน**
แบบโต้ตอบ (Interactive) ผ่าน Terminal — แนวคิด "Time Sharing" หมายถึงการแบ่งเวลาประมวลผลของ CPU ให้
หลายผู้ใช้ใช้งานพร้อมกันโดยแต่ละคนรู้สึกเหมือนได้ใช้เครื่องคนเดียว (แนวคิดนี้เป็นรากฐานสำคัญของระบบ
คอมพิวเตอร์ยุคใหม่ทั้งหมด รวมถึง Multi-user server บน Linux/Unix ที่พัฒนาต่อยอดมาจากแนวคิดเดียวกัน)

### ISPF (Interactive System Productivity Facility) คืออะไร

**ISPF** คือเครื่องมือส่วนต่อประสานผู้ใช้แบบ**เมนูและฟอร์มข้อความ (Text-based Menu/Panel)** ที่รันอยู่
บน TSO อีกทีหนึ่ง เปรียบเสมือน "IDE" ของโลก Mainframe แม้จะมีลักษณะหน้าตาต่างจาก IDE สมัยใหม่ (เช่น
VS Code ที่เรียนใน Part 002) มาก แต่ทำหน้าที่คล้ายกัน: แก้ไขโค้ด, จัดการไฟล์ (Dataset), ส่ง Job,
ดูผลลัพธ์การรัน, และเครื่องมือช่วยพัฒนาอื่น ๆ

### หน้าตาโดยทั่วไปของ ISPF (คำอธิบายเชิงแนวคิด)

ISPF ทำงานผ่านระบบเมนูที่มีหมายเลขกำกับ ผู้ใช้พิมพ์หมายเลขตัวเลือกแล้วกด Enter เพื่อเข้าสู่เมนูย่อย
ตัวอย่างโครงสร้างเมนูหลักโดยทั่วไป (**หมายเหตุ: นี่คือคำอธิบายเชิงแนวคิดของโครงสร้างเมนูมาตรฐาน
ไม่ใช่การจำลองหน้าจอจริงที่รันได้ในสภาพแวดล้อมนี้**):

```
ISPF PRIMARY OPTION MENU
   0  SETTINGS    - ตั้งค่าพารามิเตอร์ทั่วไปของ ISPF
   1  BROWSE      - ดูเนื้อหาไฟล์ (อ่านอย่างเดียว)
   2  EDIT        - แก้ไขไฟล์ (เขียนโค้ด COBOL ที่นี่)
   3  UTILITIES   - เครื่องมือจัดการ Dataset (คัดลอก, ลบ, เปลี่ยนชื่อ)
   4  FOREGROUND  - คอมไพล์/ทดสอบโปรแกรมแบบ Interactive
   6  COMMAND     - รันคำสั่ง TSO โดยตรง
   D  SDSF        - ดูสถานะ Job ที่ส่งไปรัน (Part 053 จะกล่าวถึง SDSF)
```

### ทำไมหลักสูตรนี้ไม่ได้ให้ทดลองใช้ ISPF จริง

ISPF เป็นซอฟต์แวร์ที่ผูกติดกับ z/OS โดยตรง ไม่สามารถติดตั้งแยกต่างหากบนเครื่อง Linux/Windows ทั่วไปได้
เหมือน GnuCOBOL การเข้าถึง ISPF จริงต้องผ่านการเชื่อมต่อ Terminal Emulator (เช่น IBM Personal
Communications, x3270) ไปยังเครื่อง Mainframe จริงหรือ LPAR ที่มีสิทธิ์เข้าถึง — Part 054 จะอธิบาย
รายละเอียดการใช้งาน TSO/ISPF เชิงแนวคิดและตัวอย่างหน้าจอเพิ่มเติม แต่ยังคงเป็นเนื้อหาเชิงทฤษฎีเช่นเดียว
กับ Part นี้

### ข้อควรระวัง

- อย่าสับสนระหว่าง TSO (ระบบพื้นฐานที่ให้ Time Sharing) กับ ISPF (โปรแกรมเมนูที่รันอยู่บน TSO) — ในทาง
  เทคนิค สามารถใช้ TSO โดยไม่ผ่าน ISPF ได้ (พิมพ์คำสั่ง TSO ตรง ๆ ที่ Prompt) แต่ในทางปฏิบัติแทบทุก
  องค์กรใช้ ISPF เป็นด่านหน้าเสมอเพราะสะดวกกว่ามาก
- หมายเลขเมนูใน ISPF (เช่น "2" สำหรับ EDIT) **อาจแตกต่างกันได้ในแต่ละองค์กร** เพราะ ISPF รองรับการ
  ปรับแต่งเมนูได้ตามความต้องการของแต่ละองค์กร ตัวอย่างข้างต้นเป็นโครงสร้างมาตรฐานทั่วไปเท่านั้น

### แบบฝึกหัดที่ 506.1

**โจทย์**: จงเปรียบเทียบแนวคิด "Time Sharing" ของ TSO กับประสบการณ์การใช้ VS Code ร่วมกับ GnuCOBOL
ที่เรียนมาตั้งแต่ Part 002 ว่าต่างกันอย่างไรในแง่ของ "ใครเป็นเจ้าของทรัพยากรประมวลผล"

**เฉลยแนวทาง**: เมื่อใช้ VS Code กับ GnuCOBOL บนเครื่องส่วนตัว (ตามที่เรียนมาตั้งแต่ Part 002) ผู้เรียน
เป็นเจ้าของทรัพยากรประมวลผล (CPU, Memory) ทั้งหมดของเครื่องนั้นแต่เพียงผู้เดียว ไม่ต้องแบ่งปันกับใคร
ในขณะที่ TSO ทำให้ผู้ใช้**หลายสิบหรือหลายร้อยคนใช้เครื่อง Mainframe เครื่องเดียวกันพร้อมกัน**โดยระบบ
ปฏิบัติการ (z/OS) เป็นผู้จัดสรรเวลาประมวลผลของ CPU ให้แต่ละคนอย่างยุติธรรมและรวดเร็วมากจนผู้ใช้แต่ละคน
รู้สึกเหมือนได้ใช้เครื่องคนเดียว (แนวคิด "Time Slicing") นี่คือความแตกต่างพื้นฐานระหว่างรูปแบบ
"คอมพิวเตอร์ส่วนบุคคล (Personal Computing)" ที่หลักสูตรนี้ใช้สอนเฟส 1-3 กับรูปแบบ "คอมพิวเตอร์
ส่วนกลางที่ใช้ร่วมกัน (Shared Central Computing)" ที่เป็นหัวใจของ Mainframe มาตั้งแต่ต้น

## ขั้นตอนที่ 507: หลักการตั้งชื่อ Dataset บน z/OS

### Dataset คืออะไร — เทียบกับ "ไฟล์" ที่คุ้นเคย

บน z/OS คำว่า **"Dataset"** ใช้แทนคำว่า "ไฟล์ (File)" ที่คุ้นเคยจากโลก Linux/Windows แนวคิดพื้นฐาน
คล้ายกัน (คือที่เก็บข้อมูลที่มีชื่อเรียก) แต่มีกฎการตั้งชื่อและคุณสมบัติที่จำเพาะกับ z/OS มากกว่ามาก
ซึ่งเป็นความรู้พื้นฐานที่จำเป็นก่อนเรียน JCL ใน Part 052 (ที่ DD Statement ต้องระบุชื่อ Dataset)

### กฎการตั้งชื่อ Dataset มาตรฐาน

ชื่อ Dataset บน z/OS ประกอบด้วย **Qualifier** หลายส่วนคั่นด้วยจุด (`.`) เช่น:

```
USER01.COBOL.SOURCE(PAYROLL)
```

| ส่วน | ชื่อเรียก | ความหมาย |
|---|---|---|
| `USER01` | High-Level Qualifier (HLQ) | มักเป็นรหัสผู้ใช้หรือรหัสโครงการ ใช้แบ่งพื้นที่เจ้าของ |
| `COBOL` | Middle-Level Qualifier | จัดหมวดหมู่ย่อยตามต้องการ (จะมีกี่ระดับก็ได้) |
| `SOURCE` | Middle/Low-Level Qualifier | ระบุประเภทเนื้อหา (ในที่นี้คือซอร์สโค้ด) |
| `(PAYROLL)` | Member Name | ชื่อสมาชิกภายใน PDS (อธิบายด้านล่าง) |

**กฎสำคัญ**:
- แต่ละ Qualifier ยาวได้สูงสุด **8 ตัวอักษร**
- ต้องขึ้นต้นด้วยตัวอักษร (A-Z) หรือสัญลักษณ์พิเศษบางตัว (`#`, `@`, `$`) ตามด้วยตัวอักษรหรือตัวเลข
- ความยาวรวมทั้งชื่อ (ไม่รวม Member Name) ต้องไม่เกิน **44 ตัวอักษร** (รวมจุดคั่น)
- **ไม่แยกตัวพิมพ์เล็ก-ใหญ่** (case-insensitive) ตามธรรมเนียม COBOL ที่คุ้นเคยมาตลอดหลักสูตร

### PDS (Partitioned Dataset) — "โฟลเดอร์" ของโลก Mainframe

**PDS** คือ Dataset ประเภทพิเศษที่ทำหน้าที่คล้าย "โฟลเดอร์" เก็บไฟล์ย่อยหลายไฟล์ (เรียกว่า **Member**)
ไว้ภายใต้ชื่อ Dataset เดียว เช่น `USER01.COBOL.SOURCE` อาจเป็น PDS ที่เก็บ Member ชื่อ `PAYROLL`,
`INVENTORY`, `ARSETUP` (คุ้นชื่อจาก Part 050!) ไว้ภายในพร้อมกัน — การอ้างอิง Member ทำผ่านวงเล็บ
`USER01.COBOL.SOURCE(ARSETUP)` ตามที่แสดงในตัวอย่างข้างต้น

```
USER01.COBOL.SOURCE           <- PDS (เปรียบเสมือนโฟลเดอร์)
   ├── ARSETUP                <- Member (เปรียบเสมือนไฟล์ในโฟลเดอร์)
   ├── ARPAYMNT
   ├── AGINGCLC
   └── ARREPORT
```

**PDSE (Partitioned Dataset Extended)** คือรุ่นปรับปรุงของ PDS ที่แก้ข้อจำกัดบางอย่างของ PDS ดั้งเดิม
(เช่น ปัญหาพื้นที่ว่างกระจัดกระจายที่ต้อง "compress" เป็นระยะ) เป็นรูปแบบที่นิยมใช้มากขึ้นในปัจจุบัน

### เปรียบเทียบกับสิ่งที่คุ้นเคยจากหลักสูตรนี้

| แนวคิด z/OS | สิ่งที่ใกล้เคียงในหลักสูตรนี้ |
|---|---|
| Dataset | ไฟล์ (`CUSTOMER.DAT`, `ARSETUP.cob`) |
| PDS/PDSE | โฟลเดอร์ (เช่น `parts/`, `copybooks/` ใน Part 050) |
| Member ภายใน PDS | ไฟล์แต่ละไฟล์ในโฟลเดอร์ (`ARSETUP.cob`, `ARPAYMNT.cob`) |
| Catalog (ระบบ index ของ Dataset ทั้งหมด) | ระบบไฟล์ (File System) ของ Linux/Windows |

### ข้อควรระวัง

- อย่าใช้จุด (`.`) เกิน 21 จุดในชื่อ Dataset (จำกัดจำนวน Qualifier สูงสุด 22 ส่วน) แม้ความยาวรวมจะ
  ไม่เกิน 44 ตัวอักษรก็ตาม เป็นกฎที่แยกต่างหากจากกฎความยาวรวม
- ชื่อ Dataset ที่ขึ้นต้นด้วยตัวเลขไม่ได้รับอนุญาต (ต้องขึ้นต้นด้วยตัวอักษรหรือสัญลักษณ์พิเศษที่กำหนด
  ไว้เท่านั้น) ต่างจากชื่อไฟล์ทั่วไปบน Linux/Windows ที่มักไม่มีข้อจำกัดนี้

### แบบฝึกหัดที่ 507.1

**โจทย์**: หากต้องการจัดเก็บโปรแกรมทั้ง 4 ตัวจากโปรเจกต์ Part 050 (`ARSETUP`, `ARPAYMNT`, `AGINGCLC`,
`ARREPORT`) ไว้บน z/OS จริง ให้ลองออกแบบชื่อ Dataset (PDS) ที่เหมาะสมสำหรับเก็บซอร์สโค้ดทั้งหมดนี้
พร้อมอธิบายเหตุผลของแต่ละ Qualifier ที่เลือกใช้

**เฉลยแนวทาง**: ตัวอย่างที่เหมาะสม เช่น `ARSYS.COBOL.SOURCE` โดย `ARSYS` (Accounts Receivable
System) เป็น High-Level Qualifier ที่สื่อความหมายว่าเป็นของระบบบัญชีลูกหนี้โดยเฉพาะ (แยกจากโปรเจกต์
อื่นในองค์กรที่อาจใช้ HLQ ต่างกัน) `COBOL` บอกว่าเป็นหมวดหมู่ของโค้ด COBOL (แยกจาก JCL ที่อาจเก็บใน
`ARSYS.JCL` ในอนาคตตาม Part 052) และ `SOURCE` บอกว่าเป็นซอร์สโค้ดต้นฉบับ (แยกจาก Copybook ที่อาจเก็บ
ใน `ARSYS.COBOL.COPYLIB` ตามธรรมเนียมที่มักพบในองค์กรจริง) จากนั้นโปรแกรมทั้ง 4 ตัวจะถูกเก็บเป็น
Member แยกกันภายใน PDS เดียวนี้: `ARSYS.COBOL.SOURCE(ARSETUP)`,
`ARSYS.COBOL.SOURCE(ARPAYMNT)`, `ARSYS.COBOL.SOURCE(AGINGCLC)`, และ
`ARSYS.COBOL.SOURCE(ARREPORT)`

| **JCL** | ทดแทนคำสั่ง `cobc`/`./program` ที่ใช้ตลอดหลักสูตร ด้วยภาษาที่ z/OS เข้าใจ |
| **VSAM (KSDS)** | แนวคิดเดียวกับ Indexed File/ISAM ที่เรียนเต็มรูปแบบใน Part 028 เพียงแต่เป็น
  implementation ของ IBM บน Mainframe โดยเฉพาะ |
| **DB2** | ก้าวข้ามจากไฟล์ (File-based) ไปสู่ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) อย่างเป็น
  ทางการ ต่างจาก Part 075 ที่สอน MySQL/PostgreSQL ในบริบทของ COBOL สมัยใหม่ |
| **CICS** | ระบบ Online ที่ทำหน้าที่คล้าย "Web Server" ของโลก Mainframe แต่มีก่อนอินเทอร์เน็ตเสียอีก |
| **RACF** | ทำหน้าที่คล้าย permission system ของ Linux (`chmod`, `chown`) แต่ครอบคลุมและละเอียดกว่ามาก |

### ทำไมหลักสูตรนี้จัดลำดับเฟส 4 แบบนี้

สังเกตว่าลำดับการเรียนใน Part นี้ตามด้วย JCL → TSO/ISPF → VSAM → DB2 → CICS นั้นไม่ใช่การสุ่ม แต่
สะท้อน**ลำดับการทำงานจริงของโปรแกรมเมอร์ Mainframe มือใหม่**: ต้องรู้จักสภาพแวดล้อมก่อน (Part 051) →
ต้องรันโปรแกรมได้ก่อน (JCL, Part 052-053) → ต้องแก้ไขโค้ดได้ (TSO/ISPF, Part 054) → จึงค่อยขยายไปสู่
การจัดการข้อมูลที่ซับซ้อนขึ้น (VSAM, DB2) → และสุดท้ายคือการสร้างระบบที่ผู้ใช้จริงโต้ตอบด้วย (CICS)

### ข้อควรระวัง

- อย่าคาดหวังว่าจะ "เชี่ยวชาญ" ทั้ง 5 เทคโนโลยีนี้ได้ภายในเวลาสั้น ๆ — แต่ละเทคโนโลยี (โดยเฉพาะ CICS
  และ DB2) เป็นสาขาอาชีพที่มีความลึกในตัวเองมาก ถึงขนาดมีตำแหน่งงานเฉพาะทาง (เช่น "CICS Systems
  Programmer", "DB2 Database Administrator") หลักสูตรนี้มุ่งสร้าง**ความเข้าใจพื้นฐานที่ถูกต้องและ
  กว้างขวางพอ**ที่จะทำงานร่วมกับทีมที่เชี่ยวชาญเฉพาะทางเหล่านี้ได้ ไม่ใช่การสร้างผู้เชี่ยวชาญระดับสูง
  ในทุกด้านพร้อมกัน
- IMS (Part 065) มักถูกมองข้ามในเนื้อหาการเรียน Mainframe ทั่วไปเพราะเก่าแก่กว่า DB2/CICS มาก แต่
  ยังคงใช้งานจริงในหลายองค์กรขนาดใหญ่ (โดยเฉพาะสถาบันการเงินและหน่วยงานรัฐบาลสหรัฐฯ ที่ใช้มานานหลาย
  ทศวรรษ) จึงยังคงมีความสำคัญที่ต้องรู้จักไว้

### แบบฝึกหัดที่ 508.1

**โจทย์**: จงอธิบายว่าทำไมการเรียน VSAM (Part 055-056) จึงควรมาหลังจากที่ได้เรียน Indexed File/ISAM
อย่างละเอียดแล้วใน Part 028 แทนที่จะสอน VSAM ไปพร้อมกับ Indexed File ตั้งแต่ต้น

**เฉลยแนวทาง**: การเรียน Indexed File/ISAM ผ่าน GnuCOBOL ใน Part 028 ทำให้ผู้เรียนเข้าใจ**แนวคิดพื้น
ฐานของการเข้าถึงข้อมูลด้วย Key** (RECORD KEY, ACCESS MODE, การค้นหา/แก้ไข/ลบ record โดยตรง) ได้อย่าง
มั่นคงก่อน โดยใช้เครื่องมือที่เข้าถึงได้ง่าย (GnuCOBOL บนเครื่องส่วนตัว) เมื่อมาถึง VSAM ใน Part 055-056
ผู้เรียนจะสามารถ**เชื่อมโยงความรู้เดิม**เข้ากับรายละเอียดเฉพาะของ VSAM ได้ทันที (เช่น VSAM KSDS ก็คือ
Indexed File ที่เรารู้จักอยู่แล้ว เพียงแต่มี option และรายละเอียดการจัดการพื้นที่ที่ซับซ้อนกว่า) แทนที่
จะต้องเรียนทั้งแนวคิดพื้นฐานและรายละเอียดเฉพาะของ VSAM ไปพร้อมกันซึ่งจะหนักเกินไปสำหรับจุดเริ่มต้น
ของเฟส 4 — นี่คือหลักการ "ค่อยเป็นค่อยไปแต่ไม่ช้าเกินไป" ที่ Part 001 ระบุไว้เป็นหลักการของหลักสูตร

## ขั้นตอนที่ 509: ทำไม Mainframe ยังคงสำคัญในปี 2026 — มุมมองเศรษฐกิจและอาชีพ

### ทบทวนสถิติจาก Part 001 ในบริบทของ Mainframe โดยเฉพาะ

Part 001 ได้แสดงสถิติที่น่าตกใจเกี่ยวกับความสำคัญของ COBOL ไว้แล้ว ขั้นตอนนี้จะเจาะจงมาที่ **Mainframe
โดยเฉพาะ** ในฐานะแพลตฟอร์มที่โค้ด COBOL เหล่านั้นทำงานอยู่จริง:

- ธุรกรรมทางการเงินระดับโลกจำนวนมหาศาลยังคงประมวลผลผ่านระบบ Mainframe เป็นแกนหลัก โดยเฉพาะในภาค
  Core Banking, การชำระเงินระหว่างธนาคาร (Interbank Settlement), และระบบประกันภัยที่มีข้อมูล
  กรมธรรม์ระยะยาว
- อุตสาหกรรม Mainframe ยังคงมีการลงทุนด้านฮาร์ดแวร์และซอฟต์แวร์อย่างต่อเนื่องจาก IBM และพันธมิตร
  (Broadcom, BMC และอื่น ๆ) ซึ่งบ่งชี้ว่าตลาดยังมีความต้องการเชิงพาณิชย์ที่แท้จริง ไม่ใช่เทคโนโลยีที่
  กำลังจะถูกทอดทิ้ง

### ทำไมองค์กรจึงยังไม่ย้ายออกจาก Mainframe อย่างสมบูรณ์

นอกเหนือจากเหตุผลที่ Part 001 อธิบายไว้แล้ว (ความเสี่ยง, ต้นทุน, ประสิทธิภาพที่พิสูจน์แล้ว) เมื่อ
มองในมุมสถาปัตยกรรม Mainframe โดยเฉพาะ มีเหตุผลเพิ่มเติมคือ:

1. **ไม่มีแพลตฟอร์มทางเลือกใดที่ให้ RAS (ขั้นตอนที่ 501) ในระดับเดียวกันได้ในราคาที่เทียบเคียงได้**
   สำหรับปริมาณธุรกรรมระดับที่ธนาคารขนาดใหญ่ต้องการ
2. **ต้นทุนการย้ายระบบ (Migration Cost) สูงกว่ามูลค่าที่จะประหยัดได้ในระยะสั้น-กลาง** โดยเฉพาะเมื่อ
   คำนึงถึงความเสี่ยงของการหยุดชะงักระบบสำคัญระดับชาติ
3. **แนวโน้มปัจจุบันคือ "Modernization" ไม่ใช่ "Replacement"** — องค์กรจำนวนมากเลือกที่จะเชื่อมต่อ
   Mainframe เข้ากับเทคโนโลยีสมัยใหม่ผ่าน API (จะเรียนเต็มรูปแบบในเฟส 5 ของหลักสูตร Part 071-085)
   แทนที่จะทิ้ง Mainframe ไปทั้งหมด — Mainframe ยังคงเป็น "ระบบหลังบ้าน (Back-end)" ที่เชื่อถือได้
   ในขณะที่ผู้ใช้ปลายทางโต้ตอบผ่านแอปพลิเคชันมือถือ/เว็บสมัยใหม่ที่เชื่อมต่อเข้ามา

### เส้นทางอาชีพในสาย Mainframe

ทบทวนจาก Part 001 ขั้นตอนที่ 4 ที่กล่าวถึงตำแหน่งงานสาย COBOL ไว้แล้ว เมื่อเจาะจงมาที่สาย Mainframe
โดยเฉพาะ ตำแหน่งงานที่เกี่ยวข้องโดยตรงกับเนื้อหาเฟส 4 นี้ ได้แก่:

| ตำแหน่งงาน | ทักษะที่เกี่ยวข้องกับเฟส 4 |
|---|---|
| Mainframe Systems Programmer | z/OS, JCL, LPAR management, Performance Tuning |
| COBOL/CICS Application Developer | JCL, CICS, VSAM |
| DB2 Database Administrator (DBA) | DB2, SQL, Performance Tuning |
| Mainframe Security Administrator | RACF, Security Policies |
| Batch Processing Specialist | JCL, DFSORT, Job Scheduling |

### ข้อควรระวัง

- อย่าตีความเนื้อหานี้ว่า "ต้องเรียนเฟส 4 ทั้งหมดให้ลึกที่สุดเพื่อหางานได้" — ตลาดงานจริงมักต้องการ
  ผู้ที่มีความเชี่ยวชาญเฉพาะทางในบางเทคโนโลยี (เช่น เชี่ยวชาญ CICS แต่ไม่จำเป็นต้องเชี่ยวชาญ IMS ด้วย)
  เป้าหมายของเฟส 4 คือให้ความเข้าใจภาพรวมที่ครอบคลุมเพื่อเลือกเส้นทางเฉพาะทางต่อไปได้อย่างมีข้อมูล
- สถิติและตัวเลขทางเศรษฐกิจเกี่ยวกับ Mainframe เปลี่ยนแปลงตามเวลาและมักไม่มีแหล่งข้อมูลที่แม่นยำ 100%
  (เนื่องจากหลายระบบเป็นข้อมูลภายในองค์กรที่ไม่เปิดเผยต่อสาธารณะ) ควรมองตัวเลขเหล่านี้เป็นภาพรวมเชิง
  แนวโน้ม ไม่ใช่ข้อเท็จจริงที่แม่นยำระดับทศนิยม

### แบบฝึกหัดที่ 509.1

**โจทย์**: จงอธิบายความแตกต่างระหว่างกลยุทธ์ "Modernization" กับ "Replacement" ในบริบทของ Mainframe
พร้อมยกตัวอย่างว่าความรู้จาก Part 050 (โปรเจกต์ระบบบัญชีลูกหนี้) จะเกี่ยวข้องกับกลยุทธ์ Modernization
อย่างไร

**เฉลยแนวทาง**: **Replacement** หมายถึงการเขียนระบบใหม่ทั้งหมดด้วยเทคโนโลยีใหม่แล้วเลิกใช้ระบบเดิม
ทั้งหมด ซึ่งมีความเสี่ยงสูงตามที่ Part 001 อธิบายไว้ ในขณะที่ **Modernization** หมายถึงการคง Logic
ทางธุรกิจหลักที่ผ่านการพิสูจน์มาแล้ว (เช่น ตรรกะการคำนวณอายุหนี้ใน `AGINGCLC` จาก Part 050) ไว้บน
Mainframe ต่อไป แต่เพิ่มช่องทางเชื่อมต่อสมัยใหม่ (เช่น REST API ที่จะเรียนใน Part 073) เข้ามาห่อหุ้ม
ระบบเดิม ทำให้แอปพลิเคชันมือถือหรือเว็บสมัยใหม่สามารถเรียกใช้ข้อมูลอายุหนี้จากระบบ Mainframe ได้โดย
ไม่ต้องเขียนตรรกะการคำนวณอายุหนี้ใหม่เลย ระบบที่สร้างใน Part 050 แม้จะรันบน GnuCOBOL/Linux แต่โครงสร้าง
แบบแยกส่วน (Subprogram `AGINGCLC` ที่มี interface ชัดเจนผ่าน `LINKAGE SECTION`) เป็นรูปแบบที่เหมาะสม
อย่างยิ่งสำหรับแนวทาง Modernization แบบนี้ในอนาคต เพราะสามารถ "ห่อหุ้ม" ด้วยเทคโนโลยีใหม่ได้โดยไม่ต้อง
แตะต้องตรรกะภายในเลย

## ขั้นตอนที่ 510: เตรียมความพร้อมก่อนเข้าสู่ Part 052 — สรุปแนวคิดสำคัญและสิ่งที่ควรรู้ก่อนเรียน JCL

### ทบทวนคำศัพท์สำคัญทั้งหมดของ Part นี้

ก่อนไปเรียน JCL ใน Part 052 ให้แน่ใจว่าคุณเข้าใจคำศัพท์ต่อไปนี้อย่างชัดเจน (ทบทวนจาก Glossary ใน
Part 001 ที่เคยแนะนำคำศัพท์บางคำไว้แบบผ่าน ๆ):

| คำศัพท์ | สรุปความหมาย | อธิบายละเอียดในขั้นตอนที่ |
|---|---|---|
| Mainframe | คอมพิวเตอร์ระดับองค์กรเน้นความน่าเชื่อถือและปริมาณธุรกรรมสูง | 501 |
| z/Architecture | สถาปัตยกรรม 64-bit ปัจจุบันของ Mainframe ตระกูล IBM Z | 502 |
| z/OS | ระบบปฏิบัติการหลักบน Mainframe (สืบทอดจาก MVS) | 502, 504 |
| LPAR | การแบ่ง Mainframe เครื่องเดียวเป็นหลายเครื่องเสมือนระดับฮาร์ดแวร์ | 503 |
| JES | ส่วนประกอบ z/OS ที่ควบคุมคิวและการรัน Batch Job | 504-505 |
| TSO | ระบบให้ผู้ใช้หลายคนเข้าถึง Mainframe พร้อมกันแบบโต้ตอบ | 506 |
| ISPF | เครื่องมือเมนู/หน้าจอที่รันบน TSO สำหรับแก้ไขโค้ด/จัดการไฟล์ | 506 |
| Dataset | คำเรียก "ไฟล์" บน z/OS พร้อมกฎการตั้งชื่อเฉพาะ | 507 |
| PDS/PDSE | Dataset ที่เก็บ Member หลายตัว คล้ายโฟลเดอร์ | 507 |
| Batch Processing | การประมวลผลเป็นชุดโดยไม่มีการโต้ตอบระหว่างรัน | 505 |
| VSAM, DB2, CICS, IMS | เทคโนโลยีหลักที่จะเรียนตลอดเฟส 4 | 508 |

### เตรียมความเข้าใจ: JCL จะเข้ามาแทนที่อะไรในเวิร์กโฟลว์ที่คุ้นเคย

ตลอดหลักสูตรนี้ตั้งแต่ Part 002 คุณคุ้นเคยกับการคอมไพล์และรันโปรแกรมด้วยคำสั่ง shell ตรงไปตรงมา:

```bash
cobc -x -o ARSETUP ARSETUP.cob
./ARSETUP
```

บน z/OS ไม่มี "shell" แบบ Linux/Unix ให้พิมพ์คำสั่งแบบนี้โดยตรง (แม้ z/OS UNIX System Services จะมี
Shell แบบ Unix ให้ใช้งานได้ในบางกรณี แต่ไม่ใช่วิธีมาตรฐานสำหรับรัน COBOL Batch Job) แทนที่ด้วยการเขียน
**JCL (Job Control Language)** ที่เป็นภาษาเฉพาะทางบอก z/OS ว่า "จะรันโปรแกรมอะไร (`EXEC PGM=`)"
"ต้องใช้ไฟล์ไหนบ้าง (`DD` Statement)" และ "ควรจัดสรรทรัพยากรอย่างไร" — Part 052 จะแนะนำไวยากรณ์นี้
ทีละส่วนอย่างละเอียด โดยใช้ความรู้เรื่อง Dataset (ขั้นตอนที่ 507) และ Batch Processing (ขั้นตอนที่
505) ที่เพิ่งเรียนไปเป็นพื้นฐาน

### ทำไมการเรียน JCL จึงยังคง "เขียนโค้ด COBOL ไม่ได้" ใน Part 052

ผู้เรียนบางคนอาจคาดหวังว่า Part 052 จะกลับไปเขียนและคอมไพล์โค้ด COBOL เหมือนเฟส 1-3 — แต่ตามที่ระบุ
ไว้ในคำนำของ Part นี้และในคำสั่งของหลักสูตร (`docs/COURSE-OUTLINE.md`) **JCL ไม่ใช่ COBOL และไม่
สามารถคอมไพล์/รันด้วย `cobc` หรือบน Linux sandbox นี้ได้เลย** เพราะ JCL ต้องอาศัย JES ของ z/OS จริง
(หรือ Mainframe Emulator เช่น Hercules) ในการประมวลผล — Part 052 จะยังคงนำเสนอไวยากรณ์ JCL ที่ถูกต้อง
ตามมาตรฐาน IBM แต่จะระบุไว้อย่างชัดเจนและตรงไปตรงมาว่าตัวอย่างเหล่านั้น**เป็นข้อมูลอ้างอิง ไม่ใช่โค้ด
ที่รันทดสอบได้ในสภาพแวดล้อมของหลักสูตรนี้**

### ข้อควรระวัง

- อย่าพยายามนำไวยากรณ์ JCL ที่จะเรียนใน Part 052 ไปรันด้วย `cobc` หรือเครื่องมือใด ๆ ในสภาพแวดล้อม
  Linux ของหลักสูตรนี้ — จะไม่มีทางทำงานได้เพราะ JCL ไม่ใช่ภาษาโปรแกรม แต่เป็นภาษาสั่งงานระบบปฏิบัติการ
  ที่ผูกติดกับ z/OS โดยเฉพาะ
- ความรู้เชิงแนวคิดจาก Part 051 นี้ (LPAR, JES, TSO, Dataset ฯลฯ) เป็น**พื้นฐานที่จำเป็น**ก่อนเข้าใจ
  JCL ได้อย่างมีความหมาย — หากยังไม่แม่นยำเรื่องความแตกต่างระหว่าง Dataset กับ PDS หรือแนวคิด Batch
  Processing ควรย้อนกลับมาทบทวนขั้นตอนที่ 505 และ 507 ก่อนไปต่อ

### แบบฝึกหัดที่ 510.1

**โจทย์**: จงสรุปด้วยคำพูดของคุณเองว่า หากเพื่อนที่ไม่เคยเรียนหลักสูตรนี้ถามว่า "ทำไม Part 052 (JCL)
ถึงไม่มีโค้ด COBOL ให้รันเหมือน Part อื่น ๆ ก่อนหน้า" คุณจะอธิบายอย่างไรให้เข้าใจง่ายที่สุด

**เฉลยแนวทาง**: คำตอบควรครอบคลุมประเด็นหลัก 2 ข้อ: (1) **JCL เป็นคนละภาษากับ COBOL โดยสิ้นเชิง** —
COBOL คือภาษาที่ใช้เขียนตรรกะของโปรแกรม (คำนวณ, ตัดสินใจ, จัดการข้อมูล) ในขณะที่ JCL เป็นภาษาที่บอก
ระบบปฏิบัติการ z/OS ว่า "จะรันโปรแกรมไหน ด้วยไฟล์อะไรบ้าง" เปรียบได้กับความแตกต่างระหว่างการเขียน
โปรแกรม Python กับการเขียน Shell Script ที่สั่งรันโปรแกรม Python นั้น (2) **z/OS (ระบบปฏิบัติการที่
เข้าใจ JCL) เป็นซอฟต์แวร์เฉพาะทางของ IBM ที่ผูกติดกับฮาร์ดแวร์ Mainframe** ไม่สามารถติดตั้งบนเครื่อง
Linux ทั่วไปได้เหมือน GnuCOBOL ทำให้สภาพแวดล้อมของหลักสูตรนี้ไม่สามารถรัน JCL จริงได้ ต่างจาก COBOL
ที่ GnuCOBOL (Open Source, ติดตั้งได้ทุกที่) ทำให้ทดสอบได้จริงมาตลอดเฟส 1-3 — ดังนั้น Part 052 จึง
เน้นสอนไวยากรณ์ JCL ที่ถูกต้องตามมาตรฐานเพื่อความเข้าใจ แต่ไม่สามารถให้ "รันจริง" ในสภาพแวดล้อมนี้ได้

## สรุปท้ายบท

Part นี้เป็นจุดเริ่มต้นของเฟส 4 (Mainframe/Enterprise) และวางรากฐานความเข้าใจเชิงแนวคิดที่จำเป็นก่อน
เรียน JCL/VSAM/DB2/CICS ในรายละเอียด ครอบคลุม:

- นิยามของ Mainframe และคุณสมบัติ RAS ที่ทำให้แตกต่างจากเซิร์ฟเวอร์ทั่วไป โดยเฉพาะสถาปัตยกรรม Channel
  I/O ที่แยกจาก CPU หลัก
- ประวัติศาสตร์ตั้งแต่ System/360 (1964) ผ่าน MVS จนถึง z/OS ปัจจุบัน และความสัมพันธ์เชิงวิวัฒนาการ
  ของชื่อระบบปฏิบัติการเหล่านี้
- LPAR และการแบ่งทรัพยากร Mainframe ระดับฮาร์ดแวร์ เปรียบเทียบกับ Virtual Machine ที่คุ้นเคย
- ส่วนประกอบหลักของ z/OS: JES, TSO, ISPF, VSAM, DB2, CICS, RACF และความสัมพันธ์ระหว่างกัน
- แนวคิด Batch Processing เชิงลึก และความเชื่อมโยงกับโปรเจกต์ระบบบัญชีลูกหนี้จาก Part 050
- TSO/ISPF ในฐานะช่องทางที่โปรแกรมเมอร์เข้าถึงและแก้ไขโค้ดบน Mainframe
- หลักการตั้งชื่อ Dataset, PDS/PDSE ที่เป็นพื้นฐานสำคัญก่อนเรียน JCL
- ภาพรวมแผนที่การเดินทางทั้งเฟส 4 และความเชื่อมโยงของแต่ละเทคโนโลยีกับความรู้เดิม
- มุมมองเศรษฐกิจและอาชีพในสาย Mainframe พร้อมความแตกต่างระหว่าง Modernization กับ Replacement
- การเตรียมความพร้อมและคำเตือนที่ชัดเจนก่อนเข้าสู่ Part 052

จำไว้เสมอว่า Part นี้ **ไม่มีโค้ดให้คอมไพล์หรือรันจริง** ตามที่ได้ระบุไว้ตั้งแต่ต้น — นี่ไม่ใช่ข้อบกพร่อง
ของเนื้อหา แต่เป็นข้อจำกัดที่ซื่อสัตย์ของสภาพแวดล้อมการเรียนรู้ที่ใช้ตลอดหลักสูตรนี้ (GnuCOBOL บน
Linux) ความรู้เชิงแนวคิดที่ได้จาก Part นี้จะกลายเป็นรากฐานสำคัญที่ทำให้ Part 052 เป็นต้นไปเข้าใจง่าย
ขึ้นมาก แม้ตัวอย่างโค้ด JCL ในบทถัดไปจะเป็นไวยากรณ์อ้างอิงที่ไม่สามารถรันในสภาพแวดล้อมนี้ได้ก็ตาม
