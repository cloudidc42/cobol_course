## ขั้นตอนที่ 891: ทำไมการบริหารโปรเจกต์ COBOL ขนาดใหญ่แตกต่างจากโปรเจกต์ซอฟต์แวร์ทั่วไป

### สี่ลักษณะเฉพาะที่ทำให้โปรเจกต์ COBOL Enterprise ต่างจากโปรเจกต์ทั่วไป

ทบทวนจาก Part 001 และ Part 086: ระบบ COBOL ขนาดใหญ่มีลักษณะที่ผู้บริหารโครงการต้องเข้าใจก่อนนำวิธีการ
บริหารโปรเจกต์แบบทั่วไปมาใช้ตรง ๆ:

1. **อายุของระบบและความรู้ที่กระจัดกระจาย (Legacy Age & Knowledge Fragmentation)** — ระบบที่เขียนเมื่อ
   30-40 ปีก่อนมักไม่มีเอกสารประกอบครบถ้วน ความรู้ที่แท้จริงอยู่ใน "หัว" ของพนักงานรุ่นเก่าบางคนเท่านั้น
   (ทบทวน "Silver Tsunami" จาก Part 001 ขั้นตอนที่ 4)
2. **ความสำคัญทางธุรกิจสูงมาก (High Business Criticality)** — ทบทวนจาก Part 001 ขั้นตอนที่ 3: ระบบ
   COBOL มักเป็นแกนหลักของธุรกรรมทางการเงินที่กระทบเงินหรือข้อมูลของคนจำนวนมาก ทำให้ความเสี่ยงจาก
   ความผิดพลาดสูงกว่าโปรเจกต์ซอฟต์แวร์ทั่วไปมาก
3. **การพึ่งพารอบ Batch ที่ตายตัว (Batch Cycle Dependency)** — ทบทวนจาก Part 066: งาน Batch ต้องรัน
   ในกรอบเวลาที่จำกัดทุกคืน การ Deploy หรือเปลี่ยนแปลงระบบต้องคำนึงถึงตารางเวลานี้เสมอ ต่างจากระบบเว็บ
   สมัยใหม่ที่มักปรับใช้ (deploy) ได้ตลอดเวลา
4. **การพึ่งพาซึ่งกันและกันสูงระหว่างหลายระบบ (High Interdependency)** — ทบทวนจาก Part 086: Copybook
   และ Interface ที่ใช้ร่วมกันทำให้การเปลี่ยนแปลงจุดเดียวอาจกระทบระบบอื่นที่ไม่เกี่ยวข้องโดยตรงได้

### ผลกระทบต่อการบริหารจัดการโปรเจกต์

ลักษณะทั้ง 4 ข้อนี้ทำให้กรอบการบริหารโปรเจกต์ COBOL Enterprise ต้องให้น้ำหนักกับเรื่องต่อไปนี้มากกว่า
โปรเจกต์ซอฟต์แวร์ทั่วไป:

| ลักษณะเฉพาะ | ผลกระทบต่อการบริหารจัดการ | ขั้นตอนที่เกี่ยวข้องใน Part นี้ |
|---|---|---|
| Knowledge Fragmentation | ต้องวางแผนถ่ายทอดความรู้อย่างเป็นระบบ ไม่ใช่แค่เขียนเอกสาร | 899 |
| High Business Criticality | การประมาณความเสี่ยงต้องเข้มงวดกว่าปกติ | 897 |
| Batch Cycle Dependency | Release ต้องวางแผนรอบ Batch Window อย่างละเอียด | 896 |
| High Interdependency | ต้องมีกระบวนการประสานงานการเปลี่ยนแปลงข้ามทีมที่เป็นทางการ | 895 |

### ข้อควรระวัง

- **อย่านำ Framework การบริหารโปรเจกต์แบบ Agile ของทีมพัฒนา Startup มาใช้ตรง ๆ โดยไม่ปรับ** — หลักการ
  พื้นฐานของ Agile (การทำงานเป็นรอบสั้น ๆ, การรับ feedback บ่อย ๆ) ยังคงมีประโยชน์ แต่ต้องปรับให้เข้ากับ
  ข้อจำกัดเฉพาะของระบบ COBOL Enterprise เช่น ไม่สามารถ "deploy บ่อย ๆ ทุกวัน" ได้เหมือนเว็บแอปพลิเคชัน
  เพราะติดข้อจำกัดเรื่อง Batch Window
- ลักษณะทั้ง 4 ข้อนี้**ไม่ได้แปลว่าโปรเจกต์ COBOL บริหารยากกว่าเสมอไป** เพียงแต่ต้องการกรอบคิดที่ปรับให้
  เหมาะสมกับบริบทเฉพาะ องค์กรที่เข้าใจลักษณะเฉพาะเหล่านี้ตั้งแต่ต้นมักบริหารโปรเจกต์ COBOL ได้ราบรื่นกว่า
  องค์กรที่พยายามยัดเยียด Framework ที่ไม่เข้ากันมาใช้

รุนแรงที่สุดต่อ Timeline ของโครงการ Modernization พร้อมให้เหตุผล

**เฉลยแนวทาง**: ไม่มีคำตอบตายตัว แต่เหตุผลที่ดีมักเชื่อมโยงกับ Knowledge Fragmentation เพราะหากทีมงาน

กระบวนการทางเทคนิคเพียงอย่างเดียว)

## ขั้นตอนที่ 892: การประมาณงานบำรุงรักษาด้วยหลักเกณฑ์ Lines-of-Code (LOC Heuristics)

### หลักการพื้นฐาน: ทำไมต้องมีหลักเกณฑ์การประมาณงาน

ผู้บริหารโครงการ COBOL ต้องตอบคำถามนี้บ่อยมาก: **"การแก้ไข/เพิ่มฟีเจอร์นี้จะใช้เวลากี่คน-วัน?"** — หนึ่งใน
หลักเกณฑ์ที่ใช้กันแพร่หลายที่สุด (แม้จะหยาบ) คือการประมาณจากจำนวนบรรทัดโค้ด (Lines of Code, LOC) ที่
คาดว่าจะต้องแก้ไขหรือเขียนใหม่ คูณกับ **อัตราผลิตภาพ (Productivity Rate)** ที่ทีมวัดได้จากงานที่ผ่านมาจริง

### อัตราผลิตภาพโดยประมาณสำหรับงาน COBOL (กรอบอ้างอิงทั่วไป)

| ประเภทงาน | อัตราผลิตภาพโดยประมาณ (LOC ต่อคน-วัน) | เหตุผล |
|---|---|---|
| เขียนโปรแกรมใหม่ทั้งหมด (Greenfield) | 20-40 | ต้องออกแบบตรรกะใหม่ทั้งหมด ทดสอบละเอียด |
| แก้ไข/เพิ่มฟีเจอร์ในโค้ดที่ทีมคุ้นเคยดี | 60-120 | ทีมเข้าใจโครงสร้างเดิม ใช้ Copybook/Pattern ที่มีอยู่ |
| แก้ไขโค้ด Legacy ที่ทีมไม่คุ้นเคย | 15-40 | ต้องใช้เวลาอ่านทำความเข้าใจก่อนแก้ไข |

> **ข้อควรระวังสำคัญที่สุดของขั้นตอนนี้**: ตัวเลขในตารางนี้เป็น**กรอบอ้างอิงทั่วไปที่พบในอุตสาหกรรม**
> เท่านั้น ไม่ใช่สูตรสำเร็จตายตัว — หลักการเดียวกับที่ Part 088 เน้นย้ำเรื่อง "วัดผลก่อนเชื่อ" ใช้ได้กับการ
> ประมาณงานเช่นกัน: **ทีมควรเก็บข้อมูลผลิตภาพจริงของตัวเองจากงานที่ผ่านมา แล้วใช้ตัวเลขนั้นแทนตัวเลข
> อ้างอิงทั่วไปเสมอเมื่อทำได้**

### ตัวอย่างการคำนวณจริงจากขนาดโค้ดที่วัดได้จริง

สมมติทีมต้องแก้ไขฟีเจอร์หนึ่งในระบบที่มีขนาดรวม 125,000 บรรทัด (ตัวเลขเดียวกับที่จะใช้คำนวณ KPI ใน
ขั้นตอนที่ 898) และคาดว่าการแก้ไขจะกระทบโค้ดประมาณ 800 บรรทัด ในโค้ดส่วนที่ทีมมีความคุ้นเคยระดับปานกลาง:

```
จำนวนบรรทัดที่ต้องแก้ไข     = 800 LOC
อัตราผลิตภาพ (คุ้นเคยปานกลาง) = 60 LOC ต่อคน-วัน (ค่าต่ำของช่วง "คุ้นเคยดี")
ประมาณการเบื้องต้น           = 800 / 60 = 13.3 คน-วัน
```

```bash
python3 -c "print(round(800 / 60, 1), 'person-days (rough estimate)')"
```

**ผลลัพธ์จริง:**

```
13.3 person-days (rough estimate)
```

### ปรับปรุงประมาณการด้วยปัจจัยเสี่ยง (Risk Buffer)

ประมาณการดิบ (13.3 คน-วัน) ยังไม่รวมเวลาสำหรับการทดสอบถดถอย (Regression Testing — ทบทวนจาก Part
079), การประสานงานกับทีมอื่นหากกระทบ Copybook ร่วม (ทบทวน Part 080 ขั้นตอนที่ 796), และเวลาที่เสียไป
กับการทำความเข้าใจโค้ดเดิม แนวปฏิบัติทั่วไปคือการเพิ่ม **Risk Buffer** อีก 30-50% สำหรับงานบำรุงรักษาระบบ
Legacy:

```
ประมาณการดิบ        = 13.3 คน-วัน
Risk Buffer (40%)    = 13.3 x 1.4 = 18.6 คน-วัน
```

```bash
python3 -c "print(round(13.3 * 1.4, 1), 'person-days (with 40% risk buffer)')"
```

**ผลลัพธ์จริง:**

```
18.6 person-days (with 40% risk buffer)
```

### ข้อควรระวัง

- **หลักเกณฑ์ LOC มีข้อจำกัดสำคัญ**: โค้ด COBOL ที่ซับซ้อนมาก (เช่น มีเงื่อนไขธุรกิจซ้อนกันหลายชั้น) กับ
  โค้ดที่เรียบง่าย (เช่น การ MOVE ข้อมูลตรงไปตรงมา) มีจำนวนบรรทัดใกล้เคียงกันได้ แต่ใช้เวลาทำความเข้าใจและ
  ทดสอบต่างกันมาก — LOC จึงเป็นเพียง**จุดเริ่มต้น**ของการประมาณการ ไม่ใช่คำตอบสุดท้าย ควรใช้ร่วมกับ
  Function Point Analysis (ขั้นตอนที่ 893) ที่คำนึงถึงความซับซ้อนเชิงฟังก์ชันด้วย
- **อย่าใช้ LOC เป็นตัวชี้วัดผลงานของนักพัฒนารายบุคคล** (เช่น "คนที่เขียนโค้ดได้มากบรรทัดกว่าทำงานดีกว่า")
  เพราะจะสร้างแรงจูงใจผิด ๆ ให้เขียนโค้ดยืดยาวโดยไม่จำเป็น — LOC ควรใช้เป็นเครื่องมือประมาณงานระดับ
  โครงการเท่านั้น ไม่ใช่เครื่องมือประเมินผลงานบุคคล

**เฉลยแนวทาง**: ควรใช้ตัวเลข **10 LOC ต่อคน-วันที่วัดได้จริงจากทีมตัวเอง** แทนค่าอ้างอิงทั่วไปในตาราง
(15-40) ทันที เพราะข้อมูลจริงของทีมสะท้อนบริบทเฉพาะ (ความซับซ้อนของระบบ, ระดับประสบการณ์ของทีม,
คุณภาพเอกสารที่มีอยู่) ได้แม่นยำกว่าค่าเฉลี่ยอุตสาหกรรมทั่วไปเสมอ — นี่คือการประยุกต์หลักการ "วัดผลก่อนเชื่อ"
จาก Part 088 มาใช้กับงานประมาณการโครงการ นอกจากนี้ทีมควรตั้งคำถามต่อว่าทำไมอัตราถึงต่ำกว่าค่าเฉลี่ย
(เช่น ขาดเอกสารมากเป็นพิเศษ หรือระบบมีความซับซ้อนสูงผิดปกติ) เพื่อนำไปใช้ปรับปรุงกระบวนการทำงานในระยะยาว

## ขั้นตอนที่ 893: การประมาณงานด้วย Function Point Analysis

### ทำไมต้องมีวิธีประมาณงานอีกแบบนอกเหนือจาก LOC

ขั้นตอนที่ 892 ชี้ให้เห็นข้อจำกัดของ LOC: โค้ดสองชิ้นที่มีจำนวนบรรทัดใกล้เคียงกันอาจมีความซับซ้อนเชิงธุรกิจ
ต่างกันมาก **Function Point Analysis (FPA)** แก้ปัญหานี้โดยประมาณงานจาก **"ฟังก์ชันการทำงานที่ผู้ใช้
มองเห็น"** แทนที่จะนับบรรทัดโค้ด ทำให้ประมาณการไม่ขึ้นอยู่กับภาษาโปรแกรมหรือสไตล์การเขียนโค้ดของแต่ละคน

### 5 องค์ประกอบพื้นฐานของ Function Point

| องค์ประกอบ | คำนิยาม | ตัวอย่างในระบบธนาคาร |
|---|---|---|
| **External Input (EI)** | ข้อมูลนำเข้าจากภายนอกที่ทำให้เกิดการเปลี่ยนแปลงข้อมูล | หน้าจอรับข้อมูลฝากเงิน |
| **External Output (EO)** | ผลลัพธ์ที่ส่งออกที่ผ่านการคำนวณ/ประมวลผล | รายงานสรุปดอกเบี้ยรายเดือน |
| **External Inquiry (EQ)** | การค้นหาข้อมูลที่ไม่มีการคำนวณเพิ่มเติม | หน้าจอตรวจสอบยอดคงเหลือ |
| **Internal Logical File (ILF)** | กลุ่มข้อมูลที่ระบบดูแลเอง | ไฟล์ Master บัญชีลูกค้า |
| **External Interface File (EIF)** | กลุ่มข้อมูลที่ระบบอื่นดูแลแต่ระบบนี้อ่านใช้ | ไฟล์อัตราแลกเปลี่ยนจากระบบภายนอก |

### ตัวอย่างการคำนวณ: โปรแกรม "ตรวจสอบยอดคงเหลือบัญชี" จาก Part 089

ทบทวนจากโปรแกรม `STEP890PIPELINE` ใน Part 089: รับชื่อลูกค้าและเลขบัญชี, ตรวจสอบความถูกต้อง, ค้นหา
ยอดคงเหลือ, แสดงผล (แบบ mask แล้ว), และบันทึก Audit Log — สมมติให้คะแนนความซับซ้อนแบบง่าย (Low=3,
Average=4, High=6 ต่อจุด ตามแนวทาง FPA มาตรฐาน):

| องค์ประกอบ | จำนวน | ความซับซ้อน | คะแนนต่อจุด | คะแนนรวม |
|---|---|---|---|---|
| EI: รับชื่อ+เลขบัญชี | 1 | Average | 4 | 4 |
| EQ: ค้นหายอดคงเหลือ | 1 | Low | 3 | 3 |
| EO: แสดงผลยอดที่ mask แล้ว | 1 | Average | 4 | 4 |
| ILF: ไฟล์บัญชีลูกค้า | 1 | Average | 7 | 7 |
| EIF: ไม่มี (ไม่พึ่งระบบภายนอก) | 0 | - | - | 0 |
| **รวม Unadjusted Function Points (UFP)** | | | | **18** |

```bash
python3 -c "print(4 + 3 + 4 + 7, 'Unadjusted Function Points')"
```

**ผลลัพธ์จริง:**

```
18 Unadjusted Function Points
```

### แปลง Function Point เป็นประมาณการเวลา

หลักเกณฑ์ทั่วไปที่ใช้แปลง Function Point เป็นชั่วโมงทำงานอยู่ที่ประมาณ **8-20 ชั่วโมงต่อ 1 Function
Point** สำหรับงานพัฒนา COBOL (ขึ้นอยู่กับความคุ้นเคยของทีมและคุณภาพเครื่องมือพัฒนา) สมมติทีมใช้ค่ากลาง
12 ชั่วโมงต่อ Function Point:

```
18 Function Points x 12 ชั่วโมง/FP = 216 ชั่วโมง
216 ชั่วโมง / 8 ชั่วโมงต่อวัน = 27 คน-วัน
```

```bash
python3 -c "hours = 18 * 12; days = hours / 8; print(f'{hours} hours = {days} person-days')"
```

**ผลลัพธ์จริง:**

```
216 hours = 27.0 person-days
```

### เปรียบเทียบผลลัพธ์ทั้งสองวิธี

| วิธีการประมาณ | ผลลัพธ์ |
|---|---|
| LOC Heuristic (ขั้นตอนที่ 892, งานคนละชิ้น) | 18.6 คน-วัน (รวม Risk Buffer) |
| Function Point Analysis (งานคนละชิ้น) | 27.0 คน-วัน |

**ทั้งสองตัวเลขนี้ประมาณงานคนละชิ้นกัน จึงเปรียบเทียบตรง ๆ ไม่ได้** — จุดสำคัญของการแสดงทั้งสองวิธีคือให้
เห็นว่า **แนวทางการคำนวณต่างกันโดยพื้นฐาน**: LOC มองจากปริมาณโค้ด ส่วน FPA มองจากปริมาณฟังก์ชันที่
ผู้ใช้มองเห็น ทีมที่บริหารจัดการโครงการอย่างเป็นระบบมักใช้**ทั้งสองวิธีร่วมกัน**เพื่อตรวจสอบไขว้กัน (Cross-
Check) หากตัวเลขจากสองวิธีต่างกันมากผิดปกติสำหรับงานชิ้นเดียวกัน อาจเป็นสัญญาณว่าประมาณการมีความเสี่ยง
ที่ต้องพิจารณาเพิ่มเติม

### ข้อควรระวัง

- **การให้คะแนนความซับซ้อน (Low/Average/High) ของแต่ละองค์ประกอบมีความเป็นอัตวิสัย (Subjective)**
  พอสมควร — ทีมควรมีแนวปฏิบัติที่ชัดเจนและสม่ำเสมอในการตัดสินระดับความซับซ้อน ไม่ใช่ให้แต่ละคนประเมิน
  ตามความรู้สึกของตัวเอง มิฉะนั้นตัวเลข FPA ระหว่างโครงการจะเปรียบเทียบกันไม่ได้เลย
- **อัตราแปลง Function Point เป็นชั่วโมง (8-20 ชั่วโมงต่อ FP) เป็นกรอบอ้างอิงทั่วไปเช่นเดียวกับ LOC
  Heuristic** — ต้องปรับตามข้อมูลจริงของทีมเสมอ (หลักการเดียวกับขั้นตอนที่ 892)

### แบบฝึกหัดที่ 893.1

**โจทย์**: หากโปรแกรมหนึ่งมี Function Point สูง (บ่งบอกว่าซับซ้อนเชิงธุรกิจมาก) แต่มีจำนวนบรรทัดโค้ด (LOC)
น้อย จะบ่งบอกอะไรเกี่ยวกับลักษณะของโค้ดนั้น

**เฉลยแนวทาง**: บ่งบอกว่าโค้ดนั้นมีแนวโน้ม**กระชับแต่ซับซ้อนเชิงตรรกะสูง** — อาจเป็นโค้ดที่ใช้สูตรคำนวณ
ทางธุรกิจที่ซับซ้อน (เช่น การคำนวณดอกเบี้ยทบต้นหลายเงื่อนไข) ที่เขียนด้วยโค้ดไม่กี่บรรทัดแต่ตรรกะภายใน
ซับซ้อนมาก กรณีแบบนี้ **LOC Heuristic เพียงอย่างเดียวจะประเมินงานต่ำเกินไปมาก** เพราะมองว่าโค้ดน้อย
บรรทัด = งานน้อย ทั้งที่ความจริงต้องใช้เวลาออกแบบ ทดสอบ และทำความเข้าใจตรรกะทางธุรกิจมากกว่าที่ LOC
บ่งบอก นี่คือเหตุผลสำคัญที่ควรใช้ FPA ควบคู่กับ LOC เสมอ โดยเฉพาะกับโปรแกรมที่มีสูตรคำนวณทางธุรกิจที่
ซับซ้อนสูง

## ขั้นตอนที่ 894: การจัดการหนี้ทางเทคนิค (Technical Debt) ในระบบ Legacy

### Technical Debt คืออะไรในบริบทของ COBOL Legacy

**Technical Debt (หนี้ทางเทคนิค)** คือ ต้นทุนเพิ่มเติมในอนาคตที่เกิดจากการเลือกวิธีแก้ปัญหาที่เร็วแต่ไม่ดี
ที่สุดในปัจจุบัน สำหรับระบบ COBOL Legacy หนี้ทางเทคนิคที่พบบ่อยที่สุด ได้แก่ การใช้ `GO TO` แทน
Structured Programming (ทบทวนจาก Part 012 และ Part 068 ขั้นตอนที่ 672), การไม่ตรวจสอบ `FILE STATUS`
(ทบทวนจาก Part 030), และการไม่มีชุดทดสอบอัตโนมัติ (ทบทวนจาก Part 079)

### สร้างชุดโค้ดตัวอย่างเพื่อสาธิตการสแกนหาหนี้ทางเทคนิค

เพื่อให้เห็นภาพจริง เราจะสร้างโค้ดตัวอย่าง 3 โปรแกรมที่จำลองสถานการณ์ codebase ผสมระหว่างโค้ดสไตล์เก่า
และสไตล์ใหม่ แล้วใช้เครื่องมือค้นหาข้อความ (`grep`) สแกนหาตัวชี้วัดหนี้ทางเทคนิคแบบเดียวกับที่ทีมจริงมักใช้
เป็นจุดเริ่มต้น (ก่อนจะลงทุนซื้อเครื่องมือวิเคราะห์โค้ดแบบมืออาชีพ)

```cobol
      *> LEGACY1.cob - uses GO TO, no FILE STATUS check
       IDENTIFICATION DIVISION.
       PROGRAM-ID. LEGACY1.
       ...
       PROCEDURE DIVISION.
       MAIN-PARA.
           OPEN OUTPUT OLD-FILE.
           GO TO WRITE-LOOP.
       WRITE-LOOP.
           ADD 1 TO WS-COUNTER.
           ...
           IF WS-COUNTER < 3
               GO TO WRITE-LOOP
           END-IF.
```

```cobol
      *> LEGACY2.cob - structured PERFORM, checks FILE STATUS
       PROCEDURE DIVISION.
       MAIN-PARA.
           OPEN OUTPUT NEW-FILE.
           IF WS-FILE-STATUS NOT = "00"
               DISPLAY "OPEN ERROR: " WS-FILE-STATUS
               STOP RUN
           END-IF.
           PERFORM VARYING WS-COUNTER FROM 1 BY 1 UNTIL WS-COUNTER > 3
               ...
           END-PERFORM.
```

(LEGACY3.cob มีรูปแบบคล้าย LEGACY1.cob — ใช้ `GO TO` 2 จุดและไม่มี `FILE STATUS`)

### ทดสอบสแกนแบบไร้เดียงสา (Naive Scan) ครั้งแรก — พบปัญหาที่ไม่คาดคิด

```bash
grep -c "GO TO" *.cob
```

**ผลลัพธ์จริง (ครั้งแรก):**

```
LEGACY1.cob:3
LEGACY2.cob:0
LEGACY3.cob:3
```

ตัวเลข `3` ของ `LEGACY1.cob` ดูผิดปกติ เพราะในโค้ดจริงมี `GO TO` แค่ 2 จุด — ตรวจสอบด้วย `grep -n`
เพื่อดูว่าบรรทัดไหนถูกนับบ้าง:

```bash
grep -n "GO TO" LEGACY1.cob
```

**ผลลัพธ์จริง:**

```
5:      *> uses GO TO for control flow and opens a file without
25:           GO TO WRITE-LOOP.
31:               GO TO WRITE-LOOP
```

### วิเคราะห์ปัญหา — False Positive จากคอมเมนต์

บรรทัดที่ 5 คือ**คอมเมนต์**ที่อธิบายว่าโปรแกรมนี้ "uses GO TO for control flow" — คำอธิบายเป็นภาษาอังกฤษ
ที่มีคำว่า "GO TO" ปนอยู่ ถูกนับเป็นการใช้งาน `GO TO` จริงไปด้วยโดยผิดพลาด! นี่คือ **False Positive
(ผลบวกลวง)** ที่พบบ่อยมากเมื่อใช้เครื่องมือค้นหาข้อความอย่างง่ายในการวิเคราะห์หนี้ทางเทคนิค เช่นเดียวกัน
การตรวจสอบว่าไฟล์ใดขาด `FILE STATUS` ด้วยวิธีไร้เดียงสาก็ล้มเหลวเช่นกัน เพราะคอมเมนต์ในบรรทัดที่ 6 ของ
`LEGACY1.cob` มีข้อความ "checking FILE STATUS at all" ทำให้สคริปต์เข้าใจผิดว่าไฟล์นี้**มี** FILE STATUS
clause ทั้งที่ความจริงไม่มีเลย

### ทางแก้: สแกนแบบตัดคอมเมนต์ออกก่อนเสมอ

```bash
echo "--- GO TO occurrences, comments excluded ---"
for f in *.cob; do
  count=$(grep -v '\*>' "$f" | grep -o "GO TO" | wc -l)
  echo "$f : $count"
done

echo "--- files missing FILE STATUS (comments excluded) ---"
for f in *.cob; do
  if grep -v '\*>' "$f" | grep -q "SELECT.*ASSIGN" \
     && ! grep -v '\*>' "$f" | grep -q "FILE STATUS"; then
    echo "$f : NO FILE STATUS CHECK"
  fi
done
```

**ผลลัพธ์จริง (หลังแก้ไข):**

```
--- GO TO occurrences, comments excluded ---
LEGACY1.cob : 2
LEGACY2.cob : 0
LEGACY3.cob : 2

--- files missing FILE STATUS (comments excluded) ---
LEGACY1.cob : NO FILE STATUS CHECK
LEGACY3.cob : NO FILE STATUS CHECK
```

ตอนนี้ตัวเลขถูกต้อง: `GO TO` รวม 4 ครั้งในโค้ดจริง (ไม่นับคอมเมนต์), และระบุถูกต้องว่า `LEGACY1.cob` กับ
`LEGACY3.cob` ขาดการตรวจสอบ `FILE STATUS` ในขณะที่ `LEGACY2.cob` ไม่ถูกระบุ (เพราะมีจริง)

### สรุปตัวชี้วัดหนี้ทางเทคนิคที่ใช้ได้จริงสำหรับ Codebase COBOL

| ตัวชี้วัด | คำสั่งสแกน (ตัดคอมเมนต์ก่อนเสมอ) | ความหมาย |
|---|---|---|
| จำนวนการใช้ `GO TO` | `grep -v '\*>' *.cob \| grep -c "GO TO"` | ยิ่งมากยิ่งเสี่ยงต่อ Spaghetti Code |
| ไฟล์ที่ขาด `FILE STATUS` | สคริปต์ตามตัวอย่างข้างต้น | เสี่ยงต่อการจัดการ error ไม่ครบถ้วน |
| สัดส่วนโปรแกรมที่มีชุดทดสอบ | เทียบจำนวนไฟล์ `.cob` กับไฟล์ทดสอบใน Part 079 | บ่งบอกความเสี่ยงเมื่อแก้ไขโค้ด |

### ข้อควรระวัง

- **เครื่องมือสแกนหนี้ทางเทคนิคแบบ Text-based (เช่น `grep`) มีข้อจำกัดเสมอ** อย่างที่พิสูจน์ในขั้นตอนนี้
  — องค์กรขนาดใหญ่มักลงทุนในเครื่องมือวิเคราะห์โค้ดแบบ Static Analysis ระดับมืออาชีพที่เข้าใจไวยากรณ์ COBOL
  จริง (ไม่ใช่แค่ค้นหาข้อความ) เพื่อลด False Positive/Negative แบบนี้ แต่แม้แต่เครื่องมือระดับมืออาชีพก็ควร
  ได้รับการตรวจทานผลลัพธ์โดยมนุษย์เสมอ ไม่ใช่เชื่อผลลัพธ์อัตโนมัติ 100%
- **การมี Technical Debt ไม่ได้แปลว่าโค้ดนั้น "แย่" เสมอไป** — บางครั้งทีมในอดีตตัดสินใจใช้ `GO TO` หรือ
  ข้ามการตรวจสอบบางอย่างด้วยเหตุผลที่สมเหตุสมผลในบริบทตอนนั้น (เช่น ข้อจำกัดของ Compiler รุ่นเก่า) สิ่ง
  สำคัญคือการ**บันทึกและติดตามหนี้เหล่านี้อย่างมีสติ** ไม่ใช่ปล่อยให้สะสมโดยไม่มีใครรู้ตัว

### แบบฝึกหัดที่ 894.1

**โจทย์**: จงอธิบายว่าทำไมการค้นพบ False Positive ในขั้นตอนนี้ (คอมเมนต์ที่มีคำว่า "GO TO" ถูกนับเป็นการ
ใช้งานจริง) จึงเป็นบทเรียนสำคัญสำหรับผู้บริหารโครงการที่ต้องรายงานตัวเลขหนี้ทางเทคนิคให้ผู้บริหารระดับสูงฟัง

**เฉลยแนวทาง**: เพราะหากผู้บริหารโครงการนำตัวเลขจากการสแกนแบบไร้เดียงสาไปรายงานตรง ๆ โดยไม่ตรวจสอบ
ก่อน (เช่น รายงานว่า "ระบบมีการใช้ `GO TO` ถึง 3 ครั้งใน LEGACY1.cob") ตัวเลขนั้นจะสูงเกินความเป็นจริง
25-50% ในกรณีนี้ (นับ 3 ครั้งทั้งที่จริงมีแค่ 2) ซึ่งอาจทำให้การตัดสินใจเชิงกลยุทธ์ผิดพลาดได้ เช่น จัดสรร
งบประมาณหรือเวลามากเกินความจำเป็นสำหรับการแก้ไขหนี้ทางเทคนิคที่ไม่ได้มากขนาดนั้นจริง ๆ หรือในทางกลับกัน
หากมีคอมเมนต์ที่บังเอิญไม่มีคำที่เกี่ยวข้อง ตัวเลขอาจต่ำกว่าความเป็นจริงก็ได้เช่นกัน บทเรียนคือ **ตัวเลขที่
ใช้ในการตัดสินใจเชิงบริหารต้องผ่านการตรวจสอบความถูกต้องของวิธีการวัดก่อนเสมอ** ไม่ต่างจากหลักการ "วัดผล
ก่อนเชื่อ" ที่ใช้กับการวัด Performance ใน Part 088

## ขั้นตอนที่ 895: การประสานงานเปลี่ยนแปลง Copybook/Interface หลายทีม — มุมมองผู้บริหารโครงการ

### ทบทวนจาก Part 080 ขั้นตอนที่ 796: ปัญหาทางเทคนิคที่พิสูจน์แล้ว

Part 080 พิสูจน์ด้วยการรันจริงว่าการแก้ไข Copybook ที่ใช้ร่วมกัน (เช่น การลดความกว้างฟิลด์ `CUST-NAME`
จาก `PIC X(20)` เป็น `PIC X(10)`) ทำให้โปรแกรมอื่นที่ `COPY` มันเข้าไปใช้เกิดข้อมูลถูกตัดทอนอย่างเงียบ ๆ
โดยไม่มี compile error เตือนเลย และแนะนำเทคนิค `grep -rl "customer.cpy" src/` เพื่อค้นหาว่าโปรแกรมใดได้
รับผลกระทบก่อนแก้ไข — ขั้นตอนนี้ขยายปัญหาทางเทคนิคนั้นให้เป็น **กระบวนการบริหารจัดการที่เป็นทางการ**
สำหรับองค์กรที่มีหลายทีมเกี่ยวข้อง

### กระบวนการ RFC (Request for Change) สำหรับ Copybook ที่ใช้ร่วมกัน

องค์กรขนาดใหญ่ที่มี Copybook ใช้ร่วมกันหลายสิบโปรแกรมจากหลายทีม ควรมีแบบฟอร์ม **RFC (Request for
Change)** ที่เป็นทางการก่อนแก้ไข Copybook ใด ๆ ประกอบด้วยหัวข้อขั้นต่ำดังนี้:

| หัวข้อใน RFC | เนื้อหาที่ต้องระบุ |
|---|---|
| ผู้ร้องขอและเหตุผลทางธุรกิจ | ใครต้องการเปลี่ยนแปลง และทำไม (เชื่อมโยงกับความต้องการทางธุรกิจที่ชัดเจน) |
| รายชื่อโปรแกรมที่ได้รับผลกระทบ | ผลลัพธ์จาก `grep -rl` (Part 080 ขั้นตอนที่ 796) แนบมาโดยอัตโนมัติจาก CI |
| ประเภทการเปลี่ยนแปลง | เพิ่มฟิลด์ท้ายสุด (ปลอดภัย) หรือแก้ไข/ลบฟิลด์เดิม (มีความเสี่ยงสูง — ทบทวน Part 086 ขั้นตอนที่ 855-856) |
| แผนการทดสอบ | ระบุว่าจะทดสอบโปรแกรมที่ได้รับผลกระทบทั้งหมดอย่างไร ไม่ใช่แค่โปรแกรมที่แก้ไขโดยตรง |
| แผนสำรอง (Rollback Plan) | หากพบปัญหาหลัง Deploy จะย้อนกลับอย่างไร |
| รายชื่อทีมที่ต้องอนุมัติ | ทุกทีมที่มีโปรแกรมได้รับผลกระทบต้องลงชื่ออนุมัติ ไม่ใช่แค่ทีมที่ร้องขอ |

### Change Advisory Board (CAB): กลไกอนุมัติสำหรับการเปลี่ยนแปลงที่มีผลกระทบวงกว้าง

**Change Advisory Board (CAB)** คือคณะกรรมการ (ตัวแทนจากทุกทีมที่เกี่ยวข้อง) ที่ทำหน้าที่พิจารณาอนุมัติ
RFC ก่อนที่การเปลี่ยนแปลงจะถูก Deploy จริง หลักการสำคัญคือ **ระดับความเข้มงวดของ CAB ควรแปรผันตาม
ความเสี่ยงของการเปลี่ยนแปลง**:

```
+------------------------------------------------------------------+
|              ระดับความเข้มงวดของกระบวนการอนุมัติ                    |
+------------------------------------------------------------------+
|                                                                    |
|  ความเสี่ยงต่ำ                                    ความเสี่ยงสูง       |
|  (เพิ่มฟิลด์ท้ายสุด,                              (แก้ไข/ลบฟิลด์เดิม,  |
|   โปรแกรมที่ได้รับผลกระทบ                          โปรแกรมที่ได้รับ     |
|   น้อยกว่า 5 โปรแกรม)                              ผลกระทบมากกว่า     |
|       |                                            20 โปรแกรม)       |
|       v                                                   |         |
|  อนุมัติโดยหัวหน้าทีมเดียว                                   v         |
|  (Lightweight Approval)                     ต้องผ่าน CAB เต็มรูปแบบ    |
|                                              (ตัวแทนทุกทีมที่กระทบ     |
|                                               ร่วมพิจารณา)           |
+------------------------------------------------------------------+
```

### ทำไมต้องแปรผันระดับความเข้มงวดตามความเสี่ยง

หากบังคับให้ทุกการเปลี่ยนแปลง (แม้แต่การเพิ่มฟิลด์เล็ก ๆ ที่ปลอดภัย) ต้องผ่าน CAB เต็มรูปแบบเสมอ จะทำให้
กระบวนการช้าเกินความจำเป็นจนทีมเริ่มหาทางเลี่ยงกระบวนการ (เช่น แอบแก้ไขโดยไม่แจ้งใคร ซึ่งอันตรายกว่ามาก)
— หลักการที่ดีคือทำให้ **เส้นทางที่ปลอดภัยเป็นเส้นทางที่ง่ายที่สุด (Make the Safe Path the Easy Path)**

### ข้อควรระวัง

- **CAB ต้องมีตัวแทนที่มีอำนาจตัดสินใจจริงจากทุกทีมที่ได้รับผลกระทบ** ไม่ใช่แค่ตัวแทนที่มาประชุมแต่ไม่มี
  อำนาจอนุมัติอะไรจริง — มิฉะนั้นกระบวนการจะกลายเป็นพิธีกรรมที่ไม่มีความหมาย
- **รายชื่อโปรแกรมที่ได้รับผลกระทบต้องมาจากการสแกนอัตโนมัติ (เช่น `grep -rl` ใน CI ตาม Part 080) ไม่ใช่
  จากความจำของคน** — ทบทวนจาก ขั้นตอนที่ 894: แม้แต่การสแกนอัตโนมัติก็ยังมีข้อจำกัด การพึ่งพาความจำของ
  คนเพียงอย่างเดียวมีความเสี่ยงสูงกว่ามาก โดยเฉพาะในองค์กรที่มีโปรแกรมนับพันไฟล์

### แบบฝึกหัดที่ 895.1

**โจทย์**: จงยกตัวอย่างการเปลี่ยนแปลง Copybook 2 กรณี กรณีหนึ่งที่ควรผ่านกระบวนการอนุมัติแบบเบา
(Lightweight) และอีกกรณีที่ควรผ่าน CAB เต็มรูปแบบ พร้อมเหตุผล

**เฉลยแนวทาง**: **กรณีที่ควรผ่านกระบวนการเบา**: เพิ่มฟิลด์ `CUST-EMAIL` ท้ายสุดของ Copybook ที่มีเพียง 3
โปรแกรมใช้งาน (ทบทวนตัวอย่างจาก Part 086 ขั้นตอนที่ 855 ที่พิสูจน์ว่าการเพิ่มฟิลด์ท้ายสุดปลอดภัยต่อโปรแกรม
เดิมที่ยังไม่ได้อัปเดต) เพราะความเสี่ยงต่ำและผลกระทบจำกัด **กรณีที่ควรผ่าน CAB เต็มรูปแบบ**: การเปลี่ยน
ชนิดข้อมูลของฟิลด์ `ACCT-BALANCE` จาก `PIC 9(7)V99` เป็น `PIC 9(9)V99` (ขยายขนาดเพื่อรองรับยอดเงิน
ที่มากขึ้น) ในระบบที่มี 80 โปรแกรมใช้ Copybook นี้ เพราะแม้จะดูเหมือนเป็นการเปลี่ยนแปลงเล็กน้อย แต่การ
เปลี่ยนขนาดฟิลด์ที่มีอยู่เดิมกระทบ**ความยาวรวมของ Record** และอาจกระทบโปรแกรมที่ใช้ `REDEFINES` หรือคำนวณ
ตำแหน่ง offset จากขนาดเดิม (ทบทวนจาก Part 022 และ Part 086 ขั้นตอนที่ 856 เรื่อง Anti-Pattern การแทรก/
แก้ไขฟิลด์กลางโครงสร้าง) จึงต้องผ่านการพิจารณาจากทุกทีมที่เกี่ยวข้องอย่างละเอียดก่อน Deploy จริง

## ขั้นตอนที่ 896: การบริหาร Release สำหรับระบบที่ขึ้นกับรอบ Batch (Batch-Cycle-Dependent Release Management)

### ปัญหาเฉพาะ: ไม่สามารถ Deploy "เมื่อไหร่ก็ได้" เหมือนเว็บแอปพลิเคชัน

ทบทวนจาก Part 066: ระบบ COBOL จำนวนมากมีงาน Batch ที่ต้องรันในกรอบเวลาจำกัดทุกคืน (Batch Window)
— การ Deploy การเปลี่ยนแปลงโปรแกรมที่เกี่ยวข้องกับ Batch **ต้องวางแผนให้สอดคล้องกับตารางเวลานี้เสมอ**
ต่างจากเว็บแอปพลิเคชันสมัยใหม่ที่มักใช้ Continuous Deployment (ทบทวนจาก Part 078) ได้ตลอดเวลา

### คำนวณความจุของ Batch Window จริง

สมมติองค์กรหนึ่งมี Batch Window ตั้งแต่ 22:30 ถึง 05:00 ของวันถัดไป และมีสายงาน Batch (Job Chain
ทบทวนจาก Part 086 ขั้นตอนที่ 853) ที่ต้องรันตามลำดับดังนี้:

| งาน | เวลาที่ใช้โดยประมาณ (นาที) |
|---|---|
| EXTRACT-TXN | 25 |
| EXTRACT-CUST | 15 |
| VALIDATE-DATA | 40 |
| CALC-INTEREST | 90 |
| UPDATE-LEDGER | 35 |
| GEN-REPORT | 20 |

```python
from datetime import datetime, timedelta
start = datetime.strptime("22:30", "%H:%M")
end = datetime.strptime("05:00", "%H:%M") + timedelta(days=1)
window_minutes = (end - start).seconds // 60

jobs = [25, 15, 40, 90, 35, 20]
total_job_minutes = sum(jobs)
buffer = window_minutes - total_job_minutes

print(f"Batch window: {window_minutes} minutes")
print(f"Total job runtime (worst case, sequential): {total_job_minutes} minutes")
print(f"Buffer remaining: {buffer} minutes ({buffer/window_minutes*100:.1f}% slack)")
```

**ผลลัพธ์จริง:**

```
Batch window: 390 minutes
Total job runtime (worst case, sequential): 225 minutes
Buffer remaining: 165 minutes (42.3% slack)
```

### นำผลการคำนวณไปใช้วางแผน Release

ตัวเลข "Buffer 165 นาที (42.3% slack)" นี้คือข้อมูลสำคัญที่ผู้บริหารโครงการต้องใช้ตัดสินใจ:

1. **ถ้า Release ใหม่เพิ่มงาน Batch ใหม่ที่ใช้เวลาไม่เกิน 165 นาที** → ยังคงอยู่ในกรอบเวลาที่ปลอดภัย
   สามารถวางแผน Deploy ได้ตามปกติ
2. **ถ้า Release ใหม่เพิ่มงานที่ใช้เวลาเกิน 165 นาที** → ต้องพิจารณาทางเลือกเพิ่มเติม เช่น การทำงานบาง
   ส่วนแบบขนาน (ทบทวน Job Dependency Graph จาก Part 086 ขั้นตอนที่ 853 ที่ `EXTRACT-TXN` และ
   `EXTRACT-CUST` ทำงานขนานกันได้), การปรับปรุงประสิทธิภาพงานเดิมก่อน (ทบทวน Part 088), หรือการขยาย
   Batch Window (ซึ่งมักกระทบข้อตกลงระดับบริการ (SLA) กับผู้ใช้ระบบ Online ที่ต้องรอ Batch เสร็จก่อน)
3. **Buffer ไม่ควรถูกใช้จนเกือบหมดโดยเจตนา** — ควรสำรอง Buffer ไว้เผื่อกรณีที่งาน Batch ใช้เวลานานกว่าปกติ
   (เช่น ปริมาณธุรกรรมสูงผิดปกติในบางคืน) แนวปฏิบัติทั่วไปคือไม่ควรวางแผนให้ใช้ Buffer เกิน 70-80% ของที่
   มีอยู่ในสถานการณ์ปกติ

### ปฏิทิน Freeze Period สำหรับช่วงเวลาที่มีความเสี่ยงสูง

นอกจากการคำนวณความจุ Batch Window แล้ว ผู้บริหารโครงการต้องวางแผน **Freeze Period** (ช่วงเวลาที่ห้าม
Deploy การเปลี่ยนแปลงใด ๆ ที่ไม่จำเป็นเร่งด่วน) สำหรับช่วงเวลาที่มีความเสี่ยงทางธุรกิจสูง เช่น:

| ช่วงเวลา | เหตุผลที่ต้อง Freeze |
|---|---|
| สิ้นเดือน/สิ้นไตรมาส/สิ้นปีบัญชี | งาน Batch ปิดบัญชีมีความซับซ้อนสูงกว่าปกติมาก ความเสี่ยงจากการเปลี่ยนแปลงระบบพร้อมกันสูงเกินไป |
| ช่วงเทศกาลที่มีธุรกรรมสูงผิดปกติ | ปริมาณธุรกรรมสูงทำให้ Batch Window ที่ปกติมี Buffer เพียงพออาจไม่พอในช่วงนี้ |
| ช่วงตรวจสอบบัญชีประจำปี (Audit) | ต้องการความเสถียรของระบบสูงสุดเพื่อไม่ให้กระทบกระบวนการตรวจสอบ |

### ข้อควรระวัง

- **การคำนวณ Buffer ต้องใช้เวลาที่วัดได้จริงจากการรัน production ไม่ใช่เวลาโดยประมาณจากการทดสอบใน
  สภาพแวดล้อม Development** เพราะปริมาณข้อมูลจริงและภาระของเครื่อง Production มักต่างจากสภาพแวดล้อม
  ทดสอบมาก (ทบทวนหลักการวัดผลจริงจาก Part 088)
- **Freeze Period ต้องสื่อสารล่วงหน้าให้ทุกทีมทราบชัดเจน** และควรมีกระบวนการยกเว้นสำหรับกรณีฉุกเฉินจริง ๆ
  (เช่น การแก้ไขบั๊กร้ายแรงที่กระทบเงินลูกค้า) ที่ผ่านการอนุมัติพิเศษ ไม่ใช่ห้ามเปลี่ยนแปลงทุกกรณีแบบตายตัว

Buffer เหลือ 165 นาที) จงเสนอทางเลือก 2 ข้อที่ทีมควรพิจารณาแทนการขอขยาย Batch Window ทันที

### กรอบคิดพื้นฐาน: Risk Score = Probability x Impact

หลักการบริหารความเสี่ยงที่ใช้กันแพร่หลายที่สุดคือการให้คะแนน **ความน่าจะเป็น (Probability)** และ
**ผลกระทบ (Impact)** แต่ละอย่างในสเกล 1-5 แล้วคูณกันเป็น **Risk Score** — ความเสี่ยงที่มีคะแนนสูงควรได้
รับความสนใจและแผนรับมือก่อนความเสี่ยงที่มีคะแนนต่ำ

### โปรแกรมคำนวณ Risk Score สำหรับความเสี่ยงตัวอย่างของโครงการ Modernization

### รูปแบบความล้มเหลวที่พบบ่อยที่สุดของโครงการ Mainframe Modernization

นอกจากการให้คะแนนความเสี่ยงเป็นรายการ (ตามตารางข้างต้น) ผู้บริหารโครงการควรรู้จัก **รูปแบบความล้มเหลว
(failure pattern) ที่เกิดซ้ำแล้วซ้ำเล่า**ในอุตสาหกรรมจริงของโครงการ Modernization ระบบ Mainframe เพื่อ
ออกแบบโครงการให้หลีกเลี่ยงรูปแบบเหล่านี้ตั้งแต่ต้น:

| รูปแบบความล้มเหลว | สาเหตุรากเหง้า | ทบทวนจาก |
|---|---|---|
| **"Big Bang" Rewrite ที่ล่มทั้งระบบ** | เขียนระบบใหม่ทั้งหมดแล้วสลับ (cutover) ครั้งเดียวโดยไม่มีการทดสอบขนานกับระบบเดิมก่อน เมื่อพบบั๊กหลัง Cutover ก็สายเกินจะย้อนกลับ | Part 001 ขั้นตอนที่ 3 (เหตุผลที่องค์กรไม่ Rewrite ทั้งระบบทันที) |
| **ตรรกะทางธุรกิจที่ไม่มีการบันทึกไว้หายไประหว่างย้ายระบบ** | ทีมใหม่เข้าใจว่า "อ่านโค้ดแล้วเขียนใหม่ให้เหมือนกัน" พอเพียง แต่พลาดกฎธุรกิจพิเศษที่ไม่มีเอกสารรองรับ | ขั้นตอนที่ 899 (Knowledge Transfer) |
| **ประเมินขอบเขตงานต่ำเกินไปเพราะนับแค่ LOC ผิวเผิน** | ใช้ LOC Heuristic เพียงอย่างเดียวกับโค้ดที่ซับซ้อนเชิงธุรกิจสูงแต่บรรทัดน้อย | ขั้นตอนที่ 893 (Function Point Analysis) |
| **เปลี่ยน Copybook ร่วมโดยไม่ประเมินผลกระทบข้ามทีม** | ทีมหนึ่งแก้ Copybook เพื่อรองรับระบบใหม่ โดยไม่รู้ว่ามีอีก 40 โปรแกรมของทีมอื่น `COPY` มันอยู่ | ขั้นตอนที่ 895 (RFC/CAB) |
| **มั่นใจเกินไปว่าระบบใหม่ถูกต้องเพราะ "คอมไพล์ผ่านและทดสอบ Unit Test ผ่านหมด"** | Unit Test ทดสอบเฉพาะกรณีที่ทีมคิดขึ้นเอง แต่ไม่ครอบคลุมกรณีขอบเขต (edge case) ที่มีอยู่จริงในข้อมูล Production หลายสิบปี | ขั้นตอนถัดไปในหัวข้อนี้ (Parallel-Run Validation) |

ระบบเดิมจริงหรือไม่" ก่อนที่จะเลิกใช้ระบบเดิม** — สองกลยุทธ์ต่อไปนี้คือคำตอบมาตรฐานของอุตสาหกรรมสำหรับ
ปัญหานี้โดยเฉพาะ

### กลยุทธ์ที่ 1: แนวทางแบบ Phased Approach แทน "Big Bang" Cutover

**Phased Approach** คือการแบ่งการย้ายระบบ (Modernization) ออกเป็นช่วง ๆ ที่มีขนาดเล็กและตรวจสอบได้
แทนที่จะสลับระบบทั้งหมดในคราวเดียว หลักการนี้สอดคล้องโดยตรงกับแนวทาง "Strangler Fig Pattern" ที่ Part
077 เคยแนะนำไว้ในบริบทเทคนิค — ในบริบทการบริหารโครงการ Phased Approach มักแบ่งเป็น 4 ระยะ:

```
+------------------------------------------------------------------+
|                  Phased Modernization Roadmap                    |
+------------------------------------------------------------------+
|                                                                    |
|  ระยะ 1: โมดูลที่มีความเสี่ยงต่ำที่สุดก่อน                          |
|  - เลือกโมดูลที่กระทบธุรกิจน้อยที่สุด (เช่น รายงานภายใน)             |
|  - เป้าหมาย: พิสูจน์ว่ากระบวนการ/เครื่องมือ Modernization ใช้ได้จริง  |
|                          |                                         |
|                          v                                         |
|  ระยะ 2: โมดูลระดับกลาง พร้อม Parallel-Run เต็มรูปแบบ               |
|  - รันระบบเก่าและใหม่คู่ขนานกันจริงในสภาพแวดล้อม Production          |
|  - เปรียบเทียบผลลัพธ์ทุกรอบก่อนตัดสินใจ Cutover โมดูลถัดไป           |
|                          |                                         |
|                          v                                         |
|  ระยะ 3: โมดูลที่มีความเสี่ยงสูง (Core Business Logic)              |
|  - ใช้บทเรียนและเครื่องมือเปรียบเทียบที่ปรับปรุงแล้วจากระยะ 1-2       |
|  - Parallel-Run ระยะเวลานานกว่าปกติ (เช่น ครบรอบบัญชีสิ้นเดือน)       |
|                          |                                         |
|                          v                                         |
|  ระยะ 4: ปลดระวางระบบเดิม (Decommission)                          |
|  - ทำหลังจากมั่นใจ 100% ว่าระบบใหม่ทำงานถูกต้องครบทุกกรณีแล้วเท่านั้น |
+------------------------------------------------------------------+
```

**ทำไม Phased Approach ถึงลดความเสี่ยงได้จริง**: หากพบปัญหาในระยะ 1 (ความเสี่ยงต่ำ) ผลกระทบทางธุรกิจ
มีจำกัด และทีมยังมีระบบเดิมที่โมดูลอื่นยังใช้งานได้ตามปกติเป็น "ตาข่ายนิรภัย" ต่างจาก Big Bang ที่หากพบ
ปัญหาหลัง Cutover ทั้งระบบ จะไม่มีทางเลือกอื่นนอกจากเร่งแก้ไขระบบใหม่ภายใต้ความกดดันสูงสุด หรือย้อนกลับ
ไปใช้ระบบเดิมทั้งหมด (ซึ่งมักทำได้ยากมากหรือเป็นไปไม่ได้เลยหากข้อมูลถูกเปลี่ยนแปลงไปแล้ว)

### กลยุทธ์ที่ 2: Parallel-Run Validation — เทคนิคหัวใจของทุกระยะ

**Parallel-Run Validation** คือการรันตรรกะเก่า (OLD/legacy logic) และตรรกะใหม่ (NEW/modernized logic)
กับข้อมูลชุดเดียวกัน แล้ว**เปรียบเทียบผลลัพธ์ทีละรายการ**ก่อนตัดสินใจ Cutover จริง — นี่คือเทคนิคที่ป้องกัน
รูปแบบความล้มเหลว "มั่นใจเกินไปว่าระบบใหม่ถูกต้องเพราะ Unit Test ผ่านหมด" ที่กล่าวถึงข้างต้นได้โดยตรง เพราะ
การเปรียบเทียบกับข้อมูลจริงจำนวนมากมีโอกาสพบกรณีขอบเขต (edge case) ที่ Unit Test ไม่เคยคิดถึงมาก่อน

ตัวอย่างต่อไปนี้จำลองสถานการณ์จริง: ทีม Modernization เขียนตรรกะคำนวณดอกเบี้ยแบบขั้นบันได (tiered
interest) ขึ้นใหม่โดยตั้งใจให้ผลลัพธ์**เหมือนกับตรรกะเดิมทุกประการ** แต่ระหว่างการ Refactor จาก
`IF...ELSE` เป็น `EVALUATE` (ทบทวนรูปแบบจาก Part 011) เกิดข้อผิดพลาดที่พบบ่อยมากในการย้ายระบบจริง:
**เงื่อนไขขอบเขต (boundary condition) ถูกเขียนผิดจาก `<` เป็น `<=`** ที่จุดแบ่งขั้นบันไดจุดหนึ่ง:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP897PARALLEL.
       AUTHOR. COBOL-COURSE.
      *> Demonstrates a "parallel run" validation: computes interest
      *> for the same set of accounts using the OLD (legacy) tiered
      *> rate logic and the NEW (modernized) tiered rate logic, then
      *> compares every result and reports MATCH or MISMATCH, the way
      *> a real modernization project verifies new code against the
      *> system it replaces before cutover.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  ACCOUNT-TABLE.
           05  ACCOUNT-ENTRY OCCURS 5 TIMES.
               10  ACCT-ID          PIC X(6).
               10  ACCT-BALANCE     PIC 9(7)V99.

       01  WS-IDX                PIC 9(1).
       01  WS-OLD-RATE           PIC 9V999.
       01  WS-NEW-RATE           PIC 9V999.
       01  WS-OLD-INTEREST       PIC 9(7)V99.
       01  WS-NEW-INTEREST       PIC 9(7)V99.
       01  WS-MISMATCH-COUNT     PIC 9(2) VALUE 0.

       PROCEDURE DIVISION.
       MAIN-PARA.
           MOVE "AC1001" TO ACCT-ID(1).
           MOVE 500.00   TO ACCT-BALANCE(1).
           MOVE "AC1002" TO ACCT-ID(2).
           MOVE 1000.00  TO ACCT-BALANCE(2).
           MOVE "AC1003" TO ACCT-ID(3).
           MOVE 2500.00  TO ACCT-BALANCE(3).
           MOVE "AC1004" TO ACCT-ID(4).
           MOVE 5000.00  TO ACCT-BALANCE(4).
           MOVE "AC1005" TO ACCT-ID(5).
           MOVE 10000.00 TO ACCT-BALANCE(5).

           DISPLAY "ACCT-ID BALANCE    OLD-INT   NEW-INT   RESULT".

           PERFORM VARYING WS-IDX FROM 1 BY 1 UNTIL WS-IDX > 5
               PERFORM OLD-CALC-INTEREST
               PERFORM NEW-CALC-INTEREST
               IF WS-OLD-INTEREST = WS-NEW-INTEREST
                   DISPLAY ACCT-ID(WS-IDX) " " ACCT-BALANCE(WS-IDX)
                       " " WS-OLD-INTEREST " " WS-NEW-INTEREST
                       "  MATCH"
               ELSE
                   ADD 1 TO WS-MISMATCH-COUNT
                   DISPLAY ACCT-ID(WS-IDX) " " ACCT-BALANCE(WS-IDX)
                       " " WS-OLD-INTEREST " " WS-NEW-INTEREST
                       "  *** MISMATCH ***"
               END-IF
           END-PERFORM.

           DISPLAY "TOTAL MISMATCHES: " WS-MISMATCH-COUNT.
           IF WS-MISMATCH-COUNT > 0
               DISPLAY "PARALLEL RUN RESULT: NOT READY FOR CUTOVER"
           ELSE
               DISPLAY "PARALLEL RUN RESULT: READY FOR CUTOVER"
           END-IF.
           STOP RUN.

       OLD-CALC-INTEREST.
           IF ACCT-BALANCE(WS-IDX) < 1000.00
               MOVE 0.010 TO WS-OLD-RATE
           ELSE
               IF ACCT-BALANCE(WS-IDX) < 5000.00
                   MOVE 0.015 TO WS-OLD-RATE
               ELSE
                   MOVE 0.020 TO WS-OLD-RATE
               END-IF
           END-IF.
           COMPUTE WS-OLD-INTEREST ROUNDED =
               ACCT-BALANCE(WS-IDX) * WS-OLD-RATE.

       NEW-CALC-INTEREST.
           EVALUATE TRUE
               WHEN ACCT-BALANCE(WS-IDX) <= 1000.00
                   MOVE 0.010 TO WS-NEW-RATE
               WHEN ACCT-BALANCE(WS-IDX) < 5000.00
                   MOVE 0.015 TO WS-NEW-RATE
               WHEN OTHER
                   MOVE 0.020 TO WS-NEW-RATE
           END-EVALUATE.
           COMPUTE WS-NEW-INTEREST ROUNDED =
               ACCT-BALANCE(WS-IDX) * WS-NEW-RATE.
```


### วิเคราะห์ผล — Parallel-Run จับบั๊กที่ Unit Test อาจพลาดได้อย่างไร

บัญชี `AC1002` มียอดคงเหลือพอดี **1000.00 บาท** ซึ่งเป็น**จุดแบ่งขั้นบันได (boundary value)** ระหว่างชั้น
ที่ 1 (ต่ำกว่า 1000) กับชั้นที่ 2 (1000 ถึงต่ำกว่า 5000) ตรรกะเดิม (`OLD-CALC-INTEREST`) ใช้เงื่อนไข
`< 1000.00` ทำให้ 1000.00 ไม่เข้าเงื่อนไขแรก และตกไปอยู่ชั้นที่ 2 (อัตรา 1.5% → ดอกเบี้ย 15.00) ในขณะที่
ตรรกะใหม่ (`NEW-CALC-INTEREST`) เขียนเงื่อนไขแรกเป็น `<= 1000.00` โดยไม่ได้ตั้งใจ ทำให้ 1000.00 ถูกจัด
เข้าชั้นที่ 1 ผิดพลาด (อัตรา 1% → ดอกเบี้ย 10.00) — **ผลต่าง 5.00 บาทต่อบัญชีนี้ดูเล็กน้อย แต่ถ้าระบบจริงมี
ลูกค้านับล้านคนและมีบางส่วนที่ยอดคงเหลือตรงจุดแบ่งพอดี ความเสียหายสะสมจะมีนัยสำคัญทางบัญชีทันที** และที่
สำคัญกว่านั้น: หากทีมทดสอบด้วย Unit Test ที่เลือกค่าทดสอบแบบสุ่ม (เช่น 500, 2500, 10000) โดยไม่ได้คิดถึง
ค่าที่ตรงกับจุดแบ่งขั้นบันไดพอดี **บั๊กนี้จะไม่ถูกพบเลยจนกว่าจะมีลูกค้าจริงที่ยอดคงเหลือตรงจุดแบ่งในระบบ
Production** — นี่คือเหตุผลที่ Parallel-Run กับ**ข้อมูลจริงทั้งชุด** (ไม่ใช่แค่กรณีทดสอบที่คนเขียนโค้ดคิดขึ้นเอง)
มีคุณค่าสูงกว่าการพึ่งพา Unit Test เพียงอย่างเดียวสำหรับโครงการ Modernization ที่มีความเสี่ยงสูง

### ข้อควรระวัง

- **Risk Score เป็นเครื่องมือจัดลำดับความสำคัญ ไม่ใช่คำทำนายที่แม่นยำ** — ความเสี่ยงที่มีคะแนนต่ำกว่ายังคง
  ต้องมีการติดตาม (monitor) อย่างสม่ำเสมอ ไม่ใช่ละเลยไปเลย เพราะสถานการณ์อาจเปลี่ยนแปลงทำให้คะแนน
  เปลี่ยนไปได้ตลอดโครงการ
- **การให้คะแนน Probability และ Impact ควรทำร่วมกันโดยทีมที่มีความรู้หลากหลาย** (ทั้งทีมเทคนิคและทีม
  ธุรกิจ) ไม่ใช่ให้คนเดียวตัดสินใจ เพราะมุมมองความเสี่ยงจากมุมเทคนิคและมุมธุรกิจมักต่างกัน (เช่น ทีมเทคนิค
  อาจมองว่า Batch Window Overrun มีผลกระทบปานกลาง แต่ทีมธุรกิจอาจมองว่าผลกระทบสูงมากเพราะกระทบความ
  เชื่อมั่นของลูกค้าโดยตรง)
- **Parallel-Run ที่ผ่านหมดทุกรายการก็ยังไม่ใช่หลักฐานว่าระบบใหม่ถูกต้อง 100%** — เป็นเพียงหลักฐานว่าระบบ
  ใหม่ถูกต้อง**เท่าที่ข้อมูลชุดที่ทดสอบครอบคลุมถึง**เท่านั้น ควรเลือกช่วงเวลาทดสอบที่ครอบคลุมสถานการณ์พิเศษ
  ให้มากที่สุด (เช่น รอบสิ้นเดือน สิ้นปีบัญชี ที่ตรรกะพิเศษมักถูกกระตุ้นใช้งาน) ไม่ใช่แค่วันทำงานปกติทั่วไป

## ขั้นตอนที่ 898: ตัวชี้วัดและ KPI สำหรับติดตามสุขภาพของโปรเจกต์ COBOL ขนาดใหญ่

### ทำไมต้องมีตัวชี้วัดเชิงปริมาณ ไม่ใช่แค่ความรู้สึก

ผู้บริหารโครงการ COBOL ขนาดใหญ่ต้องรายงานสถานะโครงการให้ผู้บริหารระดับสูงทราบอย่างสม่ำเสมอ — การ
รายงานด้วยความรู้สึก ("ระบบดูเสถียรดี") ไม่เพียงพอสำหรับการตัดสินใจเชิงกลยุทธ์ จำเป็นต้องมี **ตัวชี้วัด
เชิงปริมาณ (KPI)** ที่วัดได้จริงและสม่ำเสมอ

### สอง KPI พื้นฐานที่สำคัญที่สุดสำหรับโปรเจกต์บำรุงรักษา COBOL

1. **Defect Density (ความหนาแน่นของข้อบกพร่อง)**: จำนวนข้อบกพร่องที่พบต่อขนาดโค้ด 1,000 บรรทัด (KLOC)
   — ยิ่งต่ำยิ่งดี บ่งบอกคุณภาพของกระบวนการพัฒนาและทดสอบ
2. **Batch SLA Compliance (อัตราการทำงานตรงเวลาของ Batch)**: สัดส่วนของรอบ Batch ที่ทำงานเสร็จภายใน
   กรอบเวลาที่กำหนด (ทบทวน Batch Window จากขั้นตอนที่ 896) — ยิ่งใกล้ 100% ยิ่งดี

### โปรแกรมคำนวณ KPI ทั้งสองตัวจากข้อมูลตัวอย่าง

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. STEP898KPI.
       AUTHOR. COBOL-COURSE.
      *> Computes two common maintenance-project KPIs from sample
      *> monthly figures:
      *>   1) Defect density = defects / (LOC / 1000)
      *>   2) Batch SLA compliance = on-time runs / total runs * 100

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-TOTAL-LOC         PIC 9(9)  VALUE 125000.
       01  WS-DEFECTS-FOUND     PIC 9(5)  VALUE 18.
       01  WS-KLOC              PIC 9(9)V99.
       01  WS-DEFECT-DENSITY    PIC 9(5)V99.

       01  WS-TOTAL-BATCH-RUNS  PIC 9(5) VALUE 300.
       01  WS-ONTIME-RUNS       PIC 9(5) VALUE 291.
       01  WS-SLA-PERCENT       PIC 9(3)V99.

       PROCEDURE DIVISION.
       MAIN-PARA.
           COMPUTE WS-KLOC = WS-TOTAL-LOC / 1000.
           COMPUTE WS-DEFECT-DENSITY ROUNDED =
               WS-DEFECTS-FOUND / WS-KLOC.
           DISPLAY "TOTAL LOC        : " WS-TOTAL-LOC.
           DISPLAY "DEFECTS FOUND    : " WS-DEFECTS-FOUND.
           DISPLAY "DEFECT DENSITY   : " WS-DEFECT-DENSITY
               " per 1,000 LOC".

           COMPUTE WS-SLA-PERCENT ROUNDED =
               WS-ONTIME-RUNS / WS-TOTAL-BATCH-RUNS * 100.
           DISPLAY "BATCH RUNS TOTAL : " WS-TOTAL-BATCH-RUNS.
           DISPLAY "ON-TIME RUNS     : " WS-ONTIME-RUNS.
           DISPLAY "BATCH SLA        : " WS-SLA-PERCENT "%".
           STOP RUN.
```

```bash
cobc -x -o step898_kpi step898_kpi.cob
./step898_kpi
```

**ผลลัพธ์จริง:**

```
TOTAL LOC        : 000125000
DEFECTS FOUND    : 00018
DEFECT DENSITY   : 00000.14 per 1,000 LOC
BATCH RUNS TOTAL : 00300
ON-TIME RUNS     : 00291
BATCH SLA        : 097.00%
```

### วิเคราะห์ผลและการนำไปใช้

- **Defect Density 0.14 ต่อ 1,000 LOC**: หมายความว่าในโค้ด 125,000 บรรทัด พบข้อบกพร่อง 18 จุด — ตัวเลข
  นี้มีประโยชน์มากที่สุดเมื่อ**เปรียบเทียบกับตัวเองในอดีต** (เช่น เทียบกับเดือนก่อนหน้า) มากกว่าการเทียบกับ
  ค่าอ้างอิงจากอุตสาหกรรมอื่น เพราะแต่ละระบบมีลักษณะเฉพาะต่างกัน
- **Batch SLA 97%**: หมายความว่าจาก 300 รอบ Batch ในช่วงเวลาที่วัด มี 291 รอบที่เสร็จตรงเวลา — ตัวเลขนี้
  ควรถูกจับตาดูเป็นพิเศษเพราะเชื่อมโยงโดยตรงกับขั้นตอนที่ 896 (การบริหาร Batch Window) หาก SLA เริ่มลดลง
  อาจเป็นสัญญาณเตือนล่วงหน้าว่า Buffer ของ Batch Window กำลังจะไม่เพียงพอ ก่อนที่จะเกิดปัญหาจริงจัง

### ข้อควรระวัง

- **อย่าใช้ KPI เพียงตัวเดียวตัดสินสุขภาพของโครงการทั้งหมด** — Defect Density ต่ำอาจเกิดจากการทดสอบไม่
  ครอบคลุมเพียงพอ (พบบั๊กน้อยเพราะไม่ได้มองหา) ไม่ใช่เพราะคุณภาพโค้ดดีจริง ควรพิจารณา KPI หลายตัวประกอบ
  กันเสมอ (เช่น เทียบคู่กับ Test Coverage จาก Part 079)
- **KPI ต้องถูกวัดอย่างสม่ำเสมอด้วยวิธีการเดียวกันทุกครั้ง** เพื่อให้เปรียบเทียบข้ามช่วงเวลาได้อย่างมีความหมาย
  — การเปลี่ยนวิธีนับ (เช่น เปลี่ยนนิยามว่าอะไรคือ "ข้อบกพร่อง") กลางทางโดยไม่แจ้งทำให้แนวโน้มที่รายงาน
  เชื่อถือไม่ได้

### แบบฝึกหัดที่ 898.1

**โจทย์**: หากเดือนถัดไป Batch SLA ลดลงจาก 97% เหลือ 90% (จาก 300 รอบ เหลือรอบที่ตรงเวลาเพียง 270 รอบ)
แต่ Defect Density ยังคงเท่าเดิม จงวิเคราะห์ว่าอาจเกิดจากสาเหตุใดได้บ้าง และควรตรวจสอบเรื่องใดก่อน

**เฉลยแนวทาง**: เนื่องจาก Defect Density ไม่เปลี่ยนแปลง แสดงว่าปัญหาไม่ได้มาจากคุณภาพโค้ดที่แย่ลง (ไม่มี
บั๊กใหม่เพิ่มขึ้น) จึงควรตรวจสอบสาเหตุอื่นที่เกี่ยวข้องกับ**ปริมาณงานหรือทรัพยากรระบบ**แทน เช่น (1) ปริมาณ
ธุรกรรมที่ต้องประมวลผลต่อคืนเพิ่มขึ้นจนใกล้หรือเกิน Buffer ที่คำนวณไว้ในขั้นตอนที่ 896 (2) มีการเพิ่มงาน
Batch ใหม่เข้าไปในสายงานโดยไม่ได้ประเมินผลกระทบต่อ Buffer อย่างเหมาะสม (เชื่อมโยงกับกระบวนการ RFC/CAB
จากขั้นตอนที่ 895 ที่ควรครอบคลุมการเปลี่ยนแปลง Batch Job ด้วย ไม่ใช่แค่ Copybook) หรือ (3) มีปัญหาด้าน
โครงสร้างพื้นฐาน (เช่น เครื่องแม่ข่ายทำงานช้าลงจากปัจจัยภายนอก) ขั้นตอนแรกที่ควรตรวจสอบคือดูว่ามีการเพิ่ม
งาน Batch ใหม่หรือมีปริมาณธุรกรรมเพิ่มขึ้นผิดปกติในช่วงเวลาเดียวกับที่ SLA เริ่มลดลงหรือไม่ เพราะเป็นสาเหตุ
ที่พบบ่อยที่สุดและตรวจสอบได้ง่ายที่สุดก่อนที่จะไปสืบสวนสาเหตุที่ซับซ้อนกว่า

จากตารางนี้ **"ระบบคำนวณดอกเบี้ย (Core)" คือลำดับความสำคัญอันดับหนึ่ง** เพราะมี Bus Factor เท่ากับ 1
พอดี และผู้เชี่ยวชาญคนเดียวที่เข้าใจระบบนี้จะเกษียณภายใน 1 ปี — ตรงกับผลการวิเคราะห์ Risk Score จาก
ขั้นตอนที่ 897 ที่ให้คะแนนความเสี่ยงประเภทนี้สูงสุด

### แผนปฏิบัติการถ่ายทอดความรู้ที่เป็นรูปธรรม

1. **กำหนดระยะเวลาเหลื่อมกัน (Overlap Period) อย่างน้อย 6-12 เดือนก่อนวันเกษียณ** — ให้ผู้เชี่ยวชาญและ
   ผู้สืบทอดทำงานร่วมกันจริงในช่วงนี้ ไม่ใช่แค่ส่งมอบเอกสารในวันสุดท้าย
2. **บันทึกการตัดสินใจสำคัญพร้อมเหตุผล ไม่ใช่แค่ "ทำอย่างไร"** — เอกสารที่ดีต้องตอบคำถาม "ทำไมถึงออกแบบ
   แบบนี้" ไม่ใช่แค่ "โค้ดนี้ทำอะไร" เพราะเหตุผลเชิงธุรกิจมักสูญหายไปพร้อมกับคนที่จากไป แม้โค้ดจะยังอยู่ครบ
3. **ใช้ Pair Programming กับงานบำรุงรักษาจริง** — ให้ผู้เชี่ยวชาญและพนักงานรุ่นใหม่แก้ไขบั๊กหรือเพิ่ม
   ฟีเจอร์ร่วมกันจริง แทนที่จะให้พนักงานรุ่นใหม่อ่านโค้ดเงียบ ๆ คนเดียว
4. **ทบทวน Knowledge Audit Matrix เป็นระยะ** (เช่น ทุกไตรมาส) เพื่อติดตามว่า Bus Factor ของแต่ละระบบ
   ดีขึ้นหรือแย่ลงตามแผนที่วางไว้หรือไม่

### ข้อควรระวัง

- **อย่ารอจนใกล้วันเกษียณของผู้เชี่ยวชาญคนสำคัญจึงเริ่มวางแผนถ่ายทอดความรู้** — ทบทวนจากขั้นตอนที่ 897:
  ความเสี่ยงประเภทนี้ยิ่งปล่อยไว้นานยิ่งแก้ไขยากขึ้นแบบไม่สามารถย้อนกลับได้ ควรเริ่มกระบวนการนี้ทันทีที่ระบุ
  ได้ว่า Bus Factor ของระบบใดเท่ากับ 1
- **การถ่ายทอดความรู้ไม่ใช่แค่ความรับผิดชอบของผู้เชี่ยวชาญที่กำลังจะเกษียณ** — องค์กรต้องจัดสรรเวลาและ
  ทรัพยากรอย่างเป็นทางการให้กับกระบวนการนี้ (เช่น ลดภาระงานปกติของผู้เชี่ยวชาญลงชั่วคราวเพื่อให้มีเวลาสอน
  งานจริง) ไม่ใช่คาดหวังให้ทำนอกเหนือจากงานประจำที่มีอยู่แล้วเต็มมือ

### แบบฝึกหัดที่ 899.1

**โจทย์**: จงอธิบายว่าทำไม "การบันทึกเหตุผลเชิงธุรกิจเบื้องหลังการตัดสินใจ" (ไม่ใช่แค่บันทึกว่าโค้ดทำอะไร)
จึงสำคัญเป็นพิเศษสำหรับการถ่ายทอดความรู้ในระบบ COBOL Legacy

**เฉลยแนวทาง**: เพราะโค้ด COBOL ที่มีอยู่แล้วสามารถบอกได้ว่า **"ทำอะไร"** อย่างชัดเจนเสมอ (อ่านโค้ดก็รู้ว่า
คำนวณอะไร เก็บข้อมูลอะไร) แต่ไม่สามารถบอกได้เลยว่า **"ทำไมถึงต้องทำแบบนี้"** เช่น กฎธุรกิจประหลาด ๆ ที่ดู
ไม่มีเหตุผลในสายตาคนรุ่นใหม่ (เช่น เงื่อนไขพิเศษสำหรับลูกค้ากลุ่มหนึ่งที่มีมาตั้งแต่ยุคก่อน) อาจมีที่มาจาก
เหตุการณ์ทางธุรกิจหรือกฎหมายในอดีตที่ไม่มีการบันทึกไว้ที่ไหนเลยนอกจากในความทรงจำของผู้เชี่ยวชาญ หากไม่มี
การบันทึกเหตุผลนี้ไว้ก่อนที่ผู้เชี่ยวชาญจะจากไป ทีมรุ่นใหม่อาจตัดสินใจ "ทำความสะอาดโค้ด" โดยลบเงื่อนไข
พิเศษที่ดูไม่มีเหตุผลนั้นออกไป โดยไม่รู้ว่ากำลังทำลายกฎธุรกิจที่จำเป็นจริง ๆ อยู่ ซึ่งอาจสร้างความเสียหายร้ายแรง
ที่ตรวจพบได้ยากมาก เพราะโค้ดยังคง "คอมไพล์ผ่าน" และดูเหมือนทำงานถูกต้องในกรณีทดสอบทั่วไป

### แบบฝึกหัดที่ 900.1

**โจทย์**: จากวงจรชีวิตการเปลี่ยนแปลงทั้ง 6 ขั้นตอนในผังข้างต้น หากคุณต้องเลือกตัดขั้นตอนใดขั้นตอนหนึ่งออก
เนื่องจากข้อจำกัดด้านเวลาของโครงการ (สมมติว่าต้องเลือกจริง ๆ) จะเลือกตัดขั้นตอนใด และมีความเสี่ยงอะไรที่
ต้องยอมรับจากการตัดขั้นตอนนั้นออก

**เฉลยแนวทาง**: ไม่มีคำตอบที่ถูกต้องตายตัว เพราะทุกขั้นตอนมีความสำคัญ แต่แนวทางการวิเคราะห์ที่ดีคือ
พิจารณาว่าขั้นตอนใด**มีกลไกชดเชยบางส่วนอยู่แล้วในขั้นตอนอื่น** เช่น หากจำเป็นต้องลดทอนขั้นตอนที่ 5 (Deploy
และติดตามผลอย่างละเอียด) เหลือเพียงการติดตามพื้นฐาน ความเสี่ยงที่ต้องยอมรับคือ **อาจตรวจไม่พบผลกระทบทาง
ลบที่เกิดขึ้นช้า ๆ** (เช่น Batch SLA ค่อย ๆ ลดลงทีละน้อยแทนที่จะลดลงทันที) แต่ยังพอมีขั้นตอนที่ 6 (ถ่ายทอด
ความรู้) ช่วยชดเชยได้บ้างหากทีมยังคงมีความเข้าใจระบบเพียงพอที่จะสังเกตความผิดปกติได้ด้วยตัวเอง **ในทาง
กลับกัน ไม่ควรตัดขั้นตอนที่ 2 (ตรวจสอบผลกระทบ) หรือขั้นตอนที่ 4 (ประเมินความเสี่ยง) ออกเด็ดขาด** เพราะทั้ง
สองขั้นตอนนี้เป็นกลไกป้องกันความเสียหายที่**เกิดขึ้นก่อน**การ Deploy จริง หากตัดออกแล้วเกิดปัญหา ความ
เสียหายอาจเกิดขึ้นจริงในระบบ production ไปแล้วก่อนที่จะมีโอกาสแก้ไข ต่างจากขั้นตอนอื่นที่เป็นกลไกติดตาม
ผลหรือปรับปรุงต่อเนื่องซึ่งยังพอมีเวลาตอบสนองได้หลังพบปัญหา
