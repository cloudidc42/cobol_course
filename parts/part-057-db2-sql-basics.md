# Part 057: DB2 และ SQL เบื้องต้นสำหรับ COBOL (ขั้นตอนที่ 561–570)

## คำนำของ Part นี้

ตลอด Part 023-029 และ Part 055-056 เราเรียนรู้การจัดการข้อมูลแบบ **record-based** (Sequential,
Indexed, Relative, VSAM) ที่โปรแกรม COBOL ต้องเขียนโค้ดควบคุมการอ่าน/เขียนทีละ record ด้วยตัวเอง
ทั้งหมด — ต้องรู้ว่า record อยู่ตำแหน่งไหน ต้องเขียน loop เพื่อไล่หา ต้องจัดการ Key เอง แนวคิดนี้
ทำงานได้ดีมากในโลกที่ข้อมูลมีโครงสร้างง่าย แต่เมื่อระบบมีความซับซ้อนขึ้น (ข้อมูลลูกค้าที่ต้อง
เชื่อมโยงกับบัญชีธนาคาร ธุรกรรม และประวัติการชำระเงินพร้อมกัน) การจัดการทุกอย่างผ่านไฟล์ record
เพียงอย่างเดียวจะซับซ้อนและเสี่ยงต่อข้อผิดพลาดมาก

**ฐานข้อมูลเชิงสัมพันธ์ (Relational Database)** และภาษา **SQL (Structured Query Language)**
ถูกออกแบบมาแก้ปัญหานี้โดยตรง: แทนที่จะบอกคอมพิวเตอร์ว่า "ทำอย่างไร" (How) ทีละขั้นตอนแบบ COBOL
procedural เราบอกฐานข้อมูลว่า "ต้องการอะไร" (What) แล้วปล่อยให้ฐานข้อมูลตัดสินใจวิธีที่ดีที่สุดเอง
Part นี้จะแนะนำแนวคิดพื้นฐานของฐานข้อมูลเชิงสัมพันธ์ ภาษา SQL มาตรฐาน และ **DB2** ซึ่งเป็น
ฐานข้อมูลเชิงสัมพันธ์ของ IBM ที่ใช้คู่กับ COBOL บน Mainframe มากที่สุด เพื่อปูทางไปสู่ **Embedded
SQL** ที่จะสอนเต็มรูปแบบใน Part 058

> **สำคัญมาก — ขอบเขตของ Part นี้**: สภาพแวดล้อม Linux Sandbox ของหลักสูตรนี้**ไม่มี DB2 ติดตั้ง
> อยู่ และไม่มีฐานข้อมูลเชิงสัมพันธ์ใด ๆ เชื่อมต่ออยู่เลย** เนื้อหาของ Part นี้จึงเป็นการอธิบาย
> **แนวคิดและไวยากรณ์ SQL มาตรฐาน** (ที่ใกล้เคียงกับ DB2 SQL Dialect) เพื่อให้คุณอ่านและเขียนเป็น
> ก่อนที่จะเชื่อมโยงกับ COBOL ผ่าน Embedded SQL ใน Part 058 **คำสั่ง SQL ทุกชิ้นในเอกสารนี้ไม่ได้
> ถูกรันจริงกับฐานข้อมูลหรือเครื่องมือใด ๆ ในสภาพแวดล้อมนี้** และไม่ได้ผูกกับ database engine
> ตัวใดตัวหนึ่งโดยเฉพาะ — เป็นการอธิบายไวยากรณ์และผลลัพธ์ที่ **คาดว่าจะได้** ตามหลักการทำงานของ
> SQL มาตรฐานเท่านั้น หากต้องการทดลองรันจริง ควรใช้ DB2 บน Mainframe จริง, DB2 Community
> Edition, หรือฐานข้อมูลเชิงสัมพันธ์อื่นที่รองรับ SQL มาตรฐาน (เช่น PostgreSQL/MySQL ที่จะกล่าว
> ถึงใน Part 075)

## ขั้นตอนที่ 561: แนวคิดฐานข้อมูลเชิงสัมพันธ์ (Relational Database)

### ปัญหาที่ฐานข้อมูลเชิงสัมพันธ์แก้ไข

ลองนึกภาพระบบธนาคารที่ต้องเก็บข้อมูลลูกค้า บัญชี และธุรกรรม ถ้าใช้ไฟล์ COBOL แบบที่เรียนมา
(Part 023-029) เราต้องออกแบบไฟล์แยกกัน 3 ไฟล์ แล้วเขียนโปรแกรมเชื่อมโยงข้อมูลระหว่างไฟล์เอง
(คล้ายเทคนิค Master-Detail ที่ Part 026 สอนไว้) ทุกครั้งที่ต้องการคำตอบใหม่ (เช่น "ลูกค้าคนไหนมี
ยอดเงินรวมทุกบัญชีมากกว่า 1 ล้านบาท") ต้องเขียนโปรแกรมใหม่ทั้งหมด — **ฐานข้อมูลเชิงสัมพันธ์**
แก้ปัญหานี้ด้วยการเก็บข้อมูลเป็น **ตาราง (Table)** ที่เชื่อมโยงกันได้อย่างยืดหยุ่น แล้วใช้ภาษา SQL
"ถาม" คำถามใหม่ ๆ ได้ทันทีโดยไม่ต้องเขียนโปรแกรมใหม่

### องค์ประกอบพื้นฐานของฐานข้อมูลเชิงสัมพันธ์

| คำศัพท์ SQL/Relational | ความหมาย | เทียบเท่าแนวคิดใน COBOL File ที่เคยเรียน |
|---|---|---|
| **Table** (ตาราง) | ชุดข้อมูลที่มีโครงสร้างแถว-คอลัมน์เดียวกัน | ไฟล์ (`FD`) |
| **Row** (แถว) หรือ Tuple | ข้อมูลหนึ่งชุดในตาราง | Record (`01` level) |
| **Column** (คอลัมน์) หรือ Field | คุณสมบัติหนึ่งอย่างของแถว | Field ย่อย (`05` level) |
| **Primary Key** | คอลัมน์ (หรือกลุ่มคอลัมน์) ที่ระบุแถวได้ไม่ซ้ำกัน | `RECORD KEY IS` (Part 028) |
| **Foreign Key** | คอลัมน์ที่อ้างอิงไปยัง Primary Key ของอีกตาราง | ไม่มีเทียบเท่าตรงตัว — ต้องเขียนโปรแกรมเชื่อมเอง |
| **Schema** | โครงสร้างและกฎทั้งหมดของฐานข้อมูล | โครงสร้างไฟล์ทั้งหมดในระบบ (รวมกันหลายไฟล์) |

### ตัวอย่างตาราง: CUSTOMER

| CUST_ID | CUST_NAME | CUST_CITY |
|---|---|---|
| 100001 | SOMCHAI JAIDEE | BANGKOK |
| 100002 | SUDA MEECHAI | CHIANG MAI |
| 100003 | PRASERT KAEWTA | BANGKOK |

### ตัวอย่างตาราง: ACCOUNT (เชื่อมโยงกับ CUSTOMER ผ่าน Foreign Key)

| ACCT_NO | CUST_ID | ACCT_BALANCE |
|---|---|---|
| 9000001 | 100001 | 15000.00 |
| 9000002 | 100001 | 5000.00 |
| 9000003 | 100002 | 8250.50 |

สังเกตว่า `CUST_ID` ในตาราง `ACCOUNT` คือ **Foreign Key** ที่ชี้กลับไปยัง `CUST_ID` (Primary
Key) ของตาราง `CUSTOMER` — ความสัมพันธ์นี้ทำให้ลูกค้าคนหนึ่ง (`100001`) มีได้หลายบัญชี
(`9000001`, `9000002`) โดยไม่ต้องเก็บชื่อลูกค้าซ้ำในตาราง `ACCOUNT` เลย นี่คือหลักการพื้นฐานที่
เรียกว่า **Normalization** (การจัดรูปแบบข้อมูลให้ไม่ซ้ำซ้อน)

### ทำไมจึงเรียกว่า "เชิงสัมพันธ์" (Relational)

คำว่า "Relational" ไม่ได้หมายถึง "ความสัมพันธ์ระหว่างตาราง" อย่างที่หลายคนเข้าใจผิดในตอนแรก
แต่มาจากทฤษฎีคณิตศาสตร์ **Relation** ของ E.F. Codd (นักวิจัยของ IBM ที่ตีพิมพ์ทฤษฎีนี้ในปี 1970)
ซึ่งนิยาม "ตาราง" ในเชิงคณิตศาสตร์ว่าเป็น Relation (ความสัมพันธ์ในความหมายทาง Set Theory)
ระหว่างค่าต่าง ๆ ในแต่ละคอลัมน์ — DB2 เป็นหนึ่งในฐานข้อมูลเชิงสัมพันธ์เชิงพาณิชย์รุ่นแรก ๆ ของโลก
ที่นำทฤษฎีนี้ของ IBM เองมาสร้างเป็นผลิตภัณฑ์จริง

### ข้อควรระวัง

- อย่าสับสนระหว่าง "ตาราง" ในฐานข้อมูล กับ "ตาราง (Table)" ที่ COBOL ใช้เรียก array/`OCCURS`
  (Part 016-018) — เป็นคำเดียวกันแต่คนละความหมายกันโดยสิ้นเชิง ในบริบทนี้ (SQL/ฐานข้อมูล)
  "ตาราง" หมายถึงชุดข้อมูลแบบแถว-คอลัมน์เสมอ
- Foreign Key เป็นเพียง **แนวคิดเชิงตรรกะ** ที่ฐานข้อมูลช่วยบังคับใช้ (referential integrity)
  แต่ไม่ได้ "เชื่อม" ข้อมูลทางกายภาพเหมือนการฝังตัวชี้ (pointer) แบบโครงสร้างข้อมูลในโปรแกรมทั่วไป

### แบบฝึกหัดที่ 561.1

**โจทย์**: จากตาราง CUSTOMER และ ACCOUNT ข้างต้น จงอธิบายว่าทำไมการเก็บ `CUST_NAME` ซ้ำในตาราง
`ACCOUNT` ทุกแถว (แทนที่จะใช้ `CUST_ID` เป็น Foreign Key) จึงเป็นการออกแบบที่ไม่ดี

**เฉลย**: หากเก็บ `CUST_NAME` ซ้ำในทุกแถวของ `ACCOUNT` เมื่อลูกค้าเปลี่ยนชื่อ (เช่นแต่งงานแล้ว
เปลี่ยนนามสกุล) จะต้องอัปเดตทุกแถวในตาราง `ACCOUNT` ที่มีบัญชีของลูกค้าคนนั้น หากอัปเดตไม่ครบทุก
แถว (เช่นลืมอัปเดตบางบัญชี) จะเกิดข้อมูลไม่สอดคล้องกัน (data inconsistency) ในขณะที่การใช้
`CUST_ID` เป็น Foreign Key ทำให้ชื่อลูกค้าถูกเก็บไว้ที่เดียว (ตาราง CUSTOMER) แก้ไขครั้งเดียวมีผล
ทุกบัญชีทันที

## ขั้นตอนที่ 562: DB2 คืออะไร และ DB2 Catalog

### DB2 คืออะไร

**DB2 (Database 2)** คือระบบจัดการฐานข้อมูลเชิงสัมพันธ์ (RDBMS - Relational Database
Management System) ของ IBM เปิดตัวครั้งแรกในปี 1983 บน Mainframe (ปัจจุบันมีหลายเวอร์ชันสำหรับ
หลายแพลตฟอร์ม เช่น DB2 for z/OS, DB2 for LUW - Linux/Unix/Windows) ในบริบทของหลักสูตรนี้ (เฟส 4
Mainframe/Enterprise) เราหมายถึง **DB2 for z/OS** ซึ่งเป็นฐานข้อมูลหลักที่องค์กรธนาคารและประกันภัย
ทั่วโลกใช้คู่กับโปรแกรม COBOL

### ความสัมพันธ์ระหว่าง DB2 กับ VSAM

ข้อเท็จจริงที่น่าสนใจคือ **DB2 for z/OS ใช้ VSAM (ที่เรียนไปใน Part 055-056) เป็นชั้นจัดเก็บ
ข้อมูลทางกายภาพเบื้องหลัง** — เมื่อสร้างตาราง DB2 ระบบจะสร้าง VSAM Linear Data Set (LDS ซึ่งเป็น
VSAM ประเภทพิเศษที่ไม่ได้กล่าวถึงในเนื้อหา Part 055 เพราะไม่ได้ออกแบบมาให้โปรแกรม COBOL เข้าถึง
โดยตรง) เพื่อเก็บข้อมูลจริง พูดง่าย ๆ คือ **DB2 คือชั้นซอฟต์แวร์ที่ "ห่อหุ้ม" VSAM ไว้อีกที**
เพื่อให้เราใช้ภาษา SQL แทนการเขียนโปรแกรมควบคุม record เองแบบที่ VSAM ทำ

### DB2 Catalog คืออะไร

**DB2 Catalog** คือชุดตารางพิเศษที่ DB2 ใช้เก็บ **ข้อมูลเกี่ยวกับข้อมูล (metadata)** ของฐานข้อมูล
เอง เช่น มีตารางอะไรบ้าง แต่ละตารางมีคอลัมน์อะไร ใครมีสิทธิ์เข้าถึงตารางใด — เปรียบได้กับ VSAM
Catalog (Part 055 ขั้นตอนที่ 548) ที่เก็บ metadata ของ Cluster ต่าง ๆ แต่ DB2 Catalog มีรายละเอียด
มากกว่ามากเพราะต้องรองรับแนวคิดเชิงสัมพันธ์ที่ซับซ้อนกว่า VSAM ล้วน ๆ

### ตารางสำคัญใน DB2 Catalog (Schema `SYSIBM`)

| ตาราง | เก็บข้อมูลเกี่ยวกับ |
|---|---|
| `SYSIBM.SYSTABLES` | รายชื่อตารางทั้งหมดในระบบ พร้อมเจ้าของ (creator) และ schema |
| `SYSIBM.SYSCOLUMNS` | รายชื่อคอลัมน์ของแต่ละตาราง พร้อม data type และลำดับ |
| `SYSIBM.SYSINDEXES` | รายชื่อ index ที่สร้างไว้บนตารางต่าง ๆ |
| `SYSIBM.SYSTABAUTH` | สิทธิ์การเข้าถึงตาราง (SELECT/INSERT/UPDATE/DELETE) ของแต่ละ userid |

### ตัวอย่างการ Query DB2 Catalog เพื่อดูรายชื่อคอลัมน์ของตาราง (ไวยากรณ์อ้างอิง)

```sql
SELECT COLNAME, COLTYPE, LENGTH
FROM SYSIBM.SYSCOLUMNS
WHERE TBNAME = 'CUSTOMER'
ORDER BY COLNO;
```

คำสั่งนี้ใช้แนวคิดเดียวกับที่จะสอนในขั้นตอนที่ 564 (`SELECT`) เพียงแต่ Query ไปยังตารางระบบแทน
ตารางข้อมูลธุรกิจปกติ — เป็นเทคนิคที่ DBA (Database Administrator) ใช้บ่อยมากเพื่อตรวจสอบโครงสร้าง
ฐานข้อมูลโดยไม่ต้องเปิดเอกสารภายนอก

### ข้อควรระวัง

- DB2 Catalog เป็น**ตารางระบบที่สำคัญมาก** ผู้ใช้ทั่วไปมักมีสิทธิ์แค่ `SELECT` (อ่าน) เท่านั้น
  ไม่มีสิทธิ์แก้ไขโดยตรง เพราะการแก้ไข Catalog ผิดพลาดอาจทำให้ฐานข้อมูลทั้งระบบเสียหาย
- **ไวยากรณ์ SQL ในขั้นตอนนี้และตลอด Part นี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงกับ
  DB2 หรือฐานข้อมูลใด ๆ ในสภาพแวดล้อมของหลักสูตรนี้**

### แบบฝึกหัดที่ 562.1

**โจทย์**: จงอธิบายว่าทำไม DB2 for z/OS จึงเลือกใช้ VSAM เป็นชั้นจัดเก็บข้อมูลเบื้องหลัง แทนที่จะ
สร้างระบบจัดเก็บข้อมูลของตัวเองขึ้นมาใหม่ทั้งหมด

**เฉลย**: เพราะ VSAM เป็นเทคโนโลยีที่ผ่านการพิสูจน์แล้วว่ามีประสิทธิภาพและความเสถียรสูงบน z/OS
มาอย่างยาวนาน (ตั้งแต่ทศวรรษ 1970) การสร้างระบบจัดเก็บข้อมูลใหม่ทั้งหมดจะเสียเวลาพัฒนามหาศาลและ
เสี่ยงต่อบั๊กที่ยังไม่เคยพบ การนำ VSAM ที่มีอยู่แล้วมาใช้เป็นฐาน ทำให้ IBM มุ่งพัฒนาเฉพาะชั้น SQL
Engine (การแปลคำสั่ง SQL เป็นการเข้าถึงข้อมูลจริง) ซึ่งเป็นจุดที่ DB2 สร้างมูลค่าเพิ่มที่แท้จริง
ได้เร็วกว่ามาก

## ขั้นตอนที่ 563: CREATE TABLE — การนิยามโครงสร้างตารางด้วย DDL

### DDL คืออะไร

คำสั่ง SQL แบ่งออกเป็นหลายกลุ่ม กลุ่มแรกที่ต้องรู้จักคือ **DDL (Data Definition Language)** —
คำสั่งที่ใช้ **นิยามโครงสร้าง** ของฐานข้อมูล (สร้าง/แก้ไข/ลบตาราง) ตรงข้ามกับ **DML (Data
Manipulation Language)** ที่ใช้ **จัดการข้อมูล** ภายในตาราง (เพิ่ม/แก้ไข/ลบ/ค้นหาแถว) ที่จะสอน
ในขั้นตอนที่ 564-566

### ไวยากรณ์ CREATE TABLE พื้นฐาน (มาตรฐาน SQL)

```sql
CREATE TABLE CUSTOMER (
    CUST_ID       CHAR(6)        NOT NULL,
    CUST_NAME     VARCHAR(20)    NOT NULL,
    CUST_CITY     VARCHAR(15),
    CUST_BALANCE  DECIMAL(9,2)   NOT NULL DEFAULT 0.00,
    PRIMARY KEY (CUST_ID)
);
```

### อธิบายจุดสำคัญ

- `CHAR(6)`: ชนิดข้อมูลข้อความความยาวคงที่ 6 ตัวอักษร (เติมช่องว่างให้เต็มเสมอ) — เทียบเท่า
  `PIC X(6)` ใน COBOL
- `VARCHAR(20)`: ชนิดข้อมูลข้อความความยาว**ไม่คงที่** สูงสุด 20 ตัวอักษร (เก็บเฉพาะความยาวจริง
  บวกกับ length prefix) — ไม่มีเทียบเท่าตรงตัวใน COBOL fixed-format แบบดั้งเดิม เพราะ COBOL
  ทุก field มีความกว้างคงที่เสมอ (ความแตกต่างนี้สำคัญมากและจะกล่าวถึงอีกครั้งในขั้นตอนที่ 569)
- `DECIMAL(9,2)`: ชนิดข้อมูลตัวเลขทศนิยม 9 หลักรวม โดย 2 หลักหลังจุดทศนิยม — **เทียบเท่า
  `PIC 9(7)V99` ใน COBOL โดยตรง** เพราะทั้งคู่ใช้หลักการ Fixed-Point Decimal เหมือนกันทุกประการ
  (ตามที่ Part 001 ขั้นตอนที่ 5 อธิบายไว้ว่าทำไม COBOL เก่งเรื่อง Decimal Arithmetic)
- `NOT NULL`: บังคับว่าคอลัมน์นี้ต้องมีค่าเสมอ ห้ามเป็นค่าว่าง (`NULL`)
- `DEFAULT 0.00`: กำหนดค่าเริ่มต้นถ้าไม่ระบุค่าตอน INSERT
- `PRIMARY KEY (CUST_ID)`: กำหนดว่า `CUST_ID` เป็น Primary Key ของตารางนี้ (ค่าต้องไม่ซ้ำกัน
  และห้ามเป็น NULL โดยอัตโนมัติ)

### ไวยากรณ์ CREATE TABLE พร้อม Foreign Key

```sql
CREATE TABLE ACCOUNT (
    ACCT_NO       CHAR(7)        NOT NULL,
    CUST_ID       CHAR(6)        NOT NULL,
    ACCT_BALANCE  DECIMAL(9,2)   NOT NULL DEFAULT 0.00,
    PRIMARY KEY (ACCT_NO),
    FOREIGN KEY (CUST_ID) REFERENCES CUSTOMER (CUST_ID)
);
```

`FOREIGN KEY (CUST_ID) REFERENCES CUSTOMER (CUST_ID)` บังคับว่าค่า `CUST_ID` ในตาราง `ACCOUNT`
ทุกแถวต้องมีอยู่จริงในตาราง `CUSTOMER` แล้วเท่านั้น (Referential Integrity) — ถ้าพยายาม INSERT
บัญชีที่อ้างถึงลูกค้าที่ไม่มีอยู่จริง ฐานข้อมูลจะปฏิเสธคำสั่งนั้นทันทีโดยอัตโนมัติ

### แนวคิด NULL — สิ่งที่ COBOL ไม่มี

**NULL** ในฐานข้อมูลเชิงสัมพันธ์หมายถึง **"ไม่มีค่า" หรือ "ไม่ทราบค่า"** ซึ่งเป็นแนวคิดที่**COBOL
fixed-format ไม่มีโดยธรรมชาติ** เพราะทุก field ใน COBOL ต้องมีค่าใดค่าหนึ่งเสมอ (แม้จะเป็นค่า
ว่าง/ศูนย์ ก็ยังถือว่า "มีค่า" อยู่) ความแตกต่างนี้เป็นจุดที่ต้องระวังมากเมื่อเชื่อมต่อ COBOL กับ
DB2 ในภายหลัง (Part 058 จะสอนเรื่อง **Indicator Variable** ที่ใช้แก้ปัญหานี้โดยเฉพาะ)

### ข้อควรระวัง

- **คำสั่ง CREATE TABLE ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงในสภาพแวดล้อมของ
  หลักสูตรนี้**
- ชนิดข้อมูล SQL แตกต่างกันเล็กน้อยระหว่าง DB2 กับฐานข้อมูลอื่น (เช่น PostgreSQL ใช้
  `VARCHAR` เหมือนกันแต่บางชนิดข้อมูลมีชื่อต่างกัน) ไวยากรณ์ในเอกสารนี้อ้างอิงมาตรฐาน SQL
  ทั่วไปที่ DB2 รองรับ แต่ควรตรวจสอบเอกสารเฉพาะเมื่อทำงานกับฐานข้อมูลจริง

### แบบฝึกหัดที่ 563.1

**โจทย์**: จงเขียน `CREATE TABLE` สำหรับตาราง `TRANSACTION` ที่มีคอลัมน์ `TXN_ID` (CHAR 10,
Primary Key), `ACCT_NO` (CHAR 7, Foreign Key อ้างอิงตาราง ACCOUNT), `TXN_TYPE` (VARCHAR 10),
และ `TXN_AMOUNT` (DECIMAL 9,2)

**เฉลย**:

```sql
CREATE TABLE TRANSACTION (
    TXN_ID        CHAR(10)       NOT NULL,
    ACCT_NO       CHAR(7)        NOT NULL,
    TXN_TYPE      VARCHAR(10)    NOT NULL,
    TXN_AMOUNT    DECIMAL(9,2)   NOT NULL,
    PRIMARY KEY (TXN_ID),
    FOREIGN KEY (ACCT_NO) REFERENCES ACCOUNT (ACCT_NO)
);
```

## ขั้นตอนที่ 564: SELECT Statement — การค้นหาข้อมูล

### DML และ SELECT

**SELECT** คือคำสั่ง DML ที่ใช้บ่อยที่สุดในภาษา SQL — ใช้**ค้นหาและดึงข้อมูล**จากตารางตาม
เงื่อนไขที่ต้องการ โดยไม่แก้ไขข้อมูลใด ๆ ในตาราง เทียบเท่ากับการ `READ` ไฟล์ COBOL แต่มีพลังในการ
กรอง/เรียงลำดับ/จัดกลุ่มข้อมูลมากกว่ามาก

### ไวยากรณ์พื้นฐาน

```sql
SELECT CUST_ID, CUST_NAME, CUST_BALANCE
FROM CUSTOMER
WHERE CUST_CITY = 'BANGKOK'
ORDER BY CUST_BALANCE DESC;
```

### อธิบายทีละส่วน

- `SELECT CUST_ID, CUST_NAME, CUST_BALANCE`: ระบุว่าต้องการเฉพาะคอลัมน์เหล่านี้ (ใช้ `*` แทน
  ถ้าต้องการทุกคอลัมน์ แต่ในทางปฏิบัติควรระบุคอลัมน์ที่ต้องการเสมอเพื่อประสิทธิภาพและความชัดเจน)
- `FROM CUSTOMER`: ระบุตารางต้นทาง
- `WHERE CUST_CITY = 'BANGKOK'`: กรองเฉพาะแถวที่ตรงเงื่อนไข (เทียบเท่า `IF` ใน COBOL ที่ใช้
  กรองก่อน DISPLAY แต่ SQL ทำการกรองที่ฐานข้อมูลก่อนส่งผลลัพธ์กลับมา ไม่ใช่ที่โปรแกรม)
- `ORDER BY CUST_BALANCE DESC`: เรียงผลลัพธ์ตามยอดเงินจากมากไปน้อย (`DESC` = descending,
  `ASC` = ascending ซึ่งเป็นค่าเริ่มต้นถ้าไม่ระบุ)

### ผลลัพธ์ที่คาดว่าจะได้ (อ้างอิงจากข้อมูลตัวอย่างในขั้นตอนที่ 561)

| CUST_ID | CUST_NAME | CUST_BALANCE |
|---|---|---|
| 100003 | PRASERT KAEWTA | (ยอดคงเหลือของ 100003) |
| 100001 | SOMCHAI JAIDEE | (ยอดคงเหลือของ 100001) |

(เฉพาะลูกค้าที่ `CUST_CITY = 'BANGKOK'` เท่านั้น ตัด `100002` ที่อยู่ CHIANG MAI ออกไป)

### เปรียบเทียบ SELECT กับ COBOL READ + IF

```cobol
      *> Equivalent COBOL logic to the SQL SELECT above
           PERFORM UNTIL END-OF-FILE
               READ CUSTOMER-FILE
                   AT END
                       SET END-OF-FILE TO TRUE
                   NOT AT END
                       IF CUST-CITY = "BANGKOK"
                           DISPLAY CUST-ID " " CUST-NAME " "
                               CUST-BALANCE
                       END-IF
               END-READ
           END-PERFORM.
```

สังเกตว่า COBOL ต้องเขียน loop และ `IF` ด้วยตัวเอง ในขณะที่ SQL เพียงประโยคเดียว (`WHERE`)
สื่อความหมายเดียวกันได้ครบถ้วน — นี่คือความแตกต่างพื้นฐานระหว่างแนวทาง **Procedural** (บอกวิธีทำ
ทีละขั้นตอน) กับ **Declarative** (บอกสิ่งที่ต้องการ แล้วให้ระบบตัดสินใจวิธีทำเอง) ที่ SQL ยึดถือ

### ข้อควรระวัง

- **คำสั่ง SELECT ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงกับฐานข้อมูลใด ๆ ใน
  สภาพแวดล้อมของหลักสูตรนี้** ผลลัพธ์ที่แสดงเป็นผลลัพธ์ที่**คาดว่าจะได้**ตามหลักการทำงานของ SQL
  มาตรฐานเท่านั้น
- ค่าข้อความ (string) ใน SQL ต้องครอบด้วยเครื่องหมายคำพูดเดี่ยว (`'...'`) เสมอ **ไม่ใช่**
  เครื่องหมายคำพูดคู่ (`"..."`) แบบที่ COBOL string literal ใช้ — เป็นจุดสับสนที่พบบ่อยมากเมื่อ
  สลับไปมาระหว่างสองภาษา

### แบบฝึกหัดที่ 564.1

**โจทย์**: จงเขียน SQL `SELECT` ที่ค้นหาบัญชีทั้งหมดในตาราง `ACCOUNT` ที่มียอดคงเหลือ
(`ACCT_BALANCE`) มากกว่า 10000 เรียงจากน้อยไปมาก

**เฉลย**:

```sql
SELECT ACCT_NO, CUST_ID, ACCT_BALANCE
FROM ACCOUNT
WHERE ACCT_BALANCE > 10000
ORDER BY ACCT_BALANCE ASC;
```

## ขั้นตอนที่ 565: INSERT, UPDATE, DELETE — การจัดการข้อมูล

### INSERT — เพิ่มแถวใหม่

```sql
INSERT INTO CUSTOMER (CUST_ID, CUST_NAME, CUST_CITY, CUST_BALANCE)
VALUES ('100004', 'WANNA SRISUK', 'PHUKET', 3000.00);
```

เทียบเท่ากับ `WRITE` ใน COBOL (Part 025) — เพิ่ม record ใหม่เข้าไปในไฟล์/ตาราง

### UPDATE — แก้ไขแถวที่มีอยู่

```sql
UPDATE CUSTOMER
SET CUST_BALANCE = CUST_BALANCE + 1000.00
WHERE CUST_ID = '100001';
```

เทียบเท่ากับ `REWRITE` ใน COBOL (Part 025) — แต่สังเกตว่า **UPDATE ไม่ต้อง "อ่านมาก่อน" เหมือน
`REWRITE` ที่ต้อง `READ` แล้วค่อย `REWRITE`** SQL สามารถ "แก้ไขและค้นหา" ในคำสั่งเดียวได้เลย
(ฐานข้อมูลจัดการหาแถวที่ตรงเงื่อนไขและแก้ไขให้ในขั้นตอนเดียวกัน)

### DELETE — ลบแถว

```sql
DELETE FROM CUSTOMER
WHERE CUST_ID = '100004';
```

เทียบเท่ากับ `DELETE` ใน COBOL Indexed File (Part 028 ขั้นตอนที่ 277) — และเช่นเดียวกับ
`UPDATE` คือไม่ต้อง `READ` มาก่อน สามารถลบตามเงื่อนไขได้โดยตรง

### ตารางสรุปเทียบ SQL DML กับ COBOL I/O Verbs

| SQL DML | ความหมาย | เทียบเท่า COBOL |
|---|---|---|
| `SELECT` | ค้นหา/อ่านข้อมูล | `READ` |
| `INSERT` | เพิ่มแถวใหม่ | `WRITE` |
| `UPDATE` | แก้ไขแถวที่มีอยู่ | `REWRITE` (แต่ไม่ต้อง READ มาก่อน) |
| `DELETE` | ลบแถว | `DELETE` (แต่ไม่ต้อง READ มาก่อน) |

### ข้อควรระวัง

- **คำสั่ง INSERT/UPDATE/DELETE ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงในสภาพ
  แวดล้อมของหลักสูตรนี้**
- **อันตรายที่สุดของ UPDATE/DELETE คือการลืมเขียน `WHERE`** — ถ้าเขียน
  `UPDATE CUSTOMER SET CUST_BALANCE = 0;` โดยไม่มี `WHERE` จะเป็นการ**แก้ไขทุกแถวในตารางทั้งหมด**
  ทันที (เทียบเท่าหายนะระดับเดียวกับการลืมเงื่อนไขหยุดใน `PERFORM UNTIL` ที่วนลูปไม่รู้จบ) ควร
  ทดสอบด้วย `SELECT` ที่มี `WHERE` เดียวกันก่อนเสมอ เพื่อยืนยันว่าเงื่อนไขกรองแถวที่ต้องการจริง
  ก่อนเปลี่ยนเป็น UPDATE/DELETE

### แบบฝึกหัดที่ 565.1

**โจทย์**: จงเขียน SQL ที่เพิ่มธุรกรรมใหม่ในตาราง `TRANSACTION` (จากแบบฝึกหัดที่ 563.1) แล้วปรับ
ยอดคงเหลือของบัญชีที่เกี่ยวข้องในตาราง `ACCOUNT` ให้ถูกต้องตามธุรกรรมนั้น (สมมติเป็นการฝากเงิน
1500.00 บาท เข้าบัญชี `9000001`)

**เฉลย**:

```sql
INSERT INTO TRANSACTION (TXN_ID, ACCT_NO, TXN_TYPE, TXN_AMOUNT)
VALUES ('TXN0000001', '9000001', 'DEPOSIT', 1500.00);

UPDATE ACCOUNT
SET ACCT_BALANCE = ACCT_BALANCE + 1500.00
WHERE ACCT_NO = '9000001';
```

สังเกตว่าต้องเขียน 2 คำสั่งแยกกัน (บันทึกธุรกรรม + ปรับยอดบัญชี) เพราะเป็นการเปลี่ยนแปลงข้อมูล
ใน 2 ตารางที่ต่างกัน — แนวคิดที่ว่าทั้งสองคำสั่งนี้ต้อง "สำเร็จพร้อมกันหรือไม่สำเร็จเลยทั้งคู่"
เรียกว่า **Transaction** ซึ่งจะกล่าวถึงรายละเอียดเพิ่มเติมใน Part 058-059

## ขั้นตอนที่ 566: WHERE Clause ขั้นสูง — Operators และ Predicates

### Comparison Operators

| Operator | ความหมาย |
|---|---|
| `=` | เท่ากับ |
| `<>` หรือ `!=` | ไม่เท่ากับ |
| `>`, `>=`, `<`, `<=` | มากกว่า/มากกว่าเท่ากับ/น้อยกว่า/น้อยกว่าเท่ากับ |
| `BETWEEN a AND b` | อยู่ในช่วง a ถึง b (รวมค่าขอบทั้งสองด้าน) |
| `IN (a, b, c)` | ตรงกับค่าใดค่าหนึ่งในรายการ |
| `LIKE 'pattern'` | ตรงกับรูปแบบข้อความ (ใช้ `%` แทนตัวอักษรกี่ตัวก็ได้ และ `_` แทน 1 ตัวอักษร) |
| `IS NULL` / `IS NOT NULL` | ตรวจสอบว่าเป็นค่า NULL หรือไม่ (ต้องใช้ `IS`, **ห้ามใช้ `= NULL`**) |

### ตัวอย่างการใช้ BETWEEN

```sql
SELECT ACCT_NO, ACCT_BALANCE
FROM ACCOUNT
WHERE ACCT_BALANCE BETWEEN 5000.00 AND 20000.00;
```

### ตัวอย่างการใช้ IN

```sql
SELECT CUST_ID, CUST_NAME
FROM CUSTOMER
WHERE CUST_CITY IN ('BANGKOK', 'CHIANG MAI');
```

เทียบเท่ากับการเขียน `WHERE CUST_CITY = 'BANGKOK' OR CUST_CITY = 'CHIANG MAI'` แต่กระชับกว่ามาก
เมื่อมีค่าให้เปรียบเทียบหลายค่า

### ตัวอย่างการใช้ LIKE

```sql
SELECT CUST_ID, CUST_NAME
FROM CUSTOMER
WHERE CUST_NAME LIKE 'S%';
```

ค้นหาลูกค้าที่ชื่อขึ้นต้นด้วยตัวอักษร `S` (เช่น `SOMCHAI`, `SUDA`) — `%` แทนตัวอักษรกี่ตัวก็ได้
รวมถึงไม่มีตัวอักษรเลยก็ได้ ในขณะที่ `_` แทนตัวอักษรพอดี 1 ตัวเท่านั้น (เช่น `S_DA` จะตรงกับ
`SUDA` แต่ไม่ตรงกับ `SUUDA`)

### ตัวอย่างการใช้ IS NULL

```sql
SELECT CUST_ID, CUST_NAME
FROM CUSTOMER
WHERE CUST_CITY IS NULL;
```

ค้นหาลูกค้าที่ยังไม่มีการระบุเมือง (`CUST_CITY` เป็น NULL) — สำคัญมากที่ต้องใช้ `IS NULL` แทน
`= NULL` เพราะในตรรกะของ SQL ค่า NULL หมายถึง "ไม่ทราบค่า" การเปรียบเทียบ `NULL = NULL` จะได้
ผลลัพธ์เป็น "ไม่ทราบ" (UNKNOWN) เสมอ ไม่ใช่ TRUE

### การรวมหลายเงื่อนไขด้วย AND/OR

```sql
SELECT CUST_ID, CUST_NAME, CUST_BALANCE
FROM CUSTOMER
WHERE CUST_CITY = 'BANGKOK'
  AND CUST_BALANCE > 10000.00;
```

### ข้อควรระวัง

- **ทุกตัวอย่าง SQL ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงในสภาพแวดล้อมของ
  หลักสูตรนี้**
- `NULL` เป็นกับดักที่พบบ่อยที่สุดของมือใหม่ SQL — จำไว้เสมอว่าต้องใช้ `IS NULL`/`IS NOT NULL`
  เท่านั้น การเขียน `WHERE CUST_CITY = NULL` จะไม่ error แต่จะได้ผลลัพธ์เป็น**ไม่มีแถวใดตรงเลย**
  เสมอ (Silent Bug ที่ตรวจจับยากมาก คล้ายกับที่ Part 047 เตือนเรื่อง `FUNCTION FORMATTED-DATE`
  ที่คืนค่าว่างเปล่าอย่างเงียบ ๆ)

### แบบฝึกหัดที่ 566.1

**โจทย์**: จงเขียน SQL ค้นหาลูกค้าที่ชื่อ (`CUST_NAME`) มีคำว่า `MEECHAI` อยู่ตรงไหนก็ได้ในชื่อ

**เฉลย**:

```sql
SELECT CUST_ID, CUST_NAME
FROM CUSTOMER
WHERE CUST_NAME LIKE '%MEECHAI%';
```

การใช้ `%` ทั้งด้านหน้าและด้านหลังคำที่ค้นหา ทำให้ตรงกับข้อความที่มีคำนั้นอยู่ตรงไหนก็ได้ในสตริง
ทั้งหมด ไม่จำกัดว่าต้องขึ้นต้นหรือลงท้ายด้วยคำนั้น

## ขั้นตอนที่ 567: JOIN — การเชื่อมโยงหลายตาราง

### ปัญหาที่ JOIN แก้ไข

จากตาราง `CUSTOMER` และ `ACCOUNT` ในขั้นตอนที่ 561 สมมติต้องการรายงาน "ชื่อลูกค้าพร้อมยอดเงินใน
แต่ละบัญชี" — ข้อมูลชื่ออยู่ในตาราง `CUSTOMER` แต่ข้อมูลยอดเงินอยู่ในตาราง `ACCOUNT` คนละตาราง
กัน **JOIN** คือกลไกของ SQL ที่ใช้**เชื่อมโยงแถวจากหลายตารางเข้าด้วยกัน**ตามเงื่อนไขที่กำหนด
(โดยทั่วไปคือ Primary Key ของตารางหนึ่งตรงกับ Foreign Key ของอีกตาราง)

### INNER JOIN — เชื่อมเฉพาะแถวที่ตรงกันทั้งสองฝั่ง

```sql
SELECT C.CUST_NAME, A.ACCT_NO, A.ACCT_BALANCE
FROM CUSTOMER C
INNER JOIN ACCOUNT A
    ON C.CUST_ID = A.CUST_ID
WHERE C.CUST_CITY = 'BANGKOK';
```

### อธิบายจุดสำคัญ

- `CUSTOMER C` และ `ACCOUNT A`: การตั้งชื่อย่อ (**Alias**) ให้ตาราง เพื่อให้เขียนโค้ดสั้นลงและ
  ชัดเจนขึ้นเมื่อต้องอ้างอิงคอลัมน์จากหลายตารางที่อาจมีชื่อคอลัมน์ซ้ำกัน
- `ON C.CUST_ID = A.CUST_ID`: เงื่อนไขการเชื่อมโยง — บอกว่าแถวจากสองตารางจะ "จับคู่" กันเมื่อ
  `CUST_ID` ตรงกัน (Primary Key ของ CUSTOMER ตรงกับ Foreign Key ของ ACCOUNT)
- `INNER JOIN`: จะแสดงเฉพาะแถวที่**มีคู่ตรงกันทั้งสองฝั่งเท่านั้น** — ถ้าลูกค้าคนใดยังไม่มีบัญชี
  เลย (ไม่มีแถวใน ACCOUNT ที่ตรงกับ CUST_ID นั้น) ลูกค้าคนนั้นจะ**ไม่ปรากฏในผลลัพธ์**เลย

### LEFT OUTER JOIN — เชื่อมพร้อมเก็บแถวฝั่งซ้ายไว้ทั้งหมด

```sql
SELECT C.CUST_NAME, A.ACCT_NO, A.ACCT_BALANCE
FROM CUSTOMER C
LEFT OUTER JOIN ACCOUNT A
    ON C.CUST_ID = A.CUST_ID;
```

`LEFT OUTER JOIN` จะแสดง**ลูกค้าทุกคน**แม้จะไม่มีบัญชีเลยก็ตาม (ตารางฝั่งซ้ายคือ `CUSTOMER` ที่
ถูกระบุใน `FROM`) โดยคอลัมน์จากตาราง `ACCOUNT` (ฝั่งขวา) จะแสดงเป็น `NULL` สำหรับลูกค้าที่ไม่มี
บัญชี — มีประโยชน์มากเมื่อต้องการรายงานที่ครอบคลุมทุกแถวของตารางหลัก ไม่ว่าจะมีข้อมูลที่เชื่อมโยง
อยู่หรือไม่

### เชื่อมโยงกับความรู้เดิม: JOIN คือ Master-Detail Processing แบบ Declarative

Part 026 สอน **Master-Detail Processing** ซึ่งเป็นเทคนิค COBOL ที่เขียนโปรแกรมไล่อ่าน 2 ไฟล์
พร้อมกัน (ที่เรียงลำดับ Key ตรงกัน) แล้วจับคู่ record ที่ Key ตรงกันด้วยตนเองทีละขั้นตอน — **JOIN
คือแนวคิดเดียวกันทุกประการ** เพียงแต่ SQL Engine จัดการการจับคู่ให้อัตโนมัติทั้งหมดโดยไม่ต้อง
เขียนโค้ดควบคุม loop หรือเปรียบเทียบ Key เองแม้แต่บรรทัดเดียว — นี่คือตัวอย่างที่ชัดเจนที่สุดของ
การเปลี่ยนจากแนวทาง Procedural (Part 026) ไปสู่แนวทาง Declarative (SQL)

### ข้อควรระวัง

- **ทุกตัวอย่าง SQL ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงในสภาพแวดล้อมของ
  หลักสูตรนี้**
- การลืมเขียน `ON` (เงื่อนไขการเชื่อมโยง) หรือเขียนผิดเงื่อนไข อาจทำให้เกิด **Cartesian
  Product** (จับคู่ทุกแถวของตารางหนึ่งกับทุกแถวของอีกตารางโดยไม่มีเงื่อนไขกรอง) ซึ่งทำให้ได้
  ผลลัพธ์จำนวนมหาศาลที่ไม่มีความหมายทางธุรกิจใด ๆ (ถ้าตารางหนึ่งมี 1,000 แถวและอีกตารางมี 1,000
  แถว Cartesian Product จะได้ผลลัพธ์ถึง 1,000,000 แถว)

### แบบฝึกหัดที่ 567.1

**โจทย์**: จงเขียน SQL ที่แสดงชื่อลูกค้าทุกคนพร้อมยอดรวมทุกบัญชี (ใช้ `INNER JOIN` เพียงอย่างเดียว
ก่อน ยังไม่ต้องรวมยอด — การรวมยอดจะสอนในขั้นตอนที่ 568)

**เฉลย**:

```sql
SELECT C.CUST_NAME, A.ACCT_NO, A.ACCT_BALANCE
FROM CUSTOMER C
INNER JOIN ACCOUNT A
    ON C.CUST_ID = A.CUST_ID
ORDER BY C.CUST_NAME;
```

## ขั้นตอนที่ 568: Aggregate Functions และ GROUP BY

### Aggregate Functions คืออะไร

**Aggregate Function** คือฟังก์ชันที่**คำนวณค่าสรุปจากหลายแถว**ให้เหลือเพียงค่าเดียว (หรือค่าเดียว
ต่อกลุ่ม) เทียบเท่ากับสิ่งที่ Part 039 สอนผ่าน **Control Break** (การคำนวณผลรวมย่อยเมื่อค่าของ
field ควบคุมเปลี่ยน) แต่ SQL ทำสิ่งนี้ได้ในประโยคเดียวโดยไม่ต้องเขียน logic ตรวจจับการเปลี่ยนแปลง
ค่าด้วยตนเองเหมือนที่ COBOL Report Writer ทำ

### ฟังก์ชันพื้นฐานที่ใช้บ่อยที่สุด

| ฟังก์ชัน | ความหมาย |
|---|---|
| `COUNT(*)` | นับจำนวนแถว |
| `SUM(column)` | ผลรวมของคอลัมน์ตัวเลข |
| `AVG(column)` | ค่าเฉลี่ยของคอลัมน์ตัวเลข |
| `MAX(column)` | ค่าสูงสุด |
| `MIN(column)` | ค่าต่ำสุด |

### ตัวอย่าง: หายอดรวมและจำนวนบัญชีทั้งหมด

```sql
SELECT COUNT(*) AS TOTAL_ACCOUNTS, SUM(ACCT_BALANCE) AS TOTAL_BALANCE
FROM ACCOUNT;
```

`AS TOTAL_ACCOUNTS` และ `AS TOTAL_BALANCE` คือการตั้งชื่อ **Alias** ให้คอลัมน์ผลลัพธ์ เพื่อให้
อ่านผลลัพธ์เข้าใจง่ายขึ้น (แทนที่จะแสดงเป็นชื่อฟังก์ชันตรง ๆ เช่น `COUNT(*)`)

### GROUP BY — สรุปผลแยกตามกลุ่ม

การใช้ Aggregate Function เพียงอย่างเดียวจะให้ผลรวม**ทั้งตาราง**เท่านั้น ถ้าต้องการ**ผลรวมแยกตาม
กลุ่ม** (เช่น ยอดรวมบัญชีแยกตามลูกค้าแต่ละคน) ต้องใช้ **`GROUP BY`** ร่วมด้วย:

```sql
SELECT CUST_ID, COUNT(*) AS ACCT_COUNT, SUM(ACCT_BALANCE) AS TOTAL_BALANCE
FROM ACCOUNT
GROUP BY CUST_ID
ORDER BY TOTAL_BALANCE DESC;
```

### ผลลัพธ์ที่คาดว่าจะได้ (อ้างอิงจากข้อมูลตัวอย่างในขั้นตอนที่ 561)

| CUST_ID | ACCT_COUNT | TOTAL_BALANCE |
|---|---|---|
| 100001 | 2 | 20000.00 |
| 100002 | 1 | 8250.50 |

(รวมยอด 2 บัญชีของลูกค้า `100001` เป็น 15000.00 + 5000.00 = 20000.00 โดยอัตโนมัติ)

### HAVING — กรองกลุ่มหลังจาก GROUP BY

```sql
SELECT CUST_ID, SUM(ACCT_BALANCE) AS TOTAL_BALANCE
FROM ACCOUNT
GROUP BY CUST_ID
HAVING SUM(ACCT_BALANCE) > 10000.00;
```

**`HAVING`** ทำหน้าที่คล้าย `WHERE` แต่ใช้กรอง**หลังจากจัดกลุ่มและคำนวณ Aggregate Function
แล้ว** ในขณะที่ `WHERE` กรองแถวดิบ**ก่อน**จัดกลุ่ม — จุดนี้เป็นกฎสำคัญที่ต้องจำ: **`WHERE` ใช้
`SUM(...)` ไม่ได้ ต้องใช้ `HAVING` เท่านั้น** เพราะตอนที่ `WHERE` ทำงาน ยังไม่มีการคำนวณผลรวมใด ๆ
เกิดขึ้นเลย

### เชื่อมโยงกับ Control Break ของ Part 039

Part 039 สอนการเขียนโปรแกรม COBOL ที่ตรวจจับเมื่อ field ควบคุม (เช่น `CUST-ID`) เปลี่ยนค่า แล้ว
พิมพ์ยอดรวมย่อยก่อนขึ้นกลุ่มใหม่ — `GROUP BY` ใน SQL ทำสิ่งเดียวกันนี้**โดยอัตโนมัติ**ทั้งหมด
ไม่ต้องเขียน flag ตรวจจับการเปลี่ยนแปลงค่า ไม่ต้องเรียงข้อมูลล่วงหน้าด้วยตนเอง (SQL Engine จัดการ
เรียงและจัดกลุ่มให้เอง) และไม่ต้องเขียนตัวแปรสะสมผลรวมเอง — เป็นตัวอย่างที่ชัดเจนอีกครั้งของพลัง
แนวทาง Declarative

### ข้อควรระวัง

- **ทุกตัวอย่าง SQL ในขั้นตอนนี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงในสภาพแวดล้อมของ
  หลักสูตรนี้**
- ทุกคอลัมน์ที่ปรากฏใน `SELECT` (ที่ไม่ใช่ Aggregate Function) **ต้องปรากฏใน `GROUP BY` ด้วย
  เสมอ** มิฉะนั้นฐานข้อมูลจะรายงาน error ทันที (กฎนี้บังคับใช้เข้มงวดในฐานข้อมูลส่วนใหญ่รวมถึง
  DB2) เพราะ SQL ไม่รู้ว่าจะเลือกค่าใดมาแสดงถ้าคอลัมน์นั้นมีหลายค่าต่างกันภายในกลุ่มเดียวกัน

### แบบฝึกหัดที่ 568.1

**โจทย์**: จงเขียน SQL ที่หาว่าเมือง (`CUST_CITY`) ใดมีลูกค้าอาศัยอยู่มากกว่า 1 คน พร้อมแสดง
จำนวนลูกค้าในแต่ละเมืองนั้น

**เฉลย**:

```sql
SELECT CUST_CITY, COUNT(*) AS CUST_COUNT
FROM CUSTOMER
GROUP BY CUST_CITY
HAVING COUNT(*) > 1;
```

## ขั้นตอนที่ 569: DB2 Data Types และการ Map กับ COBOL PICTURE Clause

### ทำไมต้องรู้เรื่องนี้ก่อนไป Part 058

Part 058 จะสอน **Embedded SQL** ซึ่งเป็นการเขียนคำสั่ง SQL ฝังอยู่ในโปรแกรม COBOL โดยตรง — ก่อน
จะไปถึงจุดนั้น จำเป็นต้องเข้าใจก่อนว่า**ชนิดข้อมูลของ DB2 แต่ละแบบควรแปลงเป็น PICTURE Clause แบบ
ใดใน COBOL** เพื่อให้โปรแกรมสามารถรับส่งข้อมูลกับฐานข้อมูลได้อย่างถูกต้อง แนวคิดของตัวแปร COBOL
ที่ใช้รับ/ส่งค่ากับ SQL เรียกว่า **Host Variable** (จะสอนละเอียดใน Part 058)

### ตารางเทียบชนิดข้อมูล DB2 กับ COBOL PICTURE Clause

| DB2 Data Type | ความหมาย | COBOL PICTURE ที่ใช้แทน |
|---|---|---|
| `CHAR(n)` | ข้อความความยาวคงที่ n ตัวอักษร | `PIC X(n)` |
| `VARCHAR(n)` | ข้อความความยาวไม่คงที่ สูงสุด n ตัวอักษร | กลุ่มข้อมูล: `PIC S9(4) COMP` (เก็บความยาวจริง) + `PIC X(n)` (เก็บข้อความ) |
| `DECIMAL(p,s)` | ตัวเลขทศนิยม p หลักรวม, s หลักทศนิยม | `PIC S9(p-s)V9(s) COMP-3` (Packed Decimal) |
| `INTEGER` | จำนวนเต็ม 4 ไบต์ | `PIC S9(9) COMP` |
| `SMALLINT` | จำนวนเต็ม 2 ไบต์ | `PIC S9(4) COMP` |
| `DATE` | วันที่ (รูปแบบภายในของ DB2 เอง) | `PIC X(10)` (รูปแบบ `YYYY-MM-DD` เมื่อแปลงเป็นข้อความ) |
| `TIME` | เวลา | `PIC X(8)` (รูปแบบ `HH.MM.SS`) |

### ทำไม VARCHAR จึงต้องใช้กลุ่มข้อมูล 2 ส่วนใน COBOL

เนื่องจาก COBOL fixed-format ไม่มีแนวคิด "ความยาวไม่คงที่" โดยธรรมชาติ (ตามที่กล่าวถึงในขั้นตอน
ที่ 563) การรับค่า `VARCHAR` จาก DB2 เข้าสู่โปรแกรม COBOL จึงต้องใช้ **กลุ่มข้อมูล 2 ส่วน**:

```cobol
       01  WS-CUST-NAME.
           05  WS-CUST-NAME-LEN     PIC S9(4) COMP.
           05  WS-CUST-NAME-TEXT    PIC X(20).
```

`WS-CUST-NAME-LEN` เก็บความยาวจริงของข้อความ (DB2 จะกรอกค่านี้ให้อัตโนมัติเมื่อดึงข้อมูลเข้ามา)
ส่วน `WS-CUST-NAME-TEXT` เก็บเนื้อหาข้อความจริง (เฉพาะความยาวเท่าที่ `WS-CUST-NAME-LEN` ระบุไว้
เท่านั้นที่มีความหมาย ส่วนที่เหลือเป็นขยะที่ไม่ควรนำไปใช้) — โครงสร้างนี้เรียกว่า **VARCHAR
Host Variable** ซึ่งจะได้ใช้งานจริงเมื่อเรียน Embedded SQL ใน Part 058

### ทำไม DECIMAL จึงแนะนำให้ใช้ COMP-3 (Packed Decimal)

`COMP-3` (Packed Decimal) เป็นรูปแบบการเก็บตัวเลขที่ประหยัดพื้นที่กว่า `DISPLAY` (การเก็บตัวเลข
แบบข้อความปกติที่เราใช้มาตลอดหลักสูตรนี้จนถึงตอนนี้) โดยเก็บตัวเลข 2 หลักต่อ 1 ไบต์ (แทนที่จะเป็น
1 หลักต่อ 1 ไบต์แบบ DISPLAY) — DB2 `DECIMAL` ใช้รูปแบบการเก็บข้อมูลภายในที่**ตรงกับ Packed
Decimal ของ COBOL พอดี** ทำให้การแปลงข้อมูลระหว่าง DB2 กับ COBOL มีประสิทธิภาพสูงสุดเมื่อประกาศ
Host Variable เป็น `COMP-3` แทน `DISPLAY` ธรรมดา

### ข้อควรระวัง

- **ตารางเทียบชนิดข้อมูลนี้เป็นข้อมูลอ้างอิงมาตรฐาน** สำหรับเตรียมความเข้าใจก่อนเข้าสู่ Part 058
  ยังไม่ได้มีการทดสอบเชื่อมต่อ COBOL กับ DB2 จริงในสภาพแวดล้อมของหลักสูตรนี้
- ความกว้างของ `PIC` ที่แปลงจาก DECIMAL ต้องคำนวณให้ถูกต้องเป๊ะ: `DECIMAL(9,2)` แปลงเป็น
  `PIC S9(7)V99` (9 หลักรวม ลบ 2 หลักทศนิยม เหลือ 7 หลักก่อนจุด) การคำนวณผิดพลาดแม้แค่ 1 หลัก
  จะทำให้ข้อมูลเสียหายทันทีเมื่อโปรแกรมรันจริง

### แบบฝึกหัดที่ 569.1

**โจทย์**: จงแปลงคอลัมน์ `ACCT_BALANCE DECIMAL(9,2)` จากตาราง ACCOUNT (ขั้นตอนที่ 563) ให้เป็น
Host Variable ของ COBOL ที่เหมาะสมที่สุด

**เฉลย**:

```cobol
       01  WS-ACCT-BALANCE      PIC S9(7)V99 COMP-3.
```

ใช้ `COMP-3` เพื่อให้ตรงกับรูปแบบ Packed Decimal ภายในของ DB2 `DECIMAL` โดยตรง ทำให้การแปลง
ข้อมูลระหว่างสองระบบมีประสิทธิภาพสูงสุดและลดโอกาสเกิดข้อผิดพลาดจากการแปลงชนิดข้อมูล

## ขั้นตอนที่ 570: กรณีศึกษารวม — ออกแบบ Schema ธนาคารพร้อม DDL และ DML ครบชุด

### โจทย์ของกรณีศึกษา

ออกแบบฐานข้อมูลธนาคารอย่างง่ายที่ครอบคลุม 3 ตารางหลัก (`CUSTOMER`, `ACCOUNT`, `TRANSACTION`)
พร้อมชุดคำสั่ง DDL (สร้างตาราง) และ DML (จัดการข้อมูล) แบบครบวงจร เพื่อเตรียมความพร้อมสำหรับ
Part 058 ที่จะนำ schema ชุดนี้ไปฝังในโปรแกรม COBOL ผ่าน Embedded SQL

### DDL: การสร้างทั้ง 3 ตาราง

```sql
CREATE TABLE CUSTOMER (
    CUST_ID       CHAR(6)        NOT NULL,
    CUST_NAME     VARCHAR(20)    NOT NULL,
    CUST_CITY     VARCHAR(15),
    PRIMARY KEY (CUST_ID)
);

CREATE TABLE ACCOUNT (
    ACCT_NO       CHAR(7)        NOT NULL,
    CUST_ID       CHAR(6)        NOT NULL,
    ACCT_TYPE     CHAR(1)        NOT NULL,
    ACCT_BALANCE  DECIMAL(9,2)   NOT NULL DEFAULT 0.00,
    PRIMARY KEY (ACCT_NO),
    FOREIGN KEY (CUST_ID) REFERENCES CUSTOMER (CUST_ID)
);

CREATE TABLE TRANSACTION (
    TXN_ID        CHAR(10)       NOT NULL,
    ACCT_NO       CHAR(7)        NOT NULL,
    TXN_TYPE      VARCHAR(10)    NOT NULL,
    TXN_AMOUNT    DECIMAL(9,2)   NOT NULL,
    PRIMARY KEY (TXN_ID),
    FOREIGN KEY (ACCT_NO) REFERENCES ACCOUNT (ACCT_NO)
);
```

`ACCT_TYPE CHAR(1)` เป็นคอลัมน์ใหม่ที่ยังไม่เคยกล่าวถึง ใช้เก็บรหัสประเภทบัญชีแบบย่อ เช่น `S`
(Savings - ออมทรัพย์) หรือ `C` (Checking - กระแสรายวัน) — เป็นเทคนิคที่ COBOL เองก็ใช้บ่อยผ่าน
`88-level condition name` (Part 010) เพื่อให้โค้ดอ่านง่ายขึ้นแทนการจำรหัสตัวอักษรตรง ๆ

### DML: การบรรจุข้อมูลเริ่มต้น (INSERT)

```sql
INSERT INTO CUSTOMER (CUST_ID, CUST_NAME, CUST_CITY) VALUES
    ('100001', 'SOMCHAI JAIDEE', 'BANGKOK'),
    ('100002', 'SUDA MEECHAI', 'CHIANG MAI'),
    ('100003', 'PRASERT KAEWTA', 'BANGKOK');

INSERT INTO ACCOUNT (ACCT_NO, CUST_ID, ACCT_TYPE, ACCT_BALANCE) VALUES
    ('9000001', '100001', 'S', 15000.00),
    ('9000002', '100001', 'C', 5000.00),
    ('9000003', '100002', 'S', 8250.50),
    ('9000004', '100003', 'S', 500.00);
```

(ไวยากรณ์ `INSERT INTO ... VALUES (...), (...), (...)` คือรูปแบบ **Multi-Row INSERT** ที่เพิ่ม
หลายแถวในคำสั่งเดียว แทนที่จะเขียน `INSERT` แยกทีละแถวหลายคำสั่ง)

### DML: Query รายงานสรุปที่ใช้ทุกเทคนิคจาก Part นี้

**รายงานที่ 1**: ยอดคงเหลือรวมทุกบัญชีของลูกค้าแต่ละคน เฉพาะลูกค้าที่มียอดรวมเกิน 10,000 บาท

```sql
SELECT C.CUST_NAME, C.CUST_CITY, SUM(A.ACCT_BALANCE) AS TOTAL_BALANCE
FROM CUSTOMER C
INNER JOIN ACCOUNT A
    ON C.CUST_ID = A.CUST_ID
GROUP BY C.CUST_NAME, C.CUST_CITY
HAVING SUM(A.ACCT_BALANCE) > 10000.00
ORDER BY TOTAL_BALANCE DESC;
```

**ผลลัพธ์ที่คาดว่าจะได้:**

| CUST_NAME | CUST_CITY | TOTAL_BALANCE |
|---|---|---|
| SOMCHAI JAIDEE | BANGKOK | 20000.00 |

**รายงานที่ 2**: จำนวนบัญชีแยกตามประเภท (Savings vs Checking) พร้อมยอดรวมของแต่ละประเภท

```sql
SELECT ACCT_TYPE, COUNT(*) AS ACCT_COUNT, SUM(ACCT_BALANCE) AS TOTAL_BALANCE
FROM ACCOUNT
GROUP BY ACCT_TYPE;
```

**ผลลัพธ์ที่คาดว่าจะได้:**

| ACCT_TYPE | ACCT_COUNT | TOTAL_BALANCE |
|---|---|---|
| S | 3 | 23750.50 |
| C | 1 | 5000.00 |

**รายงานที่ 3**: ลูกค้าทุกคนพร้อมจำนวนบัญชี (รวมลูกค้าที่ยังไม่มีบัญชีเลยด้วย โดยใช้
`LEFT OUTER JOIN`)

```sql
SELECT C.CUST_NAME, COUNT(A.ACCT_NO) AS ACCT_COUNT
FROM CUSTOMER C
LEFT OUTER JOIN ACCOUNT A
    ON C.CUST_ID = A.CUST_ID
GROUP BY C.CUST_NAME;
```

### สรุปการเตรียมพร้อมสำหรับ Part 058

Schema ทั้ง 3 ตารางนี้ (`CUSTOMER`, `ACCOUNT`, `TRANSACTION`) และ Host Variable ที่ออกแบบไว้ใน
ขั้นตอนที่ 569 จะถูกนำไปใช้ต่อเนื่องใน Part 058 เมื่อเราเขียนโปรแกรม COBOL ที่มีคำสั่ง `EXEC SQL`
ฝังอยู่จริง เพื่อ `SELECT` ข้อมูลเข้าตัวแปร COBOL, `INSERT` ข้อมูลใหม่จากค่าที่โปรแกรมคำนวณได้ และ
จัดการ **Transaction** (การรับประกันว่าการเปลี่ยนแปลงหลายคำสั่ง SQL จะสำเร็จพร้อมกันหรือไม่สำเร็จ
เลยทั้งหมด ตามที่กล่าวถึงเกริ่นไว้ในแบบฝึกหัดที่ 565.1)

### ข้อควรระวัง

- **คำสั่ง SQL ทั้งหมดในกรณีศึกษานี้เป็นไวยากรณ์มาตรฐานอ้างอิง ไม่ได้ถูกรันจริงกับฐานข้อมูลหรือ
  เครื่องมือใด ๆ ในสภาพแวดล้อมของหลักสูตรนี้** ผลลัพธ์ที่แสดงเป็นผลลัพธ์ที่คำนวณด้วยมือตามหลักการ
  ทำงานของ SQL มาตรฐาน เพื่อประกอบความเข้าใจเท่านั้น
- การออกแบบ schema ที่ดีควรพิจารณา Normalization (ตามที่กล่าวถึงในขั้นตอนที่ 561) ตั้งแต่ต้น
  เพื่อหลีกเลี่ยงข้อมูลซ้ำซ้อนที่จะสร้างปัญหาความไม่สอดคล้องกันในระยะยาว — schema ในกรณีศึกษานี้
  ได้แยก `CUSTOMER`/`ACCOUNT`/`TRANSACTION` ออกจากกันตามหลักการนี้แล้ว

### แบบฝึกหัดที่ 570.1

**โจทย์**: จงเขียน SQL Query ที่แสดงรายละเอียดธุรกรรมทั้งหมด พร้อมชื่อลูกค้าเจ้าของบัญชีที่เกิด
ธุรกรรมนั้น (ต้อง JOIN ทั้ง 3 ตารางเข้าด้วยกัน)

**เฉลย**:

```sql
SELECT T.TXN_ID, C.CUST_NAME, A.ACCT_NO, T.TXN_TYPE, T.TXN_AMOUNT
FROM TRANSACTION T
INNER JOIN ACCOUNT A
    ON T.ACCT_NO = A.ACCT_NO
INNER JOIN CUSTOMER C
    ON A.CUST_ID = C.CUST_ID
ORDER BY T.TXN_ID;
```

คำสั่งนี้แสดงให้เห็นว่า JOIN สามารถเชื่อมโยงได้มากกว่า 2 ตารางพร้อมกันในคำสั่งเดียว โดยเชื่อม
`TRANSACTION` เข้ากับ `ACCOUNT` ก่อน แล้วเชื่อม `ACCOUNT` ต่อเข้ากับ `CUSTOMER` อีกทอดหนึ่ง
ตามลำดับความสัมพันธ์ระหว่างตารางที่ออกแบบไว้

## สรุปท้ายบท

ใน Part นี้ เราได้เรียนรู้แนวคิดพื้นฐานของฐานข้อมูลเชิงสัมพันธ์และภาษา SQL ที่จะเป็นรากฐานสำคัญ
สำหรับ Embedded SQL ใน Part 058:

- แนวคิดฐานข้อมูลเชิงสัมพันธ์: Table, Row, Column, Primary Key, Foreign Key, Normalization
- DB2 for z/OS และความสัมพันธ์กับ VSAM (ที่เรียนไปแล้วใน Part 055-056) ในฐานะชั้นจัดเก็บข้อมูล
  เบื้องหลัง พร้อม DB2 Catalog สำหรับตรวจสอบ metadata
- `CREATE TABLE` (DDL) พร้อมชนิดข้อมูลพื้นฐาน (`CHAR`, `VARCHAR`, `DECIMAL`) และแนวคิด NULL
- `SELECT` (DML) สำหรับค้นหาข้อมูล เทียบเท่าแต่ทรงพลังกว่า `READ` + `IF` ของ COBOL
- `INSERT`, `UPDATE`, `DELETE` (DML) เทียบเท่า `WRITE`, `REWRITE`, `DELETE` ของ COBOL
- `WHERE` Clause ขั้นสูง: `BETWEEN`, `IN`, `LIKE`, `IS NULL`
- `JOIN` (INNER/LEFT OUTER) ที่เทียบเท่า Master-Detail Processing (Part 026) แบบ Declarative
- Aggregate Functions และ `GROUP BY`/`HAVING` ที่เทียบเท่า Control Break (Part 039) แบบ
  Declarative
- การแปลงชนิดข้อมูล DB2 เป็น COBOL PICTURE Clause และแนวคิด Host Variable/VARCHAR Host
  Variable ที่เตรียมพร้อมสำหรับ Embedded SQL
- กรณีศึกษารวม: schema ธนาคาร 3 ตารางพร้อม DDL/DML ครบชุดที่จะถูกนำไปใช้ต่อใน Part 058

**ย้ำอีกครั้ง**: คำสั่ง SQL ทั้งหมดในเอกสารนี้เป็นไวยากรณ์มาตรฐานอ้างอิงที่สอดคล้องกับ DB2 SQL
Dialect แต่**ไม่ได้ถูกรันจริงกับฐานข้อมูลหรือเครื่องมือใด ๆ ในสภาพแวดล้อมของหลักสูตรนี้** และไม่ได้
ผูกกับ database engine ตัวใดตัวหนึ่งโดยเฉพาะ ผลลัพธ์ที่แสดงเป็นผลลัพธ์ที่คำนวณตามหลักการทำงานของ
SQL มาตรฐานเพื่อประกอบความเข้าใจเท่านั้น หากต้องการทดลองรันจริง แนะนำให้ใช้ DB2 บน Mainframe จริง
หรือฐานข้อมูลเชิงสัมพันธ์อื่นที่รองรับ SQL มาตรฐาน

Part ถัดไป (**Part 058**) จะนำทุกสิ่งที่เรียนมาใน Part นี้มาต่อยอดเป็นทักษะที่ใช้งานได้จริงในโลก
Mainframe: **Embedded SQL — การเขียนคำสั่ง `EXEC SQL` ฝังอยู่ในโปรแกรม COBOL โดยตรง** พร้อมแนะนำ
SQLCA (SQL Communication Area), Host Variable แบบเต็มรูปแบบ และการจัดการ Transaction เบื้องต้น
