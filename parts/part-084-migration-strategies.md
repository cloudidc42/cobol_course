# Part 084: Migration Strategies: COBOL to Java/C# (ขั้นตอนที่ 831–840)

## คำนำของ Part นี้

Part 083 สอนให้เราวิเคราะห์ระบบ Legacy อย่างเป็นระบบจนเข้าใจ Data Model, Control Flow, และกฎธุรกิจของ
โปรแกรม `LEGACYORD` อย่างถ่องแท้ — แต่การวิเคราะห์เพียงอย่างเดียวยังไม่ตอบคำถามที่สำคัญที่สุดสำหรับผู้
บริหารเทคโนโลยีและสถาปนิกระบบ: **"แล้วเราควรทำอะไรกับระบบนี้ต่อไป?"**

Part นี้จะพาไปสำรวจ **3 กลยุทธ์หลักในการ Migrate ระบบ COBOL** ที่ใช้กันจริงในอุตสาหกรรม พร้อมข้อดี
ข้อเสีย และสถานการณ์ที่เหมาะสมของแต่ละแนวทาง จากนั้นจะลงลึกในรายละเอียดทางเทคนิคที่สำคัญที่สุดอย่างหนึ่ง
ของการ Migrate ไปยัง Java หรือ C#: **ปัญหาการแปลงชนิดข้อมูลตัวเลขทศนิยม** ระหว่าง COBOL's fixed-point
decimal (`PIC 9V99`, `COMP-3`) กับชนิดข้อมูลของภาษาสมัยใหม่ (`double`, `BigDecimal`) — พร้อมตัวอย่างที่
คอมไพล์และรันได้จริงทั้งฝั่ง COBOL และฝั่ง Java ที่พิสูจน์ให้เห็นว่าปัญหานี้เกิดขึ้นจริง ไม่ใช่แค่ทฤษฎี

ความรู้จาก Part นี้ (โดยเฉพาะการเลือกกลยุทธ์ Wrap/Encapsulate) จะถูกนำไปใช้เป็นแนวทางหลักใน **Part 085**
ซึ่งเป็นโปรเจกต์รวบยอดปิดท้ายเฟส 5 ของหลักสูตร

## ขั้นตอนที่ 831: ภาพรวม 3 กลยุทธ์หลักในการ Migrate ระบบ COBOL

### ทำไมต้องมี "กลยุทธ์" ไม่ใช่แค่ "ลงมือทำ"

เมื่อองค์กรตัดสินใจว่าจะปรับปรุงระบบ COBOL Legacy ให้ทันสมัยขึ้น คำถามแรกที่ต้องตอบไม่ใช่ "จะเขียนโค้ด
อย่างไร" แต่คือ **"จะเปลี่ยนผ่านระบบทั้งหมดด้วยวิธีการแบบไหน"** เพราะแต่ละแนวทางมีต้นทุน ความเสี่ยง และ
ระยะเวลาที่แตกต่างกันอย่างมาก การเลือกกลยุทธ์ผิดสามารถทำให้โครงการที่ควรใช้เวลา 6 เดือนกลายเป็นโครงการ
ที่ล้มเหลวหลังจากลงทุนไปแล้ว 3 ปีได้จริงในโลกอุตสาหกรรม

### กลยุทธ์ที่ 1: Full Rewrite (เขียนใหม่ทั้งหมด)

เขียนระบบทดแทนขึ้นใหม่ทั้งหมดด้วยภาษาสมัยใหม่ (Java, C#, Python ฯลฯ) โดยอ้างอิงจากความเข้าใจที่ได้จาก
Legacy Analysis (Part 083) แล้ว**เลิกใช้ COBOL เดิมทั้งหมด**เมื่อระบบใหม่พร้อม

### กลยุทธ์ที่ 2: Automated Transpilation (แปลงโค้ดอัตโนมัติ)

ใช้เครื่องมือซอฟต์แวร์แปลงซอร์สโค้ด COBOL ให้เป็นซอร์สโค้ดภาษาอื่นโดยอัตโนมัติ (เช่น COBOL เป็น Java)
โดยพยายามคงตรรกะเดิมไว้มากที่สุดโดยมนุษย์เข้าไปแก้ไขโค้ดที่แปลงแล้วให้น้อยที่สุด

### กลยุทธ์ที่ 3: Wrap / Encapsulate (ห่อหุ้มด้วย Strangler Fig Pattern)

**ไม่เขียนโค้ด COBOL เดิมใหม่เลย** แต่สร้างชั้น (layer) ใหม่ห่อหุ้มรอบระบบเดิม (เช่น REST API ตาม Part
073) แล้วค่อย ๆ ย้ายฟังก์ชันการทำงานออกจากระบบเดิมไปยังระบบใหม่ทีละส่วนตามหลัก **Strangler Fig Pattern**
ที่ Part 077 เคยแนะนำไว้ในบริบทของ Cloud Modernization — Part นี้จะทบทวนแนวคิดนั้นและลงรายละเอียดเพิ่มเติม

### ตารางเปรียบเทียบภาพรวม

| มิติ | Full Rewrite | Automated Transpilation | Wrap/Encapsulate |
|---|---|---|---|
| ความเสี่ยงต่อธุรกิจระหว่างทำ | สูงมาก (Big Bang) | ปานกลาง-สูง | ต่ำ (ค่อยเป็นค่อยไป) |
| ต้นทุนเริ่มต้น | สูงมาก | ปานกลาง (ค่าเครื่องมือ+ตรวจสอบ) | ต่ำ-ปานกลาง |
| ต้องเข้าใจ Business Logic ลึกแค่ไหน | ลึกมาก (ต้องเขียนใหม่ทั้งหมด) | ปานกลาง (ตรวจสอบผลลัพธ์เครื่องมือ) | ค่อยเป็นค่อยไปตามส่วนที่ย้าย |
| คุณภาพโค้ดผลลัพธ์ | ดีที่สุด (ออกแบบใหม่ได้เต็มที่) | มักอ่านยาก (โค้ดที่แปลงอัตโนมัติ) | ดี เฉพาะส่วนที่ Refactor แล้ว |
| เวลาที่เห็นผลลัพธ์แรก | ช้ามาก (ต้องรอจบทั้งระบบ) | เร็วกว่า Full Rewrite | เร็วที่สุด (เห็นผลทีละส่วน) |
| ความนิยมในทางปฏิบัติจริง (2026) | ต่ำ สำหรับระบบใหญ่ | ปานกลาง | **สูงที่สุด** |

รายละเอียดของแต่ละกลยุทธ์จะอธิบายลึกในขั้นตอนที่ 832-834

### ข้อควรระวัง

- ไม่มีกลยุทธ์ใดที่ "ดีที่สุดเสมอ" — การเลือกขึ้นอยู่กับปัจจัยเฉพาะของแต่ละองค์กร เช่น ขนาดของระบบ,
  ความเสี่ยงที่ธุรกิจยอมรับได้, งบประมาณ, และเวลาที่มี
- อย่าตัดสินใจเลือกกลยุทธ์ก่อนทำ Legacy Analysis (Part 083) ให้เสร็จสมบูรณ์ — การเลือกกลยุทธ์โดยไม่เข้าใจ
  ระบบเดิมอย่างถ่องแท้เป็นสาเหตุสำคัญของความล้มเหลวในโครงการ Modernization จริง

### แบบฝึกหัดที่ 831.1

**โจทย์**: จงยกตัวอย่างสถานการณ์องค์กร 1 กรณีที่คุณคิดว่า Full Rewrite อาจเป็นทางเลือกที่เหมาะสมกว่า
Wrap/Encapsulate ทั้งที่ตารางข้างต้นระบุว่า Wrap/Encapsulate ได้รับความนิยมสูงสุด

**เฉลยแนวทาง**: กรณีที่ระบบ Legacy มีขนาดเล็กมาก (เช่นไม่กี่พันบรรทัด), มีผู้ใช้งานจำนวนน้อย, ความเสี่ยง
ทางธุรกิจต่ำหากหยุดทำงานชั่วคราว, และทีมมีเวลา/ทรัพยากรเพียงพอที่จะเขียนใหม่และทดสอบอย่างละเอียดก่อน
Go-live — ในกรณีนี้ Full Rewrite อาจให้ผลลัพธ์ที่คุณภาพดีกว่าและใช้เวลาไม่นานเกินไป ต่างจากระบบขนาดใหญ่
หลายล้านบรรทัดที่ Full Rewrite มีความเสี่ยงสูงเกินกว่าจะยอมรับได้

## ขั้นตอนที่ 832: เจาะลึกกลยุทธ์ Full Rewrite

### ข้อดี

1. **โอกาสออกแบบสถาปัตยกรรมใหม่ทั้งหมด** — ไม่ต้องแบกรับข้อจำกัดของโครงสร้างเดิม สามารถใช้ Design
   Pattern สมัยใหม่ (ทบทวน Part 082) ได้อย่างเต็มที่ตั้งแต่ต้น
2. **กำจัดโค้ดที่ตายแล้วและหนี้ทางเทคนิค (Technical Debt) ได้หมดจด** — ไม่ต้องพะวงกับ Dead Code แบบที่
   พบใน `OLD-CALC-DISCOUNT-V1` ของ Part 083
3. **ดึงดูดนักพัฒนารุ่นใหม่ได้ง่ายกว่า** — ทำงานกับภาษาและเครื่องมือที่ตลาดแรงงานคุ้นเคย

### ข้อเสีย

1. **ความเสี่ยงแบบ "Big Bang"** — ระบบใหม่ทั้งหมดต้องถูกทดสอบและพิสูจน์ว่าทำงานถูกต้องก่อน Go-live
   ครั้งเดียว หากพลาดแม้แต่กฎธุรกิจข้อเดียวที่ไม่ได้ถูกวิเคราะห์ไว้ใน Part 083 ผลกระทบอาจรุนแรงมาก
2. **ต้นทุนเวลาและงบประมาณสูงมาก** — ระบบที่มีขนาดหลายแสนถึงหลายล้านบรรทัดอาจใช้เวลาเขียนใหม่หลายปี
   ตามที่ Part 001 เคยกล่าวถึงไว้
3. **ความรู้ทางธุรกิจที่ฝังอยู่ในโค้ดเดิมอาจสูญหายระหว่างทาง** — แม้จะทำ Legacy Analysis ดีแค่ไหน
   ก็มีโอกาสพลาดกฎย่อยบางข้อที่ไม่ปรากฏชัดในข้อมูลทดสอบที่ใช้ตรวจสอบ

### กรณีที่เหมาะสม

ระบบขนาดเล็ก-กลาง, มีเอกสาร/ความเข้าใจทางธุรกิจที่ชัดเจนอยู่แล้ว, ความเสี่ยงจากการหยุดทำงานต่ำ, หรือ
ระบบเดิมมีปัญหาด้านสถาปัตยกรรมรุนแรงจนการ Refactor แบบค่อยเป็นค่อยไปทำไม่ได้จริง

### ข้อควรระวัง

- หากเลือก Full Rewrite ต้องมี **Golden Master Testing** (เทคนิคที่ Part 085 ขั้นตอนที่ 842 จะสอน)
  อย่างเข้มงวดที่สุด เพราะไม่มีระบบเดิมให้เทียบเคียงแบบค่อยเป็นค่อยไปเหมือนกลยุทธ์ Wrap/Encapsulate
- "Second System Effect" เป็นความเสี่ยงที่รู้จักกันดีในวิศวกรรมซอฟต์แวร์: ทีมที่เขียนระบบทดแทนมักอยาก
  ใส่ฟีเจอร์ใหม่ที่ระบบเดิมไม่มีเข้าไปด้วยระหว่างทาง ทำให้ขอบเขตงานบานปลายและความเสี่ยงเพิ่มขึ้นอีก

### แบบฝึกหัดที่ 832.1

**โจทย์**: จงอธิบายว่า Legacy Analysis จาก Part 083 (โดยเฉพาะ Decision Table ของกฎส่วนลดใน ขั้นตอนที่
827) มีความสำคัญอย่างไรเป็นพิเศษหากองค์กรเลือกใช้กลยุทธ์ Full Rewrite

**เฉลยแนวทาง**: เพราะใน Full Rewrite ไม่มีระบบเดิมให้รันคู่ขนานเพื่อเปรียบเทียบผลลัพธ์แบบ real-time
ระหว่างที่ระบบใหม่ยังพัฒนาไม่เสร็จ (ต่างจาก Wrap/Encapsulate ที่ค่อย ๆ ย้ายทีละส่วนและเปรียบเทียบได้ตลอด)
Decision Table ที่สกัดไว้อย่างละเอียดจึงเป็น**แหล่งความจริงเดียว**ที่ทีมพัฒนาระบบใหม่ใช้ยืนยันความถูกต้อง
ของ Business Logic ก่อน Go-live หากสกัดกฎมาไม่ครบหรือผิดพลาด ระบบใหม่จะมีบั๊กที่อาจไม่ถูกค้นพบจนกว่าจะ
ใช้งานจริงกับลูกค้าจริงแล้ว ซึ่งมีต้นทุนความเสียหายสูงกว่าการพบบั๊กในขั้นตอนพัฒนามาก

## ขั้นตอนที่ 833: เจาะลึกกลยุทธ์ Automated Transpilation

### แนวคิด

**Transpilation** (หรือ Transcompilation) คือการใช้เครื่องมือซอฟต์แวร์อ่านซอร์สโค้ด COBOL แล้วสร้าง
ซอร์สโค้ดภาษาอื่นที่มีพฤติกรรมเทียบเท่ากันออกมาโดยอัตโนมัติ แนวคิดคล้ายกับที่ Part 072 เคยกล่าวถึงการ
เชื่อมต่อ COBOL กับภาษาอื่นผ่าน `CALL` แต่ต่างกันตรงที่ Transpilation **แปลงโค้ดทั้งหมด** ไม่ใช่แค่เรียก
ใช้งานข้ามภาษา

### ตัวอย่างแนวคิดการแปลง (ภาพประกอบ ไม่ใช่ output จากเครื่องมือจริง)

เครื่องมือ Transpiler เชิงพาณิชย์ในตลาด (เช่นจากผู้ให้บริการที่เชี่ยวชาญด้าน Mainframe Modernization)
มักแปลง COBOL แบบ statement-ต่อ-statement ให้ใกล้เคียงต้นฉบับที่สุด แทนที่จะแปลงเป็นโค้ดภาษาใหม่ที่
"อ่านเป็นธรรมชาติ" — ตัวอย่างเช่น คำสั่ง COBOL:

```cobol
       COMPUTE WS-TOTAL ROUNDED = WS-NET + WS-TAX-AMT.
```

มักถูกแปลงเป็นโค้ด Java ที่เรียกใช้ Library เลียนแบบพฤติกรรม COBOL โดยตรง (ไม่ใช่โค้ด Java ที่เขียนขึ้น
เองตามธรรมชาติของภาษา) เพื่อรับประกันว่าพฤติกรรมการปัดเศษเหมือนเดิมทุกกรณี ผลลัพธ์คือโค้ดที่ทำงานถูกต้อง
แต่ "อ่านเหมือน COBOL ที่สวมเสื้อ Java" มากกว่าจะเป็น Java ที่ทีมพัฒนา Java เขียนขึ้นเองตามธรรมชาติ

### ข้อดี

1. **เร็วกว่า Full Rewrite มาก** สำหรับระบบขนาดใหญ่ที่มีโค้ดหลายแสนบรรทัด เพราะไม่ต้องเขียนใหม่ทีละบรรทัด
2. **ลดความเสี่ยงจากการตีความกฎธุรกิจผิดพลาด** เพราะเครื่องมือแปลงโครงสร้างตรรกะแบบตรงตัว ไม่ใช่การ
   ตีความใหม่โดยมนุษย์

### ข้อเสีย

1. **โค้ดผลลัพธ์มักมีคุณภาพต่ำในแง่ Maintainability** — ไม่ได้ใช้ Design Pattern หรือ Idiom ตามธรรมชาติ
   ของภาษาปลายทาง ทำให้ทีมพัฒนา Java/C# รุ่นใหม่ยังต้องเรียนรู้ "วิธีคิดแบบ COBOL" อยู่ดีเพื่อแก้ไขโค้ด
   ที่แปลงมาได้
2. **ต้องพึ่งพาเครื่องมือเชิงพาณิชย์ราคาสูง** และผลลัพธ์คุณภาพแตกต่างกันมากตามผู้ให้บริการแต่ละราย
3. **ยังต้องทดสอบอย่างละเอียดเท่ากับ Full Rewrite** เพราะเครื่องมือแปลงโค้ดไม่รับประกันความถูกต้อง 100%
   โดยเฉพาะจุดที่ COBOL มีพฤติกรรมเฉพาะตัว (เช่นการปัดเศษทศนิยมที่ Part นี้จะสาธิตในขั้นตอนที่ 836-837)

### กรณีที่เหมาะสม

ระบบขนาดใหญ่มากที่ Full Rewrite ทำไม่ได้จริงในเวลาที่มี แต่องค์กรมีความจำเป็นเร่งด่วนที่ต้องเลิกใช้
Mainframe/COBOL ทั้งหมด (เช่นด้วยเหตุผลด้านสัญญากับผู้ให้บริการ หรือขาดแคลนบุคลากรอย่างรุนแรง)

### ข้อควรระวัง

- อย่าคาดหวังว่าโค้ดที่ได้จากการ Transpile จะพร้อมใช้งาน production ทันทีโดยไม่มีการตรวจสอบของมนุษย์
  ควรมีขั้นตอน Code Review และทดสอบเทียบผลลัพธ์กับระบบเดิมอย่างละเอียดเสมอ (ใช้เทคนิค Golden Master
  Testing เดียวกับ Full Rewrite)
- ทีมพัฒนาที่จะดูแลโค้ดหลัง Transpile ต้องเตรียมใจว่าโค้ดอาจอ่านยากกว่าที่คาดไว้ในช่วงแรก และอาจต้องมี
  โครงการ Refactor เพิ่มเติมภายหลังเพื่อปรับให้เป็น Java/C# ที่เป็นธรรมชาติมากขึ้น

### แบบฝึกหัดที่ 833.1

**โจทย์**: จงอธิบายว่าทำไมเครื่องมือ Transpiler ถึงมักเลือก "แปลงแบบตรงตัวที่สุด" (แม้จะได้โค้ดที่อ่าน
ยาก) แทนที่จะพยายามสร้างโค้ดภาษาปลายทางที่ "สวยงามเป็นธรรมชาติ"

**เฉลยแนวทาง**: เพราะเป้าหมายหลักอันดับหนึ่งของ Automated Transpilation คือ**ความถูกต้องของพฤติกรรม**
(behavioral correctness) ไม่ใช่ความสวยงามของโค้ด การแปลงแบบตรงตัวช่วยลดความเสี่ยงที่การตีความใหม่ให้
"สวยงามขึ้น" จะเปลี่ยนพฤติกรรมของระบบไปโดยไม่ตั้งใจ (เช่นการปัดเศษทศนิยมที่ต่างไปเพียงเล็กน้อยก็อาจสร้าง
ความเสียหายทางการเงินได้ ตามที่จะเห็นตัวอย่างจริงในขั้นตอนที่ 837) เครื่องมือจึงยอมแลกความสวยงามของโค้ด
เพื่อแลกกับความมั่นใจในความถูกต้อง แล้วปล่อยให้การปรับปรุงความสวยงาม (Refactoring) เป็นงานขั้นถัดไปที่ทำ
โดยมนุษย์ภายหลัง เมื่อมีเวลาและความมั่นใจในความถูกต้องมากขึ้นแล้ว

## ขั้นตอนที่ 834: เจาะลึกกลยุทธ์ Wrap/Encapsulate (Strangler Fig Pattern)

### ทบทวนแนวคิด Strangler Fig จาก Part 077

Part 077 เคยแนะนำแนวคิด **Strangler Fig Pattern** ในบริบทของ Cloud Modernization: ชื่อนี้มาจากต้นไม้
ในธรรมชาติที่ชื่อ Strangler Fig ซึ่งเติบโตขึ้นล้อมรอบต้นไม้เจ้าบ้าน (host tree) อย่างช้า ๆ จนในที่สุด
ต้นไม้เจ้าบ้านตายไปและเหลือแต่ Strangler Fig ยืนต้นอยู่แทนที่ — ในบริบทซอฟต์แวร์ หมายถึงการสร้างระบบใหม่
ขึ้นมา**ล้อมรอบ**ระบบเดิม แล้วค่อย ๆ ย้ายการทำงานออกจากระบบเดิมไปยังระบบใหม่**ทีละส่วน** จนในที่สุด
ระบบเดิมไม่มีงานอะไรเหลือให้ทำแล้วจึงปลดระวางได้อย่างปลอดภัย

### ขั้นตอนการทำงานของ Wrap/Encapsulate ในบริบท COBOL

```
ระยะที่ 1: ห่อหุ้ม (Wrap)
+------------------+        +-------------------+
|  REST API Layer  | -----> |  COBOL Program     |
|  (Part 073)       |        |  (ทำงานเหมือนเดิม  |
|                   |        |   ทุกประการ)        |
+------------------+        +-------------------+
       ^
       | ผู้เรียกทั้งหมด (เว็บ, มือถือ, ระบบอื่น)
       | เรียกผ่าน API เท่านั้น ไม่แตะ COBOL ตรง ๆ

ระยะที่ 2: ย้ายทีละส่วน (Strangle)
+------------------+        +-------------------+
|  REST API Layer  | --+--> |  COBOL Program     |
|                   |   |    |  (เหลือ Logic       |
|                   |   |    |   บางส่วน)          |
+------------------+   |    +-------------------+
                        |
                        +--> +-------------------+
                             |  New Java Service |
                             |  (Logic ที่ย้ายแล้ว) |
                             +-------------------+

ระยะที่ 3: ปลดระวาง (Retire)
+------------------+        +-------------------+
|  REST API Layer  | -----> |  New Java Service  |
|                   |        |  (ครบทุก Logic แล้ว)|
+------------------+        +-------------------+
       COBOL Program ถูกปลดระวางอย่างปลอดภัย
```

### ทำไม Wrap/Encapsulate ถึงเป็นที่นิยมที่สุดในทางปฏิบัติ

1. **ความเสี่ยงต่ำที่สุด** — ในแต่ละช่วงเวลา มีเพียงส่วนเล็ก ๆ ของระบบที่เปลี่ยนแปลง หากเกิดปัญหาสามารถ
   ย้อนกลับ (rollback) เฉพาะส่วนนั้นได้ง่าย โดยไม่กระทบส่วนอื่นที่ยังทำงานปกติ
2. **เห็นผลลัพธ์เร็ว** — REST API Layer (Part 073) สามารถสร้างและ Go-live ได้ภายในไม่กี่สัปดาห์ แม้ว่า
   ด้านหลังยังเป็น COBOL เดิมทั้งหมดอยู่ก็ตาม สร้างความมั่นใจให้ผู้บริหารเห็นความคืบหน้าเป็นระยะ
3. **ทดสอบเปรียบเทียบได้ตลอดเวลา** — เพราะระบบเดิมยังทำงานคู่ขนานอยู่ สามารถรันทั้งสองระบบพร้อมกันแล้ว
   เปรียบเทียบผลลัพธ์ได้จริง (Parallel Run Testing ตามที่จะกล่าวถึงในขั้นตอนที่ 838)
4. **ไม่ต้องหยุดพัฒนาฟีเจอร์ใหม่ระหว่างทาง** — ต่างจาก Full Rewrite ที่มักต้อง "หยุดนิ่ง" ระบบเดิมไม่ให้
   เปลี่ยนแปลงระหว่างที่เขียนระบบใหม่ (เพื่อไม่ให้เป้าหมายขยับ) Wrap/Encapsulate ยอมให้ระบบเดิมยังคงได้รับ
   การแก้ไขเล็กน้อยระหว่างทางได้

### ข้อเสียที่ต้องรับทราบ

1. **ใช้เวลานานกว่าจะเสร็จสมบูรณ์ทั้งระบบ** — เพราะเป็นการย้ายทีละส่วน อาจใช้เวลาหลายปีกว่าจะปลดระวาง
   COBOL ได้ทั้งหมด (แต่ระหว่างทางระบบยังคงใช้งานได้ปกติตลอด ต่างจาก Full Rewrite ที่ธุรกิจต้องรอ)
2. **ต้องดูแลทั้งสองระบบไปพร้อมกันชั่วคราว** — เพิ่มภาระงานให้ทีมในช่วงเปลี่ยนผ่าน
3. **ความซับซ้อนของ API Layer เพิ่มขึ้นเรื่อย ๆ** ในช่วงกลางของกระบวนการ (ต้องรู้ว่าคำขอไหนควรส่งไปที่
   COBOL เดิม คำขอไหนควรส่งไปที่ระบบใหม่)

### นี่คือกลยุทธ์ที่ Part 085 จะใช้

เพราะเหตุผลข้างต้น **Part 085 (โปรเจกต์รวบยอดเฟส 5) จะเลือกใช้กลยุทธ์ Wrap/Encapsulate** ผสมกับการ
Refactor โค้ด COBOL ภายใน (Part 081/082) แทนที่จะเขียนใหม่เป็น Java/C# ทั้งหมด — นี่คือการตัดสินใจเชิง
สถาปัตยกรรมที่บันทึกเป็น ADR (Architecture Decision Record) ตามรูปแบบที่ Part 050 เคยแนะนำไว้:

> **ADR: เลือก Wrap/Encapsulate + Refactor แทน Full Rewrite/Transpilation สำหรับ Part 085**
> **เหตุผล**: ระบบตัวอย่างมีขนาดเล็กพอที่จะ Refactor ได้อย่างปลอดภัยด้วย Unit Test (Part 079), มี REST
> API Layer อยู่แล้วจาก Part 073 ที่นำมาต่อยอดได้ทันที, และการคง COBOL ไว้เป็นแกนคำนวณสอดคล้องกับความ
> เชี่ยวชาญด้าน Decimal Arithmetic ที่ Part 001 เคยอธิบายไว้ว่าเป็นจุดแข็งของ COBOL ที่ไม่ควรทิ้งโดยไม่
> จำเป็น

### ข้อควรระวัง

- Wrap/Encapsulate ไม่ได้แปลว่า "ไม่ต้องแก้โค้ด COBOL เดิมเลย" — ในทางปฏิบัติมักต้อง Refactor โค้ด COBOL
  ภายในให้สะอาดขึ้นก่อน (ตามเทคนิค Part 081/082) เพื่อให้ห่อหุ้มด้วย API ได้ง่ายขึ้น (เช่นแยก Business
  Logic ออกจาก File I/O ตามที่ Part 085 จะสาธิต)
- ต้องมีแผนที่ชัดเจนว่า "เมื่อไหร่จะย้ายส่วนไหน" — Wrap/Encapsulate ที่ไม่มีแผนงานชัดเจนอาจกลายเป็น
  "ห่อหุ้มไว้ตลอดกาล" โดยไม่เคยปลดระวาง COBOL เดิมได้จริงสักที ซึ่งแม้จะไม่ใช่หายนะ แต่ก็ไม่บรรลุเป้าหมาย
  การ Modernization อย่างสมบูรณ์

### แบบฝึกหัดที่ 834.1

**โจทย์**: จงอธิบายว่าทำไม "ทดสอบเปรียบเทียบได้ตลอดเวลา" (ข้อดีข้อที่ 3) ถึงเป็นข้อได้เปรียบที่สำคัญมาก
เมื่อเทียบกับ Full Rewrite โดยเฉพาะในบริบทของระบบการเงินที่ต้องการความแม่นยำสูง

**เฉลยแนวทาง**: เพราะในระบบการเงิน ความถูกต้องของตัวเลขทุกหลักสำคัญมาก (ตามที่ Part 001 เน้นย้ำเรื่อง
Decimal Arithmetic) การที่ระบบเดิม (COBOL) ยังทำงานอยู่คู่ขนานระหว่างการ Migrate ทำให้ทีมสามารถส่งข้อมูล
เดียวกันเข้าทั้งสองระบบแล้วเปรียบเทียบผลลัพธ์แบบ**เรียลไทม์**ได้ตลอดกระบวนการ Migration หากพบความ
แตกต่างแม้เพียงสตางค์เดียว ทีมจะรู้ทันทีว่าส่วนที่เพิ่งย้ายมีบั๊ก และสามารถแก้ไขได้ก่อนที่จะเปลี่ยนไปใช้
ระบบใหม่จริงทั้งหมด ต่างจาก Full Rewrite ที่ไม่มีระบบเดิมให้เปรียบเทียบระหว่างทาง ต้องรอจนกว่าจะทดสอบ
เสร็จสมบูรณ์ก่อน Go-live ครั้งเดียว ความเสี่ยงที่จะพบบั๊กหลัง Go-live จึงสูงกว่ามาก

## ขั้นตอนที่ 835: ตัวอย่างที่เป็นรูปธรรม — แปลง Paragraph คำนวณส่วนลด/ภาษีจาก COBOL เป็น Java

### เป้าหมายของตัวอย่างนี้

ไม่ว่าจะเลือกกลยุทธ์ใดใน 3 ข้อข้างต้น สุดท้ายก็มักมีจุดที่ต้องแปลง Business Logic บางส่วนจาก COBOL เป็น
ภาษาอื่นจริง ๆ (ไม่ว่าจะทำด้วยมือใน Full Rewrite, ตรวจสอบผลจาก Transpiler, หรือเขียนใหม่เฉพาะส่วนที่ย้าย
ใน Wrap/Encapsulate) ขั้นตอนนี้จะสาธิตการแปลงแบบ**ด้วยมือ** (Manual Translation) ของ Paragraph คำนวณ
ส่วนลดและภาษีอย่างละเอียด **ทั้งสองฝั่งถูกคอมไพล์และรันจริง** เพื่อพิสูจน์ว่าผลลัพธ์ตรงกันทุกตัวเลข

### ฝั่ง COBOL: DISCTAX.cob

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DISCTAX.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-ITEM-PRICE           PIC 9(5)V99  VALUE 19.99.
       01  WS-QTY                  PIC 9(3)     VALUE 3.
       01  WS-DISCOUNT-PCT         PIC 9V999    VALUE 0.070.
       01  WS-TAX-RATE             PIC 9V999    VALUE 0.070.
       01  WS-SUBTOTAL             PIC 9(7)V99.
       01  WS-DISCOUNT-AMT         PIC 9(7)V99.
       01  WS-NET                  PIC 9(7)V99.
       01  WS-TAX-AMT              PIC 9(7)V99.
       01  WS-TOTAL                PIC 9(7)V99.

       PROCEDURE DIVISION.
       MAIN-PARA.
           PERFORM CALC-TOTAL
           DISPLAY "SUBTOTAL:     " WS-SUBTOTAL
           DISPLAY "DISCOUNT-AMT: " WS-DISCOUNT-AMT
           DISPLAY "NET:          " WS-NET
           DISPLAY "TAX-AMT:      " WS-TAX-AMT
           DISPLAY "TOTAL:        " WS-TOTAL
           STOP RUN.

      *> This is the paragraph Part 084 translates to Java, statement
      *> by statement, to show how COMPUTE ... ROUNDED maps onto
      *> BigDecimal.setScale(2, RoundingMode.HALF_UP) in the host
      *> language - and why a plain "double" does not give the same
      *> answer in every case.
       CALC-TOTAL.
           COMPUTE WS-SUBTOTAL ROUNDED =
               WS-ITEM-PRICE * WS-QTY
           COMPUTE WS-DISCOUNT-AMT ROUNDED =
               WS-SUBTOTAL * WS-DISCOUNT-PCT
           COMPUTE WS-NET ROUNDED =
               WS-SUBTOTAL - WS-DISCOUNT-AMT
           COMPUTE WS-TAX-AMT ROUNDED =
               WS-NET * WS-TAX-RATE
           COMPUTE WS-TOTAL ROUNDED =
               WS-NET + WS-TAX-AMT.
```


### ฝั่ง Java: DiscTax.java (คอมไพล์และรันจริงด้วย javac/java)

สภาพแวดล้อมที่เตรียมเอกสารนี้มี `javac`/`java` (OpenJDK 21) ติดตั้งอยู่จริง จึงสามารถคอมไพล์และรันฝั่ง
Java ได้จริงเช่นเดียวกับฝั่ง COBOL ไม่ใช่แค่โค้ดอ้างอิงเฉย ๆ:

```java
import java.math.BigDecimal;
import java.math.RoundingMode;

// Java translation of DISCTAX.cob's CALC-TOTAL paragraph.
// Each BigDecimal.setScale(2, RoundingMode.HALF_UP) mirrors one
// COBOL "COMPUTE ... ROUNDED" statement, applied at the SAME point
// in the calculation - this is the part that is easy to get wrong
// when migrating: rounding at the wrong step gives a different
// final answer even though the formula looks identical.
public class DiscTax {
    public static void main(String[] args) {
        BigDecimal itemPrice = new BigDecimal("19.99");
        BigDecimal qty = new BigDecimal("3");
        BigDecimal discountPct = new BigDecimal("0.070");
        BigDecimal taxRate = new BigDecimal("0.070");

        BigDecimal subtotal = itemPrice.multiply(qty)
                .setScale(2, RoundingMode.HALF_UP);
        BigDecimal discountAmt = subtotal.multiply(discountPct)
                .setScale(2, RoundingMode.HALF_UP);
        BigDecimal net = subtotal.subtract(discountAmt)
                .setScale(2, RoundingMode.HALF_UP);
        BigDecimal taxAmt = net.multiply(taxRate)
                .setScale(2, RoundingMode.HALF_UP);
        BigDecimal total = net.add(taxAmt)
                .setScale(2, RoundingMode.HALF_UP);

        System.out.println("SUBTOTAL:     " + subtotal);
        System.out.println("DISCOUNT-AMT: " + discountAmt);
        System.out.println("NET:          " + net);
        System.out.println("TAX-AMT:      " + taxAmt);
        System.out.println("TOTAL:        " + total);
    }
}
```

คอมไพล์และรัน:

```bash
javac DiscTax.java
java DiscTax
```

**ผลลัพธ์จริงที่ได้:**

```
SUBTOTAL:     59.97
DISCOUNT-AMT: 4.20
NET:          55.77
TAX-AMT:      3.90
TOTAL:        59.67
```

### เปรียบเทียบผลลัพธ์ทั้งสองฝั่ง

| ฟิลด์ | COBOL (`DISCTAX.cob`) | Java (`DiscTax.java`) | ตรงกันหรือไม่ |
|---|---|---|---|
| SUBTOTAL | 59.97 | 59.97 | ตรงกัน |
| DISCOUNT-AMT | 4.20 | 4.20 | ตรงกัน |
| NET | 55.77 | 55.77 | ตรงกัน |
| TAX-AMT | 3.90 | 3.90 | ตรงกัน |
| TOTAL | 59.67 | 59.67 | ตรงกัน |

ผลลัพธ์ตรงกันทุกตัวเลขจริง เพราะโค้ด Java **จงใจปัดเศษที่จุดเดียวกันทุกจุด**ตามที่ COBOL's `ROUNDED`
phrase ทำในแต่ละ `COMPUTE` statement — นี่คือกุญแจสำคัญที่จะอธิบายในขั้นตอนที่ 836-837 ต่อไป

### ข้อควรระวัง

- สังเกตว่าโค้ด Java ใช้ `new BigDecimal("19.99")` (สร้างจาก `String`) **ไม่ใช่** `new
  BigDecimal(19.99)` (สร้างจาก `double`) — ความแตกต่างนี้สำคัญมากและจะอธิบายเหตุผลแบบเจาะลึกพร้อมตัวอย่าง
  จริงในขั้นตอนที่ 837
- การแปลผลลัพธ์ให้ตรงกันในตัวอย่างนี้สำเร็จเพราะ **ปัดเศษที่ทุกขั้นตอนย่อยเหมือนกันทุกจุด** — หากโค้ด
  Java คำนวณสูตรทั้งหมดรวดเดียวแล้วปัดเศษครั้งเดียวตอนจบ (แทนที่จะปัดเศษทีละ `COMPUTE` เหมือน COBOL)
  ผลลัพธ์อาจต่างกันได้ในบางกรณี แม้สูตรทางคณิตศาสตร์จะดูเหมือนกันทุกประการก็ตาม

### แบบฝึกหัดที่ 835.1

**โจทย์**: หากลบ `.setScale(2, RoundingMode.HALF_UP)` ออกจากทุกบรรทัดในโค้ด Java (คำนวณด้วยความแม่นยำ
เต็มที่ตลอดแล้วค่อยปัดเศษครั้งเดียวตอนแสดงผลลัพธ์สุดท้าย) ผลลัพธ์ `TOTAL` จะยังคงเป็น `59.67` เท่าเดิม
หรือไม่ จงอธิบายเหตุผล (ไม่จำเป็นต้องคำนวณตัวเลขจริง อธิบายแนวคิดก็เพียงพอ)

**เฉลยแนวทาง**: มีความเป็นไปได้ที่จะได้ผลลัพธ์ต่างกัน เพราะ COBOL's `COMPUTE ... ROUNDED` ปัดเศษ
**ทุกครั้ง**ที่มีการคำนวณ (ปัดเศษ `WS-DISCOUNT-AMT` ก่อนนำไปคำนวณ `WS-NET`, ปัดเศษ `WS-TAX-AMT` ก่อน
นำไปคำนวณ `WS-TOTAL`) หากโค้ด Java เก็บค่าความแม่นยำเต็มที่ตลอดทุกขั้นตอนแล้วปัดเศษครั้งเดียวตอนจบ ค่าที่
ป้อนเข้าสู่การคำนวณขั้นถัดไปจะมีทศนิยมมากกว่าที่ COBOL ใช้จริงในแต่ละขั้นตอน ทำให้ผลลัพธ์สะสมความคลาด
เคลื่อนต่างไปได้ (แม้ในตัวอย่างนี้บังเอิญอาจไม่ต่างกัน แต่ไม่สามารถรับประกันได้ในทุกกรณี) — นี่คือเหตุผล
ที่การ Migrate โค้ดทางการเงินต้อง**คงจุดปัดเศษ (rounding points) ให้ตรงกับต้นฉบับทุกจุด** ไม่ใช่แค่สูตร
คณิตศาสตร์ที่ดูเหมือนกัน

## ขั้นตอนที่ 836: Data Type Mapping — COMP-3/PIC 9V99 กับชนิดข้อมูลใน Java

### ทำไมการแปลงชนิดข้อมูลตัวเลขถึงเป็นจุดเสี่ยงอันดับหนึ่งของการ Migrate

Part 001 (ขั้นตอนที่ 5) เคยอธิบายไว้ว่า COBOL's PICTURE Clause ให้ **Fixed-Point Decimal** ที่แม่นยำ
100% ตามจำนวนหลักที่กำหนด ต่างจาก `double` ในภาษาสมัยใหม่หลายภาษาที่ใช้ **Floating-Point Binary** ซึ่งมี
ข้อจำกัดในการเก็บค่าทศนิยมบางค่าให้แม่นยำเป๊ะ — นี่คือรากเหง้าของปัญหาที่ทำให้การ Migrate ระบบการเงินจาก
COBOL ไป Java/C# ต้องระมัดระวังเป็นพิเศษ

### ตารางเทียบชนิดข้อมูล COBOL กับ Java

| COBOL Type | ตัวอย่าง PICTURE | Java ที่ตรงที่สุด | เหตุผล |
|---|---|---|---|
| Zoned Decimal | `PIC 9(7)V99` | `java.math.BigDecimal` | เก็บทศนิยมแบบฐาน 10 แม่นยำเป๊ะ เหมือน COBOL |
| Packed Decimal | `PIC 9(7)V99 COMP-3` | `java.math.BigDecimal` | `COMP-3` เป็นแค่การเก็บข้อมูลแบบอัดแน่นกว่า (2 หลักต่อไบต์) แต่ค่าตัวเลขและความแม่นยำเหมือน Zoned Decimal ทุกประการ — มีผลต่อพื้นที่จัดเก็บ ไม่มีผลต่อค่าที่ถูกต้อง |
| Binary Integer | `PIC 9(9) COMP` / `COMP-5` | `int` หรือ `long` | ไม่มีทศนิยม ใช้ Binary Integer ของ Java ได้ตรงไปตรงมา |
| Alphanumeric | `PIC X(20)` | `String` | ตรงไปตรงมา แต่ต้องระวังเรื่อง trailing space (ดูข้อควรระวัง) |
| **สิ่งที่ห้ามใช้** | (ใด ๆ ที่มีทศนิยม) | ~~`double`~~ / ~~`float`~~ | มีข้อจำกัดด้าน Binary Floating-Point ตามที่จะพิสูจน์ในขั้นตอนที่ 837 |

### ทำไม COMP-3 กับ Zoned Decimal ถึง Map ไปยัง BigDecimal เหมือนกัน

`COMP-3` (Packed Decimal, ทบทวนแนวคิดจาก Part 049 เรื่อง Compiler Directives ที่กล่าวถึงความแตกต่าง
ระหว่าง Dialect) เป็นเพียง**รูปแบบการจัดเก็บทางกายภาพ**ที่อัดตัวเลข 2 หลักลงในทุก ๆ ไบต์เพื่อประหยัดพื้นที่
บน Mainframe (สำคัญมากในยุคที่หน่วยความจำมีราคาแพง) — แต่**ค่าทางคณิตศาสตร์และความแม่นยำเหมือนกันทุก
ประการ**กับ Zoned Decimal ธรรมดา (`PIC 9(7)V99` แบบไม่มี `COMP-3`) ดังนั้นเมื่อ Migrate ไป Java ซึ่งไม่มี
concept เรื่อง "การจัดเก็บแบบอัดแน่น" แบบนี้ ทั้งสองแบบจึง Map ไปยัง `BigDecimal` เหมือนกัน — ความแตกต่าง
เรื่องการจัดเก็บเป็นเรื่องของ Performance/Storage ไม่ใช่เรื่องของค่าตัวเลขที่ถูกต้อง

### ข้อควรระวังเรื่อง String และ Trailing Space

`PIC X(20)` เก็บค่าด้วยความยาวคงที่เสมอ (เติมช่องว่างขวาถ้าข้อความสั้นกว่า) ในขณะที่ Java's `String` มี
ความยาวผันแปรได้ตามธรรมชาติ เมื่อ Migrate ต้องตัดสินใจว่าจะ **ตัด trailing space ทิ้งตอนอ่านเข้า Java
หรือไม่** — การตัดสินใจนี้ต้องสอดคล้องกับพฤติกรรมเดิมของระบบ (เช่น ถ้าโค้ด COBOL เดิมเปรียบเทียบชื่อลูกค้า
โดยใช้ `PIC X(20)` เต็มความยาวรวม trailing space ด้วย การ Migrate ไป Java แล้ว `.trim()` string ก่อน
เปรียบเทียบอาจทำให้ผลลัพธ์การเปรียบเทียบเปลี่ยนไปในบางกรณี)

### ข้อควรระวัง

- อย่าใช้ `double`/`float` สำหรับข้อมูลการเงินใด ๆ ใน Java แม้ในกรณีที่ดูเหมือนตัวเลขจะ "ลงตัวพอดี" ก็ตาม
  เพราะไม่มีการรับประกันว่าการคำนวณในอนาคตจะยังคง "ลงตัวพอดี" เสมอไป — ใช้ `BigDecimal` เป็นค่าเริ่มต้น
  เสมอสำหรับตัวเลขที่มีทศนิยมในโดเมนการเงิน
- `BigDecimal` ใน Java ไม่ปัดเศษอัตโนมัติเหมือน COBOL's `ROUNDED` — ต้องเรียก `.setScale(n,
  RoundingMode.XXX)` อย่างชัดเจนทุกครั้งที่ต้องการปัดเศษ มิฉะนั้นค่าจะสะสมทศนิยมยาวขึ้นเรื่อย ๆ ตามที่
  เห็นในขั้นตอนที่ 835

### แบบฝึกหัดที่ 836.1

**โจทย์**: จงอธิบายว่าทำไมฟิลด์ `PIC 9(9) COMP` (Binary Integer ไม่มีทศนิยม เช่นตัวนับจำนวนธุรกรรม)
ถึง Map ไปยัง Java's `long` ได้อย่างปลอดภัย โดยไม่มีความเสี่ยงแบบเดียวกับฟิลด์ที่มีทศนิยม

**เฉลยแนวทาง**: เพราะปัญหาความไม่แม่นยำของ Floating-Point เกิดจากการที่เลขฐาน 2 (binary) ไม่สามารถ
แทนค่าเศษส่วนทศนิยม (ฐาน 10) บางค่าได้แม่นยำเป๊ะ (เช่น 0.1 ในฐาน 2 เป็นเลขซ้ำไม่รู้จบ) แต่ปัญหานี้เกิด
**เฉพาะกับค่าที่มีทศนิยม**เท่านั้น จำนวนเต็ม (Integer) ไม่มีปัญหานี้เลย เพราะเลขจำนวนเต็มทุกค่าที่อยู่ใน
ขอบเขตของชนิดข้อมูลนั้น (เช่น `long` ของ Java รองรับได้ถึงประมาณ 9.2 ล้านล้านล้าน) สามารถแทนค่าด้วยเลข
ฐาน 2 ได้แม่นยำ 100% เสมอ ไม่มีการปัดเศษหรือความคลาดเคลื่อนใด ๆ เกิดขึ้น

## ขั้นตอนที่ 837: พิสูจน์ปัญหาการปัดเศษด้วยตัวอย่างที่ทดสอบจริง

### ตั้งโจทย์: ปัดเศษ 1.005 ให้เหลือ 2 ตำแหน่งทศนิยม

โจทย์นี้ดูเรียบง่ายมาก: นำค่า `1.005` มาปัดเศษให้เหลือทศนิยม 2 ตำแหน่งด้วยกฎ "ปัดขึ้นเมื่อเลขหลักที่ 3
เป็น 5 ขึ้นไป" (Round Half Up ซึ่งเป็นค่าเริ่มต้นของ COBOL's `ROUNDED`) คำตอบทางคณิตศาสตร์ที่ถูกต้องคือ
**`1.01`** เพราะหลักที่ 3 คือ 5 พอดี

### ฝั่ง COBOL: ROUNDCHK.cob

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. ROUNDCHK.
       AUTHOR. COBOL-COURSE.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-AMOUNT               PIC 9(3)V999 VALUE 1.005.
       01  WS-ROUNDED              PIC 9(3)V99.

       PROCEDURE DIVISION.
       MAIN-PARA.
           COMPUTE WS-ROUNDED ROUNDED = WS-AMOUNT
           DISPLAY "COBOL FIXED-DECIMAL 1.005 ROUNDED TO 2DP: "
               WS-ROUNDED
           STOP RUN.
```

```bash
cobc -x -o roundcheck roundcheck.cob
./roundcheck
```

**ผลลัพธ์จริงที่ได้:**

```
COBOL FIXED-DECIMAL 1.005 ROUNDED TO 2DP: 001.01
```

**ถูกต้องตามที่คาดหวังพอดี (`1.01`)** — เพราะ COBOL เก็บ `1.005` เป็นเลขฐาน 10 แบบ Fixed-Point ที่แม่นยำ
100% ไม่มีการแปลงผ่านเลขฐาน 2 เลย

### ฝั่ง Java: ทดลองสองวิธี เปรียบเทียบกัน

```java
import java.math.BigDecimal;
import java.math.RoundingMode;

// Demonstrates the classic COBOL-to-Java migration pitfall: a plain
// "double" cannot represent 1.005 exactly in binary, so naive
// rounding gives the wrong cent value even though the formula looks
// correct. BigDecimal built from a String (not from the double)
// reproduces COBOL's exact fixed-point answer.
public class RoundCheck {
    public static void main(String[] args) {
        double amountDouble = 1.005;
        System.out.println("double 1.005 actually stores as: "
                + new BigDecimal(amountDouble));
        System.out.println("amountDouble * 100 evaluates to:  "
                + (amountDouble * 100));

        long naiveCents = Math.round(amountDouble * 100);
        System.out.println("naive double rounding (WRONG):    "
                + (naiveCents / 100.0));

        BigDecimal amountExact = new BigDecimal("1.005");
        BigDecimal correct = amountExact.setScale(2, RoundingMode.HALF_UP);
        System.out.println("BigDecimal(\"1.005\") rounded (OK): "
                + correct);
    }
}
```

```bash
javac RoundCheck.java
java RoundCheck
```

**ผลลัพธ์จริงที่ได้:**

```
double 1.005 actually stores as: 1.00499999999999989341858963598497211933135986328125
amountDouble * 100 evaluates to:  100.49999999999999
naive double rounding (WRONG):    1.0
BigDecimal("1.005") rounded (OK): 1.01
```

### วิเคราะห์ผลลัพธ์: เกิดอะไรขึ้นจริง

1. **`double amountDouble = 1.005;`** — ค่าที่ Java เก็บจริงในหน่วยความจำ**ไม่ใช่** `1.005` พอดี แต่เป็น
   `1.00499999999999989...` เพราะเลขฐาน 2 ไม่สามารถแทนค่า `1.005` (เศษส่วนฐาน 10) ได้แม่นยำเป๊ะ — นี่คือ
   ข้อจำกัดพื้นฐานของ Binary Floating-Point ที่ไม่เกี่ยวกับภาษาโปรแกรมใดภาษาหนึ่งเป็นการเฉพาะ (เกิดกับ
   ทุกภาษาที่ใช้ IEEE 754 double เหมือนกันหมด รวมถึง JavaScript, Python's `float`, C's `double`)
2. **วิธี "ไร้เดียงสา" (naive)**: คูณด้วย 100 แล้วปัดเศษเป็นจำนวนเต็ม (`Math.round(amountDouble *
   100)`) — เมื่อ `amountDouble * 100` ได้ค่า `100.49999999999999` (ต่ำกว่า 100.5 เล็กน้อยเพราะความ
   คลาดเคลื่อนจากข้อ 1) `Math.round()` จึงปัด**ลง**เป็น `100` แทนที่จะเป็น `101` ทำให้ได้ผลลัพธ์ `1.0`
   ซึ่ง**ผิดจากคำตอบที่ถูกต้อง (`1.01`) โดยสิ้นเชิง**
3. **วิธีที่ถูกต้อง**: สร้าง `BigDecimal` จาก **String** (`new BigDecimal("1.005")`) แทนที่จะสร้างจาก
   `double` — วิธีนี้เก็บค่า `1.005` แบบฐาน 10 แม่นยำเป๊ะเหมือน COBOL ทำให้ `.setScale(2,
   RoundingMode.HALF_UP)` ปัดเศษได้ผลลัพธ์ที่ถูกต้อง (`1.01`) ตรงกับ COBOL ทุกประการ

### บทเรียนสำคัญที่สุดของ Part นี้

นี่คือหลักฐานที่ทดสอบจริงว่า **การแปลง Fixed-Point Decimal ของ COBOL ไปเป็น `double` ของภาษาอื่นสามารถ
ทำให้ผลลัพธ์ทางการเงินผิดพลาดได้จริง แม้สูตรคำนวณจะดูถูกต้องทุกประการ** — นี่คือเหตุผลที่ทุกกลยุทธ์การ
Migrate (Full Rewrite, Transpilation, หรือ Wrap/Encapsulate) ต้องมีขั้นตอนตรวจสอบชนิดข้อมูลตัวเลขอย่าง
ละเอียดเป็นพิเศษ และเป็นเหตุผลสำคัญข้อหนึ่งที่ Part 085 จะเลือกคง COBOL ไว้เป็นแกนคำนวณแทนที่จะ Migrate
Business Logic ทางการเงินไปเป็นภาษาอื่นทั้งหมด

### ข้อควรระวัง

- อย่าใช้ `new BigDecimal(someDouble)` (constructor ที่รับ `double`) กับข้อมูลการเงินเด็ดขาด — ให้ใช้
  `new BigDecimal(someString)` หรือ `BigDecimal.valueOf(someDouble)` แทน (แม้ `valueOf` จะปลอดภัยกว่า
  constructor ที่รับ `double` ตรง ๆ เพราะใช้ `Double.toString()` ภายใน แต่ทางที่ปลอดภัยที่สุดคือรับค่า
  ตัวเลขจากต้นทางเป็น String หรือ BigDecimal ตั้งแต่แรกโดยไม่ผ่าน `double` เลย)
- ค่า `1.005` ในตัวอย่างนี้ไม่ใช่กรณีพิเศษหายาก — ค่าทศนิยมจำนวนมากที่ลงท้ายด้วย 5 ในหลักที่ 3 มีความเสี่ยง
  แบบเดียวกัน (เช่น `2.675`, `35.855` ก็มีปัญหาลักษณะเดียวกันเมื่อทดสอบจริง) ต้องตรวจสอบทุกจุดที่มีการ
  แปลงจาก COBOL decimal ไปยัง Java `double` อย่างละเอียด ไม่ใช่แค่กรณีที่ "ดูน่าสงสัย"

### แบบฝึกหัดที่ 837.1

**โจทย์**: จงอธิบายว่าทำไม `BigDecimal.valueOf(1.005)` (ไม่ใช่ constructor ตรง ๆ) ยังคงมีความเสี่ยงที่จะ
ให้ผลลัพธ์ไม่ตรงกับ COBOL ได้ ทั้งที่ `BigDecimal.valueOf()` ถือว่าปลอดภัยกว่า constructor ที่รับ
`double` ตรง ๆ

**เฉลยแนวทาง**: เพราะ `BigDecimal.valueOf(double)` ทำงานภายในโดยเรียก `Double.toString(double)` ก่อน
แล้วค่อยสร้าง `BigDecimal` จาก String นั้น ซึ่งได้ผลลัพธ์ที่ดูสมเหตุสมผลกว่า constructor ตรง ๆ มาก (เพราะ
`Double.toString()` แสดงค่าที่ "สั้นที่สุดที่ยังแยกแยะจากค่า double ข้างเคียงได้" ซึ่งมักตรงกับสิ่งที่
มนุษย์พิมพ์ไว้ตอนแรก) แต่ **ความเสี่ยงยังไม่หมดไปทั้งหมด** เพราะค่า `double` ตัวแปรต้นทาง (`amountDouble
= 1.005`) ได้ถูกปัดเป็นค่าประมาณ (`1.00499999999999989...`) ไปแล้วตั้งแต่ตอนที่ถูกกำหนดค่าเข้าตัวแปร
`double` เป็นครั้งแรก ก่อนที่ `valueOf()` จะมีโอกาสทำงานด้วยซ้ำ — ทางที่ปลอดภัยที่สุดจริง ๆ คือหลีกเลี่ยง
การให้ค่าตัวเลขการเงินผ่านตัวแปร `double` ตั้งแต่ต้นทางเลย ไม่ว่าจะที่จุดใดในกระบวนการก็ตาม (รับค่าจาก
ไฟล์/ฐานข้อมูล/ผู้ใช้เป็น String หรือ BigDecimal โดยตรงเสมอ)

## ขั้นตอนที่ 838: กลยุทธ์การทดสอบระหว่าง Migration — Parallel Run และ Golden Master

### แนวคิด

ไม่ว่าจะเลือกกลยุทธ์ใด การทดสอบระหว่าง Migration ต้องตอบคำถามเดียวกันเสมอ: **"ระบบใหม่ให้ผลลัพธ์ตรงกับ
ระบบเดิมทุกกรณีหรือไม่"** — Part นี้แนะนำ 2 เทคนิคหลักที่ใช้กันจริงในอุตสาหกรรม ซึ่ง Part 085 จะนำเทคนิค
แรกไปใช้จริงในโปรเจกต์

### เทคนิคที่ 1: Golden Master Testing

บันทึกผลลัพธ์ของระบบเดิม (เช่นจากชุดข้อมูลทดสอบที่ครอบคลุม) ไว้เป็น **"Golden Master"** (ผลลัพธ์ต้นแบบที่
ถือว่าถูกต้อง) แล้วทุกครั้งที่แก้ไขหรือ Migrate โค้ด ให้รันชุดข้อมูลเดียวกันแล้วเปรียบเทียบผลลัพธ์กับ
Golden Master ทันที หากไม่ตรงกันแม้เพียงตัวอักษรเดียว แปลว่าพฤติกรรมเปลี่ยนไปแล้ว ต้องตรวจสอบว่าเป็นการ
เปลี่ยนแปลงที่ตั้งใจหรือเป็นบั๊ก — เทคนิคนี้ตรงกับสิ่งที่ Part 083 ขั้นตอนที่ 829 เริ่มเตรียมไว้แล้ว
(บันทึกผลลัพธ์ที่คาดหวังของ `LEGACYORD` ไว้เป็นลายลักษณ์อักษร) และ Part 085 ขั้นตอนที่ 842 จะนำไปใช้เป็น
ขั้นตอนแรกของโปรเจกต์จริง

### เทคนิคที่ 2: Parallel Run Testing

รันระบบเดิมและระบบใหม่**พร้อมกัน**ด้วยข้อมูลนำเข้าจริงจากการทำงานประจำวัน (Production Data) แล้ว
เปรียบเทียบผลลัพธ์ของทั้งสองระบบอัตโนมัติ โดยที่ผลลัพธ์จากระบบใหม่**ยังไม่ถูกนำไปใช้งานจริง** (ระบบเดิม
ยังคงเป็นระบบที่ธุรกิจพึ่งพาอยู่) จนกว่าจะมั่นใจว่าทั้งสองระบบให้ผลลัพธ์ตรงกันอย่างต่อเนื่องเป็นระยะเวลา
นานพอ (เช่น รันคู่ขนานทุกวันเป็นเวลา 1-3 เดือนโดยไม่มีความแตกต่างเลย) จึงค่อยสลับไปใช้ระบบใหม่จริง

### เปรียบเทียบสองเทคนิค

| มิติ | Golden Master Testing | Parallel Run Testing |
|---|---|---|
| ข้อมูลที่ใช้ | ชุดข้อมูลทดสอบที่เตรียมไว้ล่วงหน้า | ข้อมูลจริงจาก Production |
| ความถี่ในการรัน | ทุกครั้งที่แก้โค้ด (ส่วนหนึ่งของ CI/CD, Part 078) | ต่อเนื่องเป็นระยะเวลานาน (สัปดาห์-เดือน) |
| เหมาะกับกลยุทธ์ | ทุกกลยุทธ์ (ใช้งานง่าย เริ่มได้เร็ว) | เหมาะกับ Wrap/Encapsulate เป็นพิเศษ (ทั้งสองระบบยังทำงานคู่ขนานได้) |
| ตรวจพบปัญหาประเภทใด | บั๊กจากการเขียน/แปลงโค้ดผิดพลาด | ทั้งบั๊กจากโค้ด และกรณีข้อมูลจริงที่ชุดทดสอบไม่ครอบคลุม |

### ข้อควรระวัง

- Golden Master Testing มีข้อจำกัดสำคัญคือ **ดีเท่าที่ชุดข้อมูลทดสอบครอบคลุมเท่านั้น** — หากชุดข้อมูล
  ทดสอบไม่ครอบคลุมกรณีขอบ (boundary case) บางกรณี (เช่นกรณี `OR-AMT = 5000.00` พอดีจาก Part 083 ขั้นตอน
  ที่ 827) บั๊กอาจไม่ถูกตรวจพบจนกว่าจะเจอข้อมูลจริงแบบนั้นในภายหลัง
- Parallel Run Testing ต้องระวังเรื่อง **Side Effect ที่ไม่ตั้งใจ** — ถ้าระบบใหม่ที่รันคู่ขนานไปเขียน
  ข้อมูลลงไฟล์/ฐานข้อมูลจริงโดยไม่ได้ตั้งใจ (แทนที่จะรันแบบอ่านอย่างเดียวหรือเขียนลงพื้นที่แยกต่างหาก)
  อาจทำให้ข้อมูล Production ปนเปื้อนได้

### แบบฝึกหัดที่ 838.1

**โจทย์**: จงอธิบายว่าทำไม Part 085 (โปรเจกต์ที่เลือกกลยุทธ์ Wrap/Encapsulate) จึงเหมาะที่จะใช้ Golden
Master Testing เป็นหลัก มากกว่า Parallel Run Testing แบบเต็มรูปแบบ

**เฉลยแนวทาง**: เพราะ Part 085 เป็นระบบตัวอย่างขนาดเล็กสำหรับการเรียนรู้ที่ไม่มี Production Data จริงให้
รันคู่ขนาน และเป้าหมายหลักคือสาธิตกระบวนการ Refactor+ห่อหุ้มด้วย REST API+ทดสอบอัตโนมัติให้เห็นภาพรวม
ทั้งหมดภายในเวลาจำกัด Golden Master Testing ที่รันเป็นส่วนหนึ่งของ CI Pipeline (Part 078) ให้ผลตอบรับ
เร็วกว่ามาก (รู้ผลภายในไม่กี่วินาทีทุกครั้งที่แก้โค้ด) เหมาะกับการเรียนรู้และการพัฒนาแบบวนซ้ำเร็ว ในขณะที่
Parallel Run Testing เหมาะกับระบบจริงระดับองค์กรที่มี Production Data ปริมาณมากและมีเวลาหลายเดือนสำหรับ
การเปลี่ยนผ่านอย่างระมัดระวังที่สุด

Rewrite, Transpilation, หรือ Wrap/Encapsulate) และไม่ว่าจะแปลงชนิดข้อมูลอย่างระมัดระวังแค่ไหน **ความ
มั่นใจว่าระบบใหม่ถูกต้องมาจากการทดสอบเปรียบเทียบกับพฤติกรรมเดิมเท่านั้น** ไม่ใช่จากความรู้สึก "น่าจะถูก
ต้อง" — ตัวอย่างการปัดเศษ `1.005` ในขั้นตอนที่ 837 พิสูจน์ให้เห็นแล้วว่าแม้โค้ดจะดู "ถูกต้องตามสัญชาตญาณ"
เพียงใด การทดสอบเปรียบเทียบผลลัพธ์จริงเท่านั้นที่เปิดเผยปัญหาที่ซ่อนอยู่ได้

## สรุปท้ายบท

Part 084 พาเราสำรวจภูมิทัศน์ของ **กลยุทธ์การ Migrate ระบบ COBOL** อย่างรอบด้าน ตั้งแต่ภาพใหญ่ระดับ
องค์กรไปจนถึงรายละเอียดทางเทคนิคที่พิสูจน์ได้จริงด้วยโค้ดที่คอมไพล์และรันจริงทั้งฝั่ง COBOL และ Java:

- 3 กลยุทธ์หลัก: Full Rewrite, Automated Transpilation, และ Wrap/Encapsulate (Strangler Fig) พร้อม
  ข้อดีข้อเสียและสถานการณ์ที่เหมาะสมของแต่ละแนวทาง (ขั้นตอนที่ 831-834)
- การแปล Paragraph คำนวณส่วนลด/ภาษีจาก COBOL เป็น Java แบบ side-by-side ที่คอมไพล์ รัน และให้ผลลัพธ์
  ตรงกันทุกตัวเลขจริง (ขั้นตอนที่ 835)
- ตาราง Data Type Mapping ระหว่าง COBOL (Zoned/Packed Decimal, Binary Integer) กับ Java (`BigDecimal`,
  `int`/`long`) (ขั้นตอนที่ 836)
- การพิสูจน์ปัญหาการปัดเศษที่แท้จริงด้วยค่า `1.005` ที่แสดงให้เห็นว่า `double` ให้ผลลัพธ์ผิด (`1.0`)
  ในขณะที่ COBOL และ `BigDecimal` (สร้างจาก String) ให้ผลลัพธ์ถูกต้อง (`1.01`) ตรงกัน (ขั้นตอนที่ 837)
- กลยุทธ์การทดสอบระหว่าง Migration: Golden Master Testing และ Parallel Run Testing (ขั้นตอนที่ 838)
- กรอบการประเมินความเสี่ยงเพื่อเลือกกลยุทธ์ที่เหมาะสม พร้อมตัวอย่างการให้คะแนนกับกรณีศึกษาจริง
  (ขั้นตอนที่ 839)
- สรุปเส้นทางการตัดสินใจทั้งหมด และเชื่อมโยงสู่ Part 085 (ขั้นตอนที่ 840)
