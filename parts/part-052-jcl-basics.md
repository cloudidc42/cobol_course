# Part 052: JCL เบื้องต้น: JOB, EXEC, DD Statement (ขั้นตอนที่ 511–520)

## คำนำของ Part นี้

Part 051 ได้วางรากฐานความเข้าใจเชิงแนวคิดเกี่ยวกับ Mainframe และ z/OS ไว้ครบถ้วนแล้ว รวมถึงแนวคิด
สำคัญที่สุดที่ Part นี้จะต่อยอดโดยตรง: **Batch Processing** (ขั้นตอนที่ 505) และ **Dataset Naming**
(ขั้นตอนที่ 507) — ถึงเวลาแล้วที่จะเรียนรู้ภาษาที่ใช้**สั่งงาน**ให้ z/OS รันโปรแกรม COBOL แบบ Batch
จริง ๆ นั่นคือ **JCL (Job Control Language)**

JCL ทำหน้าที่เดียวกับที่คำสั่ง `cobc -x -o program program.cob && ./program` ทำมาตลอดทั้งหลักสูตรนี้
(สั่งให้ระบบรันโปรแกรม พร้อมระบุไฟล์ที่เกี่ยวข้อง) แต่มีไวยากรณ์ รูปแบบ และรายละเอียดเฉพาะของตัวเองที่
สืบทอดมาจากยุค 1960s ผ่านการปรับปรุงมาหลายทศวรรษ

> **สิ่งสำคัญที่สุดที่ต้องเข้าใจก่อนอ่าน Part นี้**: **JCL ไม่ใช่ COBOL และไม่สามารถคอมไพล์หรือรันด้วย
> `cobc` หรือเครื่องมือใด ๆ บน Linux sandbox ของหลักสูตรนี้ได้เลย** การรัน JCL จริงต้องอาศัย z/OS จริง
> หรือ Mainframe Emulator (เช่น Hercules) เท่านั้น **ทุกตัวอย่าง JCL ในเอกสารนี้เป็นไวยากรณ์มาตรฐาน
> ตามธรรมเนียมของ IBM ที่ถูกต้องและใช้ได้จริงในโลก Mainframe จริง แต่ไม่สามารถรันทดสอบในสภาพแวดล้อม
> ของหลักสูตรนี้ได้** — บล็อกโค้ด JCL ทุกบล็อกในเอกสารนี้จะมีหมายเหตุกำกับไว้อย่างชัดเจนเพื่อไม่ให้
> เกิดความเข้าใจผิดว่าเป็นโค้ดที่ผ่านการรันทดสอบจริงเหมือนโค้ด COBOL ในเฟส 1-3

### กฎการเขียนคอลัมน์ของ JCL (คล้ายกับ Fixed-Format COBOL ที่คุ้นเคย)

JCL แบบดั้งเดิมมีกฎเรื่องตำแหน่งคอลัมน์คล้ายกับ Fixed-Format COBOL ที่เรียนมาตั้งแต่ Part 003:

| คอลัมน์ | ความหมาย |
|---|---|
| 1-2 | ต้องเป็น `//` เสมอสำหรับทุก Statement (ยกเว้น Comment ที่ใช้ `//*`) |
| 3 เป็นต้นไป | ชื่อ (Name Field) ตามด้วยช่องว่าง แล้วตามด้วย Operation (`JOB`, `EXEC`, `DD`) และ Parameter |
| ต่อบรรทัด (Continuation) | บรรทัดที่ยาวเกินต้องจบด้วยเครื่องหมายจุลภาค (`,`) แล้วบรรทัดถัดไปขึ้นต้นด้วย `//` ตามด้วยช่องว่างแล้วพิมพ์ parameter ต่อ (มักเริ่มที่คอลัมน์ 16) |
| ความยาวสูงสุดต่อบรรทัด | 80 คอลัมน์ (สืบทอดมาจากยุคบัตรเจาะรู — Punch Card — ที่ Part 001 กล่าวถึงประวัติศาสตร์ยุคแรกของวงการคอมพิวเตอร์) |

## ขั้นตอนที่ 511: JOB Statement — จุดเริ่มต้นของทุก Job

### แนวคิด

ทุก JCL ต้องเริ่มต้นด้วย **JOB Statement** เพียงหนึ่งเดียว ทำหน้าที่ระบุ **ชื่อของ Job** และค่า
พารามิเตอร์ควบคุมระดับ Job ทั้งหมด (เช่น ข้อมูลบัญชีสำหรับเรียกเก็บค่าใช้ทรัพยากร, ระดับความสำคัญ,
ผู้ที่จะได้รับแจ้งเตือนเมื่อ Job เสร็จ)

### ไวยากรณ์มาตรฐาน (ตัวอย่างอ้างอิง)

```jcl
//ARJOB01  JOB (ACCT123,DEPT99),'AR SYSTEM SETUP',
//             CLASS=A,
//             MSGCLASS=X,
//             MSGLEVEL=(1,1),
//             NOTIFY=&SYSUID
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายแต่ละส่วน

| ส่วน | ความหมาย |
|---|---|
| `ARJOB01` | ชื่อ Job (Job Name) สูงสุด 8 ตัวอักษร ต้องขึ้นต้นด้วยตัวอักษร |
| `(ACCT123,DEPT99)` | Accounting Information — ข้อมูลบัญชี/แผนกที่ใช้เรียกเก็บค่าใช้ทรัพยากร รูปแบบกำหนดโดยแต่ละองค์กร |
| `'AR SYSTEM SETUP'` | Programmer Name/Description — ข้อความอธิบาย Job (สูงสุด 20 ตัวอักษร) |
| `CLASS=A` | Job Class — กำหนดกลุ่มทรัพยากรและลำดับความสำคัญที่ JES ใช้จัดคิว |
| `MSGCLASS=X` | กำหนดว่าข้อความ Output ของ Job (SYSOUT) จะถูกส่งไปที่ output class ไหน |
| `MSGLEVEL=(1,1)` | ควบคุมว่าจะแสดงรายละเอียด JCL Statement และข้อความ Allocation ในรายงานผลมากน้อยเพียงใด |
| `NOTIFY=&SYSUID` | แจ้งเตือนผู้ใช้ (ผ่าน TSO) เมื่อ Job รันเสร็จ — `&SYSUID` คือ System Symbol แทนรหัสผู้ใช้ปัจจุบัน |

### เปรียบเทียบกับสิ่งที่คุ้นเคย

| แนวคิด JCL | เทียบเท่ากับที่คุ้นเคยจากหลักสูตรนี้ |
|---|---|
| JOB Statement | บรรทัดคำสั่ง shell ที่เรียก `cobc`/`./program` (จุดเริ่มต้นของการทำงาน) |
| CLASS | คล้ายกับ priority ของ process (เช่น `nice` บน Linux) |
| NOTIFY | คล้ายกับการรัน `command && echo "Done"` เพื่อแจ้งเตือนเมื่อเสร็จ |

### ข้อควรระวัง

- ชื่อ Job **ต้องไม่ซ้ำกับ Job อื่นที่กำลังรันอยู่ในระบบเดียวกัน** ณ ขณะนั้น มิฉะนั้น JES อาจปฏิเสธ
  หรือเกิดความสับสนในการติดตามสถานะ
- Accounting Information และรูปแบบที่ยอมรับได้**แตกต่างกันไปในแต่ละองค์กร** ต้องตรวจสอบมาตรฐานของ
  แต่ละที่ก่อนเขียน JCL จริง ตัวอย่างในเอกสารนี้เป็นรูปแบบทั่วไปเพื่อการอธิบายเท่านั้น
- ลืมเครื่องหมายจุลภาค (`,`) ท้ายบรรทัดที่ต้องการต่อบรรทัดถัดไปเป็นข้อผิดพลาดที่พบบ่อยที่สุดสำหรับ
  ผู้เริ่มต้นเขียน JCL — จะทำให้ JES ตีความ parameter ที่เหลือผิดพลาดทันที

### แบบฝึกหัดที่ 511.1

**โจทย์**: จงอธิบายว่าทำไม JOB Statement จึงต้องมีพารามิเตอร์ Accounting Information ทั้งที่ในการ
เขียนโปรแกรมด้วย GnuCOBOL ตลอดหลักสูตรนี้ไม่เคยต้องระบุข้อมูลลักษณะนี้เลย

**เฉลยแนวทาง**: Mainframe เป็นทรัพยากรที่มีต้นทุนสูงมากและมักถูกใช้ร่วมกันโดยหลายแผนก/โครงการภายใน
องค์กรเดียวกัน (ตามแนวคิด Time Sharing และ LPAR ที่เรียนมาใน Part 051) องค์กรจึงจำเป็นต้อง**ติดตามว่า
ใครใช้ทรัพยากรไปเท่าไหร่** เพื่อคิดค่าใช้จ่ายภายใน (Chargeback) หรือวิเคราะห์การใช้งานทรัพยากรอย่าง
เป็นระบบ ต่างจาก GnuCOBOL บนเครื่องส่วนตัวที่ผู้เรียนเป็นเจ้าของทรัพยากรทั้งหมดแต่เพียงผู้เดียวจึงไม่
จำเป็นต้องติดตามการใช้งานลักษณะนี้เลย

## ขั้นตอนที่ 512: EXEC Statement — ระบุโปรแกรมที่จะรัน

### แนวคิด

หลังจาก JOB Statement กำหนดค่าระดับ Job แล้ว **EXEC Statement** ทำหน้าที่ระบุว่า **จะรันโปรแกรมอะไร**
(หรือ Procedure ที่กำหนดไว้ล่วงหน้า) หนึ่ง Job อาจมีหลาย EXEC Statement (เรียกแต่ละอันว่า **Step**)
เพื่อรันโปรแกรมหลายตัวติดต่อกันเป็นลำดับ

### ไวยากรณ์มาตรฐาน (ตัวอย่างอ้างอิง)

```jcl
//STEP010  EXEC PGM=ARSETUP,
//             PARM='PROD',
//             COND=(4,LT)
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายแต่ละส่วน

| ส่วน | ความหมาย |
|---|---|
| `STEP010` | ชื่อ Step (Step Name) — สูงสุด 8 ตัวอักษร นิยมตั้งชื่อแบบมีตัวเลขเว้นระยะ (010, 020, 030) ตามธรรมเนียม Numbered Paragraph ที่คุ้นเคยจาก Part 014-015 เพื่อให้แทรก Step ใหม่ได้ง่ายในอนาคต |
| `PGM=ARSETUP` | ชื่อโปรแกรมที่จะรัน — ต้องตรงกับชื่อโปรแกรมที่คอมไพล์ไว้แล้วในรูปแบบ Load Module (เทียบเท่ากับไฟล์ executable ที่ `cobc -x` สร้างขึ้น) |
| `PARM='PROD'` | ค่าพารามิเตอร์ที่ส่งเข้าไปให้โปรแกรม COBOL รับผ่าน `LINKAGE SECTION` ของ `PROCEDURE DIVISION USING` (เชื่อมโยงกับแนวคิด parameter passing จาก Part 032) |
| `COND=(4,LT)` | เงื่อนไขการข้าม Step นี้ — ถ้า Return Code ของ Step ก่อนหน้า**น้อยกว่า (LT)** 4 ให้ข้าม Step นี้ไป (รายละเอียดเต็มรูปแบบเรื่อง Condition Code จะสอนใน Part 053) |

### การเชื่อมโยงกับ PARM และ LINKAGE SECTION

ค่าที่ส่งผ่าน `PARM=` ใน JCL จะถูกโปรแกรม COBOL รับผ่าน `LINKAGE SECTION` ตัวแรกใน
`PROCEDURE DIVISION USING` เทียบเคียงได้กับการรับพารามิเตอร์ผ่าน `CALL ... USING` ระหว่างโปรแกรม
COBOL ด้วยกันเองที่เรียนมาใน Part 031-032 — เพียงแต่คราวนี้ "ผู้เรียก" คือ JCL ไม่ใช่โปรแกรม COBOL
อีกตัวหนึ่ง

### ข้อควรระวัง

- ชื่อโปรแกรมใน `PGM=` **ต้องเป็นชื่อ Load Module ที่ถูกคอมไพล์และ Link-Edit ไว้แล้วบน z/OS** ไม่ใช่
  ชื่อไฟล์ซอร์สโค้ด `.cob` การเตรียม Load Module ต้องผ่านขั้นตอน Compile → Link-Edit ก่อนเสมอ (แนวคิด
  คล้ายกับ `cobc -x` ที่ทำทั้งสองขั้นตอนรวดเดียวให้อัตโนมัติในโลก GnuCOBOL)
- ค่าที่ส่งผ่าน `PARM=` มีข้อจำกัดความยาว (โดยทั่วไป 100 ตัวอักษร) และโปรแกรม COBOL ต้องออกแบบ
  `LINKAGE SECTION` ให้รองรับความยาวข้อมูลที่จะได้รับอย่างถูกต้อง มิฉะนั้นอาจเกิดข้อมูลไม่ครบหรือ
  ล้นฟิลด์

### แบบฝึกหัดที่ 512.1

**โจทย์**: จงเปรียบเทียบ `PARM='PROD'` ใน EXEC Statement กับเทคนิค `>>DEFINE`/`-D` ที่เรียนมาใน
Part 049 ว่ามีจุดร่วมกันอย่างไรในแง่ของการควบคุมพฤติกรรมโปรแกรมจากภายนอกโดยไม่ต้องแก้ไขซอร์สโค้ด

**เฉลยแนวทาง**: ทั้งสองเทคนิคมีเป้าหมายร่วมกันคือ**การควบคุมพฤติกรรมของโปรแกรมจากภายนอกโดยไม่ต้อง
แก้ไขซอร์สโค้ดเลย** — `-D` (Part 049) ควบคุมที่**เวลาคอมไพล์** (compile time) ผ่าน Conditional
Compilation ทำให้โค้ดบางส่วนถูกหรือไม่ถูกคอมไพล์เข้าไปเลย ในขณะที่ `PARM=` ใน JCL ควบคุมที่**เวลารัน**
(runtime) โดยส่งค่าเข้าไปให้โปรแกรมที่คอมไพล์ไว้แล้วตรวจสอบและตัดสินใจเอง (ผ่าน `LINKAGE SECTION`
และ `IF`/`EVALUATE` ปกติ) ทั้งสองวิธีล้วนสะท้อนหลักการเดียวกันคือ "แยกโค้ดโปรแกรมออกจากค่าคอนฟิกูเรชัน
เฉพาะสภาพแวดล้อม" เพียงแต่ทำที่คนละจังหวะของวงจรชีวิตซอฟต์แวร์

## ขั้นตอนที่ 513: DD Statement — เชื่อมโยงไฟล์เข้ากับโปรแกรม

### แนวคิด

**DD (Data Definition) Statement** คือหัวใจของการเชื่อมโยงไฟล์ (Dataset) เข้ากับโปรแกรม COBOL —
ทำหน้าที่เดียวกับ `SELECT ... ASSIGN TO "filename"` ใน `FILE-CONTROL` ที่เรียนมาตั้งแต่ Part 023
ทุกประการ เพียงแต่การเชื่อมโยงเกิดขึ้น**จาก JCL ภายนอก** แทนที่จะฝังชื่อไฟล์ไว้ในซอร์สโค้ดโดยตรง

### ไวยากรณ์มาตรฐาน (ตัวอย่างอ้างอิง)

```jcl
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,
//            DISP=SHR
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายแต่ละส่วน

| ส่วน | ความหมาย |
|---|---|
| `CUSTFILE` | ชื่อ DD (DDNAME) — **ต้องตรงกับชื่อที่ระบุใน `ASSIGN TO` ของโปรแกรม COBOL ทุกตัวอักษร** (ดูรายละเอียดด้านล่าง) |
| `DSN=ARSYS.CUSTOMER.DATA` | ชื่อ Dataset เต็ม (ทบทวนกฎการตั้งชื่อจาก Part 051 ขั้นตอนที่ 507) |
| `DISP=SHR` | Disposition — บอกสถานะของ Dataset นี้ (รายละเอียดเต็มรูปแบบในขั้นตอนที่ 514) |

### จุดเชื่อมโยงสำคัญที่สุด: DDNAME กับ ASSIGN TO ในโปรแกรม COBOL

นี่คือกลไกที่ทำให้โปรแกรม COBOL บน Mainframe **ไม่ผูกติดกับชื่อไฟล์จริงเลย** — โปรแกรม COBOL อ้างอิง
"สัญลักษณ์" (Symbolic Name) ผ่าน DDNAME แทนชื่อไฟล์จริง แล้วให้ JCL เป็นผู้กำหนดว่า DDNAME นั้น
ผูกกับ Dataset ตัวไหนจริง ๆ ในการรันครั้งนั้น:

```cobol
      *> COBOL source code (compiled on Mainframe, not GnuCOBOL):
           SELECT CUSTOMER-FILE ASSIGN TO CUSTFILE
               ORGANIZATION IS INDEXED
               RECORD KEY IS CUST-ID.
```

```jcl
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,DISP=SHR
```

> **ตัวอย่างทั้งสองส่วนนี้เป็นไวยากรณ์อ้างอิง ไม่สามารถคอมไพล์/รันบนสภาพแวดล้อมของหลักสูตรนี้ได้**
> ต้องใช้ COBOL Compiler บน z/OS จริงร่วมกับ JCL ที่รันบน z/OS จริงหรือ Emulator เท่านั้น

**ประโยชน์สำคัญ**: หากต้องการเปลี่ยนให้โปรแกรมเดียวกันอ่านไฟล์ทดสอบแทนไฟล์จริง เพียงแค่แก้ `DSN=`
ใน JCL เป็นชื่ออื่น **โดยไม่ต้องแก้ไขหรือคอมไพล์โปรแกรม COBOL ใหม่เลย** — นี่คือความแตกต่างสำคัญจาก
`SELECT ... ASSIGN TO "CUSTOMER.DAT"` แบบที่ใช้ตลอดหลักสูตรนี้กับ GnuCOBOL ที่ชื่อไฟล์ถูกฝังตรงในโค้ด

### ข้อควรระวัง

- **DDNAME มีข้อจำกัดความยาวสูงสุด 8 ตัวอักษร** เช่นเดียวกับ Qualifier ของ Dataset — ชื่อที่ยาวเกินไป
  จะถูกปฏิเสธตอนคอมไพล์หรือรัน
- ความไม่ตรงกันระหว่าง DDNAME ใน JCL กับชื่อที่ระบุใน `ASSIGN TO` ของโปรแกรม COBOL เป็นสาเหตุ
  ข้อผิดพลาดที่พบบ่อยที่สุดอย่างหนึ่งสำหรับ Batch Job ที่ล้มเหลว (มักได้ Abend Code เช่น `S013` ที่
  บ่งบอกปัญหาการเปิดไฟล์ — จะกล่าวถึงรายละเอียดเพิ่มเติมในขั้นตอนที่ 520)

### แบบฝึกหัดที่ 513.1

**โจทย์**: จงอธิบายว่าการที่โปรแกรม COBOL อ้างอิงไฟล์ผ่าน DDNAME (สัญลักษณ์) แทนชื่อไฟล์จริงโดยตรง
มีข้อดีอย่างไรเมื่อเทียบกับวิธี `SELECT ... ASSIGN TO "CUSTOMER.DAT"` ที่ฝังชื่อไฟล์ไว้ในโค้ดตรง ๆ
ตามที่ใช้มาตลอดหลักสูตรนี้

**เฉลยแนวทาง**: การอ้างอิงผ่าน DDNAME ทำให้โปรแกรม COBOL ตัวเดียวกัน**นำไปใช้กับ Dataset ที่แตกต่างกัน
ได้ในแต่ละครั้งที่รัน** เพียงแค่เปลี่ยน `DSN=` ใน JCL โดยไม่ต้องแก้ไขหรือคอมไพล์โปรแกรมใหม่เลย — มี
ประโยชน์มากในสถานการณ์เช่น การรันโปรแกรมเดียวกันกับข้อมูล Production ในบางวัน และข้อมูลทดสอบในบางวัน
หรือการรันโปรแกรมเดียวกันสำหรับหลายสาขา/หลายลูกค้าที่มี Dataset แยกกัน ในขณะที่วิธี `ASSIGN TO
"CUSTOMER.DAT"` ที่ฝังชื่อไฟล์ไว้ตรง ๆ ในซอร์สโค้ด (ตามที่ใช้ตลอดหลักสูตรนี้เพื่อความง่ายในการเรียนรู้)
จำเป็นต้องแก้ไขและคอมไพล์โปรแกรมใหม่ทุกครั้งที่ต้องการเปลี่ยนไฟล์ที่จะใช้งาน ซึ่งไม่สะดวกและมีความ
เสี่ยงมากกว่าในสภาพแวดล้อมองค์กรจริง

## ขั้นตอนที่ 514: DISP Parameter โดยละเอียด — สถานะของ Dataset

### แนวคิด

`DISP` (Disposition) เป็นพารามิเตอร์ที่สำคัญที่สุดตัวหนึ่งของ DD Statement บอก z/OS ว่า **Dataset นี้
มีอยู่แล้วหรือกำลังจะถูกสร้างใหม่ (สถานะปัจจุบัน)** และ **จะทำอย่างไรกับมันเมื่อ Step จบการทำงาน**
(ทั้งกรณีสำเร็จและกรณีล้มเหลว) — เทียบเคียงได้กับความแตกต่างระหว่าง `OPEN INPUT`, `OPEN OUTPUT`,
`OPEN I-O` ที่เรียนมาใน Part 025 แต่ควบคุมจากภายนอกโปรแกรมแทน

### รูปแบบเต็มของ DISP

```
DISP=(status,normal-disposition,abnormal-disposition)
```

### ตารางค่า status (สถานะปัจจุบันของ Dataset)

| ค่า | ความหมาย | เทียบเคียงกับ COBOL |
|---|---|---|
| `NEW` | สร้าง Dataset ใหม่ (ต้องยังไม่มีอยู่ก่อน) | `OPEN OUTPUT` บนไฟล์ที่ยังไม่เคยมี |
| `OLD` | เปิดใช้ Dataset ที่มีอยู่แล้ว แบบ**ครอบครองเฉพาะ (Exclusive)** ไม่ให้ Job อื่นแตะต้องพร้อมกัน | `OPEN I-O` ที่ต้องการความเป็นเจ้าของเดียว |
| `SHR` | เปิดใช้ Dataset ที่มีอยู่แล้ว แบบ**แชร์ร่วมกันได้** กับ Job อื่นที่ขอ `SHR` เช่นกัน | `OPEN INPUT` แบบอ่านอย่างเดียว |
| `MOD` | เปิดต่อท้าย (Append) ถ้ามีอยู่แล้ว หรือสร้างใหม่ถ้ายังไม่มี | คล้าย `OPEN EXTEND` จาก Part 025 |

### ตารางค่า normal/abnormal-disposition (จะทำอย่างไรเมื่อ Step จบ)

| ค่า | ความหมาย |
|---|---|
| `KEEP` | เก็บ Dataset ไว้ต่อไปหลัง Step จบ (แต่ไม่ลงทะเบียนใน Catalog หากยังไม่เคยลงทะเบียน) |
| `DELETE` | ลบ Dataset ทิ้งเมื่อ Step จบ — มักใช้กับไฟล์ชั่วคราวที่ไม่ต้องการเก็บต่อ |
| `CATLG` | เก็บไว้ต่อไป**และลงทะเบียนใน Catalog ของระบบ** ทำให้ Job/Step อื่นค้นหาเจอได้โดยไม่ต้องระบุตำแหน่งจัดเก็บ (VOLUME) เอง |
| `UNCATLG` | เก็บไว้ต่อไปแต่ลบออกจาก Catalog |

### ตัวอย่างการใช้งานจริง (ไวยากรณ์อ้างอิง)

```jcl
//NEWFILE  DD DSN=ARSYS.NEWDATA.TEST,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(10,5))
//OLDFILE  DD DSN=ARSYS.CUSTOMER.DATA,
//            DISP=SHR
//TEMPFILE DD DSN=&&TEMPDATA,
//            DISP=(NEW,DELETE,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(5,5))
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายตัวอย่าง

- `NEWFILE`: สร้างใหม่ (`NEW`) → ถ้า Step สำเร็จ ให้เก็บและลงทะเบียน Catalog (`CATLG`) → ถ้า Step
  ล้มเหลว ให้ลบทิ้ง (`DELETE`) เพราะข้อมูลอาจไม่สมบูรณ์
- `OLDFILE`: ใช้ `DISP=SHR` เพียงค่าเดียว (ไม่ระบุ normal/abnormal disposition) หมายถึงใช้ค่า
  **default ตามสถานะเดิมของ Dataset** — เหมาะกับการอ่านไฟล์ที่มีอยู่แล้วโดยไม่ต้องการเปลี่ยนสถานะมัน
- `TEMPFILE`: ใช้ `&&TEMPDATA` (เครื่องหมาย `&&` นำหน้า) หมายถึง **Temporary Dataset** ที่มีอยู่แค่
  ระหว่างการรัน Job นี้เท่านั้น (จะกล่าวถึงรายละเอียดเพิ่มเติมในขั้นตอนที่ 519) — ลบทิ้งเสมอไม่ว่า
  Step จะสำเร็จหรือล้มเหลว

### ข้อควรระวัง

- การใช้ `DISP=OLD` กับ Dataset ที่ Job อื่นกำลังใช้งานด้วย `DISP=OLD` หรือ `DISP=SHR` พร้อมกัน จะทำให้
  Job ที่มาทีหลังต้อง**รอ (Enqueue Wait)** จนกว่า Job แรกจะปล่อย Dataset นั้น — เป็นสาเหตุของปัญหา
  Job ค้างที่พบบ่อยในระบบที่มี Batch Job จำนวนมากทำงานพร้อมกัน
- ลืมระบุ abnormal disposition อาจทำให้ Dataset ที่สร้างไม่สมบูรณ์ (เพราะ Job ล้มเหลวกลางคัน) ยังคง
  ถูกเก็บไว้และลงทะเบียนใน Catalog โดยไม่ตั้งใจ สร้างความสับสนในภายหลังว่าทำไมมีข้อมูลที่ไม่ถูกต้อง
  ปะปนอยู่

### แบบฝึกหัดที่ 514.1

**โจทย์**: จงอธิบายว่าทำไม `DISP=(NEW,CATLG,DELETE)` จึงเหมาะสมกับการสร้างไฟล์ผลลัพธ์ถาวรของ
โปรแกรม แต่ `DISP=(NEW,DELETE,DELETE)` เหมาะกับไฟล์ชั่วคราวที่ใช้แค่ระหว่างการประมวลผล

**เฉลยแนวทาง**: `DISP=(NEW,CATLG,DELETE)` สื่อความหมายว่า "ถ้าโปรแกรมรันสำเร็จ ข้อมูลที่สร้างขึ้นมี
ค่าและควรเก็บไว้ใช้งานต่อ (`CATLG`) แต่ถ้าโปรแกรมล้มเหลวกลางคัน ข้อมูลที่สร้างไว้อาจไม่สมบูรณ์และไม่
ควรเก็บไว้สร้างความสับสน (`DELETE`)" ตรงกับพฤติกรรมที่ต้องการสำหรับไฟล์ผลลัพธ์ถาวร เช่น `INVOICE.DAT`
จาก Part 050 ในทางตรงข้าม `DISP=(NEW,DELETE,DELETE)` สื่อว่า "ไม่ว่าผลจะเป็นอย่างไร ไฟล์นี้ก็ไม่มี
ประโยชน์ต้องเก็บไว้ต่อ" ซึ่งเหมาะกับไฟล์ชั่วคราวที่ใช้เป็นที่พักข้อมูลระหว่าง Step ต่าง ๆ ภายใน Job
เดียวกันเท่านั้น (เช่น ผลลัพธ์กลางจากการ `SORT` ก่อนนำไปประมวลผลต่อในอีก Step หนึ่ง)

## ขั้นตอนที่ 515: การจัดสรรพื้นที่ Dataset ใหม่ — UNIT และ SPACE

### แนวคิด

เมื่อสร้าง Dataset ใหม่ (`DISP=NEW`) z/OS ต้องรู้ว่า **จะจัดเก็บไว้ที่อุปกรณ์ไหน** และ **ต้องการพื้นที่
เท่าไหร่** — ต่างจาก GnuCOBOL บน Linux ที่ไฟล์ใหม่ถูกสร้างโดยระบบปฏิบัติการจัดสรรพื้นที่ให้อัตโนมัติ
โดยผู้เขียนโปรแกรมไม่ต้องกังวลเรื่องขนาดล่วงหน้าเลย

### UNIT — ระบุประเภทอุปกรณ์จัดเก็บ

```jcl
//NEWFILE  DD DSN=ARSYS.NEWDATA.TEST,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

`SYSDA` เป็นชื่อกลุ่มอุปกรณ์ (Generic Unit Name) ที่ใช้กันแพร่หลายที่สุด หมายถึง "พื้นที่ดิสก์ทั่วไป
ที่ระบบจัดสรรให้อัตโนมัติจากกลุ่มดิสก์ที่มีพื้นที่ว่าง" — ไม่จำเป็นต้องระบุอุปกรณ์เฉพาะเจาะจง (แต่
สามารถระบุได้ในกรณีพิเศษ เช่น ต้องการเทปแม่เหล็กหรือดิสก์ประเภทเฉพาะ)

### SPACE — ระบุขนาดพื้นที่ที่ต้องการ

```
SPACE=(หน่วยวัด,(primary,secondary,directory))
```

```jcl
//NEWFILE  DD DSN=ARSYS.NEWDATA.TEST,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(10,5))
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

| ส่วน | ความหมาย |
|---|---|
| `TRK` | หน่วยวัดคือ Track (หน่วยพื้นที่ดิสก์แบบดั้งเดิมของ Mainframe) ทางเลือกอื่นได้แก่ `CYL` (Cylinder) หรือ `(blksize,(qty))` เพื่อระบุเป็นจำนวน Block |
| `10` | Primary Quantity — พื้นที่เริ่มต้นที่จัดสรรให้ทันที (10 Track) |
| `5` | Secondary Quantity — พื้นที่เพิ่มเติมที่จะขยายให้อัตโนมัติทีละ 5 Track หากพื้นที่เดิมเต็ม (Extent) |

### เปรียบเทียบกับโลกที่คุ้นเคย

| แนวคิด z/OS | เทียบเท่ากับที่คุ้นเคยจากหลักสูตรนี้ |
|---|---|
| `UNIT=SYSDA` | ระบบไฟล์ (File System) เริ่มต้นของ Linux ที่ `cobc`/GnuCOBOL เขียนไฟล์ลงไปโดยอัตโนมัติ |
| `SPACE=(TRK,(10,5))` | ไม่มีสิ่งที่เทียบเท่าโดยตรงในหลักสูตรนี้ — Linux/GnuCOBOL ให้ไฟล์ "ขยายได้อัตโนมัติ" โดยผู้ใช้ไม่ต้องกำหนดขนาดล่วงหน้าเลย |

### ข้อควรระวัง

- การกำหนด Primary Quantity น้อยเกินไปโดยไม่มี Secondary Quantity สำรอง อาจทำให้ Job ล้มเหลวกลางคัน
  ด้วยข้อผิดพลาด "พื้นที่ไม่พอ" (Out of Space, มักแสดงเป็น Abend `B37` หรือ `D37`) แม้ตรรกะโปรแกรม
  จะถูกต้องสมบูรณ์ก็ตาม — เป็นปัญหาที่ผู้เรียนที่คุ้นเคยกับ Linux/GnuCOBOL (ที่ไม่เคยเจอปัญหานี้เลย)
  มักไม่คาดคิดมาก่อน
- การจัดสรร Secondary Quantity หลายครั้งเกินไป (Dataset ขยาย Extent บ่อยเกินไป) ส่งผลเสียต่อ
  ประสิทธิภาพการอ่าน/เขียน เพราะข้อมูลอาจกระจัดกระจายไม่ต่อเนื่องกันทางกายภาพ ควรประมาณขนาด Primary
  ให้เหมาะสมกับข้อมูลจริงตั้งแต่ต้นเท่าที่ทำได้

### แบบฝึกหัดที่ 515.1

**โจทย์**: จงอธิบายว่าทำไมการที่ผู้เขียน JCL ต้องกำหนดขนาดพื้นที่ (`SPACE=`) ล่วงหน้าอย่างชัดเจน จึง
เป็นความแตกต่างสำคัญจากประสบการณ์การเขียนไฟล์ด้วย GnuCOBOL บน Linux ที่ใช้มาตลอดหลักสูตรนี้

**เฉลยแนวทาง**: บน Linux/Unix ระบบไฟล์ (เช่น ext4) จัดการพื้นที่จัดเก็บแบบไดนามิกเต็มรูปแบบ — เมื่อ
โปรแกรม `WRITE` ข้อมูลเพิ่ม ระบบปฏิบัติการจะขยายไฟล์และจัดสรรพื้นที่ดิสก์ให้อัตโนมัติโดยผู้เขียนโปรแกรม
ไม่ต้องกำหนดขนาดล่วงหน้าเลย (ตามที่สัมผัสมาตลอดการเขียนไฟล์ทุกไฟล์ในหลักสูตรนี้ตั้งแต่ Part 023)
ในขณะที่ระบบจัดเก็บดั้งเดิมของ Mainframe (ก่อนยุค SMS - Storage Management Subsystem ที่ช่วย
อัตโนมัติบางส่วน) ออกแบบมาให้ผู้ดูแลระบบ/ผู้เขียน JCL เป็นผู้ควบคุมการจัดสรรพื้นที่อย่างชัดเจนตั้งแต่
ต้น เพื่อให้การบริหารจัดการทรัพยากรดิสก์ (ซึ่งในอดีตมีราคาแพงมากและมีจำกัด) เป็นไปอย่างมีประสิทธิภาพ
และคาดเดาได้ — แม้ปัจจุบันเทคโนโลยี SMS จะช่วยให้การจัดการพื้นที่อัตโนมัติมากขึ้น แต่การเข้าใจ `SPACE=`
ยังคงเป็นความรู้พื้นฐานที่จำเป็นสำหรับโปรแกรมเมอร์ Mainframe ทุกคน

## ขั้นตอนที่ 516: SYSIN และ SYSOUT — อินพุต/เอาต์พุตมาตรฐานของ Batch Job

### แนวคิด

**SYSIN** และ **SYSOUT** คือ DDNAME พิเศษตามธรรมเนียมที่ใช้กันแพร่หลายที่สุดในโลก Mainframe เทียบเคียง
ได้กับ **stdin** และ **stdout** ที่เรียนมาใน Part 015 (การทดสอบโปรแกรมที่ใช้ `ACCEPT` ด้วย stdin
redirection) — แม้ชื่อจะคล้ายกัน แต่กลไกเบื้องหลังต่างกันโดยสิ้นเชิง

### SYSOUT — ส่งผลลัพธ์ไปยังคิวเอาต์พุตของ JES

```jcl
//SYSOUT   DD SYSOUT=*
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

`SYSOUT=*` หมายถึง "ส่งไปที่ output class เดียวกับที่กำหนดใน `MSGCLASS=` ของ JOB Statement" — ผลลัพธ์
จาก `DISPLAY` ในโปรแกรม COBOL (เทียบเท่ากับ stdout ที่คุ้นเคย) จะถูกส่งไปที่นี่ แล้วผู้ใช้ดูผ่าน
เครื่องมือติดตามสถานะ Job เช่น **SDSF (System Display and Search Facility)** ผ่าน ISPF (แทนที่จะ
เห็นทันทีบนหน้าจอ terminal เหมือนตอนรัน `./program` บน Linux)

### SYSIN — ป้อนข้อมูล Instream เข้าสู่โปรแกรม

```jcl
//SYSIN    DD *
PAYMENT001500000
PAYMENT005002000000
/*
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

`SYSIN DD *` ตามด้วยเครื่องหมายดอกจัน (`*`) หมายถึง **Instream Data** — ข้อมูลที่ตามมาถูกฝังไว้
**ภายใน JCL เอง** แทนที่จะอยู่ใน Dataset แยกต่างหาก บรรทัด `/*` บอกจุดสิ้นสุดของข้อมูล Instream

### เปรียบเทียบกับเทคนิค stdin Redirection ที่เรียนมาใน Part 015

| แนวคิด | GnuCOBOL (Part 015) | Mainframe JCL |
|---|---|---|
| การป้อนข้อมูลจากภายนอก | `printf "1\n10\n5\n" | ./program` | `SYSIN DD *` พร้อม Instream Data |
| การรับข้อมูลในโปรแกรม COBOL | `ACCEPT WS-VARIABLE` (ไม่ระบุ `FROM`) | `ACCEPT WS-VARIABLE FROM SYSIN` (ระบุชัดเจน) |
| การดูผลลัพธ์ | แสดงบน terminal ทันที | ต้องดูผ่าน SDSF/ISPF หลัง Job รันเสร็จ |

### ข้อควรระวัง

- Instream Data (`SYSIN DD *`) เหมาะกับข้อมูลจำนวนน้อยที่เกี่ยวข้องเฉพาะกับการรันครั้งนั้น ๆ สำหรับ
  ข้อมูลปริมาณมากหรือข้อมูลที่ต้องใช้ซ้ำหลายครั้ง ควรเก็บเป็น Dataset แยกต่างหากแล้วอ้างอิงด้วย `DSN=`
  ตามที่เรียนมาในขั้นตอนที่ 513-514 แทน
- ห้ามลืมบรรทัด `/*` ปิดท้าย Instream Data — หากลืม JES อาจตีความบรรทัด JCL ถัดไปเป็นส่วนหนึ่งของ
  ข้อมูล Instream อย่างผิดพลาด

### แบบฝึกหัดที่ 516.1

**โจทย์**: จงอธิบายว่าทำไมการดูผลลัพธ์จากโปรแกรม COBOL ที่รันผ่าน JCL (ต้องดูผ่าน SDSF หลัง Job
รันเสร็จ) จึงมีประสบการณ์ที่แตกต่างจากการรัน `./program` บน Linux ที่เห็นผลลัพธ์ทันทีบนหน้าจอ

**เฉลยแนวทาง**: ความแตกต่างนี้สะท้อนธรรมชาติของ Batch Processing ที่เรียนมาใน Part 051 ขั้นตอนที่
505: เมื่อ submit Job เข้าไปแล้ว Job จะเข้าคิวรอ JES จัดสรรทรัพยากรและรันตามลำดับความสำคัญ ซึ่งอาจใช้
เวลาไม่กี่วินาทีจนถึงหลายชั่วโมงขึ้นกับภาระงานของระบบ ผู้ใช้ไม่ได้ "นั่งรอ" อยู่หน้าจอเหมือนการรัน
โปรแกรมแบบ interactive บนเครื่องส่วนตัว จึงจำเป็นต้องมีเครื่องมือแยกต่างหาก (SDSF) ให้ตรวจสอบสถานะและ
ผลลัพธ์**ภายหลัง**จากที่ Job เสร็จสิ้นแล้ว ต่างจากการรัน `./program` บน Linux ที่โปรแกรมรันและแสดงผล
ทันทีในเซสชันเดียวกันกับที่ผู้ใช้เรียกคำสั่ง เพราะเป็นการประมวลผลแบบ Interactive ไม่ใช่ Batch

## ขั้นตอนที่ 517: ตัวอย่างสมบูรณ์ — รัน ARSETUP ผ่าน JCL (เชิงแนวคิด)

### แนวคิด

ขั้นตอนนี้รวบรวมทุกสิ่งที่เรียนมาจากขั้นตอนที่ 511-516 เพื่อแสดง **JCL ฉบับสมบูรณ์ที่จะใช้รันโปรแกรม
`ARSETUP` จาก Part 050 หากระบบนั้นถูกนำไป deploy บน Mainframe จริง** — นี่คือตัวอย่างที่เชื่อมโยง
โดยตรงระหว่างโปรเจกต์รวบยอดเฟส 3 กับความรู้ JCL ที่เพิ่งเรียนใหม่ในเฟส 4

### JCL ฉบับสมบูรณ์ (ไวยากรณ์อ้างอิง)

```jcl
//ARJOB01  JOB (ACCT123,DEPT99),'AR SYSTEM SETUP',
//             CLASS=A,
//             MSGCLASS=X,
//             NOTIFY=&SYSUID
//*--------------------------------------------------------------*
//* STEP010: RUN ARSETUP TO INITIALIZE CUSTOMER AND INVOICE FILES *
//*--------------------------------------------------------------*
//STEP010  EXEC PGM=ARSETUP
//STEPLIB  DD DSN=ARSYS.LOADLIB,
//            DISP=SHR
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(5,5)),
//            DCB=(RECFM=FB,LRECL=40)
//INVFILE  DD DSN=ARSYS.INVOICE.DATA,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(10,5)),
//            DCB=(RECFM=FB,LRECL=35)
//SYSOUT   DD SYSOUT=*
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายทุกส่วนของ JCL นี้

- **บรรทัดที่ขึ้นต้นด้วย `//*`**: Comment — คล้ายกับ `*>` ใน COBOL ที่เรียนมาตั้งแต่ Part 001 ใช้
  อธิบายเจตนาของโค้ดโดยไม่ส่งผลต่อการทำงาน
- **`STEPLIB DD DSN=ARSYS.LOADLIB,DISP=SHR`**: บอก z/OS ว่า Load Module ของโปรแกรม `ARSETUP` (ที่
  ผ่านการ Compile + Link-Edit แล้ว) อยู่ใน PDS/PDSE ชื่อ `ARSYS.LOADLIB` — คล้ายกับการตั้งค่า `PATH`
  environment variable บน Linux ที่บอกว่าจะหา executable ได้จากที่ไหน
- **`CUSTFILE DD ...` และ `INVFILE DD ...`**: เชื่อมโยง DDNAME (ที่ต้องตรงกับ `ASSIGN TO CUSTFILE`
  และ `ASSIGN TO INVFILE` ในซอร์สโค้ด COBOL ของ `ARSETUP`) เข้ากับ Dataset ใหม่ที่จะสร้างขึ้น พร้อม
  กำหนดขนาดพื้นที่ (`SPACE=`) ตามที่เรียนมาในขั้นตอนที่ 515
- **`DCB=(RECFM=FB,LRECL=40)`**: กำหนดคุณสมบัติของ Record — `RECFM=FB` หมายถึง Fixed-Block (ความยาว
  record คงที่ จัดกลุ่มเป็น Block เพื่อประสิทธิภาพการอ่าน/เขียน) และ `LRECL=40` หมายถึงความยาว
  record คือ 40 ไบต์ ซึ่ง**ต้องตรงกับความยาวรวมของ `CUSTOMER-RECORD`** ตาม Copybook `CUSTREC.CPY`
  จาก Part 050 (`CUST-ID` 5 + `CUST-NAME` 20 + `CUST-CREDIT-LIMIT` 9 + `CUST-BALANCE` 9 = 43 — ใน
  ตัวอย่างนี้ปัดเป็น 40 เพื่อความง่ายในการอธิบายแนวคิด ตัวเลขจริงต้องคำนวณจากขนาด record ที่แท้จริง
  ของ Copybook เสมอ)

### ข้อควรระวัง

- **`LRECL` ที่ไม่ตรงกับขนาด record จริงของโปรแกรม COBOL เป็นสาเหตุข้อผิดพลาดที่พบบ่อยมากที่สุด**
  เมื่อย้ายโปรแกรมจาก GnuCOBOL ไป Mainframe จริง — ต้องคำนวณขนาด record จาก Copybook อย่างละเอียด
  ถี่ถ้วนเสมอ (ผลรวมของทุก `PIC` clause ในระดับ 05 ของ record) ไม่ใช่เดาโดยประมาณ
- ตัวอย่างนี้เป็นเพียงการสาธิตแนวคิดการแปลงโปรแกรมจาก Part 050 ให้พร้อมสำหรับ JCL เท่านั้น การ deploy
  จริงยังต้องผ่านขั้นตอนเพิ่มเติมอีกมาก เช่น การ Compile ด้วย COBOL Compiler บน z/OS จริง (ไม่ใช่
  GnuCOBOL), การปรับ `ASSIGN TO` ให้ตรงกับ DDNAME, และการทดสอบอย่างละเอียดในสภาพแวดล้อม Mainframe
  จริงหรือ Emulator ก่อนนำไปใช้งานจริง

### แบบฝึกหัดที่ 517.1

**โจทย์**: จากโครงสร้าง `INVREC.CPY` ใน Part 050 (`INV-NUMBER PIC 9(6)`, `INV-CUST-ID PIC 9(5)`,
`INV-DATE PIC 9(8)`, `INV-AMOUNT PIC 9(7)V99`, `INV-PAID-AMOUNT PIC 9(7)V99`, `INV-STATUS PIC X(1)`)
จงคำนวณว่าค่า `LRECL` ที่ถูกต้องสำหรับ `INVFILE DD` ควรเป็นเท่าใด

**เฉลย**: คำนวณความยาวรวมของแต่ละฟิลด์: `INV-NUMBER` (6 ไบต์) + `INV-CUST-ID` (5 ไบต์) +
`INV-DATE` (8 ไบต์) + `INV-AMOUNT` (9 ไบต์ — `PIC 9(7)V99` มี 7+2 = 9 หลัก โดย `V` ไม่กินพื้นที่จริง
ตามที่เรียนมาใน Part 006) + `INV-PAID-AMOUNT` (9 ไบต์ เช่นเดียวกัน) + `INV-STATUS` (1 ไบต์) รวมทั้งหมด
`6+5+8+9+9+1 = 38` ไบต์ ดังนั้น `LRECL` ที่ถูกต้องคือ `LRECL=38` (ตัวอย่างในขั้นตอนที่ 517 ที่ใช้
`LRECL=35` เป็นเพียงตัวเลขสมมติเพื่อสาธิตไวยากรณ์ ไม่ใช่ค่าที่คำนวณจริงจาก Copybook)

## ขั้นตอนที่ 518: Multi-Step Job — เชื่อมโยง ARSETUP, ARPAYMNT, ARREPORT เข้าด้วยกัน

### แนวคิด

Part 050 ขั้นตอนที่ 499 แสดงการรัน `ARSETUP` → `ARPAYMNT` → `ARREPORT` ตามลำดับผ่านการรันคำสั่ง
shell ทีละบรรทัด บน Mainframe จริง ลำดับการรันแบบนี้จะถูกเขียนเป็น **Multi-Step Job เดียว** ที่มี
หลาย EXEC Statement ต่อเนื่องกัน — ทำให้ทั้งกระบวนการ (Setup → Payment → Report) กลายเป็น "หน่วยงาน
เดียว" ที่ Submit ครั้งเดียวแล้วรันครบทุกขั้นตอนอัตโนมัติ

### JCL Multi-Step ฉบับสมบูรณ์ (ไวยากรณ์อ้างอิง)

```jcl
//ARBATCH  JOB (ACCT123,DEPT99),'AR DAILY BATCH',
//             CLASS=A,
//             MSGCLASS=X,
//             NOTIFY=&SYSUID
//*--------------------------------------------------------------*
//* STEP010: INITIALIZE CUSTOMER AND INVOICE MASTER FILES         *
//*--------------------------------------------------------------*
//STEP010  EXEC PGM=ARSETUP
//STEPLIB  DD DSN=ARSYS.LOADLIB,DISP=SHR
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,SPACE=(TRK,(5,5)),
//            DCB=(RECFM=FB,LRECL=43)
//INVFILE  DD DSN=ARSYS.INVOICE.DATA,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,SPACE=(TRK,(10,5)),
//            DCB=(RECFM=FB,LRECL=38)
//SYSOUT   DD SYSOUT=*
//*--------------------------------------------------------------*
//* STEP020: APPLY PAYMENTS - ONLY RUNS IF STEP010 SUCCEEDED      *
//*--------------------------------------------------------------*
//STEP020  EXEC PGM=ARPAYMNT,COND=(4,LT,STEP010)
//STEPLIB  DD DSN=ARSYS.LOADLIB,DISP=SHR
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,DISP=OLD
//INVFILE  DD DSN=ARSYS.INVOICE.DATA,DISP=OLD
//PAYFILE  DD DSN=ARSYS.PAYMENTS.DAILY,DISP=SHR
//ERRLOG   DD DSN=ARSYS.PAYMENT.ERRLOG,
//            DISP=(NEW,CATLG,DELETE),
//            UNIT=SYSDA,SPACE=(TRK,(2,2)),
//            DCB=(RECFM=FB,LRECL=60)
//SYSOUT   DD SYSOUT=*
//*--------------------------------------------------------------*
//* STEP030: GENERATE AGING REPORT - ONLY RUNS IF STEP020 OK      *
//*--------------------------------------------------------------*
//STEP030  EXEC PGM=ARREPORT,COND=(4,LT,STEP020)
//STEPLIB  DD DSN=ARSYS.LOADLIB,DISP=SHR
//CUSTFILE DD DSN=ARSYS.CUSTOMER.DATA,DISP=SHR
//INVFILE  DD DSN=ARSYS.INVOICE.DATA,DISP=SHR
//REPTOUT  DD SYSOUT=*
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

### อธิบายจุดสำคัญ

- **`COND=(4,LT,STEP010)`** ใน `STEP020`: หมายถึง "ข้าม Step นี้ถ้า Return Code ของ `STEP010` **น้อย
  กว่า (LT)** 4" — เขียนแบบนี้ดูสวนทางความรู้สึก (เพราะปกติเราอยากให้ Step ก่อนหน้า "สำเร็จ" ถึงจะรัน
  ต่อ) แต่นี่คือไวยากรณ์มาตรฐานของ `COND=` ที่ระบุ **เงื่อนไขการข้าม (skip)** ไม่ใช่เงื่อนไขการรันต่อ
  — รายละเอียดและความสับสนที่พบบ่อยเรื่องนี้จะอธิบายละเอียดเต็มรูปแบบใน Part 053
- สังเกตว่า `STEP010` ใช้ `DISP=(NEW,...)` สำหรับ `CUSTFILE`/`INVFILE` (สร้างใหม่) แต่ `STEP020`
  เปลี่ยนเป็น `DISP=OLD` (เปิดไฟล์ที่เพิ่งสร้างในขั้นก่อนหน้า แบบครอบครองเฉพาะเพื่อ `REWRITE` ได้) และ
  `STEP030` เปลี่ยนเป็น `DISP=SHR` (อ่านอย่างเดียวสำหรับสร้างรายงาน ไม่ต้องครอบครองเฉพาะ) — นี่คือ
  ตัวอย่างการเลือกใช้ค่า `DISP` ที่**สอดคล้องกับพฤติกรรมจริงของแต่ละโปรแกรม** (`ARSETUP` เขียนใหม่,
  `ARPAYMNT` แก้ไข, `ARREPORT` แค่อ่าน) ตามที่ออกแบบไว้ใน Part 050
- ทั้ง 3 Step ใช้ Dataset ชื่อเดียวกัน (`ARSYS.CUSTOMER.DATA`, `ARSYS.INVOICE.DATA`) ที่**คงอยู่ต่อ
  เนื่องข้าม Step** ภายใน Job เดียวกัน — ตรงกับแนวคิด "persistent shared state" ที่ Part 050 ขั้นตอน
  ที่ 494 อธิบายไว้ เพียงแต่คราวนี้การส่งต่อสถานะเกิดขึ้น**ภายใน Job เดียวที่ประกาศ DSN เดียวกันซ้ำ
  ในแต่ละ Step** แทนที่จะเป็นการรันโปรแกรม shell แยกกันคนละคำสั่ง

### ข้อควรระวัง

- การใช้ `DISP=OLD` ใน `STEP020` หมายความว่า **ไม่มี Step อื่นใน Job อื่นสามารถเข้าถึง Dataset นี้
  พร้อมกันได้เลยระหว่างที่ `STEP020` กำลังรันอยู่** (ตามที่เรียนมาในขั้นตอนที่ 514) ควรพิจารณาผลกระทบ
  นี้เมื่อออกแบบ Job ที่ต้องรันพร้อมกับ Job อื่นที่อาจต้องการเข้าถึง Dataset เดียวกัน
- หาก `STEP010` ล้มเหลว (Return Code สูงกว่า 4) `STEP020` และ `STEP030` จะถูกข้ามไปเนื่องจากเงื่อนไข
  `COND=` (และเนื่องจาก `STEP030` มีเงื่อนไขอ้างอิงจาก `STEP020` การข้าม `STEP020` ก็ไม่ได้หมายความว่า
  `STEP030` จะถูกข้ามโดยอัตโนมัติเสมอไป ขึ้นอยู่กับรายละเอียดการตั้งค่า COND ที่ซับซ้อนกว่านี้ — จะ
  อธิบายอย่างละเอียดใน Part 053)

### แบบฝึกหัดที่ 518.1

**โจทย์**: จงอธิบายว่าทำไมการรวม `ARSETUP`, `ARPAYMNT`, `ARREPORT` เป็น Job เดียวที่มี 3 Step (แทนที่
จะ Submit เป็น 3 Job แยกกัน) จึงเหมาะสมกับการดำเนินธุรกิจแบบ "Daily Batch" ที่ต้องรันทุกวัน

**เฉลยแนวทาง**: การรวมเป็น Job เดียวทำให้ทั้งกระบวนการ (Setup/Update → Payment Processing → Report
Generation) ถูกมองเป็น**หน่วยงานเดียวที่มีความสัมพันธ์กันชัดเจน** ผ่านกลไก `COND=` ที่ทำให้ Step
ถัดไปรันต่อก็ต่อเมื่อ Step ก่อนหน้าสำเร็จเท่านั้น (ป้องกันไม่ให้ `ARREPORT` สร้างรายงานจากข้อมูลที่
ยังไม่ได้ปรับปรุงด้วย `ARPAYMNT` เพราะ Step นั้นล้มเหลว) หากแยกเป็น 3 Job อิสระ ผู้ดูแลระบบ/Job
Scheduler ต้องจัดการเงื่อนไขการรันต่อเนื่องเอง (เช่น ตั้งเวลาให้ Job ที่สองรันหลัง Job แรกเสมอ โดยไม่มี
การตรวจสอบผลลัพธ์ของ Job แรกโดยอัตโนมัติ) ซึ่งเสี่ยงต่อการที่ Job ที่สองรันไปแม้ Job แรกจะล้มเหลว
ทำให้ได้ผลลัพธ์ที่ผิดพลาดโดยไม่มีใครรู้ทันที การรวมเป็น Job เดียวจึงปลอดภัยและควบคุมได้ง่ายกว่าสำหรับ
กระบวนการที่มีความสัมพันธ์แบบต่อเนื่องกันชัดเจนแบบนี้

## ขั้นตอนที่ 519: Temporary Dataset และเทคนิคขั้นสูงของ DD Statement

### Temporary Dataset — ข้อมูลที่มีชีวิตอยู่แค่ระหว่าง Job

Part 050 มีตัวอย่างการใช้ไฟล์ log ชั่วคราวและไฟล์ error log ที่ใช้แค่ตรวจสอบระหว่างการพัฒนา — บน
Mainframe แนวคิดนี้ตรงกับ **Temporary Dataset** ที่ใช้ชื่อขึ้นต้นด้วย `&&`:

```jcl
//SORTWORK DD DSN=&&SORTTEMP,
//            DISP=(NEW,DELETE,DELETE),
//            UNIT=SYSDA,
//            SPACE=(TRK,(5,5))
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

Temporary Dataset (`&&SORTTEMP`) มีคุณสมบัติพิเศษ:
- **มีอยู่เฉพาะระหว่างที่ Job กำลังรันเท่านั้น** — ถูกลบทิ้งอัตโนมัติเมื่อ Job จบ ไม่ว่าจะกำหนด
  disposition อย่างไรก็ตาม (จึงมักเห็น `DISP=(NEW,DELETE,DELETE)` กำกับไว้เพื่อความชัดเจน แม้จะ
  ถูกลบอัตโนมัติอยู่แล้ว)
- **สามารถส่งต่อระหว่าง Step ภายใน Job เดียวกันได้** เหมือน Dataset ถาวรทุกประการ เพียงแต่ไม่ต้อง
  กังวลเรื่องการลบทิ้งหรือชื่อไปชนกับ Dataset อื่นในระบบ
- ไม่ต้องผ่านกระบวนการลงทะเบียน Catalog ใด ๆ ทำให้จัดการง่ายกว่า Dataset ถาวร

### DUMMY — DD Statement ที่ไม่มีข้อมูลจริง

```jcl
//ERRLOG   DD DUMMY
```

> **ตัวอย่างนี้เป็นไวยากรณ์ JCL มาตรฐาน ไม่สามารถรันบนสภาพแวดล้อมนี้ได้ ต้องใช้ z/OS จริงหรือ
> Mainframe Emulator (เช่น Hercules)**

`DD DUMMY` บอกว่า DDNAME นี้**มีอยู่จริงในทางเทคนิค** (โปรแกรมเปิดมันได้โดยไม่ error) **แต่ไม่มีข้อมูล
จริงอยู่เบื้องหลัง** — การ `WRITE` ไปยังไฟล์นี้จะถูก "ทิ้ง" ไปเฉย ๆ ไม่มีที่เก็บจริง มีประโยชน์มาก
สำหรับการทดสอบโปรแกรมที่ไม่ต้องการให้เขียน log จริงชั่วคราว โดยไม่ต้องแก้ไขโปรแกรม COBOL เลย

### เปรียบเทียบกับสิ่งที่คุ้นเคยจาก Linux

| แนวคิด z/OS | เทียบเท่ากับที่คุ้นเคยจาก Linux |
|---|---|
| Temporary Dataset (`&&NAME`) | ไฟล์ใน `/tmp/` ที่ลบทิ้งเมื่อรีสตาร์ทเครื่อง (แนวคิดคล้ายกันแต่ระดับ "การมีอยู่" ต่างกัน) |
| `DD DUMMY` | การ redirect ไปยัง `/dev/null` เช่น `./program > /dev/null` |

### ข้อควรระวัง

- Temporary Dataset ที่ชื่อซ้ำกัน (`&&SORTTEMP`) ในหลาย Step ของ Job เดียวกัน **จะอ้างอิงถึง Dataset
  เดียวกัน** (ส่งต่อข้อมูลระหว่าง Step ได้) แต่ถ้าอยู่คนละ Job กัน แต่ละ Job จะได้ Temporary Dataset
  ของตัวเองแยกกันเสมอ แม้จะตั้งชื่อเหมือนกันก็ตาม
- `DD DUMMY` ทำให้การทดสอบดูเหมือนโปรแกรมทำงาน "สำเร็จ" ได้ทั้งที่ไม่มีข้อมูลถูกเขียนจริง ต้องระวัง
  ไม่ให้หลงเหลือ `DUMMY` ไว้ในการรัน Production จริงโดยไม่ตั้งใจ (เช่น ลืมเปลี่ยนกลับจากการทดสอบ)

### แบบฝึกหัดที่ 519.1

**โจทย์**: จงเปรียบเทียบ `DD DUMMY` กับเทคนิคการ redirect output ไปยัง `/dev/null` บน Linux
(`command > /dev/null`) ว่ามีจุดร่วมและจุดต่างกันอย่างไร

**เฉลยแนวทาง**: จุดร่วมคือทั้งสองเทคนิคทำให้ output ที่โปรแกรมพยายามเขียน**หายไปโดยไม่มีข้อผิดพลาด**
(โปรแกรมยังคงทำงานสำเร็จตามปกติ ไม่ crash) มีประโยชน์เมื่อไม่สนใจผลลัพธ์ส่วนนั้นจริง ๆ จุดต่างสำคัญคือ
`DD DUMMY` ทำงานที่ **ระดับ Dataset Allocation ของ JCL** (ก่อนที่โปรแกรมจะเริ่มรันด้วยซ้ำ z/OS "จำลอง"
การมีอยู่ของไฟล์นั้นให้โปรแกรมเข้าใจว่าเปิดได้ปกติ) ในขณะที่ `> /dev/null` บน Linux ทำงานที่ **ระดับ
Shell** โดยเชื่อมต่อ File Descriptor ของโปรแกรมเข้ากับอุปกรณ์พิเศษ `/dev/null` ที่ระบบปฏิบัติการ
จัดเตรียมไว้ให้ "รับข้อมูลได้ไม่จำกัดแต่ไม่เก็บอะไรไว้เลย" — เป็นกลไกที่ต่างกันในรายละเอียดทางเทคนิค
แต่ให้ผลลัพธ์ในเชิงปฏิบัติที่คล้ายคลึงกันมาก

## ขั้นตอนที่ 520: ข้อผิดพลาดที่พบบ่อยใน JCL และการเตรียมพร้อมสำหรับ Part 053

### ข้อผิดพลาดที่พบบ่อยที่สุดสำหรับผู้เริ่มต้นเขียน JCL

| อาการ | สาเหตุที่พบบ่อย |
|---|---|
| JCL ถูกปฏิเสธทันที (JCL ERROR) ไม่ทันได้รันโปรแกรมเลย | ลืมเครื่องหมายจุลภาคท้ายบรรทัดต่อเนื่อง, ชื่อ DDNAME ยาวเกิน 8 ตัวอักษร, ลำดับ parameter ผิด |
| Abend `S013` | ปัญหาการเปิด Dataset — DDNAME ไม่ตรงกับที่โปรแกรมคาดหวัง, Dataset ไม่มีอยู่จริงทั้งที่ใช้ `DISP=SHR`/`OLD` |
| Abend `S0C7` | ข้อมูลตัวเลขไม่ถูกต้อง (non-numeric data ในฟิลด์ที่ประกาศเป็นตัวเลข) — มักเกิดจาก `LRECL` ไม่ตรงกับ record จริง ทำให้อ่านข้อมูลผิดตำแหน่ง |
| Abend `B37`/`D37` | พื้นที่ไม่เพียงพอ (`SPACE=` ที่กำหนดไว้น้อยเกินไป ตามที่เรียนในขั้นตอนที่ 515) |
| Job ค้างไม่รันสักที (สถานะ "waiting") | Dataset ที่ต้องการถูก Job อื่นครอบครองด้วย `DISP=OLD` อยู่ (Enqueue Wait ตามที่เรียนในขั้นตอนที่ 514) |

### แนวทางการตรวจสอบ JCL เบื้องต้นก่อน Submit

แม้ในสภาพแวดล้อมนี้จะไม่สามารถ Submit JCL จริงได้ แต่หลักการตรวจสอบพื้นฐานที่ควรฝึกเป็นนิสัยคือ:

1. **ตรวจสอบ DDNAME ทุกตัวให้ตรงกับ `ASSIGN TO` ในโปรแกรม COBOL ทุกตัวอักษร** (case-insensitive
   ตามธรรมเนียม COBOL แต่ต้องสะกดตรงกัน)
2. **คำนวณ `LRECL` จาก Copybook อย่างละเอียด** ทุกครั้งที่มีการแก้ไขโครงสร้าง record (ตามที่ฝึกใน
   แบบฝึกหัดที่ 517.1)
3. **ตรวจสอบเครื่องหมายจุลภาคท้ายบรรทัดทุกบรรทัดที่ต่อเนื่อง** ให้ครบถ้วน
4. **ตรวจสอบว่า `DISP=` ของแต่ละ DD สอดคล้องกับพฤติกรรมจริงของโปรแกรม** (สร้างใหม่ vs อ่านอย่างเดียว
   vs แก้ไข) ตามที่แสดงในขั้นตอนที่ 518

### เตรียมความพร้อมสำหรับ Part 053

Part นี้ให้พื้นฐาน JCL ที่จำเป็น (JOB, EXEC, DD) ครบถ้วนแล้ว Part 053 จะขยายความลึกขึ้นไปอีกในสอง
เรื่องสำคัญที่ถูกแตะไว้เพียงผิวเผินใน Part นี้:

1. **JCL Procedures (PROC)** — การเก็บชุด Step ที่ใช้ซ้ำบ่อย ๆ (เช่น STEPLIB + SYSOUT มาตรฐาน) ไว้
   เป็น Procedure เดียว แล้วเรียกใช้ซ้ำในหลาย Job โดยไม่ต้องเขียนซ้ำทุกครั้ง (เทียบเคียงได้กับแนวคิด
   Copybook จาก Part 033 แต่ใช้กับ JCL แทน COBOL)
2. **Condition Code โดยละเอียด** — กลไก `COND=` ที่แนะนำผิวเผินในขั้นตอนที่ 512 และ 518 จะถูกอธิบาย
   อย่างละเอียดครบถ้วน รวมถึงทางเลือกที่ทันสมัยกว่าอย่าง `IF/THEN/ELSE/ENDIF` ใน JCL ที่ IBM เพิ่มเข้า
   มาในภายหลังเพื่อแก้ปัญหาความสับสนของ `COND=` แบบดั้งเดิม

### ข้อควรระวัง

- Abend Code ที่แสดงในตารางข้างต้น (`S013`, `S0C7`, `B37`, `D37`) เป็นเพียงตัวอย่างที่พบบ่อยที่สุด
  เท่านั้น ระบบ z/OS มี Abend Code อีกจำนวนมากที่มีความหมายเฉพาะเจาะจงต่างกัน ผู้ที่ทำงานกับ Mainframe
  จริงควรมีคู่มืออ้างอิง Abend Code ของ IBM ติดตัวไว้เสมอ (หรือระบบค้นหาภายในองค์กร)
- การ "ตรวจสอบ JCL เบื้องต้นก่อน Submit" ในเอกสารนี้เป็นเพียงหลักการทั่วไป — องค์กรจริงมักมีเครื่องมือ
  ตรวจสอบ Syntax ของ JCL อัตโนมัติ (JCL Syntax Checker) ในสภาพแวดล้อม TSO/ISPF ที่ควรใช้ก่อน Submit
  จริงเสมอ เพื่อจับข้อผิดพลาดพื้นฐานก่อนที่จะเสียเวลาคิวรอ JES จริง

### แบบฝึกหัดที่ 520.1

**โจทย์**: จงจับคู่ Abend Code ทั้ง 4 ตัวในตารางข้างต้น (`S013`, `S0C7`, `B37`, `D37`) เข้ากับ
แนวคิด COBOL/JCL ที่เรียนมาตลอด Part 052 นี้ว่าแต่ละตัวเกี่ยวข้องกับหัวข้อใดมากที่สุด

**เฉลย**:
- `S013` (ปัญหาเปิด Dataset) → เกี่ยวข้องกับขั้นตอนที่ 513 (DD Statement และความสัมพันธ์ DDNAME กับ
  `ASSIGN TO`)
- `S0C7` (ข้อมูลตัวเลขไม่ถูกต้องจาก LRECL ผิด) → เกี่ยวข้องกับขั้นตอนที่ 517 (การคำนวณ `LRECL` จาก
  ขนาด record ของ Copybook)
- `B37`/`D37` (พื้นที่ไม่เพียงพอ) → เกี่ยวข้องกับขั้นตอนที่ 515 (การกำหนด `SPACE=` สำหรับ Dataset ใหม่)

การจับคู่นี้แสดงให้เห็นว่าแต่ละหัวข้อที่เรียนมาตลอด Part นี้ล้วนเชื่อมโยงกับปัญหาจริงที่พบได้บ่อยใน
การทำงานกับ JCL ไม่ใช่เพียงความรู้เชิงทฤษฎีที่แยกขาดจากการใช้งานจริง

## สรุปท้ายบท

Part นี้พาคุณเรียนรู้ไวยากรณ์พื้นฐานของ **JCL (Job Control Language)** ซึ่งเป็นกลไกที่ z/OS ใช้สั่งงาน
ให้รันโปรแกรม COBOL แบบ Batch ครอบคลุม:

- **JOB Statement** — จุดเริ่มต้นของทุก Job พร้อม Accounting Information, CLASS, MSGCLASS, NOTIFY
- **EXEC Statement** — ระบุโปรแกรมที่จะรัน (`PGM=`), การส่งพารามิเตอร์ (`PARM=`) ที่เชื่อมโยงกับ
  `LINKAGE SECTION` จาก Part 031-032
- **DD Statement** — การเชื่อมโยงไฟล์เข้ากับโปรแกรมผ่าน DDNAME ที่ต้องตรงกับ `ASSIGN TO` ในซอร์สโค้ด
  COBOL ทุกตัวอักษร
- **DISP Parameter** — สถานะของ Dataset (`NEW`/`OLD`/`SHR`/`MOD`) และการจัดการเมื่อ Step จบ
  (`KEEP`/`DELETE`/`CATLG`/`UNCATLG`)
- **UNIT และ SPACE** — การจัดสรรพื้นที่จัดเก็บสำหรับ Dataset ใหม่ ต่างจากประสบการณ์ GnuCOBOL/Linux
  ที่ไม่ต้องกำหนดขนาดล่วงหน้าเลย
- **SYSIN/SYSOUT** — อินพุต/เอาต์พุตมาตรฐานของ Batch Job เทียบเคียงกับเทคนิค stdin redirection จาก
  Part 015
- ตัวอย่าง JCL ฉบับสมบูรณ์ที่เชื่อมโยงโดยตรงกับโปรเจกต์ระบบบัญชีลูกหนี้จาก Part 050 (การรัน `ARSETUP`,
  `ARPAYMNT`, `ARREPORT` ผ่าน Multi-Step Job เดียว)
- **Temporary Dataset** (`&&name`) และ **DD DUMMY** สำหรับข้อมูลชั่วคราวและการทดสอบ
- ข้อผิดพลาด JCL ที่พบบ่อยที่สุด (Abend Code `S013`, `S0C7`, `B37`/`D37`) พร้อมความเชื่อมโยงกับแนวคิด
  ที่เรียนมาตลอด Part นี้

ทุกตัวอย่าง JCL ใน Part นี้เป็น**ไวยากรณ์มาตรฐานอ้างอิง** ที่ถูกต้องตามธรรมเนียมของ IBM แต่**ไม่สามารถ
รันทดสอบได้ในสภาพแวดล้อมของหลักสูตรนี้** ตามที่ได้ระบุไว้อย่างชัดเจนตั้งแต่ต้น — ความเข้าใจไวยากรณ์
เหล่านี้จะเป็นพื้นฐานสำคัญที่ทำให้ Part 053 (JCL ขั้นสูง: Procedures และ Condition Codes) ต่อยอดได้
อย่างราบรื่น รวมถึงเป็นพื้นฐานที่จำเป็นก่อนเรียน VSAM, DB2, และ CICS ในลำดับถัดไปของเฟส 4
